# Space Invaders — how the machine works

This map describes the parts of Space Invaders (Intel 8080, Midway `mw8080bw` board) whose behaviour is
described here. It is a **current-state** description of the machine, not a history
of the port. Every claim is tagged with the confidence of its reading:

- **[seen]** — a role confirmed by a MAME observation.
- **[code]** — a role read from the routine bodies; MAME grounding still open. The per-item tag lives in
  names.js (a cell's inline `// [seen]`/`// [code]`, a routine's `cert`).
- **[guess]** — an unclear reading; these keep a `loc_<addr>` placeholder rather than a descriptive name.

What is described here spans the machine's **helper routines** — the primitives the game's spine calls to touch
video, sound, the alien field, the player shot and shields, the per-player records, scoring, and the frame
timers — and the control-flow spine itself: the interrupt bodies, the attract cycle, the object-table handlers,
and the in-game main loop and round restarts, all described below. The object-table **dispatcher** `walkObjectTable` —
the walker the interrupt bodies call to run the handlers — reads each record's handler address and calls it.
A routine named `loc_<addr>` anywhere below keeps a placeholder name because its game-role or naming is not yet
settled; its mechanism may already be read at [code].

## Video RAM and the framebuffer

The framebuffer occupies a fixed span of memory that begins at VIDEO_RAM_BASE (0x2400) and runs up to, but not including, VIDEO_RAM_END (0x4000) [seen]. clearScreen walks a pointer from the base, stores zero at every address, and stops once the pointer's high byte reaches 0x40, blanking the whole 0x2400-0x3fff window in a single pass [seen]. That window is 0x1c00 bytes, and the drawing code treats it as a grid of 32-byte columns: consecutive addresses step through one column, while adding 0x20 crosses into the neighbouring one, so the full width spans 0xe0 (224) columns of 0x20 bytes each [code]. Each byte packs eight pixels -- the coordinate mapping below divides a pixel position by eight to reach a byte, which is what fixes the eight-pixels-per-byte packing [code].

Two clears coexist because not all of the framebuffer is playfield. clearScreen erases everything, including the fixed heads-up margins [seen]. clearPlayfield instead starts at PLAYFIELD_VRAM_BASE (0x2402) and, as it walks each 32-byte column, steps over a six-byte margin: it writes bytes up through offset 0x1b, and once the low five bits of the pointer reach 0x1c it jumps forward six bytes -- landing on offset 0x02 of the next column -- and repeats until the high byte reaches 0x40 [seen]. The effect is to leave the two lowest bytes and four highest bytes of every column untouched -- the bottom status strip and the top score band -- while erasing the playfield between them [seen]. PLAYFIELD_VRAM_BASE is exactly VIDEO_RAM_BASE displaced by that two-byte bottom margin [seen].

At the foot of that preserved margin sits the ground line. drawBottomLine paints it by filling the lit byte 0x01 into offset 0x02 of all 0xe0 columns, one column-step (0x20) apart, starting at PLAYFIELD_VRAM_BASE -- a one-pixel line spanning the full screen width, laid down into the very region clearPlayfield refuses to touch [seen].

drawBottomLine and the strip clears all funnel through a single fill primitive. fillScreenRow takes a byte value, a pass count, and a start address, then repeatedly stores the value and advances the pointer by 0x20, finally leaving that pointer one stride past the end [seen]. clearScreenStrip is its zero-fill front door: it forces the value to zero and drops into the same loop, blanking a run of columns from a given address [seen]. Wider blanks compose from that strip. clearScreenRegion repeatedly clears 0x10-column strips, advancing 0x200 (one strip's worth) each pass, until the strip base's high byte reaches the terminator 0x35 -- used to wipe the reserve-life icon band before it is redrawn [seen]. blankScreenStrip clears a fixed 0x20-column strip anchored at loc_391c, but only in one-player mode: it first reads the mode-guard cell TWO_PLAYER_GAME (0x20ce) and returns without disturbing the screen when it is nonzero [seen]. loc_391c is a specific framebuffer address serving as that strip's origin; its precise role is not yet recovered, so it keeps its loc_ name [guess].

Sprites and other positioned graphics reach the framebuffer through a coordinate mapping. coordToScreenAddr takes a packed coordinate in HL, shifts it right by three -- dividing by eight to turn a pixel position into a byte position -- then forces the high byte into the 0x20-0x3f range so the result always lands inside the video window [seen]. The three low bits discarded by that shift are the sub-byte pixel offset, and they are not thrown away: seatBlitPosition captures them first, writing L's low three bits to output port 0x02 -- the bit-shifter's alignment offset -- before folding HL into a screen address through the same coordinate mapping [seen]. Between them they seat a blit, with the shift offset choosing which of the eight pixels within a byte a sprite starts on and the byte address choosing the column; the sprite-drawing routines all position themselves this way [code].

Bulk moves in and out of the framebuffer rest on two copy routines. blockCopy is the general byte mover: it copies B bytes from the source pointer (DE) to the destination (HL) with both advancing, treating a count of zero as a full 256 [seen]. It is the workhorse behind record, template, and work-buffer copies as well as shield-buffer setup, and is not specific to video memory [seen]. captureScreenRect is the rectangular mover: for each of B rows it copies C contiguous bytes and then advances the source base by 0x20 to the next column, gathering a B-column by C-byte rectangle of the screen into a contiguous byte stream [seen]. The shield save/restore drives it exactly that way -- capturing four stacked 0x16-by-0x02 blocks, and stepping DRAW_BLOCK_STRIDE (0x02e0) between successive block origins while a counterpart routine paints the stored rectangles back [seen]. That stride works out to 0x17 columns, the spacing between the four shields [seen].

## Sprite drawing

Space Invaders paints everything on the field -- aliens, shots, shields, score digits, the running text lines -- through one small library of column blitters, and they all share the same picture of the framebuffer: video memory is walked one screen row at a time by adding 0x20 to the destination pointer, so what the code calls a "column" is a vertical strip laid down the display. The routines fall into two families. One copies byte-aligned graphics straight into memory; the other pushes each source byte through the hardware bit shifter so a sprite can land at any pixel position rather than only on an eight-pixel boundary.

The plainest member is `drawSpriteColumn` (0x1439): over B rows it copies one source byte from DE into the screen at HL, bumps DE, and advances HL by 0x20 to the next row, returning HL sitting 0x20*B past where it began [seen]. A row count of zero wraps to a full 256-row pass [seen]. `drawSpriteColumn16` (0x1844) is just this with the count pinned to 0x10, preserving the caller's BC across the draw [seen]. `drawSprite8x8` (0x08ff) is the glyph plotter built on top: it treats A as a sprite id, resolves its eight source bytes at an eight-byte-per-entry table based at `loc_1e00` [seen] (the cell itself is still open, `loc_1e00` [guess]), writes A to port 0x06 [seen], and hands an eight-row copy to `drawSpriteColumn` -- so a glyph is one byte wide by eight rows, and the call leaves HL advanced one glyph-cell down the screen [seen].

That advance is what strings glyphs into text. `drawSpriteList` (0x08f3) walks C consecutive sprite ids starting at DE, drawing each through `drawSprite8x8` and letting the returned HL carry down to the next id, so a run renders as a line [seen]; `drawThreeSprites` (0x08f1) is the same driver with the count seeded to three [seen]. The game's fixed text lives on this path. Numbers ride it too: `drawDigit` (0x09c5) adds 0x1a to A to reach a glyph id and plots it via `drawSprite8x8` [seen], and `drawBcdByte` (0x09b2) draws a byte as two glyphs, high nibble first and then low [seen].

For graphics wider than a single byte that must merge over what is already on screen, `orBlitBitmap` (0x1a69) runs a two-dimensional OR-blit: an outer loop over B rows, an inner loop OR-ing C source bytes across into consecutive destination bytes, then the destination pointer reset to the row start plus 0x20 for the next row while the source runs straight through [seen]. This is how the shields are stamped down without wiping the background beneath them.

The shifted family exists because a sprite's horizontal position is a pixel coordinate, not a byte address. Each shifted blitter first seats itself through `seatBlitPosition` (0x1474), which sends L's low three bits to port 0x02 as the shift amount and then folds HL into a screen address via `coordToScreenAddr` (0x1a47) -- shifting the coordinate right by three (eight pixels per byte) and forcing the high byte into the 0x2000-0x3fff video window [seen]. With the offset seated, a source byte is fed to the shifter by writing it to port 0x04 and reading the shifted result back from port 0x03; writing a byte and then a zero yields the two overlapping halves a shifted sprite occupies, which land in two adjacent screen bytes (HL and HL+1) before the pointer steps down 0x20 to the next row [code].

The four shifted blitters differ only in how they combine those halves with the screen. `blitShiftedSprite` (0x15d3) overwrites, storing both halves straight in [seen]. `orBlitShiftedSprite` (0x1400) ORs each half into what is there, preserving the background [seen]. `eraseShiftedSprite` (0x1452) does the inverse -- it complements the shifted byte and ANDs it into the screen, clearing exactly the bits the sprite would have set [seen]. `drawSpriteWithCollision` (0x1491) is the OR blit with a test woven in: it clears `COLLISION_FLAG` (0x2061) to zero at the start [seen], and on each half ANDs the incoming shifted bits against the screen before OR-ing them in, so any overlap (a nonzero AND on either half) latches `COLLISION_FLAG` to 1 [seen]. That is the hit test the game reads after drawing a shot -- `drawAlienShotWithCollision` seats the alien-shot descriptor and drops straight into it. `clearSpriteColumn` (0x1424) reuses the same seat step but simply zeros the two-byte-wide footprint over B rows [seen], used to wipe a sprite when a shot's alien-explosion despawns.

Two feeders drive the blitters from data streams. `fetchNextDrawRecord` (0x1856) reads a four-byte record through the BC cursor: a leading 0xff is the terminator and returns with carry set and BC left parked; otherwise it unpacks two little-endian words -- a screen address into HL and a graphics pointer into DE -- steps BC past all four bytes, and clears carry [seen]. A draw-sequence walker pairs this with `drawSpriteColumn16`, pulling record after record and blitting each as a sixteen-row column until the terminator flags carry and stops the loop.

`stepAnimationFrame` (0x1868) advances one frame of a scripted animation held in a small block of state. It bumps a frame counter at `loc_20c2` [seen] (the cell itself is still open, `loc_20c2` [guess]), folds the step at `ANIM_COORD_STEP_LO` (0x20c3) into the animation's two running coordinate totals -- one of which is `ANIM_SPRITE_COORD` (0x20c5) -- and compares the resulting total against `ANIM_END_COORD` (0x20ca); on a match it latches `ANIM_DONE_FLAG` (0x20cb) to 1 and stops [seen]. Otherwise it takes the frame's sprite source from the base pointer `ANIM_BASE_SPRITE_SRC` (0x20cc), adding 0x30 to it while bit 2 of the counter is clear so the sprite alternates between two frames every four steps as it moves [seen], stores that into `ANIM_SPRITE_SRC` (0x20c7) [seen], loads the five-byte descriptor at `ANIM_SPRITE_COORD` (0x20c5) to recover the current coordinate and the source pointer, and shift-blits the frame with `blitShiftedSprite` [seen].

## Sound

Space Invaders talks to two of the board's output ports. Port 3 carries the discrete one-shot cues (a player shot, a scoring cue, and the saucer's continuous whine), while port 5 carries the fleet-march "footsteps" and the saucer-hit tone. Because several independent effects share each port, the game never composes a port byte from scratch: it keeps a RAM shadow of each latch — SOUND_PORT3_SHADOW at 0x2094 [seen] and SOUND_PORT5_SHADOW at 0x2098 [seen] — edits individual bits in the shadow, and mirrors the whole byte out. Every effect therefore reduces to "raise this bit" or "clear this bit," with the shadow remembering what the rest of the mixer is doing.

Two tiny primitives do all the port-3 bit work. `startSound` (0x18fa) [seen] ORs a caller-supplied mask into SOUND_PORT3_SHADOW, stores it back, and writes it to port 3, turning a cue on; `clearSoundPort3Bit` [seen] is the mirror image, ANDing the shadow with a mask to turn a cue off, and likewise writes port 3. Both leave the resulting byte in A. The callers choose the bit: a companion step keyed on the player-shot state raises bit 1 (mask 0x02) while a shot is in flight and clears it (mask 0xfd) when it ends [seen]; a scoring path raises bit 3 (mask 0x08) as it stamps a score-add, gated on the game being in progress [seen]; and the saucer logic drives bit 0.

The fleet march is produced by two routines working in tandem — a metronome on the interrupt and a bookkeeper on the frame loop. `stepFleetMarchSound` (0x1740) [seen] is the metronome, driven from the interrupt handler at 0x0010 only while GAME_IN_PROGRESS (0x20ef) [seen] is set. Each tick it counts down FLEET_SOUND_OFF_TIMER (0x209b) [seen]; when that reaches zero it runs the note-off helper `silenceFleetMarchNote` [seen], which re-emits only the two high bits of the port-5 shadow (mask 0x30) and so silences the four low march tones — this is what makes each footstep a discrete note rather than a drone. It then reads an enable flag at 0x2068 (`loc_2068`, open [guess]); if that is clear it silences through `silenceFleetMarchNote` and stops. Otherwise it counts down the beat timer FLEET_SOUND_TIMER (0x2096) [seen] and returns until it expires. On the beat it writes the full port-5 shadow out (sounding the current tone) and — provided ALIEN_COUNT (0x2082) [seen] is nonzero — reloads the beat timer from FLEET_SOUND_PERIOD (0x2097) [seen], sets the trigger FLEET_SOUND_STEP (0x2095) [seen] to 1, and arms FLEET_SOUND_OFF_TIMER to 4, so the note rings for four ticks before the off-timer cuts it. When the last alien is gone the beat plays but nothing is re-armed, and the march goes quiet.

`advanceFleetMarchSound` (0x1775) [seen] runs each frame from the main loop and does the pitch-and-tempo work the metronome requested. When FLEET_SOUND_STEP is set, it first chooses the tempo for how thin the wave has become: it walks the threshold table FLEET_RATE_THRESHOLDS (0x1a11) [seen] against ALIEN_COUNT, advancing a parallel index until the alien count is at least the threshold, and copies the matching byte from FLEET_RATE_TABLE (0x1a21) [seen] into FLEET_SOUND_PERIOD — so as aliens die the period shrinks and the march accelerates. Then it steps the tone: it isolates the low nibble of the port-5 shadow and rotates it left one bit, cycling the single lit bit 0x01 -> 0x02 -> 0x04 -> 0x08 and wrapping 0x10 back to 0x01, which is the familiar four-note descending loop, while OR-ing the two high bits (mask 0x30) back untouched. Finally it clears FLEET_SOUND_STEP. On every frame, triggered or not, it also counts down SFX_OFF_TIMER (0x2099) [seen], and when that expires it clears port-3 bit 4 (mask 0xef through `clearSoundPort3Bit`) — a one-shot port-3 effect that auto-silences at the end of its window.

Alongside these sits `latchSoundPort5` (0x1770) [seen], a bare helper that masks A to the two high sound-select bits (mask 0x30) and writes port 5 — used when code wants to emit those latched high bits directly; `silenceFleetMarchNote` [seen] is the same tail but reads its byte from the port-5 shadow first.

The saucer's continuous tone is a single port-3 bit governed frame by frame by `updateSaucerSound` (0x1804) [seen] off a two-flag gate. If SAUCER_ACTIVE (0x2084) [seen] is clear it delegates to `stopSaucerSound` (0x0707) [seen], which clears bit 0 (mask 0xfe through `clearSoundPort3Bit`) and kills the whine. If the saucer is active but SAUCER_HIT (0x2085) [seen] is set — it has been shot and is in its death sequence — the routine simply returns and leaves the latch as it stands. Only when the saucer is active and not hit does it call `startSound` with mask 0x01, holding bit 0 on. When the saucer actually appears is scheduled elsewhere: SAUCER_TIMER (0x2091) [seen] is a rolling 16-bit countdown — not itself a sound cell — whose expiry arms the next saucer, and the audio simply follows the resulting active/hit flags.

When the player shoots the saucer down, `playSaucerHitSoundAndDrawSprite` (0x074b) [seen] fires the hit. It ORs bit 4 (mask 0x10) into the port-5 shadow and latches it through `latchSoundPort5`, sounding the UFO-explosion tone; it then repoints the saucer's sprite record (0x2087) at the explosion-graphic table SAUCER_HIT_SPRITE (0x1d7c) [seen] and draws that column, so the bang and the burst arrive together. That the hit tone lives in port-5 bit 4 — inside the 0x30 mask the fleet-march routines deliberately preserve — is precisely why the march can keep rotating its low nibble without ever clobbering a saucer-hit that is still ringing.

## The alien field and its march

Each player owns an entire 256-byte page of work RAM for its aliens. Player one's page begins at ALIEN_FIELD_P1 (0x2100) and player two's at ALIEN_FIELD_P2 (0x2200) [seen]; the low 0x37 (55) bytes of each page form the liveness grid — one byte per alien, laid out as five rows of eleven — and a byte reads nonzero for as long as that alien is still on the board. Which of the two pages is currently in play is named by a single page-number byte, ACTIVE_PLAYER_PAGE (0x2067) [seen]: shifting that byte left by eight yields the base of the active grid, so the same code walks whichever player's field is live simply by reading the page byte and forming page<<8.

A fresh wave is armed by markAllAliensAlive [seen], which writes 0x01 into 0x37 consecutive bytes from a caller-supplied address — fifty-five live aliens in one tight fill. Two thin seaters choose the target: markAllAliensAliveP1 [seen] points the fill at 0x2100 and markAllAliensAliveP2 [seen] at 0x2200. Notice these two name the page bases as fixed constants rather than going through the active-page byte, so each resets a specific player's grid regardless of who is currently active.

Counting the survivors is the job of countLiveAliens [seen]. It forms the active grid base from ACTIVE_PLAYER_PAGE, scans all 0x37 cells, counts the nonzero ones, and publishes the running total to ALIEN_COUNT (0x2082) [seen]. That published count is what the rest of the machine reads to decide how fast the fleet should feel — the fleet-march sound, for one, steps its tempo from it [seen]. As a special case, when exactly one alien remains countLiveAliens raises LAST_ALIEN_FLAG (0x206b) [seen] to single out the lone survivor (no reader for it is identified in the code).

Where the whole fleet sits on screen is tracked not per-alien but by a single reference corner, from which every alien's position is derived. loadReferenceAlienState [seen] rebuilds that reference from the active player's saved record, which lives at the top of the same per-player page. activeFieldRecordPointer forms page<<8 | 0xfc [seen]; loadReferenceAlienState reads the 16-bit coordinate word stored there and mirrors it into two working spots — the pair at loc_2009/loc_200a and ALIEN_DRAW_ADDR (0x200b) [seen] (loc_2009/loc_200a themselves are still open [guess]). It then steps one byte below the pointer, to page-offset 0xfb — the per-player saved delta held at loc_21fb for player one and loc_22fb for player two [guess] — copies that byte down into a working count at loc_2008 (decrementing it by one when it reads 0x03) [guess], and when the byte carries the sentinel value 0xfe it raises FLEET_MOVE_DIR (0x200d) [seen]. Those delta bytes start life seeded to 0x02 for both players [guess]. Because the reference word and the delta are saved per page, each player's fleet keeps its own position and heading across the hand-off between turns; the save side stages the working count and coordinate word back toward the record [code].

The reference corner becomes an actual alien position through alienIndexToScreenCoords [seen]. Given an alien's index (0..54) in L, it seeds two registers from the reference pair — one from loc_2009, one from loc_200a — then decomposes the index over 0x0b: every whole group of eleven advances the first coordinate by 0x10 and bumps a row counter, and each leftover column advances the second coordinate by 0x10 [seen] (the two seed cells remain open [guess]). In effect an alien's screen coordinate is the fleet's reference corner plus sixteen pixels per grid step in each direction. Because loadReferenceAlienState refreshes loc_2009/loc_200a from the saved record on every pass, nudging that one reference corner slides the whole fleet in lockstep — that is the march.

The march is animated one alien at a time. A selector (pickNextMarchingAlien) refuses to pick a new alien while a draw is still outstanding — it returns early whenever ALIEN_DRAW_PENDING (0x2000) [seen] is set — and otherwise walks an index cursor forward through the 55-cell grid, wrapping back to the start when it runs off the end, until it lands on a live cell. It resolves that cell through alienIndexToScreenCoords, stows the resulting coordinate pair into ALIEN_DRAW_ADDR (0x200b) [seen] (overwriting the reference word that loadReferenceAlienState had parked there), and raises ALIEN_DRAW_PENDING to hand the work off. If the resolved coordinate has descended past a limit — it range-checks the value against 0x28 — the selector diverts elsewhere instead of drawing [guess]. The drawing pass (drawPendingAlien) then reads ALIEN_DRAW_ADDR, blits the alien sixteen rows tall, and clears ALIEN_DRAW_PENDING, freeing the selector to advance to the next alien on the following pass. Advancing exactly one alien per pass is what makes the fleet ripple rather than jump.

Each alien also has a two-frame walk cycle, and selectAlternateSpriteFrame [seen] is the toggle: it advances the sprite pointer by 0x30 (DE += 0x30) to the alternate frame's bank, and the drawing pass invokes it only when the alien's descriptor carries the alternate-frame flag [seen], so aliens flip between their two poses as they step.

The horizontal sweep and the drop at the edges ride on FLEET_MOVE_DIR (0x200d) [seen]. The edge handler `reverseFleetAtEdge` reads that flag to choose which screen boundary to test — the left-edge VRAM column FLEET_LEFT_EDGE_VRAM (0x2524) [seen] while the fleet moves left, the right-edge column FLEET_RIGHT_EDGE_VRAM (0x3ea4) [seen] while it moves right — and scans that column through `fleetReachedEdge`, which reports by carry whether any alien pixel has reached it. When the leading edge does reach the boundary it flips FLEET_MOVE_DIR, republishes the horizontal step into the working count at loc_2008 (0xfe = two pixels leftward when reversing to the left, or a small positive step the other way), and copies the one-row vertical drop FLEET_DROP_DELTA (0x200e) [seen] into the drop cell FLEET_STEP_DY (0x2007) [seen] — consumed the next sweep as the fleet's descent step, added into the reference Y. FLEET_MOVE_DIR set means the fleet is sweeping one way; clear, the other.

Finally, the same reference corner supports the inverse mapping — from a screen coordinate back to a fleet-grid block — used when the game must know which grid cell a given point falls in. scaleXToBlock [seen] steps the reference base held in loc_2009 up by 0x10 at a time until it reaches the coordinate in L (the coordinate is the threshold), returning the step count less one as a block index in B and the leftover as a residual in L/A; scaleYToBlock [seen] does the same for loc_200a stepped up to a coordinate in H, leaving the residual in H/A. Both lean on the very cells that place the aliens (loc_2009/loc_200a, still open [guess]), so screen-to-grid and grid-to-screen share a single origin. Whether that origin's two bytes are the horizontal-versus-vertical pair — and hence whether the "X" and "Y" labels on these two routines are literal — is not yet pinned down.

## Player records, shields, and the player shot

This subsystem is organized around the idea of an *active player*. A single work-RAM byte, the active-player page at `0x2067` (`ACTIVE_PLAYER_PAGE`, [seen]), names both the RAM page that holds the current player's state and, in its low bit, which of the two players is currently on the machine. Almost every routine here begins by consulting that byte.

### Locating the active player's data

Three tiny helpers turn the page byte into a pointer. `activePlayerPageBase` (0x1611, [seen]) simply shifts the page byte left eight bits, handing back `HL = mem[0x2067] << 8` — the base of the current player's page. `activeFieldRecordPointer` (0x0886, [seen]) does the same but forces the low byte to `0xfc`, yielding `(page << 8) | 0xfc`, which addresses the field-save record near the top of that page. `readActivePlayerPageTopByte` (0x092e, [seen]) builds on `activePlayerPageBase`, forces the low byte to `0xff`, and reads the byte sitting at the very top of the page into `A` (leaving that address in `HL`). Because the two player pages are `0x21xx` and `0x22xx`, these three produce `0x2100/0x2200`-relative pointers that follow whichever player is active.

`currentPlayerRecordPtr` (0x09ca, [seen]) takes a different route to the *same* distinction: it rotates bit 0 of the page byte into carry and returns one of two fixed descriptor addresses — `PLAYER1_OBJ_DESC` at `0x20f8` ([seen]) when the bit is set, `PLAYER2_OBJ_DESC` at `0x20fc` ([seen]) when it is clear. So bit 0 of `0x2067` is the player selector: set means player 1 (page `0x21xx`, descriptor `0x20f8`), clear means player 2 (page `0x22xx`, descriptor `0x20fc`). Input follows the same selector: `readActivePlayerInput` (0x17c0, [seen]) rotates bit 0 into carry and reads hardware input port 1 for player 1 (bit set) or port 2 for player 2 (bit clear), returning the byte in `A`.

`stageActivePlayerFieldSave` (0x0878, [code]) prepares to write the active player's field back to its record: it loads a count byte from `0x2008` into `B`, loads the reference-alien coordinate word from `0x2009` into `DE`, and then calls `activeFieldRecordPointer` so `HL` addresses the `page:0xfc` save slot. It is reached during the player-switch path, where the outgoing player's field is stashed before the incoming player's is restored.

### Generic record helpers

`advanceRecordTotals` (0x01d9, [seen]) is a small running-total accumulator over a four-byte record pointed at by `HL`: it reads the delta byte at `[HL+1]`, adds `C` into the total at `[HL+2]`, adds that delta into the second total at `[HL+3]`, and returns the second total in `A`. It is a shared primitive used by the scripted-animation stepper and other record-walking code, not tied to any one object.

A pair of eleven-byte scratch movers back the object-processing code. `copyRecordToWorkBuffer` (0x0550, [seen]) first stashes `A` into the scratch cell `0x207f`, then copies eleven bytes from the caller's source (`DE`) into the shared eleven-byte work buffer at `0x2073`. Its twin `copyWorkBufferToRecord` (0x055b, [seen]) copies those same eleven bytes from `0x2073` back out to the caller's destination (`HL`). Together they lift an object's move-record into a fixed scratch strip for in-place work and write it back afterward.

### Sprite descriptors

`loadSpriteDescriptor` (0x1a3b, [seen]) is the shared five-byte descriptor decoder. Reading forward from `HL`, it takes a two-byte graphics pointer into `DE`, then a coordinate byte into `A`, then two more bytes into `C` and `B`, and finally repoints `HL` at the composite address `C:A`. Several routines wrap it around a fixed record cell. `loadPlayerShotDescriptor` (0x0430, [seen]) points at the player-shot descriptor `PLAYER_SHOT_DESC` at `0x2027` ([seen]) and decodes it, leaving `HL` at the shot's screen coordinate word. `resolveSpriteScreenAddr` (0x0742, [seen]) decodes the descriptor at `0x2087` and then folds the resulting pointer through the coordinate-to-screen conversion, so it returns with `HL` = screen address and `DE` = the graphics pointer. `loadDrawSequenceBlock` (0x0ae2, [seen]) is a related loader that copies a twelve-byte draw/animation sequence from the caller's source (`DE`) into the fixed work slot at `0x20c2`.

### Shields

Each player owns a backup buffer for the four bunker shields: `PLAYER1_SHIELD_BUFFER` at `0x2142` ([seen]) and `PLAYER2_SHIELD_BUFFER` at `0x2242` ([seen]), both living inside that player's own `0x21xx`/`0x22xx` page. `initShieldBuffers` (0x01f8, [seen]) fills such a buffer by replicating a `0x2c`-byte shield template (from `0x1d20`) four times into consecutive slots, `0x2c` bytes each, and hands back the end pointer. `initPlayer1ShieldBuffers` (0x01ef, [seen]) and `initPlayer2ShieldBuffers` (0x01f5, [seen]) are the thin front doors that seat the respective buffer base first; they are run when a player's round is being set up.

The screen-side work runs through `drawOrSaveShields` (0x021e, [seen]), the common four-block body. It first records the caller's `A` into the mode flag `SHIELD_SAVE_RESTORE_MODE` at `0x2081` ([seen]), then walks four blocks down video RAM starting at `SHIELD_VRAM_BASE` (`0x2806`, [seen]), each block a `0x16`-column by two-byte screen rectangle (`0x2c` bytes, matching the template) and each next block `0x02e0` bytes further down. On every pass it re-reads the mode flag: when the flag is set it captures the screen rectangle into the buffer (a *save*), and when clear it OR-merges the buffer's bitmap back onto the screen (a *restore*). That direction is fixed by the four public entries: `savePlayer1Shields` (0x0209, [seen]) and `savePlayer2Shields` (0x020e, [seen]) force the flag to 1 (save), while `restorePlayer1Shields` (0x021a, [seen]) and `restorePlayer2Shields` (0x0213, [seen]) force it to 0 (restore). Each of those in turn goes through `saveOrRestorePlayer1Shields` (0x021b, [seen]) or `saveOrRestorePlayer2Shields` (0x0214, [seen]), whose only job is to seat `DE` at the correct player's buffer base before running the shared body. In practice these fire around the player switch and round setup — the outgoing player's shields are captured, the incoming player's are painted back — so each player's bunker damage persists across turns.

### The player shot and firing

`PLAYER_SHOT_STATUS` at `0x2025` ([seen]) is the player-shot state cell. `advanceRoundState` (0x1618, [seen]) is the gated pre-round step that arms it. It does nothing unless a start sentinel at `0x2015` reads `0xff`, the field object cells at `0x2010`/`0x2011` are both idle, and `PLAYER_SHOT_STATUS` is zero. Once past that gate its behavior forks on `GAME_IN_PROGRESS` at `0x20ef` ([seen]). In attract mode (`GAME_IN_PROGRESS` zero) it stamps `PLAYER_SHOT_STATUS` to 1 and advances a scripted marching pointer, `ATTRACT_DEMO_PTR` at `0x20ed` ([seen]): it increments the sixteen-bit pointer and, when the low byte reaches `0x7e`, wraps it back to `0x74` (a small demo window), then reads the byte at that pointer into `0x201d`. During real play (`GAME_IN_PROGRESS` nonzero) it instead watches the fire button through `FIRE_BUTTON_LATCH` at `0x202d` ([seen]): if the latch is set it waits for the fire bit (mask `0x10`) to release before clearing the latch, and if the latch is clear it waits for a fresh fire press, then arms the shot by setting both `PLAYER_SHOT_STATUS` and `FIRE_BUTTON_LATCH` to 1. The latch is what enforces one shot per distinct press.

### Alien shot rate and rendering

The rate at which aliens fire scales with how much of the fleet remains. `selectAlienShotRate` (0x170e, [seen]) reads a field-size key from the second byte of the active player's descriptor (`currentPlayerRecordPtr()+1`), then scans the four-entry threshold table `ALIEN_SHOT_RATE_THRESHOLDS` at `0x1cb8` ([seen]) for the first entry that is greater than or equal to the key. The parallel byte from `ALIEN_SHOT_RATE_TABLE` at `0x1aa1` ([seen]) is stored to `0x20cf`, where the per-frame shot stepper later reads it — so a smaller surviving fleet selects a faster shot cadence.

An alien shot is drawn and erased through the descriptor at `ALIEN_SHOT_SPRITE_PTR` (`0x2079`, [seen]). `drawAlienShotWithCollision` (0x066c, [seen]) decodes that five-byte descriptor and then OR-blits the sprite column into video RAM with collision detection (the overlap sets the collision flag). `eraseAlienShot` (0x0675, [seen]) decodes the same descriptor and instead ANDs the sprite's bits back out of the screen, removing it.

The per-frame alien-shot handler `stepAlienShot` ([seen]) drives that descriptor. With a shot live (bit 7 of its status byte `loc_2073`) it steps it — `objectMatchesDrawPhase` gates the object to the matching raster half, `stepAlienShotBlowup` runs while the blowup bit (bit 0) is set, and otherwise it advances the sprite frame and the shot's Y (by the step in `loc_207e`), redraws through `drawAlienShotWithCollision`, and retires the shot once it reaches the shield and ground bands with the collision flag latched. With none live it may launch one: it gates on `TASK_FLAGS` and the per-column rate cells `loc_2070`/`loc_2071` against the cadence in `loc_20cf`, picks a firing column from the cursor `loc_2076` or by scaling the Y source `loc_201b` through `scaleYToBlock`, and if `findLiveAlienInColumn` finds a live alien in that column seats the shot's start coordinates and flips it live. Its launch-attempt counter `loc_2074` and the gate flags `loc_2069`/`loc_2075` keep `loc_` names because their roles are not confident from the code alone.

### The pending score-add packet

Three adjacent cells form a small pending-score-add record: `SCORE_ADD_PENDING` at `0x20f1` ([seen]), `SCORE_ADD_VALUE` at `0x20f2` ([seen]), and `SCORE_ADD_VALUE_HI` at `0x20f3` ([seen]). They are written together, gated on `GAME_IN_PROGRESS`: the looked-up point value goes into `SCORE_ADD_VALUE`, its high byte is cleared into `SCORE_ADD_VALUE_HI`, and the pending flag `SCORE_ADD_PENDING` is raised to 1, so a later pass can fold the queued value into the score. (Only the scoring cue writes this packet; no routine in this subsystem consumes it.)

### The player-shot collision lifecycle

Space Invaders has no prize or bonus object: this chain is the player shot's collision teardown. When a player shot overlaps a sprite, `drawSpriteWithCollision` latches `COLLISION_FLAG`, and the object processor copies it into `PLAYER_SHOT_HIT` at `0x2002` ([seen]) — the shot-collision latch that drives a short chain. `clearShotHitAndSilence` (0x154a, [seen]) is the base: it clears `PLAYER_SHOT_HIT` and masks bit 3 out of the port-3 sound shadow, silencing the invader-die tone. `retirePlayerShot` (0x1545, [seen]) sits just above it, first stamping `PLAYER_SHOT_STATUS` (`0x2025`) with 4 (retiring) and then running the silence. Two entries lead into that retirement. `markSaucerHitAndRetireShot` (0x1579, [seen]) is reached from the shot resolver when the shot collides in the saucer's altitude band; it raises `SAUCER_HIT` at `0x2085` ([seen]) — read by `updateSaucerSound` and the saucer handler to switch the saucer into its explosion/score sequence — before retiring the shot. `tickAlienExplosionDespawn` (0x1538, [seen]) drives the alien explosion's timed disappearance: it decrements `ALIEN_EXPLOSION_TIMER` at `0x2003` ([seen]) and returns while it is still nonzero; on expiry it reloads the explosion sprite's stored screen position from `ALIEN_EXPLOSION_ADDR` at `0x2064` ([seen]) into `HL`, clears its sixteen-row sprite column, and then runs the same retirement tail.

## Attract screen and status display

The screen's fixed furniture -- the score header across the top, the CREDIT label at the bottom, the Taito copyright line, and the player's remaining-lives readout -- is painted by a family of small routines that each seat a handful of constants and hand off to the general glyph-drawing machinery.

drawScoreHeader (0x191a) [seen] is the plainest of the type. It seats a run of 0x1c (28) sprite ids sourced from SCORE_HEADER_TEXT (0x1ae4) [seen], points the screen pointer at SCORE_HEADER_SCREEN_ADDR (0x241e) [seen], and hands off to the sprite-list driver drawSpriteList [seen]. That driver walks the id list one byte at a time, drawing each id as an 8x8 glyph through drawSprite8x8 and stepping the destination along by one glyph per id, so the header comes out as a 28-glyph line of preset text [seen].

drawCreditLabel (0x193c) [seen] is cut from the same cloth: 0x07 (7) sprite ids from CREDIT_LABEL_TEXT (0x1fa9) [seen] to CREDIT_LABEL_SCREEN_ADDR (0x3501) [seen], again through drawSpriteList -- a seven-glyph label [seen]. Header and label are emitted together during the screen's redraw pass (`redrawScorePanel` first blanks video RAM, then calls drawScoreHeader, three sibling draws, and drawCreditLabel in sequence, and drawCreditReadout likewise finishes on drawCreditLabel), which is why they read as one static frame [guess].

drawTaitoCopyright (0x199a) [seen] paints its nine-glyph line -- TAITO_COPYRIGHT_TEXT (0x0bf7) [seen] to TAITO_COPYRIGHT_SCREEN_ADDR (0x2e1b) [seen], count 0x09 -- but only from behind a two-stage input gate. It keys off INPUT_CODE_STAGE_FLAG (0x201e) [seen], a one-shot latch. While that latch is clear, every call reads input port 1, masks off the bits in 0x76, and demands the exact value 0x72; a mismatch returns without drawing, while a match bumps the latch to 1 [seen]. Once armed, the routine reads port 1 a second time, masks the same 0x76, and now demands 0x34; only when that second code is present does it fall through to drawSpriteList and lay down the copyright [seen]. The copyright is therefore not ordinary furniture -- it surfaces only after the specific two-step port-1 combination is entered, and because the first stage is latched it stays satisfied once seen, leaving just the second code to gate each subsequent draw [seen]. The gate is reached through updateFleetAndDrawCopyright, which calls another routine and then hands straight into it [guess].

The bottom status line -- how many lives remain -- is split across two routines. drawReserveLifeIcons (0x19e6) [seen] seats the icon-strip base RESERVE_SHIP_ICONS_SCREEN_ADDR (0x2701) [seen] and, when it is entered with a nonzero count in A, paints that many reserve-ship icons: each icon is a 16-byte blit of RESERVE_SHIP_SPRITE (0x1c60) [seen] laid down through drawSpriteColumn [seen] (0x10 bytes at a 0x20 stride), with the destination walking forward one icon slot per pass, and the loop repeating A times [seen]. After the final icon -- or immediately, if it was entered with the count-zero (Z) condition and skipped drawing altogether -- it calls clearScreenRegion [seen] to blank the strips beyond the icons down to the terminator row, so icons left over from a higher life count get wiped [seen]. Its sole caller (decrementShipsAndDrawReadout) fetches the count, bails when it is zero, and passes count minus one, so the icons shown are the reserves held back beyond the ship currently in play [guess].

drawLivesDigit (0x1a8b) [seen] supplies the numeric half of the readout. It seats LIVES_DIGIT_SCREEN_ADDR (0x2501) [seen], reduces A to its low nibble (a value 0 through 15), and hands to drawDigit [seen], which maps the nibble to its hex-glyph id by adding 0x1a and plots it through drawSprite8x8 -- a single-digit lives count at a fixed screen slot [seen]. decrementShipsAndDrawReadout arrives here by falling through immediately after drawReserveLifeIcons, restoring the true life count first, so the digit and the reserve icons together form one coherent readout [guess]; other callers reach the routine on their own, including one that zeroes A first to force a "0" (loc_166d) [guess].

## Frame tasks, timers, boot, and scoring

At cold start the machine paints its own work RAM into existence from a fixed template. `seedWorkRamImage` (0x01e4) sets a copy length of 0xc0 bytes and drops straight into `initWorkRam` (0x01e6) [seen], which aims the copy from `WORKRAM_INIT_IMAGE` at 0x1b00 [seen] into the base of work RAM, `ALIEN_DRAW_PENDING` at 0x2000 [seen], and hands the move itself to `blockCopy` — the plain byte-for-byte loop that walks source and destination forward together [seen]. Those 0xc0 (192) bytes cover 0x2000–0x20bf, so the whole object/sprite work area is stamped down in one pass, with `GAME_OBJECT_TABLE` at 0x2010 [seen] sitting inside that seeded block. `initWorkRam` is also reachable on its own (from bootInit [guess]) with a caller-chosen copy length [seen], while the 0xc0-preset form is re-run later on player handoff and round resets — the next-round handoff advanceToNextRound, for instance, runs it with the running player index at 0x2067 saved across the call so the seed does not disturb it [code].

The single byte that records whether a game is live is `GAME_ACTIVE` at 0x20e9 [seen]. `setGameActive` (0x19d1) and `clearGameActive` (0x19d7) [seen] both funnel through one shared store, `storeGameActive`, which writes the accumulator into 0x20e9 [seen]; the former hands it 1, the latter 0. The flag is raised where a game or round begins (enterRoundWithFieldReload/enterRoundWithoutFieldReload, returnToAttractFlow) and dropped on death, reset, and handoff (drawCreditReadout, playerShipHandler, loc_16e6, the tilt/reset handler checkTiltInput, startGameFlow) [guess], and the next-round handoff advanceToNextRound additionally zeroes 0x20e9 directly [code]. Everything downstream treats it as the master gate: both interrupt bodies load 0x20e9 first and, finding it zero, fall straight to their epilogue without touching the play field [code].

Those interrupt bodies are where per-frame work is scheduled; each does its per-frame work and returns to the main loop. The vblank-time routine loc_0010 [code] decrements a frame counter at 0x20c0, runs the tilt/reset handler checkTiltInput (its only unconditional per-frame call — a no-op unless the tilt input on port 2 is set), samples the coin bit into `COIN_INPUT_LATCH` (0x20ea) [seen], and keeps a BCD credit counter at 0x20eb by adding one and decimal-adjusting it on eligible frames — the only score-style arithmetic in this group [code] — before dispatching on `GAME_ACTIVE`. The mid-screen routine loc_008c [guess] clears the raster draw-phase flag DRAW_PHASE_FLAG (0x2072) [seen] to 0 — the vblank body loc_0010 stamps it 0x80 at frame top, so this one byte names which raster half is currently live. The object dispatchers gate drawing on it through `objectMatchesDrawPhase`, which sets carry only when an object's phase bit (bit7) matches DRAW_PHASE_FLAG, so each object is serviced in just one of the two half-frames and no sprite is torn across the beam. loc_008c then checks `GAME_ACTIVE`, and then, unless a separate flag at 0x20ef forces the draw, consults the per-frame task bitfield `TASK_FLAGS` at 0x20c1 [seen]: it rotates the low bit out and runs its draw pair only when that bit is set [code], so 0x20c1 is the one-byte record of which drawing task the frame owes. `storeTaskFlags` is that cell's writer, storing the accumulator into 0x20c1 [seen]. The mid-screen body's draw scan `pickNextMarchingAlien` picks the next alien to paint each mid-frame; when the fleet has reached the bottom it arms a round-ending warm restart — the death-wait, screen teardown, and hand-off to game-over. Each frame the tilt handler reads the tilt input and, on a press, arms a warm-restart reset (`tiltReset` — wipe the play-field, drop the game, type the tilt banner, then join the attract teardown), guarded by `TILT_RESET_ACTIVE` (0x209a) so it never re-arms mid-reset; that reset runs over several frames.

The attract sequence runs off that same interrupt heartbeat. While no game is live the machine spins in short busy-wait delays that watch the frame counter `FRAME_DELAY_TIMER` (0x20c0) [seen], which loc_0010 decrements once per frame — so a routine paces an animation by seating that counter and waiting for it to reach zero. waitFrames [seen] is the primitive delay (seat the counter, then wait); typePacedSpriteRun [seen] walks a per-byte typed script, drawing one glyph and waiting a fixed cadence (`TYPE_PACE_COUNT`, 0x206c) [seen] per byte; runAttractAnimTask [seen] instead waits on the `ANIM_DONE_FLAG` (0x20cb) handshake. The attract cycle itself is bootInit (cold-boot work-RAM seed + score panel) → enterAttractCycle (seat the round/mode byte at 0x20cf) → runAttractCycle (per-round setup and the free-running demo loop) → finishAttractCycle (teardown, which flips the `SCREEN_MODE_TOGGLE` alternator at 0x20ec) [seen] and loops back to enterAttractCycle, so those four routines are the join of the attract loop. The demo's animation steps hand off through `ATTRACT_ANIM_ACK` (0x2055) [code], an interrupt/foreground handshake bit.

Timing that is not tied to the raster runs off countdown cells. `TIMER_RELOAD` at 0x0600 [seen] is the reload constant for the flying-saucer cadence: `tickSaucerSpawnTimer` [seen] counts a rolling 16-bit timer down on each pass while its gate cell sits below 0x78, and when that count reaches zero it reloads from `TIMER_RELOAD` and raises a wrap flag before storing the decremented value, giving the saucer a fixed, free-running interval [seen]. A second mode byte, `TWO_PLAYER_GAME` at 0x20ce [seen], guards mode-specific screen work — `blankScreenStrip` [seen] checks it and skips its strip-clear when the cell is already set.

Two small helpers feed setup and placement. `readStartingShips` (0x08d1) [seen] reads input port 2, keeps the low two bits, and adds 3, yielding a 3..6 starting-lives selector taken straight off the ships dip switch; it is pulled in at game and round setup (startGameFlow, runAttractCycle) [guess]. `countStepsToThreshold` (0x1554) [seen] is the coordinate-scaling primitive: it counts, in C, how many 0x10 steps lift A up to or past a threshold in H, first normalizing a negative A upward through `normalizeUpBySteps` [seen], and exits with carry deliberately cleared for the callers that read it. `scaleXToBlock` and `scaleYToBlock` [seen] drive it with an object's X or Y coordinate as the threshold to turn a pixel coordinate into a coarse block index plus the leftover residual — the mapping from screen position onto the coarse grid the object logic works in.

Several more leaf routines are named from the code. `drawPendingAlien` (0x0100) is the per-alien draw pass above. `stepAlienShotBlowup` (0x0644) runs the alien shot's terminal animation off `ALIEN_SHOT_BLOWUP_TIMER` (0x2078) [seen]: at 3 it erases the shot and re-seats the descriptor to `ALIEN_SHOT_BLOWUP_SPRITE` (0x1cdc) [seen] with a six-row height (`ALIEN_SHOT_ROW_COUNT`, 0x207d) before redrawing, and at 0 it erases. `awardSaucerScore` (0x070c) reads the current key through `SAUCER_SCORE_KEY_PTR` (0x208d) [seen], matches it in `SAUCER_SCORE_KEY_TABLE` (0x1d4c) [seen], copies the parallel `SAUCER_SCORE_SPRITE_TABLE` (0x1d50) [seen] entry into the saucer score record, and lays down the three-glyph score. `awardExtraShip` (0x0935) grants a bonus ship once the active player's tally passes the port-2-selected threshold, bumping the stored count and repainting the reserve column and lives digit. `drawBcdWord` (0x09ad) renders a 16-bit value as four BCD glyphs. `drawCreditCount` (0x1947) draws the BCD `CREDIT_COUNT` (0x20eb) [seen] at `CREDIT_COUNT_SCREEN_ADDR` (0x3c01) [seen]. `decrementShipsAndDrawReadout` (0x1a7f) is the ships-readout half above. The alien march's per-draw cursor `ALIEN_DRAW_INDEX` (0x2006) [seen] and the sprite base `ALIEN_SPRITE_TABLE` (0x1c00) [seen] are likewise named.

The state-2 handler `resolvePlayerShotHit` (0x14d8) resolves what a live player shot struck. Gated on `PLAYER_SHOT_STATUS`==2, it returns unless a hit is latched in `PLAYER_SHOT_HIT` (0x2002, which `playerShotHandler` copies straight from `COLLISION_FLAG` (0x2061) [seen]). By the shot's Y at `loc_2029` it either stands the shot down (missed off the top), marks the saucer hit and retires the shot (the saucer altitude band), or indexes the 55-cell alien grid (row×11+column via `alienGridCellPtr`), tests that cell live and clears it, and queues the killed alien's score and the invader-die sound through `queueInvaderKillScore` — killing the alien and entering the explosion (state 5). Its coordinate inputs `loc_2029`/`loc_202a` are a shared object-coordinate scratch pair; these — together with the alien-shot descriptor coords `loc_207b`/`loc_207c` that `stepAlienShotBlowup` recenters and the alien-draw state bytes `loc_2004`/`loc_2005` that `drawPendingAlien` reads — keep `loc_` names because the pixel-axis convention is not confident from the code alone.

## Object-table handlers

`GAME_OBJECT_TABLE` (0x2010) holds five 16-byte records the object dispatcher walks each frame; each record names a handler address the walker reads and calls, and the handler edits its own record in place. `playerShipHandler` (`PLAYER_SHIP_HANDLER_ADDR` 0x028e) is the rec0 player-ship handler, described below. `alienShotSlot2Handler` (`ALIEN_SHOT_SLOT2_HANDLER_ADDR` 0x0476) and `alienShotSlot3Handler` (`ALIEN_SHOT_SLOT3_HANDLER_ADDR` 0x04b6) are the two alien-shot step handlers — the record-2 (slot 2) and record-3 (slot 3) shots respectively (the specific Space Invaders shot type each drives — rolling / plunger / squiggly — is not derivable from the code): each [seen] primes the record's descriptor strip into the shared work buffer (`copyRecordToWorkBuffer`), seats the per-column rate cells, steps the shot through `stepAlienShot`, and either restores the strip or blits the record template and stows the firing column; `alienShotSlot3Handler` additionally clamps its firing column at 16 and latches the gate cell that self-disables it once one alien survives. `saucerHandler` (`SAUCER_HANDLER_ADDR` 0x0682) [seen] is the mystery-ship (saucer) handler: it copies the record template with a caller-chosen source (`copyTemplateToRecord`), latches a gate on the last alien, publishes the column word, and delegates to `alienShotSlot4Handler` [seen] outside its saucer-active window. `alienShotSlot4Handler` is the clean leaf they share, reached by an ordinary call (a tail from `saucerHandler`). The dispatcher `walkObjectTable` reads each record's handler address and calls it, passing the record pointer (`rec+4`) as its argument. The record sub-fields and the per-record ROM blit templates at 0x1b30.. keep `loc_` names because their roles are not confident from the code.

`playerShotHandler` [seen] is the player-shot handler for the rec1 record at 0x2020 — the only handler that branches on a record *type* byte (the shot status at `PLAYER_SHOT_STATUS`, 0x2025) rather than a single mode cell. It runs only in the matching raster half, then dispatches on the status: type 1 launches a shot (bump the status, seat the muzzle X from `loc_201b`, blit); type 2 steps a shot in flight — erase the sprite, advance its Y by the per-frame step in `loc_202c`, then redraw with `drawSpriteWithCollision` and copy any `COLLISION_FLAG` into `PLAYER_SHOT_HIT` for the collision resolver; type 3 counts a retiring shot down one animation frame at a time (erase, nudge the descriptor to the next explosion cell, redraw), and when its countdown (0x2026) reaches zero — as does any other status via `doR` — runs a shared tally that reseeds the record from its ROM template (`loc_1b25`), steps the two saucer-key counters at `SAUCER_SCORE_KEY_PTR` (0x208d) and 0x208f, and, when no saucer is active, publishes one of two movement pairs to 0x208a/0x208c chosen by a bit of the byte the counter pointer (loc_208f) addresses. Because it erases then redraws at a recomputed Y, each sprite position is re-read from the descriptor after the erase (the recomputed Y is stored to 0x2029 before the redraw so the descriptor carries it). Like the other four record handlers it is called by the walker `walkObjectTable`, which passes the record pointer as its argument.

## The in-game main loop and round restarts

A game starts from attract when a coin is inserted. The vblank interrupt banks the credit (the BCD `CREDIT_COUNT`, 0x20eb) on the coin-switch press edge, then hands off to the credit screen: `creditScreen` draws the one-player-start prompt, latches `CREDIT_SCREEN_SHOWN` (0x2093) so it shows once, and polls input port 1 each frame for the start button (bit 2 = one player, bit 1 = two players) until one is pressed. The chosen start (startOnePlayerGame one-player, startTwoPlayerGame two-player) seeds the player count and its score-line constants through the shared init startGameFlow, which falls into the round-start chain startRoundFlow below. The coin → prompt → start → game path advances one stage per frame as the start button is polled.

Once a game starts, control enters the in-game frame loop `mainLoop` (loc_081f→loc_0849, which tail-jumps back to loc_081f so the body runs one pass per displayed frame). Each pass advances the pre-round arm step (`advanceRoundState`), resolves the player shot and fleet edge (resolveShotAndFleetEdge), counts the live aliens into `ALIEN_COUNT` (0x2082), and applies any pending score packet. While aliens remain it then steps the alien-shot rate, the extra-ship award, the low-alien flag, and the per-frame sound services, gating the round-start blip on the arm-trigger poll (isArmTriggerSet, [0x2015]==0xff). The loop has two exits: when `ALIEN_COUNT` reaches zero the wave is cleared and it hands to the next-round handoff advanceToNextRound, and the per-frame object timer playerShipHandler can, on expiry, hand off to one of three flows. The round-start chain that feeds the loop is startRoundFlow → restoreShieldsAndEnterRound → enterRoundWithFieldReload/enterRoundWithoutFieldReload: startRoundFlow runs the 0xb0-frame round-start splash (showRoundStartSplash, which flashes the active score on the counter's bit 2 while `FRAME_DELAY_TIMER` drains), clears the field and `TASK_FLAGS`; restoreShieldsAndEnterRound restores the active player's shields (chosen by the `ACTIVE_PLAYER_PAGE` bit); and enterRoundWithFieldReload loads the saved reference-alien field (enterRoundWithoutFieldReload, the doJ re-entry, skips that reload), then both mark the game active, cue the sound, and fall into the loop.

The three flows playerShipHandler arms are round restarts. `newRoundFlow` (loc_02ed→loc_02f8) saves the outgoing player's shields, stages the field record, reseeds work RAM, and republishes the select byte and sound-select shadow for the incoming player (0x21 / off for player 1, 0x22 / the alternate tone for player 2) before re-entering startRoundFlow — the select byte read at the top is carried across the work-RAM reseed (which overwrites `ACTIVE_PLAYER_PAGE`) to pick both branches, so the cell is saved and restored around the reseed. `gameOverFlow` (loc_166d→loc_1671) zeros the lives digit, promotes the player's score to the high score when it beats it (16-bit compare, high byte then low), and then either joins the attract teardown returnToAttractFlow→finishAttractCycle (a one-player game, or both players out) or hands the turn to the survivor via `newRoundFlow`. `doJFlow` (loc_1a7f then enterRoundWithoutFieldReload) is the extra-life continuation: take one reserve ship, then re-enter the field-arm tail without reloading the field. The next-round handoff advanceToNextRound is the SAME player's next round (not a switch — the switch is `newRoundFlow`): it preserves `ACTIVE_PLAYER_PAGE` across the reseed, bumps that player's own round counter at page:0xfe, looks the next round's field-config byte up in the loc_1da2 table, re-seeds that same player's shields and alien field, and re-enters restoreShieldsAndEnterRound. The busy-wait paces (showRoundStartSplash's 0xb0-frame splash, waitNextRoundArm's 0x30-frame handoff wait) drain `FRAME_DELAY_TIMER` the same way the attract delays do.

The dispatcher itself is `walkObjectTable`, which the interrupt bodies call each half-frame (seated at the vblank object table 0x2010 through `walkVblankObjectTable`, and at the mid table 0x2020 directly). It walks the 16-byte records — 0xff ends the walk, an inactive record's timer field or gate byte is counted down in place — and for each active record reads the handler address the record carries and calls the matching handler (`0x028e`, `0x03bb`, `0x0476`, `0x04b6`, or `0x0682`), passing the record pointer as its argument, stopping the walk the moment a handler arms a round restart. Because the five in-game handler targets are seeded from a fixed ROM template at round start, the map is static (keyed by the named `PLAYER_SHIP_HANDLER_ADDR` / `PLAYER_SHOT_HANDLER_ADDR` / `ALIEN_SHOT_SLOT2_HANDLER_ADDR` / `ALIEN_SHOT_SLOT3_HANDLER_ADDR` / `SAUCER_HANDLER_ADDR`); the only target outside it is the entropy-residual attract-demo fork, which the walker rejects. `playerShipHandler` is the record-0 player-ship handler: it moves the ship's column by demo script or live input, counts that record's frame timer down and steps the ship animation while it runs, and on expiry clears `GAME_ACTIVE` and — during play — consumes the life and arms one of the three restart flows above.

During the attract demo the vblank interrupt reaches the dispatcher through a per-frame task selector, `dispatchAttractTask`: it reads the `TASK_FLAGS` bitfield and runs exactly one arm — the animation step, or (one bit) the attract-demo object walk over its own record table at 0x2050, or (another bit) the shared vblank record tail `serviceVblankObjects` (pending-alien draw, the object walk over the main table, and the saucer timer). In-game that same `serviceVblankObjects` tail runs every frame after the fleet-march beat, so it is the single body both the demo selector and the live game share.

## What is still open

Two items keep a `[code]` tag because their role is read from the code but not yet confirmed against MAME:
`stageActivePlayerFieldSave` (0x0878), which stages the outgoing player's field save, and `ATTRACT_ANIM_ACK`
(0x2055), the interrupt/foreground animation-handshake bit. A set of cells keep `loc_<addr>` names because their
role is not confident from the code alone: the reference-alien anchor pair `loc_2009`/`loc_200a`, the saucer
sprite pointer `loc_2087` and active flag `loc_2083`, the alien-shot rate cell `loc_20cf`, the object work
buffer `loc_2073`, the alien-shot descriptor coords `loc_207b`/`loc_207c`, the shared object-coordinate scratch
`loc_2029`/`loc_202a`, and several other work-RAM and ROM cells.

Three thin wrappers front the shared score draw, one per record: `drawPlayer1Score` (0x1925), `drawPlayer2Score`
(0x192b) and `drawHighScore` (0x1950) each seat a fixed record base — `PLAYER1_OBJ_DESC`, `PLAYER2_OBJ_DESC`, and
`HIGH_SCORE_OBJ_DESC` (0x20f4), the third sibling of the two player records — and tail-delegate to `drawScoreRecord`,
which unpacks the four-byte record (a BCD value word then its screen address) and paints the total there [seen].
