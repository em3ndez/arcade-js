# Space Invaders — how the machine works

This map describes the parts of Space Invaders (Intel 8080, Midway `mw8080bw` board) whose behaviour has
been recovered into the idiomatic layer. It is a **current-state** description of the machine, not a history
of the port. Every claim is tagged with the confidence of its reading:

- **[seen]** — a role confirmed by a MAME observation.
- **[code]** — a role read from the routine bodies; MAME grounding still open. A stage-B grounding pass (boot +
  attract + a coin/start/1-player capture) confirmed a broad set as **[seen]**: the sound-port shadows and the
  fleet-march sound chain, the living-alien count and the alien-draw handshake, the alien-shot rate tables, the
  game-active and game-in-progress gates, the saucer launch timer, the shield save/restore, and the framebuffer
  draw/clear routines with their video-RAM constants. What stays **[code]** is what that capture could not
  exercise — the player-shot and scoring chain, the register-bridge delegators, and the still-disputed cells —
  pending a two-player / saucer / play-bot capture. The per-item tag lives in names.js (a cell's inline
  `// [seen]`/`// [code]`, a routine's `cert`).
- **[guess]** — an unclear reading; these keep a `loc_<addr>` placeholder rather than a descriptive name.

What is described here is the layer of **helper routines** — the primitives the game's spine calls to touch
video, sound, the alien field, the player shot and shields, the per-player records, scoring, and the frame
timers. The game's control-flow spine (the main loop, the object-state dispatcher and its handlers, the
interrupt handlers) is not yet recovered and is **not** described yet; a routine named `loc_<addr>` anywhere
below is one still awaiting a descriptive name — its mechanism may already be read at [code], its game-role or
naming still open.

## Video RAM and the framebuffer

The framebuffer is a flat block of memory that begins at `VIDEO_RAM_BASE` (0x2400) [seen] and runs up to, but not including, `VIDEO_RAM_END` (0x4000) [seen] -- a little under 7 KB in which every bit is a lit or dark pixel. `clearScreen` is the clearest window onto that span: it walks a pointer from 0x2400 and stores zero at each cell until the pointer's high byte reaches 0x40, so the whole video region 0x2400..0x3fff goes dark in one linear pass [seen]. Nothing in this region is structured as records; it is raw pixels, eight to a byte, which is why every routine that touches it works in terms of byte addresses and bit shifts rather than named fields.

The geometry the drawing code assumes is visible in how it steps. `coordToScreenAddr` takes a coordinate in HL, shifts it right by three -- dividing the pixel position by eight, the eight pixels packed into each byte -- and then forces the high byte into the 0x20..0x3f page window (masking to 0x3f and setting bit 0x20) so the result always lands inside the RAM window that holds video memory [seen]. That fold is the standard conversion from a pixel position to the byte that contains it. The other recurring constant is the stride 0x20: the fill and copy primitives move by 32 bytes to reach the next scan position, so cells a fill touches sit 0x20 apart in memory, which corresponds to adjacent screen lines [seen from fillScreenRow] [code from captureScreenRect's row stepping].

Blitting a sprite to an arbitrary pixel needs both a byte address and a sub-byte offset, and `seatBlitPosition` produces both at once: it writes the low three bits of L out to hardware port 2 -- the shift-register offset that the bit shifter will apply to the sprite bytes -- and then calls `coordToScreenAddr` to fold HL into a screen byte address [code]. The result is that the fractional part of the position lives in the shift hardware while the whole-byte part lives in HL. This is the seating step the sprite blitters (`blitShiftedSprite`, `orBlitShiftedSprite`, `eraseShiftedSprite`, `clearSpriteColumn`, `drawSpriteWithCollision`) rely on before they lay bytes down, and `resolveSpriteScreenAddr` uses the same `coordToScreenAddr` fold to turn a loaded sprite descriptor's coordinate into its target byte.

Filling is built from one primitive, `fillScreenRow`, which stores a given byte into `[HL]`, advances HL by 0x20, and repeats for B passes, leaving HL one stride past the last cell it wrote [seen]. Because it steps by a full screen line each pass, a single call paints a vertical run of identical bytes down the display. Two callers specialize it. `clearScreenStrip` simply zeroes A first and hands the run to `fillScreenRow`, so it blanks a column of B lines from HL [code]. `drawBottomLine` seats A=0x01, B=0xe0, and HL=`PLAYFIELD_VRAM_BASE` (0x2402), painting the single-bit value 0x01 down 0xe0 lines from the play-field's base -- the one-pixel boundary line laid across the bottom of the field [code].

Above the single-strip primitive sit the bulk clears. `clearPlayfield` erases the play-field framebuffer starting from `PLAYFIELD_VRAM_BASE` (0x2402) [seen], the base two bytes above the video origin [seen], writing zeros and incrementing but skipping a six-byte column margin between rows: whenever the low five bits of the pointer reach 0x1c it jumps ahead by six, so each 32-byte line clears only its interior and leaves the margin bytes untouched, and it stops once the high byte reaches 0x40 [seen]. This is the routine invoked when the field is wiped between states (its sole caller, `loc_1988`, does nothing but forward to it). `clearScreenRegion` clears a taller region by repeatedly running `clearScreenStrip` with B=0x10: each pass blanks sixteen lines and advances the base by 0x200, and it keeps going until the strip base's high byte reaches the terminator page 0x35, returning the final pointer along with that page byte in A and B=0 [code]. `blankScreenStrip` is a guarded one-shot: it first reads `TWO_PLAYER_GAME` (0x20ce) and returns immediately if that flag is set, otherwise it blanks a fixed 0x20-line strip based at loc_391c [code] -- an address that sits inside the 0x2400..0x3fff video window but whose precise on-screen meaning is not yet pinned down (loc_391c, open) [guess].

Moving pixels rather than clearing them is the job of two copy primitives. `blockCopy` is the plain linear byte copy: it reads B bytes from DE and writes them to HL with both pointers advancing, treating a count of zero as a full 256 [seen]. It is the general-purpose mover used well beyond the framebuffer -- seeding and initializing work RAM (`initWorkRam`, `seedWorkRamImage`), shuttling object records to and from work buffers (`copyRecordToWorkBuffer`, `copyWorkBufferToRecord`, `copyTemplateToRecord`), and staging draw sequences and shield buffers (`loadDrawSequenceBlock`, `initShieldBuffers`). Its screen-aware cousin is `captureScreenRect`, which copies a rectangle: for each of B rows it copies C bytes from the source into a contiguous destination stream, then advances the source base by 0x20 -- one screen line -- so a two-dimensional patch of the display is flattened into a linear buffer, and it returns both the destination end pointer and the advanced source base [code]. Its consumer is `drawOrSaveShields`, which walks four stacked blocks of 0x16 by 0x02 down the screen from `SHIELD_VRAM_BASE` (0x2806): when its mode flag is set it uses `captureScreenRect` to save each shield's pixels off-screen, and between blocks it adds `DRAW_BLOCK_STRIDE` (0x02e0) [code] to the advanced pointer to reach the next shield's position. That stride is the fixed gap the save/restore path steps by to line up the four shields down the field.

## Sprite drawing

Everything the game puts on screen is written into a single bitmap that lives in a video-RAM window: a coordinate in HL is folded into that window (`coordToScreenAddr` shifts it right by three, since eight pixels pack into a byte, and forces the high byte into the 0x2000-region) before any pixels land. Because the display is stored rotated, what the drawing code calls a "column" runs *down* the screen, and stepping to the next scanline means adding 0x20 to the destination pointer — a stride that recurs in every routine here [seen]. On top of that geometry the drawing code splits into two families: byte-aligned copiers, which drop whole source bytes straight onto byte boundaries, and hardware-shifted blitters, which push each source byte through the board's shift register so a sprite can sit at any of the eight sub-byte pixel offsets.

### Byte-aligned columns

The heart of the aligned family is `drawSpriteColumn` (0x1439) [seen]. Given a source pointer, a destination, and a row count B, it copies B bytes down B successive rows: read one source byte, store it, bump the source by one, and advance the destination by 0x20 to the next row. A count of zero wraps to a full 256-byte pass, and the loop leaves HL sitting at the column's end as its live-out [seen]. Two thin wrappers exist only to fix the count. `drawSprite8x8` (0x08ff) [code] first turns a sprite id in A into a source address — `loc_1e00 + 8*A`, preserving the caller's HL across that arithmetic — writes the id out to port 6, sets B to 8, and hands off to the column copier, so it always paints an eight-row sprite [code]. `drawSpriteColumn16` (0x1844) [code] does the same for a fixed sixteen-row column, forcing B to 0x10 and taking care to save and restore the caller's BC around the draw [code].

Above `drawSprite8x8` sit two consumers. `drawSpriteList` (0x08f3) [code] walks a run of C sprite ids sitting consecutively in memory: it loads each id, blits it, then advances the id pointer, letting the returned HL carry the screen position downward from one 8x8 sprite to the next until the count reaches zero [code]. `drawDigit` (0x09c5) [code] is a one-line adapter for text: it adds 0x1a to a small value to select that value's glyph in the sprite table, then plots it as an ordinary 8x8 sprite — so the digit and hex glyphs are simply the sprite entries beginning at index 0x1a [code].

The table those indices reach into is the still-unnamed `loc_1e00` [guess/open]: an array of eight-byte-per-entry bitmaps, addressed as `loc_1e00 + 8*A`, holding both the game's sprites and its glyph shapes. Its exact contents and layout are inferred only from how the resolver indexes it, so it stays a `loc_` cell.

### Hardware-shifted columns

Sprites that must move at single-pixel resolution cannot rely on byte alignment, so a second family runs each source byte through the board's shift register. They all begin the same way, via `seatBlitPosition`: the low three bits of the coordinate become the pixel offset (latched to port 2), and the rest of the coordinate is folded into the screen window. Thereafter each row does a two-step dance with the shifter — write the source byte to port 4 and read the shifted result back from port 3 for the left screen byte, then write a zero to port 4 and read again to collect the bits that spilled past the byte boundary into the neighbouring screen byte — before stepping down 0x20 to the next row [code]. What separates the four variants is purely how those two shifted bytes are combined with what is already on screen.

`blitShiftedSprite` (0x15d3) [code] overwrites: it stores the shifted bytes directly, and because it stashes the starting address on entry it reports that base back as its live-out HL. `orBlitShiftedSprite` (0x1400) [code] merges instead, OR-ing each shifted byte into the screen so the sprite is drawn over existing pixels. `eraseShiftedSprite` (0x1452) [code] is the inverse: it complements each shifted byte and ANDs it into the screen, so exactly the sprite's own bits are cleared and nothing else is disturbed — the standard way a moving object is lifted off before being redrawn one pixel over. And `drawSpriteWithCollision` (0x1491) [code] is `orBlitShiftedSprite` with a detector bolted on: before OR-ing each half it ANDs the shifted byte against the pixels already there, and if that overlap is non-zero it raises a flag [code].

That flag is `COLLISION_FLAG` (0x2061) [code]. `drawSpriteWithCollision` clears it to zero at entry and sets it to one the instant any drawn bit lands on an already-lit pixel [code]; it is the game's overlap signal — the mechanism by which a shot striking an alien, shield, or player is noticed by whoever inspects 0x2061 after the draw.

Rounding out this family is `clearSpriteColumn` (0x1424) [code], which seats the position like the others but then simply zeroes the two adjacent screen bytes on each of B rows, wiping a two-wide column's footprint outright rather than reading anything back through the shifter [code].

### Bitmap rectangles and the draw-record list

Not every blit is a single column. `orBlitBitmap` (0x1a69) [seen] handles a rectangle: an outer loop over B rows and an inner loop over C bytes per row, OR-ing each source byte into the destination and running the source pointer straight through the whole image, while the destination jumps back to the start of the row and down 0x20 at each row boundary [seen]. It is the merge used when a saved bitmap is laid back down, for instance restoring the shields.

Finally, some drawing is driven from a compact list rather than issued call by call. `fetchNextDrawRecord` (0x1856) [code] reads four-byte records through a cursor in BC: if the first byte is 0xff it is the terminator, and the routine returns with carry set and BC left parked; otherwise it unpacks two little-endian words — one into HL, one into DE — advances BC past all four bytes, and returns with carry clear [code]. A script walker pairs this fetcher with `drawSpriteColumn16`, reading destination/source pairs one after another and laying down fixed sixteen-row columns until the 0xff record ends the list [code] — the way block graphics such as the title layout are painted from a table instead of from individual draw calls.

## Sound

Space Invaders speaks to two write-only sound outputs, sound port 3 and sound port 5, and the code never reads them back. Instead, every bit that is currently asserted is kept in a work-RAM shadow so an update can flip one effect without disturbing the others. `SOUND_PORT3_SHADOW` (0x2094 [seen]) shadows sound port 3, which carries the discrete one-shot and looping effects; `SOUND_PORT5_SHADOW` (0x2098 [seen]) shadows sound port 5, which carries the marching-fleet tone. All sound activity funnels through a handful of read-modify-write helpers over those two cells.

Sound port 3 is driven by exactly two primitives. `startSound` (0x18fa [seen]) ORs a caller-supplied bit mask into `SOUND_PORT3_SHADOW`, writes the result back, and emits it to port 3, turning an effect on without touching the rest. Its complement is loc_19dc (0x19dc [seen]), which ANDs the shadow with a caller mask, stores it, and re-emits, turning an effect off. Each bit belongs to one effect, as the callers make plain: bit 0 is the saucer, bit 1 the player shot (raised by loc_172c with `startSound` 0x02, cleared with mask 0xfd [code]), bit 3 a scoring cue (set by loc_0a5f with `startSound` 0x08 [code], cleared by deactivatePrize with mask 0xf7 [code]), and bit 4 is a one-shot that the fleet code clears on a timer (below).

The flying saucer's looping tone lives on bit 0 and is gated per frame by updateSaucerSound (0x1804 [code]). It first reads `SAUCER_ACTIVE` (0x2084 [code]); when that flag is clear it hands off to stopSaucerSound (0x0707 [code], which is simply loc_19dc with mask 0xfe) to drop bit 0. When the saucer is active it then consults `SAUCER_EXITING` (0x2085 [code]): while the saucer is leaving the screen it leaves the latch as-is and returns, and only when the saucer is fully present does it call `startSound` 0x01 to hold the tone on. When the saucer can appear at all is paced elsewhere by `SAUCER_TIMER` (0x2091 [seen]), a 16-bit counter that loc_0913 rolls down each frame while its gate cell is below a threshold, reloading it to 0x0600 and raising a wrap flag when it underflows.

The marching-fleet tone is the section's most involved piece. The port-5 shadow packs two things at once: its top two bits (mask 0x30) are held select bits, and its low nibble is a one-hot naming which of the four marching tones is currently sounding. Two helpers can silence the note while preserving those select bits: loc_176d (0x176d [code]) reads the shadow and emits only `shadow & 0x30` to port 5, and latchSoundPort5 (0x1770 [code]) is a variant that masks and emits whatever is already in the accumulator rather than the shadow.

The audible march is produced by two cooperating per-frame routines. stepFleetMarchSound (0x1740 [seen]) is the beat engine. Each frame it decrements `FLEET_SOUND_OFF_TIMER` (0x209b [seen]) and, when that note-on countdown reaches zero, calls loc_176d to cut the note, so every beat has a short fixed length. It then checks the enable flag loc_2068 ([guess]); if that is clear it silences and returns. Otherwise it decrements the beat countdown `FLEET_SOUND_TIMER` (0x2096 [seen]), and until that reaches zero nothing further happens. On the beat it emits the full `SOUND_PORT5_SHADOW` to port 5, sounding the current tone; then, provided `ALIEN_COUNT` (0x2082 [seen]) is nonzero (otherwise it silences and returns), it reloads `FLEET_SOUND_TIMER` from `FLEET_SOUND_PERIOD` (0x2097 [code]), sets `FLEET_SOUND_STEP` (0x2095 [seen]) to arm the pitch advance, and reloads `FLEET_SOUND_OFF_TIMER` to 4 so the note will auto-silence four frames later.

advanceFleetMarchSound (0x1775 [seen]) is armed by that `FLEET_SOUND_STEP` flag and does the pitch and tempo work. When the flag is set it walks the parallel ROM tables `FLEET_RATE_THRESHOLDS` (0x1a11 [seen]) and `FLEET_RATE_TABLE` (0x1a21 [seen]), scanning the thresholds for the first entry the live alien count meets or exceeds and copying the matching table byte into `FLEET_SOUND_PERIOD`. Because a smaller alien count selects a smaller period, the beat interval shrinks as the fleet is thinned, which is the familiar acceleration of the march. It then rotates the tone: preserving the 0x30 select bits, it shifts the low-nibble one-hot left by one (0x01 to 0x02 to 0x04 to 0x08, wrapping 0x10 back to 0x01), writes it back to `SOUND_PORT5_SHADOW`, and clears `FLEET_SOUND_STEP`. Independently of that trigger, on every call it decrements `SFX_OFF_TIMER` (0x2099 [seen]); while the timer is still running it returns, and on the frame it reaches zero it calls loc_19dc with mask 0xef to clear bit 4 of the port-3 latch, an automatic timed shut-off for that port-3 one-shot.

## The alien field and its march

The fleet lives in memory as a flat status array: one byte per alien, 0x37 (55) of them — the eleven-wide, five-deep block the player sees. Each player owns a private copy, ALIEN_FIELD_P1 at 0x2100 and ALIEN_FIELD_P2 at 0x2200 [code], with each field pinned to the base of its own memory page. A nonzero byte means that alien is still on screen; a zero means it has been shot away. Which of the two fields is live at any moment is named by ACTIVE_PLAYER_PAGE (0x2067) [code], a single page high-byte — 0x21 for one player, 0x22 for the other — and `activePlayerPageBase` turns that byte into a pointer by shifting it up eight bits, so one set of field-walking routines serves whichever player is up.

A round begins with every alien present. `markAllAliensAlive` [seen] is the primitive: from a base pointer it writes 0x01 into 0x37 consecutive bytes and stops. Two thin seats wrap it — `markAllAliensAliveP1` [code] aims the fill at 0x2100, `markAllAliensAliveP2` [code] at 0x2200 — and game setup fires both back to back so each player's field is fully populated before play starts, alongside the seeding of the per-player records described below.

Every frame the game re-tallies the survivors. `countLiveAliens` [seen] walks the active field's 0x37 bytes, counts the nonzero cells into ALIEN_COUNT (0x2082) [seen], and, when exactly one cell survives, raises LAST_ALIEN_FLAG (0x206b) [code] — the cue for the lone-invader endgame. ALIEN_COUNT is then read all over the per-frame work: it feeds the fleet's marching tempo (the march-sound step indexes a fleet-rate table by the live count [code]) and it trips a threshold at nine (a per-frame check stamps 0xfb into 0x207e once fewer than nine aliens remain [code]), which is the mechanism behind the fleet speeding up as it thins. When the count reaches zero the frame loop diverts away from the play body [code] — a cleared wave.

The fleet's place on screen hangs off a single anchor. The active player's record pointer is built as `(page << 8) | 0xfc` (`activeFieldRecordPointer`), landing at 0x21fc or 0x22fc, and the 16-bit word stored there is the reference alien's position — game setup seeds it to 0x3878 [code]. `loadReferenceAlienState` [seen] reads that word and mirrors it into two places: the still-open anchor pair loc_2009/loc_200a, and ALIEN_DRAW_ADDR (0x200b) [seen]. It then reaches one byte below the pointer for a count, drops that value by one when it reads exactly 0x03, and parks the result in the cell just under the anchor (loc_2008). From the same byte it fixes the travel direction: FLEET_MOVE_DIR (0x200d) [seen] is set to 1 only when the byte reads the edge sentinel 0xfe and cleared otherwise [code]. The anchor pair loc_2009/loc_200a is the grid origin every other alien is measured against — loc_2009 the X reference, loc_200a the Y reference, per the routines below (both still open, kept as loc_).

Turning an alien's slot in the field into a screen position is `alienIndexToScreenCoords`' [code] job. Given an index across the 55 cells it divides by 0x0b (eleven, a row's width): the quotient advances one coordinate by 0x10 per whole row — and is also returned as the row number — while the remainder advances the other coordinate by 0x10 per column, both counting up from the loc_2009/loc_200a anchor [code]. The result is a regular sixteen-pixel grid pinned to the reference point. This resolver drives the redraw handshake: each pass picks the next live alien, resolves its coordinate here, stores it into ALIEN_DRAW_ADDR, and raises ALIEN_DRAW_PENDING (0x2000) [seen]; the draw step consumes that address, blits the sprite, and clears the pending flag [code]. Because a new alien is not queued while ALIEN_DRAW_PENDING is set, exactly one invader is redrawn per pass — the one-at-a-time creep that is Space Invaders' signature march.

While it draws, each alien alternates between two poses. `selectAlternateSpriteFrame` [code] is the small step that flips the pose: it advances the sprite pointer by 0x30 into the second sprite bank, and the draw step invokes it only when the alien's frame selector byte is nonzero [code] — so a marching alien toggles between its two frames as it steps.

The same anchor answers the inverse question — given a pixel position, which alien is there? `scaleXToBlock` [code] and `scaleYToBlock` [code] handle it. Each counts how many 0x10 (sixteen-pixel) steps separate a coordinate from the anchor threshold, first normalizing a wrapped value back into range [code]: `scaleXToBlock` measures the X in L against loc_2009 and returns the block index (the step count less one) in B with the leftover pixels as a residual; `scaleYToBlock` measures the Y in H against loc_200a and returns its step count in C with its own residual. Those two block indices then locate an exact cell in the field, which is how a shot's — or a landing prize's — screen position is mapped back onto a specific alien.

## Player records, shields, shot, and prize

Everything in this subsystem pivots on a single selector byte at 0x2067, the active-player page marker. Its full value is the high byte of the current player's RAM page, and its low bit distinguishes the two players. `activePlayerPageBase` (0x1611) shifts that byte left eight bits to land HL at the top of the page — 0x2100 for one player, 0x2200 for the other [code]. `activeFieldRecordPointer` (0x0886) performs the same shift but forces the low byte to 0xfc, addressing a fixed record slot near the top of the page (0x21fc / 0x22fc) [code], while `readActivePlayerPageTopByte` (0x092e) builds the base the same way, forces the low byte to 0xff, and returns the byte living at 0x21ff / 0x22ff in A [code]. The low bit alone drives two further selectors: `currentPlayerRecordPtr` (0x09ca) tests bit 0 and returns PLAYER1_OBJ_DESC (0x20f8) when it is set or PLAYER2_OBJ_DESC (0x20fc) when it is clear [code], and `readActivePlayerInput` (0x17c0) uses that same bit to choose which hardware input port to read — port 1 for the bit-set player, port 2 for the other — leaving the raw port byte in A [code]. So both players share one body of code that transparently reads and writes whichever player's page and control panel is currently live. `stageActivePlayerFieldSave` (0x0878) is the setup step that pairs with the record pointer: it loads a count byte from loc_2008 into B and a 16-bit pointer from the word at loc_2009 into DE, then builds the active player's record pointer through `activeFieldRecordPointer`, so HL, B, and DE are all seated before a save runs [code].

The two object descriptors that `currentPlayerRecordPtr` chooses between are the heads of each player's per-field record. `advanceRecordTotals` (0x01d9) folds new deltas into such a record: it reads a delta from [HL+1], adds the caller's C into [HL+2], adds that delta into [HL+3], and returns the second running total in A — a paired accumulate of the C and delta values into the record's two totals [seen]. Records move in and out of a shared eleven-byte work buffer at loc_2073 through a matched pair: `copyRecordToWorkBuffer` (0x0550) first stashes A at loc_207f, then copies eleven bytes from the caller's source (DE) into loc_2073 [seen], while its twin `copyWorkBufferToRecord` (0x055b) copies those eleven bytes back out of loc_2073 into the caller's destination (HL) [code]. A separate `loadDrawSequenceBlock` (0x0ae2) copies a twelve-byte block from the caller's source into a fixed work slot at loc_20c2 [code].

Each player also owns a shield backup region — PLAYER1_SHIELD_BUFFER at 0x2142 and PLAYER2_SHIELD_BUFFER at 0x2242 [code]. `initShieldBuffers` (0x01f8) fills one of these regions by replicating the 0x2c-byte template at loc_1d20 four times in a row, advancing the destination by 0x2c each pass and returning the end pointer in HL [code]; the four copies are the four shields, each 0x2c (44) bytes. `initPlayer1ShieldBuffers` (0x01ef) and `initPlayer2ShieldBuffers` (0x01f5) are the two entry points that seed HL with the player-1 or player-2 buffer base before running that shared body [code]. Those same buffers are the counterpart of the shields on screen, moved by `drawOrSaveShields` (0x021e): it stores the caller's mode byte in SHIELD_SAVE_RESTORE_MODE (0x2081), then walks four blocks of 22×2 bytes — 0x2c bytes each, exactly one buffer slot — down the screen starting at SHIELD_VRAM_BASE (0x2806), stepping 0x02e0 between blocks [seen]. Re-reading the mode flag on every pass, a nonzero mode captures the on-screen region into the buffer (a save) while a zero mode ORs the buffered bitmap back onto the screen (a restore/draw) [seen]. `saveOrRestorePlayer1Shields` (0x021b) and `saveOrRestorePlayer2Shields` (0x0214) are the per-player entry points that seed DE with the matching buffer base and pass the caller's mode straight through [code]. Taken together with the init routines this is a full per-player shield lifecycle: seed four backup slots from the template, then save or restore that player's four on-screen shields as play alternates between the two players.

Sprites are described by a five-byte record read by `loadSpriteDescriptor` (0x1a3b): the first two bytes become DE, the third goes to A, the fourth to C, the fifth to B, and HL is finally rebuilt as C:A [code]. Two callers specialize it. `loadPlayerShotDescriptor` (0x0430) points HL at PLAYER_SHOT_DESC (0x2027), the player-shot descriptor, and runs that read so the shot's C:A pointer ends up live in HL [code]. `resolveSpriteScreenAddr` (0x0742) reads the descriptor at loc_2087 the same way and then folds the resulting C:A coordinate through `coordToScreenAddr`, leaving a screen address in HL and the descriptor's pointer in DE [code].

The player's shot is armed by `advanceRoundState` (0x1618), a gate that acts only when the round is armed (loc_2015 == 0xff) and the field is idle — GAME_OBJECT_TABLE (0x2010) and loc_2011 both zero, and PLAYER_SHOT_STATUS (0x2025) zero [code]. Past those checks it splits on GAME_IN_PROGRESS (0x20ef) [seen]. In attract/demo mode (flag clear) it force-arms the shot by writing PLAYER_SHOT_STATUS = 1, advances the demo-script pointer ATTRACT_DEMO_PTR (0x20ed) by one — wrapping its low byte back to 0x74 once it reaches 0x7e so it loops over a fixed window — and copies the byte it now points at into loc_201d as the canned input [code]. During real play (flag set) it instead reads the live fire button through `readActivePlayerInput`, masking bit 0x10, and leans on FIRE_BUTTON_LATCH (0x202d) as a debounce: when the latch is already set it waits for the button to be released before clearing it, and only when the latch is clear and the button is freshly pressed does it arm the shot, setting both PLAYER_SHOT_STATUS = 1 and the latch = 1 so one press yields exactly one shot [code]. PLAYER_SHOT_STATUS is thus the shot's state cell — it gates re-entry here, and elsewhere it drives a port-3 sound bit that is raised while the status is nonzero and masked off when it returns to zero [code].

`selectAlienShotRate` (0x170e) decides how fast the aliens return fire. It takes the byte one past the active player's object descriptor — reached through `currentPlayerRecordPtr` then +1 — as a key and scans the four-entry ALIEN_SHOT_RATE_THRESHOLDS table (0x1cb8) for the first entry greater than or equal to that key; the parallel ALIEN_SHOT_RATE_TABLE (0x1aa1) supplies the rate byte at the matching index, which it stores at loc_20cf for the shot stepper to consume [seen]. The two tables run in lockstep, so a larger key advances to a later entry and a different firing rate [seen].

The bonus prize is tracked by PRIZE_ACTIVE (0x2002) [code]. `deactivatePrize` (0x154a) clears that flag and then masks bit 3 off the port-3 sound shadow (through loc_19dc with 0xf7), silencing the prize's sound [code]. `retirePrize` (0x1545) is the fuller teardown: it first drives PLAYER_SHOT_STATUS to 4 — a retiring state distinct from the arm value of 1 — and then continues into `deactivatePrize` to clear the flag and its sound [code]. The shared PLAYER_SHOT_STATUS cell is what links the prize back to the shot subsystem.

Scoring that this subsystem feeds is staged as a small pending-add packet, all of it gated on GAME_IN_PROGRESS. When a scoring event fires during play, SCORE_ADD_VALUE (0x20f2) receives a looked-up point value, SCORE_ADD_VALUE_HI (0x20f3) is cleared to zero, and SCORE_ADD_PENDING (0x20f1) is raised to 1 to signal the display code that an addition is waiting [code]. When the game is not in progress the packet is left untouched, so no score accrues in attract mode [code].

## Frame tasks, timers, boot, and scoring

Before any per-frame bookkeeping runs, the machine seeds its work RAM from a fixed ROM template. That template lives at WORKRAM_INIT_IMAGE (0x1b00) [seen], and the copy always lands at the base of work RAM, ALIEN_DRAW_PENDING (0x2000) [seen]. Two entry points feed the same forward copy. `seedWorkRamImage` [code] pins the length at 0xc0 bytes and then falls into `initWorkRam` [code], which is also reachable on its own from the boot path with the source preset to 0x1b00, the destination to 0x2000, and the caller's byte count already supplied. Either way the effect is a straight byte-for-byte copy of B bytes (0xc0 from the fixed entry) out of the ROM image and into the work-RAM base — memory is the only result. This is how the alien-draw region and the state cells packed just above it start from a known image rather than from whatever the previous round left behind.

Sitting 0x10 bytes into that same freshly-seeded region is GAME_OBJECT_TABLE (0x2010) [code], the head of the live object/state block. Its leading byte doubles as a "field busy" indicator: the pre-round gate in advanceRoundState refuses to advance while either 0x2010 or the byte immediately after it is non-zero, so the table's first cell reading zero is part of what tells the round logic that the playfield has settled.

The game-active flag is its own tiny subsystem. GAME_ACTIVE (0x20e9) [seen] is a single byte written only through one shared store point, loc_19d3 [seen], which drops the accumulator into 0x20e9 and returns. `setGameActive` [code] reaches it with the accumulator holding 1, `clearGameActive` [code] with it cleared to 0, so those two named routines are simply the "raise" and "lower" faces of the same one-byte flag. The flag is set and cleared from several game-control sites and polled from several more, all still loc_ and open [guess]; within this scope the only established fact is that 0x20e9 carries a 0/1 game-in-progress state.

A second flag cell, TASK_FLAGS (0x20c1) [code], is written the same minimal way — loc_1982 stores the accumulator into it. It is read from a number of places (still loc_, open [guess]), but on the write side it is just a work-RAM flag byte that one routine latches for others to test. TWO_PLAYER_GAME (0x20ce) [code] acts as a mode guard rather than a task flag: blankScreenStrip, for instance, tests it first and returns without blanking its VRAM strip whenever the cell is non-zero, so a set 0x20ce steers mode-dependent work away from the one-player path.

Timing is handled by a rolling countdown rather than dedicated timer hardware. TIMER_RELOAD (0x0600) [code] is the 16-bit value the countdown is refilled with — despite its address-shaped name it is used here as a literal reload count, not a pointer. loc_0913 [code] decrements a 16-bit timer (SAUCER_TIMER, 0x2091) once per pass while its gate byte at 0x2009 stays below 0x78, and when that timer reaches zero it reloads it to 0x0600 and raises a wrap flag (0x2083) for the next stage to notice. So 0x0600 is the period of that timed event expressed as a decrement count.

Starting-ship count comes straight off the cabinet. `readStartingShips` [code] reads input port 2, keeps its low two bits, and adds 3, yielding a value in the range 3..6 — the two-bit lives selector biased into an actual starting ship count — and leaves the result in the accumulator for its callers (still loc_, open [guess]).

Finally, the coordinate-to-grid scaler. `countStepsToThreshold` [code] counts, in C, how many 0x10-sized steps it takes to lift A up to or past the threshold held in H. If the opening compare finds A already at or beyond H it first runs loc_1590 [code], which walks A upward by 0x10 at a time — counting each step in C — until A is no longer negative, pulling a wrapped or low value back into range; the main loop then keeps adding 0x10 and bumping the count until A finally reaches H. Carry is returned explicitly cleared, a live-out the callers depend on. Those callers are scaleXToBlock and scaleYToBlock [code], which run an object's X or Y cell against a threshold and turn the returned step count (less one) into a grid block index, keeping the leftover as the sub-block residual. That is how a pixel coordinate becomes the block-addressed position the rest of the drawing code works in.

## What is not described yet

The control-flow spine — the main frame loop, the object-state dispatcher and its per-state handlers, the two RST
interrupt handlers, collision, and the attract-mode demo — is not yet recovered and is not described here. A few
helper routines also keep `loc_<addr>` names because their role is not yet confident from the code alone:
`loc_0a5f` (queues a points value, but hit-reward vs bonus is open), `loc_172c` (gates a sound bit on the shot
status), and `loc_073c` (draws a descriptor sprite, saucer-vs-generic open). The reference-alien anchor pair
`loc_2009`/`loc_200a` is the rack origin but its X/Y axis order is unpinned; the strip target `loc_391c`, the
alien-shot rate cell `loc_20cf`, the saucer sprite pointer `loc_2087` and active flag `loc_2083`, the object work
buffer `loc_2073`, and several other work-RAM and ROM cells keep `loc_` names pending grounding. These resolve at
grounding or when their callers lift and their roles become confident from the code.
