# Centipede — how the machine works

Current-state description of the centiped port's idiomatic layer, derived from the routine bodies. It is
regenerated whole each understanding pass, never patched. Names and roles are the single source in
`idiomatic/names.js`; this document cites them and never contradicts them.

**Grounding tags.** `[seen]` a role confirmed by a MAME observation; `[code]` a reading from the routine
behaviour, not yet MAME-grounded; `[guess]` uncertain. A cell whose role is not yet confident keeps a
`loc_<addr>` placeholder until the routines that touch it are all understood.

This first pass covers the batch-1 leaf routines: the POKEY sound engine, the segment/head motion helpers,
playfield and mushroom seeding, the high-score/EAROM path, object-slot marshalling, and text plotting.

## collide-hs cluster

**Object column-collision test.** During play `detectColumnCollision` runs many times per frame [seen] (reached ~16624 times in the capture). It answers one question about a query object X: does any other live object share X's column and sit within a short row band of it? The routine first stamps X into the scratch pair loc_8b/loc_8c — loc_8b = X, loc_8c = X+1 [seen] (pc 0x2c6f, 0x2c71) — using loc_8b as the "skip my own slot" reference for the scan. It then reads X's three per-slot attributes once: the column from loc_64+X, the fine row from loc_54+X, and a row-delta fold key from loc_44+X. Walking slots Y = 0x0c down to 0, it skips any slot whose column (loc_64+Y) differs, any slot already retired — loc_34+Y >= 0xf4 marks a dead slot [seen] (armSlotState stamps 0xff there at pc 0x2cd2; the play loop otherwise churns loc_34 between live values, pc 0x297a 0x4->0x6) — and X's own slot. For a surviving neighbour it folds the wrapped row distance (loc_54+X - loc_54+Y) with X's delta key and reports a hit when the result lands in the top band (>= 0xf4), returning carry set on the first collision. The four parallel arrays loc_34/loc_44/loc_54/loc_64 form the shared object table; movement routines outside this cluster write them every frame (loc_54 fine-row at pc 0x2a9b 0x7e->0xee, loc_64 column at pc 0x2a94 0xf6->0xe0) [seen], so they stay loc_ pending a fuller census.

**Arming a slot.** `enterArmBlockUnlessValueHigh` is the compare-first door into the shared arm block [seen] (reached, pc 0x2cea). It tests the incoming value against 0x0e and hands the resulting carry to armSlotState as a bail flag, so the block arms only when the value is below 0x0e. When it does arm, armSlotState lays down a fixed template — loc_87=0x30, loc_42=0x28, loc_43=0x20, retires the addressed slot with loc_34+X=0xff, zeroes loc_b2..SFX_TIMER_CH4, and (unless loc_86 is negative) sets SFX_TIMER_CH1_PRIORITY=0x13 — all observed firing together [seen]. That loc_34+X=0xff stamp is the same retirement marker the collision scan treats as a dead slot, tying the two routines to one object-table convention.

**Drawing the grid side borders.** `drawGridSideBorders` paints the two vertical edges of the play grid [seen] (reached: it builds the cursor at pc 0x26cc/0x26e8 and spins the run counter at pc 0x26da/0x26fc). It assembles a 16-bit draw cursor in loc_91 (low) / loc_92 (high) by folding fixed constants against the orientation bytes loc_f6/loc_f7 — 0xdf^loc_f6 into loc_91 with a masked 0x04^loc_f7 into loc_92 for the first side, then 0x5f^loc_f6 and 0x06^loc_f7 for the second — so the same code addresses opposite edges under screen flip. loc_f6/loc_f7 held 0 throughout this upright capture, so their flip role is [code] only. Each side then walks a fixed six-cell run counted down in loc_8b, handing every cell to `writeMaskedByteAndAdvancePointer`; a sign-bit down-counter (seeded from loc_a5 on the first side, from 6-loc_a6 on the second) picks a 0x1f border tile while non-negative and a 0x00 blank once it goes negative, with the polarity inverted between the two runs so the edges mirror. writeMaskedByteAndAdvancePointer writes each masked cell through the loc_91/loc_92 pointer and advances it, running heavily across all rendering (); it is the observed consumer that confirms the cursor drawGridSideBorders builds [seen] (pc 0x3847->loc_91, pc 0x384c->loc_92). loc_91/loc_92 are the render-wide tile-draw pointer (pc 0x3895/0x389b advance it) and loc_8b is general zero-page scratch reused by dozens of routines, so all three stay loc_. loc_a5 was seen changing (pc 0x2536 0x2->0x0) but its writer lies outside this cluster; loc_a6 never moved here ([code]).

**High-score table, EAROM, and the checksum.** The 64-byte high-score block lives in RAM at HIGH_SCORE_TABLE..0x01b7, a mirror of the EAROM device. `loadHighScoreTableFromEarom` refreshes that mirror [seen]: for X = 0x3f down to 0 it reads cell X through readEaromCell and stores it into HIGH_SCORE_TABLE+X (the whole mirror observed filling, pc 0x3aa2 across 0x0178..0x01b6), then parks the writeback cursor loc_f9 at 0xff — "nothing pending" — because the mirror is now fresh from the device. readEaromCell drives the hardware: it latches the address at 0x1600+X, pulses the 0x1680 control register 8/9/8/0, and reads back 0x1700+X, and is the primitive the load calls per cell [code — its own address-latch/data-out writes are memory-mapped EAROM, not re-derivable from the RAM write-trace]. loc_f9 is later ticked by the EAROM flush path (pc 0x3b22 0x3d->0xff, pc 0x3b36 0x3d->0x0) [seen], which sits outside this cluster, so the cell stays loc_. The last used byte of the block, HIGH_SCORE_CHECKSUM (index 0x3d), is the table's integrity checksum [seen] (written 0x0->0x8b at pc 0x3a5c). `foldHighScoreChecksum` guards it: seeding 0xff it XOR-folds the table bytes HIGH_SCORE_TABLE..0x01b4 into one byte, publishes the fresh fold to HIGH_SCORE_CHECKSUM, and returns the old-XOR-new delta — zero exactly when the table is unchanged since the last fold. That fold never ran during coin->start->play, so foldHighScoreChecksum is [code] here (its publish site pc 0x3a18 never fired). `foldSignedMagnitude`, finally, is the tail of the 6502 abs idiom — it passes a non-negative A through and two's-complement negates a negative one, threading the sign in as the N-flag input rather than recomputing it; it touches no memory, so the write-trace cannot witness it and it stays [code].

## Segment and head motion (motion-a cluster)

The centipede's body advance is driven column by column. Given a starting column index, `advanceSegmentColumns` walks the columns downward one at a time; for each it reads the per-column body cell `SEGMENT_COL_BODY` (0xcf,X, an array over 0xcf/0xd0/0xd1) and isolates its low-5-bit step index. [seen: pc 0x33d3 drives 0xcf/0xd0/0xd1 0x20->0x1f] A control bit selected out of the `IN1` port -- bit 7 for columns >= 2, bit 6 for column 1, bit 5 for column 0 -- picks the branch. [code] On the normal branch the step index is nudged toward its clamp, backed off one when it is already past 0x1b or, every eighth frame, when the low three bits of the free-running `SEGMENT_MOVE_FRAME_COUNTER` (0xd4) are all set. [seen: 0xd4 0x0->0x7c, free-running] On the control branch the index instead wraps forward by 0x20 or re-arms to the 0x1f clamp.

Whichever branch runs, the column body is stored and its timers serviced. A shared `SEGMENT_RELOAD_TIMER` (0xd2) reloads to 0xf0 unless `IN1` bit 4 is set, and while it counts down it blanks that column's body and life timer -- a global freeze on segment motion. [code: 0xd2 stayed 0 in this capture] The column's own `SEGMENT_COL_LIFE_TIMER` (0xcc,X) then decrements, and only the pass on which it reaches exactly zero opens the carry gate. [seen: pc 0x33f1 0xcc 0x78->0x0]

When the gate opens, a small per-column row delta -- zero for column 0, and for the others selected out of the packed `loc_d3` byte (0xd3) -- is folded, together with a +1, into the twin move accumulators `SEGMENT_MOVE_ACCUM` (0xca) and `SEGMENT_MOVE_ACCUM_B` (0xc9), and the column's `loc_c5` (0xc5,X) is bumped. [seen: 0xc5 watched changing; code: the accumulator fold] After the last column, the row index Y (the top three bits of `loc_d3`) selects a threshold from the `SEGMENT_ROW_THRESHOLD_TABLE` (ROM 0x3413); that threshold is subtracted from the accumulator. A borrow aborts the commit; otherwise the accumulator keeps the difference, the row-crossing counter `SEGMENT_ROW_CROSS_COUNT` (0xcb) is bumped -- twice on the top row -- and control passes to the phased-counter tail. [code]

The head rides on top of this. `advanceHeadOrientation` has two entries over one body. The wrap-guard unfolds the head's orientation byte (XOR the 0xef fold mask) and returns once it reaches the top of its range, otherwise re-seeding a fresh heading and velocity. The per-tick entry, every fourth tick (gated on 0x00 & 0x03), rotates the head orientation in `loc_40` (0x40) by one modulo four and re-folds it into 0x30..0x33; it then resolves the tile the head faces from its position coordinate (0x70) and, only when that cell reads in the band [0x3c,0x40), stamps a masked marker back through the working tile pointer (0x32/0x33). [code: this routine did not reach its role writes in the capture; head cells are seeded from seedWaveState at 0x20ec/0x20f2] The signed steering deltas that move the head are conditioned by `clampAndHalveSignedDelta`: a pure helper that snaps a mid-range byte to the nearer playfield rail (the extremes pass through), arithmetic-halves it with the sign preserved, and packs the dropped low bit into a separate byte. Its output is consumed every frame by the position accumulators at 0x84 and 0x63. [seen: consumers the per-frame motion driver (0x84 0x0->0x80) and its sibling motion driver (0x63 0x81->0x34) both reached]

Two support routines round out the cluster. `armSlotState` is a carry-gated slot initializer: with entry carry clear it stamps a batch of fixed timer/flag constants (0x87=0x30, 0x43=0x20, 0x42=0x28), retires slot X's row byte by writing 0xff into 0x34,X, arms the 0xb7 flag to 0x13 unless the 0x86 sign cell is negative, and clears the per-object working flags 0xb2-0xb5/0xb8; with entry carry set it touches nothing. [seen: full constant stamp observed] Finally, `copyZpStateToSnapshot` refreshes the page-1 buffer the high-score checksum folds: it marks 0xc1/0xc2 with 0xff, copies the 0x02.. and 0x1a.. zero-page blocks up into the 0x0178/0x0181 snapshot buffers (index 8..0), and hands off to the checksum fold. [seen: block copy observed at pc 0x26ae/0x26b3] `broadcastByteToStateBlock`, which fans one source byte across the sound/state block and the flip-screen latch, was not exercised in this capture and is grounded [code] from its frozen body.

## Playfield grid, segment sprites, and the high-score EAROM

Centipede's playfield is a coarse tile grid whose cells live in the object/framebuffer pages `$0400`-`$07ff`. Everything in this cluster either lays that grid down, reads a cell out of it, turns a segment into drawable sprites, or persists the high score to NVRAM.

**Seeding the grid.** At the start of a board, `resetPlayfieldAndSeedMushrooms` wipes the slate and scatters the mushroom field. It first writes a fixed palette colour into color RAM (`$1404` = `0x0f`) [code — palette RAM is not in the state diff], clears the current object's status cell (`$c2+$88`) [seen], and reads the first palette colour record (via loadPaletteRecordPair), then zero-fills all four object pages `$0400`-`$0700` in one sweep [seen: pc 0x28d5]. With the field blank it runs a 46-column sweep: each column composes a pseudo-random cell pointer in the shared zero-page pointer word `$8d`/`$8e` from the POKEY random register (`$100a`) [code — a read-only MMIO RNG] masked with a cycling column stride held in `$8b` (0x1b..0x02) [seen: pc 0x292f], parking the outer column counter in `$8f` across the inner clobbers [seen: pc 0x2900]. Every column unconditionally stamps the cell with `0x3f ^ $ef` [code]; where the chosen cell is empty and passes a density test (the threshold flips on whether the tile mask `$ef` is zero) it additionally bumps the per-object mushroom tally `$d7+$88` [seen: pc 0x291c]. The random layout is only reproducible while the poly counter is idle, so this is a clock-free step. It then tail-falls into the shot/start-cell seeding, so its work and that seeding share one return.

**Reading the grid back.** `resolveTileCellAtXY` is the shared "where does this pixel land, and what's there" helper. Given a screen X in A and a row in Y it derives a column (`A>>3`, rounded by bit 2), folds the row (`Y*8`, clamped and merged through `$8b`) into a pointer, and assembles the tile-map address in the same convention the seeder used, landing it in the pointer word `$32`/`$33` [seen: the pointer bytes are written tens of thousands of times, pc 0x2c34/0x2c64/0x2c4f/0x2c52]. A top-row wrap fixes the last block of row 7. It then dereferences `$32`/`$33`, and if the fetched cell is non-empty folds the same `$ef` mask back in before returning it in A with N/Z set — so callers can branch on empty-vs-occupied and read the cell's attribute in one call. `$32`/`$33` is thus the game's canonical tile-map cursor, reused by every tile test-and-position path.

**Turning a segment into sprites.** `rebuildSegmentSpriteTables` regenerates one centipede segment's five parallel 12-entry sprite-attribute tables (`$34`, `$44`, `$54`, `$64`, `$74`) for the currently-selected object `$88` [seen: 64 role writes across those ranges]. It only refreshes when the object's redraw gate `$94+$88` is clear, at which point it sets the busy bit `0x80` in the status cell `$c2+$88` [seen: pc 0x2329] and, when the segment sub-count `$9c` warrants, ticks the segment length `$9a` (wrapping `0`->`0x0c`) and reseeds the sub-count to 1 or 2 depending on the `$ab` threshold. It seeds the `[0]` entries — a code marker (`$34`=3), the length (`$74`), a signed delta in `$44` (negated unless `$00` bit1 is set), a colour `0xf8 ^ $f0` in `$64`, and a base `0x80` in `$54` — then copies descriptor rows (`$43`/`$53`/`$73`) into slots `1..length-1`, and random-fills the remaining slots from `$100a` when the length isn't yet full. Finally it stamps the redraw gate `$94+$88` to `0x0c` [seen: pc 0x23d3] and latches `$97` from `$fe` [seen: pc 0x23d7], handing the finished tables to the (not-yet-decompiled) sprite blitter.

**Two small table helpers** feed drawing and table selection. `plotZpTableByteAtCursor` reads one byte from the zero-page source table `$001A,Y` and plots it through the draw cursor, called repeatedly to lay a row [code — a read-only fragment, unreachable-confirmable from a write trace]. `readFdBitsTableByte` picks a ROM table byte at `$21bf` using bits 5-4 of the control byte `$fd` (shifted to an even index 0/2/4/6), returning the byte in A and the index in Y for a parallel table [code — pure reader, 0 writes].

**Persisting the high score.** `readEaromCell` is the primitive that reads one byte of the ER2055 high-score NVRAM. It latches the cell index by writing to the address window `$1600+X`, pulses the control register `$1680` through `0x08` (read mode, clock low), `0x09` (clock high), `0x08` (falling edge latches the addressed cell into the data-out register), reads the byte back from `$1700+X`, then releases the chip by writing `0x00` [code — the EAROM is memory-mapped hardware whose address-latch and data-out accesses are not re-derivable from a RAM write-trace]. The byte comes back in A for the high-score display/compare path.

## Timing and periodic-event layer

The timer cluster is the game's clockwork: a bank of countdown bytes, a few one-shot column and spawn countdowns, and the small compute helpers periodic code leans on. Nothing here draws anything itself — each routine ticks a counter and, the moment it expires, arms the cell some other subsystem is waiting on.

At the centre is **serviceTimerBank**, run once per service pass. It walks the fourteen countdown bytes based at $34 from index 13 down to 0 [seen: pc 0x270d writes the $34..$3f/$41 bank, 0xff->0xf9]. A byte below 0xF9 is resting and left alone; a byte at exactly 0xF9 is a just-expired marker; a byte at 0xFA or above is a live countdown that gets decremented, and on reaching zero it — like the marker — asks to re-arm the master. Re-arming touches only the master slot (index 0x0D) and only while the $43 step counter's gate bits ($43 & 0xAF) are clear, at which point the master cell $41 is reloaded with $d7 ^ $ef [seen: pc 0x271f re-arms $41 0xb8->0xb7]. After the scan, still only while that gate is clear, the routine paces itself off the global frame counter $00 — acting every fourth frame, ($00 & 0x03)==0 [seen: $00 is the main frame counter, pc 0x38de walks 0x0->0x86] — and nudges the $43 step counter up by one until it saturates at 0x28. The single step carrying $43 across to 0x28 [seen: pc 0x2736 walks $43 0x20->0x28] seeds a 16-bit pointer pair, $da=0x00 and $db=0x04 (i.e. $0400) [seen: pc 0x273e arms $da], which a later display routine consumes and drives hard [seen: pc 0x2d58 rewrites $da over 11k times].

**tickColumnCountdown** is a self-contained one-shot on the column countdown $a1. Almost every tick it just decrements $a1 and returns [seen: pc 0x22fa walks $a1 0x60->0x0, ~3550 times]; on the tick that wraps it through zero it reloads a fresh random interval — a byte from the hardware random source $100a masked to 0x2f then floored to at least 0x0f [seen: pc 0x2305 reloads $a1 to 0x0f] — and re-arms two companions: $b5 to 0x14 [seen: pc 0x2309], consumed downstream [seen: pc 0x3096 walks $b5 0x14->0x5], and the shared master cell $41 to 0x14 ^ $f2 [seen: pc 0x230d]. Note $a1 wears two hats: this routine treats it as one countdown byte, while the spawner below indexes it as a per-channel reload table, so the cell stays loc_ pending a pass that reconciles the two [code].

**spawnActorOnTimer** is the gated periodic actor spawner. It does nothing unless the enable flag $97 is set and the busy flag $87 is clear [seen: $97 toggles 0/1 pc 0x298c; $87 clears 0x30->0x0 pc 0x241f]. While enabled it ticks its own countdown $a0 and leaves as long as it is still running [seen: pc 0x2be9 decrements $a0 0xc0->0xb0]. On the frame $a0 hits zero it scans the twelve actor slots based at $34 for a free one (high bit set), high index to low; finding one, it claims the slot and seeds that actor's field bytes — the orientation-folded $64+y (0x40 ^ $f0), the motion seeds $54+y and $74+y, and a variant chosen from a random bit of $100a into $44+y [seen: pc 0x2c02/0x2c07/0x2c0c/0x2c29 seed the per-slot fields]. It then reloads $a0 from the per-channel value in the $a1 table, ratcheting that value down by 8 while it stays at or above 0x60 so spawns arrive progressively faster [seen: pc 0x2c17 writes back the ratcheted reload, pc 0x2c19 reloads $a0], and bumps the per-channel spawn counter $94+x [seen: $94 is a counter, pc 0x383b]. Because $a0 is managed only here, it is the clearest naming candidate — proposed SPAWN_TIMER.

**stampEmptyTileCell** is the tile-stamping step invoked as the playfield is walked. It dereferences the 16-bit tile pointer $32 and does nothing if the pointed cell is already occupied [seen: $32 is a live tile pointer, pc 0x2c34/0x2c64 step it]; otherwise it reads the low five bits of the pointer as a column code, rejects the two edge columns, and consults the fold mask $ef to pick which column band is stampable and, within that band, whether the write also bumps a per-slot counter $d7+x [seen: pc 0x2ba9/0x2bd4 bump the $d7,X counter]. The stamp itself writes 0x3F ^ $ef through the pointer, so one routine covers both mirrored orientations depending on whether $ef is zero.

**stepPhasedCountersAndWrapCells** is a per-tick bookkeeping step shared with the segment-column subsystem. A two-bit phase from $d3 [seen: $d3 carries the phase, pc 0x256b] selects a sub-step subtracted from a 16-bit accumulator ($c9 low, a high byte, and wrap counter $c8): the accumulator floors at zero rather than borrowing past it, and $c8 is bumped as the low byte rolls [seen: pc 0x3489 bumps $c8 0->1; cleared elsewhere pc 0x2600]. It then ticks frame counter $d4 and, only on even frames, runs a two-pass normalisation of the three coordinate cells $c5..$c7 into a modulo-0x10 grid — pass one subtracts 0x10 from any cell at or above 0x10, and only if nothing changed does pass two subtract 0x11 from each nonzero cell, stopping at the first negative result [seen: pc 0x34a3 walks $c5 0xe0->0x0]. These cells are co-owned with advanceSegmentColumns, so they remain loc_.

**stepAxisBySelectorBits** is the small axis-step helper the movement code calls constantly [seen: reached ~28800 times]. It reads the top two bits of the accumulator as a selector and produces a one-step nudge of an axis value — step down clamped into 0xFA..0xFF, step up clamped into 0x01..0x06, or zero the axis — then shifts the selector out so the next call reads the following pair. Its stepped result is stored to the actor axis cell $bd and consumed immediately by movement [seen: pc 0x3a03 writes $bd 0xbf->0x36 on every call], which is what grounds its role even though the idiomatic form is written as a pure compute helper.

## Round-start seeding and shared no-op returns

When Centipede starts a wave it lays down the initial state of the first playfield objects through a small family of straight-line seeders, then falls back on a couple of shared bare-return landings wherever a control path has nothing to do. This cluster is those seeders and those returns.

The connective tissue running through every seeder is the screen-flip mask block at $ef-$f2 [code]. In an upright cabinet these bytes are all zero, so every `value ^ $ef`, `^ $f0`, `^ $f1`, `^ $f2` fold in the game leaves its operand unchanged; when the cabinet view is flipped the same folds mirror coordinates and orientations. MAME confirms this indirectly: throughout coin->start->play the whole $ef-$f8 block holds only 0 [seen], and the seeded start cells come out at their un-mirrored values because the masks were zero.

**seedWaveState** ($20e8) [seen] is the wave-start initializer. It folds the two config/mask bytes into working cells -- $40 := 0x1c^$ef and $70 := 0xf8^$f0 [seen] -- which the head-steer routine later reads as its orientation and its tile-resolve X. It then rejection-samples the POKEY RANDOM register at $100a [code] (keep the top five bits, require >= 0x10) and stores that value minus four into $60 [seen], the per-round random parameter; MAME catches this as an in-write change (0xa4->0x9c) at that store. Finally it picks a small count of 3 or 2 into $80 by reading the per-object table $ab indexed by the current slot $88 [seen], and clears $50 and $b8. This routine is also the target of the head-orientation wrap guard: when the head's unfolded orientation has not yet reached the top of its range, that guard re-seeds a fresh wave state here rather than returning.

**seedSegmentSpawnState** ($21c7) [seen] seeds the spawn cells for whichever object slot $88 currently selects. It first derives a selector: 0x02 normally, dropped to 0x01 when the slot's gate byte $ab[X] is zero and the config-derived threshold ($fd & 0x40)|0x10 is >= the slot's $a9[X] entry (a comparison — $a9[X] is read, never written) [seen]. It stashes that selector in $81, then writes a possibly two's-complement-negated copy into $51 depending on a random bit of $100a. The remaining spawn cells are stamped to fixed values -- $71 := 0x60^$f0 (the heading), $61 := 0xff, $41 := 0xf8, $a1 := 0x60, $b5 := 0 -- all confirmed by MAME at [seen]. These same cells ($41/$61/$71/$a1/$b5) are then continuously rewritten by the unseen per-object mover and AI routines, so they read as parallel object-attribute arrays whose slot-0 initial state this routine establishes.

**seedPlayerShotStartCells** ($2932) [seen] seeds the six player/shot start cells. Three are mirror-folded against the mask bytes -- $43 := 0x10^$f2, $73 := 0x08^$f0, $72 := 0x0c^$f1, $42 := 0x11^$f2 -- and two are the un-mirrored midline seed $62 = $63 = 0x80. MAME shows exactly 0x10/0x08/0x0c at those cells [seen], which both confirms the routine and independently confirms the masks were zero. Downstream gameplay then drives these same cells as live positions (the $62/$63 pair, for instance, moves 0x81->0x34 under the player/shot updater).

**seedStateBlockConstants** ($252a) is meant to stamp the $ef-$f8 block back to fixed startup constants (0xf8, 0xff, 0xfe, 0xe0, 0xc0, 0x40, ...), set the $1c07 flip latch to bit7, dead-store $2400, and clear $bd/$bf. Its role is NOT grounded by this capture and is flagged [code]. MAME reaches the 0x252a-0x2560 PC range but the writes there contradict the frozen oracle at identical PCs: the $ef-$f8 cells receive only 0, $1c07 receives 0 rather than 0x80, $2400 is never written, and pc 0x2536 -- which the oracle disassembles as `sta $f4` -- instead clears $a5 to 0 in MAME. Every other routine in this cluster matches its oracle PC-for-PC, so the divergence is localized to this routine and looks like a faithful-but-wrong oracle (the real code appears to clear the mask block, not seed non-zero constants). This is the one reconciliation item to hand back to the LEAD.

**returnImmediately** ($2acd) [code] and **returnNoop** ($2ec5) [code] are the cluster's shared bare-return landings. returnImmediately is the RTS tail of a neighbor routine, exposed as a second entry that another path tail-calls; its neighborhood executes in the trace (adjacent write PCs appear) but a no-op has no state effect to observe, so it stays [code]. returnNoop is the lone RTS that the steer paths fold onto when there is nothing to steer; that branch was not exercised in this capture. Both names describe their (empty) effect correctly.

## Object marshalling, palette fan-out, and text plotting (objinit-plot cluster)

The routines in this cluster are the small support layer that feeds Centipede's per-object machinery, primes its colour hardware, and paints characters — they surround the heavier motion and rendering code rather than forming a single loop, so their common thread is that each one grooms state that a larger consumer immediately uses.

The object side rests on a set of parallel per-slot arrays in zero page: a heading array at $44 (loc_44), a BASE/row-fine array at $54 (loc_54), and a COLUMN array at $64 (loc_64), all read zp,X so that X selects an object slot. `loadObjectTileInputs` is the marshaller for one slot: it copies that slot's base byte $54,x into the shared scratch cell $8b, folds the sign bit of the heading $44,x into a +/-1 step returned in Y (0xff when bit7 is set, else 0x01), and returns the slot's column $64,x in A — the exact register/scratch shape a tile-cell probe expects [seen: own write pc 0x2312 -> $8b; the heading/base/column arrays are watched changing at pc 0x2aaf/0x2a9b/0x2a94]. Those three arrays are written and consumed well beyond this cluster (detectColumnCollision reads them, rebuildSegmentSpriteTables and spawnActorOnTimer seed them), so their authoritative names belong to the segment cluster; here they read cleanly as heading/row-fine/column.

`loc_2b79` is a per-frame fixup over a second family of paired slot fields — the +2/+3 entries of the $40, $60 and $70 arrays. ## Sound and high-score/EAROM subsystem

This cluster spans three loosely-related subsystems that share the zeropage but not much else: the per-frame sound engine, the high-score integrity gate, the EAROM (NVRAM) writeback machine, and a pair of low-level tile-drawing primitives.

### Per-frame sound (updateSoundChannels)

Every frame `updateSoundChannels` refreshes the four POKEY voices from a bank of sound-effect countdown timers. It first checks the master audio flag `loc_86` ($86): if it is negative the four control registers AUDC1/2/3/4 are zeroed and the frame is silent [seen]. Otherwise each voice is serviced in turn. A timer sitting at zero means "idle" and leaves that voice's control register at zero; a nonzero timer is decremented and used to index that effect's waveform table in program ROM, whose next byte is copied straight into the voice's frequency register while a control byte sets its volume [seen]. `loc_b2`..`SFX_TIMER_CH4` ($b2-$b5) drive the four base voices — CH4 ($b5) only on odd frames, wrapping back to 0x14 when it underflows [seen]. Two priority timers pre-empt shared channels: `SFX_TIMER_CH2_PRIORITY` ($b6) grabs AUDF2 for a pitched voice before the general collision decision runs [code], and `SFX_TIMER_CH1_PRIORITY` ($b7) overrides the CH1 base voice with its own waveform, nudging the volume up by two [seen]. When no pitched CH2 effect is pending, a small decision block picks the CH2 content from game state — reading position/flag cells ($70^$f0, $43&0xaf, $40^$ef) to choose between the CH2 base voice [seen], a free-running down-sweep (`loc_b8`, $b8, cycling 0x14..1), or a computed noise value from $70^$f4. The base-voice route runs on nearly every frame; the sweep and noise sub-branches are not exercised in this capture [code]. The timers are counted down here but armed elsewhere (armSlotState/seedWaveState), so their trigger semantics live outside this cluster.

### High-score integrity gate (validateOrResetHighScores)

At boot `validateOrResetHighScores` decides whether the retained high-score table is trustworthy. It first copies the ROM template into the zeropage working area, then folds a checksum over the table; any nonzero delta means the table changed and forces a clean wipe [code]. It next snapshots the machine's configuration byte (`CONFIG_DIP_BYTE` $fd masked with 0x7c) into `HIGH_SCORE_CONFIG_BYTE` — a field that lives *inside* the table block itself (`HIGH_SCORE_TABLE`+0x12) — and bails without rebuilding if the config changed since last boot. If the top entry probes empty, or any promoted score byte is out of BCD range, the same clean-table path runs, zero-filling `HIGH_SCORE_TABLE` ($178) and re-recording the config snapshot. Otherwise the validated top entries are promoted into the zeropage working copies [code]. This is a boot-time integrity gate that a coin->start->play capture never re-enters, so its role stays [code] until a cold-boot capture reaches it.

### EAROM writeback (tickEaromWriteback)

`tickEaromWriteback` is the RAM→NVRAM flush half of the EAROM subsystem, run only every fourth frame (gated on `loc_00` & 0x03). It walks the high-score table one slot at a time using `loc_f9` ($f9); a cursor with bit 7 set means nothing is pending. `loc_fa` ($fa) is a shift register whose low bit alternates the machine between a scan/erase half and a commit half. In the scan half it compares each EAROM cell against its RAM mirror in `HIGH_SCORE_TABLE`; on the first mismatch it parks the cursor on the dirty slot, latches the wanted byte into `EAROM_DATA_WINDOW` ($1600), and strobes `EAROM_CONTROL` ($1680) to arm and begin an erase, then flips to the commit phase [seen — control strobes 0x06/0x0e and the bulk clean-wipe of $1600-$163f are both observed]. The following pass takes the commit half, re-strobing `EAROM_CONTROL` to write the latched byte and stepping the cursor down. The read/load half of this machine (which repopulates the RAM mirror from EAROM at boot) lives in the adjacent routine at 0x3b04+ and co-owns `loc_f9`/`loc_fa`, which is why those cells see most of their writes from outside this module.

### Tile-drawing primitives (writeMaskedByteAndAdvancePointer, writePointerTableRow, transposeScreenBitmap)

`writeMaskedByteAndAdvancePointer` is the shared store primitive that lays tiles into video RAM: a nonzero code is XOR'd with the display mask cell ($ef) and a zero code is stored raw, both through the 16-bit output cursor `loc_91/HI` ($91/$92), which is then advanced by a flip-aware stride (0x20^mask) with a per-column high adjust ($f3) [seen — the cursor advances on every one of thousands of calls; the ROM body was disassembled and matches its model exactly, so the store's video-RAM target is simply unwatched rather than missing]. `writePointerTableRow` sits above it: it indexes a ROM pointer table (0x346d) by a row selector combined with the mode bits of `CONFIG_DIP_BYTE`, fetches a row descriptor, seeds the output cursor from the descriptor's leading word, and then emits each tile code through the store primitive until a descriptor byte with its top bit set ends the row — folding space and 0x30-range codes to blanks along the way, with `rewritePointerTableRowFromStart` re-entering the same loop from descriptor offset 0 [code — not reached in this capture, though its store sub is exercised heavily by other renderers]. `transposeScreenBitmap` is a standalone screen-transition effect that reads the whole tilemap as a monochrome bit image, packs eight tiles per byte, rotates the image one column per pass through a scratch column ($0100), and rewrites every cell as blank or solid; it is a wipe used at transitions and does not run during ordinary play [code].
