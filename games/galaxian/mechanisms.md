# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–10.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

At the very bottom of the ROM sit a handful of tiny helpers that the rest of the machine leans on constantly: a pseudo-random generator, two restart-vector utilities (a block fill and a table lookup), an unsigned divide, and the epilogue that keeps the per-frame interrupt alive. None of them decide anything about the game on their own; they are the arithmetic and memory plumbing every larger routine calls down into.

Randomness comes from a single byte of state. `advanceRandomSeed` [seen] reads the current seed out of `RNG_SEED` (0x401e), advances it one step of a linear-congruential generator — `seed*5 + 1`, kept to eight bits by discarding everything above the low byte — writes the new value back to `RNG_SEED`, and hands that same new byte back as this call's random draw. So every draw both mutates the shared seed and returns it; two draws in a row never repeat, and the whole game's "luck" descends from this one cell. The seed*5 term is built the cheap way, by doubling the seed twice and adding the original back, but the observable result is exactly `(5*seed + 1) mod 256`. Consumers pull draws for things like jittering an enemy shot's horizontal velocity and reseeding a formation object's vertical position, so this routine is the source every "random" choice traces back to.

`fillMemoryBlock` [code] is the block-fill primitive reached through the RST 10 vector. Given a destination pointer, a byte value, and a count, it stores the value into that many consecutive bytes, walking the pointer forward one address at a time. The count is decremented as a byte, so a caller that asks for zero bytes actually gets a full 256-byte fill (the count wraps 0 -> 255 on the first decrement and runs the loop all the way around). When it finishes it leaves the pointer sitting just past the filled region and the count spent to zero, which lets a caller chain a second fill immediately after the first. This is the workhorse behind clearing and repainting: the routines that blank or reset video-RAM rows and that zero out RAM object/state blocks all funnel their writes through here, and because the destination is just an address, the same primitive serves both plain work RAM and the memory-mapped screen.

`fetchIndexedTableByte` [code] is the companion lookup primitive on the RST 20 vector: an indexed read into a table. It takes a base pointer and an 8-bit index, adds the index to the pointer with the carry propagated up into the high byte (so a table that straddles a 256-byte page boundary still indexes correctly), then reads the byte at the computed address. It returns that byte and also leaves the advanced pointer behind, so a caller can keep the resolved address for a follow-up read. The tile-drawing paths use it to turn a small index into a glyph or block code pulled from a ROM table, which is why it shows up wherever the screen is being populated from table data.

The unsigned divide, `divideUnsigned8` [code], computes A divided by D and is the one piece of real arithmetic here. It runs the classic restoring long division: eight rounds of compare, conditional subtract, and shift, with the divisor walked down one bit per round rather than the dividend being shifted up. Each round asks whether the running remainder still contains the current divisor; if it does, the divisor is subtracted and a 1 bit is shifted into the quotient, otherwise a 0 is shifted in. After eight rounds the quotient has accumulated in C — the value callers actually read — the remainder is left in A, the fully shifted-down divisor sits in D, and the round counter is spent to zero. It touches no memory at all; it is pure register math. Its two users are geometric: one turns a rise-over-run slope into a 0-7 heading octant (clamping the steepest case and taking the top three quotient bits), and the other scales a slope into a horizontal shot velocity before folding in a bounded random jitter. (The divide is entered by first zeroing the quotient accumulator and setting the eight-round counter; that entry, the compare/subtract step, and the shift-and-loop tail are one and the same operation described above.)

`rearmVblankInterruptAndRestoreRegs` [code] is the tail end of the once-per-frame interrupt. When the display's vertical-blank fires, the handler's prologue saves six register pairs and clears the interrupt-enable latch to acknowledge the pending interrupt; this epilogue is its mirror image. It writes `IRQ_ENABLE` (0x7001) back to 1 — re-arming the latch so the next vblank will assert another interrupt — then restores all six saved pairs (the index registers IY and IX, then HL, DE, BC, and finally AF, so the caller's accumulator and flags come back intact over the byte just used to set the latch) and returns through the address the interrupt had suspended, dropping the machine back into the main loop exactly where it left off. The re-arm is the load-bearing part: because the prologue disarms the latch on entry, if this epilogue did not turn it back on, only the very first vblank would ever be serviced and the per-frame update would freeze after one frame.

Finally, `loc_090b` [code] is a deliberately unnamed one-line stack epilogue: it restores the caller's saved HL and returns, touching no RAM. It is the shared exit of the command-queue enqueue path, reached both when a slot is found occupied and by falling through the normal completion, and exists only to undo the pointer the enqueue routine had pushed on entry.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

The machine that decides *what the whole game is doing right now* is a two-level index. A coarse selector, `GAME_STATE` (0x4005), picks one of five top-level handlers each frame — screen-fill boot, attract, the start screen, and two play handlers. Whichever handler is chosen then reads a finer selector, `SEQUENCE_STATE` (0x400a), and runs one sub-state routine from its own table. Almost every routine below is either a sub-state handler that lives in one of those tables, or a shared primitive those handlers lean on to move `SEQUENCE_STATE` forward on a timer. The tables are: game-state 0 = the boot filler; game-state 1 = attract; game-state 2 = `runStartScreenAndLaunchGame`; game-state 3 and 4 = the two play handlers (a fresh board and a restore-saved board), which share most of their sub-state table and differ only at two slots.

### Cold boot and the config latch

`fillScreenThenLatchConfigAndAdvanceState` [seen] is game-state 0, the very first thing that runs. Every frame it stamps a 32-tile blank run (tile 16) into the tilemap at the fill cursor `VRAM_WRITE_PTR` (0x400b) and walks that cursor forward across `VRAM_BASE` (0x5000) and beyond, so the screen wipes to blank a strip at a time while a per-state countdown at loc_4008 ticks down. When that countdown crosses zero the machine leaves boot: it resets the state cluster (loc_4007 = 1, mode flag loc_4006 = 0, `GAME_STATE` back to 1, `SEQUENCE_STATE` to 0), then *latches the cabinet configuration* — it folds bits out of the input shadows into their flag cells (loc_4000 takes a two-bit field from `IN1_SHADOW` (0x4011), loc_401f a bit from `IN2_SHADOW` (0x4012), loc_400f a bit from `IN0_SHADOW` (0x4010)), reads a coinage byte out of a four-entry ROM table indexed by the low two bits of `IN2_PORT` (0x7000) into loc_40ac, unpacks the packed flag bitmask, seeds the object shadow and the three player-1 status glyphs (`PLAYER1_STATUS_VRAM` (0x5340), loc_5320, loc_5300), and finally appends two deferred command words to the event queue. Setting `GAME_STATE` to 1 hands control to the attract handler for the following frame; loc_4000 (the config cell) now also doubles as the base page the command queue is addressed from.

### The attract sequence and its dwell cascade

Attract (game-state 1) walks a long chain of `SEQUENCE_STATE` sub-states, and the ones here are its opening and its timekeepers. `initSequenceEnableStarfield` [seen] is sub-state 0: it queues two setup command words, switches the starfield on (`STARS_ENABLE` (0x7004)), zeroes the per-sequence cells (`CURRENT_PLAYER` (0x400d), loc_400e, mode loc_4006, countdown loc_4019, and sets loc_4007), advances `SEQUENCE_STATE`, and *seeds the dwell cascade* — loc_4008 = 96 as the fast sub-timer and loc_4009 = 16 as the slower tier above it. `armStepCountdownAndTickSequenceTimer` [seen] is the next sub-state; it arms the one-frame countdown cell loc_4019 = 1 and then ticks the prescaled timer. `enterSequenceStep1` [code] is the wrap point that drops the sequence back to step 1: it sets `SEQUENCE_STATE` to 1 outright and re-seeds the dwell pair loc_4008/loc_4009 to a very short 3 and 3, so step 1 counts down almost immediately and the attract loop replays.

The dwell cascade itself is the heart of how time advances the sequence, and it is built from one shared primitive. `tickCascadeCountdown` [seen] decrements the byte it is pointed at (wrapping 0 to 255); while that byte is still nonzero it does nothing more, but when it hits zero it steps to the *next byte in the same page* and increments that one — a carry from a low tier into the tier above it. The counterintuitive fact is that this "increment the next cell" is exactly how the sequence advances: the callers point it at the mid-tier timer loc_4009, whose next-door neighbour is `SEQUENCE_STATE` (0x400a) itself, so a timer expiry literally carries into the state index and bumps the machine to its next sub-state. `tickSequenceDwellTimer` [code] is the thin sub-state handler that just points at loc_4009 and runs that tick every frame. `tickPrescaledSequenceTimer` [seen] adds a prescaler in front of it: it counts loc_4008 down each frame and only when loc_4008 wraps does it reload it to 60 and pass the tick up to loc_4009 — so this sub-state dwells sixty times longer per state step than the plain one.

Three more primitives re-arm that mid-tier timer with fixed values after a handler has set the next state. `reloadSequenceDwellTimer` [code] simply stamps loc_4009 = 80. `advanceSubstateAndReloadDwell` [code] first bumps the sub-state counter it is handed (the callers pass `SEQUENCE_STATE`) and then re-arms via that same 80-tick reload. `setSequenceStateByModeAndReloadDwell` [code] instead *chooses* the value it writes into the counter cell — 4 when the mode flag loc_4006 bit 0 is set, 14 when it is clear — before re-arming the dwell to 80, so the same handler can jump the sequence to a different resume point depending on whether the game is in a demo or a live-play mode. `advanceSubstateAfterDwellAndQueue` [code] is a self-contained state-timer sub-state: it ticks loc_4009 down itself, and only on the zero-cross does it reload it to 20, advance `SEQUENCE_STATE`, and enqueue that state's command word (selected out of a ROM table by the new state index).

### From attract into a game: credit and the start button

Game-state 2 is `runStartScreenAndLaunchGame` [code], the interactive start screen. Each frame it runs the formation sweep and occupancy summary (shared display work), then switches on `SEQUENCE_STATE` — values 0 through 3 drive the object-RAM reset, the lamp-hold countdown, the row-blanking, and the start-button lamp drive respectively — and, whatever the sub-state did, always finishes at `beginGameOnStartButton`. That trailing call is what makes the start button live on every frame of the start screen.

`beginGameOnStartButton` [code] is the credit-to-play transition. It reads `IN1_SHADOW`: bit 0 (the one-player button) hands straight off to `startOnePlayerGame`; otherwise bit 1 (two-player) must be set *and* the credit count loc_4002 must be at least two, in which case it spends two credits, blits the 32-byte ROM row template into `SAVED_STATE_SNAPSHOT` (0x41a0), conditionally arms the state-advance gate when config bit loc_401f bit 0 is set, and enters the shared round-start entry with a fixed spawn pointer. `startOnePlayerGame` [code] is the cheaper path: with no credits left it just forces `GAME_STATE` back to 1 (bounce to attract) and stops; otherwise it spends a single credit, zero-fills the 32-byte `SAVED_STATE_SNAPSHOT`, and enters the round start with a null spawn pointer. Both funnel into the same round-start setup, which is what actually flips `GAME_STATE` to 3 and resets `SEQUENCE_STATE` to 0 — so the next frame lands in the play handler at sub-state 0.

### Playfield init and the play sub-states

`initPlayfieldState` [code] is sub-state 0 of *both* play handlers — the first thing a live board does. It turns both start lamps off (`START_LAMP_0` (0x6000), `START_LAMP_1` (0x6001)), zero-fills three work-RAM spans (the 128-byte flag block at `FLAG_BITS_BASE` (0x4100), a span from `OBJ_ACTIVE_FLAG` (0x4200), a span from loc_4218, and the object-record region at loc_4260), clears loc_425f, sets one activity gate loc_4226 = 1, advances `SEQUENCE_STATE`, arms the dwell timer loc_4009 = 32, and points the fill cursor `VRAM_WRITE_PTR` back at `VRAM_BASE`. After a run of screen-clearing sub-states, the two play tables diverge at their sub-state-2 slot. The fresh-board table uses `restoreFormationAndEnterPlaySubstate` [seen]: it unpacks the `PACKED_FLAG_BITMAP` (0x4180) into the flag block, copies the eight-byte template trailing it into loc_4218, clears loc_425f/loc_4220 and the flip and direction latches (`FLIP_SCREEN_X` (0x7006), `FLIP_SCREEN_Y` (0x7007), loc_4018), advances the sub-state, arms the state timer loc_4009 = 150, publishes a deferred-callback pointer into loc_4245, and — only if the sound gate loc_4006 bit 0 is open — posts the board-start sound cue, choosing the paired-player burst when loc_400e bit 0 is set and a plain channel-5 prologue-plus-burst otherwise. The continued-game table uses `restoreSavedStateAndEnterPlaySubstate` [code] instead, which is the same shape but unpacks the *saved* snapshot `SAVED_STATE_SNAPSHOT` rather than the packed bitmap, mirrors the flip config loc_400f into the flip latches when set, publishes a different callback pointer, and enqueues a five-word intro burst when the sound gate is open.

The interesting slot is sub-state 6, where the two play handlers each run a small nested state machine keyed on gates. `stepPlaySubstate6` [code] (fresh board) branches on the arm gate loc_421d together with the state-advance gate loc_41b5 and the paired-player flag loc_400e: depending on which are set it either advances the sub-state and reloads the dwell, sets the state by mode, or falls to the shared reset tail — and in its own inline arm it bumps `SEQUENCE_STATE`, arms loc_4009 = 130, and (only when mode loc_4006 bit 0 is set) queues two channel-6 command words. `stepAltPlaySubstate6` [code] (continued board) mirrors this but keys the "advance" decision on the sub-state-advance gate loc_4195 instead of loc_41b5, reloading the dwell to 80 on its show arm and 130 on its default arm. The shared exit both of them fall to is `advanceDwellOrResetToState1` [code]: when mode loc_4006 bit 0 is clear it just advances the sub-state and reloads the dwell, but when it is set it *tears the round down* — `GAME_STATE` = 1, mode and `SEQUENCE_STATE` cleared, sound and the interrupt/starfield silenced, and command word 6 queued — dropping the machine back to attract.

The two gates those handlers test are set by tiny one-liners. `armStateAdvanceGate` [code] stamps the armed marker 3 into loc_41b5, the gate `stepPlaySubstate6` reads as nonzero; `armSubstateAdvanceGate` [seen] stamps the same 3 into loc_4195, the gate `stepAltPlaySubstate6` reads. These are the hooks the credit path and the round-start entry pull to steer which branch sub-state 6 will take when it next runs.

### The command / event queue

Everything above that "queues a command word" is feeding one ring. `enqueueCommandWord` [seen] takes a 16-bit word (a channel in the high byte, a param in the low byte) and, reading the write-head index loc_40a0, looks at the slot it addresses off the page base loc_4000 (the live slots sit at 0x40c0 and up). Only if that slot is free — its bit 7 set — does it write the high byte there and the low byte in the next cell, advance the head by two, clamp the head up to a floor of 0xc0 if it fell below, and commit; if the slot is occupied it leaves the queue untouched. Either way it restores the caller's saved pointer. The commit step is factored out as `commitQueueWriteHead` [seen], which writes the advanced head back to loc_40a0 and then returns through the shared epilogue loc_090b [code] — a deliberately unnamed, pure-stack tail that restores the saved pointer and returns with no work-RAM effect of its own.

Two helpers post fixed bursts of these words for sound cues. `enqueueCommandWordBurst` [code] emits a five-word set around a caller-supplied channel — two on the next channel and two fixed cues on channel 7. `queueBoardStartSoundBurst` [code] is the paired-player board-start cue: a single channel-5 prologue word followed by that standard burst on channel 5.

### The per-frame timer and gate cluster

A separate group of routines are not sub-state handlers at all — they run every frame from the play pipeline, gated so they only do work while a round is live (the master enable being `OBJ_ACTIVE_FLAG` (0x4200) bit 0). `clearGateOnPendingRequest` [code] watches the request flag loc_420b: when its bit 0 is pending it acknowledges it by clearing loc_420b and also clears the behavior gate loc_4208 that gate governs. Its counterpart `armBehaviorGateOnInputOrTimer` [code] is what *sets* that behavior gate: it does nothing unless the enable gate is open and loc_4208 isn't already armed, then — keyed on mode loc_4006 bit 0 — either arms on a timer (only when the low five bits of the frame counter loc_425f are all clear, i.e. roughly once every 32 frames) or arms on input (bit 4 of the selected input shadow, chosen between `IN0_SHADOW`/`IN1_SHADOW` by loc_4018 and masked by its guard cell loc_4013 or loc_4014), raising both loc_4208 and the companion flag loc_41cc on the input path.

`rampCounterToCeiling` [code] is a gated three-tier prescaler: while the enable gate is open and the inhibit flag loc_422b bit 0 is clear, it ticks an outer prescaler loc_4218 (reload 60), and each time that wraps it ticks an inner one loc_4219 (reload 20), and each time *that* wraps it steps the counter loc_421a up by one, clamping at a ceiling of 7 — a slow climb that saturates.

The delayed-event mechanism is a two-part arm-and-fire pair. `scheduleDelayedEvent` [code] runs only when three enable bits agree (the master enable and loc_41ef set, the inhibit loc_422b clear); with the mode bit loc_4006 clear it ticks an outer/inner cascade (loc_4245 reload 60, loc_4246 reload 5) and on a full elapse arms a *fixed* triple — `DELAYED_EVENT_TIMER` (0x422f) = 90, loc_424a = 45, `DELAYED_EVENT_ARMED` (0x422e) = 1 — while with the mode bit set it instead derives the payload from a region flag loc_4221 or from the byte-sums of the word cells loc_4177 and loc_421a and fans it into the triple by bit-rotations. `fireDelayedEventRequest` [code] is the one-shot that consumes it: while armed it counts `DELAYED_EVENT_TIMER` down and does nothing until it reaches zero, at which point it disarms `DELAYED_EVENT_ARMED` and, only if both the master enable and loc_41ef are still set, raises `DELAYED_EVENT_REQUEST` (0x4229). `expireActivityGatedTimer` [code] is a third timer of the same family: only while its arm flag loc_422b bit 0 is set *and* at least one activity gate is open (loc_4224 nonzero, or loc_4221 nonzero, or loc_4226 bit 0 set) does it tick its counter loc_422c down, clearing the arm flag once the counter reaches zero — so it measures out a phase that only elapses while the field is "busy."

### A stray clamp helper

`markValueOutOfRange` [code] belongs here only by proximity, not by role: it is the saturate arm of a value clamp, snapping register B to the fixed sentinel 128 (0x80) when a fold input runs out of range. It touches no memory and does no state work — it is the out-of-range case pulled out of the tile-variant fold, and plays no part in the sequence machine itself.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

Every enemy the player faces -- the standing block of aliens and every attacker that peels out of it -- lives in one of a few parallel tables of fixed-stride records, and its position on screen is derived, frame by frame, from a compact grid model. This section follows how that grid is seeded, how the standing formation sways and reports its own shape, how a per-object state machine drives each alien, and how new attackers are paced, launched, and spawned.

### The two representations: a packed cell grid and per-object records

The formation is stored twice. The authoritative membership map is a flat block of 128 one-byte-per-cell flags based at `FLAG_BITS_BASE` (0x4100), where a cell's bit 0 means "a live alien occupies this grid slot." A 6-row by 10-column window into that block, based at `OCCUPANCY_GRID` (0x4123) with rows 16 bytes apart, is the grid the rest of the machine reasons over. Alongside it the moving actors live in 32-byte object records: the main object table at `OBJ_TABLE` (0x42d0), the standalone descriptor slots at `DESCRIPTOR_SLOT_TABLE` (0x4330), and an eight-record band at `SPRITE_SOURCE_OBJ_BASE` (0x42b0) that doubles as the sprite-source region and the shot-hit scratch area. Within a record, byte 0 is the active flag, byte 2 the state selector, bytes 3/4 the on-screen X/Y the renderer reads, byte 5 a heading, byte 6 a direction/spawn-code byte, and byte 7 the packed grid cell (its high nibble is the row, low nibble the column).

### Seeding the object shadow and the flag block

At screen and formation init the interleaved object-shadow field is laid down by `seedObjectRamShadowField` [seen], which copies 32 source bytes into every other cell of the table based at 0x4021 (stride 2, spanning 0x4021..0x405f). `seedObjectShadowFromRom` [seen] is the fixed entry point: it points the copier at the ROM template `STRIDED_TABLE_SRC` (0x1d71) and runs it. `advanceSequenceStateAndReseedObjectShadow` [code] wraps that with a small side effect useful during the boot sequence -- it advances a pointer's low byte within its page and increments the byte now named (its callers arrive on 0x4009, so the increment carries into the top-level `SEQUENCE_STATE` at 0x400a), then reseeds the shadow. `clearFlagBlockAndReseedObjectShadow` [code] is the full sequence-init reset: it zero-fills the entire 128-byte flag block at `FLAG_BITS_BASE`, clears the frame/phase counter 0x425f and a status byte 0x4238, arms the mid-tier dwell timer 0x4009 to 64, and then advances the sequence state and reseeds the shadow through the routine just described.

### Packing and unpacking the formation bitmask

The 128 flag bytes are the working form; their compact form is a 16-byte bitmask. `unpackBitmaskToFlagBytes` [seen] expands a 16-byte packed mask into the 128 one-byte flags at `FLAG_BITS_BASE`, LSB first, writing 1 for each set bit and 0 for each clear one, and hands back a pointer just past the 16 mask bytes so the caller can read whatever data trails the mask. `packFlagBytesToBitmask` [code] is its exact inverse: it reads bit 0 of the 128 flag bytes and repacks them, LSB first, into a 16-byte bitmap, returning the pointer advanced 16 bytes so a copy can be chained after it.

Three routines drive those. `loadDescriptorAndAdvanceSequence` [code] unpacks a packed descriptor bitmask from ROM (`loc_051b`, 0x051b) into the flag block, copies the 8-byte template that follows the mask into the template buffer at `loc_4218`, clears the frame counter 0x425f, raises status byte `loc_421d`, steps `SEQUENCE_STATE`, stamps the VRAM fill cursor `VRAM_WRITE_PTR` (0x400b) to 150, and publishes a deferred-callback pointer (`loc_0640`, 0x0640) into `loc_4245`. The two terminal handlers do the reverse at end of a run. `packFlagsToBitmapAndSwitchPlayerState` [code], on expiry of the dwell timer 0x4009, clears `SEQUENCE_STATE` and two status bytes (`loc_4222`, `loc_422b`), packs the flag bytes into `PACKED_FLAG_BITMAP` (0x4180), copies the 8-byte template after it, marks `CURRENT_PLAYER` (0x400d) as player 1, and moves `GAME_STATE` (0x4005) to 4. Its mirror, `saveFlagsToSnapshotAndSwitchPlayerState` [code], on the same timer expiry clears `SEQUENCE_STATE`, sets `CURRENT_PLAYER` to 0 and `GAME_STATE` to 3, snapshots the flag bytes into `SAVED_STATE_SNAPSHOT` (0x41a0), and appends the companion 8-byte block after it -- the two-player handoff that preserves one player's formation while the other plays.

Separate from the bitmask work, `activateDescriptorSlot` [seen] initializes a single standalone slot: it reads a descriptor number at (HL), uses number-minus-one to pick the 32-byte slot in `DESCRIPTOR_SLOT_TABLE`, and stamps its fixed init fields -- active flag 1, byte 2 = 13, byte 5 = 12, byte 7 = the slot index -- leaving bytes 3 and 6 untouched.

### The side-to-side sweep

The standing block's characteristic sway is a 16-bit position word at `loc_420e` (the formation anchor) oscillating between a bound pair, with a one-byte direction flag `OBJ_SWEEP_DIRECTION` (0x420d) choosing which way it currently walks. `advanceFormationSweepOscillator` [seen] runs the sway once every four frames (throttled by the low bits of the frame counter `loc_425f`): while ascending it steps the word up until its low byte reaches the from-right bound and then hands off to `setSweepDescending` [seen], which sets 0x420d to 1; while descending it steps down until it reaches the from-left bound and hands off to `setSweepAscending` [seen], which clears 0x420d. Each accepted step broadcasts the new position across the column table so the whole block shifts together.

That broadcast is a small family. `broadcastToStridedTable` [seen] writes one byte across nine cells at stride 2 based at 0x4028 -- the shared position field for the formation's columns. `broadcastNegatedSweepToStridedTable` [seen] broadcasts the two's-complement of a supplied low byte (the sway coordinate is negated for the hardware's coordinate sense), and `broadcastNegatedFormationSweepToStridedTable` [code] is the convenience form that reads the current sway word's low byte from `loc_420e` and negates that. `clearStridedTable` [seen] is the same writer with a value of zero, blanking the column positions. The oscillator normally exits through the negated-broadcast path, but it opens with a proximity shortcut: when the shot gate `loc_4208` bit 0 is armed and the shot's position (`loc_4209`) sits in a narrow window aligned to the sway word, and the target column -- derived from the delta between the shot's X (`loc_420a`) and the anchor -- reads occupied in `COLUMN_OCCUPANCY`, it skips the stepping entirely and re-broadcasts the current formation position. The deliberately unnamed epilogue `loc_090b` is simply the shared stack-restoring return of the command-enqueue path these routines share; it carries no logic of its own.

### Summarizing the grid's shape

Once per relevant frame `summarizeFormationOccupancy` [seen] reduces the occupancy grid into the summaries everything else consults. It ORs each of the six rows into `ROW_OCCUPANCY` (0x41e8, behind two always-empty guard cells) and each of the ten columns into `COLUMN_OCCUPANCY` (0x41f0, behind three guard cells). It then finds the horizontal extent of the surviving block by scanning the column summaries inward from each end -- stepping a bound outward one column-pitch per empty column -- and writes the resulting pair into `FORMATION_X_BOUNDS` (0x4210) as a packed word (low byte the from-right bound the sweep turns on, high byte the from-left bound). Finally it folds four region-clear flags, each the OR of a region XOR 1 so that bit 0 set means "this region is empty": `loc_4221` from the top four rows, `loc_4220` from all six rows, `loc_4226` from seven object-table slots, and `loc_4225` from an eight-slot field at `loc_42b1`. Those clear flags are the pivots the launcher, the pacer, and the stage-advance arm all gate on.

### Deriving screen position from a grid cell

Because the display axes are rotated a quarter turn from the formation grid, `positionObjectFromGridCell` [code] translates a record's packed cell (byte 7) into the two position fields the renderer reads. The row bits drive the X field (byte 3) as a fixed origin of 124 minus three-quarters of the row value; the column bits drive the Y field (byte 4) as the moving anchor `loc_420e` plus the column scaled up by 16, offset by the sprite hotspot of 7. This is why sway of the single anchor word slides the entire column of aliens along the screen's long axis. `stageObjectsToSpriteShadow` [seen] is the per-frame presenter for the standing block: it renders eight consecutive source records from `SPRITE_SOURCE_OBJ_BASE` (stride 32) into eight consecutive sprite-shadow records at `SPRITE_SHADOW_BASE` (0x4060, stride 4), laid out as a band of three then a band of five, with the first band's Y offset (9 or 7) chosen by the orientation bit `loc_4018` and the tail band settling at 8 either way.

### The per-object state machine

Each active record is driven by a state selector in byte 2 that picks one of sixteen behaviors; the members of this subsystem occupy three of those slots. State 0 is `initSpawnedObjectFromGridCell` [code], the first-tick init of a freshly launched attacker: it clears the step timer, raises the spawn flag `loc_41c2`, derives the sprite position from the packed cell, and enqueues a type-1 spawn command word carrying the cell. It then looks up the object's sprite number and flight-curve seed from the ROM record table `SPAWN_RECORD_TABLE` (0x1dd1) indexed by row; for the top row it also gives the object a distinct attribute base and tallies its two look-ahead neighbor slots into `ACTIVE_NEIGHBOR_COUNT` (0x422a). Both paths then seed the motion counters, advance to the next state, and set the signed heading (+12 or -12) from the direction bit.

State 6 is `settleObjectIntoFormationCell` [code], the handler that walks an attacker back into its formation slot: it bumps a frame counter, repositions from the packed cell, and compares the counter against the positioned value. When they coincide the object has arrived -- it deactivates, sets its cell's flag in the flag block, and enqueues a command word for the arrival; a small even gap nudges the phase byte up or down by the direction bit, while a large or odd gap is left to close on a later frame. State 5 is `reseedFormationObjectState` [code], the formation-object recycler: it resets the record's X to the left edge and heading to zero and ticks its leg counter, then -- while objects are enabled and an activity gate is open (`loc_4224` or `loc_4221` set) -- rolls a fresh random Y, arms a hold timer, and advances the state. The special case is a fully-set row nibble (byte 7 & 0x70 == 0x70): while active neighbors remain it recounts them into `ACTIVE_NEIGHBOR_COUNT` and reseeds, but once none are left it deactivates the object and ramps the pending-request/phase counter `loc_421e` toward its ceiling of 2 -- the mechanism that turns a cleared-out region into a later spawn request.

Two small helpers sit near this machine. `noopAnimDispatchSlot` [code] is the do-nothing terminal slot of the dying-object animation table, present so that sub-state always has a valid target. `bumpCountIfNeighborsInactive` [code] peeks the two object slots 32 and 64 bytes above a base and, only if both are inactive, returns a supplied count plus one; the kill-scoring path uses it to inflate the neighbor bonus read from `ACTIVE_NEIGHBOR_COUNT`, so an alien picked off with its two neighbors already gone scores extra.

### Player shot versus formation

`flagPlayerShotHitOnFormation` [code] registers the player's shot destroying a standing alien. While the shot gate `loc_4208` bit 0 is armed, it bands the shot's Y (`loc_4209`) into a formation row by stepping down through the alternating 7-and-5-pixel row spacing, rejects shots in the gaps or beyond the block, and bands the shot's X delta against the anchor into a column, rejecting anything outside the hit window. It indexes the flag grid at that cell and does nothing unless the cell holds a live alien; on a real hit it clears the cell, enqueues a kind-1 command word carrying the grid index, stamps a hit record at `loc_420b`/`loc_42b1`/`loc_42b2`/`loc_42b3` (an active flag, a zeroed phase, and the shot's position word), and enqueues a second kind-3 command word carrying a column code derived from the grid index -- the pair of events that later resolve the kill's scoring and sound.

### Pacing and launching attackers

New dives are metered by `paceEnemyLaunchTrigger` [code]. It runs only while the play flag `OBJ_ACTIVE_FLAG` (0x4200) is set and both the region-clear gate `loc_4220` and inhibit flag `loc_422b` are clear. It sizes a sweep span from the pace counter `loc_421a` and, for later stages, the stage selector `loc_421b`, then ticks a master counter `loc_424a`; until the master expires it just drops the refill flag. On expiry it reloads the master from the ROM reload table `SUBCOUNTER_RELOAD_TABLE` (0x15e3) and sweeps that span of sub-counters, refilling each that reaches zero from its matching reload entry, and raises `SUBCOUNTER_REFILL_FLAG` (0x4228) if any refilled.

`launchAttackerFromFormation` [code] consumes that one-shot refill flag and, while the region-clear gate `loc_4220` is not set (there is still a formation to launch from), peels one attacker out. It derives a slot budget of one to four from the summed pace counters, claims the first all-zero object slot scanning downward from `loc_4391` (stride 31), and stamps the shared launch direction `loc_4215` into the slot's direction byte. It then scans `COLUMN_OCCUPANCY` for an occupied column -- from the high end down for direction 0, the low end up otherwise -- and walks that column's grid cells in `FLAG_BITS_BASE` (the row count and geometry chosen by the sweep-mode bit `loc_41ef`) looking for a filled cell. On a hit it consumes the formation cell, activates the slot at state 0 with a cleared phase and the cell's low byte recorded, and enqueues a type-1 spawn command -- one standing alien becomes one diving attacker.

### Advancing the stage and rebuilding the formation

When a wave is cleared, `armFormationAdvanceTrigger` [code] arms the advance: only if both the all-rows clear flag `loc_4220` and the object-region clear flag `loc_4225` have bit 0 set, and the pending word `loc_4222` is not already armed, does it set `loc_4222` to 1 (its low byte the enable, its high byte a zeroed countdown). `advanceStageAndReseedFormation` [code] then services that arm per frame: it bails unless the enable is set and its countdown (`loc_4223`) lands on zero this tick. On that tick it disarms the enable, rebuilds the 128-flag block from the packed ROM template (`loc_051b`), zeroes the pace counter `loc_421a` and frame counter 0x425f, reseeds the formation anchor `loc_420e` to 1, and steps the stage selector `loc_421b` (its high byte counting up freely, its low byte advancing but saturating at 7). It enqueues a command word carrying a ROM pointer (`loc_0700`) and finally drains the pending-request counter `loc_421e` -- raising the first spawn trigger flag `loc_4177`, decrementing the count, and raising the second trigger `loc_4178` if any remains. This is where the requests accumulated by `reseedFormationObjectState` turn into concrete spawn triggers for the next wave.

### The spawn tree

New objects on a scheduled event flow through a small dispatch tree rooted at `spawnObjectsOnDelayedEvent` [code]. It is gated on the region-clear flag being clear, the object subsystem enabled, a pending `DELAYED_EVENT_REQUEST` (0x4229) consumed here as a one-shot, and the object-table head word being even. If the launch direction `loc_4215` is odd it routes the whole trigger block through `spawnObjectsFromTriggerFlags`; otherwise it scans the primary trigger block (`PRIMARY_TRIGGER_BLOCK`, 0x4176, four flags) high to low and, on a set flag, calls `spawnPrimaryAndSecondaryObjects`; failing that it scans the secondary window just below the primary block and calls `spawnIntoFreeDescriptorSlot`.

`spawnObjectsFromTriggerFlags` [code] scans the primary block for the first set flag: it spawns a primary into `OBJ_TABLE`, then walks the secondary flags at the matching offset in `SECONDARY_TRIGGER_BLOCK` (0x4165), spawning up to two secondaries into successive slots from the table's second record. If no primary flag is set it scans the secondary block and instead seeds a free descriptor slot. `spawnPrimaryAndSecondaryObjects` [code] is the same shape reached directly: spawn one primary, then walk a short block of trigger flags backed up from the primary trigger's low byte, spawning a secondary per set flag until the two-secondary budget runs out, at which point the walk ends after that pass.

At the leaves, `activateObjectSlotAndEnqueueSpawn` [code] is the primary seeder: it consumes the trigger flag it was found under, marks the slot active with a cleared phase, records the spawn code and the source index (the trigger pointer's low byte), and enqueues a type-1 spawn command word. `spawnSecondaryObjectIntoSlot` [code] is the secondary seeder: it bails if either of the slot's two live flags is already set, else consumes the trigger, marks the slot alive, clears its state, inherits byte 6 from the source record, stashes the trigger index, and enqueues an activation command word. `spawnSecondaryObjectAndAdvanceWalk` [code] is the reusable per-slot step of a secondary walk -- spawn into the current slot, advance the slot pointer by one record, decrement the budget, and when the budget is spent force the caller's loop counter to 1 so the walk stops after this pass. `spawnIntoFreeDescriptorSlot` [code] is the shared free-slot finder for descriptor-backed spawns: it scans the four slots of `DESCRIPTOR_SLOT_TABLE` from the last downward for one whose two guard bytes are both zero and, on a hit, seeds it through `activateObjectSlotAndEnqueueSpawn`; with no free slot it does nothing.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

This subsystem is the live playfield: the player ship, the single player shot, the enemy objects that peel out of the formation to dive and swoop, the aimed shots those enemies drop, and the two collision sweeps that resolve everything. Two work-RAM cells form its spine. `OBJ_ACTIVE_FLAG` (0x4200) is the master enable for the whole object/AI/projectile machine — it is raised when play begins and pulled down the instant the player is hit. The cell 0x4202 (a still-`loc_4202` placeholder) is the player ship's position along its movement axis; it is written by the ship-mover and read as the *target* by nearly every AI routine, so "steer toward the player" throughout this code means "steer toward 0x4202".

### The object slots and their state machine

Each frame the game walks eight object records laid end to end at 0x42b0 on a 32-byte stride, handing each in turn to `driveObjectSlot` [code]. That routine makes three decisions per record. If the record's death flag (byte 1, bit 0) is set, the object is dying and is passed to the animation dispatcher (below). Otherwise, if the active flag (byte 0, bit 0) is clear, the slot is idle and nothing happens. Otherwise the record's state index (byte 2, values 0..15) selects one handler from a sixteen-entry table and runs it. The handlers relevant here occupy states 1 (`advanceObjectPathStep`), 2 (`advanceActorPhaseAndCommitMove`), 3 (`advanceObjectFlightAndFire`), 4 (`advanceObjectDiveStep`), 7 (`homeObjectXTowardPlayer`), 8 (`armDirectedMoveWhenInWindow`), 9 (`advanceHomingObjectFlightAndFire`), 10 (`advanceObjectPathStepDescending`), 11 (`advanceObjectPathStepAlias`), 12 (`restartObjectMoveRun`), 13 (`initObjectPhaseSteps`), and 15 (`settleObjectXAtRest`); the remaining states (grid-cell spawn, formation reseed, formation-cell settle, message column) belong to neighbouring subsystems.

One current-state fact is worth stating up front, because it makes the record layout look contradictory until you see it: **the object record is union-typed by state.** The bytes at 0x19..0x1c are the two 16-bit flight-curve accumulators while an object is diving, but the very same bytes hold the move planner's target-X and move accumulator while it is cruising; byte 0x09 is read as a per-frame Y increment by the flight states and written as the signed move delta by the move planner; and the two position bytes at +3/+4 are read as X-then-Y by the path walkers but as Y-then-X by the aiming code, reflecting the 90°-rotated display convention. The fields are not stably typed — their meaning follows the state byte.

### The player ship

`moveControlledObjectAndStageSprite` [code] moves the ship and stages its sprite. When `OBJ_ACTIVE_FLAG` is set it selects a set of movement bits — the AI command `OBJ_MOVE_CMD` (0x423f) when the mode cell 0x4006 is in auto, otherwise one of the two input shadows `IN1_SHADOW` (0x4011) or `IN0_SHADOW` (0x4010) chosen by the direction flag 0x4018 — and nudges 0x4202 one count down (bit 3, while above the floor 23) or up (bit 2, while below the ceiling 233), clamping the ship to the [23,233] band. When the ship is inactive it either parks the position at 0 or, if the death cell 0x4201 has bit 0 set, freezes it in place under an alternate sprite code (this is how the ship's explosion holds its spot). In every case it stages the one's-complemented position as four interleaved (value, code) pairs into `OBJ_STAGE_BLOCK` (0x4054), the ship's sprite cells.

### The player shot

`advancePlayerShot` [code] drives the single shot as a timing block. While the shot gate 0x4208 (bit 0) is armed it drains the travel counter 0x4209 by four each frame and raises the retire flag 0x420b whenever the counter lands in the narrow [14,17] near-end window — the moment the shot reaches the top of its flight. When the gate is clear the shot is idle: the counter is reset to 220 (parked at the bottom) and its lateral field 0x420a is loaded from the ship position 0x4202 when the subsystem is enabled, else zeroed — so a freshly loaded shot inherits the ship's lateral position. `advancePlayerShotAndStageSprite` [code] services that block and then reads the {counter, field} pair back as a coordinate, writing the shot's two render cells 0x409f and 0x409d (complementing the field, and picking one of two X formulas by direction flag 0x4018). The {0x4209, 0x420a} pair doubles as the shot's collision reference.

### Building the hardware sprites

`renderObjectSprite` [seen] turns one object record into one hardware sprite record. For an active object (byte 0) it copies the sprite number from record+0x16, sets sprite X to field+3 minus 8 and sprite Y to the complement of field+4 minus a caller Y-offset, and folds the object's signed heading (record+5) into a display attribute: whole 24-count sectors are peeled off until the heading settles into one of four ranges near straight-ahead, each mapping to a facing attribute (added to the base attribute at record+0x0f) plus a one-pixel nudge on the diagonal cases. A secondary-active object (byte 1) instead gets fixed sprite number 7 and the alternate attribute at record+0x12. With both flags clear the sprite is parked off-screen at (248,248). This runs for the block of eight object slots each frame (as three sprites then five, at a Y offset chosen by 0x4018), which is what puts the objects on screen.

### Path walking (formation entry and re-entry)

Three closely related handlers walk an object along a canned path stored in `PATH_STEP_TABLE` (0x1e00), read in (Y-delta, X-delta) pairs through a per-object cursor. `advanceObjectPathStep` [code] (state 1, and the target of the bare trampoline `advanceObjectPathStepAlias` [code] at state 11) adds the pair's first byte to field+3 and its second byte to field+4 in the direction chosen by record+6 bit 0; if the object crosses the near edge (position plus a 7-pixel margin below 14) it is dropped into the fall-away state 5, otherwise the cursor advances, a throttle (record+0x10, reloaded to 4) ticks, and on throttle expiry the cross-step (record+5) is nudged and the leg counter (record+0x11) ticks, advancing the state when the last leg finishes. `advanceObjectPathStepDescending` [code] (state 10) is the subtract-direction mirror: it subtracts the X delta from field+3, then — unless record+6 bit 0 hands the vertical half off to the ascending arm — subtracts the Y delta from field+4, ticking the same throttle/leg pair and, on a finished leg, advancing the state while reloading throttle=3, leg=12, heading=12 and cursor=0. `advanceObjectPathStepAscending` [code] is that vertical arm: it *adds* the step byte to field+4, ticks throttle and leg identically, and on a finished leg reloads throttle=3, leg=12, heading=244 and cursor=0. Together the three give an object a scripted swoop-in whose vertical direction is selectable per leg.

### The swoop: flight curve, dive, and homing

The characteristic Galaxian dive comes from a discrete oscillator. `advanceObjectFlightCurve` [code] runs ((record+0x18 seed & 3)+1) integration steps over two cross-coupled 16-bit accumulators held at record+0x19/0x1b and record+0x1a/0x1c: each step adds twice the *other* accumulator's sign-extended high byte into this one, with a guard that reverts any step whose result high byte lands exactly on 128. This is a fixed-point rotation, and the high byte of the first accumulator (record+0x19) becomes the sinusoidal heading offset the dive states add to the object's screen position.

`advanceObjectFlightAndFire` [seen] (state 3) is the free dive: it bumps the object's frame counter (record+3), runs the flight curve, and sets screen position field+4 to the per-object increment (record+9) plus that heading byte. If the result rides too high (position plus 7 wrapping below 0x0e) it advances the state by two; if the frame counter has run out (counter ≥ 0xb8) it advances by one; otherwise, gated by `OBJ_ACTIVE_FLAG`, it aims at the player and — unless the delayed-event/inhibit bit 0x422b is set — scans the row-schedule table at 0x4213 (low byte a count, high byte the match value, striding the counter by 0x19 per row) and fires an aimed shot on a match. `advanceObjectDiveStep` [code] (state 4) is a variant that first steps record+3 by one or two on the frame-parity bit 0x425f and, while that position sits inside a [6,9) window, simply bumps the state; outside the window it runs the flight curve and folds heading plus increment into field+4, but bumps the state instead of storing when the sum's carry crosses the signed boundary (the swoop has run off the bottom). `advanceHomingObjectFlightAndFire` [code] (state 9) mirrors the free dive but first steers the object's column (record+9) toward the player column 0x4202 according to a mode byte (record+0x17): mode 4 homes only on odd frame parity, mode above 4 homes every frame, mode below 4 never homes; its overrun cases jump to fixed states 5 and 4, and it advances via a move-throttle countdown rather than by two — otherwise its aim-and-fire tail is identical.

### Horizontal move planning

A cluster of small routines chooses and commits an object's next horizontal target. `commitMoveToTargetX` [seen] is the primitive: it stashes the chosen target X at record+0x19, records the signed move delta (current field+4 minus target) at record+0x09, zeroes the three-byte move accumulator at record+0x1a..0x1c, and advances the planner sub-state at record+2. `commitMoveAcrossPlayerX` [code] picks a target on the *far* side of the player: it signed-halves the gap between the actor and 0x4202, biases it by 16, and clamps into the right band [144,208] when the actor is left of the player or the left band [48,112] when at or right of it, then commits via `commitMoveToTargetX` — the crossing behaviour that makes divers weave across the ship. `commitMoveToStoredOrPlayerTargetX` [code] chooses between two pickers: when the object-table mode flag at `OBJ_TABLE` (0x42d0) bit 0 is set it steers toward that record's stored target (0x42d0+0x19), otherwise it runs the ordinary cross-player pick. `beginObjectCrossPlayerMove` [code] is the shared tail that both picks a cross-player target and arms the fresh move — seeding the flight-curve step seed at record+0x18 to 3 (four curve steps) and the move throttle at record+0x10 to 100.

Three state handlers build on those. `advanceActorPhaseAndCommitMove` [code] (state 2) bumps the phase counter at record+3 and then commits a move — the stored/player selector when the kind field (record+7) masked by 0x70 equals 0x60, the plain cross-player selector otherwise. `armDirectedMoveWhenInWindow` [code] (state 8) ticks an arm counter at record+3 and keeps cruising cross-player until both that counter and field+4 sit inside the [96,160) window; once in-window it advances the sub-state by two, seeds the move timers (record+0x10=3, record+0x11=12), clears record+5 and record+0x13, and sets the direction bit at record+6 from the player-position compare. `restartObjectMoveRun` [code] (state 12) bumps record+3, forces the state back to 8 (re-entering the arm window), and kicks off a fresh cross-player move. `homeObjectXTowardPlayer` [code] (state 7) is the tight tracker: it bumps record+3 and steers the 16-bit position:subpixel pair at record+4/record+9 toward 0x4202 by roughly four times the signed distance each frame (carrying a small rounding bias), advancing to the next state when the dwell timer at record+0x10 counts to zero.

### Phase entry and settling

`initObjectPhaseSteps` [seen] (state 13) derives a step count n as the low two inverted bits of the seed at record+7, records n+1 at record+0x16 and a code byte ((n+1)<<4 + 140) at record+3, arms a 24-tick phase timer at record+0x10, advances the sub-state, and clears the ready flag at record+0x0f — re-arming that flag to 24 only when n is zero. `settleObjectXAtRest` [seen] (state 15) is the resting handler: it nudges field+4 up one count per frame until the field lands within 5 of the rest value 200, then holds — how an object eases into and stays at its resting spot.

### The dying-object animation

When `driveObjectSlot` sees a record's death flag set, it hands off to `dispatchDeactivatedObjectAnim` [code], which reads the animation sub-state at record+2 and runs one of four phase handlers (the entry/arm phase and a no-op terminal slot belong to a neighbouring subsystem). `tickDeactivatedObjectAnim` [code] (sub-state 1) counts a fast timer at record+0x10 down, reloading it to 4 and bumping a companion at record+0x12 each time it elapses, then counts a slow timer at record+0x11; when the slow timer elapses it either retires the object (clearing state byte record+1) or, if the position field record+7 is at least 112, reloads the fast timer to 50, reseeds the companion from the global 0x422d plus 32, and advances the sub-state. `endObjectAnimOnTimerExpiry` [code] (sub-state 2) simply counts the timer at record+0x10 down and clears the state byte record+1 to retire the object when it hits zero.

### Enemy fire aimed at the player

When a diving object reaches a firing row it drops a shot aimed at the ship. `aimObjectAtTarget` [seen] derives a direction: it forms a vertical drop (0xf0 minus one position byte) and a horizontal delta (0x4202 minus the other), and turns their ratio into a heading stored at record+5 — mirroring the octant and negating it when the target is to the left. The ratio-to-heading step is `computeDirectionOctantFromSlope` [seen], which divides dividend by divisor, treats a top-bit-set (steepest) quotient as clamped to 0x80, and returns the top three bits as a 0..7 octant. `spawnAimedProjectileAtPlayer` [code] claims the first free entry (bit 0 of entry byte 0 clear) in the 14-entry enemy-shot table at 0x4260 (five bytes per entry), marks it active, copies the source object's two position bytes into entry+1 and entry+3, and stores a scaled X velocity at entry+4 aimed toward 0x4202 (mirrored when the target is left). That velocity is `computeJitteredXVelocity` [code]: the same slope division plus a random draw kept to 0..31 and a floor of 6, clamped to 0x7f on positive overflow, so aimed shots fan out with a little randomness rather than tracking perfectly. If the table is full the spawn is a no-op.

### Dive scheduling

Which objects launch, in which direction, and when is decided by a few schedulers. `selectAttackerRowScan` [code] seeds a (slot, base) pair from the alt flag 0x421b (nonzero gives slot 2 / base 157, else slot 1 / base 132), scans up to four two-byte slots of `ROW_OCCUPANCY` (0x41e8) advancing while neither byte of a slot has bit 0 set, and stores the resulting pair at 0x4213 — this is exactly the (count, match-value) pair the dive handlers scan against when deciding whether the current frame is a firing row. `chooseNextAttackerDirection` [code] sets the shared launch-direction flag 0x4215: the sign of the 16-bit formation anchor `loc_420e` (0x420e) picks which edge of `FORMATION_X_BOUNDS` (0x4210) to measure against, and within 28 pixels of that edge the direction is forced away from it, otherwise it is a fresh random bit. `computeControlledObjectMoveCommand` [code] is the auto-pilot that steers the ship in attract/demo: once every 32 frames (when 0x425f+9 masks to zero), and only while both the master enable 0x4007 and `OBJ_ACTIVE_FLAG` are set, it folds every record of both object tables into a running weight, adds a scaled anchor-versus-player offset (0x420e+128−0x4202) and a random ±1 nudge, and buckets the result into `OBJ_MOVE_CMD` (0x423f) as 0, 4, or 8 — the very bits `moveControlledObjectAndStageSprite` reads to move the ship. The per-object contribution is `accumulateObjectPositionWeight` [code], which contributes nothing unless the object is active, its position sits in one of two 52-row bands measured from 128, and its horizontal delta from 0x4202 is in the lower half; when it qualifies it folds a flag bit and two delta bits together with the band into a 0..15 index and adds the signed step read from `OBJ_STEP_TABLE` (0x1a45) to the accumulator.

### Collisions and the hit response

Two sweeps resolve overlaps each frame, both walking the seven records that begin one slot into the object block at `OBJ_TABLE` (0x42d0, 32-byte stride) — that is, slots one through seven of the eight-slot table. `flagPlayerShotHitsOnObjects` [code] runs only while the shot gate 0x4208 is armed, testing each object with `flagPlayerShotHitOnObject` [code]: an active object whose two position bytes fall inside a 6-wide by 12-tall box around the shot reference {0x4209, 0x420a} raises the shot-retire flag 0x420b and is scored and deactivated. `flagObjectHitsOnPlayer` [code] runs only while `OBJ_ACTIVE_FLAG` is set, testing each object with `flagObjectHitOnPlayer` [code]: it classifies the object's position (record+3 plus 33) into a near (<5) or far (<17) proximity window and, when the player-relative delta (0x4202 minus record+4) falls inside that window's band, raises `HIT_EVENT_FLAG` (0x4204) and scores/deactivates the object.

`handlePlayerHitEvent` [code] is the sole consumer of `HIT_EVENT_FLAG`. If its bit 0 is clear it does nothing; otherwise it clears the flag, pulls down `OBJ_ACTIVE_FLAG` and raises the death cell 0x4201 (which is what tells the ship-mover to freeze the ship under the explosion code), arms two pulse counters at 0x4205=10 and 0x4206=4, queues the hit sound, decrements the pace counter 0x421a with a floor of zero, steps the [0,5] cycle counter 0x421d, and pulses `SOUND_W_REG3` (0x6803) when the mode bit 0x4006 is set.

### Bringing the playfield up

Two sequence handlers stand this whole subsystem up. `resetObjectRamAndAdvanceSequence` [code] (sequence selector 0) reseeds the interleaved OBJRAM shadow from the ROM template at `loc_1d91` (0x1d91), zeroes the 64-byte sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad object-record region from 0x4260, clears 0x4238 and `MESSAGE_SCROLL_ENABLE` (0x40b0), points `VRAM_WRITE_PTR` (0x400b) two cells into the grid at `VRAM_BASE` (0x5000), arms the dwell timer 0x4009 to 16, and advances `SEQUENCE_STATE` (0x400a). `activateObjectsAndBeginPlayPhase` [code] then ticks that dwell timer each frame and, on its expiry, reloads it to 10, advances the sequence step, writes 1 across `OBJ_ACTIVE_FLAG` and its neighbour (enabling the subsystem while clearing the death cell 0x4201), centres the player at 0x4202=128, refills the 16-byte enemy-launch sub-counter block at 0x424a from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears the scratch cells 0x4058 and 0x405a, and queues two display commands. (The tiny shared stack epilogue `loc_090b` [code] — deliberately left unnamed — is just the common return of the command-enqueue path used by the queue helpers here; it touches no work RAM.)

## Sound

The sound machine runs off two clocks. Once per frame the vblank interrupt runs the composer `driveSoundFrame` [code] (0x16f5), which rebuilds this frame's discrete-sound bytes from scratch, and then runs `driveSoundLfoLevel` [code] (0x1898), which manages the vibrato/LFO level. Separately, the in-play update at 0x0661 fires three effect drivers that write hardware directly rather than composing through the main pitch path: `driveGatedSoundStepSequence` [code] (0x1327), `driveDecayingSoundSweep` [code] (0x16a6), and `driveSoundVoicesFromOccupancy` [code] (0x16b8). Everything lands on the board's discrete-sound latches: the eight write registers SOUND_W_REG0..SOUND_W_REG7 (0x6800-0x6807), the four LFO-frequency latches based at SOUND_LFO_FREQ (0x6004-0x6007), and the pitch latch SOUND_PITCH_W (0x7800).

### The per-frame composer

`driveSoundFrame` opens each frame from a clean slate: it clears the composite byte loc_41c0 and primes the pitch shadow SOUND_PITCH (0x41c1) to 0xFF. It then runs seven channel/effect updaters in a fixed order, each free to overwrite those two shadows, and finally latches the outcome to hardware — the composite loc_41c0 goes to SOUND_W_REG6 (0x6806), that same byte rotated right one bit goes to SOUND_W_REG7 (0x6807), and the pitch shadow goes to the pitch latch SOUND_PITCH_W (0x7800). Because every updater that produces sound both raises loc_41c0 (to 1 or 2) and overwrites SOUND_PITCH, the last-firing effect in the fixed order wins the frame's pitch, and loc_41c0 records which class of effect it was.

The first updater is `armSoundSequenceOnRequest` [seen] (0x1747). It watches the request byte loc_41d1 and fires only when that byte holds 1; on a fire it clears loc_41d1, raises the channel-A descriptor loc_41d2 and the shared duration timer loc_41d6 to 1, and publishes the sequence-data pointer SOUND_SEQ_PTR (0x41d3) at the ROM tone table loc_1e68. Any other value of loc_41d1 leaves everything untouched.

The second updater, `updateSoundSweepVoice` [code] (0x17d0), is the swept-pitch voice and only runs while the driver-enable bit loc_4006 bit0 is set. It counts the voice counter loc_41c2 down; on any frame where the pre-decrement is still nonzero it hands the counter's address to the sound-counter manager `advanceSoundSweepAndStagePitch` [code] (0x17e5), and on the one frame where the counter would reach zero it reloads the idle template instead — loc_41c2 = 0, the swept cell just past it (0x41c3) = 2, and the sound counter loc_41c4 = 160. That reload parks the sound counter well past its ceiling of 96, which is what stops the sweep from advancing until it decays.

The manager `advanceSoundSweepAndStagePitch` returns immediately while the mute gate loc_4226 bit0 is set. Otherwise it steps its pointer forward one cell (from the voice counter to the swept cell 0x41c3) and branches on the frame-phase flag loc_425f: with loc_425f bit0 set it stages the pitch straight away; otherwise it bumps the swept cell 0x41c3 by one so long as the sound counter loc_41c4 is still below 96, then falls into the counter tick `tickSoundCounterAndStagePitch` [seen] (0x17f9). That tick decrements loc_41c4 whenever the count is still running, and either way stages the pitch keyed on the swept cell. Pitch staging goes through `stageSoundPitchBySelector` [code] (0x1801): it reads the low two bits of the swept cell as a selector; a zero selector stages a fixed pitch of 96, while a nonzero selector recomputes the pitch from the counter through `stagePitchFromSoundCounter` [code] (0x180c). That recompute passes the counter value through unchanged on an even selector, and on an odd selector biases it by 96 and rotates the sum right one bit (the add's carry rotating back into the top bit) to produce a warbled pitch. The base staging primitive `stageSoundPitch` [seen] (0x1815) simply parks its argument into SOUND_PITCH; it writes that shadow and nothing else.

The third updater, `armSoundSequenceBySelector` [code] (0x1819), runs only while the driver-enable bit loc_4006 bit0 is set and reads the shared request byte loc_41df as a selector. A value of 6 arms this sequence — unless SOUND_SEQ_ACTIVE (0x41cd) already shows it running — by raising the channel-B descriptor loc_41cf and the shared duration loc_41d6 and publishing SOUND_SEQ_PTR at the ROM table loc_1ebd. Any other value is handed to `armSoundSequenceForSelector16` [code] (0x183a), which acts only on the selector 0x16: it clears loc_41cf, raises the channel-C flag SOUND_SEQ_ACTIVE (0x41cd) and the duration loc_41d6, and publishes SOUND_SEQ_PTR at the ROM table loc_1edf. Every other selector value is a no-op there. The three arm entry points thus each raise a different descriptor (loc_41d2, loc_41cf, or SOUND_SEQ_ACTIVE) and point the single shared cursor at a different ROM table (loc_1e68, loc_1ebd, or loc_1edf).

Those three descriptors are played by the fourth updater, `advanceAllSoundSequenceChannels` [code] (0x175d), which steps each of them — loc_41d2, loc_41cf, and SOUND_SEQ_ACTIVE (0x41cd) in turn — through `advanceSoundSequenceChannel` [code] (0x176c). A worth-noting current fact is that although there are three descriptor bytes, all three channels read and write one shared set of playback state: the current tone loc_41d5, the duration timer loc_41d6, and the cursor SOUND_SEQ_PTR (0x41d3). For an active descriptor the channel step raises loc_41c0 to 2 and publishes the current tone loc_41d5 into SOUND_PITCH, then ticks loc_41d6; while the timer still runs there is nothing more to do. When it expires the step pulls the next command byte from the cursor: the end marker 0xE0 deactivates that descriptor, while any other byte splits into a low-five-bit index into the ROM tone table SOUND_TONE_TABLE (0x17a9) — the new loc_41d5 — and a high-three-bit index into the ROM duration table SOUND_DURATION_TABLE (0x17c8) — the new loc_41d6 — and the cursor advances past the byte.

The fifth updater, `advancePulseToneEnvelope` [code] (0x184f), drives a decrementing envelope word whose low byte is loc_41c7 and high byte loc_41c8. When bit0 of the low byte is set it resets the word to its 0x8000 sentinel (loc_41c7 = 0, loc_41c8 = 128) and stops; otherwise it hands the high byte to `pulseSoundToneFromCountdown` [code] (0x185e). That handler idles when the high byte is zero, else stores it decremented back into loc_41c8 and stages a two-level pulse through `stagePitchAndRaiseSoundFlag` [code] (0x186c) — 129 when bit2 of the decremented count is set, otherwise 0, so the tone gates on and off as the envelope counts down. `stagePitchAndRaiseSoundFlag` stores its argument minus one (modulo 256) into SOUND_PITCH and raises loc_41c0 to 1, marking the shadow pair filled.

The sixth updater, `driveRisingPitchRamp` [code] (0x1876), watches an arm byte loc_41c9. While a test-only pre-decrement of that byte stays nonzero it advances the ramp through `advanceSoundPitchRamp` [seen] (0x1886); when the pre-decrement reaches its reset point it instead clears loc_41c9 and reloads the ramp pair (countdown loc_41ca = 32, pitch loc_41cb = 0). `advanceSoundPitchRamp` works over a {countdown, pitch} pair sitting one and two bytes past its pointer: a drained countdown means idle, otherwise it consumes one count, adds a fixed step of 4 to the pitch, publishes the new pitch into SOUND_PITCH — and, unusually among these updaters, clears loc_41c0 back to 0 rather than raising it, so the rising ramp emits a pitch while leaving the composite silent.

The seventh updater, `advanceGatedSquareTone` [code] (0x1723), runs a separate square-wave voice off a phase counter loc_41cc. While a pre-decrement of that counter stays nonzero it drives the tone through `driveGatedSquareTone` [code] (0x1733); at the expiry step it parks loc_41cc at 0 and re-arms the tone duration SOUND_TONE_DURATION (0x41ce) to 8. `driveGatedSquareTone` reads that duration: while it is nonzero it counts one tick off it and forms a level from the frame flag loc_4007 with bit0 flipped — a bit that alternates each frame, so the output toggles into a square wave — and once the duration is spent it emits 0 to silence. Either way the level is written straight to SOUND_W_REG5 (0x6805), so this voice bypasses the composite/pitch path entirely.

### The LFO level

Right after the composer, the vblank path runs `driveSoundLfoLevel` [code] (0x1898). With no pending reset (SOUND_LFO_RESET_REQUEST at 0x41d0 is zero) it runs the per-frame decay `decaySoundLfoLevel` [code] (0x18a6); otherwise it consumes the request and slams the level to full (15) across the LFO latches. `decaySoundLfoLevel` is armed only on the frame where the phase counter loc_425f reads 0xFF (once every 256 frames) and only while the level shadow SOUND_LFO_LEVEL (0x421f) is still nonzero, in which case it drops the level by one. Both paths publish through `broadcastSoundLfoLevel` [seen] (0x18b2), which saves the level into SOUND_LFO_LEVEL and then fans it across the four SOUND_LFO_FREQ latches (0x6004-0x6007), rotating the byte right one bit between writes so each latch receives a progressively shifted copy.

### The in-play effect drivers

Three more drivers run from the in-play update at 0x0661 and write hardware directly. `driveGatedSoundStepSequence` [code] (0x1327) is gated by the enable flag loc_4201 bit0; a prescaler loc_4205 (reload 10) fires once every ten eligible frames, and on each fire it enqueues a command word (opcode 2 carrying the current step from loc_4206) into the command queue and steps loc_4206 down. When the step count drains it disables itself (loc_4201 = 0) and silences SOUND_W_REG3 (0x6803). `driveDecayingSoundSweep` [code] (0x16a6) acts only on even frames (loc_4007 bit0 clear): while the countdown loc_41df is nonzero it emits that byte rotated right two bits to SOUND_W_REG4 (0x6804) and decrements it, so the emitted value shrinks toward silence. `driveSoundVoicesFromOccupancy` [code] (0x16b8), also even-frame gated, sums the 6×10 OCCUPANCY_GRID (0x4123, row stride 16) into a tally seeded at 1, lights that many of the three latches SOUND_W_REG0..SOUND_W_REG2 (0x6800-0x6802) capped at three while zeroing the rest, and sets the near-empty flag loc_4224 to 1 once the tally has nearly run dry — the formation "hum" that thins as the grid empties.

### The sound-request cell and the object-anim producer

The byte loc_41df is the shared sound-request cell, and it is read two different ways, which is why it remains an unnamed placeholder. `armSoundSequenceBySelector` treats it as a selector during the composer's pass (6 arms the loc_1ebd sequence, 0x16 arms the loc_1edf sequence, anything else no-ops), while `driveDecayingSoundSweep` treats any nonzero value in it as a countdown it emits and decrements. Its producer is `armObjectAnimAndRequestSound` [code] (0x10f0), the entry (sub-state 0) handler of a deactivated/dying object's animation: it seeds that object's animation timers (frame divider = 4, step count = 4, step field = 28), advances the object's sub-state so the entry runs once, and posts a sound request into loc_41df — 0x07 when the object's position byte (record+7) is below 112, 0x17 at or above it.

### Silencing the hardware

`silenceSoundAndDisableIrqStars` [code] (0x1cb5) is the hard quiesce used on shutdown and reset paths. It sets the four SOUND_LFO_FREQ latches (0x6004-0x6007) to 1, clears the eight write registers SOUND_W_REG0..SOUND_W_REG7 (0x6800-0x6807), clears IRQ_ENABLE (0x7001) and STARS_ENABLE (0x7004) to halt the vblank interrupt and the starfield, and drives the pitch latch SOUND_PITCH_W (0x7800) fully high (0xFF).

## Coins, credits, the HUD, score display, and the message scroller

This subsystem is the machine's "front of house": the parts that count coins into credits, light the start buttons, keep the on-screen scores and status glyphs current, and animate the attract-mode text. Almost all of it hangs off two spines — a small per-frame coin/credit/scroll service that runs during vertical blank, and a work-RAM command queue (write head at 0x40a0) onto which routines drop deferred draw and sound requests that a later HUD dispatcher renders. Whenever a routine here "queues a command word," it is appending a two-byte (channel, parameter) request to that queue; the append itself finishes through the deliberately-unnamed stack epilogue `loc_090b` (0x090b), which restores the caller's saved pointer and touches no work RAM.

### Counting coins into credits

Every frame the vblank service runs three coin routines back to back. First is `serviceCoinInputs` [seen], the front end that watches the physical coin lines. It reads the coinage/config mode in loc_4000: in mode 3 it simply hands off to `presetCreditCount` [code], which pins the credit machinery to free-play by clearing the coin-phase flag loc_4001 to 0 and forcing the credit count loc_4002 to 9. Otherwise it debounces the inputs — it ORs the live input shadow IN0_SHADOW (0x4010) with the previous-frame shadow loc_4013, complements that, and masks it against the two older history frames loc_4015 and loc_4016, so a coin only registers on a clean, sustained transition rather than a single noisy frame. If the high (0x80) line survives that mask it calls `addCreditForCoin` [code] directly; otherwise the low two bits are the two coin-slot pulse lines, and each one that is set ticks the coarse coin-pulse accumulator loc_4004 (up to twice per frame).

`addCreditForCoin` is the immediate-credit path: while the credit count loc_4002 is below its ceiling of 99 it bumps the count, raises the ready flag loc_41c9 (the same cell the pitch-ramp arms on), and queues a channel-7 command that repaints the credit line on the HUD; at the 99 cap it does nothing.

The accumulated coin pulses in loc_4004 are turned into credits by the second per-frame routine, `tickCoinMeterAndAwardCredits` [seen]. It runs a two-stage meter: while the reload/pulse-width cell loc_4003 is still nonzero it calls `pulseCoinCounter` [seen] and counts loc_4003 down; once loc_4003 reaches zero and there is coarse pulse work outstanding in loc_4004, it decrements loc_4004, refills loc_4003 to 15, and awards credits according to the coinage mode in loc_4000 — mode 3 awards nothing, mode 1 runs the two-coins-per-credit path, mode 2 awards two credits per coin (it steps the credit counter twice), and every other mode awards one. `pulseCoinCounter` is what actually drives the electromechanical coin meter: it circular-rotates the byte it is handed right by three bits (so bit 3 of the value lands in bit 0, the only wired bit) and latches that to COIN_COUNTER_0_LATCH (0x6003), then decrements the timer cell it was pointed at, giving the meter output a timed pulse.

Two small routines finish the credit-count arithmetic. `incrementCreditCount` [code] steps the counter at loc_4002 toward the 99 ceiling: at the ceiling it stops, above the ceiling it calls `clampCreditsToMax` [code] to pin the cell back to exactly 99, and below the ceiling it bumps the count, raises the ready flag loc_41c9, and queues the same channel-7 credit-line redraw. `clampCreditsToMax` is just that overshoot arm — it writes 99 into the cell. The two-coins-per-credit case is handled by `awardCreditEverySecondCoin` [code], a phase toggle over loc_4001: on the first coin of a pair (phase bit clear) it calls `setCoinPhaseFlag` [code] to raise the flag; on the second coin it clears loc_4001 and delegates to `incrementCreditCount` to actually award the credit. `setCoinPhaseFlag` simply writes 1 into the phase cell.

The third per-frame coin routine is `updateCoinLockoutFromCredits` [code], which drives the physical coin-mechanism lockout coil from the banked credit total: at nine or more credits in loc_4002 it releases the lockout by calling `clearCoinLockout` [code] (which writes 0 to COIN_LOCKOUT, 0x6002), and below nine it engages the lockout by writing 1 there. So the cabinet stops accepting coins once nine credits are banked.

One more counter-refill primitive sits in this neighbourhood by shape rather than by wiring: `reloadExpiredCounterAndTally` [seen] copies a reload byte from a source table into an expired counter cell and returns the running refill tally bumped by one. Its live user is the enemy-launch pacer, which sweeps a bank of attacker sub-counters and refills each expired one from SUBCOUNTER_RELOAD_TABLE (0x15e3); it is the same reload-and-tally idiom the coin meter uses when it refills loc_4003, which is why it reads as kin to the credit machinery even though it belongs to the attack pacer.

### Start-button lamps and the jump into play

`driveStartButtonLamps` [code] mirrors the credit total onto the two start-button lamp outputs START_LAMP_0 (0x6000) and START_LAMP_1 (0x6001), gated on bit 5 of the free-running frame/phase counter loc_425f: while that bit is clear both lamps are forced off, and while it is set the lamps reflect credits — no credits leaves them, one credit lights lamp 0, and two or more lights both. Because loc_425f is decremented every frame, bit 5 alternates on a roughly 32-frame cycle, so the start lamps blink whenever there are credits to spend.

Several attract-sequence handlers keep the lamps in step while marching the sequence state forward. `holdStartLampsThenAdvanceSequence` [code] ticks the countdown loc_4019 each frame and, while it stays nonzero, keeps re-driving the lamps through `driveStartButtonLamps`; on the countdown's zero-crossing it advances SEQUENCE_STATE (0x400a) and clears the 128-byte flag block at FLAG_BITS_BASE (0x4100). `blankVramRowsThenDriveStartLamps` [code] is the sequence step that clears the play area: it fills two 28-cell blank-tile rows through the VRAM write cursor VRAM_WRITE_PTR (0x400b) (skipping a four-cell gap between them), counts down the dwell tier loc_4009, and while rows remain it returns; on the last row it advances SEQUENCE_STATE, clears the screen-flip latches FLIP_SCREEN_X/FLIP_SCREEN_Y (0x7006/0x7007) and the direction flag loc_4018, queues two command words (a channel-7 and a channel-6 draw), and re-drives the lamps.

The credit-to-play transition itself is `advanceGameStateOnCredit` [code]: when the credit count loc_4002 is nonzero it advances the game-state index GAME_STATE (0x4005) and clears a cluster of attract-state cells — the frame-parity flag loc_4007, SEQUENCE_STATE, loc_41c2, the sound-request/sweep selector loc_41df, and the message-scroller enable MESSAGE_SCROLL_ENABLE (0x40b0); with zero credits it is a no-op, so play only begins once a credit has been banked. Once a game is committed, `startGameRoundAndClearScores` [code] does the round setup: it stores the player-count/spawn word into CURRENT_PLAYER (0x400d) (a 16-bit store that also seeds the paired-player flag loc_400e), blits the 32-byte row template from ROM loc_051b into the packed-flag buffer PACKED_FLAG_BITMAP (0x4180), optionally arms the sub-state advance gate when config bit loc_401f bit 0 is set, enters play (GAME_STATE = 3, SEQUENCE_STATE = 0, mode gate loc_4006 = 1, loc_41d1 = 1), then queues a start-message draw (channel 6) and two channel-4 commands that clear the score slots — which is where the scores get zeroed for the new round.

### Score display

Scores live as three-byte packed-BCD fields — PLAYER1_SCORE_BCD (0x40a2), PLAYER2_SCORE_BCD (0x40a5), and HIGH_SCORE_BCD (0x40a8) — and are painted as vertical runs of digit tiles (the display is rotated, so a VRAM column reads as a horizontal score on screen). The lowest-level converter is `byteToPackedBcd` [code], which reduces a binary byte to its value modulo 100 and packs the tens into the high nibble and the units into the low nibble. `drawBcdDigit` [code] paints one BCD nibble as a font glyph — digits map to the contiguous tiles 0x90..0x99 — with leading-zero suppression: while the blank budget is nonzero a leading zero draws the blank tile (the 0x80 bias wraps the digit base to tile 0x10) and consumes one unit of budget, and the first significant digit ends suppression; it then steps the cursor by its stride. `drawBcdNumberColumn` [code] walks three packed-BCD bytes downward from a source pointer, most-significant first, emitting six digit tiles up a column (one row, −32, per digit) with a four-digit leading-zero budget.

Selection and dispatch sit on top of those. `selectCurrentPlayerScore` [code] returns the active player's score field base — 0x40a2 for player 1, else 0x40a5 — chosen by CURRENT_PLAYER. `drawScoreToSelectedPlayerField` [code] picks the destination VRAM digit field from a selector — the primary field DIGIT_FIELD_PRIMARY (0x5381) when zero, else the alternate field DIGIT_FIELD_ALT (0x5121) — and paints the BCD column into it. `drawHighScoreDigits` [code] paints six high-score digits into the fixed high-score field at loc_5241. `drawScoreFieldByIndex` [code] is the index-driven redraw: index 0 repaints player 1's score, index 1 repaints player 2's score but only when the paired-player flag loc_400e is set (which also selects the alternate field), index 2 repaints the high score, and an index of 3 or more descends, repainting every lower field. `clearAndRedrawScoreField` [seen] is the clearing sibling: for the same index scheme it zeroes the selected field's three digit bytes plus a companion scratch byte (loc_40ad for player 1, loc_40ae for player 2; the high score simply re-zeroes its own first byte) and then repaints via `drawScoreFieldByIndex`; index 3 or more clears and repaints all lower fields — this is what the channel-4 commands from round start drive.

Scores actually grow through the channel-3 BCD score-add handler, which ties several of these routines together: it adds a BCD increment into the current player's field, redraws it via `drawScoreToSelectedPlayerField`, and compares the folded running total against a per-player bonus threshold in loc_40ac and against the stored high total; when the total tops the high score it copies three bytes into HIGH_SCORE_BCD and repaints through `drawHighScoreDigits`, and when the bonus threshold is crossed it calls `awardBonusMarker` [code]. `awardBonusMarker` is a one-shot per player: it indexes the per-player flag table at loc_40ad by CURRENT_PLAYER and returns if that player's slot is already flagged; otherwise it flags the slot, raises the sound-envelope trigger loc_41c7 (the bonus jingle), bumps the marker counter loc_421d, and repaints the marker row with the new count. Kill scoring feeds the same add path: `awardKillScoreByBandAndDeactivate` [code] deactivates the hit object (clearing its active byte, setting its second byte to 1, and zeroing its state byte), then scans the object's packed field byte in three bands against the 0x50 threshold — each missed band bumps the score parameter and drops the field by 16 — and queues a channel-3 score-add sized by the matched band. On band-exhaust it raises the inhibit/arm word loc_422b (to 0xf001), folds in a neighbour bonus when the active-neighbour count ACTIVE_NEIGHBOR_COUNT (0x422a) is exactly two, records the bonus in loc_422d, and queues the folded score request.

The marker row itself is drawn by `drawMarkerRow` [code], which paints a five-slot row at MARKER_ROW_VRAM (0x539e): it stamps `markers` marker glyphs (tile 102) growing upward from the row cell, then blanks the remaining slots until its signed slot counter goes negative. When the object-active flag OBJ_ACTIVE_FLAG (0x4200) is set the displayed count is dropped by one, and if that empties it the whole row is blanked instead — so the row shows one fewer marker while play is live.

### The player-status column

Alongside the scores each player has a three-cell status column in VRAM — player 1's at PLAYER1_STATUS_VRAM (0x5340), player 2's at PLAYER2_STATUS_VRAM (0x50e0). `selectPlayerStatusVram` [code] returns the right base for a player index. `paintPlayerStatusColumn` [code] paints the three cells from a base stepping by a stride — the top cell gets the incremented character code, the middle a fixed tile 0x25, the bottom a fixed tile 0x20 — and afterwards, only when the caller's flag bit 4 is clear and the mode gate loc_4006 is zero, it clears the saved-status byte loc_40ab. `repaintPlayerStatusColumn` [code] wraps that with a mode bit: with the caller's bit 4 clear it paints the active player's column directly; with bit 4 set it blanks the active column's three cells (tile 16, stepping one row up) and, when the paired-player flag loc_400e is set, also paints the other player's column. `repaintPlayerStatusColumnIfSaved` [code] gates a repaint on the saved-status byte loc_40ab being nonzero, and `repaintPlayerStatusColumnFromModeGate` [seen] latches the mode: when the mode byte loc_4006 is nonzero it saves that value into loc_40ab and repaints, and when loc_4006 is zero it repaints only if loc_40ab is already set — so the status column follows the mode gate but keeps painting once it has been armed.

### Attract text columns

Static on-screen text — the DIP-configured readouts and score-table lines shown in attract mode — is painted a column at a time. `drawTextColumn` [code] is the loop: for `count` characters it reads a source byte, subtracts the '0' code (48) to map it to a font tile, stores it, then steps the source forward one byte and the destination by a stride (a −32 stride walks up a column; a count of zero means a full 256 passes). `drawTextColumnFromDescriptor` [code] unpacks a five-byte descriptor (source word, destination word, count byte) and paints that many characters up a column with the −32 stride. `drawTextColumnByIndex` [code] indexes the five-byte descriptor table TEXT_DESCRIPTOR_TABLE (0x1cf6) by a number and paints that descriptor — this is how the attract screen turns a DIP field into the right line of text.

### The message system and scroller

Discrete messages (the flashing prompts and callouts) go through `renderMessageColumn` [seen], a painter selected by an index. It reads a record (a destination word followed by the message text) from the message pointer table MESSAGE_PTR_TABLE (0x235c), and the index's top two bits pick the mode. Bit 7 blanks the message — it overwrites each character cell up the column with the blank tile until the terminator (character 63). Bit 6 is the scroll-arm setup: it records the destination pointer into MESSAGE_DEST_PTR (0x40b5) and the text pointer into MESSAGE_TEXT_PTR (0x40b3), derives a per-column counter cursor at loc_4020 + column*2 and stores it in MESSAGE_CURSOR_PTR (0x40b1), clears the whole 32-cell column to tile 16, seeds that counter cell with a value packed from the destination's position, and raises MESSAGE_SCROLL_ENABLE (0x40b0). With neither high bit set it just draws every glyph up the column immediately (a static message, mapping each source byte to a tile up a −32 stride to the terminator).

Once armed, the scroll is advanced one frame at a time by `advanceMessageScroller` [seen], which runs from the same per-frame vblank service. While MESSAGE_SCROLL_ENABLE is set it reads the counter through MESSAGE_CURSOR_PTR: if the counter's low three bits are still nonzero it merely ticks the counter (a delay), so a new glyph is revealed only about every eighth frame; when they reach zero it takes the character at MESSAGE_TEXT_PTR — at the terminator (63) it emits nothing and just finishes the countdown, otherwise it advances the text pointer, maps the character to its tile into the cell at MESSAGE_DEST_PTR, steps that destination up one row (−32), and ticks the counter. The tick is done by `endMessageScrollOnExpiry` [seen], which decrements the counter and, on the exact zero-crossing, clears MESSAGE_SCROLL_ENABLE so the scroller stops; `endMessageScrollOnExpiryFromDe` [seen] is its twin for when the counter pointer arrives in the alternate register, used by the glyph-emit and terminator paths. So the packed seed value both paces the reveal (its low bits) and bounds how long the scroller runs (its magnitude).

Messages are requested through the command queue by three handlers. `advanceObjectAndQueueMessageColumn` [seen] is an object's own state step: it bumps the object record's tick counter and counts down its dwell timer, and while the timer runs it returns; on expiry it queues a channel-6 command whose parameter is the object's payload selector plus 75 (dispatched to `renderMessageColumn`) and advances the object's state — so certain objects trigger a message when their dwell elapses. `emitMessageColumnsThenAdvanceSequence` [seen] is an attract sequence-state handler: it runs the shared strided-table reset, then a two-tier dwell over the sub-timer loc_4008 and tier loc_4009 — each low-tier expiry reloads it to 80 and queues a channel-6 message-column command whose index tracks the mid-tier count (mid + 6), painting successive message columns across the screen — and on the mid-tier's expiry it advances SEQUENCE_STATE, reloads both tiers (32 and 4), clears the sprite-source block at SPRITE_SOURCE_OBJ_BASE (0x42b0), and zeroes the redraw count DRAWN_COLUMN_COUNT (0x4241). `postCreditAndMessageDrawsAndAdvance` [code] is the simpler sequence step that queues one channel-7 credit/score redraw and one channel-6 message-column draw, advances SEQUENCE_STATE, and re-arms the two-tier dwell cascade (loc_4008 = 96, loc_4009 = 16).

### The attract screen-fill wipe

Attract mode animates a tiled wipe down the screen. `drawInputTextColumnsAndSeedScreenFill` [seen] both draws the DIP readout and seeds that wipe: it decodes three two-bit input fields — IN1 (0x6800) bits 6–7, IN2_PORT (0x7000) bits 0–1, and IN2 bit 2 — into text-descriptor indices and paints each column via `drawTextColumnByIndex`, and then, unless the service/test input IN0 bit 6 is asserted, it seeds the fill state (clears the mode gate loc_4006, sets loc_401a to 2, seeds the dwell pair loc_4008/loc_4009 to 16/48, rewinds VRAM_WRITE_PTR to VRAM_BASE at 0x5000), clears the four-byte lamp/coin latch block, and silences the sound hardware. `armInputFlagAndDrawInputColumns` [code] is the link that reaches it from the input scan: it folds the two input-port bytes it is handed and, when their shared bit 4 (start) is set, raises the companion control flag loc_41cc, then falls through to that seed-and-draw routine.

The per-frame animation is `advanceScreenFillStrip` [code]: it pets the watchdog (a discarded read of SOUND_PITCH_W, 0x7800), then reads the strip gate/counter loc_4008 — if it is zero there is no strip to draw so it restarts the outer dwell via `restartScreenFillOnDwellExpiry`, otherwise it loads the live cursor VRAM_WRITE_PTR and draws the strip's first half. `drawScreenFillStripFirstHalf` [code] stamps 16 two-tile pairs (tiles 48 and 50) forward from the cursor and flows straight into `drawScreenFillStripSecondHalf` [code], which stamps 16 more pairs (tiles 52 and 54), saves the advanced cursor back to VRAM_WRITE_PTR, and ticks the strip countdown loc_4008; while that is still running it is done, and on its expiry it restarts the outer dwell. `restartScreenFillOnDwellExpiry` [seen] ticks the high dwell tier (the byte just past its pointer, i.e. loc_4009) and, when that reaches zero — or is already zero — re-seeds the whole fill through `resetScreenFillState`. `resetScreenFillState` [seen] is the re-seed itself: unless IN0 bit 6 is asserted it rewinds VRAM_WRITE_PTR to VRAM_BASE, re-arms the fill-length counter loc_4008 to a full page (32), and clears both the alternate-dispatch flag loc_401a and GAME_STATE — so the wipe loops indefinitely in attract, held only by the service/test switch.

### Per-frame sound and input scan behind the attract screen

In the A==1 game-state selected by the top-level frame dispatch, the machine runs a per-frame audio-and-input pass, `driveSoundFrameAndScanInput` [code]: it ticks the sound driver and the decaying sweep, pets the watchdog (a discarded read of SOUND_PITCH_W), then reads IN0 (0x6000) and, if any of its arm bits (7, 1, 0) is set, raises the pitch-ramp arm cell loc_41c9; it then falls into the input-scan chain carrying the raw IN0 byte. `requestSoundOnInput1AndContinueScan` [code] reads IN1 (0x6800) and, if either of its low two bits is set, seeds the sound-request selector loc_41df to 0x16, then continues the scan handing on both port bytes. `requestSound6AndContinueInputScan` [code] tests bits 2–3 of the folded input ports and, if either is set, seeds loc_41df to 6 (the selector the sound arm keys on), then falls through into `armInputFlagAndDrawInputColumns` — which raises the start companion flag loc_41cc if warranted and redraws the DIP text columns while re-seeding the screen-fill wipe. So the attract screen's demo sound and its live redraw both ride out of this one input-scan chain each frame.

## Tile / VRAM drawing primitives and coordinate mapping

The tile picture lives in a 32-by-32 grid of one-byte cells beginning at `VRAM_BASE`
(0x5000). Almost every drawing routine here writes tile codes into that grid, and they are
built up in a small tower: a two-cell stamp at the bottom, block builders that call it,
fixed-seed and table-driven front doors above those, and a handful of coordinate mappers
and animation helpers that decide *where* and *which* tile to draw.

### From a packed coordinate to a cell address

`mapPackedCoordToVram` [code] is the addressing heart of the whole subsystem. It takes a
single packed coordinate byte and reshuffles its nibble fields into a tilemap-cell address.
The low nibble is rotated so that its top two bits become a 2-bit *page* (0..3) — the cell
address's high byte — and its bottom two bits seed the top of the low byte; the coordinate's
high-nibble bits are folded (a complemented running sum kept to a nibble) into the rest of
the low byte. The final address is `VRAM_BASE + (page << 8) + low`, so every mapped cell
lands somewhere in 0x5000..0x53ff. The routine hands back three things at once, and callers
lean on all of them: `HL` carries the cell address, `A` is left holding coordinate bits 6..5,
and — the fact worth pinning down — the *carry* flag is left equal to coordinate **bit 4**.
That carry, not any separate test, is how the figure drawers downstream decide between a
square block and a tall pair. The routine also parks the original coordinate in `B` on its way
through, which one animated caller reuses as the variant input.

### The two-cell stamp and the double-height glyph

`stampTilePair` [code] is the primitive everything block-shaped is made of. Given a seed tile
code in `A` and a destination in `HL`, it writes `tile` at `HL`, `tile+1` at `HL+1`, then
advances the pointer past that pair by the caller-supplied stride and bumps the tile code by
two — so a caller that keeps calling it walks a run of consecutive glyph codes across memory.
Because the store truncates to a byte, a seed of 0xff writes 0xff then 0x00. The advanced
`{tile, pointer}` are returned (and mirrored into the registers) precisely so chained callers
can thread one stamp into the next.

`drawDoubleHeightTile` [code] is the vertical counterpart used when a figure is one cell wide
but two tall: it writes the seed tile at `HL` and `tile+2` one tilemap row (32 cells) directly
below. That "+2" is the convention throughout — the bottom half of a stacked glyph pair is
coded two above the top half.

### Building 2x2 blocks up and down

`drawTileBlock2x2` [code] lays a square block of four cells from a single seed: it stamps the
top pair `(tile, tile+1)`, then the bottom pair `(tile+2, tile+3)` one row down. It does this
with two `stampTilePair` passes carrying a stride of 31, so each pair advances +1 (past itself)
and then +31 = +32, dropping exactly one tilemap row. `DE` comes back untouched. In the
original there is a shared exit these block writers fall into after staging the top pair —
`drawBottomTilePairRestoreDe` [code] — which stamps that second (bottom) pair through the same
primitive and then restores the `DE` the caller stacked before the block began, handing it
back. It is the common tail of the 2x2 writers rather than an entry point of its own.

`drawTileBlock2x2Up` [code] is the mirror image, growing a block *upward* from the pointer.
It uses a stride of 65503 (−33 taken as an unsigned 16-bit step) so that after each pair's
built-in +1 the pointer moves one row up, and it steps the seed code back by four before the
upper pair — so the visual top-to-bottom ordering of glyph codes stays consistent even though
the block is built bottom-first.

Several fixed-seed front doors sit over these builders so callers need pass no tile code.
`drawFixedTileBlock2x2` [code] seeds `drawTileBlock2x2` with tile 44 (0x2c); its upward twin
`drawFixedTileBlock2x2Up` [code] seeds `drawTileBlock2x2Up` with tile 46 (0x2e).
`drawFixedTilePairHorizontal` [code] seeds a single horizontal pair (tile 44) through
`stampTilePair` and returns its advanced tile/pointer so a caller's loop can chain the next
pair; `drawFixedTilePairVertical` [code] seeds the same tile 44 into `drawDoubleHeightTile`
for a tall pair instead of a wide one.

`drawTileBlock2x2AtDe` [code] is the block writer used when the destination arrived in `DE`
rather than `HL`. It exchanges `DE` and `HL` — so the incoming `DE` becomes the draw pointer
and the old `HL` is handed back in `DE` — then draws the 2x2 block there. This swap-then-draw
shape is what lets the table-driven callers stash a pointer across a table fetch that would
otherwise clobber it.

### Selecting a block from a table, or a glyph

`drawIndexedTileBlock` [code] reads a block's seed tile out of the ROM block table
`TILE_BLOCK_TABLE` (0x215b) by an index, then stamps that 2x2 block at the pending `DE`
pointer through `drawTileBlock2x2AtDe`. `drawSelectedTileBlockOrFallback` [code] puts a signed
gate in front of it: a non-negative selector is used as that table index, while a negative
selector (high bit set) skips the table entirely and stamps a fixed fallback block seeded with
tile 0xa4 at the `DE` pointer.

`drawTileGlyphOrBlock` [code] is the tile-draw dispatcher that chooses between a block and a
glyph based on the incoming carry. On carry it swaps `DE`/`HL` and hands off to
`drawSelectedTileBlockOrFallback`, drawing the selected 2x2 block at the swapped pointer. With
no carry it instead fetches a tile code for the selector from the index table at `loc_2157`
(0x2157) and paints it as a double-height glyph at the *incoming* `HL`; the pointer exchange on
this path is only there to shelter `HL` across the table fetch, which would otherwise overwrite
it, so the glyph still lands at the address the caller supplied.

### Timer-animated tile variants

Two folders bias a tile-variant value by the frame counter so a figure can shimmer between a
few glyph forms. `computeTileVariantFromTimer` [code] works on `B`: if `B` is at or above 112
(0x70) it saturates to the out-of-range marker (0x80) and leaves everything else alone;
otherwise it swaps the nibbles of the frame-counter byte at `loc_425f` (0x425f), adds `B` and
the carry input `C`, and keeps the low two bits — collapsing the value to a 2-bit variant
index in `B`. `computeTileVariantFromValueAndTimer` [code] is the usual entry to it: it
likewise saturates at 112, but for in-range values it takes only the value's low nibble and
manufactures the carry input by comparing that nibble against the low nibble of the same frame
counter — a carry when the counter's nibble is the smaller — before folding through
`computeTileVariantFromTimer`. The net effect is a variant index that walks as the frame
counter turns over.

### Drawing a figure at a packed coordinate

`drawFixedTileFigureAtPackedCoord` [code] is the fixed-tile figure drawer: it maps a packed
coordinate to its cell, then — reading the mapper's carry live-out, which is coordinate bit 4
— draws either a fixed 2x2 block (`drawFixedTileBlock2x2`) when that bit is set or a fixed
vertical tile pair (`drawFixedTilePairVertical`) when it is clear. `drawAnimatedTileFigureAtPackedCoord`
[code] is its animated sibling and threads three of the pieces above together: it maps the
coordinate to a cell, folds that same coordinate (recovered from `B`, where the mapper left it)
into a timer-animated variant via `computeTileVariantFromValueAndTimer`, and then dispatches
through `drawTileGlyphOrBlock` — a 2x2 block when coordinate bit 4 is set, a double-height
glyph otherwise — carrying `VRAM_BASE` in as the pointer for the block path's swap.

### Blanking blocks and composing indicator forms

`blankTileBlock4x4` [code] wipes a 4x4 patch anchored at `loc_51da` (0x51da), writing the
blank-tile code 0x40 into four rows of four cells, stepping a full 32-cell row between row
starts. Note this uses 0x40 as its blank code, distinct from the 0x10 (16) blank used by the
row/column fills below. `blank4x4AndDraw2x2Icon` [code] clears that 4x4 patch and then draws a
2x2 block seeded with tile 96 (0x60) at `loc_51fc` (0x51fc), overlaying a small icon on the
cleared field. `draw4x4TileForm` [code] is the three-way indicator painter selected by a form
index: form 0 is the blank-and-icon composition just described, form 1 is a bare 4x4 blank, and
any higher form folds `(form − 2)` into the mid bits of a tile code (shifted, complemented,
masked to 0x30, over a fixed 0xc0 base) and stamps four 2x2 blocks across the indicator's four
corners at `loc_51da`, `loc_51dc` (0x51dc), `loc_521a` (0x521a) and `loc_521c` (0x521c), the
seed advancing four codes per corner so the four blocks draw consecutive glyph runs.

### Vertical tile-column strips

A separate primitive handles the thin vertical strips redrawn during play.
`drawTileColumnTriple` [code] copies three source bytes up a single VRAM column: each byte is
written at the destination, whose low address byte then steps down 32 (one tilemap row up)
within a fixed page — the high byte never moves. After the three cells the low byte has dropped
96, and the routine adds 98, landing two past the column's start so the next column is lined up;
it returns the advanced source pointer and destination for chaining.  `blankTileColumns` [code]
is the erase counterpart: for each of `columns` columns it stamps the blank tile 16 into three
cells, stepping up one row each, then advances the low byte by 98 to the next column, starting
from `loc_5193` (0x5193). Because the loop is a decrement-and-branch over the column count, a
count of zero wraps to a full 256 columns.

`redrawTileColumnsPeriodically` [code] drives both of those on a frame cadence. It reads the
running `DRAWN_COLUMN_COUNT` (0x4241); with fewer than two counted columns it does nothing.
Otherwise it looks at the frame counter `loc_425f`: on the phase where the low six bits are
zero it blanks the columns, and only on the phase where they equal 32 does it redraw them —
every other frame is skipped. On the draw phase the first column is sourced from the row picked
by the frame counter's top two bits within the source table `TILE_COLUMN_TABLE` (0x039a, three
bytes per row) and written to `loc_5193`; the remaining columns are drawn from the continuation
stream `TILE_COLUMN_TABLE_CONT` (0x03a6), threading source and destination forward from each
draw.

### VRAM-fill sequence steps

A short chain of state-machine steps clears and repaints the screen a strip at a time during
the attract/init sequence, each keyed off the sequence-step index `SEQUENCE_STATE` (0x400a)
and a running write cursor `VRAM_WRITE_PTR` (0x400b), and each ticking a dwell timer at
`loc_4009` before advancing.

`primeVramFillAndAdvanceStep` [seen] sets that machinery up: it zeroes a 128-byte work-RAM
block from `FLAG_BITS_BASE` (0x4100) and clears the two status bytes `loc_425f` and `loc_4224`
(0x4224), points the write cursor two cells into the grid (`VRAM_BASE + 2`), arms the page
counter `loc_4009` to 32, and bumps the sequence step. `fillVramRowThenResetObjectState`
[seen] then runs one strip per invocation: it paints a 28-cell strip of tile 16 at the cursor
and steps the cursor a full 32-cell row on, and ticks the dwell timer; while the timer still
counts it simply returns. When the timer expires it advances the sequence step, re-arms the
two-tier dwell cascade (`loc_4008` = 64, `loc_4009` = 4), clears a 48-byte active-object block
from `OBJ_ACTIVE_FLAG` (0x4200), drops both screen-flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y`
and the direction flag `loc_4018`, raises the status flag `loc_4238`, and reseeds the object
shadow from the ROM template `OBJ_SHADOW_RESEED_TEMPLATE` (0x1db1).

`blankVramRowThenResetSpriteState` [code] is the analogous step on the sprite side: it clears
a strided table, blanks a 28-cell row of tile 16 at the cursor and advances it a row, and ticks
the same dwell timer. On expiry it advances the sequence step, clears the whole 256-byte object
source block at `SPRITE_SOURCE_OBJ_BASE` (0x42b0) and 64 bytes of sprite shadow at
`SPRITE_SHADOW_BASE` (0x4060), re-arms the two dwell tiers, reseeds the object shadow from ROM,
and queues command word 6. `blankScreenRowsThenAdvanceSequence` [code] is the plainest of the
three: it blanks 32 cells of tile 16 at the cursor and stores the advanced cursor back, ticks
the phase counter `loc_4009`, and on the final phase advances the sequence state and reseeds the
object shadow.

### Projectile integration and rendering

Sitting alongside the tile drawers, three routines integrate and render the moving-projectile
records that share the base at `loc_4260` (0x4260). `advanceAndRenderProjectiles` [code] steps
seven 10-byte records, each of which is two 5-byte sub-slots (active bit, sub-position,
16-bit integrated position, and a signed velocity). A phase bit in the frame counter `loc_425f`
selects which sub-slot leads this frame; the other sub-slot merely has its sub-position bumped
by two. For the leading sub-slot when active, the routine advances the sub-position (and
deactivates on overflow), integrates the 16-bit position by twice the sign-extended velocity,
and deactivates the slot when the position's high byte leaves the vertical window
(`(hi + 0x10) < 0x20`); deactivating zeros the active, sub-position and high bytes. It then
writes the sprite's `Y` and code into the sprite shadow at `loc_4081` (0x4081) — either
straight or complemented depending on the direction flag `loc_4018` — with a ±1 code nudge on
the first three records of the pass.

Collision against the player is a separate pair. `flagProjectileHitsOnPlayer` [code] is the
gate: only when projectiles are enabled (the low bit of `OBJ_ACTIVE_FLAG` set) does it box-test
all fourteen 5-byte entries starting at `loc_4260`. A subtlety worth stating: the per-entry
Y-band delta it passes is always 5, the record stride, because that is what the register holds
as the loop walks the table — never any value a caller left behind. `flagProjectileHitOnPlayer`
[code] performs the single-entry test: it ignores inactive entries, reads the player X
reference at `loc_4202` (0x4202), and branches on a near/far Y band computed from the entry's
shifted Y. In the far band it accepts a hit when X is within the band delta of the player (plus
a small bias); in the near band it first requires the entry Y within nine units and then X
within eleven. On a hit it deactivates the struck entry and raises `HIT_EVENT_FLAG` (0x4204).

For completeness, the game keeps one deliberately-unnamed shared epilogue, `loc_090b`, which
simply restores `HL` and returns; it belongs to an unrelated enqueue path rather than to these
drawing routines, but it is the same kind of pure-stack tail that the block writers reach
through `drawBottomTilePairRestoreDe`.

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs.
