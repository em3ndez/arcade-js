# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–6.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

These are the small, general-purpose services that the rest of the machine leans on: two low-address restart vectors that any routine can invoke with a single-byte instruction, a pseudo-random generator, and the epilogue that keeps the per-frame interrupt alive.

### Two restart-vector utilities

Because the Z80 reserves its lowest addresses as one-byte restart entry points, Galaxian parks its two most-used byte-level helpers there so callers reach them cheaply. The first, at `0x0010`, is `fillMemoryBlock` [code]: a tight memory-fill loop that stores a single value into a run of consecutive bytes. The caller hands it a destination pointer, the fill value, and a byte count; the routine walks the pointer forward, writing the value at each step, until the count is exhausted, then hands back the pointer sitting just past the fill (with the count spent to zero). The one subtlety worth holding onto is that the count is decremented and tested *after* the first write, so a count of zero does not skip the fill — it wraps around and lays down a full 256 bytes. This one primitive does nearly all of the game's bulk clearing and blanking: wiping object RAM before a round, blanking VRAM rows and tile columns for screen transitions, clearing flag blocks, and painting the screen fill; callers such as `resetObjectRamAndAdvanceSequence`, `blankScreenRowsThenAdvanceSequence`, `clearFlagBlockAndReseedObjectShadow`, and `fillScreenThenLatchConfigAndAdvanceState` all route their bulk writes through it. Its store targets whatever the pointer names, so the same loop that clears work RAM can also drive a memory-mapped video or hardware address.

The second, at `0x0020`, is `fetchIndexedTableByte` [code]: the machine's standard indexed table lookup. Given a table base pointer and an 8-bit index, it adds the index to the pointer — carrying correctly into the high byte, so an index that runs the pointer across a 256-byte page boundary still lands on the right byte — and then reads the byte at the resulting address. It returns that byte and leaves the advanced pointer behind for the caller, so a routine can fetch an entry and immediately keep reading from that spot. This is the workhorse behind data-driven drawing: `drawIndexedTileBlock`, `drawTileGlyphOrBlock`, and `fillScreenThenLatchConfigAndAdvanceState` all use it to translate an index into a table entry (a tile code, a descriptor byte, a configuration value).

### The pseudo-random generator

Randomness comes from `advanceRandomSeed` [seen], a linear-congruential generator built on the single seed byte `RNG_SEED` at `0x401e`. Each draw reads the current seed, computes `seed*5 + 1` folded back into eight bits, stores that new value back into `RNG_SEED`, and returns it as the draw. There is no separate "value" versus "seed": the stored byte and the number handed to the caller are the same thing, so `RNG_SEED` is a running state that advances one LCG step every time anyone asks for a random number. The gameplay AI is the main consumer — `reseedFormationObjectState` rolls a fresh random Y position for an object when it re-enters the formation, `chooseNextAttackerDirection` takes the low bit of a draw to pick a launch direction when an attacker is not near a formation edge, and `computeControlledObjectMoveCommand` pulls draws to vary movement — so the sequence of dives, entry heights, and swerves the player sees is exactly this arithmetic chain walking forward.

### Keeping the frame interrupt alive

The game runs one interrupt per vertical blank, and its handler saves a stack of registers on entry and acknowledges (disables) the interrupt latch so it will not immediately re-trigger. Closing that handler is `rearmVblankInterruptAndRestoreRegs` [code], the shared epilogue every vblank path converges on. It does two things in order. First, it writes `1` to the interrupt-enable latch `IRQ_ENABLE` at `0x7001`, re-arming the hardware so the *next* vertical blank will assert the interrupt again — this is the counterpart to the acknowledge the prologue performed, and without it only the very first interrupt would ever fire and the entire per-frame loop would freeze. Second, it restores the six register pairs the prologue saved off the stack (index registers, then HL, DE, BC, and finally the accumulator/flags), so the interrupted code resumes with its registers intact — and note the accumulator/flags are restored *last*, deliberately overwriting the `1` that was loaded to poke the latch, so the re-arm leaves no trace in the caller's registers. The final return resumes execution at the point in the main loop that the interrupt broke into.

### A shared return stub

Finally, `loc_090b` [code] is a deliberately-unnamed two-instruction stack epilogue: it restores the caller's saved HL and returns, touching no RAM. It exists purely as the common tail of the command-queue enqueue path — `commitQueueWriteHead` finishes its work and falls into it to undo the HL that path had stashed — so it is best read as shared plumbing for that one routine rather than a primitive of its own.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

Galaxian runs its whole life -- from the moment the board powers up, through the attract demo, past the coin/start hand-off, and into a played round -- on a two-level state machine driven once per video frame. A single game-phase byte, GAME_STATE (0x4005), picks which of five top-level phases is live; within a phase a second byte, SEQUENCE_STATE (0x400a), picks which step of that phase runs this frame. Each byte indexes an in-ROM word table (the game-phase table lists boot, attract, coin-wait, fresh-play, and restored-play; each phase then carries its own step table), so advancing the machine is nothing more than writing a larger number into 0x4005 or 0x400a and letting next frame's lookup land on the new handler. Almost every routine below is one cell in one of those tables, and almost every one ends by nudging one of those two bytes forward.

### Boot: clear the screen, then latch the machine's configuration

Phase 0 is `fillScreenThenLatchConfigAndAdvanceState` [seen]. It is a slow, multi-frame job: each frame it blanks a 32-byte run of tilemap starting at the write cursor VRAM_WRITE_PTR (0x400b), then bumps that cursor 32 forward, so over many frames the fill cursor sweeps the whole tilemap from VRAM_BASE (0x5000) up through 0x53ff, wiping the screen a strip at a time. A per-phase countdown in the low dwell byte 0x4008 governs how long this lasts; while it is still counting the routine just fills-and-returns. When it finally hits zero the machine reconfigures itself for the attract era: it stamps 0x4007=1, clears the mode byte 0x4006, sets GAME_STATE (0x4005) to 1 and zeroes SEQUENCE_STATE (0x400a) so the next frame drops into attract step 0. In the same breath it reads the board's DIP/input shadows and folds the operator settings into work RAM: two bits of IN1_SHADOW become the config byte at 0x4000, one bit of IN2_SHADOW becomes the gate-config flag at 0x401f, one bit of IN0_SHADOW becomes the screen-flip flag at 0x400f, and the low two bits of the live IN2_PORT (0x7000) index a four-entry coinage table at 0x0152 (the bytes 07,10,12,20) whose selected value is parked at 0x40ac as the coinage setting. It then unpacks a packed flag bitmask, seeds the object shadow and the player-1 status glyphs, and posts two deferred callback words to the command queue. That single expiry is the whole "power-on configuration" event; every later phase reads those latched cells rather than re-sampling the switches.

### The dwell-timer cascade that paces every phase

The pacing of the state machine rides on a three-tier byte cascade at 0x4008 / 0x4009 / 0x400a, where the top tier *is* SEQUENCE_STATE. The primitive is `tickCascadeCountdown` [seen]: given a pointer, it decrements that byte, and while the byte is still nonzero it does nothing more; only when the byte reaches zero does it step to the very next byte in the same page and increment *that*. So a carry out of one tier bumps the next tier by one -- and when the byte being counted is the mid-tier dwell timer 0x4009, its expiry increments SEQUENCE_STATE (0x400a), i.e. advances the phase to its next step. Two step-handlers wrap this primitive at different clock rates. `tickSequenceDwellTimer` [code] simply points at 0x4009 and ticks it, so it burns down the dwell one unit per frame and steps the sequence on when the dwell empties. `tickPrescaledSequenceTimer` [seen] instead ticks the fast sub-timer 0x4008 each frame; only when *that* wraps does it reload 0x4008 to 60 and then cascade one tick into the 0x4009 dwell -- a slow, prescaled advance for steps that should linger about sixty times longer. `reloadSequenceDwellTimer` [code] is the companion re-arm: it stamps the mid-tier dwell 0x4009 back up to 80 frames so a freshly-entered step gets a full dwell before it can expire again.

Several helpers combine "advance the step" with "re-arm the dwell" so a handler can hand the machine on in one call. `advanceSubstateAndReloadDwell` [code] bumps the step counter it is handed (its callers pass SEQUENCE_STATE itself) and then calls the reload to give the new step its 80-frame dwell. `setSequenceStateByModeAndReloadDwell` [code] does a mode-dependent jump instead of a plain increment: it forces the step counter to 4 or to 14 depending on bit 0 of the mode byte 0x4006, then re-arms the dwell -- a way for a handler to branch the sequence to one of two downstream steps. `advanceSubstateAfterDwellAndQueue` [code] is the timed-step form used inside played phases: it ticks 0x4009 each frame, and on the zero-cross it reloads that dwell to 20, advances SEQUENCE_STATE, and posts this step's callback word (the pointer 0x0682) to the queue.

### The attract sequence: a scripted, looping timeline

Phase 1 is the attract show, and its step table is a scripted timeline of roughly nineteen entries indexed by SEQUENCE_STATE. Step 0 is `initSequenceEnableStarfield` [seen]: it posts two setup words to the command queue, switches the starfield hardware on via STARS_ENABLE (0x7004), sets the 0x4007 flag, resets the per-sequence cells (CURRENT_PLAYER 0x400d, the paired-player flag 0x400e, the mode byte 0x4006, and the one-frame flag 0x4019), seeds the dwell cascade (0x4008=96, 0x4009=16), and advances SEQUENCE_STATE to step 1. Step 1 is `armStepCountdownAndTickSequenceTimer` [seen]: it arms the one-shot countdown cell 0x4019 to 1 and then runs the prescaled tick, so this step advances only on the slow prescaled clock. From there the timeline walks forward: some steps do one-off setup work and advance the state themselves, while the purely-timed steps just call one of the tick handlers (the plain dwell tick sits at two of the later steps, and the prescaled tick is reached by fall-through from earlier ones) so the machine dwells and then steps on by itself. The timeline is a loop rather than a dead end: its final scripted step is `enterSequenceStep1` [code], which rewinds SEQUENCE_STATE back to 1 and re-arms the dwell cascade with a short 3/3 pair (writing 3 into both 0x4008 and 0x4009), so the attract demo replays indefinitely until a coin and a start press pull the machine out of phase 1.

### The credit / start-button transition into a played round

Once coins have moved the machine into phase 2 (the coin-wait phase), that phase runs `beginGameOnStartButton` [code] as its per-frame tail after its own step handler. This is the credit gate. It reads the start buttons out of IN1_SHADOW (0x4011): bit 0 hands off immediately to `startOnePlayerGame` [code]; bit 1 asks for a two-player start, which proceeds only if the credit counter at 0x4002 holds at least two, in which case it spends two credits, copies the 32-byte ROM row template from 0x051b into the saved-state snapshot SAVED_STATE_SNAPSHOT (0x41a0), and -- when the boot-latched gate-config bit at 0x401f is set -- arms the state-advance gate before entering the round with the two-player spawn word (0x0100). `startOnePlayerGame` is the one-credit path: with no credit left it simply forces GAME_STATE back to 1 (drop to attract); otherwise it spends one credit at 0x4002, zero-fills the snapshot at 0x41a0, and enters the round with spawn word 0. Both paths funnel into the shared round-start entry, which stores that spawn word into CURRENT_PLAYER (0x400d) -- so its high byte lands in the paired-player flag 0x400e, set for a two-player start and clear for one -- lays the row template into the packed-bitmap buffer PACKED_FLAG_BITMAP (0x4180), sets GAME_STATE=3 with SEQUENCE_STATE=0 to begin fresh play, and arms the substate-advance gate on that same 0x401f config bit.

The two gate-arming helpers are the mechanism behind that config bit. `armStateAdvanceGate` [code] writes the marker 3 into gate byte 0x41b5, and `armSubstateAdvanceGate` [seen] writes the same marker 3 into gate byte 0x4195; each gate is later tested as nonzero by one of the two play-phase step-6 handlers to decide whether to take its advance path. Because both are armed off the boot-latched 0x401f bit, a single operator setting reaches through the whole start sequence to steer how the played round's state-6 step behaves.

### Playfield init and the two played phases

A played round lives in phase 3 (fresh play) or phase 4 (restored play); the two share most of their step table and differ mainly in where a board's layout comes from. Step 0 of both is `initPlayfieldState` [code]: it turns both start lamps off (START_LAMP_0/START_LAMP_1 at 0x6000/0x6001), zero-fills the flag block from FLAG_BITS_BASE (0x4100) and three object/work spans (a 23-byte span from OBJ_ACTIVE_FLAG 0x4200 with a one-byte gap before a 24-byte span at 0x4218, and a 70-byte span from 0x4260), sets the frame/status byte 0x425f to 0 and the activity flag 0x4226 to 1, advances SEQUENCE_STATE, arms the dwell 0x4009 to 32, and points the VRAM fill cursor 0x400b back at 0x5000 -- a clean slate for the board about to be drawn.

The two phases diverge at step 2. Phase 3 runs `restoreFormationAndEnterPlaySubstate` [seen], which unpacks the *fresh* PACKED_FLAG_BITMAP (0x4180) into the flag grid, copies the eight trailing template bytes into the buffer at 0x4218, clears the status/flip/direction cells (0x425f, 0x4220, the flip selector 0x4018) and both display-flip latches FLIP_SCREEN_X/Y (0x7006/0x7007), advances the sequence, arms a long 150-frame dwell in 0x4009, publishes a deferred-callback pointer (0x0640) into the 0x4245 cell, and -- when the sound gate 0x4006 bit 0 is open -- posts the board-start jingle. Phase 4 runs `restoreSavedStateAndEnterPlaySubstate` [code] instead, the mirror image: it unpacks the *saved* SAVED_STATE_SNAPSHOT (0x41a0) rather than the fresh bitmap, so a paused player's board is restored on the way back to their turn; it likewise copies the eight template bytes to 0x4218, clears 0x425f/0x4220, mirrors the flip flag 0x400f into the flip selector and both flip latches when it is set, advances the sequence, arms the 150-frame dwell, publishes its own callback pointer (0x0830) into 0x4245, and posts a five-word intro cue when the sound gate is open. In short: phase 3 builds a fresh board from the packed bitmap; phase 4 rebuilds a stored board from the snapshot. Step 3 in both is the timed `advanceSubstateAfterDwellAndQueue` described above, which dwells and then steps the round forward, and step 0-init aside, both tables also reach a common per-frame update step (discussed below).

Step 6 of each played phase is a small decision node. `stepPlaySubstate6` [code] (phase 3) branches on the arm gate 0x421d and the two mode flags 0x41b5 and 0x400e: with the arm gate open it either advances-and-reloads or does the mode-keyed jump; with the arm gate closed it either runs the shared dwell/reset tail, or -- when both mode flags are set -- inlines an advance itself, bumping SEQUENCE_STATE, arming a 130-frame dwell, and (only when 0x4006 bit 0 is set) queuing two channel-6 command words. `stepAltPlaySubstate6` [code] (phase 4) is the same shape keyed on the substate gate 0x4195 in place of 0x41b5, arming an 80-frame dwell on its show arm and 130 on its default arm and queuing its own pair of channel-6 words. Both fall back to the shared tail `advanceDwellOrResetToState1` [code], which is the round's exit valve: when mode-byte 0x4006 bit 0 is clear it just advances the step and reloads the dwell (round continues), but when that bit is set it tears the round down -- forces GAME_STATE back to 1, clears 0x4006 and SEQUENCE_STATE, silences the sound and halts the interrupt/starfield hardware, and posts command word 6 -- returning the machine to attract.

### The command queue that carries every deferred cue

The setup handlers above all speak to a small command/event queue rather than acting immediately. `enqueueCommandWord` [seen] appends a 16-bit word at the current write-head: the head index lives at 0x40a0 and addresses a slot in the top of the 0x40xx page (the head is clamped never to drop below 0xc0, so live slots sit at 0x40c0-0x40ff). It writes only when the target slot is free -- its top bit set -- storing the word's high byte in the slot and low byte in the next, then advancing the head by two and clamping it to the 0xc0 floor before committing it back to 0x40a0. `commitQueueWriteHead` [seen] is the bare form that just writes an already-advanced head index back to 0x40a0 and returns through the shared pop-and-return epilogue at loc_090b [code], a tiny tail that restores the caller's saved pointer and touches no RAM. Two helpers post fixed bursts: `enqueueCommandWordBurst` [code] fires five words in a row -- two on the caller's channel and its successor, then two fixed cues on channel 7 -- and `queueBoardStartSoundBurst` [code] prefixes a channel-5 prologue word before delegating to that burst, and is the paired-player board-start cue selected by phase 3's step-2 handler when the paired-player flag 0x400e is set.

### The per-frame gate and timer bank inside played phases

Step 5 of the played phases is a dense per-frame update pipeline (at 0x0661), and several of the machine's arming gates and countdowns are ticked there every frame while a round is live. `armBehaviorGateOnInputOrTimer` [code] is the arming logic for the behavior gate 0x4208: it does nothing unless the enable bit OBJ_ACTIVE_FLAG (0x4200) bit 0 is set and the gate is not already armed; then, on the timer path (mode 0x4006 bit 0 clear) it arms the gate only when the low five bits of the frame counter 0x425f are all zero -- roughly once every thirty-two frames -- and on the input path (mode bit set) it tests bit 4 of the selected input shadow (IN0_SHADOW or IN1_SHADOW, chosen by 0x4018) masked against its guard byte (0x4013 or 0x4014) and, if that line is active, arms both the gate 0x4208 and its companion flag 0x41cc. `clearGateOnPendingRequest` [code] is the acknowledger on the other side: when request flag 0x420b bit 0 is pending it consumes the request (clears 0x420b) and clears that same behavior gate 0x4208.

The same pipeline hosts a slow difficulty ramp and a delayed-event subsystem. `rampCounterToCeiling` [code] is a gated two-tier prescaler: while the enable bit at 0x4200 is set and the inhibit flag 0x422b clear, it ticks an outer prescaler at 0x4218 (reload 60) and, on each of its wraps, an inner one at 0x4219 (reload 20), and only when both wrap does it step the 0..7 ramp counter 0x421a up by one, clamped at 7 -- a very gradual pace/difficulty climb. `scheduleDelayedEvent` [code] is a guarded two-tier timer that arms a delayed-event triple: it bails unless the enable bits (0x4200 and 0x41ef set, inhibit 0x422b clear) agree, then, keyed on mode byte 0x4006 bit 0, either arms a fixed triple on a full outer/inner cascade elapse (DELAYED_EVENT_TIMER 0x422f=90, 0x424a=45, DELAYED_EVENT_ARMED 0x422e=1) or derives the payload from the byte-sums of two work-RAM word cells and fans it into the triple by rotations. Note that the outer/inner timer bytes it drives, 0x4245 and 0x4246, are the very cells the step-2 setup handlers earlier published a callback pointer into -- the pair is repurposed from a stored pointer into a running countdown once the timed play phase is under way. `fireDelayedEventRequest` [code] is the one-shot that later cashes it in: while DELAYED_EVENT_ARMED (0x422e) is set it counts DELAYED_EVENT_TIMER (0x422f) down each frame, and on the zero tick it disarms itself and -- only if both enable bits (0x4200 and 0x41ef) are set -- raises DELAYED_EVENT_REQUEST (0x4229). Alongside them, `expireActivityGatedTimer` [code] ends an activity-gated timed phase: while the arm flag 0x422b is set and at least one activity gate is open (either whole-byte flag 0x4224 or 0x4221 nonzero, or 0x4226 bit 0 set) it ticks counter 0x422c and clears the arm flag once that counter reaches zero.

### A shared clamp arm

Finally, `markValueOutOfRange` [code] is a small shared arithmetic helper rather than a piece of the sequence machine proper: it is the out-of-range arm of a value clamp used elsewhere, snapping register B to the fixed saturation sentinel 128 when a clamp's input falls beyond its permitted range, so downstream folding code reads the sentinel rather than a wild index.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

Galaxian's aliens live as two overlapping representations that this subsystem keeps in step: a **formation** — the grid of aliens sitting in ranks and swaying side to side — and a pool of **flight objects**, the 32-byte records that describe an individual alien whether it is standing in the grid or diving at the player. The formation is stored as occupancy bits; a flight object is stored as a record; and the machinery below is mostly about moving aliens between those two forms (grid cell becomes diving object; diving object that survives settles back into a grid cell) and about painting whichever one is current onto the sprite hardware.

### The formation flag block and its packed form

The heart of the formation is a 128-byte block based at `FLAG_BITS_BASE` (0x4100): one byte per formation cell, byte value's bit 0 meaning "a live alien occupies this cell." The block is transported to and from ROM/save storage in a compact 16-byte bitmap. `unpackBitmaskToFlagBytes` [seen] reads a 16-byte packed mask and explodes it LSB-first into those 128 flag bytes (1 for a set bit, 0 for a clear one), handing back the source pointer advanced 16 bytes so the caller can pick up whatever data follows the mask. `packFlagBytesToBitmask` [code] is its exact inverse: it reads bit 0 of the 128 flag bytes and packs them back into a 16-byte bitmap, returning the destination advanced +16 so a companion block can be copied straight after it. The block can also be wiped wholesale: `clearFlagBlockAndReseedObjectShadow` [code] zero-fills all 128 bytes, clears two status cells (loc_425f and loc_4238), arms the mid-tier dwell timer at loc_4009 to 64, then advances the top-level sequence step and reseeds the object-RAM shadow. This is the "start a fresh screen with an empty formation, then lay the aliens back in" reset.

A related sequence-state handler, `loadDescriptorAndAdvanceSequence` [code], does the opposite of clearing — it *installs* a formation. It unpacks a packed descriptor bitmask living in ROM at loc_051b into the flag block, copies the 8-byte template that follows the mask into the template buffer at loc_4218, clears loc_425f, sets loc_421d to 1, steps `SEQUENCE_STATE` (0x400a), stamps `VRAM_WRITE_PTR` (0x400b) with 150, and publishes a deferred-callback pointer (loc_0640) into loc_4245. So the descriptor carries both the alien layout (the mask) and an 8-byte payload that rides alongside it (the template).

Two mirror-image "terminal" handlers close out a player's turn and hand off to the other player, each keyed off the dwell timer at loc_4009 counting down to zero. `packFlagsToBitmapAndSwitchPlayerState` [code] waits for expiry, then clears `SEQUENCE_STATE`, loc_4222 and loc_422b, packs the live flag bytes into `PACKED_FLAG_BITMAP` (0x4180), copies the 8-byte template (loc_4218) in right behind the packed bitmap, sets `CURRENT_PLAYER` (0x400d) to 1 and `GAME_STATE` (0x4005) to 4. `saveFlagsToSnapshotAndSwitchPlayerState` [code] is the same shape with the other destination and the other player: on expiry it clears `SEQUENCE_STATE`, sets `CURRENT_PLAYER` to 0 and `GAME_STATE` to 3, snapshots the packed flags into `SAVED_STATE_SNAPSHOT` (0x41a0) and copies the 8-byte companion block after them. Between them these two freeze the surviving formation into a compact per-player snapshot so the other player's turn can be restored later — the packed bitmap is the durable form of the formation, the flag block its working form.

### Reducing occupancy: row/column summaries and the sway bounds

A window of the flag block is treated as a coordinate grid. `OCCUPANCY_GRID` (0x4123) sits 0x23 bytes into the flag block, i.e. behind two guard rows and three guard columns, and spans 6 rows of 10 columns at a 16-byte row stride. `summarizeFormationOccupancy` [seen] reduces this grid every relevant tick. It ORs each row's ten cells into a per-row summary at `ROW_OCCUPANCY` (0x41e8, behind two zeroed guard cells) and ORs each column's six cells into a per-column summary at `COLUMN_OCCUPANCY` (0x41f0, behind three zeroed guards). From the column summaries it derives the pair of horizontal sway bounds: scanning inward from the rightmost column it starts a "from-right" bound at 34 and steps it +16 per empty column until it meets an occupied one, and scanning inward from the leftmost it starts a "from-left" bound at 224 and steps it -16 per empty column; the two are packed into `FORMATION_X_BOUNDS` (0x4210) with the from-right value in the low byte and from-left in the high byte. The practical effect is that as the edge columns of the formation are shot away, the bounds march inward and the surviving block sways within a tighter span. Finally it folds four region-"clear" flags by XORing the summarized any-occupied bit with 1: loc_4221 covers the top four rows, loc_4220 the whole grid, and loc_4226 / loc_4225 two eight/seven-wide object-table fields (scanned at 32-byte stride from `OBJ_TABLE` and loc_42b1). These "clear" flags are the gates the launch, stage-advance, and sway logic consult to decide whether the formation is empty enough to act.

### The side-to-side sway

`advanceFormationSweepOscillator` [seen] is the per-frame formation sway, and it only actually steps once every four frames (throttled on the low two bits of the frame counter loc_425f). It reads the swept 16-bit word at loc_420e — the formation's horizontal anchor — and the two bytes of `FORMATION_X_BOUNDS`. When the sweep-direction flag `OBJ_SWEEP_DIRECTION` (0x420d) is 0 (ascending) it steps the word up until its low byte reaches the from-right bound, at which point it calls `setSweepDescending` [seen] to store 1 into the flag; descending, it steps the word down until the low byte drops below the from-left bound, where `setSweepAscending` [seen] stores 0. Those two are trivial one-line flag writes, but they are the turnaround points that give the formation its pendulum motion. After each step the oscillator broadcasts the *negated* low byte of the anchor across a small strided per-column offset table. A leading proximity gate short-circuits the whole thing: if the player's shot is armed (loc_4208 bit 0), its Y is within a narrow window, and the formation column the shot lines up on is occupied, the routine skips stepping and jumps straight to re-broadcasting the current offset — so the formation visually holds position under an aligned incoming shot.

The broadcast targets are a family of tiny strided writers. `broadcastToStridedTable` [seen] writes one byte into nine cells at stride 2 based at loc_4028 (0x4028, 0x402a, … 0x4038) — this is the per-column X-offset field the formation's columns are drawn against. `clearStridedTable` [seen] is just that writer called with 0, the per-state reset of the offset field. `broadcastNegatedSweepToStridedTable` [seen] broadcasts the two's-complement of a low byte across the same nine cells, and `broadcastNegatedFormationSweepToStridedTable` [code] is the convenience form that first fetches the anchor's low byte from loc_420e and then does that negated broadcast — the exact call the sway makes each step.

That nine-cell offset field is interleaved with a second strided field carrying each object's base value. `seedObjectRamShadowField` [seen] copies a 32-byte ROM template into every *other* cell of the object-RAM shadow starting at loc_4021 (0x4021, 0x4023, … 0x405f), and `seedObjectShadowFromRom` [seen] is the fixed-source wrapper that points that copier at ROM template `STRIDED_TABLE_SRC` (0x1d71) and runs it. Because the seeded field occupies the odd cells and the sway offsets the even cells (0x4028…), the two interleave into a single shadow where each object slot carries a static base beside its live sway offset. `advanceSequenceStateAndReseedObjectShadow` [code] pairs a re-seed with a sequence step: it advances a pointer's low byte within its page, increments the byte the pointer now names (both callers arrive pointing at loc_4009, so the increment lands on `SEQUENCE_STATE`), then reseeds that shadow field from ROM — the "step the state machine and lay the object bases back down" primitive that `clearFlagBlockAndReseedObjectShadow` builds on.

### Object records and the rotated position mapping

Every flight object is a 32-byte record; the fields this subsystem touches are the active flag (byte 0), the sub-state (byte 2), the X and Y position fields (bytes 3 and 4), the signed heading (byte 5), a direction bit (byte 6), and the packed grid cell (byte 7). `positionObjectFromGridCell` [code] is the shared translator from grid coordinates to screen position, and it encodes Galaxian's counterintuitive rotated geometry: the display axes are turned 90° from the formation grid, so the cell's **row** bits (byte 7 & 0x70) drive the **X** field as 124 minus three-quarters of the row value, while the **column** bits (byte 7 & 0x0f) drive the **Y** field as the swept anchor (loc_420e) plus the column times sixteen plus a seven-pixel hotspot. Row moves you across the screen, column moves you down it.

### Object-AI state handlers

A freshly launched object walks through a handful of state handlers selected by its sub-state byte. `initSpawnedObjectFromGridCell` [code] is the first-tick handler: it clears the object's step timer, raises the spawn flag loc_41c2, positions the sprite from the grid cell, and queues a spawn command (type 1 carrying the cell). It then indexes `SPAWN_RECORD_TABLE` (0x1dd1) by the cell's row bits to read a 2-byte {sprite number, flight-curve seed} record into the object; when the row is the top row it also sets a display-attribute base of 24 and tallies how many of its two look-ahead neighbour slots (32 and 64 bytes on) are still active into `ACTIVE_NEIGHBOR_COUNT` (0x422a). It finishes by seeding the motion counters (throttle 3, leg count 12), advancing the sub-state, and choosing the signed heading (+12 or −12) from the direction bit.

`settleObjectIntoFormationCell` [code] is the mirror at the end of a dive that returns to the ranks: it repositions from the grid cell (which rewrites the position/frame field), bumps a frame counter, and compares. When the counter catches up to the positioned value it deactivates the object (byte 0 = 0), marks its formation cell live (`FLAG_BITS_BASE` + cell = 1) and queues a command word carrying the cell — the alien has rejoined the formation. While the gap is still open, a small even gap nudges the object's phase by the direction bit (up or down); a large gap (≥25) or an odd one is left alone.

`reseedFormationObjectState` [code] handles an object being recycled: it resets X to the left edge (8) and heading to 0 and ticks a leg counter. Ordinarily — and only while play is enabled (`OBJ_ACTIVE_FLAG` 0x4200 bit 0) and an activity gate is open (loc_4224 or loc_4221 nonzero) — it rolls a fresh random Y from `advanceRandomSeed`, half-folds it into the Y field with a +32 bias, arms a 40-tick hold timer, and advances the sub-state an extra step. The special case is a grid cell whose high bits are all set (byte 7 & 0x70 == 0x70): while `ACTIVE_NEIGHBOR_COUNT` is nonzero it recounts its two neighbour slots and reseeds; once no neighbours remain it deactivates the object and ramps a phase/difficulty counter (loc_421e) up toward a ceiling of 2. `bumpCountIfNeighborsInactive` [code] is the standalone form of that neighbour test used elsewhere in the same bookkeeping: it returns a running count incremented by one only when *both* of an object's two look-ahead slots (32 and 64 bytes on) are inactive, and unchanged otherwise. `noopAnimDispatchSlot` [code] rounds out the family — it is the deliberate do-nothing terminal entry in the object-animation handler table, present so the sub-state 3 slot has a valid target and simply returns.

### Pacing launches and diving out of the formation

Two routines cooperate to peel a diving attacker off the standing formation, one arming and one firing, running one after the other inside the per-frame gameplay tick. `paceEnemyLaunchTrigger` [code] is a gated prescaler: it runs only while play is on and both inhibit flags (loc_4220, loc_422b) are clear. It computes a span of attacker sub-counters to service from the pace counter (loc_421a) and the clamped stage (loc_421b), then ticks a master counter at loc_424a; until the master expires it simply clears the refill flag and stops. On expiry it reloads the master from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), decrements that span of sub-counters, refills each one that hit zero from its matching reload-table entry, and — if any refilled — raises `SUBCOUNTER_REFILL_FLAG` (0x4228). So the launch cadence speeds up with the pace counter and the stage.

`launchAttackerFromFormation` [code] consumes that flag. It runs only when `SUBCOUNTER_REFILL_FLAG` is raised (clearing it), and holds off entirely while the region-clear gate loc_4220 is set. It derives a 1..4 slot budget by folding the sum of the pace counter and stage selector and capping at 3+1, then claims the first object slot whose two guard bytes are both zero, scanning downward in 32-byte steps from the table top at loc_4391. It stamps the launch direction (loc_4215) into the slot, uses that direction to pick which end of `COLUMN_OCCUPANCY` to scan for an occupied column, then walks that column of the flag grid looking for a filled cell. On a hit it clears the formation cell, activates the object (byte 0 live, phase byte 2 = 0, source index = the cell's low byte) and queues a type-1 spawn command. One live alien has left the grid and become a diver. Because the pacing routine runs *after* the launch routine within a frame, the refill flag raised on one frame is the trigger the launch consumes on the next.

### Player shot versus the formation

`flagPlayerShotHitOnFormation` [code] is the collision check that runs in the same per-frame tick. While the shot gate loc_4208 bit 0 is armed, it rejects shots outside the formation's vertical span (shot Y at loc_4209 must be below 104 and at least 30), then bands the Y into a formation row by repeatedly subtracting the 7-then-5 row spacing, and bands the shot's X-delta against the anchor (loc_420a − loc_420e) into a column, rejecting anything outside the hit window. It reconstitutes the packed grid index by nibble-swapping the column and row together and reads `FLAG_BITS_BASE` + index; unless that cell holds a live alien it bails, otherwise it clears the cell. It queues a type-1 command word carrying the grid index, stamps a hit record (loc_420b = 1, loc_42b1 = 1, loc_42b2 = 0, and the shot's position word into loc_42b3), and queues a second, type-3 command word carrying a column code derived from the index. The two queued words are what downstream scoring, explosion, and sound stages pick up; this routine's whole job is to register that a standing alien was destroyed and hand the event on.

### Spawning objects from trigger flags

New objects are requested by raising bytes in two trigger-flag blocks — the primary block at `PRIMARY_TRIGGER_BLOCK` (0x4176, four flags) and the secondary block at `SECONDARY_TRIGGER_BLOCK` (0x4165), whose entries sit exactly 0x11 below the primary ones so the same index reaches both. The bottom of the spawn machinery is `activateObjectSlotAndEnqueueSpawn` [code]: given a trigger pointer and a target slot, it consumes the trigger flag (writes 0), marks the slot active with a cleared phase, records the spawn code in byte 6 and the trigger pointer's low byte as the source index in byte 7, and queues a type-1 spawn command keyed by that index — returning the trigger pointer unchanged so callers can read its low byte back. `spawnSecondaryObjectIntoSlot` [code] is the analogous seeder for a secondary slot: it does nothing if either of the slot's two live flags (bytes 0 and 1) is already set, otherwise it consumes the trigger, marks byte 0 live, clears the state byte, inherits field 6 from a source record, stashes the trigger index, and queues its activation command.

Those two are wrapped by several walkers. `spawnIntoFreeDescriptorSlot` [code] scans the four descriptor slots at `DESCRIPTOR_SLOT_TABLE` (0x4330) from the last downward at 32-byte stride for one whose two guard bytes are both zero, and on a hit seeds it via `activateObjectSlotAndEnqueueSpawn`. `spawnSecondaryObjectAndAdvanceWalk` [code] is one step of a secondary spawn walk — it spawns into the current slot, advances the slot pointer 32 bytes, and counts a budget down, forcing the enclosing loop to end after this pass when the budget is spent. `spawnPrimaryAndSecondaryObjects` [code] spawns a primary into `OBJ_TABLE` (0x42d0), then walks three trigger flags backed up 15 bytes from the primary trigger's low byte and, for each set flag, seeds a secondary into successive slots from the table's second record (0x42f0) until a budget of two is spent.

`spawnObjectsFromTriggerFlags` [code] is the entry the per-frame tick actually invokes. It scans the four primary flags first; the first set one spawns a primary into `OBJ_TABLE` and then walks the secondary block at the same offset, spawning up to two secondaries. If no primary flag is set, it scans the secondary block and, on the first set flag there, instead seeds a free descriptor slot. Separately, `activateDescriptorSlot` [seen] initialises one 32-byte descriptor slot chosen by the number held at its pointer (index = number − 1): it stamps byte 0 active, byte 2 = 13, byte 5 = 12, the slot index into byte 7, zeroes bytes 1 and 4, and leaves bytes 3 and 6 alone. The shared exit of the command-word enqueue path is the deliberately unnamed pure-stack epilogue loc_090b [code], which just restores the caller's saved register pair and returns with no work-RAM effect.

### Advancing the stage and rebuilding the formation

When a formation is cleared enough, the game arms a delayed stage advance. `armFormationAdvanceTrigger` [code] is the one-shot arm: only when both status gates loc_4220 and loc_4225 have bit 0 set and the pending word loc_4222 is not already armed does it write a 16-bit 1 into loc_4222 — enable byte 1, countdown byte (loc_4223) 0. `advanceStageAndReseedFormation` [code] consumes it: it bails unless the enable is set and its countdown, decremented each tick, lands on zero. On that tick it disarms the enable, rebuilds the entire 128-flag block from the packed template at loc_051b (via `unpackBitmaskToFlagBytes`), resets the pace counter loc_421a and loc_425f, reseeds the formation anchor loc_420e to 1, and steps the stage selector loc_421b (its high byte counting up, its low byte advancing but saturating at 7). It then queues a command word and services a pending two-slot request held in loc_421e by raising the trigger flags at loc_4177 and loc_4178 — which, being the second and third bytes of `PRIMARY_TRIGGER_BLOCK`, are exactly the flags `spawnObjectsFromTriggerFlags` picks up on a later tick. That is the closed loop: clearing the formation arms the advance, the advance rebuilds the grid and raises spawn triggers, and the spawn scan turns those triggers into the next wave of objects.

### Staging the formation onto sprite hardware

Finally, `stageObjectsToSpriteShadow` [seen] is the per-frame painter that puts eight formation objects onto the sprite shadow. It reads eight consecutive 32-byte object records from `SPRITE_SOURCE_OBJ_BASE` (0x42b0) and writes eight consecutive 4-byte sprite-shadow records at `SPRITE_SHADOW_BASE` (0x4060), rendering them as a band of three followed by a band of five. The Y offset applied to each object depends on an orientation bit (loc_4018 bit 0): the first band uses 9 or 7 by that bit, and the tail band settles at 8 either way, so the two bands abut cleanly whichever way the screen is oriented.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

Everything in this subsystem is switched on and off by a single enable, the object-active pair at `OBJ_ACTIVE_FLAG` (0x4200) and its companion `loc_4201` (0x4201): while bit0 of 0x4200 is set the ship, the shot, the eight attacker slots and the collision tests all run; when it is clear they freeze. During a play frame these pieces are driven in a fixed order — first the ship mover, then the shot service, then the per-slot object driver, then the two collision sweeps, and finally the attacker-director and player-hit-consumer routines. The ship's own horizontal position lives at the reference cell `loc_4202` (0x4202); that one byte is the anchor almost every routine below reads, because in this game the enemies aim, home, and cross relative to where the ship currently sits.

### The player ship

`moveControlledObjectAndStageSprite` [code] (0x0837) both steers the ship and stages its sprite. When the subsystem is active it first decides where the movement bits come from: in attract/autopilot mode (`loc_4006` (0x4006) bit0 clear) it takes them from the director's decision at `OBJ_MOVE_CMD` (0x423f); in live play it reads an input shadow, choosing `IN1_SHADOW` (0x4011) or `IN0_SHADOW` (0x4010) by `loc_4018` (0x4018) bit0 (the cocktail second-player select). Bit3 of the resulting command steps the ship position down while it is above the floor of 23, bit2 steps it up while it is below the ceiling of 233, so the ship is clamped to [23,233]. The chosen position is written back to `loc_4202`, then complemented-and-offset (one's-complement plus 128) into a staged value that, with code 6, is written four times as interleaved (value, code) pairs into `OBJ_STAGE_BLOCK` (0x4054) — the hardware missile/ship staging record. Two off-normal cases share the tail: if the ship is in its hit/frozen state (`loc_4201` bit0 set) the current position is staged unclamped under code 7 instead; if the subsystem is entirely inactive the position is parked at 0 (staged value 128) under code 6.

### The player shot

The single missile is a countdown, not a coordinate object. `advancePlayerShot` [code] (0x08bc) reads a gate at `loc_4208` (0x4208): while bit0 is armed the shot is in flight, so the counter `loc_4209` (0x4209) is drained by four each frame, and when that remaining value lands in the near-end window [14,17] the retire flag `loc_420b` (0x420b) is raised (the shot has reached the top of the screen). While the gate is clear the shot is idle: the counter is re-parked at 220 (the bottom), and its cross-axis field `loc_420a` (0x420a) is reloaded from the ship X `loc_4202` whenever the subsystem is active — so a freshly fired shot inherits the column the ship was sitting in. `advancePlayerShotAndStageSprite` [code] (0x0898) runs that service and then converts the {counter, field} pair into the shot's two on-screen render cells: `loc_409f` (0x409f) gets the X, computed as counter−1 when `loc_4018` bit0 is set and as complement(counter)+252 otherwise, and `loc_409d` (0x409d) gets the complemented field.

### The attacker object records and their state machine

There are eight attacker records of 0x20-byte stride based at `SPRITE_SOURCE_OBJ_BASE` (0x42b0), and each frame the driver walks all eight, carrying the current record's base while it advances. For each record it first checks the secondary/dying flag (record+1 bit0): if that is set the record is running its death animation and is dispatched through a small four-entry table on its sub-state (record+2). Otherwise, if the primary active flag (record+0 bit0) is clear the slot does nothing; if it is active, the record's state byte at record+2 indexes a sixteen-entry jump table that selects one of the path/dive/home/settle handlers below. Two coordinate fields recur: record+4 is the horizontal position (the field every horizontal target-picker compares against the ship X), and record+3 is the object's other axis — its descent counter or phase counter depending on the state.

The heart of the flight AI is a table-walk. `advanceObjectPathStep` [code] (0x0d71) reads a per-record cursor (record+0x13) into the shared step table `PATH_STEP_TABLE` (0x1e00), adds that entry's first delta to record+3 and its second, direction-controlled delta to the horizontal record+4 (the direction bit record+6 bit0 selects add versus subtract). If the horizontal position (plus a 7-pixel margin) crosses the near edge (below 14) it forces the state to 5, the fall-away handler; otherwise it steps the cursor past the pair, ticks a move throttle at record+0x10 (reloaded to 4), and on throttle expiry nudges the cross-step at record+5 and ticks a leg counter at record+0x11, advancing the state when the leg finishes. `advanceObjectPathStepAlias` [code] (0x108e) is a bare trampoline occupying one dispatch slot that forwards straight into `advanceObjectPathStep` for the currently selected record and holds no state of its own. The subtract-everything mirror is `advanceObjectPathStepDescending` [code] (0x101f): it subtracts the current step table's X delta from record+3 and, unless the direction bit hands the Y half off to the ascending arm, subtracts the Y delta from record+4, then runs the same throttle/leg bookkeeping and, on a finished leg, advances the state and reloads throttle=3, leg=12, heading=12 and cursor=0. `advanceObjectPathStepAscending` [code] (0x1060) is that ascending arm: it adds the step-table byte at the walk pointer to record+4, advances the cursor, ticks the throttle and — on expiry — steps the heading at record+5 and ticks the leg counter, and on a finished leg advances the state and reloads throttle=3, leg=12, heading=244, cursor=0. The mirrored heading reloads (12 versus 244, i.e. +12 versus −12) are what bend the two arms in opposite directions.

The dive is a separate curve. `advanceObjectDiveStep` [code] (0x0e6b) steps the descent position record+3 by one or two (alternating on the frame-parity bit `loc_425f` (0x425f)) and window-checks it: while it sits inside [6,9) the state index is simply bumped, otherwise the swoop is advanced. The swoop shape comes from `advanceObjectFlightCurve` [code] (0x116b), a cross-coupled fixed-point rotation over two 16-bit accumulators held in the record (high/low bytes at record+0x19/+0x1b and record+0x1a/+0x1c). It runs ((record+0x18 seed)&3)+1 integration steps; each step adds twice the *other* accumulator's sign-extended high byte into this one, and a resulting high byte of exactly 128 is treated as an overflow and reverted to its pre-step value. The two accumulator high bytes become the swoop offset: back in the dive step, the first accumulator's high byte (record+0x19) plus the per-object increment (record+9) folds into a fresh Y at record+4, and a carry that crosses the signed boundary — the swoop running off the bottom — bumps the state instead of storing the Y.

Homing is the endgame of an attack run. `homeObjectXTowardPlayer` [code] (0x0f3c) bumps a frame counter (record+3), then steers the record's 16-bit horizontal position:subpixel pair (high byte record+4, low byte record+9) toward the ship X `loc_4202` by roughly four times the signed distance each frame, carrying a small rounding bias (nothing on target, +2 or +3 depending on which side it overshoots from). When the dwell timer at record+0x10 counts down to zero it advances to the next state.

Several handlers arm and re-arm runs rather than move the object. `advanceActorPhaseAndCommitMove` [code] (0x0dd1) ticks the phase counter record+3 and then chooses the record's next horizontal move: if the kind field (record+7) masked by 0x70 equals 0x60 it uses the stored/player target selector, otherwise the plain cross-player selector. `armDirectedMoveWhenInWindow` [code] (0x0f66) ticks an arm counter at record+3 and, while either that counter or the horizontal position record+4 sits outside the window [96,160), keeps the object cruising across the player; once both are in-window it advances the state by two, seeds the move timers (record+0x10=3, record+0x11=12), clears record+5 and record+0x13, and sets the direction bit record+6 from whether the ship X is below the object. `restartObjectMoveRun` [code] (0x1091) simply bumps its sub-counter record+3, forces the state back to 8 (re-entering that arm-window state), and kicks off a fresh cross-player move. `initObjectPhaseSteps` [seen] (0x109b) is a phase entry: it derives a step count n = (~seed)&3 from record+7, writes n+1 to the step count at record+0x16 and a derived code byte ((n+1)<<4)+140 to record+3, arms a phase timer (record+0x10=24), advances the sub-state, and clears the ready flag at record+0x0f — re-arming that flag to 24 only when n is zero. Finally `settleObjectXAtRest` [seen] (0x10d8) is how a returning attacker parks: it steps record+4 up one count per frame until the 8-bit-wrapped distance from the rest value 200 falls within a band of 5, and then simply holds.

### Choosing where an attacker moves horizontally

The commit routines all end at the same primitive. `commitMoveToTargetX` [seen] (0x0df6) stashes a chosen target X into record+0x19, stores the signed move delta (current record+4 minus target) into record+9, zeroes the three-byte move accumulator at record+0x1a..0x1c so the new move accumulates from scratch, and bumps the planner sub-state at record+2. `commitMoveAcrossPlayerX` [code] (0x0ddd) picks that target so the attacker crosses to the opposite side of the ship: it signed-halves the gap between the attacker's record+4 and the ship X `loc_4202`, biases it by 16, and clamps it into the right-hand band [144,208] when the attacker is left of the ship or the left-hand band [48,112] when it is at or right of the ship, then commits it. `commitMoveToStoredOrPlayerTargetX` [code] (0x0e20) is the alternate branch used by the mode record: if bit0 of the first object-table record `OBJ_TABLE` (0x42d0) is set it commits toward that record's stored target X (`OBJ_TABLE`+0x19), otherwise it falls back to the cross-player pick. `beginObjectCrossPlayerMove` [code] (0x0f7b) is the shared tail that several states use to launch a fresh run: it runs the cross-player pick and then seeds the flight-curve step seed (record+0x18=3, giving four curve steps) and the move throttle (record+0x10=100).

### The dying object animation

When a record's secondary flag (record+1 bit0) is set it is diverted into a four-slot death sequence keyed on record+2. `tickDeactivatedObjectAnim` [code] (0x1112) is sub-state 1: it counts a fast timer (record+0x10) down, reloading it to 4 and bumping a companion byte (record+0x12) on each elapse, then counts a slow timer (record+0x11); when the slow timer elapses it either retires the object (clearing its state byte record+1) or — if the position field record+7 is at least 112 — reloads the fast timer to 50, re-seeds the companion from the global `loc_422d` (0x422d) plus 32, and advances the sub-state. `endObjectAnimOnTimerExpiry` [code] (0x113d) is sub-state 2: it simply counts the timer at record+0x10 down and, on the frame it hits zero, clears the state byte record+1 to retire the actor.

### Rendering an object as a hardware sprite

`renderObjectSprite` [seen] (0x0c20) turns one object record into a four-byte hardware sprite record (Y, attr, sprite#, X). If the primary active flag (record+0 bit0) is set it copies the sprite number from record+0x16, sets the sprite X to objX−8 and the sprite Y to complement(objY) minus a caller-supplied offset, and folds the signed heading at record+5 into a display attribute: the heading is normalised into whole 24-count sectors, mapped to a facing attribute (with a one-pixel diagonal nudge on the near-forward and near-back cases), and added to the base attribute at record+0x0f. If instead the secondary flag (record+1 bit0) is set — the object is in its death animation — it draws the fixed explosion sprite number 7 at the same copied position using the fixed attribute at record+0x12. With both flags clear the sprite is parked off-screen at (248,248).

### Collisions

Two sweeps run every frame. `flagPlayerShotHitsOnObjects` [code] (0x1227) fires only while the shot gate `loc_4208` bit0 is armed, box-testing the shot against each of the seven attacker records from `OBJ_TABLE` (0x42d0) at 0x20 stride via `flagPlayerShotHitOnObject` [code] (0x123f). That per-object test skips inactive records, then checks whether the record's position (record+3, record+4) falls inside a 6-wide by 12-tall window around the shot reference at `loc_4209`/`loc_420a`; on an overlap it raises the shot-retire flag `loc_420b` and tail-calls the score-and-deactivate handler. Symmetrically, `flagObjectHitsOnPlayer` [code] (0x129e) runs only while the subsystem enable `OBJ_ACTIVE_FLAG` bit0 is set, testing the same seven records against the ship via `flagObjectHitOnPlayer` [code] (0x12b6). That test classifies the object's record+3 (biased by 33) into a near window (below 5) or a far window (below 17), and if the ship X `loc_4202` minus record+4 sits within that window's band (a tighter band up close, a looser one further away) it raises `HIT_EVENT_FLAG` (0x4204) and tail-calls the same score-and-deactivate handler.

That hit event is consumed later in the same frame by `handlePlayerHitEvent` [code] (0x12ed). If bit0 of `HIT_EVENT_FLAG` is clear it does nothing; otherwise it clears the flag, disables the subsystem by zeroing `OBJ_ACTIVE_FLAG` and setting `loc_4201`=1 (freezing the attackers and flipping the ship into its staged-under-code-7 hit state), arms the two explosion pulse counters `loc_4205` (0x4205)=10 and `loc_4206` (0x4206)=4, queues the hit-sound command word (2,5), decrements the activity/pace counter `loc_421a` (0x421a) floored at zero, steps the wrapping [0,5] cycle counter `loc_421d` (0x421d), and — only in live play (`loc_4006` bit0 set) — pulses the discrete-sound latch `SOUND_W_REG3` (0x6803).

### Dive scheduling and the attacker director

Three routines decide who dives and, in attract mode, where the ship itself slides. `selectAttackerRowScan` [code] (0x15f4) seeds a starting slot and base from the alternate flag `loc_421b` (0x421b) — slot 2/base 157 when it is nonzero, slot 1/base 132 otherwise — then scans up to four two-byte slots of `ROW_OCCUPANCY` (0x41e8), advancing past a slot only while neither of its bytes has bit0 set, and stores the resulting (slot, base) pair into `loc_4213` (0x4213) for the row-scan handlers to consume. `chooseNextAttackerDirection` [code] (0x13e1) sets the shared launch/curve direction flag `loc_4215` (0x4215): the sign of the 16-bit formation anchor `loc_420e` (0x420e) picks which edge of `FORMATION_X_BOUNDS` (0x4210) to measure the gap against, and within 28 pixels of that edge the flag is forced away from it (0 near the high bound, 1 near the low bound); otherwise it is a fresh random bit.

The attract-mode autopilot is `computeControlledObjectMoveCommand` [code] (0x198e). Once every 32 frames — gated on the phase counter `loc_425f`, and only while both master enables `loc_4007` (0x4007) bit0 and `OBJ_ACTIVE_FLAG` bit0 are set — it folds every record of both object tables (the seven at `OBJ_TABLE` and the seven tighter records at `loc_4260` (0x4260)) into a running weight via `accumulateObjectPositionWeight` [code] (0x1a12), adds a scaled offset between the formation anchor `loc_420e` and the ship X `loc_4202`, applies a random ±1 nudge, and buckets the biased result into `OBJ_MOVE_CMD` (0x423f) as 0, 4, or 8 — the same up/down move bits the ship mover reads. Each per-object contribution in `accumulateObjectPositionWeight` skips objects that are inactive, whose Y is not in one of two 52-row bands above 128, or whose X delta from `loc_4202` is not in the near half; for the rest it folds the object's flag bit7, the X-delta bits, and the row band into a 0–15 index and adds the signed step from `OBJ_STEP_TABLE` (0x1a45) to the accumulator, so nearer and more-threatening attackers pull the ship harder.

### Bringing the subsystem up

Two sequence handlers set the board before play. `resetObjectRamAndAdvanceSequence` [code] (0x0408) is the wave-reset: it seeds the interleaved OBJRAM shadow field from the ROM template at `loc_1d91` (0x1d91), zeroes the 64-byte sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad object-record region from `loc_4260` (a full 256-byte page plus an 80-byte tail), clears `loc_4238` (0x4238) and `MESSAGE_SCROLL_ENABLE` (0x40b0), points the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) two cells into `VRAM_BASE` (0x5000), arms the dwell tier `loc_4009` (0x4009)=16, and advances `SEQUENCE_STATE` (0x400a). `activateObjectsAndBeginPlayPhase` [code] (0x0614) is the timed transition into play: it ticks the dwell timer `loc_4009` and returns while it still runs; on expiry it reloads that timer to 10, advances `SEQUENCE_STATE`, switches the whole subsystem on by writing 1 into the `OBJ_ACTIVE_FLAG`/`loc_4201` word (enabling attackers and clearing the hit state), centres the ship by setting `loc_4202`=128, refills the 16-byte enemy-launch sub-counter block at `loc_424a` (0x424a) from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears the scratch cells `loc_4058` (0x4058) and `loc_405a` (0x405a), and queues two display/sound command words (7,3) and (2,0).

The command-word queue those last routines and the hit-consumer feed shares one unremarkable return tail, the deliberately unnamed `loc_090b` (0x090b): it restores the caller's saved register and returns, touching no work RAM — it exists only as the common exit of the enqueue path.

## Sound

The sound machine is built around a small block of shadow cells in work RAM that a per-frame driver composes and then latches out to the discrete-sound hardware. Two cells carry the running output. `SOUND_PITCH` (0x41c1) is the pitch shadow copied to the pitch port (0x7800) at the end of every frame, and `loc_41c0` is a composite level/flag cell copied to sound-write register 6 (0x6806) and, rotated one bit, to register 7 (0x6807). Each frame the driver first blanks this pair — the pitch shadow up to 0xff and the composite down to 0 — then runs its chain of voice updaters, each of which may overwrite the pitch shadow or raise the composite, and finally latches whatever the chain left behind. Everything below either stages into that pair or writes one of the other discrete-sound latches directly. A frame-parity flag, `loc_4007`, whose bit 0 alternates every frame, gates several of the voices and supplies the raw square-wave toggle.

**Staging a pitch.** The leaf that every pitch producer funnels through is `stageSoundPitch` [seen], which parks a byte in `SOUND_PITCH` (0x41c1). Its sibling `stagePitchAndRaiseSoundFlag` [code] does the same but stores the value less one (modulo 256) and additionally raises the composite cell `loc_41c0` to 1, marking the pair filled for this frame.

**The pitch sweep and its selector.** A per-frame head at 0x17d0 decrements a sweep counter at 0x41c2 and, while it stays nonzero, enters `advanceSoundSweepAndStagePitch` [code] with the pointer aimed at that counter; when the counter expires the head reloads the 16-bit cell 0x41c3/0x41c4 to 0xa002. `advanceSoundSweepAndStagePitch` early-returns while gate `loc_4226` bit 0 is set; otherwise it steps the pointer forward one cell to the sweep byte at 0x41c3. If gate `loc_425f` bit 0 is set it hands that cell straight to the pitch-selector dispatcher; otherwise it bumps the sweep byte upward while the sound counter `loc_41c4` (0x41c4) stays below 96, then falls into `tickSoundCounterAndStagePitch` [seen], which decrements the sound counter (when it is still running) and hands off to `stageSoundPitchBySelector` [code]. That dispatcher reads the low two bits of the pointed cell: a nonzero selector routes to `stagePitchFromSoundCounter` [code], which reads the sound counter `loc_41c4` and — on an odd selector — biases it by 96 and rotates the biased sum right, with the add's carry rotating back into the top bit, producing a warble; an even selector passes the counter through, and a zero selector yields a fixed pitch of 96. Each path ends by staging its value into `SOUND_PITCH`.

**The rising pitch ramp.** `driveRisingPitchRamp` [code] tests an arm byte `loc_41c9` by predecrement (the decrement is a branch test only, not stored). While it stays nonzero the routine runs `advanceSoundPitchRamp` [seen] over the {countdown, pitch} pair that sits just past the arm byte at 0x41ca/0x41cb: while the countdown has ticks left it decrements the countdown, adds a fixed step of 4 to the pitch, publishes the pitch to `SOUND_PITCH`, and clears the composite `loc_41c0` so the frame composes cleanly. When the arm reaches its reset point `driveRisingPitchRamp` clears `loc_41c9` and reloads the ramp pair (`loc_41ca` = 32, its pitch byte = 0).

**The pulse-tone envelope.** `advancePulseToneEnvelope` [code] manages an envelope word whose low byte is `loc_41c7` and high byte `loc_41c8`. When the low byte's bit 0 is set it re-arms the word to a sentinel (low byte 0, high byte 128); otherwise it hands the high byte to `pulseSoundToneFromCountdown` [code]. That handler idles while the high byte is zero; otherwise it stores the high byte decremented back into `loc_41c8` and stages, through `stagePitchAndRaiseSoundFlag`, a two-level pulse — 129 when bit 2 of the decremented value is set, 0 otherwise. As the high byte counts down from 128, bit 2 flips every four counts, so the staged tone pulses on and off while raising the composite each time it fires.

**The gated square tone.** `advanceGatedSquareTone` [code] carries a gate counter `loc_41cc`. While it is more than one step from expiry (again a predecrement test, not written back) it drives `driveGatedSquareTone` [code]; at the expiry step it parks `loc_41cc` at 0 and re-arms the tone duration `SOUND_TONE_DURATION` (0x41ce) to 8. `driveGatedSquareTone` runs that duration down: while it is nonzero it counts one tick off and writes the frame-parity flag `loc_4007` with bit 0 flipped to sound-write register 5 (0x6805) — since bit 0 alternates each frame, the output toggles frame to frame, a square wave — and once the duration is spent it writes 0, silencing the register.

**The sequence player.** A single-voice tune player is driven from three descriptor/active-flag cells — `loc_41d2`, `loc_41cf`, and `SOUND_SEQ_ACTIVE` (0x41cd) — that share one cursor `SOUND_SEQ_PTR` (0x41d3), one current-tone cell `loc_41d5`, and one duration timer `loc_41d6`. Each frame `advanceAllSoundSequenceChannels` [code] walks the three descriptors in turn through `advanceSoundSequenceChannel` [code]. A descriptor holding 0 is inactive and skipped. An active one stages the composite (`loc_41c0` = 2) and publishes the current tone `loc_41d5` into `SOUND_PITCH`, then ticks the shared duration `loc_41d6`; while that timer still runs there is nothing more to do. When it expires the player pulls the next command byte at the cursor: 0xe0 is an end marker that deactivates that descriptor; any other byte splits into a low-5-bit index into `SOUND_TONE_TABLE` (0x17a9) for the new tone (stored in `loc_41d5`) and a high-3-bit index into `SOUND_DURATION_TABLE` (0x17c8) for the new duration timer (stored in `loc_41d6`), and the cursor advances one byte.

Three routes arm this player, each raising one descriptor and pointing the cursor at a different tune table. `armSoundSequenceOnRequest` [seen] fires when the request gate `loc_41d1` holds 1: it clears that gate, raises the `loc_41d2` descriptor and the shared timer `loc_41d6`, and points the cursor at the table at `loc_1e68` (0x1e68). `armSoundSequenceBySelector` [code] runs only while the driver-enable bit is set (`loc_4006` bit 0) and reads a request selector from `loc_41df`: selector 6 arms the `loc_41cf` descriptor at table `loc_1ebd` (0x1ebd), skipping if `SOUND_SEQ_ACTIVE` is already set; any other selector is handed to `armSoundSequenceForSelector16` [code], which recognizes only selector 0x16 — clearing `loc_41cf`, raising `SOUND_SEQ_ACTIVE` (0x41cd) and `loc_41d6`, and pointing the cursor at table `loc_1edf` (0x1edf) — and ignores every other value.

**The LFO level.** `driveSoundLfoLevel` [code] chooses per frame between a reset and a decay. When the reset request `SOUND_LFO_RESET_REQUEST` (0x41d0) is set it consumes the request and slams the full level (15) out; otherwise it runs `decaySoundLfoLevel` [code], which acts only on the tick where `loc_425f` reads 0xff and the current level `SOUND_LFO_LEVEL` (0x421f) is nonzero, dropping the level by one. Either path publishes through `broadcastSoundLfoLevel` [seen], which stores the level in `SOUND_LFO_LEVEL` and fans it across the four LFO-frequency latches based at `SOUND_LFO_FREQ` (0x6004 through 0x6007), rotating the byte right one bit between successive latches.

**The formation hum.** `driveSoundVoicesFromOccupancy` [code] runs only on even frames (`loc_4007` bit 0 clear). It sums the 6-by-10 flag grid `OCCUPANCY_GRID` (0x4123, row stride 16) into an 8-bit tally seeded at 1, then lights one of the three sound-write latches `SOUND_W_REG0`..`SOUND_W_REG2` (0x6800 through 0x6802) per unit of tally, up to three, and zeroes any latch past the point the tally drains — so the hum thickens with a fuller grid and thins as the grid empties. It also raises the near-empty flag `loc_4224` once the tally has nearly run dry (below 2).

**The decaying sweep.** `driveDecayingSoundSweep` [code] likewise runs only on even frames. While the countdown byte in `loc_41df` is nonzero it emits that byte, rotated right two bits, to sound-write register 4 (0x6804) and ticks the countdown down one step, so the emitted value shrinks toward silence. Note that `loc_41df` does double duty: `armSoundSequenceBySelector` reads it as the sequence selector while this routine drains it as the sweep's countdown.

**The stepped effect.** `driveGatedSoundStepSequence` [code] is gated by bit 0 of `loc_4201`. When enabled, a prescaler `loc_4205` (reload 10) lets it fire once every ten eligible frames; on each fire it enqueues a command word (opcode 2 in the high byte, the current step `loc_4206` in the low byte) and steps `loc_4206` down. When the step counter drains it disables the effect (`loc_4201` = 0) and silences sound-write register 3 (0x6803). The stack epilogue shared by that enqueue path, the deliberately-unnamed `loc_090b` [code], merely restores a saved register and returns and has no sound effect of its own.

**Requesting a sound from gameplay.** `armObjectAnimAndRequestSound` [code] is the entry (sub-state 0) handler of a deactivated object's multi-phase animation. It seeds that object's animation timers (frame divider = 4, step count = 4, step field = 28, at record offsets 16, 17 and 18), advances the object's sub-state (offset 2) so this entry runs only once, and posts a sound request into `loc_41df` keyed on the object's position byte (offset 7): 0x07 when the position is below 112, 0x17 at or above. That posted byte is exactly what the decaying sweep then drains out to register 4.

**Silencing everything.** `silenceSoundAndDisableIrqStars` [code] quiesces the hardware: it sets the four LFO-frequency latches (`SOUND_LFO_FREQ`, 0x6004 through 0x6007) to 1, clears all eight sound-write registers (from `SOUND_W_REG0`, 0x6800), clears the interrupt-enable latch `IRQ_ENABLE` (0x7001) and the starfield-enable latch `STARS_ENABLE` (0x7004), and drives the pitch latch `SOUND_PITCH_W` (0x7800) fully high (0xff). Beyond muting audio it also halts the vblank interrupt and the starfield, so it is the routine the machine uses to tear down its running sound and video state.

## Coins, credits, the HUD, score display, and the message scroller

This subsystem is the bookkeeping-and-display half of the machine: it turns coin-switch pulses into credits, drives the coin meter and lockout and the start-button lamps, keeps the two players' scores and the high score in packed BCD and paints them, animates the attract-mode screen wipe and the DIP-configured attract text, and runs the character-at-a-time message scroller. Most of the on-screen work is deferred: a producer posts a word to the shared draw/sound command queue whose high byte names the handler that will service it later and whose low byte is that handler's parameter. The handlers seen throughout this subsystem are the message painter (queue byte 6), the credit/score HUD line (byte 7), a score-field clear-and-repaint (byte 4), and the BCD score-add (byte 3). Keeping this in mind makes the rest of the flow legible.

### The coin path

Coins are handled in two stages once per frame. The front end is `serviceCoinInputs` [seen], the first call in the frame's service cluster (it runs right after the frame-timer at `loc_425f` is decremented, ahead of the sound and scroller ticks). In coinage mode 3 (`loc_4000` == 3, free play) it hands straight off to `presetCreditCount` [code], which forces the credit count `loc_4002` to 9 and clears the coin-phase flag `loc_4001` — nine credits is above the lockout threshold, so free play leaves the mechanism open. Otherwise it debounces the coin switches: it OR-combines this frame's raw input shadow `IN0_SHADOW` (0x4010) with the previous frame's copy `loc_4013`, complements that, and masks by the two-frames-and-three-frames-ago history cells `loc_4015` and `loc_4016`, so only a switch that has been asserted across the input history survives. If the high bit of the result is set it calls `addCreditForCoin` [code] directly; otherwise the low two bits each advance the coarse coin accumulator `loc_4004` (up to twice in one pass, one tick per bit).

The second stage is `tickCoinMeterAndAwardCredits` [seen], the next call in the same cluster, which paces the physical coin-counter output and converts accumulated coins into credits. While the fine reload cell `loc_4003` is nonzero it calls `pulseCoinCounter` [seen] and counts `loc_4003` down; `pulseCoinCounter` circular-rotates its input right three bits so bit 3 lands in bit 0 and latches that to the coin-counter output `COIN_COUNTER_0_LATCH` (0x6003), of which only the low bit is wired, then decrements the pulse-width cell — that is what makes the counter output a timed pulse rather than a level. When `loc_4003` reaches zero and the coarse counter `loc_4004` still has coins, it ticks `loc_4004` down, refills `loc_4003` to 15, and applies the coinage mode from `loc_4000`: mode 3 awards nothing, mode 1 runs the two-coins-per-credit path `awardCreditEverySecondCoin` [code], mode 2 runs the credit step twice, and any other mode runs it once.

`awardCreditEverySecondCoin` uses `loc_4001` as a one-bit phase flag: on the first coin of a pair (bit 0 clear) it calls `setCoinPhaseFlag` [code] to raise the flag; on the second (bit 0 set) it clears the flag and awards a credit through `incrementCreditCount`. `setCoinPhaseFlag` is simply the set-to-one arm of that toggle. Adding a credit is `incrementCreditCount` [code]: at the ceiling of 99 it does nothing, above the ceiling it pins back down through `clampCreditsToMax` [code] (which writes exactly 99), and below it bumps the count, raises the credit-ready flag `loc_41c9` (which arms the rising-pitch coin-accept sound), and posts a byte-7 credit-line redraw. `addCreditForCoin`, the direct-credit arm of `serviceCoinInputs`, does the same bump-if-below-99 / raise-`loc_41c9` / queue-a-redraw sequence without the two-coin gate. All of these treat `loc_4002` as the live credit count.

The coin mechanism's lockout coil tracks the credit bank. `updateCoinLockoutFromCredits` [code], the third call in the service cluster, reads `loc_4002`: at nine or more credits it releases the lockout via `clearCoinLockout` [code] (writing 0 to the `COIN_LOCKOUT` latch at 0x6002), and below nine it engages it (writing 1). `clearCoinLockout` is the shared "release" primitive.

### From a credit to the start of a game

During the attract state the credit count is what breaks the machine out of attract. `advanceGameStateOnCredit` [code] is the state-1 attract handler's continuation: when `loc_4002` is nonzero it advances the game-state index `GAME_STATE` (0x4005) and tears down the attract cluster — clearing the frame flag `loc_4007`, the sequence step `SEQUENCE_STATE` (0x400a), state flag `loc_41c2`, the sound-sweep countdown `loc_41df`, and the message-scroller enable `MESSAGE_SCROLL_ENABLE` (0x40b0); with zero credits it is a no-op.

The start-button lamps are driven from the same credit count by `driveStartButtonLamps` [code], gated by bit 5 of `loc_425f`: with that bit clear both lamp latches `START_LAMP_0` (0x6000) and `START_LAMP_1` (0x6001) go dark; otherwise zero credits leaves the lamps as they are, one credit lights lamp 0, and two or more light both. Two sequence-state handlers in the pre-game run keep the lamps live while they tick down their dwell. `holdStartLampsThenAdvanceSequence` [code] counts `loc_4019` down and, while it stays nonzero, re-runs `driveStartButtonLamps` each frame; on the zero-crossing it advances `SEQUENCE_STATE` and clears the 128-byte flag-bits block at `FLAG_BITS_BASE` (0x4100). `blankVramRowsThenDriveStartLamps` [code] is the next state: it fills two 28-cell blank-tile rows through the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) with a 4-cell gap between rows, ticks the dwell tier `loc_4009`, and while rows remain returns; on the last row it advances `SEQUENCE_STATE`, clears the screen-flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y` (0x7006/0x7007) and the direction flag `loc_4018`, queues a byte-7 and a byte-6 draw, and re-drives the lamps.

Committing to a round is `startGameRoundAndClearScores` [code]. A single 16-bit store seeds both `CURRENT_PLAYER` (0x400d) and the paired-player/alt-field flag `loc_400e` (0x400e) at once from its pointer argument. It blits the 32-byte ROM row template `loc_051b` into the packed-flag buffer `PACKED_FLAG_BITMAP` (0x4180), arms the sub-state advance gate when config bit 0 of `loc_401f` is set, enters play (`GAME_STATE` = 3, `SEQUENCE_STATE` = 0, `loc_4006` = 1, `loc_41d1` = 1), and posts three queue words: a byte-6 message draw and two byte-4 requests that clear and repaint the player-1 and player-2 score fields, so both score readouts are zeroed and painted fresh at the round's start.

### Score storage and rendering

Scores are three-byte packed-BCD values: player 1 at `PLAYER1_SCORE_BCD` (0x40a2), player 2 at `PLAYER2_SCORE_BCD` (0x40a5), and the high score at `HIGH_SCORE_BCD` (0x40a8). `byteToPackedBcd` [code] converts a binary byte to its two-decimal-digit packed form (value mod 100, tens in the high nibble), and is what the HUD uses to render the credit count as digits.

Digits reach VRAM through a small painter stack. `drawBcdDigit` [code] paints one nibble as a glyph — digits map to the contiguous tiles 0x90..0x99 — with leading-zero suppression: while the blank budget in C is nonzero a leading zero is drawn as the blank tile (base 0x80, which added to 0x90 wraps to tile 0x10) and the budget drops; the first significant digit ends suppression; a zero after suppression has ended draws a real '0'. It then advances the cursor by its stride. `drawBcdNumberColumn` [code] walks a three-byte field downward from the source pointer, painting high nibble then low as six digit tiles up the VRAM column (stride −32, one tile row up per digit) with a four-digit blank budget, so the four leading positions can blank but the low two digits always show. Callers point it at a field base plus 2 so it reads the most-significant byte first.

`selectCurrentPlayerScore` [code] returns the active player's score-field base (player 1 → 0x40a2, else player 2 → 0x40a5) and touches no memory; it feeds the score-add handler. `drawScoreToSelectedPlayerField` [code] chooses a VRAM digit-field cursor by a selector — 0 → the primary field `DIGIT_FIELD_PRIMARY` (0x5381), otherwise the alternate field `DIGIT_FIELD_ALT` (0x5121) — and paints the number there. `drawScoreFieldByIndex` [code] is the redraw dispatcher keyed by a counter index: 0 repaints player 1's score in the primary field, 1 repaints player 2's score in the alternate field but only when the paired-player flag `loc_400e` is set (whose nonzero value also serves as the alt-field selector), and 2 repaints the high score; an index of 3 or more recurses downward, redrawing every field from index−1 down to 0 in one call. `clearAndRedrawScoreField` [seen] is the clear-first counterpart used by the byte-4 queue handler: it zeroes the selected field's three digit bytes plus a companion scratch byte — `loc_40ad` for player 1, `loc_40ae` for player 2 (the high-score arm has no separate scratch and simply re-zeroes its own first byte) — then repaints through `drawScoreFieldByIndex`; it recurses the same way for indices of 3 or more. The high-score readout is painted by `drawHighScoreDigits` [code], which fixes the cursor at the high-score VRAM field `loc_5241` and draws six BCD digits from the caller's source; it is reached both from the score handler's high-score tail (after a new record is copied into 0x40a8) and from the index-2 redraw path.

Awarding points during play is `awardKillScoreByBandAndDeactivate` [code]. It deactivates the hit object (its slot header becomes 0,1,0) and sizes the kill's score by which of three bands the object's packed field (obj+7) falls into against the 0x50 threshold, bumping a request parameter and dropping the field by 16 per missed band; a matched band posts a byte-3 BCD score-add immediately. If all three bands are exhausted it raises the inhibit/request word `loc_422b`, and when the active-neighbour count `ACTIVE_NEIGHBOR_COUNT` (0x422a) is exactly two it folds in a neighbour bonus, records it at `loc_422d`, and posts the folded score-add. The byte-3 handler that services those requests selects the current player's field via `selectCurrentPlayerScore`, adds the indexed BCD increment, checks the bonus-marker threshold, repaints through `drawScoreToSelectedPlayerField`, and promotes a new high score through `drawHighScoreDigits` — so this routine is one producer feeding that whole score-update chain.

### Bonus markers

`drawMarkerRow` [code] paints the five-slot marker row at `MARKER_ROW_VRAM` (0x539e): it stamps `markers` marker tiles (tile 102) growing upward, then blanks the remaining slots until a signed slot counter goes negative. When the object-active flag `OBJ_ACTIVE_FLAG` (0x4200) is set the displayed count is dropped by one, and if that empties the count every slot is blanked instead. `awardBonusMarker` [code] is the one-shot that grants a marker to the current player: it indexes a per-player guard flag by `CURRENT_PLAYER` (this is the same `loc_40ad`/`loc_40ae` pair used as the score-clear scratch, so clearing a player's score also re-arms its bonus-marker guard), and if the player's slot is not already flagged it flags it, raises the sound-envelope trigger `loc_41c7`, increments the marker counter `loc_421d`, and repaints the row with the new count. It fires from the score handler when a score-threshold is first crossed.

### The player-status indicator columns

Each player has a status-indicator column in VRAM — player 1 at `PLAYER1_STATUS_VRAM` (0x5340), player 2 at `PLAYER2_STATUS_VRAM` (0x50e0) — selected by `selectPlayerStatusVram` [code]. `paintPlayerStatusColumn` [code] paints a three-cell column stepping by DE: the top cell gets the player code plus one, then two fixed tiles (0x25 middle, 0x20 bottom); afterward, only when flag bit 4 is clear and the mode gate `loc_4006` is zero, it clears the status flag `loc_40ab`. `repaintPlayerStatusColumn` [code] chooses behaviour by flag bit 4: clear paints the active player's column directly; set blanks the active column's three cells (tile 16) and, only when the paired-player flag `loc_400e` is set, also paints the other player's column (player XOR 1). `repaintPlayerStatusColumnIfSaved` [code] repaints only when the saved status byte `loc_40ab` is nonzero, and `repaintPlayerStatusColumnFromModeGate` [seen] latches the mode: a nonzero mode gate `loc_4006` is saved into `loc_40ab` before repainting, while a zero gate repaints only if `loc_40ab` is already set — so the indicator persists across frames where the mode byte has gone quiet.

### The attract screen-fill animation and DIP text

The attract screen wipe is an animated tile-strip fill. `advanceScreenFillStrip` [code] is its per-frame head: it pets the watchdog (a discarded read of the sound pitch port), and if the strip gate `loc_4008` is zero there is nothing to draw so it restarts the outer dwell; otherwise it loads the live cursor `VRAM_WRITE_PTR` and draws the strip's first half. `drawScreenFillStripFirstHalf` [code] stamps sixteen two-tile pairs (tiles 48/50) forward from the cursor, then falls into `drawScreenFillStripSecondHalf` [code], which stamps sixteen more pairs (tiles 52/54), saves the advanced cursor back to `VRAM_WRITE_PTR`, and ticks the strip countdown `loc_4008`; while it is still running it returns, and on expiry it restarts the outer dwell. `restartScreenFillOnDwellExpiry` [seen] ticks the high dwell tier (the byte just past its pointer, `loc_4009`): already zero, or reaching zero on this tick, re-seeds the whole fill via `resetScreenFillState`; otherwise it keeps counting. `resetScreenFillState` [seen] is that re-seed: unless the service input `IN0` bit 6 is asserted, it rewinds `VRAM_WRITE_PTR` to the top of VRAM `VRAM_BASE` (0x5000), re-arms the fill length `loc_4008` to a full page of 32, clears the alternate-dispatch flag `loc_401a`, and resets `GAME_STATE` to 0 — dropping the machine back to the top of attract.

The attract screen's configuration text is drawn by `drawInputTextColumnsAndSeedScreenFill` [seen]: it decodes three two-bit fields from the input ports (`IN1` bits 6–7, `IN2` bits 0–1, and `IN2` bit 2) into text-descriptor indices and paints each as a column, then, unless `IN0` bit 6 is asserted, seeds the fill state (`loc_4006` = 0, `loc_401a` = 2, the dwell pair `loc_4008`/`loc_4009` = 16/48, `VRAM_WRITE_PTR` = `VRAM_BASE`), clears the four-byte lamp/coin latch block, and silences the sound hardware. `armInputFlagAndDrawInputColumns` [code] is the input-scan link ahead of it: it folds the two supplied input-port bytes and, when their shared bit 4 (a start input) is set, raises the companion flag `loc_41cc`, then falls through into that same attract init.

Those attract text columns are painted through a reusable descriptor-driven text stack. `drawTextColumn` [code] is the innermost loop: for `count` characters (a count of 0 meaning a full 256) it reads a source byte, subtracts the '0' code (48) to map it to a tile, stores it, and steps the source forward one byte and the destination by a signed stride — a negative stride walks up a column. `drawTextColumnFromDescriptor` [code] unpacks a five-byte descriptor (source word, destination word, count byte) and paints that many characters up a column with the −32 up-a-row stride. `drawTextColumnByIndex` [code] indexes the ROM text-descriptor table `TEXT_DESCRIPTOR_TABLE` (0x1cf6) by A (five-byte records) and paints the selected descriptor's column.

### The message scroller

The scroller reveals a message one glyph at a time up a VRAM column. It is armed by `renderMessageColumn` [seen], the byte-6 queue handler, which indexes the message pointer table `MESSAGE_PTR_TABLE` (0x235c) by A to get a record holding a destination word and a text pointer, then branches on A's top two bits. Bit 7 blanks the message: it overwrites each of the text's cells up the column with the blank tile (64) to the 63 terminator. Bit 6 is position setup: it records the destination and text pointers in `MESSAGE_DEST_PTR` (0x40b5) and `MESSAGE_TEXT_PTR` (0x40b3), computes a per-column pacing cursor into the `loc_4020` cursor table (`loc_4020` + column×2) and stores it in `MESSAGE_CURSOR_PTR` (0x40b1), packs the destination row into that cursor's top bits, clears the whole 32-cell column to tile 16, and raises `MESSAGE_SCROLL_ENABLE` (0x40b0) so the scroller starts running. With neither top bit set it simply draws each character's glyph up the column immediately.

`advanceMessageScroller` [seen], one of the per-frame service-cluster calls, steps an armed scroll: while `MESSAGE_SCROLL_ENABLE` bit 0 is set it reads the pacing counter through `MESSAGE_CURSOR_PTR`, and if that counter's low three bits are still set it merely ticks the counter via `endMessageScrollOnExpiry`; otherwise it reads the next source character, and at the 63 terminator it just finishes the countdown via `endMessageScrollOnExpiryFromDe`, else it emits one glyph — advancing `MESSAGE_TEXT_PTR` by one, writing the character-minus-48 tile into the `MESSAGE_DEST_PTR` cell, stepping that destination one row up (−32) — and then ticks the counter. `endMessageScrollOnExpiry` [seen] decrements the countdown byte at its pointer and, on the exact zero-crossing, clears `MESSAGE_SCROLL_ENABLE` so the scroller stops; `endMessageScrollOnExpiryFromDe` [seen] is the identical tail entered with the counter pointer arriving in the alternate register (the terminator path), delegating straight to it.

Two attract sequence-state handlers pump message columns through the queue while running two-tier dwell timers (`loc_4008` the low tier, `loc_4009` the mid tier). `emitMessageColumnsThenAdvanceSequence` [seen] runs the shared strided-table reset, then on each low-tier expiry reloads it to 80 and posts a byte-6 message draw whose parameter tracks the mid count plus 6; on the mid-tier expiry it advances `SEQUENCE_STATE`, reloads both tiers to 32/4, clears the sprite-source block `SPRITE_SOURCE_OBJ_BASE` (0x42b0), and zeroes the redraw count `DRAWN_COLUMN_COUNT` (0x4241). `postCreditAndMessageDrawsAndAdvance` [code] is a shorter sequence step that simply posts a byte-7 credit-line redraw and a byte-6 message draw, advances `SEQUENCE_STATE`, and re-arms the dwell cascade (`loc_4008` = 96, `loc_4009` = 16). A message can also be fired by a flying object: `advanceObjectAndQueueMessageColumn` [seen] is an object-AI state that bumps the object's tick (ix+4) and counts down its dwell (ix+16), and on expiry posts a byte-6 message draw carrying the object's selector (ix+7) plus 75 and advances the object's own state.

### Shared helpers

`reloadExpiredCounterAndTally` [seen] is a small reusable primitive used by the pacing logic (its caller re-arms an enemy-launch timer): it copies a reload byte from a source table into an expired counter cell and returns the refill tally incremented by one, so a caller both re-arms a counter and records that it did. Finally, `loc_090b` is the deliberately unnamed pure-stack epilogue shared by the command-queue enqueue path — it restores the caller's saved pointer register and returns, with no work-RAM effect.

## Tile / VRAM drawing primitives and coordinate mapping

The tilemap lives at VRAM_BASE (0x5000): a 32-cell-wide grid where each cell holds one tile code, and the cell one screen-row lower sits +32 bytes on. Nearly every routine here is some layering over two byte-writes, so it is worth starting from the stamp primitive they all reach for and working outward to the coordinate math, the block builders, the periodic column redraw, the full-screen clears, and finally the moving-projectile render/collision pair that shares this same VRAM-writing machinery.

### The stamp primitives

`stampTilePair` [code] is the atom. Given a tile code, a destination cell, and a stride, it writes the code at the cell and code+1 at the very next cell, then hands back the pointer advanced past the pair by the stride and the tile code advanced by two. Because the store is an 8-bit truncation, a seed of 0xff writes 0xff followed by 0x00 — the +1 wraps. Choosing the stride is how callers turn this one primitive into rows, columns, or blocks: a stride of 31 lands the returned pointer exactly one tilemap row (+32) below the pair's first cell, while a large "negative" stride walks upward instead.

`drawDoubleHeightTile` [code] is the other atom, for glyphs that are one cell wide but two cells tall: it writes the seed at the cell and seed+2 in the cell one row (+32) below, leaving the caller's DE pointer untouched. The +2 code step is the convention that the bottom half of a tall glyph is the second entry in a top/bottom code pair.

### 2×2 tile blocks

A 2×2 block is four consecutive tile codes laid two-wide, two-tall. `drawTileBlock2x2` [code] builds it as two `stampTilePair` calls with a stride of 31: the first stamps (seed, seed+1) across the top row and drops the pointer one row down, the second stamps (seed+2, seed+3) across the row below. It preserves DE. `drawBottomTilePairRestoreDe` [code] is that same second-pair tail factored out — it stamps the bottom pair and then restores the DE the caller had saved before the block began, the shared exit used by the block writers.

`drawTileBlock2x2Up` [code] is the upward mirror: it stamps the top pair with a −33 stride (which, after the pair's built-in +1, nets one row up), then steps the code back by four and stamps the second pair in the row *above*. It is the form used when a block must grow toward the top of the screen rather than down.

Several entry points fix the seed instead of taking one. `drawFixedTileBlock2x2` [code] draws a 2×2 block seeded with glyph code 44 (0x2c), so it lays codes 0x2c..0x2f — the block form of the decorative "0x2c family" of tiles. `drawFixedTilePairHorizontal` [code] stamps just a horizontal pair from that same seed 44 and returns the advanced tile/pointer so a caller's loop can chain the next pair across a row (the score/credit HUD line at loc_24b7 uses it this way). `drawFixedTilePairVertical` [code] instead paints a tall pair from seed 44 through `drawDoubleHeightTile`. `drawFixedTileBlock2x2Up` [code] seeds the upward block builder with glyph 46 and is what the marker-row drawer at drawMarkerRow (0x22b3) uses to blank the unused slots of the five-slot marker row.

`drawTileBlock2x2AtDe` [code] is an address adapter: it swaps the DE and HL pointers so that the destination that arrived in DE becomes the draw target (the old HL is handed back in DE), then draws a normal 2×2 block there. This exists because the table-driven callers keep their working VRAM pointer in DE while the block builder wants it in HL.

### 4×4 forms

The larger indicator forms are drawn into a fixed VRAM region rather than a caller-supplied pointer. `blankTileBlock4x4` [code] wipes a 4×4 cell region anchored at loc_51da, writing blank code 0x40 to four rows of four cells with a 32-cell start-to-start stride. Note this "blank" is 0x40 — distinct from the 0x10 blank the row and column fills use elsewhere; the code that reads as empty is context-dependent, not a single constant. `blank4x4AndDraw2x2Icon` [code] is indicator form 0: it blanks that 4×4 region and then overlays a 2×2 block seeded with tile 96 at loc_51fc, an icon centred in the cleared field.

`draw4x4TileForm` [code] is the dispatcher over those forms, selected by an argument: form 0 is the blank-and-icon just described, form 1 is a bare `blankTileBlock4x4`, and any other value folds (form−2) into the middle bits of a complemented tile code over a fixed 0xc0 base and stamps four 2×2 blocks — at loc_51da, loc_51dc, loc_521a, and loc_521c, which together tile a contiguous 4×4 cell area — with the seed advancing four codes per block so each quadrant carries the next run of glyph codes.

### Coordinate mapping and table-driven figure drawing

`mapPackedCoordToVram` [code] is the coordinate translator the display-list handlers lean on. It takes a single packed coordinate byte and shuffles its nibble fields — rotating the low nibble to form the address high byte and the top bits of the low byte, then folding a complemented running sum of the high-nibble field into the rest — to produce a cell address of the form VRAM_BASE + (high<<8) + low. It leaves behind three live results the callers branch on: the cell address itself, a 2-bit field from the coordinate, and a carry bit that is the coordinate's bit 4.

`drawFixedTileFigureAtPackedCoord` [code] is the channel-1 draw handler (reached from the display-list handler at loc_207d). It maps the packed coordinate to its cell and then, on the coordinate's bit 4, either stamps a fixed 0x2c-family 2×2 block (`drawFixedTileBlock2x2`) or a fixed vertical pair (`drawFixedTilePairVertical`) — one packed byte selects both where and which of the two figure shapes.

A second family of handlers picks the tile *code* from a table. `drawIndexedTileBlock` [code] looks a 2×2 block's seed code up in the ROM block table TILE_BLOCK_TABLE (0x215b) by an index and stamps that block at the pending DE destination through `drawTileBlock2x2AtDe`. `drawSelectedTileBlockOrFallback` [code] wraps that with a signed test on a selector: non-negative selectors index the table as above, while a negative selector stamps a fixed fallback block seeded with tile 0xa4 instead. `drawTileGlyphOrBlock` [code] is the top of this dispatch, keyed on the incoming carry flag: with carry set it swaps DE/HL and hands off to `drawSelectedTileBlockOrFallback` to draw a 2×2 block at that pointer; with carry clear it fetches the tile code for the index out of the byte table at loc_2157 and paints it as a double-height glyph at the incoming HL. This is where the display-list slot handlers at loc_2055 and loc_2089 converge after resolving a cell.

Two register-only helpers animate which tile variant those handlers draw. `computeTileVariantFromTimer` [code] folds an input value with the per-frame counter at loc_425f: below a range limit of 112 it swaps the counter byte's nibbles, adds the value and an incoming carry, and keeps the low two bits — a 0..3 variant index that cycles with the frame counter; at or above 112 it saturates the result to the 0x80 out-of-range sentinel (via markValueOutOfRange). `computeTileVariantFromValueAndTimer` [code] is the front end for it: it likewise saturates to 0x80 at or above 112, otherwise takes the value's low nibble and sets a carry when the frame counter's low nibble is the smaller before folding through `computeTileVariantFromTimer`. Neither touches memory; both just leave the chosen variant index in place for the draw dispatch that follows.

### VRAM columns and the periodic column redraw

Columns are the transposed case: instead of walking +1 across a row, these walk the low address byte up by 32 per cell within a fixed page. `drawTileColumnTriple` [code] copies three source bytes up one VRAM column — each byte stored, the low destination byte stepped −32 (staying inside the page), and after the three the low byte advanced +98 to line up the next column — returning the advanced source pointer and destination so successive columns chain. `blankTileColumns` [code] is the erase counterpart: for each of B columns it stamps blank code 16 into three cells stepping −32 per row (a 16-bit step so it borrows into the high byte), then advances +98 to the next column, all anchored at loc_5193; its loop is a decrement-and-branch, so a count of 0 means a full 256 columns.

`redrawTileColumnsPeriodically` [code] drives both on a schedule. It reads the running column count at loc_4241 (DRAWN_COLUMN_COUNT) and does nothing until at least two columns are counted, then works with count−1 columns. It gates on the frame counter loc_425f: when the low six bits are zero it wipes the columns with `blankTileColumns`, and only when they equal 32 does it repaint — drawing the first column from a source row in TILE_COLUMN_TABLE (0x039a) selected by the counter's top two bits into the VRAM start at loc_5193, then the remaining columns from the consecutive source stream (TILE_COLUMN_TABLE_CONT, 0x03a6) with each draw threading its advanced source and destination into the next. So DRAWN_COLUMN_COUNT is a live running total of queued columns, not a fixed width, and the blank and draw halves happen on different frame phases.

### Full-screen fills in the sequence state machine

Several of these are one step of the top-level sequence state machine, each filling a strip of the screen per frame and advancing the sequence step index at SEQUENCE_STATE (0x400a) when its dwell timer runs out. `primeVramFillAndAdvanceStep` [seen] is the setup step: it clears the 128-byte flag block at FLAG_BITS_BASE (0x4100) and two status bytes (loc_425f, loc_4224), points the VRAM write cursor VRAM_WRITE_PTR (0x400b) two cells into the grid at VRAM_BASE+2, arms the page/dwell tier loc_4009 to 32, and bumps the sequence step.

`fillVramRowThenResetObjectState` [seen] then runs each frame: it paints a 28-cell strip of tile 16 at the write cursor and steps the cursor a full 32-cell row on, and ticks the dwell tier loc_4009. While the tier is still counting it simply returns; on expiry it advances the sequence step, re-arms the two-tier dwell cascade (loc_4008=64, loc_4009=4), clears the 48-byte active-object block at OBJ_ACTIVE_FLAG (0x4200), zeroes the two screen-flip latches FLIP_SCREEN_X/FLIP_SCREEN_Y (0x7006/0x7007) and the direction flag loc_4018, raises the status flag loc_4238, and reseeds the object-shadow field from the ROM template at OBJ_SHADOW_RESEED_TEMPLATE (0x1db1). `blankVramRowThenResetSpriteState` [code] is the near-identical sibling for a later state: it first clears the strided work-RAM table (clearStridedTable), blanks a 28-cell row of tile 16 at the cursor and steps it +32, and on dwell expiry advances the step, clears the sprite-source region SPRITE_SOURCE_OBJ_BASE (0x42b0, a full 256-byte wipe) and the sprite shadow SPRITE_SHADOW_BASE (0x4060, 64 bytes), re-arms the same dwell cascade, reseeds the object shadow, and queues a command word. `blankScreenRowsThenAdvanceSequence` [code] is the play-state-1 progressive clear used by both play tables: it blanks 32 cells of tile 16 at the cursor, advances it +32, and ticks the phase counter loc_4009, and on the final phase advances the sequence and reseeds the object shadow. Across these three, the row cursor at loc_400b is the shared state carried frame to frame while the screen wipes downward a strip at a time.

### Projectile integration, rendering, and collision

`advanceAndRenderProjectiles` [code] steps and draws the moving objects, and it too ends in VRAM/shadow writes. It reads the record block at loc_4260 as seven records, each a pair of five-byte sub-slots, with the low bit of the frame counter loc_425f selecting which sub-slot of each record leads this frame (the trailing one just gets its sub-position bumped +2). For a leading sub-slot that is active it advances the sub-position, integrates the 16-bit position by twice the signed velocity byte, and deactivates the slot — zeroing its active/sub-position/high bytes — when the sub-position overruns or the position leaves the vertical window. It then writes each object's on-screen Y and tile code into the sprite shadow at loc_4081, mirroring the Y (complement-minus-one) when the direction flag loc_4018 is clear and applying a ±1 code nudge to the first three records so those objects' glyphs offset by one.

The collision pass views that same 70-byte region differently. `flagProjectileHitsOnPlayer` [code] first checks that projectiles are enabled (bit 0 of OBJ_ACTIVE_FLAG, 0x4200) and then reads the region at loc_4260 not as seven ten-byte records but as fourteen five-byte entries, running each through the per-entry test with a band width fixed at 5 (the entry stride) — that width is always 5, never a value inherited from the caller. `flagProjectileHitOnPlayer` [code] is that per-entry test: for an active entry (bit 0 of its first byte) it box-tests the entry's X (offset 3) against the player-X reference at loc_4202 and its Y (offset 1, biased by 31) across a near band and a far band; on overlap it deactivates the entry by zeroing its first byte and raises the hit-event flag HIT_EVENT_FLAG (0x4204)=1, which the rest of the game reads as "the player was struck." The dual reading of loc_4260 — seven records for motion and rendering, fourteen entries for collision — is a real property of the layout, not a discrepancy.

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs.
