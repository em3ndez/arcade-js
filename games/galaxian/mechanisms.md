# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–13.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

Beneath the gameplay logic sits a floor of tiny, general-purpose helpers that the rest of the machine leans on frame after frame. They do no game reasoning of their own; they are the arithmetic, the bulk memory work, the table lookups, and the interrupt housekeeping that everything else is built out of.

The pseudo-random number generator is a single-byte linear congruential step. `advanceRandomSeed` [seen] reads the current seed out of `RNG_SEED` (0x401e), computes `seed*5 + 1` truncated to eight bits, writes the new value straight back into that same cell, and hands the fresh byte back as this draw's result. The seed is therefore a rolling counter, not a fixed constant — each draw both consumes and updates it, so the sequence only advances when someone actually pulls a number. Its consumers are scattered across the object AI: `reseedFormationObjectState` rolls a fresh random Y when it re-inits an object, `chooseNextAttackerDirection` uses a single random bit to pick a launch direction when the formation edge doesn't force the choice, and `computeJitteredXVelocity` folds a bounded draw into a spawned projectile's speed. Because every one of these shares the one seed cell at 0x401e, the game's "randomness" is really one deterministic stream fanned out to many callers.

Bulk memory work goes through `fillMemoryBlock` [code], the processor's restart-vector fill primitive living at 0x0010. Given a destination pointer, a fill byte, and a count, it stores the byte, steps the pointer forward, and repeats until the count is exhausted, returning with the pointer sitting one past the filled region and the count spent to zero. The count is decremented as a byte, so a starting count of zero wraps through 255 and fills a full 256-byte page — and callers exploit that deliberately: `blankVramRowThenResetSpriteState` clears an entire sprite-source page by passing a count of zero, then follows up with an explicit 64-byte clear of the sprite shadow region. The routine is the workhorse behind screen blanking, VRAM row clears, and object-RAM resets throughout the boot and between-round sequences, wherever a contiguous span needs to be wiped or set to a uniform value. One caveat worth stating plainly: the store targets whatever the pointer names, and that pointer can land on a hardware latch rather than plain RAM, so a fill is sometimes a way of poking device registers, not only clearing memory.

Its sibling at the next restart vector is `fetchIndexedTableByte` [code] at 0x0020, an indexed table read. It adds an eight-bit index to a base pointer, carrying correctly into the high byte so a table can straddle a page boundary, then reads the byte at the resulting address and returns both that byte and the advanced pointer. This is the standard "look up entry N of this table" operation: `drawIndexedTileBlock` uses it to pull a tile id out of a block table, `drawTileGlyphOrBlock` indexes a glyph table with it, and `fillScreenThenLatchConfigAndAdvanceState` uses it to translate the low two bits of an input port into a configuration byte via a small lookup table. The pointer it leaves behind lets a caller keep reading forward from the entry it just fetched.

The unsigned divide is `divideUnsigned8` [code] at 0x0048, a classic restoring division of the dividend in A by the divisor in D. It runs eight rounds; each round compares the running remainder against the divisor, subtracts when it fits and records a one bit (records a zero otherwise), shifts that quotient bit into the accumulator, and then walks the divisor down one bit for the next round. When the eight rounds finish, the quotient sits in C — which is the value callers actually read — the remainder is left in A, the fully-shifted divisor in D, and the round counter is spent to zero. It touches no memory; it is pure register arithmetic. Two callers use it to turn a slope into something meaningful: `computeDirectionOctantFromSlope` divides a rise by a run and keeps the top three bits of the quotient as a 0–7 heading octant, and `computeJitteredXVelocity` divides to scale a slope before adding its random jitter and a floor.

Finally there is the interrupt housekeeping. Once per frame the vblank interrupt is serviced, and `rearmVblankInterruptAndRestoreRegs` [code] at 0x00d8 is the tail end of that service. It writes 1 into `IRQ_ENABLE` (0x7001) to re-arm the interrupt so the next frame's vblank will fire again — the entry side of the handler cleared that latch to acknowledge the current interrupt, so without this write only the very first vblank would ever be taken and the entire per-frame loop would freeze. Having re-armed, it restores the six register pairs the handler saved on entry (IY, IX, HL, DE, BC, and finally AF, unwound in the reverse of the order they were saved) and returns to the point in the main loop that the interrupt suspended, leaving the interrupted code none the wiser.

Sharing the same low-level flavor is `loc_090b` [code], a deliberately-unnamed two-instruction stack epilogue: it restores the one register pair (HL) that its enqueue path saved on the way in and returns. It does no work-RAM of its own; it exists purely as the shared exit that `commitQueueWriteHead` and the rest of the command-enqueue path fall into so they all unwind the same way.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

Galaxian runs the whole machine off two nested selectors in work RAM. The coarse one is `GAME_STATE` (0x4005); each frame the top-level handler for the current game-state runs, and the five game-states map one-to-one onto five handlers: state 0 is the boot/self-fill handler `fillScreenThenLatchConfigAndAdvanceState` [seen], state 1 is the attract loop `runAttractSequenceAndAdvanceOnCredit` [code], state 2 is the "press start" screen `runStartScreenAndLaunchGame` [code], and states 3 and 4 are the two play frames `runPlayerOnePlayFrame` [code] and `runPlayerTwoPlayFrame` [code]. The finer selector is `SEQUENCE_STATE` (0x400a): four of those five game-state handlers do their real work by fanning out again on `SEQUENCE_STATE` into a bank of sub-state handlers, so a game-state names *what phase of the game* we are in and the sequence-state names *how far through that phase* we have progressed. The whole thing is driven forward by timers that, on expiry, simply bump `SEQUENCE_STATE` (and occasionally `GAME_STATE`) to the next value.

### The dwell-timer tiers and their carry into the sequence state

The heartbeat of every phase is a little two-tier down-counter that lives in three consecutive bytes: a prescaler sub-timer at `loc_4008` (0x4008), a dwell tier at `loc_4009` (0x4009), and — deliberately — `SEQUENCE_STATE` at the very next byte, 0x400a. That adjacency is the trick the machine turns on. `tickCascadeCountdown` [seen] decrements the byte it is pointed at, and *only on the tick that carries it to zero* it steps to the following byte in the page and increments that. Point it at `loc_4009` and the increment it fans out on expiry lands squarely on `SEQUENCE_STATE`, so "the dwell timer ran out" and "advance to the next sub-state" are the same event. `tickSequenceDwellTimer` [code] is exactly that: it aims the cascade at `loc_4009`, so each frame it counts the dwell tier down and, when the tier hits zero, nudges `SEQUENCE_STATE` up by one. `tickPrescaledSequenceTimer` [seen] adds the outer tier: it counts `loc_4008` down each frame, and only when the sub-timer wraps does it reload it to 60 and then hand a single tick to `loc_4009` through the same cascade — so a state armed this way dwells 60× longer than a bare `loc_4009` tick would give it before the sequence advances.

Several handlers re-arm those timers rather than count them. `reloadSequenceDwellTimer` [code] stamps `loc_4009` back up to 80 (0x50) frames. `advanceSubstateAndReloadDwell` [code] does the pair-move a handler wants at the end of a step — bump the sub-state counter it is handed (its callers always hand it `SEQUENCE_STATE`) and then re-arm the dwell via `reloadSequenceDwellTimer`. `setSequenceStateByModeAndReloadDwell` [code] is the branching variant: instead of a plain increment it *jumps* the state counter to a fixed target — 4 when the mode bit `loc_4006` bit0 is set, 14 when it is clear — and then re-arms the dwell, letting a single flag pick which of two downstream sub-state clusters runs next. `enterSequenceStep1` [code] is the reset knee: it forces `SEQUENCE_STATE` to 1 and seeds the dwell pair to 3,3 (a 16-bit store of 0x0303 into 0x4008/0x4009), a very short countdown that immediately carries the sequence forward again — the mechanism by which the attract sequence, having reached its last index, folds back to the top.

### Boot: fill the screen, then latch the machine's configuration

Game-state 0, `fillScreenThenLatchConfigAndAdvanceState` [seen], is the cold-start handler and it is written as a per-frame worker rather than a one-shot. Each frame it blanks a 32-byte run of tilemap starting at the cursor `VRAM_WRITE_PTR` (0x400b) with the blank tile (16) and advances that cursor 32 bytes, so across successive frames it wipes the whole tile grid 0x5000–0x53ff while a per-state timer at `loc_4008` counts down. When that timer expires the machine's configuration is latched in one burst: the state cluster is reset (`loc_4007`=1, `loc_4006`=0, `GAME_STATE`=1 so the attract loop runs next, `SEQUENCE_STATE`=0); the number-of-lives/difficulty bits are folded out of the input shadows into `loc_4000` (top two bits of `IN1_SHADOW`), `loc_401f` (a bit of `IN2_SHADOW`), and the cabinet/flip bit into `loc_400f` (a bit of `IN0_SHADOW`); the coinage byte is selected from a four-entry ROM table (`loc_0152`) by the low two bits of the raw IN2 port `IN2_PORT` (0x7000) and stored at `loc_40ac`; the packed flag bitmask is unpacked; the object shadow and the three player-1 status glyphs (`PLAYER1_STATUS_VRAM` 0x5340 and neighbours 0x5320/0x5300) are seeded; and two deferred command words are queued. So boot both draws a clean field and reads the DIP/cabinet wiring into the RAM cells every later phase consults.

### The attract loop and the credit hand-off

In game-state 1, `runAttractSequenceAndAdvanceOnCredit` [code] first runs the shared per-frame formation prep, then dispatches on `SEQUENCE_STATE` across a bank of nineteen sub-state handlers (indices 0..18; two are duplicates and index 8 repeats index 2, index 17 repeats index 11), and finally tail-runs the credit check. This is where most of the assigned sequence handlers live. `initSequenceEnableStarfield` [seen] is sub-state 0's setup: it queues two setup command words, turns the starfield on (`STARS_ENABLE`, 0x7004), sets `loc_4007`, clears the per-sequence bookkeeping (`CURRENT_PLAYER` 0x400d, `loc_400e`, `loc_4006`, and the step-countdown cell `loc_4019`), seeds the dwell cascade to 96/16, and steps `SEQUENCE_STATE`. Sub-state 1 is `armStepCountdownAndTickSequenceTimer` [seen], which arms the one-frame countdown cell `loc_4019`=1 and then ticks the prescaled sequence timer so this state dwells on the slow tier. `activateDescriptorSlotsThenAdvanceSequence` [seen] and `queueColumnDrawAndAdvanceSequence` [seen] are the two "do a piece of drawing, then advance" states: both run the four shared subsystem updates and then count down the timers, but they re-arm and carry explicitly rather than by cascade. The first runs a two-phase countdown — on the `loc_4008` sub-timer's expiry it reloads that timer (to 0xd2), activates the descriptor slot named by the byte at `loc_4009`, and bumps `DRAWN_COLUMN_COUNT` (0x4241); then on the `loc_4009` dwell's expiry it advances `SEQUENCE_STATE`, again reloads 0xd2, and clears `loc_4058`. The second counts the `loc_4009` dwell down and, on expiry, advances `SEQUENCE_STATE`, re-arms the two-tier pair to sub=0x40 / tier=0x11, bumps `DRAWN_COLUMN_COUNT`, and enqueues a channel-6 column-draw command word (arg 0x0f). `dwellThenAdvanceSequence` [code] is the pure wait: it runs the same four subsystem updates and does nothing of its own but tail-tick the prescaled sequence timer, so it simply idles on the slow tier until the cascade carries `SEQUENCE_STATE` forward. Sub-states 11 and 17 are both plain `tickSequenceDwellTimer` dwells, and the last index, 18, is `enterSequenceStep1`, which snaps the sequence back to step 1 so the demo replays.

The exit from attract is not one of those sub-states — it is the tail every frame of `runAttractSequenceAndAdvanceOnCredit` runs after dispatching: `advanceGameStateOnCredit`. That routine reads the credit counter `loc_4002`, and while it is nonzero it increments `GAME_STATE` (moving 1→2, out of attract into the press-start screen) and clears the phase bookkeeping (`loc_4007`, `SEQUENCE_STATE`, two sound cells, and `MESSAGE_SCROLL_ENABLE`). So a coin's only structural job at this level is to make the credit count nonzero; the state machine notices on the next frame and steps the coarse selector.

### Press start, and launching a round

Game-state 2's `runStartScreenAndLaunchGame` [code] runs the formation prep and then dispatches `SEQUENCE_STATE` across just four start-screen sub-handlers, and — every frame, regardless of sub-state — tail-runs `beginGameOnStartButton` [code], the round launcher. That launcher watches the debounced input shadow `IN1_SHADOW`: bit0 (the one-player button) hands straight off to `startOnePlayerGame` [code]; bit1 (two-player) requires at least two credits, spends them from `loc_4002`, blits the 32-byte ROM row template `loc_051b` into the saved-state snapshot `SAVED_STATE_SNAPSHOT` (0x41a0), and — when config bit `loc_401f` bit0 is set — arms the state-advance gate before entering the round with the two-player spawn word. `startOnePlayerGame` is the credit-gated one-player path: with no credits left it falls back to forcing `GAME_STATE`=1 (back to attract); otherwise it spends one credit from `loc_4002`, zeroes the snapshot at 0x41a0, and enters the round start with a null spawn pointer. Both feed the shared round-start (which sets `GAME_STATE` to 3, i.e. player-one play).

### The play frames and their sub-states

Game-states 3 and 4 are the two play handlers, `runPlayerOnePlayFrame` [code] (a fresh board) and `runPlayerTwoPlayFrame` [code] (the restore-a-saved-board sibling). Both run the formation prep and then dispatch `SEQUENCE_STATE` across eight play sub-states; they share sub-states 0,1,3,4,5 and differ only at 2, 6 and 7, and at their terminals they trade off: player-one saves the current board into `PACKED_FLAG_BITMAP` (0x4180), sets `CURRENT_PLAYER`=1 and hands to game-state 4, while player-two saves into `SAVED_STATE_SNAPSHOT` (0x41a0), sets `CURRENT_PLAYER`=0 and hands back to game-state 3 — the two-player alternation.

Sub-state 0 of both is `initPlayfieldState` [code], the board setup: it turns both start lamps off (`START_LAMP_0`/`START_LAMP_1`), zero-fills four work-RAM spans (the flag block from `FLAG_BITS_BASE` 0x4100, the object-active/formation span from `OBJ_ACTIVE_FLAG` 0x4200, the `loc_4218` window, and a long run from `loc_4260`), clears `loc_425f`, sets `loc_4226`=1 (an activity gate, below), advances `SEQUENCE_STATE`, arms the dwell `loc_4009`=32, and points the VRAM cursor `VRAM_WRITE_PTR` back at `VRAM_BASE` (0x5000) for the row-blank state that follows. Sub-state 3 is `advanceSubstateAfterDwellAndQueue` [code]: it ticks the dwell `loc_4009` and, on zero-cross, reloads it to 20, advances `SEQUENCE_STATE`, and enqueues this state's command word.

Sub-state 2 is where the two frames split. On a fresh board `restoreFormationAndEnterPlaySubstate` [seen] unpacks the packed bitmap at `PACKED_FLAG_BITMAP` (0x4180) into the flag grid, copies the trailing 8-byte board template into `loc_4218`, clears the status/flip/direction cells (`loc_425f`, `loc_4220`, `loc_4018`), advances `SEQUENCE_STATE`, arms a 150-frame dwell in `loc_4009`, publishes a deferred-callback pointer (`loc_0640`) into `loc_4245`, and — when the sound gate `loc_4006` bit0 is open — cues the board-start sound (the paired-player burst `queueBoardStartSoundBurst` when `loc_400e` bit0 is set, otherwise a plain channel-5 prologue plus the standard burst). On a saved board `restoreSavedStateAndEnterPlaySubstate` [code] does the mirror image out of the *saved* snapshot `SAVED_STATE_SNAPSHOT` (0x41a0): unpack it into the flag block, copy its 8-byte template into `loc_4218`, clear `loc_425f`/`loc_4220`, and — this is the restore-specific part — when the flip flag `loc_400f` is set, mirror it into `loc_4018` and the display-flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y` (0x7006/0x7007) so the second player's screen orientation is honoured. It then advances `SEQUENCE_STATE`, arms the 150-frame dwell, publishes its own deferred pointer (`loc_0830`) into `loc_4245`, and enqueues a five-word intro cue when the sound gate is open.

Sub-state 6 is the other split, and it is gated. `stepPlaySubstate6` [code] (player one) reads the arm gate `loc_421d` and two mode flags, `loc_41b5` (the state-advance gate) and `loc_400e` (the paired-player flag). When `loc_421d` is set it either advances the sub-state and reloads the dwell (both mode flags set) or jumps the state by mode via `setSequenceStateByModeAndReloadDwell`; when `loc_421d` is clear it takes the shared reset tail `advanceDwellOrResetToState1` unless *both* mode flags are set, in which case it inlines the advance — bump `SEQUENCE_STATE`, arm `loc_4009`=130, and (when `loc_4006` bit0 is set) queue two channel-6 command words. `stepAltPlaySubstate6` [code] is the player-two mirror, keyed instead on the sub-state-advance gate `loc_4195`: closed gate delegates (to `setSequenceStateByModeAndReloadDwell` or `advanceDwellOrResetToState1`), open gate advances `SEQUENCE_STATE` inline and arms the dwell to 80 on the gated arm or 130 on the default arm, again queuing two channel-6 words when the sound bit is set. Both funnel through `advanceDwellOrResetToState1` [code], the shared tail that decides between *carry on* and *tear down*: with `loc_4006` bit0 clear it just advances the sub-state and reloads the dwell, but with the bit set it resets the whole phase — `GAME_STATE`=1, clear `loc_4006` and `SEQUENCE_STATE`, silence the sound hardware and halt the interrupt/starfield, and queue command word 6 — i.e. game over, back to attract.

The two gate cells those handlers test are set elsewhere by tiny arming helpers. `armStateAdvanceGate` [code] stamps the marker 3 into `loc_41b5` so `stepPlaySubstate6` reads it as "armed"; `armSubstateAdvanceGate` [seen] stamps the same marker 3 into `loc_4195` for `stepAltPlaySubstate6`. Both are pure one-byte writes whose only meaning is "nonzero," and the value 3 is a marker rather than a count.

### The command queue that carries the deferred writes

Nearly every handler above "enqueues a command word," and that queue is a small ring the sequence machine uses to defer sound and draw work. `enqueueCommandWord` [seen] takes a 16-bit word (a `(channel << 8) | param` pair the callers build) and, if the slot at the current write head is free — marked by bit 7 being set — stores the hi byte, then the lo byte in the next slot, advances the head by two, and floors the head at 0xc0 so the queue occupies the top of its page (base `loc_4000` + head, i.e. from 0x40c0 up) and never underflows into the config bytes below. The write head itself lives at `loc_40a0`. `commitQueueWriteHead` [seen] is the alternate persist path used by a different enqueuer: it writes the advanced head back to `loc_40a0` and returns through the shared stack epilogue `loc_090b` [code] — a deliberately-unnamed leaf that only restores the caller's saved pointer and returns, with no work-RAM effect. Two convenience builders sit on top: `enqueueCommandWordBurst` [code] posts a fixed five-word cue — two on the caller's channel and its neighbour, then two fixed cues on channel 7 — and `queueBoardStartSoundBurst` [code] prefixes that burst with a channel-5 prologue word, the board/level-start jingle the play-substate-2 handlers fire.

### Background timers layered over play

A handful of the assigned routines are not on the sequence spine at all but are free-running timers the play frames lean on, all guarded by the object-active enable `OBJ_ACTIVE_FLAG` (0x4200) bit0. `rampCounterToCeiling` [code] is a slow difficulty/pace ramp: while enabled and the inhibit flag `loc_422b` bit0 is clear, it runs a two-tier prescaler (outer `loc_4218` reloading 60, inner `loc_4219` reloading 20) and, on each double-wrap, steps the 0..7 counter `loc_421a` up by one, clamped at 7 — so it climbs to a ceiling and stays there (a fresh stage elsewhere zeroes `loc_421a` to restart the climb). `scheduleDelayedEvent` [code] is a guarded two-tier timer that arms a delayed-event triple: it bails unless `OBJ_ACTIVE_FLAG` and `loc_41ef` bit0 are both set and the inhibit `loc_422b` is clear, then, on the mode bit `loc_4006`, either arms a fixed triple on a full outer(`loc_4245`,60)/inner(`loc_4246`,5) cascade elapse — `DELAYED_EVENT_TIMER` (0x422f)=90, `loc_424a`=45, `DELAYED_EVENT_ARMED` (0x422e)=1 — or, in the derived mode, computes a payload from `loc_4221` or the byte-sums of the word cells at `loc_4177` and `loc_421a` and fans it into the same triple through bit-rotations. (Note that `loc_4245`/`loc_4246` do double duty: the play-substate-2 handlers publish a 16-bit deferred-callback pointer there, while this timer reinterprets the same two bytes as its outer/inner prescaler during active play.) `fireDelayedEventRequest` [code] is the one-shot that fires it: while `DELAYED_EVENT_ARMED` is set it counts `DELAYED_EVENT_TIMER` down each frame, and on the zero tick it disarms itself and — only if `OBJ_ACTIVE_FLAG` and `loc_41ef` are both still set — raises `DELAYED_EVENT_REQUEST` (0x4229) for the consumer to act on. `expireActivityGatedTimer` [code] is a countdown that only advances while the field is busy: with its arm flag `loc_422b` bit0 set and at least one activity gate open (`loc_4224` nonzero, or `loc_4221` nonzero, or `loc_4226` bit0 set — the same `loc_4226` `initPlayfieldState` primes to 1), it ticks `loc_422c` and clears the arm flag once the counter reaches zero, ending an activity-gated timed phase. `armBehaviorGateOnInputOrTimer` [code] arms a behavior gate `loc_4208`: skipping when the enable bit is clear or the gate is already armed, on the timer path (`loc_4006` bit0 clear) it arms only when the low five bits of the frame-phase counter `loc_425f` are zero (roughly every 32 frames), and on the input path (`loc_4006` bit0 set) it tests bit 4 of the selected input shadow — `IN0_SHADOW`/`IN1_SHADOW` picked by `loc_4018`, masked against its guard `loc_4013`/`loc_4014` — and, when active, arms both `loc_4208` and its companion `loc_41cc`. `clearGateOnPendingRequest` [code] is the acknowledger for that gate: when the request flag `loc_420b` bit0 is pending it consumes it (clears `loc_420b`) and clears the behavior gate `loc_4208` back down.

### A small clamp helper on the edge of this set

Finally, `markValueOutOfRange` [code] belongs to a tile-variant fold rather than to the sequence spine: it is the out-of-range arm of a clamp (its sole caller folds the frame-phase counter `loc_425f` into a two-bit tile variant), snapping the fold index to the fixed 0x80 saturation sentinel when the input is beyond range. It is included here only because it shares the neighbourhood; structurally it is a one-line saturation stamp, not a state or timer step.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

Galaxian's enemies live as a standing formation of aliens plus a handful of loose "objects" that peel off it to dive. The machine keeps that whole picture in a few overlapping work-RAM structures: a bit-per-cell **formation grid** at `FLAG_BITS_BASE` (0x4100), reductions of that grid into per-row and per-column summaries, a set of 32-byte **object records** that carry the live divers, and a small pile of sweep, pacing, and trigger cells that make the formation breathe and shed attackers. This section follows how those pieces are seeded, summarised, swept, drawn, and finally spawned and launched.

### Two interleaved tables, seeded from ROM

Two distinct stride-2 tables sit near the top of work RAM and are easy to confuse because both are written "every other byte". The first is an **object-shadow field** based at `loc_4021` (0x4021, 0x4023, …, 0x405f). `seedObjectRamShadowField` [seen] is the primitive that fills it: given a source pointer it copies 32 consecutive ROM bytes into those 32 interleaved destination cells, one byte per cell. `seedObjectShadowFromRom` [seen] is the fixed-source wrapper — it hands `seedObjectRamShadowField` the ROM template at `STRIDED_TABLE_SRC` (0x1d71) and runs it, which is how the shadow field is (re)initialised at screen and formation init.

The second table is a nine-cell **strided per-column table** based at `loc_4028` (0x4028, 0x402a, …, 0x4038). `broadcastToStridedTable` [seen] writes one byte across all nine cells; `clearStridedTable` [seen] is just that primitive called with zero, a per-state reset. This table is the target of the sweep code below: `broadcastNegatedSweepToStridedTable` [seen] takes a low byte, two's-complements it, and broadcasts the result across the nine cells, and `broadcastNegatedFormationSweepToStridedTable` [code] is the same thing sourced from the live formation anchor — it reads the low byte of the swept word at `loc_420e` and negates-and-broadcasts it. So every column of the formation shares one signed horizontal offset, republished each time the sweep moves.

### The formation sway (sweep oscillator)

The whole formation's side-to-side drift is `advanceFormationSweepOscillator` [seen]. It carries a 16-bit swept word at `loc_420e` and a direction flag `OBJ_SWEEP_DIRECTION` (0x420d). One frame in four (a throttle on the low two bits of `loc_425f`) it steps the swept word one unit toward the bound pair held in `FORMATION_X_BOUNDS` (0x4210): while ascending it counts up until it reaches the low-byte (from-right) bound and then calls `setSweepDescending` [seen] to flip the flag to 1; while descending it counts down until it passes the high-byte (from-left) bound and calls `setSweepAscending` [seen] to clear the flag back to 0. The word's sign lives in its high byte's top bit, which is how the turn-around comparisons stay correct across the zero crossing. After each real step it republishes the negated low byte across the strided per-column table. There is also a leading proximity shortcut: if the player shot is armed (`loc_4208` bit0), its position `loc_4209` sits in a narrow window, and the swept column reads occupied in `COLUMN_OCCUPANCY`, the routine skips the stepping entirely and just re-broadcasts the current anchor via `broadcastNegatedFormationSweepToStridedTable`. The oscillator is run once per frame from each of the play/attract loops.

Notice that `loc_420e` does double duty: it is both the thing the sweep oscillates and the moving Y anchor the positioning code reads (below). Oscillating one 16-bit word is what makes the entire formation appear to slide as a rigid body.

### Reducing the grid: occupancy summaries and bounds

`summarizeFormationOccupancy` [seen] is the once-per-frame reduction of the formation. It reads the occupancy grid at `OCCUPANCY_GRID` (0x4123) as six rows of ten columns (rows 16 bytes apart) and folds it two ways. Per-row ORs land in `ROW_OCCUPANCY` (0x41e8) behind two always-zero guard cells; per-column ORs land in `COLUMN_OCCUPANCY` (0x41f0) behind three guards. From the column summaries it then derives the horizontal sweep limits: it scans inward from the rightmost occupied column, adding sixteen per empty column onto a base of 34, and inward from the leftmost, subtracting sixteen per empty column from a base of 224, packing the two results into `FORMATION_X_BOUNDS` (low byte = from-right, high byte = from-left) — the exact pair the sweep oscillator turns around on, so the formation's travel automatically tightens as its edges are cleared. Finally it folds four region-"clear" flags, each the OR of some cells XOR'd with 1 (so the flag reads *set* when the region is empty): `loc_4221` from the top four rows, `loc_4220` from all six rows, `loc_4226` from seven `OBJ_TABLE` (0x42d0) slots at 32-byte stride, and `loc_4225` from those OR'd with eight slots based at `loc_42b1`. Those clear flags are the gates the launch, stage-advance, and pacing logic consult.

### Packed grid cell to sprite position

Each object record carries a packed grid cell at record+7, and `positionObjectFromGridCell` [code] unpacks it into the two position fields the sprite builder reads. The display axes are rotated ninety degrees from the formation grid, so the *row* bits (cell & 0x70) drive the X field at record+3 — a fixed origin of 124 minus three-quarters of the row value — while the *column* bits (cell & 0x0f) drive the Y field at record+4, computed as the current anchor `loc_420e` plus sixteen per column plus a seven-pixel hotspot. Because the anchor is the swept word, a formation alien's Y follows the sway for free.

### Packing and unpacking the flag block

The 128-cell formation grid is a byte-per-flag expansion of a compact 16-byte bitmask, and two inverse primitives move between the forms. `unpackBitmaskToFlagBytes` [seen] reads sixteen packed bytes and writes 128 one-byte flags at `FLAG_BITS_BASE`, LSB-first, one for each set bit and zero for each clear one, returning the source pointer advanced past the mask so a caller can read the data that follows it. `packFlagBytesToBitmask` [code] is the exact inverse: it reads bit0 of the 128 flag bytes and packs them LSB-first into sixteen destination bytes, returning the destination advanced sixteen so a caller can chain a block copy after it.

Those primitives feed the two player-switch terminals. `packFlagsToBitmapAndSwitchPlayerState` [code] and `saveFlagsToSnapshotAndSwitchPlayerState` [code] are mirror-image state handlers: each ticks the mid-tier dwell timer `loc_4009` and does nothing until it expires, then clears `SEQUENCE_STATE` (0x400a), packs the live flag block, and copies an eight-byte template that trails it. The first packs into `PACKED_FLAG_BITMAP` (0x4180), copies the template from `loc_4218`, sets `CURRENT_PLAYER` (0x400d) to 1 and `GAME_STATE` (0x4005) to 4; the second snapshots into `SAVED_STATE_SNAPSHOT` (0x41a0), sets `CURRENT_PLAYER` to 0 and `GAME_STATE` to 3. Together they hand the compressed formation and its companion state back and forth as play alternates between the two players.

### Seeding the field at sequence boundaries

Several sequence-state handlers rebuild the field from ROM. `clearFlagBlockAndReseedObjectShadow` [code] zero-fills the 128-byte flag block, clears the status bytes `loc_425f` and `loc_4238`, arms the dwell `loc_4009` to 64, then advances the sequence and reseeds the shadow field via `advanceSequenceStateAndReseedObjectShadow` [code]. That helper advances the counted byte just past the dwell timer — both callers arrive pointed at `loc_4009`, so bumping the next in-page byte increments `SEQUENCE_STATE` — and falls through into `seedObjectShadowFromRom` to relay the ROM template into the shadow field. `loadDescriptorAndAdvanceSequence` [code] is the richer variant: it unpacks a packed descriptor bitmask from ROM at `loc_051b` into the flag block, copies the eight-byte template that follows into `loc_4218`, clears `loc_425f`, sets `loc_421d` to 1, advances `SEQUENCE_STATE`, stamps `VRAM_WRITE_PTR` (0x400b) to 150, and publishes the deferred-callback pointer `loc_0640` into `loc_4245`.

`activateDescriptorSlot` [seen] initialises one 32-byte slot in `DESCRIPTOR_SLOT_TABLE` (0x4330): the descriptor *number* at the passed pointer minus one selects the slot, and the routine stamps its active flag [0]=1, [1]=0, [2]=13, [4]=0, [5]=12, and [7]=index while leaving [3] and [6] alone. Its caller passes the descriptor number held at `loc_4009` and then bumps `DRAWN_COLUMN_COUNT` (0x4241), so descriptor slots are drip-activated one per timer expiry during that attract state.

### Staging objects to sprites

`stageObjectsToSpriteShadow` [seen] is the per-frame bridge from object records to hardware sprites. It walks eight consecutive object records from `SPRITE_SOURCE_OBJ_BASE` (0x42b0) at 32-byte stride and renders each into eight consecutive four-byte records at `SPRITE_SHADOW_BASE` (0x4060), laid out as a band of three then a band of five. The Y offset applied to each band is chosen by the orientation bit `loc_4018` bit0: flipped, the first band uses offset 9 and the tail 8; unflipped, 7 and 8 — both orientations settle the tail at 8.

### The object-AI handlers

The eight object slots are driven once per frame; each record's state index at record+2 selects a handler, and three of those handlers belong to this subsystem. State 0 is `initSpawnedObjectFromGridCell` [code], the first-tick setup of a freshly launched attacker: it clears the step timer at record+23, raises the spawn flag `loc_41c2`, derives the sprite position from the packed cell, and posts a type-1 spawn command into the event queue. It then looks up the object's sprite number and flight-curve seed from `SPAWN_RECORD_TABLE` (0x1dd1) indexed by the cell's row bits; when those bits are all set (the top row) it uses attribute base 24 and tallies how many of its two neighbour slots are active into `ACTIVE_NEIGHBOR_COUNT` (0x422a), otherwise attribute base 0. Both paths seed the motion counters (throttle=3 at record+16, leg=12 at record+17, cursor=0 at record+19), advance the state, and set the signed heading at record+5 to ±12 from the direction bit at record+6.

State 5 is `reseedFormationObjectState` [code], which re-homes an alien back into the standing formation. It resets X to the left edge (record+3=8), zeroes the heading, and ticks the leg counter at record+23. If the packed cell's high bits are *not* all set it takes the reseed-and-advance path: gated on the subsystem being enabled (`OBJ_ACTIVE_FLAG` 0x4200 bit0) and an activity gate open (`loc_4224` or `loc_4221` nonzero), it rolls a fresh random Y into record+4, arms the hold timer at record+16 to 40, and advances the state an extra step. If the high bits *are* all set it treats the record as a formation sentinel: while `ACTIVE_NEIGHBOR_COUNT` is nonzero it recounts the two neighbour slots and reseeds, but once no neighbours remain it deactivates the object (record+0=0) and ramps the phase/difficulty counter `loc_421e` up toward a ceiling of 2.

State 6 is `settleObjectIntoFormationCell` [code], which parks a returning diver in its grid cell. It bumps the frame counter at record+3, repositions from the packed cell (which overwrites that same field with the target value), and compares the two: when the running counter has caught the target it deactivates the object, marks that cell live in the flag block, and posts its command word; a small even shortfall nudges the phase at record+5 by the direction bit, while a large (≥25) or odd shortfall is left to keep counting.

Two small helpers round out the object-AI side. `bumpCountIfNeighborsInactive` [code] peeks the two look-ahead slots at base+32 and base+64 and returns the running count incremented only when both are inactive, which the scoring path uses to tell whether a kill emptied a formation column. And `noopAnimDispatchSlot` [code] is the do-nothing terminal (sub-state 3) of the deactivated-object animation dispatch, present only so that table has a valid final entry. The tiny unnamed `loc_090b` is the shared stack epilogue at the end of the command-enqueue path — it restores the caller's saved register and returns with no work-RAM effect, so it is worth noting only as plumbing between the enqueue helpers.

### Pacing and launching attackers

Attackers are metered out by a two-stage timer. `paceEnemyLaunchTrigger` [code] runs only while the subsystem is enabled and both inhibit flags (`loc_4220`, `loc_422b`) are clear. It computes a span from the pace counter `loc_421a` plus the stage `loc_421b` (the latter only once it reaches 2), masked to a nibble and plus one. It ticks a master counter at `loc_424a`; until that expires it simply clears the refill flag `SUBCOUNTER_REFILL_FLAG` (0x4228) and stops. On expiry it reloads the master from `SUBCOUNTER_RELOAD_TABLE` (0x15e3) and sweeps that many attacker sub-counters, decrementing each and refilling any that hit zero from the matching table entry; if any refilled, it raises the refill flag. That flag is the one-shot the launcher consumes.

`launchAttackerFromFormation` [code] fires exactly when the refill flag is set (and consumes it), and only while the region-clear gate `loc_4220` is clear. It derives a one-to-four slot budget by folding the sum of the pace counter and stage right one bit and capping at three, then claims the first object slot whose two lead bytes are both zero, scanning downward from `loc_4391` at 31-byte stride. It stamps the shared launch direction `loc_4215` into the slot's field 6, which also picks the column-scan orientation, and searches `COLUMN_OCCUPANCY` for an occupied column from the appropriate end. The sweep-mode flag `loc_41ef` then selects the grid geometry, and the routine walks up that column of `FLAG_BITS_BASE` looking for a filled cell. On a hit it clears the formation cell, records the cell's low byte into the slot, activates the slot at state 0, and enqueues a type-1 spawn command — one standing alien peels off and becomes a diver. The launch direction itself is chosen upstream by `chooseNextAttackerDirection` from the anchor's sign and its distance to the bounds.

### Player shot versus formation

`flagPlayerShotHitOnFormation` [code] is the per-frame collision of the single player shot against the standing formation. While the shot gate `loc_4208` bit0 is armed, it bands the shot's Y position `loc_4209` into a formation row (rejecting shots above the top or in the gaps, using the same seven-then-five row pitch the layout uses) and bands the shot's X offset from the anchor — `loc_420a` minus `loc_420e` — into a column, rejecting anything outside the hit window. It nibble-swaps the row and column into a grid index, and if that `FLAG_BITS_BASE` cell holds a live alien it clears the cell, posts a kind-1 command word carrying the grid index, stamps a hit record (`loc_420b`=1, `loc_42b1`=1, `loc_42b2`=0, and the shot's position word into `loc_42b3`), and posts a second kind-3 command word carrying a column code derived from the index — registering the kill and queuing its scoring and sound events.

### Spawning secondary objects and delayed events

A cluster of routines handles bulk spawning off trigger-flag blocks. The shared seeder is `activateObjectSlotAndEnqueueSpawn` [code]: it consumes the trigger flag at the pointer it was handed (writing 0), marks the object slot active with a cleared phase, records the spawn code into field 6 and the trigger pointer's low byte as the source index into field 7, and enqueues a type-1 spawn command keyed by that index, returning the pointer unchanged so the caller can read its low byte back. `spawnSecondaryObjectIntoSlot` [code] is the per-slot variant used for companions: it bails if either of the target slot's two live flags is already set, otherwise consumes the trigger, marks the slot alive, clears its state, inherits field 6 from a source record, stashes the trigger index, and enqueues its activation word. `spawnIntoFreeDescriptorSlot` [code] is the free-slot finder that scans the four descriptor slots at `DESCRIPTOR_SLOT_TABLE` high-to-low for one whose two guard bytes are both zero and seeds it through the shared seeder.

Those combine in the walk helpers. `spawnSecondaryObjectAndAdvanceWalk` [code] spawns into the current slot, steps the slot pointer forward by 32, decrements the budget, and — when the budget is spent — forces the caller's loop counter to 1 so the walk ends after that pass. `spawnPrimaryAndSecondaryObjects` [code] spawns a primary into `OBJ_TABLE`, then walks three trigger flags backed up fifteen from the primary trigger's low byte, spawning a secondary into each following slot for every set flag until a budget of two is spent. `spawnObjectsFromTriggerFlags` [code] scans the four flags of `PRIMARY_TRIGGER_BLOCK` (0x4176): the first set flag spawns a primary plus up to two secondaries drawn from `SECONDARY_TRIGGER_BLOCK` (0x4165) at the same offset; if no primary flag is set it scans the secondary block and instead seeds a free descriptor slot on the first hit.

The whole thing is triggered per frame by `spawnObjectsOnDelayedEvent` [code]. It is gated on the region-clear flag `loc_4220` being clear, the subsystem enabled via `OBJ_ACTIVE_FLAG`, and a pending `DELAYED_EVENT_REQUEST` (0x4229) bit0 that it consumes as a one-shot, and it holds off unless the `OBJ_TABLE` head word is even. Then the launch direction `loc_4215` bit0 routes the work: set, it runs the full trigger-block spawn; clear, it scans the primary trigger block high-to-low for a set flag to spawn a primary plus secondaries, then falls back to the secondary window (fifteen below the primary block) to seed a free descriptor slot.

### Advancing the stage and rebuilding the formation

Finally, two routines advance the game between formation waves. `armFormationAdvanceTrigger` [code] is a gated one-shot: only when both region-clear gates `loc_4220` and `loc_4225` read set (their bit0), and the pending word `loc_4222` is not already armed, does it write the 16-bit `loc_4222` to 1 — enable byte 1, countdown byte `loc_4223` zeroed. `advanceStageAndReseedFormation` [code] consumes that armed one-shot: it fires when the enable bit is set and the countdown decrements to zero, then disarms the enable, rebuilds the 128-flag formation block from the packed template at `loc_051b`, resets the pace counter `loc_421a` and `loc_425f`, reseeds the formation anchor `loc_420e` to 1, and steps the stage selector `loc_421b` — its high byte counting up while its low byte advances but saturates at 7. It enqueues a command word from `loc_0700` and then services a pending two-slot request read from `loc_421e` (the same phase counter that `reseedFormationObjectState` ramps up): a nonzero value raises the first request slot `loc_4177`, and a remaining count raises the second `loc_4178` before the counter is cleared. That is the seam where clearing the field arms a new stage, and the difficulty the field accumulated becomes the number of extra attackers the next formation is asked to field.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

Everything in this subsystem hangs off one per-frame driver, `runGameplayFrameAndAdvanceOnFieldClear` [code], which is the beating heart of a live playfield. Each frame it runs the same fixed sequence of subsystem updates — move the ship and stage its sprite, service the player shot, integrate the enemy shots, walk every object's AI, stage the sprites, arm the behaviour gate, run all four collision sweeps, service the spawner/launcher/pace machinery, drive the play-phase sound voices, and recompute the demo-mode ship command — and only *after* all of that does it look at whether the field has gone quiet. The quiescence test is deliberately conservative: it bails unless bit0 is clear in every one of the shot/behaviour gate `loc_4208`, the death-in-progress flag `loc_4201`, and the object-subsystem master enable `OBJ_ACTIVE_FLAG` (0x4200); *and* the stage-advance side flag `loc_4225` bit0 is set; *and* none of the fourteen five-byte enemy-shot records based at `loc_4260` (0x4260) still has its active bit0 set. Only when the board is genuinely empty of live bullets and attackers does it tick the sequence dwell timer `loc_4009` and, on the tick that reaches zero, bump `SEQUENCE_STATE` (0x400a) to move the game on to the next board phase. So "you cleared the wave" is defined here, mechanically, as "nothing on the field is moving any more."

### The player ship and its demo-mode autopilot

The ship's horizontal position is a single byte, `loc_4202` (0x4202) — and this is the load-bearing cell of the whole subsystem, because the same byte doubles as the *aim target* every enemy reads. `moveControlledObjectAndStageSprite` [code] owns it. When the object subsystem is enabled (`OBJ_ACTIVE_FLAG` bit0 set) it chooses its movement bits three ways: with the play/attract mode flag `loc_4006` bit0 clear it takes the autopilot command `OBJ_MOVE_CMD` (0x423f); otherwise it reads a hardware input shadow — `IN1_SHADOW` (0x4011) when the direction flag `loc_4018` bit0 is set, else `IN0_SHADOW` (0x4010). Bit3 of the command steps the position down while it is above the floor 23, bit2 steps it up while below the ceiling 233, so the ship slides one pixel per frame and can never leave its rail. It then stages the position as four interleaved (value, code) pairs into `OBJ_STAGE_BLOCK` (0x4054), the value being a one's-complement-plus-128 fold of the coordinate and the code 6. If the ship is instead inactive but the death flag `loc_4201` bit0 is set, it stages the current position under code 7 (the death pose) without clamping; if fully inactive it parks the position at 0. 

In attract mode the ship flies itself, and `computeControlledObjectMoveCommand` [code] is the autopilot that fills `OBJ_MOVE_CMD`. It fires only on one frame in thirty-two (gated on the free-running frame counter `loc_425f` phase) and only while both `loc_4007` bit0 and `OBJ_ACTIVE_FLAG` bit0 are set. It sums a "where is the danger" weight across both object tables — the eight-slot table walked from `OBJ_TABLE` (0x42d0) and the fourteen-entry shot table at `loc_4260` — then folds in a scaled offset between the formation anchor `loc_420e` and the ship, halves it, adds a random ±1 nudge, and buckets the signed result into 0 / 4 / 8, the very bits `moveControlledObjectAndStageSprite` reads. The per-object weighting is `accumulateObjectPositionWeight` [code]: it contributes nothing unless the object is active, its Y sits in one of two 52-row bands measured from 128, and its X delta from the ship falls in the near half; when it does qualify it folds the object's flag bit7, X-delta bits 5–6, and band into a 0–15 index and adds the signed step `OBJ_STEP_TABLE[idx]` (0x1a45) to the running total. The net effect is a crude threat-avoidance demo brain that leans the ship away from clustered attackers.

### The player shot

The single player bullet is a small state block. `advancePlayerShot` [code] reads its gate at `loc_4208`: while bit0 is armed it drains the position counter `loc_4209` by four each frame and raises the retire flag `loc_420b` — but note the subtle current fact, confirmed by the machine's two chained subtractions of 14 then 4: the flag is raised only when the drained counter lands in the narrow band [14,17], not merely "near zero." Because the counter is reset to 220 and always steps by four, it passes cleanly through that band as the shot reaches the top of its travel. When the gate is clear the routine re-parks the shot: counter back to 220 and the X field `loc_420a` seeded from the ship X `loc_4202` (or zeroed if the object subsystem is off), so the next shot launches from wherever the ship is standing. `advancePlayerShotAndStageSprite` [code] wraps that: it runs the shot service, then reads the {counter, field} pair back as a coordinate and writes the two sprite render cells `loc_409f` and `loc_409d`, complementing the field and picking one of two low-byte X formulas by the direction flag `loc_4018` bit0 (counter−1 when set, ~counter+252 when clear).

### The enemy object subsystem — birth, driving, and death

A play phase begins in `activateObjectsAndBeginPlayPhase` [code], the state-timer handler that, on its dwell expiry, flips `OBJ_ACTIVE_FLAG` on, centres the ship reference `loc_4202` at 128, refills the sixteen-byte enemy-launch sub-counter block at `loc_424a` from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears scratch cells `loc_4058`/`loc_405a`, and queues its display commands. The complementary cold reset is `resetObjectRamAndAdvanceSequence` [code], which reseeds the interleaved OBJRAM shadow from ROM template `loc_1d91`, zeroes the 64-byte sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad object-record region from `loc_4260`, clears the message-scroll enable `MESSAGE_SCROLL_ENABLE` (0x40b0) and the status cell `loc_4238`, and advances the sequence.

Every frame `driveAllObjectSlots` [code] walks the eight object records based at `SPRITE_SOURCE_OBJ_BASE` (0x42b0) on a 32-byte stride, handing each to `driveObjectSlot` [code]. That per-slot driver reads the record's flags and state: if the death-animation flag (record+1 bit0) is set it hands the record to the death-animation dispatcher; if the active flag (record+0 bit0) is clear it skips the slot; otherwise it selects one of sixteen AI handlers by the state byte record+2. The sixteen states form the attacker life-cycle — spawn-init at 0, the path walk at 1, the actor move-planner at 2, powered flight at 3, the dive at 4, formation reseed/settle at 5/6, X-homing at 7, the arm-window at 8, homing flight at 9, the descending path walk at 10, a path-walk alias at 11, a move-run restart at 12, phase-step init at 13, a message-column emitter at 14, and the at-rest settle at 15.

A dying object routes instead through `dispatchDeactivatedObjectAnim` [code], which reads the record's animation sub-state (record+2 again, now interpreted 0–3) and hands off to the matching phase handler; whatever the handler returns is the dispatcher's result. Sub-state 1 is `tickDeactivatedObjectAnim` [code]: it counts a fast field (record+16) down, reloading it to 4 and bumping a companion (record+18) on each elapse, then a slow field (record+17); when the slow field elapses it either retires the object by clearing its state byte record+1, or — if the object's position field record+7 has reached 112 — reloads the fast field to 50, seeds the companion from the global `loc_422d` plus 32, and advances the sub-state. Sub-state 2 is `endObjectAnimOnTimerExpiry` [code], a plain countdown of record+16 that clears the state byte record+1 to retire the actor on the frame it hits zero. Note the record+1 dual role: the same bit0 that marks "dying" also tells `renderObjectSprite` to draw the fixed explosion sprite, so the death animation and its visual are the same flag.

### Object-AI motion: paths, dives, and flight curves

The standing-formation-to-attack motion is driven by a family of path-walkers reading the ROM step table `PATH_STEP_TABLE` (0x1e00). `advanceObjectPathStep` [code] (state 1) walks a per-object cursor (record+19) through the table two bytes at a time, adding the first delta to record+3 and the second, direction-controlled by record+6 bit0, to record+4; if the X field (plus a 7px margin) crosses the near screen edge it forces the object into the fall-away state 5, otherwise it advances the cursor, ticks a throttle (record+16, reload 4) and on throttle expiry nudges the cross-step record+5 and ticks the leg counter record+17, advancing the dispatch state when a leg finishes. `advanceObjectPathStepDescending` [code] (state 10) is the mirror that *subtracts* the X and Y deltas and reloads the next leg with heading 12; when its direction bit record+6 bit0 is set it hands the Y half to `advanceObjectPathStepAscending` [code], the mirrored arm that adds the step-table byte to record+4, ticks the same throttle/leg counters, and on a finished leg reloads throttle 3 / leg 12 / heading 244 / cursor 0. `advanceObjectPathStepAlias` [code] (state 11) is a bare trampoline that forwards to `advanceObjectPathStep` unchanged — a second slot for the same walk.

The signature Galaxian swoop is `advanceObjectDiveStep` [code] (state 4) sitting on top of `advanceObjectFlightCurve` [code]. The flight curve is a cross-coupled fixed-point rotation over two 16-bit accumulators held in the record (hi/lo at record+0x19/+0x1b and +0x1a/+0x1c): it runs ((record+0x18 seed)&3)+1 integration steps, each adding twice the *other* accumulator's sign-extended high byte into this one, with a guard that treats a resulting high byte of exactly 128 as overflow and reverts that step. The accumulators' high bytes become the swoop offset. `advanceObjectDiveStep` steps the dive position record+3 by one or two (alternating on the frame-parity bit `loc_425f`), and if it lands in the [6,9) window bumps the state; otherwise it runs the flight curve and folds the curve heading (record+0x19) plus the per-object increment (record+9) into a new screen Y (record+4), bumping the state instead when the sum crosses the signed boundary — i.e. when the swoop runs off the bottom of the screen.

Powered flight is `advanceObjectFlightAndFire` [seen] (state 3): it bumps the object counter record+3, runs the flight curve, then sets screen Y = per-object increment + curve heading; a Y that has climbed too high advances the state by two, a wrapped-out counter by one, and otherwise — gated by `OBJ_ACTIVE_FLAG` — it aims at the target and, unless the delayed-event inhibit `loc_422b` bit0 is set, scans the row table at `loc_4213` for its counter value and fires when a row matches. `advanceHomingObjectFlightAndFire` [code] (state 9) is the same shape with a column-homing pre-step keyed on the mode byte record+0x17: mode 4 homes only on odd frame parity, mode above 4 always, mode below 4 never; it nudges the column record+9 one step toward the ship column `loc_4202` before computing Y, and its too-high / counter-out arms drop to states 5 and 4 respectively. Pure horizontal homing is `homeObjectXTowardPlayer` [code] (state 7): it steers the object's 16-bit X:subpixel pair (record+4 high, record+9 low) by roughly four times the signed distance to `loc_4202` each frame, carrying a small rounding bias, and advances the state when the dwell timer record+16 drains. When an attacker finally comes to rest, `settleObjectXAtRest` [seen] (state 15) nudges record+4 up one count per frame until it lands within 5 of the rest value 200, then holds. `initObjectPhaseSteps` [seen] (state 13) is a phase entry that derives a step count n = (~record+7)&3, writes n+1 to record+22 and a derived code byte to record+3, arms the phase timer record+16 to 24, advances the sub-state, and arms the ready flag record+15 only when n is zero.

### Horizontal target planning

Several states share a small planner that decides where an attacker should slide to horizontally. The primitive is `commitMoveToTargetX` [seen]: given a chosen target X it stashes it at record+0x19, stores the signed move delta (current X record+4 minus target) at record+9, zeroes the three-byte move accumulator at record+0x1a, and advances the planner sub-state record+2. `commitMoveAcrossPlayerX` [code] is the usual target picker: it takes the gap between the actor's X (record+4) and the ship reference `loc_4202`, halves it, biases by 16, and clamps to the band on the *opposite* side of the ship — 144–208 when the actor is left of the ship (aim right), 48–112 when at or right (aim left) — then commits that target. `commitMoveToStoredOrPlayerTargetX` [code] chooses between two sources: if the `OBJ_TABLE` (0x42d0) mode flag bit0 is set it steers toward that table's stored target X (its record+0x19), otherwise it runs the ordinary cross-ship pick. `advanceActorPhaseAndCommitMove` [code] (state 2) bumps the actor's phase counter record+3, then routes by the kind field: when (record+7)&0x70 equals 0x60 it uses the stored/player select, else the plain cross-ship select. `beginObjectCrossPlayerMove` [code] is the shared tail that commits a cross-ship move and then arms the object for the run — flight-curve step seed record+0x18=3 (four curve steps) and move throttle record+0x10=100. `armDirectedMoveWhenInWindow` [code] (state 8) ticks the arm counter record+3 and, while either it or the position record+4 is outside the [96,160) window, keeps cruising via `beginObjectCrossPlayerMove`; once both are in-window it advances the state by two, seeds move timers record+0x10=3 / record+0x11=12, clears record+5/record+0x13, and sets the direction record+6 from the ship-reference compare. `restartObjectMoveRun` [code] (state 12) simply bumps record+3, forces the state back to 8, and re-enters the cross-ship move — a way to loop an attacker back into the arm-window behaviour.

### Aiming and firing enemy shots

When a flying attacker is eligible to shoot it first aims. `aimObjectAtTarget` [seen] derives a direction octant from the vertical drop to the sprite (0xf0 − record+3) and the horizontal delta to the ship anchor `loc_4202`, mirroring the octant when the target is to the left, and stores it in the object's direction field record+5. The slope-to-octant conversion is `computeDirectionOctantFromSlope` [seen]: it divides dividend by divisor, clamps a top-bit-set (steepest) quotient to 0x80, and returns the top three bits as a 0–7 octant. On a firing-row match the flight handlers call `spawnAimedProjectileAtPlayer` [code], which claims the first free slot in the fourteen-entry table at `loc_4260` (stride 5, entry[0] bit0 = active), marks it active, copies the object's sprite Y and X into entry[1]/entry[3] (entry[2] untouched), and stores a scaled X velocity into entry[4] aimed at the ship, mirrored when the ship is to the left. The velocity comes from `computeJitteredXVelocity` [code]: it divides the horizontal slope, adds a bounded PRNG draw (0–31) plus a floor of 6, and clamps to 0x7f on positive overflow — so enemy bullets fan toward the player's column with a little random spread.

### Attacker scheduling helpers

Two small routines feed the launch machinery. `selectAttackerRowScan` [code] seeds a slot/base pair from the alt flag `loc_421b` (nonzero → slot 2 / base 157, else slot 1 / base 132), scans up to four two-byte slots of `ROW_OCCUPANCY` (0x41e8) advancing only while neither byte of a slot has bit0 set, and stores the resulting (slot index, base) pair into `loc_4213` — exactly the row table the flight handlers scan when deciding whether to fire. `chooseNextAttackerDirection` [code] sets the shared launch/curve direction flag `loc_4215`: the 16-bit formation anchor `loc_420e`'s sign picks which `FORMATION_X_BOUNDS` (0x4210) edge to measure the gap against, and within 28px of that edge the flag is forced away from the edge, otherwise a fresh random bit decides it.

### Sprite rendering

`renderObjectSprite` [seen] builds one hardware sprite record (Y, attr, sprite#, X) from an object struct. An active object (record+0 bit0) copies its sprite number from record+0x16, sets X = objX(record+3) − 8 and Y = complement(objY, record+4) − a Y offset, and folds the signed heading record+5 into a display attribute: the fold rotates the angle by whole 24-count sectors into a small range, maps it to a facing attribute added onto the base attr record+0x0f, and applies a one-pixel nudge on the diagonal cases. A secondary-active object (record+1 bit0) instead uses the fixed sprite number 7 and the alternate attribute record+0x12 — this is the explosion/death frame. With both flags clear the sprite is parked off-screen at (248, 248).

### Collisions and the hit response

Four sweeps run every frame from the pipeline. `flagPlayerShotHitsOnObjects` [code] fires only when the shot gate `loc_4208` bit0 is armed, box-testing the shot reference {`loc_4209`,`loc_420a`} against each of seven object records walked from `OBJ_TABLE` (0x42d0) on a 32-byte stride via `flagPlayerShotHitOnObject` [code]; each per-object test checks the object's position (record+3/record+4) inside a 6-wide × 12-tall window around the shot, and on overlap raises the retire flag `loc_420b` and scores-and-deactivates the object. Symmetrically, `flagObjectHitsOnPlayer` [code] runs only while `OBJ_ACTIVE_FLAG` bit0 is set, testing the same seven objects against the ship via `flagObjectHitOnPlayer` [code]; that per-object test classifies the object's field record+3 (plus a bias of 33) into a near or far proximity window, tests the ship reference `loc_4202` minus the object X record+4 against that window's band, and on overlap raises `HIT_EVENT_FLAG` (0x4204) and scores-and-deactivates the object.

The raised hit event is consumed once per frame by `handlePlayerHitEvent` [code], the sole reader of `HIT_EVENT_FLAG`. If bit0 is clear it does nothing; otherwise it clears the flag, tears the ship down for its death sequence — clears `OBJ_ACTIVE_FLAG` and sets the death-in-progress flag `loc_4201`=1 — arms the two pulse counters `loc_4205`=10 and `loc_4206`=4 (the pair the hit-sound stepper ticks), queues the hit-sound command, decrements the pace/difficulty counter `loc_421a` (floored at zero), steps the [0,5] cycle counter `loc_421d`, and pulses `SOUND_W_REG3` (0x6803) when the mode flag `loc_4006` bit0 is set. That death-in-progress flag `loc_4201` is exactly what `moveControlledObjectAndStageSprite` watches to keep staging the ship's wreck under code 7, and what the frame driver's quiescence guard watches to hold the board until the death plays out.

Finally, the command-enqueue path these routines use to post scoring, sound, and draw events shares a tiny stack-cleanup epilogue, the deliberately-unnamed loc_090b — it pops the caller's saved register pair and returns with no work-RAM effect of its own.

## Sound

The sound machine is composed once per video frame into a small block of work-RAM shadows and then latched out to the board's discrete-sound registers. The heart of it is `driveSoundFrame` [code], the per-frame sound tick run from the VBLANK interrupt. It opens each frame from a clean slate — the composite output byte at `0x41c0` zeroed and the staged-pitch shadow `SOUND_PITCH` (0x41c1) primed high to `0xff` — then runs seven channel/effect updaters in a fixed order, each of which folds its contribution into those two shadows. When they have all run it latches the result to hardware: the composite byte goes to `SOUND_W_REG6` (0x6806), its rotate-right to `SOUND_W_REG7` (0x6807), and the staged pitch to the pitch port `SOUND_PITCH_W` (0x7800). Because every updater writes into the same `0x41c0`/`SOUND_PITCH` pair, the fixed seven-way order is what arbitrates between the effects for the port each frame.

The seven updaters, in the order they run, are the request-gated sequence arm, the sweep voice, the selector-driven sequence arm, the three sequence channels, the pulse-tone envelope, the rising pitch ramp, and the gated square tone.

**Arming a note sequence.** Two of those updaters can arm a note sequence. `armSoundSequenceOnRequest` [seen] watches a one-shot request gate at `0x41d1`: it fires only when that byte holds exactly 1, then consumes the request (clears `0x41d1`), raises the sequence's active-descriptor byte at `0x41d2` and the shared duration timer at `0x41d6` to 1, and publishes the sequence-data cursor `SOUND_SEQ_PTR` (0x41d3) aimed at the ROM note table at `loc_1e68`. `armSoundSequenceBySelector` [code] instead runs only while the sound driver is enabled (`loc_4006` bit0) and reads a request selector from `0x41df`. Any selector other than 6 is handed to `armSoundSequenceForSelector16` [code], which acts on the single value `0x16` — clearing companion descriptor `0x41cf`, raising the active descriptor `SOUND_SEQ_ACTIVE` (0x41cd) and duration `0x41d6`, and aiming `SOUND_SEQ_PTR` at ROM sequence `loc_1edf`; every other value passes through untouched. A selector of 6 is handled inline: unless `SOUND_SEQ_ACTIVE` is already set, it raises companion descriptor `0x41cf` and duration `0x41d6` and aims `SOUND_SEQ_PTR` at ROM sequence `loc_1ebd`. So three distinct ROM sequences can be armed through three descriptor bytes (`0x41d2`, `0x41cf`, `SOUND_SEQ_ACTIVE`).

**Playing the sequence channels.** `advanceAllSoundSequenceChannels` [code] steps those same three descriptors once per frame, in turn — `0x41d2`, then `0x41cf`, then `SOUND_SEQ_ACTIVE` (0x41cd) — each through `advanceSoundSequenceChannel` [code]. A descriptor holding 0 is an idle channel and is skipped. An active channel writes composite flag `0x41c0`=2 and publishes its current tone (held at `0x41d5`) into `SOUND_PITCH`, then ticks the duration timer `0x41d6` down; while the timer still runs there is nothing more to do. When it expires the channel pulls the next command byte from the cursor `SOUND_SEQ_PTR` (0x41d3): the end marker `0xe0` deactivates the channel (its descriptor byte is cleared to 0); any other byte is split — its low five bits index the ROM tone table `SOUND_TONE_TABLE` (0x17a9) for the new tone (stored to `0x41d5`), its high three bits index the ROM duration table `SOUND_DURATION_TABLE` (0x17c8) for the new timer (stored to `0x41d6`) — and the cursor advances one byte. A current-state quirk worth noting: the tone at `0x41d5`, the duration timer `0x41d6`, and the sequence cursor `SOUND_SEQ_PTR` are single shared cells rather than per-channel state, so the three descriptors gate the playback of one voice rather than three independent ones.

**The sweep voice and the pitch chain.** `updateSoundSweepVoice` [code], the second updater, is gated on the same driver-enable bit `loc_4006` bit0. It watches a counter at `0x41c2`: on any frame where that byte is not 1 it hands the pointer to the sound-counter manager `advanceSoundSweepAndStagePitch` [code]; on the single tick where it holds 1 it reloads an idle template instead — counter `0x41c2`=0, the adjacent sweep cell at `0x41c3`=2, and the sound counter `0x41c4`=160. That 160 parks the sound counter well past the ceiling of 96 the manager enforces, which stalls the sweep from climbing until the counter decays back down. `advanceSoundSweepAndStagePitch` returns immediately while gate `0x4226` bit0 is set; otherwise it steps its pointer forward one cell (from the counter `0x41c2` to the sweep cell `0x41c3`). If frame-timer gate `0x425f` bit0 is set it skips the sweep and jumps straight to staging a pitch; otherwise it bumps the sweep cell `0x41c3` up by one — but only while the sound counter `0x41c4` is still below 96 — and falls into `tickSoundCounterAndStagePitch` [seen], which decrements the sound counter `0x41c4` when it is still running and stores it back, then stages the pitch. The sweep cell climbs and the sound counter falls together, shaping the swept note.

Pitch staging is a two-level dispatch shared by that whole chain. `stageSoundPitchBySelector` [code] reads the low two bits of the pointed cell as a selector: a nonzero selector recomputes the pitch from the sound counter through `stagePitchFromSoundCounter` [code], a zero selector stages a fixed pitch of 96. `stagePitchFromSoundCounter` takes the current sound counter `0x41c4` and, on an odd selector, biases it by 96 and rotates the sum right one bit (the add's carry rotating back into the top bit) to produce a warbled value; an even selector passes the counter through unchanged. Either result lands in `SOUND_PITCH` (0x41c1) through `stageSoundPitch` [seen], the leaf that does nothing but park the byte for `driveSoundFrame` to latch out at end of frame.

**The pulse-tone envelope.** `advancePulseToneEnvelope` [code], the fifth updater, manages a decrementing envelope word whose low byte is `0x41c7` and high byte `0x41c8`. When bit0 of the low byte is set the word is re-armed to a high-bit sentinel (`0x41c7`=0, `0x41c8`=128) and nothing sounds; otherwise the high byte is handed to `pulseSoundToneFromCountdown` [code]. That routine idles when the high byte is zero; otherwise it stores the byte decremented back to `0x41c8` and stages a two-level pulse through `stagePitchAndRaiseSoundFlag` [code] — value 129 when bit2 of the decremented byte is set, else 0. `stagePitchAndRaiseSoundFlag` parks `(A − 1)` into `SOUND_PITCH` (so 129 becomes 128, 0 becomes 255) and raises composite flag `0x41c0` to 1, marking the pair filled for the frame. The result is a square pulse whose on/off follows bit2 of the counting-down envelope.

**The rising pitch ramp.** `driveRisingPitchRamp` [code], the sixth updater, watches an arm counter at `0x41c9`. The arm byte is only tested, never stored while nonzero: while `(arm − 1)` is nonzero it advances the ramp one step through `advanceSoundPitchRamp` [seen]; on the tick where the arm reaches its reset point it clears `0x41c9` and reloads the ramp's {countdown, pitch} pair at `0x41ca` to 32 (countdown 32 at `0x41ca`, pitch 0 at `0x41cb`). `advanceSoundPitchRamp` reads the countdown one byte past its pointer (`0x41ca`) and idles when it is zero; otherwise it consumes one count, adds a fixed step of 4 to the pitch byte at `0x41cb`, publishes that pitch to `SOUND_PITCH`, and clears composite flag `0x41c0` so the frame composes cleanly. The arm cell `0x41c9` is raised outside this subsystem when the input scan sees the fire/arm bits, so this is the climbing whistle that accompanies a player shot.

**The gated square tone.** `advanceGatedSquareTone` [code], the last updater, watches a gate counter at `0x41cc` — again a test-only predecrement. While `(0x41cc − 1)` is nonzero it drives the tone through `driveGatedSquareTone` [code]; on the expiry step it parks the gate at 0 and re-arms the tone duration `SOUND_TONE_DURATION` (0x41ce) to 8. `driveGatedSquareTone` runs the duration counter `0x41ce` down each tick and, while it is still running, writes the frame-parity byte `0x4007` with its bit0 flipped straight to `SOUND_W_REG5` (0x6805); because `0x4007`'s low bit alternates every frame, this toggles the register between two levels for a square wave. Once the duration is spent it writes 0 to silence the tone.

**The LFO level.** Alongside `driveSoundFrame`, the VBLANK handler also runs `driveSoundLfoLevel` [code] once per frame. If no reset is pending (`SOUND_LFO_RESET_REQUEST` 0x41d0 is 0) it runs the per-frame decay `decaySoundLfoLevel` [code]; otherwise it consumes the request (clears `0x41d0`) and slams the full level of 15 across the LFO latches through `broadcastSoundLfoLevel` [seen]. `decaySoundLfoLevel` is gated to act only on the frame where the frame-timer `0x425f` reads `0xff`, and only while the level `SOUND_LFO_LEVEL` (0x421f) is still nonzero: on that tick it drops the level by one and rebroadcasts. `broadcastSoundLfoLevel` saves the level to `0x421f` and then fans it across the four LFO-frequency latches at `SOUND_LFO_FREQ` (0x6004–0x6007), rotating the byte right one bit between each write so the four latches receive successively rotated copies. The whole effect is a level that is slammed full on a trigger and then decays one step at a time toward silence.

**Effects driven from the gameplay frame.** Three sound routines are ticked from the per-frame play pipeline rather than the sound driver. `driveSoundVoicesFromOccupancy` [code] runs on even frames only (`0x4007` bit0 clear): it sums the 6×10 occupancy grid `OCCUPANCY_GRID` (0x4123, 16-byte row stride) into a tally seeded at 1, then lights one of the three voice latches `SOUND_W_REG0`..`SOUND_W_REG2` (0x6800–0x6802) per unit of tally — capped at three and stopping the instant the tally drains — and zeros the remaining latches from the stopping point on, finally raising a near-empty flag at `0x4224` when the tally came out below 2. The louder-with-more-occupants behavior is the throbbing hum that tracks how much of the alien formation is still on the field.

`driveGatedSoundStepSequence` [code] is a self-timed descending effect gated on `0x4201` bit0. A prescaler at `0x4205` counts down and fires only once every ten eligible frames (reloading to 10 on each fire); on each fire it enqueues a command word carrying opcode 2 and the current step value from `0x4206`, then steps `0x4206` down. When the step counter reaches zero the sequence ends: it clears its enable flag `0x4201` and silences `SOUND_W_REG3` (0x6803). The command-word enqueue it uses returns through a small shared epilogue, `loc_090b` [code], which restores the caller's saved HL register and returns.

`driveDecayingSoundSweep` [code] runs on even frames (`0x4007` bit0 clear) and reads a countdown from `0x41df`; while that byte is nonzero it emits the countdown rotated right two bits to `SOUND_W_REG4` (0x6804) and then ticks it down one, so the emitted value shrinks toward silence. A counterintuitive current fact: `0x41df` is the same cell that `armSoundSequenceBySelector` reads as its request selector and that the object-animation code writes as a sound request — so writing an effect code there both seeds this decaying downward sweep on register 4 and is offered to the sequence-arm dispatch, and the sweep's own countdown ticking that byte back to 0 is what finally quiets the request. `armObjectAnimAndRequestSound` [code] is one such writer: it is the entry (sub-state 0) handler of a deactivated object's animation, seeding the object's animation timers (frame divider 4 at record offset 16, step count 4 at offset 17, step field 28 at offset 18), advancing its sub-state so the entry runs once, and then posting a sound request into `0x41df` — `0x17` when the object's position byte (offset 7) is at or above 112, otherwise `0x07` — so a destroyed object's explosion sweep is pitched by where on the screen it died.

**Silencing everything.** `silenceSoundAndDisableIrqStars` [code] is the hardware quiesce used on reset and attract-mode init. It sets the four LFO-frequency latches `SOUND_LFO_FREQ` (0x6004–0x6007) to 1, clears all eight sound registers `SOUND_W_REG0`..7 (0x6800–0x6807), clears the interrupt-enable latch `IRQ_ENABLE` (0x7001) and the starfield-enable latch `STARS_ENABLE` (0x7004), and drives the pitch port `SOUND_PITCH_W` (0x7800) fully high to `0xff`. It therefore not only silences the audio but halts both the vblank interrupt that drives the sound frame in the first place and the starfield.

## Coins, credits, the HUD, score display, and the message scroller

### The command queue and the display list

Almost everything in this subsystem reaches the screen indirectly, through a single ring buffer of pending draw commands. `enqueueCommandWord` appends a 16-bit word to that ring at the write head kept in loc_40a0: it looks at the head slot (in the page-0x40 block based at loc_4000) and, only if that slot is still free — its top bit set — stores the word's high byte there, its low byte in the next cell, and bumps the head by two, clamping it up to a floor of 0xc0 so the ring occupies 0x40c0..0x40ff. A busy slot is left alone and the word is dropped. Each word's high byte is a channel number and its low byte an argument. Every routine here that "queues" a redraw calls this; the shared tail loc_090b [code] is just the pop-and-return epilogue that path collapses to, with no work-RAM effect.

The ring is drained frame by frame by a loop that walks the read cursor DISPLAY_LIST_CURSOR (loc_40a1, the low byte of a page-0x40 pointer). It reads a slot's control byte and doubles it: the doubling both tests the top "free" bit (a still-free slot is handed to an idle-work step and re-scanned) and turns the channel number into an even index. `decodeDisplayListSlotAndDispatch` [seen] takes that doubled control byte, masks its low nibble, retires both bytes of the slot to 0xff, advances the cursor past them (wrapping back to 0xc0 when it would drop below), and calls one of eight draw handlers keyed by the nibble, handing the slot's second byte over as the argument. Because the channel is doubled first, channel 0 reaches the first handler and channel 7 the eighth. Five of the eight belong to this subsystem: channel 3 adds to the score (`addBcdScoreIncrementAndUpdateHighScore`), channel 4 clears-and-repaints a score field (`clearAndRedrawScoreField`), channel 5 repaints a score field (`drawScoreFieldByIndex`), channel 6 paints a message column (`renderMessageColumn`), and channel 7 renders a HUD field (`renderHudFieldBySelector`). The other three (channels 0–2) draw tile figures and belong to the tile/sprite subsystem.

### Coins and credits

The coin machinery runs every vblank. `serviceCoinInputs` [seen] is the front end. In coinage mode 3 — free play, read from loc_4000 — it simply hands off to `presetCreditCount` [code], which pins the credit count loc_4002 to 9 and clears the coin-phase flag loc_4001. Otherwise it folds the two coin-input shadows (IN0_SHADOW at 0x4010 together with loc_4013), complements them, and masks the result through the two guard cells loc_4015 and loc_4016. If bit 7 survives — a service/free-credit line — it calls `addCreditForCoin` [code] to bank a credit at once; otherwise the low two bits are the two coin slots, and each set bit ticks the coarse coin counter loc_4004 (up to twice in one pass).

`tickCoinMeterAndAwardCredits` [seen], also a per-vblank call, turns those banked coin pulses into credits and drives the physical coin meter. While the pulse-width cell loc_4003 is nonzero it calls `pulseCoinCounter` [seen] and counts loc_4003 down; `pulseCoinCounter` rotates the countdown value right three bits so bit 3 of the count lands in bit 0 of the write-only coin-counter output COIN_COUNTER_0_LATCH (0x6003), producing a meter pulse held high across roughly half of each 15-frame window. When loc_4003 reaches zero and a coin is still waiting in loc_4004, it decrements that coarse counter, refills loc_4003 to 15, and converts the coin to credits per the coinage mode: mode 3 awards nothing, mode 1 runs the two-coins-per-credit path `awardCreditEverySecondCoin` [code], mode 2 awards two credits (two credit steps), and any other mode awards one.

`awardCreditEverySecondCoin` uses loc_4001 as a one-bit phase memory: the first coin of a pair merely raises the flag through `setCoinPhaseFlag` [code]; the second clears it and awards a credit. Awarding always funnels through `incrementCreditCount` [code], which walks loc_4002 toward its ceiling of 99 — refusing to move at 99, pinning an overshoot back down through `clampCreditsToMax` [code], and otherwise bumping it, raising the ready flag loc_41c9, and queuing a channel-7 word (argument 1) so the credit-count HUD field repaints. `addCreditForCoin` does the same bump-and-repaint directly, capping at 99. That loc_4002 is genuinely the credit count, not merely a scratch byte, is corroborated all across the subsystem: the lamps, the lockout, the credit-to-start logic, and the HUD digit line all read it.

Two hardware outputs track that count. `updateCoinLockoutFromCredits` [code] engages the coin-lockout coil COIN_LOCKOUT (0x6002) whenever fewer than nine credits are banked and releases it — via `clearCoinLockout` [code], which writes zero — at nine or more, so a nearly-full bank stops accepting coins. `driveStartButtonLamps` [code] lights the two start-button lamps START_LAMP_0 / START_LAMP_1 (0x6000 / 0x6001, the write side of the IN0 port address) from the same count, but only when bit 5 of the frame/status byte loc_425f is set: with that gate clear both lamps go dark; with it set, one credit lights lamp 0 and two or more light both, while zero credits leaves the lamps as they are.

### From credit to game start

`advanceGameStateOnCredit` [code] is what lets the machine leave attract mode. It does nothing while loc_4002 is zero; once a credit is present it increments the master GAME_STATE and wipes the attract sub-state cluster — the frame flag loc_4007, SEQUENCE_STATE, the sound-sweep countdown loc_41c2, the sound-request selector loc_41df, and the scroller enable MESSAGE_SCROLL_ENABLE — so the next state begins clean.

The "press start" screen then advances through sequence sub-states that keep the lamps live. `holdStartLampsThenAdvanceSequence` [code] ticks the countdown loc_4019, calling `driveStartButtonLamps` each frame it is still running, and on the zero-crossing advances SEQUENCE_STATE and clears the 128-byte flag-bits block at FLAG_BITS_BASE. `blankVramRowsThenDriveStartLamps` [code] fills two 28-cell blank rows through the VRAM write cursor VRAM_WRITE_PTR, and on its last row advances the sequence, clears the screen-flip latches FLIP_SCREEN_X / FLIP_SCREEN_Y and the direction flag loc_4018, queues a channel-7 (arg 2) HUD draw and a channel-6 (arg 1) message draw, and drives the lamps once more.

When the player commits, `startGameRoundAndClearScores` [code] sets the round up: it stashes the player/spawn word in CURRENT_PLAYER, blits the 32-byte ROM row template loc_051b into the packed-flag buffer PACKED_FLAG_BITMAP, optionally arms the sub-state advance gate when config bit loc_401f is set, then enters play (GAME_STATE 3, SEQUENCE_STATE 0, mode flag loc_4006 1, loc_41d1 1). Its three queued words are the visible "new game" effect: a channel-6 message column (arg 4) plus two channel-4 clears — argument 0 and argument 1 — that zero and repaint the player-1 and player-2 score fields.

### Scores

Scores are three-byte packed BCD. `byteToPackedBcd` [code] is the scalar converter — value modulo 100 with tens in the high nibble, units in the low — used by the HUD digit lines. The score itself is added by `addBcdScoreIncrementAndUpdateHighScore` [code], the channel-3 handler. It first honors an early skip: if bit 0 of loc_4007 is set the whole update is abandoned. Otherwise it picks the current player's field with `selectCurrentPlayerScore` [code] (loc_400d chooses PLAYER1_SCORE_BCD at 0x40a2 or PLAYER2_SCORE_BCD at 0x40a5) and adds the three-byte increment found at SCORE_INCREMENT_TABLE + index×3, carrying in decimal, low byte first. It then derives a threshold value from the score's upper bytes and, when it reaches the bonus threshold held in loc_40ac, awards a bonus marker. It repaints the player's digits, then compares the new total against the stored high score HIGH_SCORE_BCD (0x40a8) high byte first, and only if strictly higher copies the total into the high score and repaints the high-score digits.

The digit painters build downward-walking BCD columns. `drawBcdDigit` [code] stamps one nibble as a font tile (digit + 0x90, so '0'..'9' become tiles 0x90..0x99) with leading-zero blanking: while a blank budget remains a leading zero is drawn as the blank tile (0x80 + 0x90 wraps to tile 0x10) and the budget is spent, and the first significant digit ends suppression. `drawBcdNumberColumn` [code] walks three score bytes from the high byte down, emitting high-then-low nibble for each as six digit tiles up a column (stride −32 per digit) with a four-slot blank budget. `drawScoreToSelectedPlayerField` [code] points that column at DIGIT_FIELD_PRIMARY (0x5381) or DIGIT_FIELD_ALT (0x5121) by a field selector, and `drawHighScoreDigits` [code] points it at the fixed high-score field loc_5241.

Two handlers repaint whole score fields by index. `drawScoreFieldByIndex` [code] (channel 5) maps index 0 to the primary player-1 field, index 2 to the high score, and index 1 to the player-2 field — but only when the two-player flag loc_400e is set, which also selects the alternate digit field; an index of 3 or more recurses down, repainting every field. `clearAndRedrawScoreField` [seen] (channel 4) is the same shape but first zeros the field's three digit bytes plus a companion byte — the per-player bonus-marker flag PLAYER1_BONUS_MARKER_AWARDED / PLAYER2_BONUS_MARKER_AWARDED for the player fields, and the high score's own first byte for index 2 — before repainting. That companion clear is what wipes a player's bonus-marker eligibility along with their score at round start.

Kill scoring bridges the object subsystem into this one. `awardKillScoreByBandAndDeactivate` [code] deactivates a hit object (its record's first three bytes) and picks a score bucket by scanning the object's type/position field in obj+7 against a threshold of 0x50 across three bands, each miss bumping the score-type parameter and dropping the field by 16; the first band that fits enqueues a channel-3 score-add. If all three are exhausted it raises the inhibit/request word loc_422b, folds in a neighbour bonus when the active-neighbour count ACTIVE_NEIGHBOR_COUNT is exactly two (recording it in loc_422d), and enqueues the folded channel-3 request.

Bonus markers are the little icons along the bottom. `awardBonusMarker` [code] is one-shot per player: it indexes the flag table at PLAYER1_BONUS_MARKER_AWARDED by loc_400d, and if this player is not already flagged, flags them, raises the sound-envelope trigger loc_41c7, bumps the marker counter loc_421d, and repaints the row with the new count. `drawMarkerRow` [code] paints that count as marker tiles (tile 102) growing upward from MARKER_ROW_VRAM (0x539e) and blanks the remaining slots of the five, stopping when a signed slot counter goes negative; while the object subsystem is active (OBJ_ACTIVE_FLAG set) the displayed count is dropped by one, and if that empties it the whole row is blanked instead.

### The HUD field renderer and the player-status columns

`renderHudFieldBySelector` [code] (channel 7) is a four-way switch on its argument. Argument 0 draws the coin/credit icon-tally row at COIN_CREDIT_ROW_VRAM (0x507e) from the count in COIN_CREDIT_ROW_COUNT (0x421c) — drawn as count+1, capped at 0x30, as a run of tens-tile and units-tile pairs with the leftover slots blanked — and, gated by the frame-parity skip flag loc_4007, nudges the LFO reset request SOUND_LFO_RESET_REQUEST when the region-clear gate loc_4220 is set. Argument 1 is the credit-count line: gated by loc_4006, it paints a label message column — message 0x10 alone when both top bits of IN1_SHADOW are set, otherwise message 0x05 followed by writing the credit count loc_4002 (capped at 0x63 = 99) as tens and units digits into CREDIT_COUNT_TENS_VRAM (0x529f) and CREDIT_COUNT_UNITS_VRAM (0x527f). This is the field the coin path repaints on every credit. Argument 2 is a two-nibble status readout of the config byte loc_40ac (skipped when it holds the 0xff sentinel), writing its low nibble to HUD_NIBBLE_LO_VRAM (0x5138) and its nibble-swapped high nibble to HUD_NIBBLE_HI_VRAM (0x5158) — the same loc_40ac that serves as the bonus threshold in the score handler. Any other argument, again gated by loc_4007, redraws the marker row from loc_421d.

The player-status column is a small three-cell indicator repainted through a short chain. `selectPlayerStatusVram` [code] returns the base — PLAYER1_STATUS_VRAM (0x5340) for player 1, PLAYER2_STATUS_VRAM (0x50e0) otherwise. `paintPlayerStatusColumn` [code] stamps three cells from that base stepping by a stride: an incremented character code on top, then the fixed middle and bottom tiles 0x25 and 0x20; afterward, when the caller's bit 4 is clear and the mode gate loc_4006 is zero, it clears the saved-status byte loc_40ab. `repaintPlayerStatusColumn` [code] chooses the current player's column and either paints it directly (bit 4 clear) or blanks its three cells and, when the two-player flag loc_400e is set, paints the other player's column too (bit 4 set). `repaintPlayerStatusColumnIfSaved` [code] guards that on loc_40ab being nonzero, and `repaintPlayerStatusColumnFromModeGate` [seen] — the per-frame entry, reached from the display-list drain's idle-work step when no object slots are active — latches the mode: a nonzero loc_4006 is saved into loc_40ab and the column repainted, while a zero loc_4006 repaints only if loc_40ab already holds a saved value.

### The message scroller and text columns

`renderMessageColumn` [seen] (channel 6) is the message painter, indexed by its argument into the pointer table MESSAGE_PTR_TABLE (0x235c) to fetch a destination cell and a text pointer. Its top two argument bits pick the mode. Bit 7 blanks the message: it walks the text and writes the blank tile 0x40 up the column to the terminator (character 63). Bit 6 is the setup-and-arm mode: it records the destination in MESSAGE_DEST_PTR and the text in MESSAGE_TEXT_PTR, computes a per-column delay-counter address into the table at loc_4020 (keyed by the destination column) and stores it in MESSAGE_CURSOR_PTR, clears the whole VRAM column (from VRAM_BASE) to tile 16, packs the destination's row position into the high five bits of the counter cell, and raises MESSAGE_SCROLL_ENABLE. With neither top bit set it draws the message statically, each character mapped to a tile (source byte − 48) up the column to the terminator.

Once armed, `advanceMessageScroller` [seen] runs every vblank. While MESSAGE_SCROLL_ENABLE is set it reads the delay counter through MESSAGE_CURSOR_PTR: if the counter's low three bits are nonzero it is still delaying and merely ticks; at a terminator character it ticks and finishes; otherwise it emits one glyph — advancing MESSAGE_TEXT_PTR by one and stepping MESSAGE_DEST_PTR up one row (−32) — then ticks. Because the counter's low three bits act as a per-glyph delay and the high bits track how far the message has climbed, one glyph appears roughly every eight frames. The tick itself is `endMessageScrollOnExpiry` [seen], which decrements the counter and, on the exact zero-crossing, clears MESSAGE_SCROLL_ENABLE to stop the scroller; `endMessageScrollOnExpiryFromDe` [seen] is the same countdown tail, reached when the counter pointer is passed in DE rather than HL.

Messages also feed off object AI and the sequence timers. `advanceObjectAndQueueMessageColumn` [seen] is an object state that bumps the object's tick, counts its dwell timer down, and on expiry queues a channel-6 message column whose argument is the object's payload selector (obj+7) plus 75, then advances the object's state — this is how demo objects trigger their captions. `emitMessageColumnsThenAdvanceSequence` [seen], a sequence-state handler, resets the strided table and runs a two-tier dwell over loc_4008 / loc_4009: each low-tier expiry reloads to 80 and queues a channel-6 column tracking the mid count, and the mid-tier expiry advances SEQUENCE_STATE, reloads both tiers, clears the sprite-source block SPRITE_SOURCE_OBJ_BASE, and zeros the redraw count DRAWN_COLUMN_COUNT. `postCreditAndMessageDrawsAndAdvance` [code] is a simpler sequence step that queues a channel-7 credit redraw and a channel-6 message draw, advances the sequence, and re-arms the dwell pair to 96 / 16.

Static text columns are a separate, non-scrolling family. `drawTextColumn` [code] is the primitive: for a run of characters it maps each source byte to a tile (source − 48) and writes it, stepping the source forward and the destination by a signed stride, so a negative stride walks up a column. `drawTextColumnFromDescriptor` [code] unpacks a five-byte descriptor — source word, destination word, count byte — and paints that many characters up a column (stride −32). `drawTextColumnByIndex` [code] indexes the ROM descriptor table TEXT_DESCRIPTOR_TABLE (0x1cf6) by number and paints that descriptor.

### The attract input readout and the screen fill

The attract screen shows the current DIP settings as text and then animates a screen wipe, and a short chain assembles it. `driveSoundFrameAndScanInput` [code] is the per-frame service for the attract/demo state: it ticks the sound driver and the decaying sweep, pets the watchdog by reading SOUND_PITCH_W (0x7800), reads IN0 (0x6000), and if any of its arm bits (7, 1, 0) are set raises the pitch-ramp arm cell loc_41c9, then falls into the input scan handing it the raw IN0. `requestSoundOnInput1AndContinueScan` [code] reads IN1 (0x6800) and, if either low bit is set, seeds the control/sound-request byte loc_41df to 0x16, then continues. `requestSound6AndContinueInputScan` [code] seeds loc_41df to 6 when bits 2–3 of the folded inputs are set, and `armInputFlagAndDrawInputColumns` [code] raises the companion input flag loc_41cc when the folded inputs' bit 4 is set. The chain lands in `drawInputTextColumnsAndSeedScreenFill` [seen], which decodes three two-bit fields — IN1 bits 6–7, IN2 bits 0–1, and IN2 bit 2, each biased into a descriptor number — and paints each as a text column, then, unless IN0 bit 6 is asserted, seeds the screen-fill state: it clears the mode flag loc_4006, sets loc_401a to 2, arms the dwell pair loc_4008 / loc_4009 to 16 / 48, points VRAM_WRITE_PTR at the top of VRAM, clears the four-byte lamp/coin latch block, and silences the sound hardware.

The animated fill itself is a per-frame strip painter. `advanceScreenFillStrip` [code] pets the watchdog and reads the strip gate loc_4008: if it is zero there is no strip to draw, so it restarts the outer dwell; otherwise it loads the VRAM cursor and paints the first half. `drawScreenFillStripFirstHalf` [code] stamps a run of tile pairs (48, 50) forward from the cursor and falls into `drawScreenFillStripSecondHalf` [code], which stamps a further sixteen pairs of a second pattern (52, 54), saves the advanced cursor back to VRAM_WRITE_PTR, ticks loc_4008, and on its expiry restarts the outer dwell. That restart is `restartScreenFillOnDwellExpiry` [seen], which ticks the high dwell tier just past loc_4008 (that is, loc_4009) and, when it reaches zero or was already zero, re-seeds the whole fill through `resetScreenFillState` [seen]. `resetScreenFillState` is input-gated on IN0 bit 6: unless that bit is asserted it rewinds VRAM_WRITE_PTR to the top of VRAM, re-arms loc_4008 to a full 32-row page, and clears the dispatch flag loc_401a and GAME_STATE — starting the wipe over.

### The shared refill primitive

`reloadExpiredCounterAndTally` [seen] sits alongside these but serves the enemy-launch pacing rather than the HUD: it copies one reload byte from a source table (the enemy sub-counter reload table SUBCOUNTER_RELOAD_TABLE at 0x15e3) into an expired counter cell, then bumps and returns a refill tally — a generic "re-arm one counter and count that it happened" step used by the launch pacer.

## Tile / VRAM drawing primitives and coordinate mapping

The tilemap lives at VRAM_BASE (0x5000): thirty-two cells to a row, four 256-byte pages stacked to cover the screen, every cell holding one glyph code. Almost everything in this subsystem writes glyph codes into that grid, and it is built from a tiny kit of stamp primitives that the larger figure-, block-, and column-drawers chain together. Two counters steer the animated and periodic pieces: loc_425f is the per-frame counter (its nibbles are also scrambled into tile variants), and loc_4009 is the dwell tier that the sequence-clearing routines tick down.

### Mapping a packed coordinate to a cell

Before the display list can draw a figure, its packed coordinate byte has to become a cell address, and mapPackedCoordToVram [code] is the shared decoder. It reads the byte as two nibble fields and shuffles them into an address of the form VRAM_BASE + (page << 8) + low. The low nibble, rotated right by two, lands its bottom two bits as the page number (0..3, selecting one of the four tilemap pages) and its top two bits as the top of the low byte; the high nibble's three-bit field then supplies the rest of the low byte through a complemented running sum folded down to a nibble. Two side results are what callers actually branch on: A returns holding the coordinate's bits 6..5, and the carry flag returns holding the coordinate's bit 4. That carry is the entire reason for the shuffle as far as the figure-drawers are concerned — it is the single bit that decides "2x2 block" versus "vertical pair."

### The stamp primitives

The floor of the kit is stampTilePair [code]. It writes the seed code at HL and the next code (seed + 1) at HL + 1 — two consecutive glyphs in adjacent cells — then steps HL forward by one-plus-the-caller's-stride and bumps the seed by two, handing back the advanced code and pointer so a caller can chain pair after pair. Because a cell store keeps only a byte, a seed of 0xff writes 0xff then 0x00. Its vertical sibling is drawDoubleHeightTile [code], which paints the two halves of a tall glyph: the seed at HL and seed + 2 one tilemap row (thirty-two cells, 0x20) directly below, leaving DE untouched.

From those two, the 2x2 block writers fall out. drawTileBlock2x2 [code] calls stampTilePair twice with a stride of 31, so each pair advances one past itself and then thirty-one more — a net +32, one row down — laying a top pair (tile, tile+1) and a bottom pair (tile+2, tile+3) from four consecutive codes, DE preserved. drawTileBlock2x2Up [code] is the upward counterpart: it stamps with a net stride of -33 (0xffdf) so the pointer climbs one row after each pair, and it steps the seed back four codes before the second pair so the upper row carries the lower glyph numbers. drawBottomTilePairRestoreDe [code] is the shared bottom-pair tail: it stamps the already-staged second pair through stampTilePair and then restores the DE the caller saved before the pair began, returning it. drawTileBlock2x2AtDe [code] is a DE-entry adapter — it swaps DE and HL so a pointer that arrived in DE becomes the draw destination (the old HL is handed back in DE), then lays a 2x2 block there from the seed in A.

A family of fixed-seed entry points sits over these for the game's decorative glyph runs, all keyed to the 0x2c glyph family. drawFixedTilePairHorizontal [code] seeds stampTilePair with code 44 (0x2c) and returns the advanced pair so a caller's loop can stitch a horizontal run; drawFixedTilePairVertical [code] seeds drawDoubleHeightTile with the same 44 to stand a two-cell column; drawFixedTileBlock2x2 [code] lays a full 2x2 of codes 0x2c..0x2f; and drawFixedTileBlock2x2Up [code] stamps an upward 2x2 from the decorative seed 46 (0x2e) — this last is what drawMarkerRow uses to blank the marker-row slots that hold no marker.

Blanking has its own primitives. blankTileBlock4x4 [code] fills a 4x4 region at loc_51da with the blank code 0x40, stepping a full thirty-two-cell row between the four row starts. blank4x4AndDraw2x2Icon [code] chains that clear with a 2x2 icon (seed tile 96) stamped at loc_51fc over the cleared block — this is "form 0" of the small indicator described below.

### Choosing the variant and dispatching the draw

For the animated figures the glyph code is not fixed but pulled toward the frame counter. computeTileVariantFromTimer [code] folds a value in B down to a two-bit index: when B is below 112 it swaps the nibbles of the frame counter loc_425f, adds B and the incoming carry, and keeps the low two bits; at 112 or above it saturates to the 0x80 out-of-range marker (via markValueOutOfRange), leaving A and the flags alone. computeTileVariantFromValueAndTimer [code] wraps that with the range gate the callers want: values at or above 112 saturate straight to 0x80, otherwise it isolates the value's low nibble, sets the carry when the frame counter's own low nibble is the smaller of the two, and folds through computeTileVariantFromTimer — so the two-bit result cycles with the frame counter, giving the figure its shimmer.

The block-or-glyph decision is made by drawTileGlyphOrBlock [code], keyed on the carry that the coordinate mapper produced. With carry set it swaps DE/HL so the mapped cell becomes the destination and stamps a 2x2 block chosen by B; with carry clear it fetches B's glyph code from the byte table at loc_2157 and paints it as a double-height glyph at the incoming HL (the swap only stashes HL across the pointer-clobbering table read, so the destination stays the incoming HL). When it takes the block path it goes through drawSelectedTileBlockOrFallback [code], which treats B as a signed selector: non-negative selects a block by index, negative stamps a fixed fallback block (tile 0xa4) at the pending destination. The non-negative case runs drawIndexedTileBlock [code], which reads a 2x2 block's base code from TILE_BLOCK_TABLE (0x215b) at that index and stamps it through drawTileBlock2x2AtDe.

### The display-list figure and form handlers

Three of these are the painters the display-list decoder (decodeDisplayListSlotAndDispatch) calls by handler index, each handed the slot's argument byte. drawFixedTileFigureAtPackedCoord [code] (index 2) maps the packed coordinate to its cell and then, on the mapper's carry (coordinate bit 4), stamps either a fixed 0x2c-family 2x2 block or a fixed vertical pair — a static figure. drawAnimatedTileFigureAtPackedCoord [code] (index 0) is its animated twin: it maps the same coordinate to a cell, folds that coordinate into a frame-timed variant, and then draws a 2x2 block when bit 4 is set or a double-height glyph otherwise, so the figure both sits at a coordinate-derived spot and cycles its glyph with loc_425f. draw4x4TileForm [code] (index 4) draws one of three indicator forms selected by its argument: form 0 clears the 4x4 block and overlays the 2x2 icon (blank4x4AndDraw2x2Icon), form 1 merely clears the block (blankTileBlock4x4), and any higher form folds (form − 2) into a complemented tile code over a fixed 0xc0 base and stamps four 2x2 blocks across a contiguous 4x4 region at loc_51da, loc_51dc, loc_521a, and loc_521c, advancing the seed four codes between blocks.

The object-slot walk that feeds those figure drawers has just been decompiled; its reading is understanding-pending. loc_2067 [code] is the scan head — reached from the main-loop drain when the display list is idle, it reads the low nibble of the frame/slot counter loc_425f: zero means no active slots, so it repaints the player-status column; otherwise it indexes the object grid OBJECT_GRID_BASE (0x4120) by that nibble and, unless loc_4238 bit0 gates it off, seeds a six-slot scan (stride 0x10) through loc_207d [code]. Each iteration reads bit0 of the slot's flag byte to route: set hands off to the active-slot handler loc_2089 [code] — map the packed coordinate to its cell, fold the counter into a tile variant, stamp the glyph or 2x2 block — while clear stamps the fixed tile figure and falls to the shared loop epilogue loc_2094 [code]; the epilogue advances the slot pointer by the stride and loops until the six slots are done. The precise roles of the grid and the per-slot flags are not yet grounded.

### Column drawing and its periodic refresh

A separate primitive walks columns rather than rows. drawTileColumnTriple [code] copies three source bytes up a single VRAM column — each byte lands at the destination and the destination's low byte then steps back thirty-two (0x20), one row up, within a fixed page — and after the three it advances the low byte by +98 (0x62) to line up the next column, returning the advanced source and destination so successive columns chain. blankTileColumns [code] is the erase counterpart: for each of B columns it stamps the blank code 0x10 into three cells stepping one row up (a full sixteen-bit step that borrows into the high byte), then advances +98 to the next column, its count decrementing so that a B of zero wraps to a full 256 columns.

Those two are driven by redrawTileColumnsPeriodically [code], which repaints a run of columns on a schedule. It reads the running column count from DRAWN_COLUMN_COUNT (0x4241) and does nothing with fewer than two; otherwise it looks at the low six bits of the frame counter loc_425f as a phase. On phase 0 it wipes the columns through blankTileColumns; only on phase 32 does it repaint — the first column drawn from a source row picked by the frame counter's top two bits within TILE_COLUMN_TABLE (0x039a), then the remaining columns pulled from the consecutive source stream at TILE_COLUMN_TABLE_CONT (0x03a6), each drawTileColumnTriple threading its advanced source and destination into the next.

### Sequence-driven full-screen fills

The attract and play state machines lean on this kit to wipe and re-arm the screen a strip at a time, all sharing the VRAM write cursor VRAM_WRITE_PTR (0x400b) and the dwell tier loc_4009. primeVramFillAndAdvanceStep [seen] sets a step up: it clears the 128-byte flag block at FLAG_BITS_BASE (0x4100) and the two status bytes loc_425f and loc_4224, points VRAM_WRITE_PTR two cells into the grid (VRAM_BASE + 2), arms loc_4009 to thirty-two, and steps SEQUENCE_STATE (0x400a). fillVramRowThenResetObjectState [seen] runs one per-frame tick of a clearing sub-state: it paints a twenty-eight-cell strip of tile 16 at the cursor and advances the cursor a full row, then ticks loc_4009; only when the tier expires does it advance SEQUENCE_STATE, re-arm the two-tier dwell (loc_4008 to 64, loc_4009 to 4), clear the forty-eight-byte active-object block at OBJ_ACTIVE_FLAG (0x4200), zero the screen-flip latches FLIP_SCREEN_X (0x7006) and FLIP_SCREEN_Y (0x7007) and the direction flag loc_4018, raise the status flag loc_4238, and reseed the object-shadow field from the ROM template at OBJ_SHADOW_RESEED_TEMPLATE (0x1db1).

blankVramRowThenResetSpriteState [code] is the same shape one state later: it clears its strided table, blanks a twenty-eight-cell row of tile 16 at the cursor and steps the cursor a row, ticks loc_4009, and on expiry advances SEQUENCE_STATE, clears the 256-byte sprite-source block at SPRITE_SOURCE_OBJ_BASE (0x42b0) and the sixty-four-byte SPRITE_SHADOW_BASE (0x4060), re-arms the dwell (loc_4008 to 64, loc_4009 to 4), reseeds the object shadow from ROM, and queues command word 6. blankScreenRowsThenAdvanceSequence [code] is the play-state variant used at sub-state 1 of both player frames: it blanks a full thirty-two-cell row of tile 16 at the cursor, advances the cursor, ticks loc_4009 as a phase counter, and on the final phase advances the sequence and reseeds the object shadow. The command-queue path these tie into ends at loc_090b, a deliberately unnamed pure-stack epilogue that simply restores a saved register and returns with no work-RAM effect.

### The projectile renderer and its collision siblings

One member of this group draws into the sprite shadow rather than the tilemap. advanceAndRenderProjectiles [code] both integrates and renders the seven moving-object records at loc_4260. Each record is two five-byte sub-slots; a phase bit in loc_425f picks which sub-slot leads this frame while the other's sub-position is nudged +2. For the leading sub-slot, when active, it advances the sub-position (deactivating on overflow), integrates the sixteen-bit position by twice the sign-extended velocity, and deactivates the slot when the position leaves the vertical window — deactivation zeroing the active, sub-position, and high bytes. It then writes each object's on-screen Y and glyph code into the sprite shadow at loc_4081, mirroring the Y and flipping the sign of a ±1 code nudge on the first three records according to the direction flag loc_4018.

The same 0x4260 field is read a second way for collisions — as fourteen five-byte entries rather than seven ten-byte records. flagProjectileHitOnPlayer [code] is the per-entry test: an inactive entry (low bit of its first byte clear) never hits; otherwise it forms the horizontal delta of the player-X reference loc_4202 against the entry's X, shifts the entry's Y up by thirty-one, and splits on a near/far band whose width comes in through E. In the far band it accepts when the biased X delta falls within that width; in the near band it first requires the shifted Y to sit within nine, then accepts when the X delta (biased by the band width) falls within eleven. A hit zeroes the entry's first byte and raises HIT_EVENT_FLAG (0x4204). flagProjectileHitsOnPlayer [code] is the driver: it does nothing unless projectiles are enabled (bit 0 of OBJ_ACTIVE_FLAG at 0x4200), then walks all fourteen entries from loc_4260 at stride five through the per-entry test. Notably it never forwards a caller's E — the loop leaves E holding the record stride, so the collision band is always exactly five wide.

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs.
