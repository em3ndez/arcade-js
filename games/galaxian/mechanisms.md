# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–12.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

Beneath the game logic sits a handful of tiny routines that everything else leans on: a pseudo-random source, a block-fill primitive, an indexed table read, an unsigned divide, and the housekeeping that keeps the per-frame interrupt alive. Several of them live at the Z80's low restart-vector addresses (0x0010, 0x0020), so they can be reached by a one-byte call and act as cheap building blocks the rest of the ROM reuses constantly.

### The pseudo-random seed

`advanceRandomSeed` [seen] (0x003c) is the machine's only source of randomness, and it is a linear-congruential generator with an unusually compact character: there is no separate "current value" and "next value". The single byte `RNG_SEED` (0x401e) is simultaneously the generator's entire state and the value returned to the caller. Each call reads that byte, multiplies it by five (the code builds `seed*5` as `seed*2`, then `*2` again to reach `seed*4`, then adds the original seed back), increments the result, folds it back into a byte, and writes it home. The freshly computed byte is what the caller receives — so *drawing* a random number and *advancing* the generator are the same act, and a call always permanently mutates the shared seed. Callers treat that byte in whatever shape they need: the formation reseeder rolls a fresh vertical position from it, the attacker-direction chooser keeps only its low bit as a coin flip, and the jittered-velocity path masks it down to a 0-31 spread. Because the state is a single global cell, the sequence any one consumer sees is interleaved with every other consumer's draws in call order.

### Filling memory in bulk

`fillMemoryBlock` [code] (0x0010) is the block-store primitive. Given a destination pointer, a fill byte, and a count, it writes the byte into that many consecutive addresses, walking the pointer forward one step at a time, and stops when the count is exhausted. The count is decremented as a byte, so a count of zero does not fill nothing — it wraps through 255 and fills a full 256 bytes, the idiom callers use to blank an entire page. When the loop finishes it hands back the pointer sitting just past the filled region and a spent count of zero, which lets a caller chain one fill straight into the next. The store is not restricted to plain work RAM: its destination can equally be a video-RAM row or a hardware latch, which is exactly how the game uses it — clearing VRAM rows before drawing, wiping object RAM back to a known state, and blanking screen regions during the attract and start sequences all funnel through this one loop.

### Indexed table lookup

`fetchIndexedTableByte` [code] (0x0020) is the companion read primitive: a table base pointer plus an 8-bit index in, one byte out. It adds the index to the low byte of the pointer and correctly propagates the carry into the high byte, so the index may push the pointer across a 256-byte boundary without corrupting it, then reads the byte at the resolved address. It returns both that byte and the advanced pointer, so a caller can fetch an entry and then keep reading forward from there. This is the workhorse behind table-driven rendering — the tile and glyph drawers use it to translate an index into the actual character or block byte to lay down, and the screen-fill-and-configure path uses it to pull entries out of its layout tables.

### Unsigned divide

`divideUnsigned8` [code] (0x0048) is a classic restoring divide of the dividend in A by the divisor in D, done in eight compare-subtract-shift rounds. Each round asks whether the running remainder still contains the current divisor: if it does, the divisor is subtracted and a 1 bit is recorded, otherwise the remainder is left alone and a 0 bit is recorded; that bit is shifted into the quotient while the divisor is simultaneously walked down one bit position for the next round. Entry sets up the work — the quotient accumulator starts at zero and the round counter at eight — before the eight rounds run. When they finish, the quotient sits in C (the value callers actually read), the remainder is left in A, the fully shifted divisor in D, and the round counter has been spent to zero. It touches no memory; it is pure register arithmetic. Its two consumers are geometric: the octant routine divides a slope's components and reads the quotient to pick one of eight facing directions, and the jittered-velocity routine divides to scale a slope before adding its random spread.

### The vblank interrupt epilogue

Once per frame the display's vertical blank raises an interrupt, and the handler that services it saves six register pairs on entry and acknowledges the interrupt by clearing the enable latch so it does not immediately re-fire. `rearmVblankInterruptAndRestoreRegs` [code] (0x00d8) is the tail that undoes all of that. It writes 1 into `IRQ_ENABLE` (0x7001) to re-arm the latch — this is the load-bearing step: without it only the very first vblank would ever be serviced and the whole per-frame cadence would freeze after one frame. It then restores the six saved pairs in the reverse of the order they were stacked, and returns through the address the interrupt had interrupted, so the main loop resumes exactly where it was. Notably the accumulator is briefly loaded with 1 to arm the latch, then immediately overwritten when the saved A/F pair is restored, so the interrupted code sees its own registers intact.

### A shared return tail

Finally, `loc_090b` [code] (0x090b) is a deliberately unnamed two-instruction epilogue: it restores the caller's saved HL from the stack and returns. It does no work and touches no RAM — it exists only as the common exit of the command-queue enqueue path, where the routine that persists the queue's advanced write head falls straight into it to unwind the one register the enqueue had preserved.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

Galaxian runs its whole front-of-house life -- power-on, the attract loop, the "press start" screen, and the two players' rounds -- as a single two-level state machine driven once per vertical-blank. The outer level is the game state, held in `GAME_STATE` (0x4005); the inner level is the sequence step, held in `SEQUENCE_STATE` (0x400a). Every frame the vblank handler reads `GAME_STATE` and hands the frame to exactly one of five top-level handlers, indexed 0..4: the boot/fill handler `fillScreenThenLatchConfigAndAdvanceState` [seen], the attract handler `runAttractSequenceAndAdvanceOnCredit` [code], the start-screen handler `runStartScreenAndLaunchGame` [code], and the two play handlers `runPlayerOnePlayFrame` [code] and `runPlayerTwoPlayFrame` [code]. Each of those, in turn, reads `SEQUENCE_STATE` and dispatches to a sub-handler for the current step. The whole thing is a ladder: the game state names the phase of the machine's life, the sequence state names how far a given phase has progressed, and both only ever count upward until something resets them.

### The dwell-timer cascade, and why advancing the sequence is just a carry

The single most important trick in this subsystem is the memory layout of three adjacent bytes: the sub-timer at 0x4008 (`loc_4008`), the dwell tier at 0x4009 (`loc_4009`), and `SEQUENCE_STATE` immediately above them at 0x400a. Because they are contiguous, a countdown that "carries" out of one byte lands in the next, and advancing the sequence state costs nothing more than letting a timer roll over into it.

`tickCascadeCountdown` [seen] is the primitive that makes this work. Handed a pointer, it decrements the byte there; while that byte is still nonzero it is finished for the frame, but on the tick that drives the byte to zero it steps its pointer to the next byte *in the same page* and increments *that* one. It is a two-tier "decrement-and-carry": expiry of the low tier bumps the high tier by one. `tickSequenceDwellTimer` [code] is the thin wrapper the state machine uses most: it points the primitive at the dwell tier 0x4009, so when 0x4009 finally expires the carry lands on 0x400a and the sequence step advances by one, automatically. `tickPrescaledSequenceTimer` [seen] puts one more prescaler stage in front of that: it decrements the sub-timer 0x4008 every frame, does nothing until it wraps, and only on the wrap reloads 0x4008 to 60 and calls the cascade primitive on the dwell tier -- so the dwell tier (and hence the eventual carry into `SEQUENCE_STATE`) advances once per 60 frames rather than every frame.

Handlers that want to re-arm rather than carry use the reload helpers. `reloadSequenceDwellTimer` [code] stamps the dwell tier 0x4009 back to 80 frames. `advanceSubstateAndReloadDwell` [code] does the two things a state-exit usually wants together: it bumps the counter it is handed (its callers pass `SEQUENCE_STATE`, so it advances the step directly) and then re-arms the dwell timer to 80 via the reload helper. `setSequenceStateByModeAndReloadDwell` [code] is the branch-y cousin: instead of incrementing, it *sets* the counter to a fixed step -- 4 when the mode bit `loc_4006` (0x4006) is set, 14 when it is clear -- and then re-arms the dwell timer, so a handler can jump the machine to one of two follow-on steps according to the current mode.

### Boot: fill the screen, then latch the machine's configuration

At power-on `GAME_STATE` is 0, so every frame runs `fillScreenThenLatchConfigAndAdvanceState`. Each pass writes a 32-byte run of the blank tile (16) at the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) and advances that cursor 32 bytes further, so the tilemap is wiped a strip at a time while the per-state timer 0x4008 counts down. When that timer expires the handler performs the machine's one-time configuration latch: it resets the state cluster (`loc_4007` = 1, `loc_4006` = 0, `GAME_STATE` = 1 to enter attract, `SEQUENCE_STATE` = 0), then folds hardware/DIP bits out of the input shadows into their flag cells -- two bits of `IN1_SHADOW` (0x4011) into `loc_4000`, one bit of `IN2_SHADOW` (0x4012) into `loc_401f`, one bit of `IN0_SHADOW` (0x4010) into the flip flag `loc_400f` -- unpacks a packed flag bitmask out of ROM template `loc_051b`, and picks a coinage byte out of the four-entry ROM table `loc_0152` indexed by the low two bits of the `IN2_PORT` (0x7000), storing it at `loc_40ac`. It then seeds the object-shadow field from ROM, paints the three player-1 status glyphs (`PLAYER1_STATUS_VRAM` 0x5340 = 1, `loc_5320` = 37, `loc_5300` = 32), and queues two deferred command words. That single expiry is the seam between "raw machine" and "configured machine": everything downstream reads the cells this handler latched.

### Attract: the sequence sub-states and the exit on credit

In game state 1 `runAttractSequenceAndAdvanceOnCredit` runs the two per-frame formation-prep passes and then dispatches on `SEQUENCE_STATE` to one of nineteen attract sub-handlers (steps 0..18; two of the slots are duplicates, and a twentieth slot is a cold-reset sentinel that a valid `SEQUENCE_STATE` never reaches). After the sub-handler runs, the attract handler finishes with the credit check described below.

Several of those sub-handlers belong to this subsystem. Step 0 is `initSequenceEnableStarfield` [seen]: it queues two setup command words, turns the starfield on (`STARS_ENABLE` 0x7004 = 1), clears the per-sequence bookkeeping cells (`CURRENT_PLAYER` 0x400d, the paired-player flag `loc_400e`, `loc_4006`, and the step countdown `loc_4019`), seeds the dwell cascade fresh (sub-timer 0x4008 = 96, dwell tier 0x4009 = 16), and increments `SEQUENCE_STATE`. Step 1 is `armStepCountdownAndTickSequenceTimer` [seen], which arms the one-frame step countdown `loc_4019` to 1 and then runs the prescaled sequence timer; the countdown at `loc_4019` is what a later handler decrements to time this step out. Step 18 is `enterSequenceStep1` [code]: it snaps `SEQUENCE_STATE` back to 1 and seeds a very short dwell (both the sub-timer 0x4008 and the dwell tier 0x4009 to 3), which is how the attract sequence loops back on itself.

Three more attract steps are pure sequence-advance handlers built on the timer cascade, each of which first runs the four shared per-frame subsystem updates (clear the strided table, stage sprites, drive the object slots, periodically redraw tile columns). `activateDescriptorSlotsThenAdvanceSequence` [seen] runs a two-phase countdown: on the sub-timer 0x4008 expiring it reloads that timer, activates the descriptor slot named by the byte at the dwell tier 0x4009, and bumps `DRAWN_COLUMN_COUNT` (0x4241); then on the dwell tier itself expiring it reloads and increments `SEQUENCE_STATE`, clearing scratch `loc_4058`. `queueColumnDrawAndAdvanceSequence` [seen] counts the dwell tier down and, on expiry, advances `SEQUENCE_STATE`, re-arms the 0x4008/0x4009 timer pair to a fixed value, bumps `DRAWN_COLUMN_COUNT`, and enqueues a channel-6 column-draw command. `dwellThenAdvanceSequence` [code] is the degenerate case -- it does the four subsystem updates and then simply ticks the prescaled sequence timer, letting the cascade carry into `SEQUENCE_STATE` on its own with no staging of its own; a pure dwell step.

The exit from attract is the credit transition. Once the attract sub-handler returns, the attract handler runs its continuation, which watches the credit count `loc_4002` (0x4002): while it is zero nothing happens and attract keeps looping, but the moment a credit is present it increments `GAME_STATE` (attract 1 -> start-screen 2) and wipes the attract sub-state cluster -- `loc_4007`, `SEQUENCE_STATE`, `loc_41c2`, the sound-sweep countdown `loc_41df`, and `MESSAGE_SCROLL_ENABLE` (0x40b0) -- so the start screen begins from a clean slate.

### The "press start" screen and launching a round

In game state 2 `runStartScreenAndLaunchGame` runs the formation-prep passes, dispatches on `SEQUENCE_STATE` (only 0..3 here) to four start-screen sub-handlers that clear object RAM, hold and drive the start-button lamps, and blank VRAM rows, and then unconditionally runs `beginGameOnStartButton` [code] as its tail. That launcher reads `IN1_SHADOW`: bit 0 (the one-player button) hands off to `startOnePlayerGame` [code]; otherwise bit 1 (the two-player button) with at least two credits in `loc_4002` spends two, blits the 32-byte ROM row template `loc_051b` into the saved-state snapshot `SAVED_STATE_SNAPSHOT` (0x41a0), optionally arms the state-advance gate when config bit `loc_401f` bit 0 is set, and enters the shared round start with the two-player spawn value. `startOnePlayerGame` mirrors that for one credit: with none left it forces `GAME_STATE` back to 1 (fall back to attract), otherwise it spends one credit, zeroes the saved-state snapshot, and enters the round start with a null spawn value.

Both funnel through the shared round-start setup, which stores the spawn word into `CURRENT_PLAYER` (0x400d), blits the ROM row template into the packed flag bitmap `PACKED_FLAG_BITMAP` (0x4180), optionally arms the *sub*-state-advance gate on the same config bit, sets `SEQUENCE_STATE` = 0, `GAME_STATE` = 3 (enter player-one play), the mode flag `loc_4006` = 1 and `loc_41d1` = 1, and queues three spawn command words. The two config-driven gate arms are the small routines `armStateAdvanceGate` [code] and `armSubstateAdvanceGate` [seen]: each simply stamps the "armed" marker 3 into its gate byte -- 0x41b5 for the state gate, 0x4195 for the sub-state gate -- which the step-6 play handlers below later read as nonzero to choose their advance path.

### The play frames and their sub-states

Game states 3 and 4 run `runPlayerOnePlayFrame` and `runPlayerTwoPlayFrame`; they are near-identical siblings that differ only at sub-states 2, 6, and 7, and each dispatches `SEQUENCE_STATE` (0..7) to eight play sub-handlers after the formation-prep passes. Sub-state 0 for both is `initPlayfieldState` [code]: it turns both start lamps off, zero-fills the flag block `FLAG_BITS_BASE` (0x4100, 128 bytes), the object/behaviour region around `OBJ_ACTIVE_FLAG` (0x4200) and `loc_4218` (with a one-byte gap at 0x4217), and the object-record span at 0x4260, then sets `loc_425f` = 0 and `loc_4226` = 1, advances `SEQUENCE_STATE`, arms the dwell tier 0x4009 to 32, and points the VRAM write cursor at the tilemap base. Sub-state 3 for both is `advanceSubstateAfterDwellAndQueue` [code]: it ticks the dwell tier and, on the zero-cross, reloads it to 20, advances `SEQUENCE_STATE`, and enqueues that step's command word.

The board-restore step differs by player. Player one's sub-state 2, `restoreFormationAndEnterPlaySubstate` [seen], unpacks the packed flag bitmap `PACKED_FLAG_BITMAP` into the flag block, copies the trailing 8-byte board template into the template buffer `loc_4218`, clears the status/flip/direction cells (`loc_425f`, `loc_4220`, the flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y`, and `loc_4018`), advances `SEQUENCE_STATE`, arms the dwell tier to 150, and publishes a deferred-callback pointer into `loc_4245`; then, only if the sound gate `loc_4006` bit 0 is open, it cues the board-start sound -- the paired-player variant when `loc_400e` bit 0 is set, otherwise a plain channel-5 prologue word followed by the standard burst. Player two's sub-state 2, `restoreSavedStateAndEnterPlaySubstate` [code], is the mirror: it expands the *saved* snapshot `SAVED_STATE_SNAPSHOT` (rather than the packed bitmap) into the flag block, mirrors the flip flag `loc_400f` into the flip latches when set, arms the dwell tier to 150, publishes its own callback pointer into `loc_4245`, and when the sound gate is open enqueues five board-start command words.

Those board-start sound cues are built from two small emitters. `enqueueCommandWordBurst` [code] posts a fixed five-word burst on a caller-chosen channel: two words on the channel and its successor, then two fixed words on channel 7. `queueBoardStartSoundBurst` [code] is the paired-player prologue -- it emits one channel-5 word (param 3) and then delegates to that same five-word burst.

Sub-state 6 is the branch-heavy "should the board advance" step, and it too differs by player. `stepPlaySubstate6` [code] keys off the arm gate `loc_421d` (0x421d) and the two mode flags `loc_41b5` and `loc_400e`: with the arm gate set it either advances-and-reloads (both flags set) or jumps to a mode-selected step via `setSequenceStateByModeAndReloadDwell`; with the arm gate clear and either flag clear it runs the shared reset tail; and with the arm gate clear and both flags set it inlines an advance -- bump `SEQUENCE_STATE`, arm the dwell tier to 130, and (only when the mode bit `loc_4006` is set) enqueue two channel-6 command words. `stepAltPlaySubstate6` [code] is player two's version, keyed on the sub-state gate `loc_4195` in place of `loc_41b5`: gate open advances the step inline and re-arms the dwell tier (to 80 on the show arm, 130 on the default arm, queuing two channel-6 words on the default arm when sound is enabled); gate closed delegates to the mode-set helper or the shared reset tail. That shared tail is `advanceDwellOrResetToState1` [code]: when the mode flag `loc_4006` bit 0 is clear it just advances the counter and reloads the dwell timer, but when it is set it tears the machine down -- `GAME_STATE` = 1, clear `loc_4006` and `SEQUENCE_STATE`, silence the sound hardware and halt the interrupt and starfield, and queue command word 6 -- which is the machine falling all the way back to attract.

### The command queue that all of the above write into

Every "enqueue" mentioned above lands in a small ring the machine drains elsewhere. `enqueueCommandWord` [seen] appends a 16-bit word at the current write-head index held in `loc_40a0` (0x40a0): if the head's slot (page 0x40, offset = the index) has bit 7 set it is free, so the routine stores the word's high byte there and low byte in the next cell, advances the head by two, clamps it up to a floor of 0xC0, and commits the new index back to `loc_40a0`; a non-free slot leaves the queue untouched. `commitQueueWriteHead` [seen] is the same commit as a standalone step -- store the advanced index into `loc_40a0` -- reached as the tail of the enqueue path. Both bottom out in `loc_090b` [code], a bare epilogue that restores the caller's saved pointer and returns without touching work RAM.

### The in-play gates, prescalers, and delayed event

Play sub-state 5 is the per-frame gameplay pipeline, and several members of this subsystem are the small gate- and timer-managers it runs in fixed order once the object subsystem is live (`OBJ_ACTIVE_FLAG` 0x4200 bit 0 set). `armBehaviorGateOnInputOrTimer` [code] arms a behaviour gate `loc_4208` when appropriate: it bails if the enable bit is clear or the gate is already armed, then on the timer path (mode flag `loc_4006` bit 0 clear) arms the gate only when the low five bits of the frame counter `loc_425f` are all zero -- i.e. roughly once every 32 frames -- and on the input path (bit 0 set) tests bit 4 of the selected raw input shadow (`IN0_SHADOW` or `IN1_SHADOW`, chosen by `loc_4018` bit 0) masked against its guard cell (`loc_4013`/`loc_4014`), arming both `loc_4208` and the companion flag `loc_41cc` when a line reads active. `clearGateOnPendingRequest` [code] is the acknowledgement side: when request flag `loc_420b` bit 0 is pending it clears both that flag and the behaviour gate `loc_4208`.

`rampCounterToCeiling` [code] is a gated two-tier prescaler that paces difficulty: while the enable bit is set and the inhibit flag `loc_422b` bit 0 clear, it ticks an outer prescaler `loc_4218` (reload 60) and, on its wrap, an inner one `loc_4219` (reload 20), and on *that* wrap steps the 0..7 pace counter `loc_421a` up by one, clamped at 7. `expireActivityGatedTimer` [code] is a gated countdown that ends a timed phase: only while the arm flag `loc_422b` bit 0 is set *and* at least one activity gate is open (`loc_4224` nonzero, `loc_4221` nonzero, or `loc_4226` bit 0 set) does it tick counter `loc_422c`, clearing the arm flag once the counter reaches zero.

The delayed-event pair schedules and then fires a one-shot. `scheduleDelayedEvent` [code] runs only when three enable bits agree (`OBJ_ACTIVE_FLAG` and `loc_41ef` set, inhibit `loc_422b` clear). With the mode flag `loc_4006` clear it ticks an outer timer `loc_4245` (reload 60) and an inner timer `loc_4246` (reload 5), and only when both cascade to zero arms the fixed event triple -- `DELAYED_EVENT_TIMER` (0x422f) = 90, `loc_424a` = 45, `DELAYED_EVENT_ARMED` (0x422e) = 1. With the mode flag set it instead derives the payload from work-RAM byte-sums (of the words at `loc_4177` and `loc_421a`, or a fixed 2 when `loc_4221` bit 0 is set), fans that value into the same triple through bit-rotations, and arms it. `fireDelayedEventRequest` [code] then waits: while `DELAYED_EVENT_ARMED` is set it counts `DELAYED_EVENT_TIMER` down each frame and, on the zero tick, disarms the one-shot and -- only if `OBJ_ACTIVE_FLAG` and `loc_41ef` are both still set -- raises `DELAYED_EVENT_REQUEST` (0x4229) for the spawner to consume.

Finally, tangential to the sequencing but part of the same set of small clamps, `markValueOutOfRange` [code] is the saturation arm of a value clamp: it snaps register `B` to the fixed sentinel 128. Its caller, the tile-variant computation, uses it to force the out-of-range marker when a value lands at or above 112 instead of folding it into a legal 2-bit tile-variant index.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

Galaxian's aliens live in two overlapping representations that this subsystem keeps in step: a compact *occupancy grid* of one-byte-per-cell flags that records which formation slots still hold a live alien, and a table of full 32-byte *object records* that carry the moving, drawable, AI-driven objects (the standing formation members plus every attacker that has broken out of it). The routines here seed and reduce the grid, oscillate the whole formation from side to side, position and stage the objects for drawing, run the per-object AI states, register player hits, and pace and execute the launches and spawns that pull aliens out of the formation.

### The object records and their tables

An object record is 32 bytes wide, and several tables of them coexist. The main object table starts at `OBJ_TABLE` (0x42d0); the diving-attacker slots run downward from `loc_4391` (0x4391) on a 31-byte pitch; a band of eight records read for sprite staging begins at `SPRITE_SOURCE_OBJ_BASE` (0x42b0); and a separate `DESCRIPTOR_SLOT_TABLE` (0x4330) holds four 32-byte "descriptor" slots used for the scripted spawns. Within a record the recurring fields are: byte 0 the active flag (bit 0), byte 1 a death-animation flag, byte 2 the AI state selector, byte 3 the X field, byte 4 the Y field, byte 5 a signed heading, byte 6 a direction/spawn-code byte, and byte 7 the packed grid cell that ties the record back to its place in the formation. Higher offsets hold motion timers (byte 16), a walk cursor (byte 19), a sprite number (byte 22), a leg/step counter (byte 23), and a flight-curve seed (byte 24). Because records are 32 bytes apart, a slot can cheaply peek at its neighbours by adding 0x20 and 0x40 — a trick several routines below exploit.

`activateDescriptorSlot` [seen] initialises one descriptor slot from a number held at a pointer: it reads that byte, subtracts one to get a slot index 0..3, and stamps the slot's fixed init fields — active flag (byte 0) = 1, byte 1 = 0, byte 2 = 13, byte 4 = 0, byte 5 = 12, and byte 7 = the slot index — while deliberately leaving bytes 3 and 6 alone. Its caller, the sequence handler that periodically activates descriptor slots, passes the pointer at `loc_4009` (0x4009), so the descriptor number is whatever that timer cell currently names.

### The occupancy grid, its packed form, and its summaries

The live-alien grid is a block of 128 one-byte flags based at `FLAG_BITS_BASE` (0x4100), with the formation body proper laid out from `OCCUPANCY_GRID` (0x4123) as six rows of ten columns on a 16-byte row stride. Bit 0 of each cell means "an alien still sits here." This block is repeatedly torn down and rebuilt from a compact 16-byte bitmask that lives in ROM at `loc_051b` (0x051b): `unpackBitmaskToFlagBytes` [seen] walks sixteen mask bytes and explodes each into eight flag bytes LSB-first (1 for a set bit, 0 for a clear one), then returns the source pointer advanced past the sixteen bytes so a caller can read the 8-byte template that immediately follows the mask. `packFlagBytesToBitmask` [code] is its exact inverse: it reads bit 0 of the 128 flag bytes, packs them back LSB-first into a 16-byte bitmap at a destination pointer, and returns that pointer advanced sixteen so a following block copy can chain onto it. The packed images land at `PACKED_FLAG_BITMAP` (0x4180) when the running state is being handed between players, and at `SAVED_STATE_SNAPSHOT` (0x41a0) when a whole state block is being preserved.

Once a frame, `summarizeFormationOccupancy` [seen] reduces the grid into the derived cells the rest of the machine consults instead of rescanning 60 cells. It ORs each of the six rows into `ROW_OCCUPANCY` (0x41e8) behind two leading always-empty guard cells, and each of the ten columns into `COLUMN_OCCUPANCY` (0x41f0) behind three guard cells. From the column summaries it derives the formation's horizontal extent: scanning inward from the rightmost column it accumulates one X step (16 units) per empty column into a from-right bound, and symmetrically from the left for a from-left bound, packing the pair into `FORMATION_X_BOUNDS` (0x4210) as high byte = from-left, low byte = from-right (both falling back to their bases when no occupied column is found). Finally it folds four region-"clear" flags: the top four rows OR into `loc_4221` (0x4221) and the whole six-row OR into `loc_4220` (0x4220); seven object slots' active flags OR into `loc_4226` (0x4226) and an eight-slot column based at `loc_42b1` (0x42b1) ORs into `loc_4225` (0x4225). Each of the four is stored with bit 0 flipped, so "clear" reads as bit 0 set — the convention the launch, spawn, and stage-advance gates test. (`loc_42b1` is the second byte of the sprite-source object band at 0x42b0; the shot-hit path below writes a live alien into exactly that column, which is why its occupancy feeds a region-clear flag.)

### The side-to-side formation sweep

The formation's oscillation is stored as a 16-bit swept word at `loc_420e` (0x420e); its low byte doubles as the moving column anchor that object positioning reads. A one-bit direction flag `OBJ_SWEEP_DIRECTION` (0x420d) says which way it is travelling — 0 = ascending, 1 = descending — and `setSweepDescending` [seen] and `setSweepAscending` [seen] simply write 1 and 0 respectively into it, called at the turnaround points.

`advanceFormationSweepOscillator` [seen] drives the motion. Only one frame in four actually steps (a phase counter `loc_425f` (0x425f) masked with 3 throttles the other three): while ascending it turns around by calling `setSweepDescending` once the low byte reaches the from-right bound, otherwise it increments the swept word; while descending it calls `setSweepAscending` at the from-left bound, otherwise decrements. After a real step it broadcasts the new low byte, negated, across the per-column offset table (see below). A leading proximity gate short-circuits all of that: when the behaviour gate `loc_4208` (0x4208) is armed, the shot at `loc_4209` (0x4209) lies in a narrow vertical window, and the swept column (derived from the shot X at `loc_420a` (0x420a) minus the anchor) reads occupied, it skips the step and jumps straight to re-broadcasting the current formation offset — freezing the sway for the frame a shot is lined up on a column.

The per-column offset table is a 9-cell, stride-2 block at `loc_4028` (0x4028). `broadcastToStridedTable` [seen] writes one byte into all nine cells; `clearStridedTable` [seen] is that with the value zero (a per-state reset); `broadcastNegatedSweepToStridedTable` [seen] broadcasts the two's-complement of a supplied low byte; and `broadcastNegatedFormationSweepToStridedTable` [code] loads the swept word's low byte from `loc_420e` and hands it to the negated broadcast. Interleaved with that block, on the odd addresses, sits a 32-entry stride-2 field based at `loc_4021` (0x4021): `seedObjectRamShadowField` [seen] copies 32 contiguous source bytes into every other cell there, `seedObjectShadowFromRom` [seen] points it at the ROM template `STRIDED_TABLE_SRC` (0x1d71) and runs it, and `advanceSequenceStateAndReseedObjectShadow` [code] first advances a pointer's low byte within its page and bumps the byte it now names (its callers arrive pointing at 0x4009, so this carries into and increments `SEQUENCE_STATE` at 0x400a) before re-seeding that shadow field.

### Turning a grid cell into a sprite position, and staging sprites

`positionObjectFromGridCell` [code] converts a record's packed grid cell (byte 7) into its X and Y fields using the rotated display convention: the row bits (mask 0x70) drive the X field as 124 minus three-quarters of the row value (a fixed origin `ROW_ORIGIN` = 124), and the column bits (mask 0x0f) drive the Y field as the moving anchor at `loc_420e` plus the column scaled by sixteen plus a 7-pixel sprite hotspot. Because the anchor is the sweeping word's low byte, every formation member's Y tracks the sway automatically.

`stageObjectsToSpriteShadow` [seen] copies the eight formation objects from `SPRITE_SOURCE_OBJ_BASE` (0x42b0, 32-byte stride) into eight sprite-shadow records at `SPRITE_SHADOW_BASE` (0x4060, 4-byte stride), rendered as a band of three then a band of five. An orientation bit in `loc_4018` (0x4018) flips the first band's Y offset between 9 and 7, but both orientations settle the tail band at 8 — so the two bands' vertical relationship inverts with orientation while the field stays coherent. It runs from the gameplay frame and from the attract/start/descriptor sequence handlers, so the formation is drawn even before play proper.

### Per-object AI states

The object driver selects one of sixteen AI handlers by the record's state selector (byte 2). Three of them belong to this subsystem. State 0, `initSpawnedObjectFromGridCell` [code], is first-tick init for a freshly-launched attacker: it clears the step timer, raises the spawn flag `loc_41c2` (0x41c2), derives the sprite position from the grid cell, and posts a spawn command word (type 1, keyed by the packed cell) to the deferred command queue. It looks up the object's sprite number and flight-curve seed from the ROM `SPAWN_RECORD_TABLE` (0x1dd1) indexed by the cell's row bits; for the top row it also sets a special attribute base (24) and tallies its two look-ahead neighbour slots' active flags into `ACTIVE_NEIGHBOR_COUNT` (0x422a). Either way it seeds the motion counters, advances the sub-state, and picks the signed heading (+12 or −12) from the direction bit.

State 5, `reseedFormationObjectState` [code], re-homes a formation member: it snaps the X field back to the left edge (8), zeroes the heading, and ticks the leg counter. When the cell's high row bits are *not* all set it takes the reseed-and-advance path — when the subsystem is enabled (`OBJ_ACTIVE_FLAG` 0x4200 bit 0) and an activity gate (`loc_4224` 0x4224 or `loc_4221`) is open it rolls a fresh random Y, arms a 40-tick hold timer, and double-advances the state, else single-advances. When the high row bits *are* all set (the 0x70 sentinel) and neighbours remain, it recounts the two look-ahead slots into `ACTIVE_NEIGHBOR_COUNT` and reseeds; once none remain it deactivates the object and ramps a phase counter `loc_421e` (0x421e) toward a ceiling of 2.

State 6, `settleObjectIntoFormationCell` [code], settles a returning attacker back into its slot: each tick it repositions from the grid cell (which rewrites the frame/position field), then bumps a frame counter and compares. When the counter catches the positioned value the object has arrived — it deactivates, sets its formation-cell flag back in the grid (`FLAG_BITS_BASE` + cell = 1), and queues a command word carrying the cell; a small even gap nudges the phase field up or down by the direction bit, while a large (≥25) or odd gap is left untouched.

Two small helpers round out the object machinery. `bumpCountIfNeighborsInactive` [code] peeks the two look-ahead slots at +0x20 and +0x40 and returns a count incremented by one only when *both* are inactive (bit 0 clear), otherwise unchanged — the kill-band scoring path uses it to tally how much of a column has already fallen. `noopAnimDispatchSlot` [code] is the terminal do-nothing slot (sub-state 3) of the deactivated-object death-animation state machine, present so that dispatch always lands on a valid handler.

### Player shot versus formation

`flagPlayerShotHitOnFormation` [code] runs each gameplay frame while the shot gate `loc_4208` is armed. It rejects a shot above the formation's vertical span, then bands the shot Y (`loc_4209`) into one of six rows by repeatedly subtracting an alternating 7-then-5 step (the same interleave the sprite bands use), and bands the shot X-delta — the shot X (`loc_420a`) minus the anchor (`loc_420e`) — into a column, rejecting anything outside the hit window. It nibble-swaps the combined row/column into a grid index and, only if that flag cell holds a live alien, clears the cell. It then posts a command word (kind 1 with the grid index), stamps a hit/explosion record over the sprite-source column — `loc_420b` (0x420b) = 1, `loc_42b1` = 1, `loc_42b2` (0x42b2) = 0, and the shot's position word into `loc_42b3` (0x42b3) — and posts a second command word (kind 3 with a column code derived from the index). That is how a player shot removes a formation alien and queues its kill, scoring, and sound follow-through.

### Pacing and launching attackers out of the formation

Launches are rate-limited by a prescaler. `paceEnemyLaunchTrigger` [code] runs only while the subsystem is enabled and both inhibit flags (`loc_4220`, `loc_422b` 0x422b) are clear. It ticks a master counter `loc_424a` (0x424a); until that expires it drops the refill flag and stops. On expiry it reloads the master from the reload table `SUBCOUNTER_RELOAD_TABLE` (0x15e3), computes a difficulty-scaled span from the pace counter `loc_421a` (0x421a) and the (clamped) stage `loc_421b` (0x421b), sweeps that many following sub-counters decrementing each, refills any that hit zero from the matching reload-table entry, and — if anything refilled — raises `SUBCOUNTER_REFILL_FLAG` (0x4228).

`launchAttackerFromFormation` [code] consumes that one-shot: if the refill flag is not set it does nothing, and if it is, it clears it and holds off while the region-clear gate `loc_4220` is set. Otherwise it derives a 1..4 slot budget by folding the pace-counter sum (`loc_421a` + `loc_421b`) and claims the first empty (both-bytes-zero) diving slot scanning down from `loc_4391` on a 31-byte stride. It stamps the launch direction `loc_4215` (0x4215) into the slot and uses it to orient a scan of `COLUMN_OCCUPANCY` for an occupied column (from the high end down for direction 0, from the low end up otherwise). Geometry then depends on the sweep-mode flag `loc_41ef` (0x41ef): it walks the chosen grid column upward looking for a filled cell, and on a hit clears that formation cell, writes the cell's low byte into the slot's byte 7, marks the slot active at state 0, and posts a type-1 spawn command word — one standing alien peeled off into a dive.

### The spawn dispatch tree

Scripted spawns fan out from `spawnObjectsOnDelayedEvent` [code], driven each gameplay frame. It is gated on the region-clear flag `loc_4220` being clear, the subsystem enabled via `OBJ_ACTIVE_FLAG`, and a pending one-shot in `DELAYED_EVENT_REQUEST` (0x4229) which it consumes; it further holds unless the object-table head word is even. Then the launch direction's low bit routes the work: if set, a full trigger-block spawn via `spawnObjectsFromTriggerFlags`; otherwise it scans the primary trigger block `PRIMARY_TRIGGER_BLOCK` (0x4176) high-to-low for a set flag and, on a hit, runs `spawnPrimaryAndSecondaryObjects`, else scans a secondary window just below it and seeds a free descriptor slot via `spawnIntoFreeDescriptorSlot`.

`spawnObjectsFromTriggerFlags` [code] scans the four primary flags: the first set one spawns a primary object into `OBJ_TABLE` and then walks the secondary block `SECONDARY_TRIGGER_BLOCK` (0x4165) at the same offset, spawning up to two secondaries; if no primary flag is set it scans the secondary block instead and seeds a free descriptor slot from the first set flag. `spawnPrimaryAndSecondaryObjects` [code] spawns the primary into `OBJ_TABLE`, then walks three trigger flags backed up fifteen from the primary trigger's low byte, spawning a secondary into each following slot (from the table's second record) until a two-secondary budget is spent. `spawnIntoFreeDescriptorSlot` [code] is the shared free-slot finder: it scans the four `DESCRIPTOR_SLOT_TABLE` slots high-to-low for one whose two guard bytes are both zero and seeds it.

The leaves that actually stamp a slot are `activateObjectSlotAndEnqueueSpawn` [code] and `spawnSecondaryObjectIntoSlot` [code]. The former consumes the trigger flag it was found under, marks the slot active with a cleared phase, records the spawn code and the trigger pointer's low byte as a source index, and posts a type-1 spawn command word keyed by that index (returning the trigger pointer unchanged so the caller can read its low byte back). The latter is the same idea for a secondary slot but first bails if either of the slot's two live flags is already set, and inherits byte 6 from the source record rather than taking a spawn code. `spawnSecondaryObjectAndAdvanceWalk` [code] is the per-step wrapper for a secondary walk: it spawns into the current slot, advances the slot pointer by 32 and counts the budget down, and when the budget reaches zero forces the caller's loop counter to 1 so the walk ends after that pass.

### Stage advancement and the flag-block reset handlers

When a board is cleared the formation is rebuilt at the next stage. `armFormationAdvanceTrigger` [code] is the one-shot arm: only when both status gates `loc_4220` and `loc_4225` have bit 0 set and the pending word `loc_4222` (0x4222) is not already armed does it write the pending word to 1 (its low byte the enable, its high byte `loc_4223` (0x4223) a zeroed countdown). `advanceStageAndReseedFormation` [code] later consumes that: gated on the enable bit and the countdown reaching zero this tick, it disarms the enable, rebuilds the 128-flag block from the packed template at `loc_051b`, resets the pace counter and phase cell, reseeds the formation anchor `loc_420e` to 1, steps the stage selector `loc_421b` (its low byte saturating at 7, its high byte counting), posts a command word, and services a pending two-slot request in `loc_421e` by raising `loc_4177` (0x4177) and, if a second remains, `loc_4178` (0x4178).

Several top-level sequence-state handlers reset or hand off the object field around the flag block. `clearFlagBlockAndReseedObjectShadow` [code] (sequence state 12) zero-fills the 128-byte block at `FLAG_BITS_BASE`, clears status cells `loc_425f` and `loc_4238` (0x4238), arms the mid-tier dwell timer `loc_4009` to 64, then advances the sequence state and re-seeds the strided object shadow. `loadDescriptorAndAdvanceSequence` [code] (state 13) unpacks the ROM descriptor bitmask into the flag block, copies the 8-byte template that follows it into the buffer at `loc_4218` (0x4218), clears/sets two status bytes (`loc_425f` = 0, `loc_421d` (0x421d) = 1), advances the sequence state, stamps the fill cursor `VRAM_WRITE_PTR` (0x400b) to 150, and publishes a deferred-callback pointer (`loc_0640`) into `loc_4245` (0x4245). The two player-handoff terminals mirror each other: `packFlagsToBitmapAndSwitchPlayerState` [code] and `saveFlagsToSnapshotAndSwitchPlayerState` [code] each tick the dwell timer at `loc_4009` and, on expiry, clear the sequence/status cells, pack the live flag bytes into a bitmap (`PACKED_FLAG_BITMAP` and `SAVED_STATE_SNAPSHOT` respectively), copy the 8-byte companion block from `loc_4218` right after it, set `CURRENT_PLAYER` (0x400d), and pick the next `GAME_STATE` (0x4005) — 4 with player 1 for the first, 3 with player 0 for the second — so the frozen formation image travels with the player switch.

Finally, the deliberately-unnamed `loc_090b` is a shared stack epilogue on the command-word path: it restores the caller's saved register and returns with no work-RAM effect of its own.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

This is the heart of the running game: one player ship at the bottom, one shot it fires upward, and a formation of aliens that peel off, swoop, home, aim, and fire back. Almost every routine here reads one shared cell, `loc_4202`. That byte holds the player ship's current X, and every attacker also reads it as the *target-X reference* it steers, homes, and aims toward — so the ship's position is simultaneously the thing the player controls and the thing the whole enemy AI chases. A companion flag, `OBJ_ACTIVE_FLAG` (0x4200), is the master enable for the entire subsystem; when its bit 0 is clear the ship parks, the collision sweeps skip, and the launch machinery idles.

### The per-frame gameplay spine

`runGameplayFrameAndAdvanceOnFieldClear` [code] is the once-per-frame play loop. It runs a fixed sequence of subsystem updates in a set order — move-and-stage the ship, service the shot, integrate and draw the projectiles, drive every object slot, stage the objects into sprite memory, run the collision flaggers, then the spawn/launch/pacing/sound/stage-advance machinery — and only after all of that does it check whether the field has gone quiet. Its quiescence guard is three-part: no bit 0 may be set across the shot gate `loc_4208`, the hit-flash flag `loc_4201`, or `OBJ_ACTIVE_FLAG`; the stage-advance side flag `loc_4225` bit 0 must be set; and none of the fourteen five-byte projectile records based at `loc_4260` may have their active bit 0 lit. Only when all three hold does it tick the sequence dwell timer `loc_4009` down one, and on the frame it reaches zero bump `SEQUENCE_STATE` (0x400a). In other words: the level advances by stalling until every alien is gone and every shot has cleared the screen.

### The player ship

`moveControlledObjectAndStageSprite` [code] moves the ship and prepares its sprite each frame. When `OBJ_ACTIVE_FLAG` bit 0 is set it selects a movement byte from one of three sources: if `loc_4006` bit 0 is clear it takes the computed auto-pilot command `OBJ_MOVE_CMD` (0x423f), otherwise it reads a live input port — `IN1_SHADOW` (0x4011) when `loc_4018` bit 0 is set, else `IN0_SHADOW` (0x4010). Bit 3 of that byte steps the ship's position `loc_4202` down by one while it stays at or above 23; bit 2 steps it up by one while it stays below 233 — the two travel-direction commands, clamped to the [23, 233] band. Whichever branch runs, the ship's position is folded to a staged value by one's-complementing it and offsetting by 128, and written together with a code byte as four identical `(value, code)` pairs into `OBJ_STAGE_BLOCK` (0x4054). If the subsystem is off but the flash flag `loc_4201` is set it stages the current position under an alternate code (7) without clamping; if it is off entirely it parks the position at zero. This is why the ship's X and its on-screen sprite are always consistent: the same routine that reads the input writes the staging block.

### The player shot

`advancePlayerShot` [code] drives the single upward shot as a small state machine over four cells. While the shot gate `loc_4208` bit 0 is armed it drains the position counter `loc_4209` by four every frame; when that counter lands in the narrow window [14, 17] — the tail end of its travel near the top of the screen — it raises the retire flag `loc_420b`. When the gate is clear (no shot in flight) it resets the counter to 220 (parked at the bottom) and loads the lateral field `loc_420a` from the ship's X `loc_4202` if the subsystem is enabled, else zero — so a fresh shot is born directly above the ship. `advancePlayerShotAndStageSprite` [code] wraps that: it calls `advancePlayerShot`, then reads the counter/field pair back and writes the two shot render cells, `loc_409f` (X, chosen as `counter - 1` when `loc_4018` bit 0 is set, otherwise the complement of the counter plus 252) and `loc_409d` (the complement of the lateral field).

### The object slots and their state table

Eight object records live at `SPRITE_SOURCE_OBJ_BASE` (0x42b0) on a 32-byte stride. `driveAllObjectSlots` [code] simply walks that base across the eight slots, calling `driveObjectSlot` [code] on each. `driveObjectSlot` inspects three bytes of the record: if the dying-animation flag (record+1) bit 0 is set it hands the record to the death-animation dispatcher; else if the active flag (record+0) bit 0 is clear it does nothing; otherwise it uses the record's state index (record+2, valued 0..15) to select one of sixteen object-AI handlers and runs it on this record. That sixteen-entry state table is the skeleton of the alien behaviour: state 0 spawns a freshly launched attacker, states 1/10/11 walk scripted paths, state 2 picks the next horizontal move, states 3/9 fly the swoop-and-fire curve, state 4 dives, states 5/6 return to and settle into the formation, state 7 homes, states 8/12 arm and restart cross-player runs, state 13 sets up phase steps, state 14 queues a message column, and state 15 settles at rest. A recurring, counterintuitive fact about these records: fields record+3 and record+4 are the object's two position bytes — the renderer reads record+3 as the on-screen X (minus 8) and record+4 as the on-screen Y (complemented) — but several flight and dive handlers reuse record+3 as their per-frame progress counter, and field record+9 is likewise multiplexed (a subpixel low byte while homing, a Y increment while diving, a column while chasing). The same offsets mean different things in different states.

### Horizontal target-picking and the cross-player move

The workhorse commit is `commitMoveToTargetX` [seen]: given a chosen target X it stashes it at record+0x19, stores the signed per-frame delta (current X at record+0x04 minus the target) at record+0x09, zeroes the three-byte move accumulator at record+0x1a, and bumps the planner sub-state at record+0x02. Everything above it just chooses the target. `commitMoveAcrossPlayerX` [code] picks a crossover target: it takes the gap between the actor's X and the reference `loc_4202`, signed-halves it, biases by 16, and clamps to the band on the *opposite* side of the player — 144..208 when the actor is left of the reference, 48..112 when it is at or right of it — then commits. `commitMoveToStoredOrPlayerTargetX` [code] chooses between two targets: if bit 0 of the object table's mode byte `OBJ_TABLE` (0x42d0) is set it steers toward the table's stored target X (OBJ_TABLE+0x19), otherwise it falls back to the cross-player pick.

Several state handlers sit on top of these. `advanceActorPhaseAndCommitMove` [code] (state 2) ticks the actor's phase counter record+3 and then commits a horizontal move — using the stored/player select when the kind nibble (record+7 & 0x70) equals 0x60, and the plain cross-player pick otherwise. `beginObjectCrossPlayerMove` [code] is a shared tail: it commits a cross-player move and then arms the flight-curve step seed record+0x18 = 3 (giving four integration steps later) and the move throttle record+0x10 = 100. `armDirectedMoveWhenInWindow` [code] (state 8) ticks the arm counter record+3 and, until both it and position record+4 sit inside the [96, 160) window, keeps cruising via the cross-player tail; once both are in-window it advances the sub-state by two, seeds the move timers (record+0x10 = 3, record+0x11 = 12), clears record+5/record+0x13, and sets the direction bit record+6 from whether the reference `loc_4202` is below record+4. `restartObjectMoveRun` [code] (state 12) bumps record+3, forces the state back to 8 (re-entering the arm-window state), and begins a fresh cross-player run.

### Path walking

`advanceObjectPathStep` [code] (state 1) walks a per-object cursor (record+0x13) through `PATH_STEP_TABLE` (0x1e00), reading delta bytes in pairs: the first is added to record+3, the second — its sign chosen by direction bit record+6 — to record+4. If that coordinate (plus a 7-pixel margin) crosses the near edge (below 14) the object drops to the fall-away state 5. Otherwise it advances the cursor, ticks the move throttle record+0x10 (reload 4), and on throttle expiry nudges the cross-step record+5 and ticks the leg counter record+0x11, advancing the state when the leg finishes. `advanceObjectPathStepDescending` [code] (state 10) is the subtract-direction mirror: it subtracts the table's X delta from record+3 and, unless direction bit record+6 hands the vertical half off to the ascending arm, subtracts the Y delta from record+4; on a finished leg it advances the state and reloads throttle = 3, leg = 12, heading record+5 = 12, cursor = 0. `advanceObjectPathStepAscending` [code] is that ascending arm — it adds the step byte at the passed pointer to record+4, advances the cursor, ticks the throttle and leg counter, and on leg completion advances the state and reloads throttle = 3, leg = 12, heading = 244, cursor = 0. `advanceObjectPathStepAlias` [code] (state 11) is a bare trampoline: it forwards unchanged to `advanceObjectPathStep` and holds no state of its own.

### The flight curve, dives, and swoops

The swoop shape comes from `advanceObjectFlightCurve` [code], a cross-coupled fixed-point rotation. It runs `(record+0x18 seed & 3) + 1` integration steps over two 16-bit accumulators held in the record (high/low at record+0x19/+0x1b and record+0x1a/+0x1c). Each step adds twice the *other* accumulator's sign-extended high byte into this one; a resulting high byte of exactly 128 is treated as overflow and that step's high byte reverts. The accumulator high bytes are the flight offset — record+0x19 in particular is the heading the dive and flight handlers fold into screen Y, so this integrator is what bends an attacker's descent into a curve rather than a straight drop.

`advanceObjectDiveStep` [code] (state 4) steps the object's position record+3 by one or two (alternating on the frame-parity bit `loc_425f`) and window-checks it: inside [6, 9) it just bumps the state index; otherwise it runs the flight curve and folds the heading high byte record+0x19 plus the per-object increment record+9 into a new screen Y at record+4 — but if that sum carries across the signed boundary (the swoop ran off the bottom) it bumps the state instead of storing the Y. `advanceObjectFlightAndFire` [seen] (state 3) bumps the counter record+3, runs the flight curve, and sets screen Y record+4 = increment record+9 + heading record+0x19; a too-high Y (near the top, `(Y+7)` wrapping below 0x0e) advances the state by two, a wrapped-out counter (>= 0xb8) by one; failing those, and only while `OBJ_ACTIVE_FLAG` is enabled, it aims at the player and — unless the delayed-event bit `loc_422b` is set — scans the row table `loc_4213` for its counter value, firing when a row matches. `advanceHomingObjectFlightAndFire` [code] (state 9) is the homing variant: driven by the mode byte record+0x17 it first homes its column record+9 toward the reference `loc_4202` (never when mode < 4, always when mode > 4, and on odd frame parity when mode == 4), sets Y = column + heading, sends a too-high Y to state 5 and a wrapped counter (>= 0xc0) to state 4, otherwise ticks the move throttle record+0x10 and on expiry steps the state back — and, failing all that, aims and fires exactly as the plain flight handler does.

### Homing and settling

`homeObjectXTowardPlayer` [code] (state 7) steers the object's 16-bit X:subpixel pair (high byte record+4, low byte record+9) toward the reference `loc_4202` by roughly four times the signed distance each frame, carrying the hardware's rounding bias (a small extra count when overshooting from the far side), and advances the state once the dwell timer record+0x10 counts to zero. `settleObjectXAtRest` [code, wait — [seen]]` — `settleObjectXAtRest` [seen] (state 15) nudges field record+4 up one count per frame until its wrapped distance from the rest value 200 falls within five, then holds, which is how an object eases into and stays at its resting position. `initObjectPhaseSteps` [seen] (state 13) sets up a multi-step phase: it derives a step count n from the low two inverted bits of the packed seed record+7, writes n+1 to the step counter record+0x16, a code byte `((n+1) << 4) + 140` to record+3, arms the phase timer record+0x10 = 24, advances the sub-state, and clears the ready flag record+0x0f — re-arming it to 24 only when n is zero.

### Aiming and firing at the player

Aiming turns a geometric slope into a heading. `computeDirectionOctantFromSlope` [seen] divides a dividend by a divisor, clamps a too-steep (top-bit-set) quotient to 0x80, and returns the top three bits as a 0..7 octant. `aimObjectAtTarget` [seen] builds the slope from the vertical drop (0xF0 minus the sprite's record+3) and the horizontal delta from the sprite's record+4 to the reference `loc_4202`, calls the octant helper, mirrors the octant when the target is to the left, and stores the result in the object's direction field record+5. When a flight handler decides to fire, `spawnAimedProjectileAtPlayer` [code] claims the first free entry in the fourteen-slot table at `loc_4260` (stride 5, active = bit 0 of entry[0]), marks it active, copies the object's sprite Y and X into entry[1]/entry[3], and computes entry[4] as a scaled X velocity aimed at the player — mirrored when the target is to the left — via `computeJitteredXVelocity` [code], which divides the slope, adds a bounded PRNG draw (0..31) plus a floor of 6, and clamps to 0x7F. The random jitter is what keeps enemy fire from being perfectly predictable.

### Rendering an object to a sprite

`renderObjectSprite` [seen] builds one hardware sprite record (Y, attribute, sprite number, X) from an object struct. An active object (record+0 bit 0) copies its position — X = record+3 − 8, Y = complement(record+4) − a caller Y offset — takes its sprite number from record+0x16, and folds the signed heading record+5 into a display attribute added to the base attribute record+0x0f, rotating the heading by whole 24-count sectors into a canonical range and nudging the sprite a pixel on the diagonal facings. A secondary-active object (record+1 bit 0) instead uses fixed sprite number 7 and the alternate attribute record+0x12. With both flags clear the sprite is parked off-screen at (248, 248). This is the routine whose grounded position convention (record+3 = X, record+4 = Y) pins down what the AI fields actually mean on screen.

### The death-throes animation

When a record's dying flag (record+1) is lit, `driveObjectSlot` routes it to `dispatchDeactivatedObjectAnim` [code], which reads the animation sub-state record+2 and runs the matching phase handler: sub-state 0 seeds the animation and posts a sound (armObjectAnimAndRequestSound), sub-state 1 is `tickDeactivatedObjectAnim` [code], sub-state 2 is `endObjectAnimOnTimerExpiry` [code], and sub-state 3 is a no-op terminal slot. `tickDeactivatedObjectAnim` counts a fast field record+0x10 down (reloading it to 4 and bumping the companion record+0x12 on elapse), then a slow field record+0x11; when the slow field elapses it either retires the object (clearing state byte record+1) or, if the position field record+7 is at or past 112, reloads the fast field to 50, seeds the companion from the global `loc_422d` plus 32, and advances the sub-state. `endObjectAnimOnTimerExpiry` simply ticks the expiry timer record+0x10 down and, on the frame it hits zero, clears state byte record+1 to retire the actor.

### Collisions and the hit event

Two symmetric sweeps run each frame. `flagPlayerShotHitsOnObjects` [code], gated on the shot gate `loc_4208` bit 0, box-tests the shot against each of the seven object records at `OBJ_TABLE` (stride 32) through `flagPlayerShotHitOnObject` [code], which checks an active object's position fields record+3/record+4 against the shot's cells `loc_4209`/`loc_420a` inside a 6-wide by 12-tall window; on overlap it raises the shot-retire flag `loc_420b` and hands off to the kill-scoring/deactivate handler. `flagObjectHitsOnPlayer` [code], gated on `OBJ_ACTIVE_FLAG`, runs the mirror: `flagObjectHitOnPlayer` [code] classifies an active object's record+3 (biased by 33) into a near (< 5) or far (< 17) proximity window and tests the reference `loc_4202` minus record+4 against that window's band; on overlap it raises `HIT_EVENT_FLAG` (0x4204) and hands off to the same kill-scoring handler. `handlePlayerHitEvent` [code] is the sole consumer of that flag from the pipeline: if bit 0 is clear it does nothing; otherwise it clears the flag, zeroes `OBJ_ACTIVE_FLAG` and sets the flash flag `loc_4201`, arms the two death-jingle pulse counters `loc_4205` = 10 and `loc_4206` = 4, queues the hit-sound command word, decrements the pace counter `loc_421a` (floored at zero), steps the [0, 5] cycle counter `loc_421d`, and pulses `SOUND_W_REG3` (0x6803) when the mode bit `loc_4006` is set. So a player death takes the whole object subsystem offline and starts the death cadence in one stroke.

### Dive scheduling and the demo/auto pilot

Which alien fires, and in which direction attackers peel off, is decided by a few schedulers the pipeline runs every frame. `selectAttackerRowScan` [code] seeds a slot/base pair from the stage flag `loc_421b` (slot 2 / base 157 when nonzero, else slot 1 / base 132), scans up to four two-byte `ROW_OCCUPANCY` (0x41e8) slots — advancing only while neither byte of a slot has bit 0 set — and stores the resulting (slot count, base value) pair at `loc_4213`; that is exactly the (count, match) pair the flight handlers walk when deciding whether to fire. `chooseNextAttackerDirection` [code] sets the launch-direction flag `loc_4215` (0 or 1): the sign of the 16-bit formation anchor `loc_420e` picks which `FORMATION_X_BOUNDS` (0x4210) edge to measure against, and within 28 pixels of that edge the flag is forced away from it, otherwise a fresh random bit decides.

The demo/auto pilot that flies the ship when no human input is selected is `computeControlledObjectMoveCommand` [code]. Once every 32 frames (when `(loc_425f + 9) & 0x1f` is zero) and only while the master enable `loc_4007` and `OBJ_ACTIVE_FLAG` are both set, it folds a position weight over both object tables — seven records at `OBJ_TABLE` (stride 32) and seven at `loc_4260` (stride 5) — through `accumulateObjectPositionWeight` [code], adds a scaled offset of the anchor `loc_420e` (plus 128) against the reference `loc_4202`, halves the result, applies a random ±1 nudge, and buckets it into `OBJ_MOVE_CMD` = 0, 4, or 8 (the two travel commands the ship-mover reads). `accumulateObjectPositionWeight` itself is a pure register computation: for an active object whose Y lies in one of two 52-row bands from 128 and whose X delta from `loc_4202` is in the lower half, it folds the flag and delta bits into a 0..15 index, reads a signed step from `OBJ_STEP_TABLE` (0x1a45), and adds it to the running accumulator — so the demo ship drifts toward wherever the aliens are massing.

### Bringing the field up and tearing it down

Two sequence-state handlers bracket a round. `resetObjectRamAndAdvanceSequence` [code] clears the board at the start of the start-screen sequence: it seeds the interleaved OBJRAM shadow from a ROM template, zeroes the 64-byte sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad object-record region from `loc_4260` (a full page plus 80 bytes), clears status cell `loc_4238` and `MESSAGE_SCROLL_ENABLE` (0x40b0), points the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) two cells into the grid, arms the dwell tier `loc_4009` = 16, and bumps `SEQUENCE_STATE`. `activateObjectsAndBeginPlayPhase` [code] is the state-timer that flips play on: it ticks `loc_4009` down, and on expiry reloads it to 10, advances the sequence, sets `OBJ_ACTIVE_FLAG` = 1 to bring the whole object/AI/projectile subsystem alive, seeds the ship/target reference `loc_4202` = 128 (screen centre), refills the sixteen-byte enemy-launch sub-counter block at `loc_424a` from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears scratch cells `loc_4058`/`loc_405a`, and queues two display command words. (The command-word enqueues used here and in `handlePlayerHitEvent` return through the deliberately unnamed pure-stack epilogue `loc_090b`, which performs no work-RAM effect of its own.)

## Sound

Galaxian's audio is a set of discrete-sound latches driven a frame at a time. The hardware surface is eight write registers `SOUND_W_REG0..7` (0x6800-0x6807), a pitch latch `SOUND_PITCH_W` (0x7800), and four LFO-frequency latches based at `SOUND_LFO_FREQ` (0x6004). The code never writes those latches directly from the effect logic; instead it composes each frame into two shadow cells — a composite flag byte `loc_41c0` and a staged pitch value `SOUND_PITCH` (0x41c1) — and latches those out once at the end of the frame. Everything below is either part of that per-frame composition or an independently-clocked effect that writes its own latch.

### The per-frame driver

`driveSoundFrame` [code] is the heart of it. It opens each frame from a clean slate: it zeroes the composite flag `loc_41c0` and primes the pitch shadow `SOUND_PITCH` to 0xFF. It then runs seven channel/effect updaters in a fixed order, each of which may write into those two shadows, and finally latches the result — the composite byte to `SOUND_W_REG6` (0x6806), that same byte rotated right one bit to `SOUND_W_REG7` (0x6807), and the staged pitch to the pitch latch `SOUND_PITCH_W`. Because the updaters run in order and several of them touch the same two shadows, the frame's audible output is whatever the last effective writer left behind before the latch.

The seven updaters, in the order `driveSoundFrame` runs them, are: `armSoundSequenceOnRequest`, `updateSoundSweepVoice`, `armSoundSequenceBySelector`, `advanceAllSoundSequenceChannels`, `advancePulseToneEnvelope`, `driveRisingPitchRamp`, and `advanceGatedSquareTone`.

### Arming and running sequenced tones

Two arms feed a small note-sequence engine. `armSoundSequenceOnRequest` [seen] is a one-shot gate: it fires only when the request byte `loc_41d1` holds exactly 1, and when it does it consumes the request (clears `loc_41d1`), raises this track's active flag `loc_41d2` and its companion `loc_41d6`, and points the sequence cursor `SOUND_SEQ_PTR` (0x41d3) at that sequence's note table `loc_1e68`; any other value in `loc_41d1` leaves it untouched. `armSoundSequenceBySelector` [code] is the request-driven arm, and it only runs while the driver-enable bit (bit 0 of `loc_4006`) is set. It reads the request selector `loc_41df`: selector 6 arms its own sequence — unless `SOUND_SEQ_ACTIVE` (0x41cd) is already up, in which case it leaves it alone — by raising `loc_41cf` and `loc_41d6` and publishing pointer `loc_1ebd`; any other selector value is handed to `armSoundSequenceForSelector16` [code], which handles exactly one code, 0x16: on a match it clears `loc_41cf`, raises `SOUND_SEQ_ACTIVE` and its companion `loc_41d6`, and publishes pointer `loc_1edf`. Any selector it does not recognize is a no-op, belonging to some other arm.

`advanceAllSoundSequenceChannels` [code] runs the actual playback: it steps three sequence descriptors in turn — `loc_41d2`, `loc_41cf`, and `SOUND_SEQ_ACTIVE` — through `advanceSoundSequenceChannel` [code]. That is the note-player. A descriptor whose byte is zero is inactive and does nothing. An active channel marks the composite flag `loc_41c0` = 2 and publishes its current tone `loc_41d5` into the pitch shadow, then ticks its own duration timer `loc_41d6` down; while the timer still runs, that is all it does. When the timer expires it pulls the next command byte from the cursor `SOUND_SEQ_PTR`: the end marker 0xE0 deactivates the channel (writes 0 back to the descriptor), and any other byte is split into a new tone and a new duration — the low five bits index `SOUND_TONE_TABLE` (0x17a9) for the tone stored into `loc_41d5`, the high three bits index `SOUND_DURATION_TABLE` (0x17c8) for the timer reloaded into `loc_41d6` — with the cursor advanced past the consumed byte.

### The sweep voice and pitch selector

`updateSoundSweepVoice` [code] is the second updater and drives a warbling pitch sweep, gated on bit 0 of `loc_4006`. It decrements its own voice counter `loc_41c2`; while that stays above 1 it hands the counter pointer to the sound-counter manager; on the pass where the counter reaches 1 it reloads an idle template instead — `loc_41c2` = 0, the sweep cell one byte above it (0x41c3) = 2, and the sound counter `loc_41c4` = 160, which parks the counter past its ceiling so the sweep stops advancing until it decays back down.

The manager head is `advanceSoundSweepAndStagePitch` [code]. It bails immediately while bit 0 of gate `loc_4226` is set. Otherwise it steps its pointer forward one cell (onto the sweep cell 0x41c3); if bit 0 of gate `loc_425f` is set it hands straight to the pitch-selector dispatcher; failing that, it bumps the pointed sweep cell up by one, but only while the sound counter `loc_41c4` is still below its ceiling of 96, and then falls into `tickSoundCounterAndStagePitch` [seen]. That tail decrements the sound counter `loc_41c4` (when it is still running) and then dispatches through `stageSoundPitchBySelector` [code]. The dispatcher reads the low two bits of the pointed cell: a nonzero selector routes to `stagePitchFromSoundCounter` [code], while a zero selector stages a fixed pitch of 96 via `stageSoundPitch`. `stagePitchFromSoundCounter` recomputes the pitch from the sound counter `loc_41c4`: on an odd selector it biases the value by +96 and rotates the biased sum right one bit — the add's carry rotating back into the top bit, producing the warble — and on an even selector it passes the counter through unchanged; either way it stages the result. `stageSoundPitch` [seen] is the common sink: it simply parks a byte into `SOUND_PITCH`, the shadow the driver latches to the pitch port at the end of the frame.

### The pulse envelope and rising ramp

`advancePulseToneEnvelope` [code] ticks a two-byte envelope word (`loc_41c7` low, `loc_41c8` high). When bit 0 of the low byte `loc_41c7` is set the word is re-armed to its sentinel — low byte 0, high byte 128 — and nothing sounds; otherwise it hands the high byte to `pulseSoundToneFromCountdown` [code]. That handler idles when the high byte is zero; otherwise it stores the high byte decremented back into `loc_41c8` and stages a two-level pulse shape whose value depends on bit 2 of the decremented byte — 129 when set, 0 when clear — through `stagePitchAndRaiseSoundFlag` [code]. `stagePitchAndRaiseSoundFlag` writes (A − 1) mod 256 into `SOUND_PITCH` (so a staged 129 stores 128, a staged 0 stores 255) and raises the composite flag `loc_41c0` to 1, marking the shadow pair filled for the frame.

`driveRisingPitchRamp` [code] arms and drives a rising pitch ramp. It tests the arm byte `loc_41c9` by predecrement only — the byte is not stored back while it stays armed. While armed it advances the ramp one step through `advanceSoundPitchRamp` [seen]; when the predecrement reaches the reset point it clears the arm `loc_41c9` and reloads the ramp's {countdown, pitch} pair at `loc_41ca` to 32 (countdown) / 0 (pitch). `advanceSoundPitchRamp` works over that pair: the countdown sits one byte past its pointer and, while nonzero, it consumes one count, adds a fixed step of 4 to the pitch, stores the pitch back and publishes it to `SOUND_PITCH`, and clears the composite flag `loc_41c0` so the frame composes cleanly; a drained countdown is idle. (The arm cell `loc_41c9` is raised elsewhere — for example when a credit is added, or when certain IN0 bits are seen — so a coin insert or player action can kick off the rising ramp.)

### Gated square tone

The last updater is `advanceGatedSquareTone` [code], a gated square-wave channel. It tests its gate counter `loc_41cc` by predecrement: unless the counter holds exactly 1 (its expiry step), it drives the tone toggler `driveGatedSquareTone` [code] — and note it does not store the counter back on that path, it only tests it. On the expiry step it parks `loc_41cc` at 0 and re-arms the tone duration `SOUND_TONE_DURATION` (0x41ce) to 8. `driveGatedSquareTone` is the toggler itself: while the duration `SOUND_TONE_DURATION` is nonzero it counts one tick off it and drives `SOUND_W_REG5` (0x6805) with the frame-parity flag `loc_4007` XOR'd with bit 0 — a value whose low bit alternates every frame, giving the square wave — and once the duration is spent it writes 0 to that register to silence the tone. That `loc_4007` cell is the frame-parity flag whose bit 0 flips each frame; it gates the alternate-frame effects below as well.

### Effects clocked outside the frame driver

Three more effects run on their own clocks rather than inside `driveSoundFrame`. `driveDecayingSoundSweep` [code] runs alongside the driver in the state-1 audio-and-input service (the same place that calls `driveSoundFrame`). It acts only on even frames (bit 0 of `loc_4007` clear) and only while a countdown in `loc_41df` is nonzero: it emits that countdown rotated right two bits to `SOUND_W_REG4` (0x6804) and ticks the countdown down one, so the emitted value shrinks toward silence. Notice `loc_41df` is the same cell the sequence-arm dispatcher reads as its request selector and that `armObjectAnimAndRequestSound` writes a request code into — it is a shared sound-trigger cell, read as a selector by one path and drained as a decaying blip on register 4 by this one.

`driveSoundVoicesFromOccupancy` [code] is the background hum driver, clocked from the play pipeline and also gated to even frames on `loc_4007`. It sums a 6-row-by-10-column flag grid based at `OCCUPANCY_GRID` (0x4123, row stride 16) into an 8-bit tally seeded at 1, then lights the three sound-write latches `SOUND_W_REG0..2` — writing 1 to one latch per unit of tally, stopping the instant the running tally drains to zero (so at most three latches), and zeroing every latch from the stopping point on. When the leftover tally has nearly run dry (below 2) it raises the near-empty flag `loc_4224`, which a downstream activity timer consumes. In effect the density of the occupancy grid controls how many of the three hum voices sound.

`driveGatedSoundStepSequence` [code] is a short countdown-driven blip sequence gated by bit 0 of the enable flag `loc_4201` (armed, for instance, by a player-hit event, which also seeds the prescaler `loc_4205` = 10 and the step counter `loc_4206`). Each eligible frame it ticks the prescaler `loc_4205`, and only on the tenth frame (it reloads to 10) does it fire: it enqueues a command word carrying opcode 2 and the current step `loc_4206`, then steps that counter down. When the step counter hits zero the sequence ends — it clears the enable flag `loc_4201` and silences `SOUND_W_REG3` (0x6803).

### The LFO level

The LFO frequency is driven from the vblank interrupt through `driveSoundLfoLevel` [code]. With no reset pending (`SOUND_LFO_RESET_REQUEST`, 0x41d0, == 0) it runs the normal per-frame decay `decaySoundLfoLevel` [code]; otherwise it consumes the request and slams the full level (15) across the LFO latches. `decaySoundLfoLevel` is guarded twice: it acts only on the tick where the shared counter `loc_425f` reads 0xFF (the same cell the sweep manager tests by bit 0) and only while the level `SOUND_LFO_LEVEL` (0x421f) is still nonzero, in which case it drops the level by one and rebroadcasts. Both the decay and the reset go through `broadcastSoundLfoLevel` [seen], which saves the level to `SOUND_LFO_LEVEL` and then fans it across the four `SOUND_LFO_FREQ` latches (0x6004-0x6007), rotating the byte right one bit between each write so the four latches receive progressively shifted copies.

### Posting a request, and silence

`armObjectAnimAndRequestSound` [code] belongs to the object-animation state machine but posts a sound request as a side effect. As the entry (sub-state 0) handler of a deactivating object's animation, it seeds that object's animation timers, advances its sub-state so the entry runs only once, and then writes a position-keyed request code into the shared trigger cell `loc_41df` — 0x17 when the object's position byte is at or above 112, 0x07 when below. This is how an object's death animation kicks off its accompanying sound.

Finally, `silenceSoundAndDisableIrqStars` [code] is the hardware quiesce used when tearing a state down. It sets all four `SOUND_LFO_FREQ` latches to 1, clears the eight sound registers `SOUND_W_REG0..7`, clears the interrupt-enable latch `IRQ_ENABLE` (0x7001) and the starfield-enable latch `STARS_ENABLE` (0x7004) to halt the vblank interrupt and the stars, and drives the pitch latch `SOUND_PITCH_W` fully high (255) — leaving the audio, the video interrupt, and the starfield all silent and stopped in one sweep.

## Coins, credits, the HUD, score display, and the message scroller

Everything in this subsystem hangs off the machine's once-per-frame service pass. Each frame, after the interrupt handler has latched the raw input ports into their shadows and shifted the input history forward, it runs the coin/credit service in a fixed order and, a little later, ticks the message scroller. So the three coin routines below run back-to-back every frame, and the scroller runs every frame too; the HUD and score painters, by contrast, are demand-driven — they fire only when some producer posts a draw command into the deferred draw/sound command queue in work RAM (a command word whose high byte selects which sub-handler paints it).

### Coins and credits

The front of the per-frame coin service is `serviceCoinInputs` [seen]. It first checks the coinage/config mode in `loc_4000`: in mode 3 (free play) it simply hands off to `presetCreditCount` [code], which forces the credit count `loc_4002` to 9 and clears the coin-phase flag `loc_4001` — the machine behaves as if it always has coins. Otherwise it does edge detection across the shifted input history: it ORs this frame's `IN0_SHADOW` (0x4010) with last frame's copy `loc_4013`, complements that, and masks the result by the two older history cells `loc_4015` and `loc_4016`. The effect is a debounced press: a bit that is now active for two consecutive frames after having been inactive for the two before. If the coin bit (bit 7) survives that filter it calls `addCreditForCoin` [code]; otherwise the two low bits stand for the coin slots, and each active one bumps the coarse coin-pulse counter `loc_4004` (once for a single slot, twice when both fire).

`addCreditForCoin` [code] is the direct credit path: as long as the credit count `loc_4002` is below its cap of 99 it increments it, raises the event flag `loc_41c9`, and posts a channel-7 command — the credit/coin-line HUD redraw. At the cap it does nothing.

The coarse coin counter `loc_4004` is drained into credits by the next routine in the frame's chain, `tickCoinMeterAndAwardCredits` [seen]. It runs a small state machine around the electromechanical coin meter. While the pulse-width cell `loc_4003` is nonzero it calls `pulseCoinCounter` [seen] to keep driving the physical meter output and count that cell down. Only when `loc_4003` has reached zero does it look at `loc_4004`: if there is a coin pending it decrements it, reloads `loc_4003` to 15 (arming a fresh 15-frame meter pulse), and then awards credit according to the coinage mode in `loc_4000` — mode 3 awards nothing, mode 1 runs the two-coins-per-credit path `awardCreditEverySecondCoin` [code], mode 2 steps the credit counter twice (one coin, two credits), and any other mode steps it once.

`pulseCoinCounter` [seen] itself rotates the byte handed to it right by three bits (circularly) and writes the result to the coin-counter latch `COIN_COUNTER_0_LATCH` (0x6003); only the low bit of that latch is wired, so bit 3 of the input value is what actually drives the coin meter. It then decrements the counter at the pointer it was given (here `loc_4003`, the pulse-width countdown).

`awardCreditEverySecondCoin` [code] is a two-phase toggle over the coin-phase flag `loc_4001`: on the first coin of a pair (flag bit clear) it delegates to `setCoinPhaseFlag` [code], which just raises the flag to 1; on the second coin (flag already set) it clears `loc_4001` and delegates to `incrementCreditCount` [code] to actually award the credit.

`incrementCreditCount` [code] is the shared credit-stepping primitive used by both the two-coin path and the coarse-meter path (both point it at `loc_4002`). It walks the counter toward a ceiling of 99: at 99 it stops, past 99 it hands off to `clampCreditsToMax` [code] to pin the cell back to exactly 99, and below 99 it increments, raises the ready flag `loc_41c9`, and posts a channel-7 credit-HUD redraw command. `clampCreditsToMax` [code] does nothing but that overshoot repair — it writes 99 into the cell.

The last coin routine in the frame chain is `updateCoinLockoutFromCredits` [code], which drives the coin-lockout latch `COIN_LOCKOUT` (0x6002) purely from the credit count `loc_4002`. At nine credits or more it takes the `clearCoinLockout` [code] path, which writes 0 to the latch; below nine it writes 1. `clearCoinLockout` [code] is the trivial zero-write helper.

Credits also feed the top-level flow. `advanceGameStateOnCredit` [code] is the tail of the attract-sequence handler: when the credit count `loc_4002` is nonzero it advances the game-state index `GAME_STATE` (0x4005) and wipes the attract sub-state cluster — the frame flag `loc_4007`, the sequence step `SEQUENCE_STATE` (0x400a), `loc_41c2`, the sound-sweep countdown `loc_41df`, and the scroller-enable flag `MESSAGE_SCROLL_ENABLE` (0x40b0). With no credit banked it is a no-op, which is what keeps the machine looping in attract until someone pays.

### Start-button lamps and starting a game

`driveStartButtonLamps` [code] keeps the two start-button lamp latches `START_LAMP_0` (0x6000) and `START_LAMP_1` (0x6001) in step with the credit count, gated by bit 5 of the free-running frame-phase counter `loc_425f`. With that bit clear it forces both lamps off; otherwise zero credits leaves them untouched, one credit lights lamp 0, and two or more lights both.

Two sequence handlers borrow that lamp logic. `holdStartLampsThenAdvanceSequence` [code] ticks the countdown cell `loc_4019` each frame; while it stays nonzero it just keeps the lamps updated through `driveStartButtonLamps`, and on the zero-crossing it advances `SEQUENCE_STATE` (0x400a) and clears the 128-byte flag-bits block at `FLAG_BITS_BASE` (0x4100). `blankVramRowsThenDriveStartLamps` [code] is the sequence state that clears the start screen: it fills two 28-cell blank-tile rows through the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) (skipping a four-cell gap between them), then ticks the dwell tier `loc_4009`; while rows remain it returns, and on the last row it advances the sequence, clears the screen-flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y` (0x7006/0x7007) and the direction flag `loc_4018`, posts two command words, and drives the lamps one last time.

`startGameRoundAndClearScores` [code] is the actual game/round-start entry. It stores the incoming spawn/player-count word into `CURRENT_PLAYER` (0x400d), blits the 32-byte ROM row template at `loc_051b` into the packed-flag buffer `PACKED_FLAG_BITMAP` (0x4180), and — when config bit 0 in `loc_401f` is set — arms the sub-state advance gate. It then drops the machine into play: `SEQUENCE_STATE` (0x400a) to 0, `GAME_STATE` (0x4005) to 3, the play-mode gate `loc_4006` to 1, and `loc_41d1` to 1. Finally it posts three command words — a channel-6 start message and two channel-4 commands that clear the two players' score fields — which is where its "clear scores" role comes from.

### The score fields and their display

Scores live as three-byte packed-BCD fields in work RAM: player 1 at `PLAYER1_SCORE_BCD` (0x40a2), player 2 at `PLAYER2_SCORE_BCD` (0x40a5), and the high score at `HIGH_SCORE_BCD` (0x40a8). They are painted into vertical tilemap columns because the display is rotated; every painter walks its cursor up the screen one row at a time (a −32 stride).

The lowest primitive is `drawBcdDigit` [code]: it isolates one BCD nibble, paints it as a font glyph (digit + 0x90, so the contiguous tiles 0x90–0x99), advances the cursor, and manages leading-zero suppression through a blank budget — while the budget is nonzero a leading zero is drawn as a blank tile (the 0x80 base wraps mod 256 to the blank tile 0x10) and the budget is spent, and the first significant digit ends suppression. `drawBcdNumberColumn` [code] drives it six times: it walks three packed-BCD bytes downward from the most-significant byte of the source, painting high nibble then low, up the column, with a four-digit blank budget. `selectCurrentPlayerScore` [code] just returns the active player's score-field base (0x40a2 or 0x40a5 keyed on `CURRENT_PLAYER`).

`drawScoreToSelectedPlayerField` [code] chooses the destination VRAM column by a selector — the primary field `DIGIT_FIELD_PRIMARY` (0x5381) when zero, the alternate `DIGIT_FIELD_ALT` (0x5121) otherwise — and paints the BCD column there. `drawHighScoreDigits` [code] is the same idea pinned to the fixed high-score field `loc_5241`. `drawScoreFieldByIndex` [code] is the dispatcher over those: index 0 repaints player 1 (primary field), index 2 repaints the high score, and index 1 repaints player 2 — but only when the two-player-active flag `loc_400e` is set, whose value doubles as the alternate-field selector; an index of 3 or more recurses down, repainting every field from index−1 to 0. `clearAndRedrawScoreField` [seen] wraps that with a wipe: it zeroes the three digit bytes of the selected field plus a per-player companion scratch byte (`loc_40ad` for player 1, `loc_40ae` for player 2; the high score re-zeroes its own first byte), then repaints through `drawScoreFieldByIndex`; index 3+ likewise descends over all lower fields. This is what the channel-4 commands from `startGameRoundAndClearScores` reach.

Scoring itself flows in from `awardKillScoreByBandAndDeactivate` [code]. When an object is hit it deactivates the record (slot bytes to 0/1/0) and sizes the award by which of three bands the object's packed field (record byte 7) falls into against the threshold 0x50 — each missed band bumps the request parameter and drops the field by 16. A matched band immediately posts a channel-3 score-add command; on band-exhaust it raises the inhibit word `loc_422b` (to 0xf001), folds in a neighbour bonus when the active-neighbour count `ACTIVE_NEIGHBOR_COUNT` (0x422a) is exactly two, records the bonus in `loc_422d`, and posts the folded channel-3 request. The channel-3 handler adds the corresponding packed-BCD increment into the current player's score, then repaints that score through `drawScoreToSelectedPlayerField`; if the new total beats the stored high score it copies it into `HIGH_SCORE_BCD` (0x40a8) and repaints the high score via `drawHighScoreDigits`; and along the way, if the total has crossed the bonus threshold, it calls `awardBonusMarker`.

`byteToPackedBcd` [code] is the binary-to-decimal helper that supports the numeric HUD: it returns its input modulo 100 as two packed decimal digits (tens in the high nibble, units in the low). It is what the credit/coin-line HUD handler uses to render the credit count as two digits when a channel-7 command drains.

### The reserve-life markers and the bonus award

`drawMarkerRow` [code] paints the five-slot reserve-life row at `MARKER_ROW_VRAM` (0x539e): it stamps as many 2×2 marker glyphs (tile 102) as the count says, growing upward, then blanks the remaining slots until the signed slot counter goes negative. When the object-active flag `OBJ_ACTIVE_FLAG` (0x4200) is set — a ship currently in play — the displayed count is dropped by one, and if that empties it, every slot is blanked instead. `awardBonusMarker` [code] is the one-shot that grants a marker: it indexes the per-player bonus-awarded flag table at `loc_40ad` by `CURRENT_PLAYER` (0x400d), and if that player's slot is already flagged it does nothing; otherwise it flags the slot, raises the sound-envelope trigger `loc_41c7`, bumps the marker counter `loc_421d`, and repaints the row with the new count. Those same `loc_40ad`/`loc_40ae` bytes are the score-field companion scratch that `clearAndRedrawScoreField` zeroes at game start, which is what re-arms the bonus for a fresh game.

### The player-up status column

A small VRAM column shows which player is currently up. `selectPlayerStatusVram` [code] returns its base — `PLAYER1_STATUS_VRAM` (0x5340) for player 1, else `PLAYER2_STATUS_VRAM` (0x50e0). `paintPlayerStatusColumn` [code] paints the three cells of that column (top cell = the player code + 1, middle tile 0x25, bottom tile 0x20) and, only when the caller's bit-4 flag is clear and the play-mode gate `loc_4006` is zero, clears the status-repaint latch `loc_40ab`. `repaintPlayerStatusColumn` [code] wraps it around `CURRENT_PLAYER`: with bit 4 clear it paints the active player's column, and with bit 4 set it blanks that column's three cells (tile 16) and, when the two-player flag `loc_400e` is set, also paints the other player's column. `repaintPlayerStatusColumnIfSaved` [code] gates that on the latch `loc_40ab` being nonzero, and `repaintPlayerStatusColumnFromModeGate` [seen] is the top of the chain: when the mode gate `loc_4006` is nonzero it saves that value into `loc_40ab` and repaints; when it is zero it repaints only if the latch was already set. The latch is thus what keeps the indicator repainting after the mode has gone quiet.

### The message scroller

Text messages are painted by `renderMessageColumn` [seen], selected by an index into the message pointer table `MESSAGE_PTR_TABLE` (0x235c). Each record yields a destination word and the text bytes that follow it. The top two bits of the index pick the mode: bit 7 blanks each of the message's cells up the column (writing tile 64 to the 63 terminator), bit 6 sets the message up for scrolling — recording the destination and text pointers into `MESSAGE_DEST_PTR` (0x40b5) and `MESSAGE_TEXT_PTR` (0x40b3), deriving the per-column countdown cell in the `loc_4020` table and stashing its address in `MESSAGE_CURSOR_PTR` (0x40b1), clearing the whole 32-cell column (tile 16), seeding the countdown byte, and raising `MESSAGE_SCROLL_ENABLE` (0x40b0) — and with neither top bit set it simply paints the whole string at once (each source byte mapped to a glyph by subtracting 48) up the column.

Once a message is armed, `advanceMessageScroller` [seen] reveals it over time. It runs every frame, and while `MESSAGE_SCROLL_ENABLE` (0x40b0) is set it consults the countdown cell named by `MESSAGE_CURSOR_PTR`: while that cell's low three bits are still set it merely ticks it down (via `endMessageScrollOnExpiry`), so a glyph only appears every eighth frame; on the eighth it reads the next character from `MESSAGE_TEXT_PTR`, and if that is the terminator (63) it just finishes the countdown, otherwise it advances the text pointer, writes the glyph (character − 48) into the destination cell, steps `MESSAGE_DEST_PTR` up one row (−32), and ticks the counter. The high bits of that countdown cell track how much of the message remains, so when it reaches zero the message is done.

`endMessageScrollOnExpiry` [seen] is the shared tail that does the ticking: it decrements the counter at its pointer and, on the exact zero-crossing, clears `MESSAGE_SCROLL_ENABLE` (0x40b0) to stop the scroller. `endMessageScrollOnExpiryFromDe` [seen] is the same thing entered with the counter pointer arriving in the alternate register — it just forwards to `endMessageScrollOnExpiry`.

Several producers feed the scroller. `advanceObjectAndQueueMessageColumn` [seen] is an object-AI state that, after its per-object dwell timer runs down, posts a channel-6 command carrying that object's payload selector (record byte 7 plus 75) and advances the object's state — the mechanism by which an in-world object triggers a message. `emitMessageColumnsThenAdvanceSequence` [seen] is the attract-sequence handler that spills a message out column by column: after resetting the strided table it runs a two-tier dwell over `loc_4008`/`loc_4009`, and on each expiry of the low tier it reloads that tier to 80 and posts a channel-6 command whose parameter tracks the mid-tier count (mid count + 6); when the mid tier finally expires it advances `SEQUENCE_STATE` (0x400a), reloads both tiers, and clears the sprite-source block and the redraw count `DRAWN_COLUMN_COUNT` (0x4241). `postCreditAndMessageDrawsAndAdvance` [code] is a simpler sequence handler that posts a channel-7 credit-count redraw and a channel-6 message draw, advances the sequence step, and re-arms the two-tier dwell cascade (`loc_4008` = 96, `loc_4009` = 16).

### Text columns

Underneath both the settings display and the descriptor-driven text is a trio of column painters. `drawTextColumn` [code] is the loop: for each of `count` characters it reads a source byte, maps it to a tile by subtracting the '0' code (48), writes it, and steps the source forward and the destination by a signed stride (a negative stride walks up a column; a count of zero means a full 256 passes). `drawTextColumnFromDescriptor` [code] unpacks a five-byte descriptor (source word, destination word, count byte) at its pointer and draws that many characters up the column (stride −32). `drawTextColumnByIndex` [code] indexes the ROM text-descriptor table `TEXT_DESCRIPTOR_TABLE` (0x1cf6) by A (five bytes per record) and paints that descriptor's column.

### The attract input/sound scan and the screen fill

When the machine is in its alternate-frame mode (selected by `loc_401a`), the interrupt routes to one of two chains. Mode 1 runs the input/sound scan, headed by `driveSoundFrameAndScanInput` [code]: it ticks the sound driver and the decaying sweep, pets the watchdog by reading `SOUND_PITCH_W` (0x7800), reads `IN0` (0x6000) and — if any of its arm bits (7, 1, 0) is set — raises the pitch-ramp arm cell `loc_41c9`, then falls into the scan chain carrying that IN0 byte. `requestSoundOnInput1AndContinueScan` [code] reads `IN1` (0x6800) and, if either low bit is set, seeds the sound-request byte `loc_41df` to 0x16, then continues, handing both port bytes onward. `requestSound6AndContinueInputScan` [code] tests the folded ports for bits 2–3 and, if set, seeds `loc_41df` to 6, then continues. `armInputFlagAndDrawInputColumns` [code] tests the folded ports for bit 4 (start) and, if set, raises the companion flag `loc_41cc`, then delegates to the settings/screen-fill init.

That init, `drawInputTextColumnsAndSeedScreenFill` [seen], decodes three two-bit DIP fields — `IN1` bits 6–7, `IN2_PORT` (0x7000) bits 0–1, and `IN2_PORT` bit 2 — into text-descriptor indices and paints each of those columns (the coinage/lives/bonus settings text). Then, unless the service/test bit (IN0 bit 6) is asserted, it seeds the screen-fill state: it clears the play-mode gate `loc_4006`, sets the alternate-frame selector `loc_401a` to 2 (arming the fill), seeds the dwell pair `loc_4008`/`loc_4009` (16/48), points the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) at `VRAM_BASE` (0x5000), clears the four-byte lamp/coin latch block at 0x6000 (both start lamps, coin lockout, coin counter), and silences the sound hardware.

Mode 2 of the alternate frame is the animated screen fill, headed by `advanceScreenFillStrip` [code]: it pets the watchdog, and if the strip gate `loc_4008` is zero there is nothing to draw so it restarts the outer dwell; otherwise it loads the write cursor and draws the strip's first half. `drawScreenFillStripFirstHalf` [code] stamps a run of two-tile pairs (tiles 48/50) forward from the cursor and flows into `drawScreenFillStripSecondHalf` [code], which stamps a further sixteen pairs (tiles 52/54), saves the advanced cursor back to `VRAM_WRITE_PTR`, and ticks the strip dwell `loc_4008`; on its expiry it calls `restartScreenFillOnDwellExpiry`. `restartScreenFillOnDwellExpiry` [seen] ticks the high dwell tier (the byte just past its pointer, `loc_4009`): if that is already zero or reaches zero on this tick it re-seeds the whole fill through `resetScreenFillState`; while it is still counting nothing happens. `resetScreenFillState` [seen] is the input-gated re-seed itself — unless IN0 bit 6 is asserted it rewinds `VRAM_WRITE_PTR` (0x400b) to `VRAM_BASE` (0x5000), re-arms the fill length in `loc_4008` to a full page (32), and clears the alternate-frame selector `loc_401a` and the game state `GAME_STATE` (0x4005), which drops the machine back to its normal per-state dispatch.

### A shared helper

`reloadExpiredCounterAndTally` [seen] does not belong to the coin/HUD flow proper — it is a small shared counter-refill helper called by the enemy-launch pacing timer. It copies one reload byte out of the ROM reload table `SUBCOUNTER_RELOAD_TABLE` (0x15e3) into an expired counter cell to re-arm it, then bumps and returns the running refill tally.

Finally, the command-word enqueues used throughout this subsystem (the channel-3/4/6/7 posts) return through a shared, deliberately-unnamed stack-only epilogue, `loc_090b`, which merely restores the caller's saved pointer and returns with no work-RAM effect of its own.

## Tile / VRAM drawing primitives and coordinate mapping

The tilemap lives at VRAM_BASE (0x5000), a grid whose logical rows are 32 cells wide. Two facts about that grid are assumed everywhere below: incrementing a cell address by one steps one cell along a row, and adding or subtracting 0x20 (32) moves to the same position one row away. The visible playfield is inset two cells from each row start and only 28 cells wide, so the full-screen fill handlers seed their cursor at VRAM_BASE+2 and paint 28-cell strips inside a 32-cell stride — the extra four cells per row are the off-screen margin.

### Packed-coordinate to cell address

Objects that live on the tilemap carry their position as a single packed byte rather than an address, and mapPackedCoordToVram [code] is the translator. It shuffles the byte's nibble fields into an offset from VRAM_BASE: the low nibble rotated right two yields both the address high byte (its low two bits, 0..3, so the reachable page is 0x5000..0x53ff) and the top two bits of the low byte; the high nibble is treated as a three-bit field whose low bit rotates out to become a live-out carry, whose remaining bits become a live-out A (coordinate bits 6..5), and whose complemented running sum folds into the low four bits of the address. The finished cell address is handed back in HL. The carry live-out is exactly the coordinate's bit 4, and every caller branches on it to choose between a wide block and a tall pair, so the mapping and the shape decision come out of the same pass.

### The two stamping primitives

Every tile write in this subsystem bottoms out in one of two primitives. stampTilePair [code] writes a consecutive pair: the seed tile at the destination and seed+1 at the very next cell, then it advances the destination past the pair by an additional caller-supplied stride and steps the tile code by two, returning the advanced pointer and code so a caller can chain pair after pair. Because the store truncates to a byte, a seed of 0xff writes 0xff then 0x00. drawDoubleHeightTile [code] instead writes a vertical pair for a double-height glyph: the seed tile at the destination and seed+2 in the cell one row (+0x20) below, leaving the pointer registers alone. The +2 code step is the second glyph in a stacked top/bottom pair.

### 2x2 blocks, and the same block grown upward

drawTileBlock2x2 [code] builds a square from a seed by calling the pair stamp twice with a stride of 31: the first pair (seed, seed+1) lands, and because the stamp already advances one cell past the pair, the extra 31 makes a net +32 so the second pair (seed+2, seed+3) sits directly below — a 2x2 block laid tiles seed..seed+3, caller's DE preserved. drawBottomTilePairRestoreDe [code] is the shared tail those block writers reach for the second pair: it stamps the bottom pair from whatever the caller already staged, then restores the DE the caller had saved and hands it back. drawTileBlock2x2Up [code] is the upward counterpart — it stamps with a stride of -33 (net -32, one row up) so the top pair sits at the pointer, then steps the tile code back four and stamps a second pair one row above, so the block grows toward the top of the screen while keeping its four codes in reading order. drawTileBlock2x2AtDe [code] is a small adapter that swaps DE and HL so a destination arriving in DE becomes the draw target (the old HL is handed back in DE), then draws an ordinary 2x2 block there; it is the entry the table-driven block draws use.

A family of fixed-seed wrappers pins these primitives to the decorative glyph family based at code 0x2c (44). drawFixedTileBlock2x2 [code] lays a 2x2 block seeded with tile 44 (codes 44..47). drawFixedTileBlock2x2Up [code] draws the upward block seeded with tile 46, which — after the upward writer's back-step — places codes 46,47 on the lower row and 44,45 above it. drawFixedTilePairHorizontal [code] stamps a single horizontal pair from seed 44 and returns the advanced pointer for a caller's loop, and drawFixedTilePairVertical [code] stamps the double-height pair from seed 44. These fixed-44 forms are the ornamental border/figure pieces the display list paints.

### 4x4 indicator forms

A larger 4x4 region anchored at loc_51da (0x51da) holds the indicator/marker figures. blankTileBlock4x4 [code] clears it, writing the blank code 0x40 to four rows of four cells with a 32-cell stride between row starts (note this uses tile 0x40 as its blank, distinct from the 0x10 blank the screen fills use). blank4x4AndDraw2x2Icon [code] clears that region and then overlays a single 2x2 icon seeded with tile 96 (0x60) at loc_51fc (0x51fc). draw4x4TileForm [code] is the form selector over the region: form 0 is the blank-then-icon overlay, form 1 is a bare blank, and any other form folds (form-2) into the mid bits of a complemented tile code over base 0xc0 and stamps four abutting 2x2 blocks — at loc_51da, loc_51dc (0x51dc), loc_521a (0x521a) and loc_521c (0x521c), a contiguous 4x4 cell area — each block seeded four codes past the previous one so the sixteen tiles run consecutively.

### Table lookups, animated variants, and the glyph/block dispatch

drawIndexedTileBlock [code] looks a block-base tile up in TILE_BLOCK_TABLE (0x215b) by index and stamps that 2x2 block at the pending destination. drawSelectedTileBlockOrFallback [code] wraps that with a sign test: a non-negative selector goes through the table lookup, while a negative selector stamps a fixed fallback block based at tile 0xa4. drawTileGlyphOrBlock [code] is the shape dispatch keyed on the mapper's carry — carry set means "wide", so it draws the selected 2x2 block (with the 0xa4 fallback for a negative index); carry clear means "tall", so it fetches the index's tile code from the glyph table at loc_2157 (0x2157) and paints a double-height glyph at the incoming cell.

Two register-compute helpers give tilemap figures a flicker/animation. computeTileVariantFromTimer [code] folds a value into a 2-bit variant index: at or above the range limit 112 it saturates to the 0x80 out-of-range marker, otherwise it swaps the nibbles of the per-frame counter loc_425f (0x425f), adds the value and the carry-in, and keeps the low two bits — so the chosen variant cycles as the frame counter turns. computeTileVariantFromValueAndTimer [code] is the front door to it: it applies the same 112/0x80 saturation, then takes the value's low nibble and sets a carry-in whenever the frame counter's low nibble is smaller, before folding through the timer routine. The result is a small animated offset added to a figure's base tile so it shimmers frame to frame.

### The two packed-coordinate figure handlers

These pieces come together in two display-list draw handlers reached from the draw-dispatch jump table at 0x203d. drawFixedTileFigureAtPackedCoord [code] maps a packed coordinate to its cell and stamps the static 0x2c-family figure there — a fixed 2x2 block when the coordinate's bit 4 is set, otherwise a fixed vertical pair. drawAnimatedTileFigureAtPackedCoord [code] is its animated sibling: it maps the same coordinate, biases that coordinate into a timer-animated variant, and then draws — a 2x2 block selected by the variant when bit 4 is set, or a double-height glyph pulled from the loc_2157 table otherwise. The mapper stashes the coordinate so the variant fold biases the figure by its own position, and it carries the VRAM base along for the block path's pointer swap. loc_090b [code] is the deliberately-unnamed shared stack epilogue on the command-queue path these handlers feed — it simply restores the caller's saved pointer and returns, with no memory effect.

### Periodic tile-column redraw

The playfield's animated column band is repainted by redrawTileColumnsPeriodically [code], one of the per-frame subsystem updates a gameplay sequence state runs. It is gated by DRAWN_COLUMN_COUNT (0x4241): fewer than two counted columns and it does nothing; otherwise it draws count-1 columns. Which action it takes depends on the low six bits of frame counter loc_425f — on phase 0 it wipes the columns, on phase 32 it repaints them, and does nothing on every other frame. The repaint's first column is sourced from a frame-selected row: the frame counter's top two bits pick one of the four 3-byte source rows in TILE_COLUMN_TABLE (0x039a), which is why the band cycles through a small animation; the remaining columns stream consecutively from TILE_COLUMN_TABLE_CONT (0x03a6).

Both the wipe and the repaint are built on a matched pair of column primitives that walk the tilemap the same way, starting at loc_5193 (0x5193). drawTileColumnTriple [code] copies three source bytes up one column — each byte lands at the destination, whose low address byte then steps up one row (-0x20) within a fixed page — and after the three cells it advances the low byte by 98 (0x62) to line up the next column's start, returning the advanced source and destination so successive columns chain. blankTileColumns [code] mirrors that traversal but stamps the blank tile 0x10 into three cells per column instead of copying, advancing +98 to the next column and looping under a column count that wraps 0 to 256.

### Full-screen fill and blank sequence steps

Several sequence-state steps clear or repaint the whole screen a strip at a time, walking VRAM_WRITE_PTR (0x400b) down the page across successive frames. primeVramFillAndAdvanceStep [seen] sets one of them up: it clears the 128-byte flag block based at FLAG_BITS_BASE (0x4100) and the status bytes loc_425f and loc_4224 (0x4224), points the write cursor at VRAM_BASE+2 (the two-cell inset), arms the dwell tier loc_4009 to 32, and steps SEQUENCE_STATE (0x400a) to the fill step. fillVramRowThenResetObjectState [seen] then runs each frame: it paints a 28-cell strip of tile 0x10 at the cursor and advances the cursor a full 32-cell row, ticking the dwell tier; while the tier still counts it simply waits, and on its expiry it advances the sequence, re-arms the two-tier dwell cascade (loc_4008=64, loc_4009=4), clears the 48-byte active-object block based at OBJ_ACTIVE_FLAG (0x4200), zeroes the FLIP_SCREEN_X (0x7006) and FLIP_SCREEN_Y (0x7007) latches and the direction flag loc_4018 (0x4018), raises status byte loc_4238 (0x4238), and reseeds the interleaved object-shadow field from the ROM template at OBJ_SHADOW_RESEED_TEMPLATE (0x1db1). blankScreenRowsThenAdvanceSequence [code] is the play-state variant that blanks 32 cells of tile 0x10 per frame, advances the cursor one row, and ticks the phase counter loc_4009 until the last phase, when it advances the sequence and reseeds the object shadow. blankVramRowThenResetSpriteState [code] is a third variant that first clears the strided work-RAM table, blanks a 28-cell row and steps the cursor a row, and on dwell expiry advances the sequence, clears the 256-byte object-source block at SPRITE_SOURCE_OBJ_BASE (0x42b0, a zero count meaning a full 256-byte wipe) and the 64-byte sprite shadow at SPRITE_SHADOW_BASE (0x4060), re-arms the dwell cascade, reseeds the object shadow, and queues a command word.

### Projectiles: integrate and render, then collide

Two related passes drive the moving shots, and unlike everything above they render into the sprite shadow rather than the tilemap. advanceAndRenderProjectiles [code] integrates and draws the seven moving-object records based at loc_4260 (0x4260). Each record holds two five-byte sub-slots, and the low bit of frame counter loc_425f picks which sub-slot leads this frame while the trailing one only gets its sub-position bumped by two. For an active leading sub-slot it advances the sub-position, deactivates on overflow, integrates the 16-bit position by twice the signed velocity byte, and deactivates the slot when the position leaves the vertical window; a deactivated slot has its active, sub-position and high bytes zeroed. It then writes each shot's Y and tile code into the sprite shadow based at loc_4081 (0x4081), mirroring the Y and flipping the sign of a +/-1 code nudge on the first three records according to direction flag loc_4018.

Collision is a second pass. flagProjectileHitsOnPlayer [code] runs only when projectiles are enabled (bit 0 of OBJ_ACTIVE_FLAG set) and then walks all fourteen entries based at loc_4260 on a five-byte stride, handing each to the per-entry test with a fixed band delta of 5 (that delta is the stride the loop leaves in register E, not a caller value). flagProjectileHitOnPlayer [code] is that per-entry test: it skips inactive entries, then box-tests the entry's X against the player-X reference loc_4202 (0x4202) across a near/far Y band — the far band demands X within the small delta of the player, the near band first requires the entry's shifted Y to sit within nine units and then X within eleven — and on an overlap it deactivates the struck entry and raises HIT_EVENT_FLAG (0x4204).

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs. Most recently lifted is the RST-08 score/HUD cluster: the BCD score-update and the HUD sub-dispatch
  routine each inline the rst-08 conditional early-return (its shared vector dissolves), and the display-list
  slot decoder absorbs its jp(hl) draw-handler table into a direct switch. They are correct-by-equivalence but
  still carry `loc_<addr>` names and `[code]` certs pending their own understanding pass. What remains translated
  is the born-live spine only — the vblank NMI vector, the shared rst-28 primitive, and the top-level frame loop.
