# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–4.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

Several of the machine's most-reused building blocks sit in the lowest bytes of ROM, where the processor's single-byte restart instructions can reach them cheaply, with two more just above. They are small, they take their arguments in registers, and almost every larger routine leans on them.

**Random numbers.** `advanceRandomSeed` [seen] is the game's pseudo-random generator, a linear-congruential step over one persistent byte, `RNG_SEED` at 0x401e. Each call reads that byte, computes `seed*5 + 1` truncated to eight bits, writes the result back, and then hands the caller that very same new byte as this draw's random value — there is no separate output register set aside for the draw; the stored seed and the returned value are one and the same. Because the seed lives in work RAM and is never reset per-call, successive draws walk the LCG steadily forward across the whole session, each frame's request continuing where the last left off. The object AI is the main consumer: the formation-reseed handler `reseedFormationObjectState` rolls a fresh vertical position for a re-entering object out of it, and `chooseNextAttackerDirection` masks a single low bit off a draw to decide which way a new attacker peels away from the formation (falling back to that random bit only when the attacker is not already pinned against a screen edge).

**Memory fill.** `fillMemoryBlock` [code] is the machine's RST-10 primitive. Given a destination pointer, a fill value, and a count, it stores the value, advances the pointer, and repeats — storing first and decrementing the count afterward — until the count runs out, then returns the pointer left sitting just past the filled region and a spent count of zero. One consequence is worth stating plainly: the count is decremented as a byte, so a caller that arrives with a count of 0 does not fill nothing, it wraps to 255-and-continue and fills a full 256 bytes. The fill target is not restricted to plain work RAM; the same primitive paints the video tilemap, which is why the boot handler `fillScreenThenLatchConfigAndAdvanceState` uses it to lay 32-byte rows of the blank tile across the 0x5000-0x53ff screen memory, while the various row-blanking and object-RAM-reset routines call on it to clear whole regions in one sweep.

**Table fetch.** `fetchIndexedTableByte` [code] is the machine's RST-20 primitive, the standard "look one entry up in a table" step. It treats the accumulator as an 8-bit index and the pointer register as a table base, forms `base + index` carrying the addition into the high byte — a genuine 16-bit pointer advance, so a table is free to straddle a 256-byte page boundary — and reads the byte living at that computed address, returning it to the caller and leaving the advanced pointer behind for reuse. `drawIndexedTileBlock` uses it to pull a graphic out of its tile table, and the boot handler uses it to index a coinage table by the coin-input bits and stash the selected coinage byte at 0x40ac.

**The vblank interrupt.** Once per displayed frame the vertical blank asserts the processor's interrupt; the frame handler saves six register pairs on entry, performs the frame's work, and then finishes at `rearmVblankInterruptAndRestoreRegs` [code] at 0x00d8. This epilogue's first act is to write 1 into the `IRQ_ENABLE` latch at 0x7001, the hardware interrupt-enable. That write is load-bearing rather than incidental: the handler's prologue cleared that same latch to acknowledge the current interrupt, so re-arming it here is precisely what allows the *next* frame's vblank to fire. Omit this one store and only the first interrupt of the whole run ever arrives, after which the per-frame loop simply freezes. Having re-armed the latch, the epilogue restores the six saved pairs in the order that unwinds the prologue's save (iy, ix, hl, de, bc, and af last, so the caller's flags and accumulator overwrite the value 1 that was just used for the latch write) and then returns through the interrupted address, resuming whatever the main loop was doing when the frame boundary struck. More than one entry path through the per-frame work converges on this single shared epilogue.

**A shared tail.** `loc_090b` [code] is a deliberately-unnamed one-line epilogue with no memory effect of its own: it restores the caller's saved `HL` pointer and returns. It exists only as the common exit of the command-queue enqueue path — the write-head commit step `commitQueueWriteHead` and the code that falls through into it both end their work here.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

Galaxian runs its whole front-of-house life — power-on screen clear, attract sequence, credit-and-start handshake, and the setup that hands control to actual play — as a two-level state machine ticked once per video frame. The outer level is a game-state index in GAME_STATE (0x4005); the inner level is a sub-state index in SEQUENCE_STATE (0x400a). Each frame the service routine reads GAME_STATE and picks one of five handlers — the boot fill, the attract-sequence driver, the credit/idle driver, and the two play drivers — and each of those in turn reads SEQUENCE_STATE and picks one entry from its own sub-state table. Almost every routine below is therefore a leaf reached by that index, and most of them do one of three things: run a timer down, and on its zero-crossing bump SEQUENCE_STATE so the next frame lands on the next leaf; arm or test a one-byte gate; or push a word onto the command queue.

### The dwell cascade: three adjacent bytes at 0x4008/0x4009/0x400a

The spine of the machine is a run of three consecutive work-RAM bytes. The lowest, loc_4008 (0x4008), is a frame prescaler / short sub-timer; the middle, loc_4009 (0x4009), is the dwell tier that actually decides how long a sub-state lingers; and the top of the run is SEQUENCE_STATE (0x400a) itself. The shared primitive that couples them is tickCascadeCountdown [seen]: it decrements the byte it is pointed at, and *only* when that byte reaches zero does it step to the next byte in the same page and increment it — a carry rippling upward. Because these three cells are adjacent, a carry out of the dwell tier is literally an increment of SEQUENCE_STATE, i.e. an advance to the next sub-state. (A current subtlety worth stating: a couple of the seeding routines write 0x4008/0x4009 as a single 16-bit value — enterSequenceStep1 writes 0x0303, initSequenceEnableStarfield writes 0x1060 — but the timers always read them back as two independent bytes, so those seeds are really "sub-timer = 3, tier = 3" and "sub-timer = 96, tier = 16".)

Two handlers ride that primitive at different rates. tickSequenceDwellTimer [code] simply points at the dwell tier loc_4009 and ticks the cascade, so it counts one dwell unit per frame and advances SEQUENCE_STATE when the tier empties. tickPrescaledSequenceTimer [seen] adds a divider in front: it decrements the sub-timer loc_4008 every frame and does nothing else until it wraps; on the wrap it reloads loc_4008 to 60 and *then* ticks the dwell tier via the same cascade — so a sub-state driven this way lingers 60× longer per dwell unit. armStepCountdownAndTickSequenceTimer [seen] is the sub-state-1 entry that first raises the one-frame dwell flag loc_4019 (0x4019) and then runs the prescaled tick, so its state both arms that flag and counts down.

enterSequenceStep1 [code] is the sequence-state handler that hard-sets SEQUENCE_STATE to 1 (rather than incrementing it) and re-seeds the cascade to the very short 3/3 dwell — a deliberate jump back to step 1 with a brief hold. reloadSequenceDwellTimer [code] is the shared re-arm that stamps the dwell tier loc_4009 back up to 80 frames after a handler has chosen the next state. advanceSubstateAndReloadDwell [code] is the common "move on" tail: it bumps the counter it is handed (its callers pass SEQUENCE_STATE) and then re-arms the dwell tier through reloadSequenceDwellTimer, so the machine steps to the next sub-state with a fresh 80-frame budget. setSequenceStateByModeAndReloadDwell [code] is the variant used when the target step depends on the mode flag loc_4006 (0x4006): it stamps the counter to 4 when bit 0 of that flag is set and to 14 when it is clear, then re-arms the dwell tier the same way — one branch is the short path, the other the long "run the whole demo" path.

### Boot: clearing the screen and latching the machine's configuration

Game-state 0 is fillScreenThenLatchConfigAndAdvanceState [seen], the power-on handler. On each frame it blanks a 32-byte block of tilemap at the cursor VRAM_WRITE_PTR (0x400b) with the blank tile and advances that cursor, sweeping the whole VRAM_BASE (0x5000) page across successive frames while a per-state timer in loc_4008 counts down. When that timer expires the screen is clear and the handler performs the one-time boot latch: it resets the state cluster (loc_4007 = 1, mode flag loc_4006 = 0, GAME_STATE = 1, SEQUENCE_STATE = 0), then folds the operator configuration out of the input shadows into flag cells — the lives/difficulty field into loc_4000 from the top bits of IN1_SHADOW (0x4011), a config bit into loc_401f (0x401f) from IN2_SHADOW (0x4012), and the cocktail/flip bit into loc_400f (0x400f) from IN0_SHADOW (0x4010) — and selects a coinage byte into loc_40ac (0x40ac) by indexing a 4-entry table with the low two bits read live from IN2_PORT (0x7000). It also unpacks the packed flag bitmask into the flag block, seeds the object-RAM shadow from ROM, writes the first three player-1 status glyphs into VRAM around PLAYER1_STATUS_VRAM (0x5340), and posts two deferred command words. Having set GAME_STATE to 1, the next frame drops the machine into the attract sequence.

initSequenceEnableStarfield [seen] is sub-state 0 of that attract driver. It enqueues two setup command words, turns the starfield on via STARS_ENABLE (0x7004), raises loc_4007, clears the per-sequence bookkeeping (CURRENT_PLAYER at 0x400d, loc_400e, the mode flag loc_4006, and loc_4019), seeds the dwell cascade to a sub-timer of 96 and a tier of 16, and bumps SEQUENCE_STATE so the sequence begins to run down that dwell on the following frames.

### The credit handshake into play

Game-state 2 is the credit/idle driver, and after its own sub-dispatch it runs a post-handler that watches the debounced input-edge byte at loc_4011 and the credit count at loc_4002. When enough credits are present it consumes two of them, copies a 32-byte board template out of ROM (at loc_051b) into the saved-state snapshot SAVED_STATE_SNAPSHOT (0x41a0), and — this is where two of our routines live — conditionally arms the advance gates. armStateAdvanceGate [code] stamps the fixed "armed" marker 3 into the state-advance gate byte loc_41b5 (0x41b5); armSubstateAdvanceGate [seen] stamps the same 3 into the sub-state-advance gate byte loc_4195 (0x4195). Both are called only when the config bit in loc_401f is set, and the start/spawn setup that follows also copies the same ROM template into the flag block, sets GAME_STATE to 3, clears SEQUENCE_STATE, raises the mode flag loc_4006, and posts its own request words — so the machine crosses from "waiting for a coin" into the play drivers with those two gates pre-loaded.

Those gates are read at the far end. The state-6 handlers of the play drivers test loc_41b5 and loc_4195 (respectively) as nonzero to decide whether to take their advance-and-show path or fall through to the shared tail. That shared tail is advanceDwellOrResetToState1 [code]: when the mode flag loc_4006 bit 0 is clear it simply advances the sub-state and reloads the dwell (via advanceSubstateAndReloadDwell); when the bit is set it tears the machine back down to the beginning — GAME_STATE = 1, mode flag cleared, SEQUENCE_STATE cleared, the sound hardware silenced and the interrupt/starfield disabled — and enqueues command word 0x0600. That is the transition that drops the game back into attract when a round or the demo ends.

### Playfield initialization and the play sub-states

initPlayfieldState [code] is sub-state 0 of both play drivers — the routine that wipes the slate for a fresh field. It turns both cabinet start lamps off (START_LAMP_0 at 0x6000 and START_LAMP_1 at 0x6001), then zero-fills four work-RAM spans: the 128-byte flag block from FLAG_BITS_BASE (0x4100); a 23-byte span from OBJ_ACTIVE_FLAG (0x4200) and, after a deliberate one-byte gap, a 24-byte span from loc_4218 (0x4218); and a 70-byte span from loc_4260 (0x4260). It also drops loc_425f to 0, raises the activity flag loc_4226 (0x4226) to 1, advances SEQUENCE_STATE, arms the dwell tier loc_4009 to 32, and points the fill cursor VRAM_WRITE_PTR back at VRAM_BASE. The zeroed span from 0x4218 is significant because that block holds the pacing timers and the difficulty counter described below, so this init hands them to the next sub-states in a known-clear state.

restoreSavedStateAndEnterPlaySubstate [code] is the play sub-state that expands the board saved earlier: it unpacks the SAVED_STATE_SNAPSHOT (0x41a0) bitmask into the flag block, copies the 8-byte template that trails the bitmask into the timer block at loc_4218, clears loc_425f and loc_4220, and — when the flip config in loc_400f is set — mirrors it into the FLIP_SCREEN_X (0x7006) and FLIP_SCREEN_Y (0x7007) latches so a cocktail second player sees the screen inverted. It then advances SEQUENCE_STATE, arms the state timer loc_4009 to 150, publishes a sub-state routine pointer into loc_4245, and, only while the sound gate loc_4006 bit 0 is open, posts a five-word intro-sound burst. advanceSubstateAfterDwellAndQueue [code] is the plainer timed sub-state: it ticks the dwell tier loc_4009, and on the zero-cross reloads it to 20, advances SEQUENCE_STATE, and enqueues this state's command word (from loc_0682) — a state that simply waits, then moves on with a cue.

### The command / event queue

Several handlers above communicate downstream by appending 16-bit words to a command queue that lives in work-RAM page 0x40. enqueueCommandWord [seen] is the appender: it reads the write-head index from loc_40a0 (0x40a0), forms the target slot relative to the queue base loc_4000 (0x4000), and writes only if that slot is free (its bit 7 is set). On a write it stores the word's high byte at the slot and low byte at the next, advances the head by two, and floors the head at 0xc0 — so the queue body always sits from 0x40c0 upward and never below. commitQueueWriteHead [seen] is the small step that persists that advanced head back into loc_40a0, after which loc_090b (the deliberately unnamed pure-stack epilogue) restores the caller's saved pointer and returns with no work-RAM effect. enqueueCommandWordBurst [code] posts five command words in one shot — three carrying the caller's channel (twice on the next channel) and two fixed words on channel 7 — each word being (channel << 8) | param. The command queue is general (its channels 6 and 7 drive display draws, not sound), so this is a neutral command/event burst; it is the tail of the board/level-setup path, which fans out a whole cluster of queued commands at once.

### Per-frame gates and pacing ramps that run under the "objects active" flag

A second family of routines runs every frame while the field is live, all of them gated on bit 0 of OBJ_ACTIVE_FLAG (0x4200) — the master "objects are active" enable. armBehaviorGateOnInputOrTimer [code] arms a behavior gate loc_4208 (0x4208): it does nothing if the enable is closed or the gate is already armed, then branches on the mode flag loc_4006. On the timer branch it arms the gate only when the low five bits of the frame counter loc_425f are all zero — i.e. roughly once every 32 frames. On the input branch it selects one of the input shadows (IN0_SHADOW or IN1_SHADOW, chosen by loc_4018) masked against its guard byte (loc_4013 / loc_4014), and if bit 4 of that line reads active it arms both the gate loc_4208 and the companion flag loc_41cc (0x41cc). clearGateOnPendingRequest [code] is the acknowledger on the other side: when the request flag loc_420b (0x420b) bit 0 is pending it clears that flag and clears the behavior gate loc_4208, releasing whatever the gate was holding back.

rampCounterToCeiling [code] is a slow difficulty/pace ramp. Guarded by OBJ_ACTIVE_FLAG set and the inhibit flag loc_422b clear, it runs a two-tier prescaler — the outer loc_4218 reloading at 60, the inner loc_4219 (0x4219) reloading at 20 — and every time both wrap it steps the 0-to-7 counter loc_421a (0x421a) up by one, clamping at 7. That counter is a pace level that rises the longer play lasts, not a static base, and it is reset to zero on a stage advance elsewhere.

scheduleDelayedEvent [code] and fireDelayedEventRequest [code] are the arm-and-fire pair for a deferred event. scheduleDelayedEvent runs only when OBJ_ACTIVE_FLAG and loc_41ef (0x41ef) are both set and the inhibit loc_422b is clear. With the mode flag clear it runs its own two-tier timer (outer loc_4245 reloading at 60, inner loc_4246 at 5) and, on a full cascade elapse, arms the fixed triple DELAYED_EVENT_TIMER (0x422f) = 90, loc_424a (0x424a) = 45, and DELAYED_EVENT_ARMED (0x422e) = 1. With the mode flag set it instead derives a payload — either a constant, or from the byte-sums of the word cells at loc_4177 (0x4177) and loc_421a — and fans that value into the same triple by bit-rotations before arming. fireDelayedEventRequest is the one-shot that consumes it: while DELAYED_EVENT_ARMED is set it counts DELAYED_EVENT_TIMER down each frame, and on the zero tick it disarms itself and — only if OBJ_ACTIVE_FLAG and loc_41ef are still both set — raises DELAYED_EVENT_REQUEST (0x4229) for a downstream consumer.

expireActivityGatedTimer [code] ends an activity-gated timed phase: while the arm flag loc_422b bit 0 is set *and* at least one activity gate is open (either whole-byte cell loc_4224 (0x4224) or loc_4221 (0x4221) is nonzero, or the activity flag loc_4226 bit 0 is set), it ticks the counter loc_422c (0x422c) and, once that counter reaches zero, clears the arm flag loc_422b — retiring the phase. If none of the activity gates is open it simply holds, so the countdown only advances while there is activity to time.

### A small clamp helper

markValueOutOfRange [code] is not part of the sequence flow proper but shares the frame counter loc_425f with the gates above. It is the out-of-range arm of a value clamp used when folding a byte against the low nibble of loc_425f: when the fold input is beyond range it forces the fold index in B to the fixed saturation sentinel 0x80 and returns, so an over-range input saturates rather than wrapping.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

The standing enemy formation lives in two parallel representations that this subsystem keeps in step every frame. One is a **128-cell flag grid** at FLAG_BITS_BASE (0x4100): one byte per formation slot, bit 0 meaning "an alien occupies this cell." The other is a set of **32-byte object records** — the moving-attacker tables at OBJ_TABLE (0x42d0) and loc_42b1, the sprite-source band at SPRITE_SOURCE_OBJ_BASE (0x42b0), and the launch-slot table scanned from loc_4391 — that carry the aliens which have peeled off the grid to dive. The flag grid is the compact, authoritative census of who is still in formation; the object records are the live actors. Almost every routine here either seeds one of these, reduces one into the other, or moves an alien between them.

### Packing, unpacking, and seeding the field

The formation grid is loaded from and saved to a compact **16-byte packed bitmask** — 128 bits, one per cell. `unpackBitmaskToFlagBytes` [seen] reads sixteen mask bytes and explodes them LSB-first into the 128 one-byte flags at FLAG_BITS_BASE, writing 1 for each set bit and 0 for each clear one, and hands back the source pointer advanced past the mask so the caller can pick up whatever data trails it. `packFlagBytesToBitmask` [code] is its exact inverse: it reads bit 0 of each of the 128 flag bytes and re-compresses them into a 16-byte bitmap at the destination, returning the destination advanced sixteen bytes so a block copy can be chained on. The packed form is what ROM templates and inter-life snapshots store; the exploded byte-per-cell form is what the running game reads and clears.

A second, lower-level shadow is seeded by `seedObjectRamShadowField` [seen]: it copies 32 consecutive source bytes into every other cell of a work-RAM field beginning at loc_4021 (loc_4021, loc_4023, … up to loc_405f), filling one field of a stride-2 record layout. `seedObjectShadowFromRom` [seen] is the fixed-source wrapper — it aims that copier at the ROM template STRIDED_TABLE_SRC (0x1d71) and runs it, laying the canonical initial object-shadow field down at screen/formation init.

### The per-column strided table and the formation sway

The formation's side-to-side sway is a single 16-bit "anchor" word at loc_420e whose low byte every on-screen alien folds into its column position. `broadcastToStridedTable` [seen] writes one byte into nine work-RAM cells at stride 2 starting at loc_4028 (loc_4028, loc_402a, … loc_4038); it is the shared writer the other broadcasters delegate to. `clearStridedTable` [seen] zeroes those nine cells by broadcasting 0. `broadcastNegatedSweepToStridedTable` [seen] broadcasts the two's-complement of a supplied low byte, and `broadcastNegatedFormationSweepToStridedTable` [code] is the same thing sourced directly from the sway anchor — it negates loc_420e's low byte and fans that single value across the nine cells. So the strided table always holds the negated current sway offset, replicated.

`advanceFormationSweepOscillator` [seen] is the sway engine, run once per frame from each of the play/sequence state handlers. Throttled to one step every four frames (gated on loc_425f's low two bits), it nudges the loc_420e word one unit toward whichever end of the bound pair in FORMATION_X_BOUNDS (0x4210) it is heading for, with OBJ_SWEEP_DIRECTION (0x420d) recording the current direction (0 = ascending, 1 = descending). When the swept word reaches the upper bound it calls `setSweepDescending` [seen], which writes 1 into OBJ_SWEEP_DIRECTION to turn the sweep around; at the lower bound it calls `setSweepAscending` [seen], which writes 0. After each step it re-broadcasts the negated low byte across the strided table so the columns track the new offset. A leading proximity gate can short-circuit the whole thing: if the player shot is armed (loc_4208 bit 0), its position (loc_4209) lies in the narrow window aligned to the swept column, and that column reads occupied in COLUMN_OCCUPANCY (0x41f0), it skips the step and goes straight to the formation broadcast — momentarily freezing the sway on the column being fired at.

### Summarizing occupancy

`summarizeFormationOccupancy` [seen] is the per-frame reduction that feeds the sway bounds and the wave-clear logic, and it too runs from the four play/sequence handlers. Reading the six-row by ten-column OCCUPANCY_GRID (0x4123, rows sixteen bytes apart), it first ORs each row into ROW_OCCUPANCY (0x41e8, behind two always-zero guard cells) and each column into COLUMN_OCCUPANCY (0x41f0, behind three guard cells). It then derives the horizontal sweep limits: scanning the column summaries inward from the right for the first occupied column it builds a from-right bound (base 34, stepping 16 per empty column), and from the left a from-left bound (base 224, stepping down 16), packing the pair into FORMATION_X_BOUNDS with the right limit in the low byte and the left limit in the high byte. This is why the sway range tightens as the formation's outer columns are emptied. Finally it folds four **region-clear flags**: the top four rows into loc_4221 and all six rows into loc_4220, plus two object-table columns — seven slots of OBJ_TABLE (stride 32) into loc_4226 and eight slots from loc_42b1 into loc_4225 — each with bit 0 inverted so the flag reads 1 ("clear") only when nothing in that region is occupied. Those clear-flags gate launching, pacing, and stage advance downstream.

### Placing an alien on screen from its grid cell

`positionObjectFromGridCell` [code] turns an object record's packed grid cell (record byte 7) into on-screen coordinates in the fields the sprite builder reads. The display is rotated ninety degrees from the formation grid, so it is the **row** bits (cell & 0x70) that drive the X field at record+3 — a fixed origin of 124 minus three-quarters of the row value — and the **column** bits (cell & 0x0f) that drive the Y field at record+4 — the live sway anchor loc_420e plus the column scaled by sixteen plus a seven-pixel sprite hotspot. Because Y is recomputed from loc_420e on every call, a positioned alien rides the sway automatically.

`stageObjectsToSpriteShadow` [seen] is the per-frame staging pass for the standing formation: it renders eight consecutive object records from SPRITE_SOURCE_OBJ_BASE (32-byte stride) into eight consecutive hardware-sprite records at SPRITE_SHADOW_BASE (0x4060, 4-byte stride), as a band of three followed by a band of five, each band at a fixed vertical offset. The orientation bit loc_4018 flips the first band's offset (9 versus 7) while both orientations settle the tail band at 8 — a one-line nudge that keeps the two bands aligned when the screen is flipped.

### Pacing and launching attackers out of the formation

Two routines in the per-frame play pipeline together decide when a new attacker peels off. `paceEnemyLaunchTrigger` [code] is the cadence prescaler: gated on the play flag OBJ_ACTIVE_FLAG (0x4200) with the inhibits loc_4220 (region-clear) and loc_422b clear, it computes a sweep span from the pace counter loc_421a and the stage selector loc_421b (wider as difficulty climbs), ticks a master counter loc_424a, and while that master is still counting it holds SUBCOUNTER_REFILL_FLAG (0x4228) low. When the master expires it reloads from SUBCOUNTER_RELOAD_TABLE (0x15e3) and decrements a span of per-attacker sub-counters that follow loc_424a, refilling any that hit zero from the reload table and raising SUBCOUNTER_REFILL_FLAG only if at least one refilled. That refill flag is the "launch now" signal.

`launchAttackerFromFormation` [code] consumes it. Running later in the same pipeline — so it acts on the flag the pacer raised a frame earlier — it clears SUBCOUNTER_REFILL_FLAG, holds off while the whole-formation-clear gate loc_4220 is set, and otherwise: derives a one-to-four slot budget by folding the pace-plus-stage sum (loc_421a + loc_421b); scans the object-slot table downward from loc_4391 for the first slot whose two flag bytes are both zero; stamps the shared launch direction loc_4215 into the claimed slot's byte 6; picks an occupied formation column out of COLUMN_OCCUPANCY by that direction (from the high end down for direction 0, from the low end up otherwise); then walks that column of the FLAG_BITS_BASE grid — over four or five rows depending on the layout flag loc_41ef — for the first filled cell. It clears that cell (the alien leaves the standing grid), records the cell's low byte in the slot, marks the slot active with a cleared phase byte, and posts a spawn command word for it. One alien has moved from the flag grid into a live diving record.

The generic slot seeders are separate from the formation-pull launcher. `activateObjectSlotAndEnqueueSpawn` [code], tail-called by the free-slot finders, consumes the trigger flag it was found under (clearing the byte at the trigger pointer), marks the record active (byte 0 = 1) with a cleared phase (byte 2 = 0), records the spawn code and the trigger pointer's low byte as the source index, and posts a type-1 spawn command keyed by that index. `spawnSecondaryObjectIntoSlot` [code] is the companion for a second object in a paired slot: it bails if either of the slot's two live flags is already set, otherwise consumes the trigger, marks the slot alive, clears its state byte, inherits field 6 from the source record, stashes the trigger index, and posts the same activation command.

### The launched attacker's own state machine

Once a slot is live, a small state machine drives it, selected each frame by the record's state index at byte 2. `initSpawnedObjectFromGridCell` [code] is state 0, the first-tick setup: it clears the step timer (record+23), raises the spawn flag loc_41c2, positions the sprite via positionObjectFromGridCell, posts the spawn command, and looks up the attacker's sprite number and flight-curve seed from SPAWN_RECORD_TABLE (0x1dd1) indexed by its grid row (the top row additionally tallies its two active neighbour slots into ACTIVE_NEIGHBOR_COUNT (0x422a) and takes a distinct display attribute). It then seeds the motion counters — move throttle 3, leg count 12, walk cursor 0 — advances the state, and sets the signed heading to +12 or −12 from the direction bit.

`settleObjectIntoFormationCell` [code] is the mirror image, the handler that returns a diving alien to the grid. Each frame it increments the record's frame counter at record+3, repositions the sprite from the grid cell (which overwrites that same field with the target X derived from the row), reads the target back, restores the counter, and compares the two. A counterintuitive detail: the field at record+3 does double duty as both the settle counter and the sprite X, and the routine plays them against each other. While the counter is still short of the target it lets the alien keep approaching — nudging its phase at record+5 up or down by the direction bit on a small even gap, leaving a large (25 or more) or odd gap alone — and when the counter catches the target exactly, the object is deactivated (byte 0 = 0), its formation flag cell in FLAG_BITS_BASE is set back to 1, and a command word carrying the cell is posted. The alien has rejoined the standing formation, and because the target X grows with the row, aliens from deeper rows take longer to settle.

`reseedFormationObjectState` [code] re-initializes a formation object at the start of a re-entry: it resets X to the left edge (8), zeroes the heading, and ticks the leg counter. If the packed cell's high bits are not all set it rolls a fresh random Y — folded as (Y >> 1) + a 0-to-31 random draw + 32 — arms a 40-frame hold timer and advances the state, but only when the subsystem is enabled and an activity gate (loc_4224 or loc_4221) is open. When the cell's high bits are all set it is treated as a wave-management marker: while ACTIVE_NEIGHBOR_COUNT still shows neighbours it recounts the two following records and reseeds, and once none remain it deactivates the object and ramps the phase counter loc_421e toward its ceiling of 2. `noopAnimDispatchSlot` [code] is the do-nothing terminal entry (sub-state 3) of a related deactivated-object animation table — a valid target that performs no work so the animation's state index has somewhere to land when it is finished.

### The player's shot against the formation

`flagPlayerShotHitOnFormation` [code] tests the player's shot against the standing grid every frame while the shot gate loc_4208 is armed. It rejects shots outside the formation's vertical span, then bands the shot's Y (loc_4209) into one of six rows spaced twelve pixels apart (a seven-pixel gap then a five-pixel hit band per row), and bands the shot's X delta from the sway anchor (loc_420a minus loc_420e) into a column, rejecting anything outside the hit window. It composes row and column into a grid index (a nibble swap of the column-high bits plus the row), and if that FLAG_BITS_BASE cell holds a live alien it clears the cell, stamps a hit record — the retire flag loc_420b set to 1, and the hit slot at loc_42b1 / loc_42b2 / loc_42b3 carrying the shot position — and posts two command words: a kind-1 word carrying the grid index and a kind-3 word carrying a column code, which together drive the kill's scoring and sound. `bumpCountIfNeighborsInactive` [code] supports the scoring that follows: given a base object record it peeks the two look-ahead slots 32 and 64 bytes above it and returns the running count incremented by one only when both are inactive, folding a "last of its group" bonus into the award.

### Clearing a wave and advancing the stage

When a wave is finally emptied, two adjacent pipeline routines advance the stage. `armFormationAdvanceTrigger` [code] is the gated one-shot arm: only when both the whole-formation-clear flag loc_4220 and the object-column-clear flag loc_4225 have bit 0 set, and the pending word loc_4222 is not already armed, does it write loc_4222 = 1 (enable byte 1, with the countdown loc_4223 zeroed). `advanceStageAndReseedFormation` [code] consumes that one-shot on the tick its countdown reaches zero: it disarms the enable, rebuilds the 128-cell flag block from the packed ROM template loc_051b, resets the pace counter loc_421a and frame phase loc_425f, reseeds the sway anchor loc_420e to 1, and steps the stage selector loc_421b — its low byte advancing but saturating at 7, its high byte counting the wraps — then posts a command word and services a pending two-slot request, draining loc_421e into loc_4177 and loc_4178. The next formation is now on screen one difficulty step higher.

### Reseeding the field across sequence and player-handoff states

Several sequence-state handlers reseed the field between phases. `advanceSequenceStateAndReseedObjectShadow` [code] advances the sequence step — its callers arrive pointing at the dwell cell loc_4009, so bumping the next in-page byte increments SEQUENCE_STATE (0x400a) — and then reseeds the stride-2 object shadow from ROM. `clearFlagBlockAndReseedObjectShadow` [code] is a sequence-init reset built on top of it: it zero-fills the 128-cell FLAG_BITS_BASE block, clears loc_425f and loc_4238, arms the mid-tier dwell timer loc_4009 to 64, and then advances the state and reseeds the shadow. `loadDescriptorAndAdvanceSequence` [code] performs the initial formation load: it unpacks a packed descriptor bitmask from ROM loc_051b into the flag block (defining which cells start filled), copies the eight-byte template that follows into the buffer loc_4218, clears loc_425f, sets loc_421d = 1, increments the sequence state, stamps the counter cell VRAM_WRITE_PTR (0x400b) to 150, and publishes a deferred-callback pointer (loc_0640) into loc_4245.

Two more terminal handlers snapshot the live formation across a player handoff, both waiting on the dwell timer loc_4009 before acting. `packFlagsToBitmapAndSwitchPlayerState` [code], on the timer's expiry, clears the sequence state and the status cells loc_4222 and loc_422b, packs the live flag bytes into PACKED_FLAG_BITMAP (0x4180) and copies the eight-byte template from loc_4218 right after it, then sets CURRENT_PLAYER (0x400d) to 1 and GAME_STATE (0x4005) to 4 — freezing this player's formation and switching to the other player. `saveFlagsToSnapshotAndSwitchPlayerState` [code] is the parallel branch: on expiry it clears the sequence state, sets CURRENT_PLAYER to 0 and GAME_STATE to 3, snapshots the flag bytes into SAVED_STATE_SNAPSHOT (0x41a0), and copies the companion block from loc_4218 after it — so a suspended formation can be restored intact when play returns to that player.

Finally, `activateDescriptorSlot` [seen], called from an attract-sequence state handler, initializes one 32-byte descriptor record in DESCRIPTOR_SLOT_TABLE (0x4330): indexing by the descriptor number minus one, it stamps the fixed init fields — active flag (byte 0 = 1), bytes 2 and 5 set to 13 and 12, and the slot index into byte 7 — while leaving bytes 3 and 6 untouched. And a note on the shared tail loc_090b: it is a deliberately unnamed pure-stack epilogue of the command-queue enqueue path that simply restores the caller's saved pointer and returns, carrying no work-RAM effect of its own.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

Everything in this subsystem hangs off two shared cells. `OBJ_ACTIVE_FLAG` (0x4200) is the master gate: while its bit 0 is set the player ship, its shot, the enemy AI and the projectile collision test all run; when it is clear the whole apparatus freezes. Sitting beside it, `loc_4202` (0x4202) is the single horizontal reference that ties the ship to its attackers — the player ship writes its own X there each frame, and virtually every enemy routine reads it back as the point to home on, dive across, or shoot at. Reading this subsystem is mostly a matter of following writes to `loc_4202` outward. Both cells are brought up together at the start of a play phase and both are torn down the instant the player is hit, as the collision path below shows.

### The player ship

The ship is the "controlled object." `moveControlledObjectAndStageSprite` [code] runs first each frame. When the ship is active it selects a movement command from one of three sources depending on the mode flag `loc_4006` (0x4006): with bit 0 clear it takes the AI steer command `OBJ_MOVE_CMD` (0x423f) — the demo/attract autopilot — and with bit 0 set it takes a live joystick shadow, choosing `IN1_SHADOW` or `IN0_SHADOW` by bit 0 of the orientation flag `loc_4018` (0x4018). Bit 3 of that command nudges the position down (while it stays at or above 23) and bit 2 nudges it up (while below 233), so the ship rides horizontally in the band [23, 233]. The resulting position is written to `loc_4202`, one's-complemented and offset by 128, and staged as four interleaved (value, code) pairs into `OBJ_STAGE_BLOCK` (0x4054) under code 6. Two inactive branches complete the picture: when `loc_4201` (0x4201) is set the last position is staged unclamped under the alternate code 7 (this is the held explosion pose after a hit), and otherwise the position is parked at zero.

The autopilot behind `OBJ_MOVE_CMD` is computed by `computeControlledObjectMoveCommand` [code], which fires only on the frame where the free-running counter `loc_425f` (0x425f) lands its 32-frame phase and only while both `loc_4007` (0x4007) bit 0 and the master gate are set. It folds every record of two object tables — the wide-stride records at `OBJ_TABLE` (0x42d0) and the tight-stride records at `loc_4260` (0x4260) — through `accumulateObjectPositionWeight` [code] to build a running weight, blends in a scaled offset between the formation anchor `loc_420e` (0x420e) and the ship reference `loc_4202`, halves the sum, applies a random plus-or-minus-one nudge, and buckets the outcome into 0, 4, or 8 — the neutral / move-up / move-down command the ship handler consumes. `accumulateObjectPositionWeight` is the per-enemy scorer: it ignores an object unless it is active, its Y sits in one of two 52-row bands measured up from 128, and its X delta from `loc_4202` falls in the near half; qualifying objects fold their facing bit and delta bits and band into a 0–15 index, read a signed step from `OBJ_STEP_TABLE` (0x1a45), and add it to the accumulator. The net effect is a demo ship that leans away from where the nearby divers are massing.

### The player shot

The single shot is a small timing block driven by `advancePlayerShot` [code]. While its gate `loc_4208` (0x4208) bit 0 is armed, the position counter `loc_4209` (0x4209) is drained by four each frame, and on the frames where it lands in the narrow window [14, 17] the retire flag `loc_420b` (0x420b) is raised — that is the shot reaching the top of its travel. While the gate is clear the counter is reloaded to 220 (parked at the bottom) and the field cell `loc_420a` (0x420a) is seeded from the ship reference `loc_4202` when the master gate is set, else zeroed — this latches the ship's X as the launch column. `advancePlayerShotAndStageSprite` [code] wraps that service call and then turns the {counter, field} pair into two on-screen render cells: it writes the shot's Y to `loc_409d` (0x409d) as the complement of the field, and its X to `loc_409f` (0x409f), where bit 0 of the orientation flag `loc_4018` picks between two low-byte formulas (counter minus one, or the complemented counter plus 252) to account for the screen flip.

### Building object sprites

Enemy objects are drawn by `renderObjectSprite` [seen], which assembles one hardware sprite record (Y, attr, sprite#, X) from a 32-byte object record. An active object (record byte 0, bit 0) copies its X (record+3, minus 8) and Y (record+4, complemented and shifted by a caller-supplied row offset), takes its sprite number from record+0x16, and folds its signed heading at record+5 into a display attribute: the fold rotates the heading by whole sectors into a small settled range, maps it to a facing attribute added to the base attribute at record+0x0f, and applies a one-pixel diagonal nudge. A secondary-active object (byte 1, bit 0) instead gets a fixed sprite number 7 and the alternate attribute at record+0x12, and an object with both flags clear is parked off-screen at (248, 248). The formation is staged through this routine in two contiguous bands (a band of three then a band of five) at fixed row offsets, the near band's offset flipped by the orientation bit.

### The object-AI state machine

Each object slot is driven from a per-slot dispatcher that first checks byte 1: if its bit 0 is set the slot is handled by the deactivated/dying sub-dispatcher (below); otherwise, if byte 0 bit 0 is set, it dispatches on the state index at record+2 through a sixteen-entry table. The routines here occupy specific slots of that table, and each advances record+2 when its leg of the behavior finishes, walking the object from one state to the next.

State 1 is `advanceObjectPathStep` [code], the shared path-walk. It reads a delta pair from `PATH_STEP_TABLE` (0x1e00) at the object's own walk cursor (record+0x13), adds the first delta to record+3 and adds or subtracts the second to record+4 according to the direction bit at record+6, and if record+4 (with a seven-pixel margin) crosses the near screen edge it forces the state to 5, the fall-away state. Otherwise it advances the cursor past the pair, ticks the move throttle at record+0x10 (reloading it to 4 on expiry), nudges the cross-step counter at record+5, and ticks the leg counter at record+0x11, advancing the state when a leg completes. `advanceObjectPathStepDescending` [code] (state 10) is the subtract-direction mirror: it subtracts the X delta from record+3 and — unless record+6 bit 0 diverts the Y half to the ascending arm — the Y delta from record+4, steps the heading at record+5 down, and on a finished leg reloads throttle 3, leg 12, heading 12 and cursor 0. That ascending arm, `advanceObjectPathStepAscending` [code], adds its step-table byte to record+4, steps the heading up on throttle expiry, and on a finished leg reloads heading 244 and cursor 0 — the two arms curl the object in opposite vertical directions. `advanceObjectPathStepAlias` [code] (state 11) is a bare trampoline that forwards, unchanged and stateless, straight back into the shared state-1 path-walk.

State 4 is the dive, `advanceObjectDiveStep` [code]. It steps the object's position field record+3 by one or two depending on the parity bit of `loc_425f`, and if that position enters the small window [6, 9) it simply bumps the state. Outside the window it advances the flight curve and folds the curve's high byte at record+0x19 plus the per-object increment at record+9 into a new screen Y at record+4 — but a carry that crosses the signed boundary (the swoop running off the bottom) bumps the state instead of storing the Y. The curve itself is `advanceObjectFlightCurve` [code], a cross-coupled fixed-point rotation: it runs ((record+0x18 seed) & 3) + 1 integration steps over two 16-bit accumulators held in the record (high/low bytes at record+0x19/+0x1b and +0x1a/+0x1c), each step adding twice the other accumulator's sign-extended high byte into this one, with a guard that reverts any step whose high byte would settle at exactly 128. The accumulator high bytes are the swoop offset the dive step reads back — this is what gives an attacker its curved plunge.

State 7 is `homeObjectXTowardPlayer` [code]. It bumps the per-frame counter at record+3, then steers the object's 16-bit X:subpixel pair (high byte at record+4, low byte at record+9) toward `loc_4202` by roughly four times the signed distance each frame, carrying a small rounding bias, and advances the state once the dwell timer at record+0x10 counts to zero — a late-flight tracking pass that lines the attacker up on the player's column.

### Choosing a horizontal target

Several states plan a new horizontal move rather than executing one. The primitive is `commitMoveToTargetX` [seen]: given a target X, it stashes that target at record+0x19, records the signed per-frame delta (current X minus target) at record+0x09, zeros the move accumulator at record+0x1a..0x1c, and advances the planner's sub-state at record+2. `commitMoveAcrossPlayerX` [code] chooses that target relative to the player: it signed-halves the gap between the actor's X (record+4) and `loc_4202`, biases it by 16, and clamps to a band on the far side of the player — right (144–208) when the actor is to the player's left, left (48–112) when at or to the right — then commits it, so the attacker aims to cross to the opposite side. `commitMoveToStoredOrPlayerTargetX` [code] is the branch in front of that: when `OBJ_TABLE` bit 0 is set it aims at the object table's own stored target X (OBJ_TABLE+0x19) instead of the player crossover, otherwise it runs the ordinary cross-player pick. `beginObjectCrossPlayerMove` [code] is the shared tail two states use to launch such a move: it runs the cross-player pick and then arms the flight-curve step seed at record+0x18 to 3 (giving four curve steps) and the move throttle at record+0x10 to 100.

### Phase entry, settling, and retirement

`initObjectPhaseSteps` [seen] (state 13) is a phase-entry step: it derives a step count n from the low two inverted bits of the seed at record+7, writes n+1 to the step-count field record+0x16 and a derived code byte ((n+1)<<4)+140 to record+3, arms the phase timer at record+0x10 to 24, advances the sub-state, and clears the ready flag at record+0x0f — re-arming that flag to 24 only when n is zero. `settleObjectXAtRest` [seen] (state 15) is the terminal hold: it steps record+4 up one count per frame until it lands within five of the rest value 200 and then holds, which is how an object eases into and keeps its formation slot.

When byte 1 marks a slot as deactivated or dying, its state index selects instead from a small sub-dispatch table. `tickDeactivatedObjectAnim` [code] handles sub-state 1: it counts a fast timer (record+0x10) down, reloading it to 4 and bumping the companion at record+0x12 on each elapse, then a slow timer (record+0x11); when the slow timer elapses it either retires the object by clearing its state byte record+1, or — if the position field record+7 has reached 112 — reloads the fast timer to 50, seeds the companion from the global `loc_422d` (0x422d) plus 32, and advances the sub-state. `endObjectAnimOnTimerExpiry` [code] handles sub-state 2 as a plain expiry: it ticks the timer at record+0x10 down and, on the frame it hits zero, clears the state byte record+1 to retire the object.

### Dive scheduling

Two routines feed the spawner that turns formation members into attackers. `selectAttackerRowScan` [code] decides which formation row launches next: it seeds a starting slot and base from the alternate flag `loc_421b` (0x421b) — slot 2 / base 157 when set, otherwise slot 1 / base 132 — scans up to four two-byte slots of the row-occupancy summary `ROW_OCCUPANCY` (0x41e8), advancing while neither byte of a slot has an occupied (bit 0) marker, and stores the resulting slot index and base as a pair at `loc_4213` (0x4213). `chooseNextAttackerDirection` [code] picks the launch/curve direction flag `loc_4215` (0x4215): the sign of the 16-bit formation anchor `loc_420e` selects which edge of the sweep bounds `FORMATION_X_BOUNDS` (0x4210) to measure against, and when the formation is within 28 pixels of that edge the direction is forced away from it (0 near the high bound, 1 near the low), otherwise a fresh random bit decides — so attackers peel off toward open space unless the swing is randomized in the middle.

### Collision and the player hit

The projectile collision test elsewhere in the frame box-checks each active enemy shot against the ship reference `loc_4202` and, on overlap, raises `HIT_EVENT_FLAG` (0x4204). `handlePlayerHitEvent` [code] is the sole consumer. If the flag's bit 0 is clear it does nothing; otherwise it clears the flag and tears the subsystem down — zeroing `OBJ_ACTIVE_FLAG` and setting `loc_4201` to 1, which is exactly the combination that makes the ship handler freeze the ship in its held explosion pose. It then arms the two pulse counters `loc_4205` (0x4205) to 10 and `loc_4206` (0x4206) to 4, queues the hit sound command, decrements the pace counter `loc_421a` (0x421a) floored at zero, steps the [0, 5] cycle counter `loc_421d` (0x421d) wrapping past zero back to 5, and pulses the sound latch `SOUND_W_REG3` when the mode bit `loc_4006` is set.

### Subsystem bring-up

Two sequence-level handlers stand this whole subsystem up. `resetObjectRamAndAdvanceSequence` [code] is the reset step: it seeds the stride-two OBJRAM shadow field from the ROM template at `loc_1d91`, zeros the sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad region from `loc_4260`, clears `loc_4238` (0x4238) and `MESSAGE_SCROLL_ENABLE` (0x40b0), points the VRAM write cursor `VRAM_WRITE_PTR` two cells into `VRAM_BASE`, arms the dwell timer `loc_4009` (0x4009) to 16, and advances `SEQUENCE_STATE` (0x400a). `activateObjectsAndBeginPlayPhase` [code] then runs the dwell down; on the frame it expires it reloads the timer to 10, advances the sequence, and flips the subsystem on — setting the `OBJ_ACTIVE_FLAG`/`loc_4201` pair so the master gate is armed and the alternate flag cleared, seeding the ship reference `loc_4202` to 128 (center), refilling the sixteen-byte enemy-launch sub-counter block at `loc_424a` (0x424a) from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clearing the scratch cells `loc_4058` (0x4058) and `loc_405a` (0x405a), and queuing two display command words.

Finally, `loc_090b` is a deliberately unnamed pure-stack epilogue used elsewhere in this area: it restores a saved register and returns, the shared exit of a small enqueue path, holding no logic of its own.

## Sound

Every frame the machine composes its sound into a handful of shadow cells and then latches those cells out to the discrete-sound hardware. Two shadows carry the bulk of the work: a *pitch shadow*, `SOUND_PITCH` (0x41c1), and a *composite flag* byte, loc_41c0. At the top of each frame the per-frame sound driver (0x16f5) clears loc_41c0 to zero and preloads `SOUND_PITCH` with 0xff, then walks its chain of channel and effect updaters — each of which may overwrite the pitch shadow and raise the composite flag — and finally latches loc_41c0 to a sound register (with a bit-rotated copy going to the next register) and `SOUND_PITCH` out to the pitch port `SOUND_PITCH_W` (0x7800). So the routines below are all painting onto that per-frame canvas; nothing they stage is heard until the driver latches it at frame's end.

**Staging a pitch.** The simplest leaf is stageSoundPitch [seen], which merely parks a byte into `SOUND_PITCH` for the driver to latch. stagePitchAndRaiseSoundFlag [code] does the same but stores the value minus one (so an input of 0 wraps to 255) and additionally raises loc_41c0 to 1, marking the composite pair filled for this frame. A richer path recomputes pitch from a running sound counter, loc_41c4: stagePitchFromSoundCounter [code] reads that counter and, when its selector is odd, biases it by 96 and folds the sum right one bit (the add's carry rotating back into the top bit) to produce a warbling value, otherwise passing the counter through unchanged, before handing the result to stageSoundPitch. Sitting above it, stageSoundPitchBySelector [code] takes the low two bits of a pointed-to cell as that selector: a nonzero selector routes to stagePitchFromSoundCounter, while a selector of zero stages a flat pitch of 96. This selector path is reached each frame through the pitch-counter manager chain that decrements loc_41c4 (holding it below 0x60) and resolves into these staging leaves.

**The rising pitch ramp.** advanceSoundPitchRamp [seen] walks a two-byte {countdown, pitch} pair: while the countdown byte is nonzero it decrements it, adds a fixed step of 4 to the pitch byte, republishes that pitch into `SOUND_PITCH`, and clears loc_41c0 back to zero; a drained countdown makes the tick idle. driveRisingPitchRamp [code] is its arming wrapper, keyed on the arm counter loc_41c9. While that counter is more than one step from zero it advances the ramp (feeding loc_41c9 itself as the pair pointer); note the arm byte is *not* written back while it stays nonzero — the predecrement only chooses the branch — and only when it reaches its reset point does the routine clear loc_41c9 and reload the ramp pair at loc_41ca to 32 (countdown 32, pitch 0). This ramp tick is one of the effect updaters the per-frame driver runs.

**The sound-sequence engine.** A single sequence player is fed by three arming descriptors over a shared cursor, `SOUND_SEQ_PTR` (0x41d3), a shared current-tone byte loc_41d5, and a shared duration timer loc_41d6. advanceSoundSequenceChannel [code] does the playback for one descriptor: an inactive descriptor (byte zero) is skipped, otherwise it raises loc_41c0 to 2, publishes the current tone loc_41d5 into `SOUND_PITCH`, and ticks loc_41d6 down; only when that timer expires does it pull the next command byte from the cursor. A command of 0xe0 is an end marker that deactivates the descriptor; any other byte is split — its low five bits index `SOUND_TONE_TABLE` (0x17a9) for the new tone and its top three bits index `SOUND_DURATION_TABLE` (0x17c8) for the new duration timer — and the cursor advances past it. advanceAllSoundSequenceChannels [code] runs that player once over each of the three descriptors in turn — loc_41d2, loc_41cf, and `SOUND_SEQ_ACTIVE` (0x41cd) — every frame; because all three share the one cursor and tone/duration cells, the descriptors act as three independent *arm* flags into a single voice rather than as three distinct channels.

Three separate arms raise those descriptors, each publishing its own sequence-data pointer. armSoundSequenceOnRequest [seen] fires only when its request gate loc_41d1 holds exactly 1: it consumes the gate, raises descriptor loc_41d2 and the duration timer loc_41d6, and points the cursor at the table at loc_1e68. armSoundSequenceBySelector [code] is the driver's request tick — it does nothing unless the sound-driver enable bit (bit 0 of loc_4006) is set, then reads the shared request byte loc_41df: a value of 6 arms *this* sequence (descriptor loc_41cf plus loc_41d6, cursor to loc_1ebd) unless `SOUND_SEQ_ACTIVE` is already set, and any other value is handed to armSoundSequenceForSelector16 [code]. That last arm handles only the selector 0x16, ignoring everything else; on a match it clears loc_41cf, raises `SOUND_SEQ_ACTIVE` and loc_41d6, and points the cursor at loc_1edf.

**The pulsed-tone envelope.** advancePulseToneEnvelope [code] ticks a 16-bit envelope word held as low byte loc_41c7 and high byte loc_41c8. When bit 0 of the low byte is set it re-arms the word to its sentinel (low byte 0, high byte 128) and stops; otherwise it hands the high byte to pulseSoundToneFromCountdown [code]. That handler idles when the high byte is zero, else stores it decremented back into loc_41c8 and stages a two-level pulse through stagePitchAndRaiseSoundFlag — passing 129 (which becomes 128 in the pitch shadow) when bit 2 of the decremented byte is set, or 0 (becoming 255) when it is clear. So the envelope counts its high byte down frame by frame and toggles the pitch shadow between two levels on that one bit, raising the composite flag as it goes.

**The gated square-wave tone.** driveGatedSquareTone [code] is the tone generator proper: it writes to `SOUND_W_REG5` (0x6805), defaulting to silence, but while the duration counter `SOUND_TONE_DURATION` (0x41ce) is nonzero it counts one tick off that counter and instead drives the frame-parity byte loc_4007 with its low bit flipped — since that bit alternates every frame, the register output toggles frame to frame, a square wave. advanceGatedSquareTone [code] is the phase gate above it: while its phase counter loc_41cc is not one step from zero it simply runs driveGatedSquareTone (leaving loc_41cc unwritten — again the predecrement is only a test), and at the expiry step it parks loc_41cc at zero and re-arms `SOUND_TONE_DURATION` to 8. This gate is the last of the per-frame driver's effect updaters.

**The LFO level.** Three routines maintain a low-frequency level fanned across the four `SOUND_LFO_FREQ` hardware latches at 0x6004. broadcastSoundLfoLevel [seen] is the writer: it saves the level into the shadow `SOUND_LFO_LEVEL` (0x421f), then writes it to all four latches in turn, rotating the byte right one bit between writes so each latch receives a progressively shifted copy. decaySoundLfoLevel [code] is the per-frame decay step: only on the tick where the gate loc_425f reads 0xff, and only while the shadow level is nonzero, does it drop the level by one and re-broadcast it. driveSoundLfoLevel [code], run from the vblank handler, dispatches between the two: with no reset pending (the flag `SOUND_LFO_RESET_REQUEST` at 0x41d0 is zero) it runs the ordinary decay, but if a reset is pending it consumes that request and slams the full level of 15 across the latches.

**Gameplay-driven voices.** Apart from the per-frame driver and the vblank LFO tick, the main game loop drives three further sound effects each frame. driveDecayingSoundSweep [code] runs only on even frames (bit 0 of loc_4007 clear); while the request byte loc_41df is nonzero it emits that byte rotated right two bits to `SOUND_W_REG4` (0x6804) and decrements it, so the emitted value shrinks toward silence — the very cell that armSoundSequenceBySelector reads as a request selector doubles here as a decaying sweep countdown. driveSoundVoicesFromOccupancy [code] is an even-frame hum keyed to how full the playfield is: it sums the 6×10 flag grid at `OCCUPANCY_GRID` (0x4123, row stride 16) into a tally seeded at 1, lights that many of the three sound-write latches `SOUND_W_REG0`..`SOUND_W_REG2` (0x6800–0x6802, capped at three) and zeroes the rest, and raises the near-empty flag loc_4224 once the tally has nearly drained. driveGatedSoundStepSequence [code] is gated by bit 0 of the enable flag loc_4201; a prescaler loc_4205 fires once every ten eligible frames, and on each fire it enqueues a command word (opcode 2 carrying the current step) and steps the step counter loc_4206 down, and when that counter drains it clears the enable flag and silences `SOUND_W_REG3` (0x6803). The command-word enqueue it uses returns through a plain shared stack epilogue, loc_090b [code], which does no work-RAM work of its own.

**Requesting an effect, and silencing everything.** armObjectAnimAndRequestSound [code] is how gameplay posts a sound request: as the sub-state-0 entry of a deactivated object's animation it seeds that object's animation timers (record fields +0x10, +0x11, +0x12 to 4, 4, and 28), advances the object's sub-state so the entry runs once, and writes the request byte loc_41df from the object's position field (+0x07) — 0x07 when that position is below 112, else 0x17 — which the sequence request tick and the decaying sweep then pick up. Finally, silenceSoundAndDisableIrqStars [code] is the hardware quiesce used at resets: it sets the four `SOUND_LFO_FREQ` latches to 1, clears all eight sound-write registers (0x6800–0x6807), clears the `IRQ_ENABLE` (0x7001) and `STARS_ENABLE` (0x7004) control latches to halt the vblank interrupt and the starfield, and drives the pitch port `SOUND_PITCH_W` (0x7800) fully high.

## Coins, credits, the HUD, score display, and the message scroller

### Coins and credits

The bank of credits lives in a single work-RAM byte, loc_4002, and everything in the coin path treats 99 (0x63) as its ceiling. When a coin drops, the coin service's coin-received branch runs addCreditForCoin [code]: if loc_4002 is already at the cap it does nothing, otherwise it bumps the byte, raises the ready flag loc_41c9, and posts a channel-7 command word (0x0701) that redraws the credit-count line (the channel-7 dispatch's arg 1 reads loc_4002, caps it at 99, and paints its two BCD digits). incrementCreditCount [code] is the more general form of the same step — its two callers hand it loc_4002 — and it adds the clamp arithmetic addCreditForCoin skips: a byte already exactly at 99 returns untouched, a byte that has somehow overshot is pinned back through clampCreditsToMax [code] (which simply writes 99 into the cell at the pointer), and only a byte below the ceiling is incremented, sets loc_41c9, and enqueues the same (7,1) credit-redraw word. Raising loc_41c9 is what arms the rising coin-insert jingle, so a genuine credit bump both shows on the HUD and is heard.

Two more coin cells complete the accounting. loc_4001 is the coin-phase flag: setCoinPhaseFlag [code] writes 1 into it to mark that the first coin of a coins-per-credit pair has arrived. presetCreditCount [code] is the service/test branch: it stores the 16-bit constant 0x0900 across loc_4001/loc_4002, i.e. it clears the coin-phase flag and presets the credit count to 9 in one stroke.

The physical coin hardware is driven by two write-only latches. pulseCoinCounter [seen] rotates its input byte right three bits so the source value's bit 3 lands in bit 0, writes that to the coin-counter output latch COIN_COUNTER_0_LATCH (0x6003) — only D0 is wired, so bit 3 of the value is what actually clicks the mechanical counter — and then decrements the pulse-width byte at the caller's pointer, tapering the pulse. Coin acceptance itself is gated by the lockout coil at COIN_LOCKOUT (0x6002): clearCoinLockout [code] writes 0 to release it, and updateCoinLockoutFromCredits [code] decides which way it goes from the credit count — at nine or more banked credits it releases the coil (through clearCoinLockout), below nine it engages it (writes 1) — so the machine physically stops taking coins once the player has stockpiled nine credits.

### Start-button lamps

driveStartButtonLamps [code] lights the two start-button lamps straight off the credit count. Its enable is bit 5 of the attract/status byte loc_425f: with that bit clear both lamp latches are forced dark. With it set, zero credits leaves the lamps as they are, one credit lights lamp 0, and two or more lights both. The lamp outputs share their addresses with the input port — START_LAMP_0 is 0x6000 (the very address read as IN0) and START_LAMP_1 is 0x6001 — the split being read-vs-write on the same board lines.

Two attract-sequence handlers keep the lamps synced while they run their own countdowns. holdStartLampsThenAdvanceSequence [code] ticks the countdown byte loc_4019 each frame; while it is still nonzero it re-runs driveStartButtonLamps so the lamps track any credit inserted during the wait, and on the tick that drives loc_4019 to zero it advances SEQUENCE_STATE and zero-fills the 128-byte flag block at FLAG_BITS_BASE (0x4100). blankVramRowsThenDriveStartLamps [code] is sequence state 2: it fills two 28-cell rows of the blank tile (16) through the VRAM write cursor VRAM_WRITE_PTR (skipping a four-cell gap between them) and steps the cursor a full 64 bytes, ticks the row tier loc_4009, and returns while rows remain; on the final row it advances SEQUENCE_STATE, clears the screen-flip latches FLIP_SCREEN_X/FLIP_SCREEN_Y and the direction flag loc_4018, queues two setup command words (7,2) and (6,1), and finishes by driving the start lamps.

### Leaving attract on a credit

advanceGameStateOnCredit [code] is the hook that pulls the machine out of attract the instant money is in. It runs each attract frame right after the sequencer step: if loc_4002 (credits) is zero it is a no-op, but the moment credits are nonzero it increments GAME_STATE and tears down the attract sub-state cluster — clearing the frame flag loc_4007, SEQUENCE_STATE, the state flag loc_41c2, the sound-sweep countdown loc_41df, and the message-scroller enable MESSAGE_SCROLL_ENABLE (0x40b0) — so the attract text stops scrolling and the game begins to spin up.

startGameRoundAndClearScores [code] is the round-start setup. It stores the incoming player-count/spawn word into the CURRENT_PLAYER pair (0x400d), copies the 32-byte ROM row template loc_051b into the packed formation bitmap PACKED_FLAG_BITMAP (0x4180), and — only when config bit 0 of loc_401f is set — arms the sub-state advance gate. It then enters play (SEQUENCE_STATE=0, GAME_STATE=3, loc_4006=1, loc_41d1=1) and posts three command words: a channel-6 start message (6,4) and two channel-4 words (4,0) and (4,1) that clear the on-screen score slots — the "clear scores" of its name.

### Turning binary into on-screen digits

byteToPackedBcd [code] is the small numeric primitive under the HUD: it reduces a binary byte modulo 100 and returns it as packed BCD, tens in the high nibble and units in the low. The coin/credits HUD line uses it to render the credit count as two decimal digits.

The score fields themselves are stored as three-byte packed-BCD runs — player 1 at PLAYER1_SCORE_BCD (0x40a2..0x40a4) and player 2 at PLAYER2_SCORE_BCD (0x40a5..0x40a7) — least-significant BCD pair at the base, most-significant at the top. selectCurrentPlayerScore [code] returns the base of whichever field belongs to the active player, chosen by CURRENT_PLAYER. drawBcdDigit [code] paints one nibble: it maps a digit d to the contiguous glyph tile 0x90+d, but suppresses leading zeros — while the blank counter is nonzero an incoming zero is drawn as the blank base 0x80 (0x80+0x90 wraps mod 256 to tile 0x10, the blank cell) and the counter is decremented, the first significant digit ends suppression, and a zero after suppression has ended draws a real '0'; it then advances the cursor by its stride. drawBcdNumberColumn [code] stacks six of these into a column: it reads three packed-BCD bytes walking the source pointer downward one byte at a time (so a caller that points it at the top byte gets most-significant first), painting the high nibble then the low nibble of each, stepping the VRAM cursor up one tile row (-32) per digit, with a four-digit leading-zero blank budget so a zero score still shows its last two digits. drawScoreToSelectedPlayerField [code] picks the destination field for that column by a selector — DIGIT_FIELD_PRIMARY (0x5381) when zero, DIGIT_FIELD_ALT (0x5121) otherwise — then paints. drawHighScoreDigits [code] is the same painter aimed at the fixed high-score field at loc_5241, fed the caller's source pointer; it runs after a new high total has been latched and on the explicit high-score redraw.

### The two player-status columns

Each player has a three-cell status column in VRAM: player 1's at PLAYER1_STATUS_VRAM (0x5340), player 2's at PLAYER2_STATUS_VRAM (0x50e0). selectPlayerStatusVram [code] returns the base for a player index (0 -> 0x5340, else -> 0x50e0). paintPlayerStatusColumn [code] paints such a column from a base pointer, stepping by a caller-supplied stride: the top cell gets the incremented code, the middle a fixed tile 0x25, the bottom a fixed tile 0x20; afterwards, only when bit 4 of the flags byte is clear and the gate cell loc_4006 is zero, it clears the saved-status byte loc_40ab. repaintPlayerStatusColumn [code] is the dispatcher over that: it selects the active player's column (CURRENT_PLAYER through selectPlayerStatusVram) and, with flags bit 4 clear, paints it directly with a -32 row stride; with bit 4 set it instead blanks the active column's three cells with the fill tile 16 and, only when the paired-player flag loc_400e is set, goes on to paint the other player's column (player index XOR 1). repaintPlayerStatusColumnIfSaved [code] guards the whole thing on loc_40ab: a zero saved-status byte returns without touching the screen, a nonzero one falls through to the repaint — so loc_40ab is the "status needs redrawing" latch that paintPlayerStatusColumn itself clears once the paint is done.

### Fixed on-screen text

drawTextColumn [code] is the character-run primitive: for a count of characters (0 meaning a full 256) it reads a source byte, subtracts the '0' code (0x30) to turn it into a font tile, stores it, then steps the source forward one byte and the destination by a signed stride — a -32 stride walking the glyphs up a screen column in the column-major tilemap. drawTextColumnFromDescriptor [code] feeds it from a five-byte descriptor record — a source word, a destination word, then a count byte — always with the -32 up-a-column stride. drawTextColumnByIndex [code] indexes the ROM descriptor table TEXT_DESCRIPTOR_TABLE (0x1cf6) by a five-byte stride and paints that record; its caller passes a decoded input/DIP field selector (0..9), so these draw the fixed configuration/readout text.

### The message scroller

renderMessageColumn [seen] is the message painter, indexed by A. It looks up a record in the pointer table MESSAGE_PTR_TABLE (masking the index to five bits, word stride); the record supplies a VRAM destination word followed by the text. The top two bits of the index choose the mode. Bit 7 is blank-fill: it overwrites each character's cell up the column (stride -32) with the blank tile 0x40 until the 63 terminator, erasing a message. Bit 6 is position setup, and it is what arms the scroller: it records the destination pointer into MESSAGE_DEST_PTR (0x40b5) and the text pointer into MESSAGE_TEXT_PTR (0x40b3), computes the target column, derives a per-column control cell at loc_4020 + column*2 and records it in MESSAGE_CURSOR_PTR (0x40b1), clears the whole 32-cell column with tile 0x10, writes a packed row byte into that control cell, and sets MESSAGE_SCROLL_ENABLE (0x40b0) to 1. With neither high bit set it draws immediately, each character mapped to its tile (char - 0x30) up the column to the 63 terminator.

advanceMessageScroller [seen] then reveals that armed message one glyph at a time. While MESSAGE_SCROLL_ENABLE bit 0 is set it fetches the control byte through MESSAGE_CURSOR_PTR; the low three bits act as a per-step delay, so while they are nonzero it only ticks the counter down. When they clear it looks at the next source character through MESSAGE_TEXT_PTR: a 63 terminator emits nothing and just ticks the countdown, otherwise it advances the source pointer, writes the glyph (char - 0x30) into the destination cell, steps the destination up one row (-32), and ticks. The tick itself is endMessageScrollOnExpiry [seen]: it decrements the countdown byte at the pointer and, only on the exact zero-crossing, clears MESSAGE_SCROLL_ENABLE to stop the scroller — so the high bits of that control byte are the message's lifetime. endMessageScrollOnExpiryFromDe [seen] is the same tick reached with the pointer arriving in DE (it swaps DE into the working pointer first), which is how the scroller ticks the counter after having stashed the pointer aside to read the text.

Messages are requested through the command/event queue. advanceObjectAndQueueMessageColumn [seen] is an object-AI state that does this on a timer: it bumps the object's tick field (record+4) and counts its dwell timer (record+16) down, and while the timer runs it returns; on expiry it enqueues a channel-6 command word carrying the object's payload selector (record+7 plus 75) and advances the object's state. Channel-6 words are consumed to paint a message column via renderMessageColumn, so an attract object walks itself across the screen by queuing one message column per dwell. emitMessageColumnsThenAdvanceSequence [seen] does the same reveal from the sequence machine: after resetting the shared strided per-column table it runs a two-tier dwell on loc_4008/loc_4009 — each expiry of the low tier reloads it to 80 and queues a channel-6 word whose parameter tracks the mid-tier count (so the painted column walks across as the mid counter descends), and on the mid tier's expiry it advances SEQUENCE_STATE, reloads both tiers (32 and 4), clears the sprite-source block at SPRITE_SOURCE_OBJ_BASE (0x42b0), and clears the redraw count DRAWN_COLUMN_COUNT (0x4241). postCreditAndMessageDrawsAndAdvance [code] is a shorter sequence step that queues a channel-7 credit-count redraw (7,1) and a channel-6 message draw (6,0), advances SEQUENCE_STATE, and then re-seeds the two-tier dwell cascade — loc_4008=96 (sub-timer) and loc_4009=16 (tier) — for the step that follows. That loc_4008/loc_4009 pair is not dedicated: the sequence machine reuses it from state to state, most often as this prescaler/dwell tier pair.

### The attract screen-fill

A separate cycle wipes and refills the screen in attract. drawScreenFillStripSecondHalf [code] stamps a run of two-tile pairs (tiles 52 and 54) forward from the VRAM cursor, saves the advanced cursor back to VRAM_WRITE_PTR, and ticks the strip countdown loc_4008; while that is still running it is done, and on its expiry it hands off to restartScreenFillOnDwellExpiry [seen]. That routine looks at the high dwell tier one byte past the pointer (loc_4009): if it is already zero, or reaches zero on this tick, it restarts the fill through resetScreenFillState; otherwise it keeps counting. resetScreenFillState [seen] is input-gated — if IN0 bit 6 is asserted it leaves everything alone — else it rewinds VRAM_WRITE_PTR to the top of video RAM (VRAM_BASE, 0x5000), re-arms the fill length to a full page (loc_4008 = 32), and clears the dispatch flag loc_401a and GAME_STATE, sending the fill/attract cycle back to the start. (IN0 is the 0x6000 read side of the same address whose write side is start lamp 0.)

### Two adjacent tallies

reloadExpiredCounterAndTally [seen] is a tiny reload-and-count helper: it copies the reload byte from a source cell (the value table) into an expired counter cell and returns a running tally incremented by one. It is driven by the enemy-launch pacing sweep, which walks a block of launch sub-counters, calls this to refill each one that has just decremented to zero, and afterward raises its refill flag when any were refreshed — so its "tally" is the count of counters refilled this pass rather than anything on the HUD.

awardKillScoreByBandAndDeactivate [code] closes the loop between a kill and the score display. It first deactivates the struck object (record bytes 0, 1, 2 -> 0, 1, 0), then scores it by band: starting from parameter 4 and the object's type/position field (record+7), it tests the field against the threshold 0x50 up to three times, and the first time the field is under threshold it enqueues a channel-3 score-add command with the current parameter and stops — a higher band (a larger field) yields a larger parameter and thus a larger award. If all three bands are exhausted it raises the inhibit word loc_422b to 0xf001, and when the active-neighbour count ACTIVE_NEIGHBOR_COUNT (0x422a) is exactly two it folds in a neighbour bonus, records it at loc_422d, adds it to the parameter, and enqueues the folded channel-3 word. Those channel-3 words are consumed by the BCD score-add handler, which adds the increment into the current player's score field and, when a new total beats the stored high score, latches it and repaints the high-score digits.

Every routine here that "enqueues a command word" leaves through the same short shared epilogue, the deliberately unnamed loc_090b [code], which merely restores the caller's saved pointer and returns without touching work RAM.

## Tile / VRAM drawing primitives and coordinate mapping

The tilemap lives at VRAM_BASE (0x5000) as a grid of one-byte tile codes, 32 cells to a row (a `+0x20` address stride from one cell to the one below it). Almost every primitive in this subsystem walks that grid *upward* -- stepping the pointer by `-0x20` per row -- because the drawn glyphs (score digits, decorative markers, the big centre indicators) are built from the bottom up in the ROM's addressing.

### Mapping a packed coordinate to a cell

The one routine that turns a compact position into a screen address is `mapPackedCoordToVram` [code]. It takes a single packed coordinate byte and scatters its two nibbles into a VRAM cell address: the low nibble, rotated right two, supplies both the address's high byte (its low two bits, so a page 0..3 above 0x5000) and the top two bits of the low byte; the high nibble is treated as a three-bit field whose complemented running sum becomes the low nibble of the low byte. The final address is `0x5000 + (high<<8) + low`. Besides the cell address it publishes two decision bits its callers steer on -- a carry equal to the coordinate's bit 4, and an accumulator equal to bits 6..5. `drawFixedTileFigureAtPackedCoord` [code] is the canonical consumer: it maps the coordinate, then on bit 4 set stamps a 2x2 block of the fixed 0x2c glyph family and on bit 4 clear stamps a vertical (double-height) pair -- the display-list handler for its draw channel, so one coordinate byte drives both *where* and *which shape* a decorative figure lands.

### The atomic stamps

Two leaf routines do the actual byte writing that everything above them composes. `stampTilePair` [code] writes a consecutive pair -- `tile` at the destination and `tile+1` in the very next cell -- then advances the pointer by `1 + stride` and the tile code by two, handing both advanced values back so a caller can chain pair after pair; the stride is the caller's lever for laying the next pair on the same row (small stride) or a row away. `drawDoubleHeightTile` [code] instead writes a *vertical* pair with no register advance: the tile at the destination and `tile+2` in the cell one full row (`+0x20`) below, preserving the caller's stride register. These are the only two places that touch tilemap bytes for the block/pair family.

### 2x2 blocks and the fixed-glyph entries

`drawTileBlock2x2` [code] builds a square from two `stampTilePair` calls with a `+0x1f` inter-row stride, so the top pair lays `(tile, tile+1)` and the second pass, after the built-in `+1`, drops one full row down to lay `(tile+2, tile+3)`; the caller's stride register survives the call. `drawTileBlock2x2Up` [code] is its mirror image, using a `-33` (0xffdf) stride so the second pair lands one row *above* the first, and re-seeding that upper pair four codes lower than where the top pair finished. In the ROM both block writers converge on a shared tail, `drawBottomTilePairRestoreDe` [code], which stamps the block's second pair and then restores the DE the caller pushed before the draw began -- the mechanism by which the whole 2x2 draw leaves the caller's stride register untouched. `drawTileBlock2x2AtDe` [code] is a convenience entry that swaps the pointer and stride registers first, so a destination arriving in the alternate pointer becomes the draw target (the old target handed back), and then draws the block normally.

Several entries just pre-seed a fixed glyph code and fall into these general writers. `drawFixedTileBlock2x2` [code] draws a 2x2 block seeded from code 44 (0x2c), laying tiles 0x2c..0x2f; `drawFixedTileBlock2x2Up` [code] draws the upward 2x2 block seeded from code 46 (0x2e), used to blank unused marker-row slots. `drawFixedTilePairHorizontal` [code] seeds `stampTilePair` with code 0x2c and returns the advanced tile/pointer so a caller's loop can chain a run of horizontal pairs, and `drawFixedTilePairVertical` [code] seeds `drawDoubleHeightTile` with 0x2c to paint a vertical pair (0x2c over 0x2e). This 0x2c family is the game's decorative-marker glyph set.

### 4x4 forms and the centre indicators

A larger draw region is cleared by `blankTileBlock4x4` [code], which stamps the blank code 0x40 into four rows of four cells starting at loc_51da (rows at 0x51da, 0x51fa, 0x521a, 0x523a -- a `+0x20` start-to-start stride). Note this uses a *different* blank code (0x40) than the row/column clears below, which blank with tile 0x10. `blank4x4AndDraw2x2Icon` [code] clears that 4x4 region and then overlays a 2x2 block seeded with tile 96 (0x60) at loc_51fc -- the small-icon indicator form. `draw4x4TileForm` [code] is the display-list handler that picks among three indicator shapes by its argument: form 0 is the blank-plus-icon just described; form 1 is a bare 4x4 blank; anything else folds `(form-2)` into the mid bits of a complemented tile code over a fixed 0xc0 base and stamps four 2x2 blocks across the four quadrants of a contiguous 4x4 region (loc_51da, loc_51dc, loc_521a, loc_521c), the seed advancing four codes per quadrant so the four sub-blocks read as one composite glyph. `drawIndexedTileBlock` [code] rounds out the block family: it looks up a 2x2 block's seed code in the ROM tile-block table TILE_BLOCK_TABLE (0x215b) by index and stamps that block at the pending destination via the DE-swap entry.

### Timer-animated tile variants

Two register-only helpers compute *which* animation frame of a tile to draw, writing no memory. `computeTileVariantFromTimer` [code] folds a value into a 2-bit variant index -- nibble-swap the free-running frame counter loc_425f, add the value and an incoming carry, keep the low two bits -- but saturates instead to a fixed 0x80 out-of-range marker (via `markValueOutOfRange`) once the value reaches 112. `computeTileVariantFromValueAndTimer` [code] is the front end: it likewise saturates at/above 112, otherwise takes the value's low nibble and derives a carry set when the frame counter's low nibble is the smaller, then hands both to `computeTileVariantFromTimer`. Together they let a draw handler animate an on-screen icon (the mapped-coordinate draw handlers stamp the resulting variant into the cell that `mapPackedCoordToVram` resolved), the frame counter cycling the glyph while the 0x80 sentinel signals "out of range, draw nothing."

### Column primitives and periodic redraw

A "column" is three cells stacked vertically. `drawTileColumnTriple` [code] copies three source bytes up a column -- each byte to the destination, the destination's low byte then stepping `-0x20` per row within a fixed page -- and after the three advances the low byte by `+0x62` to line up the next column two cells over; it returns the advanced source and destination so column draws chain. `blankTileColumns` [code] is the erase counterpart: starting at loc_5193 it stamps the blank tile 0x10 into three cells per column (again `-0x20` per row, but here as a true 16-bit subtraction that would borrow into the high byte) and advances `+0x62` per column, looping a caller-supplied count where a count of zero wraps to 256 columns. `redrawTileColumnsPeriodically` [code] drives both on a schedule: it does nothing until DRAWN_COLUMN_COUNT (0x4241) reaches two, then keys off the frame counter's low six bits -- phase 0 wipes the run with `blankTileColumns`, phase 32 repaints it, the first column sourced from TILE_COLUMN_TABLE (0x039a) offset by the frame counter's top two bits and the rest streamed from the continuation table TILE_COLUMN_TABLE_CONT (0x03a6). That is the attract-mode marquee whose columns cycle on and off.

### Sequence-driven row fill/blank and state reset

A cluster of sequence-state handlers paints the screen a row at a time through the 16-bit fill cursor VRAM_WRITE_PTR (0x400b), each advancing the top-level SEQUENCE_STATE (0x400a) when its dwell tier expires. `primeVramFillAndAdvanceStep` [seen] sets one up: it clears the 128-byte flag block at FLAG_BITS_BASE (0x4100) and two status bytes (loc_425f, loc_4224), seeds the write cursor to `VRAM_BASE+2`, arms a 32-count page counter in loc_4009, and bumps the sequence step. `fillVramRowThenResetObjectState` [seen] and `blankVramRowThenResetSpriteState` [code] then each tick: they paint a 28-cell strip of tile 0x10 at the cursor (28, not 32, leaving the side margins) and step the cursor a full row (`+0x20`), decrementing the dwell tier loc_4009; only on its expiry do they do the heavy reset -- advance the sequence, re-arm the two-tier dwell cascade (loc_4008=64, loc_4009=4), reseed the stride-2 object-shadow field from its ROM template (0x1db1 for the former), and -- fillVramRowThenResetObjectState only -- clear the screen-flip latches FLIP_SCREEN_X/Y; the blank variant instead also wipes the sprite source and shadow blocks (SPRITE_SOURCE_OBJ_BASE 0x42b0, SPRITE_SHADOW_BASE 0x4060) and queues command word 6. `blankScreenRowsThenAdvanceSequence` [code] is the play-state version, blanking a full 32-cell row and stepping `+0x20` each tick, and on the last phase advancing the sequence and reseeding the object shadow. When one of these reset handlers queues its command word, the append closes through the unnamed shared stack epilogue loc_090b, which merely pops the caller's saved pointer and returns with no work-RAM effect.

### The projectile integrator (a sprite-shadow outlier)

Three routines grouped here operate on the enemy-shot records rather than the tilemap, staging into the sprite shadow instead of VRAM. `advanceAndRenderProjectiles` [code] integrates and renders seven 10-byte moving-object records at loc_4260 -- each holding two 5-byte sub-slots, with the frame/phase bit in loc_425f choosing which sub-slot leads this frame. For the leading, active sub-slot it advances the sub-position by two (deactivating on overflow), integrates the 16-bit position by twice the sign-extended velocity, and deactivates the slot when the position's high byte leaves the vertical window; deactivation zeroes the active, sub-position and high bytes. It then writes each object's Y and code into the sprite-shadow record at loc_4081 (4-byte stride), mirroring Y by the direction flag loc_4018 and nudging the code `+/-1` on the first three records. `flagProjectileHitsOnPlayer` [code] runs the collision pass -- only while the object subsystem is enabled (OBJ_ACTIVE_FLAG 0x4200 bit 0 set) it walks all fourteen projectile entries (base loc_4260, stride 5, that stride also serving as the Y-band delta) through `flagProjectileHitOnPlayer` [code], which box-tests one active entry's X against the player-X reference loc_4202 across a near/far Y band and, on overlap, deactivates the entry and raises HIT_EVENT_FLAG (0x4204) for the player-hit handler to consume.

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift.
- Many handlers stay `[code]` because their state was not reached by the attract + single-coin/one-player
  captures (a credited play branch, a deep formation state, a later board), or because their only side effect
  lands in VRAM or a hardware latch the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is
  owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs.
