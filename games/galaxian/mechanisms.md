# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–11.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

Underneath the game logic sits a small set of sharp-edged helpers the rest of the machine leans on: a pseudo-random source, two block/table memory primitives parked at the processor's low restart vectors so any routine can reach them with a single-byte call, an unsigned 8-bit divide, and the housekeeping that keeps the once-per-frame interrupt alive. None of them make game decisions on their own; they are the arithmetic and memory plumbing everything else is built out of.

Randomness comes from `advanceRandomSeed` [seen], a textbook linear-congruential step. It reads the single seed byte held in `RNG_SEED` (0x401e), computes `seed*5 + 1` truncated to eight bits, writes that result back over the old seed, and hands the same new byte to the caller as this draw's random value. The point worth holding onto is that `RNG_SEED` is not a fixed base but the running state of the generator: every draw both consumes and rewrites it, so successive calls walk the LCG sequence forward. The callers show the spread of uses from a single primitive. `reseedFormationObjectState` rolls a whole fresh byte into an enemy's vertical position; `chooseNextAttackerDirection` takes only the low bit to pick a launch direction; and `computeJitteredXVelocity` masks the draw down to 0..31 to add bounded jitter to a projectile's horizontal speed. In each case the shape is identical — one mutation of `RNG_SEED`, then a read of the freshly-advanced byte.

Memory fill is `fillMemoryBlock` [code], sitting at the 0x0010 restart vector. Given a destination pointer, a fill value, and a count, it stores the value into consecutive bytes while walking the pointer forward until the count is exhausted, then hands back the pointer one past the last byte written along with the spent count of zero. Its one subtlety is that count: because the loop writes first and decrements the counter afterward, a count of zero does not fill nothing — it wraps around and performs a full 256-byte fill. The destination is free to be ordinary work RAM or a memory-mapped hardware region, so the same primitive both zeroes blocks of object state and blanks the tile framebuffer; the screen- and RAM-clearing routines such as `fillScreenThenLatchConfigAndAdvanceState` and `resetObjectRamAndAdvanceSequence` all funnel their work through it.

Table lookup is `fetchIndexedTableByte` [code], at the 0x0020 restart vector. It takes a base pointer and an 8-bit index, adds the index to the pointer with the carry propagated up into the high byte, reads the byte found there, and returns it while leaving the advanced pointer behind for the caller to reuse. The carry-into-the-high-byte detail is what makes it more than a low-byte bump: this is a genuine 16-bit pointer add, so a large index can push the read across a 256-byte page boundary instead of wrapping back to the start of the page. The tile painters `drawTileGlyphOrBlock` and `drawIndexedTileBlock` use it to pull glyph and attribute data out of ROM tables by index.

Division is `divideUnsigned8` [code], a restoring unsigned divide of a dividend by a divisor over eight rounds. Each round compares the running remainder against the current divisor, subtracts the divisor when it still fits and records a 1 quotient bit (a 0 otherwise), shifts that bit up into the quotient, and shifts the divisor down one place for the next round. After the eighth round the quotient is the interface value the callers actually want, with the remaining dividend (the remainder) and the shifted-out divisor left behind as by-products; the whole thing is register math and touches no memory. This feeds the aiming code: `computeDirectionOctantFromSlope` [seen] divides a slope to distill a target bearing into one of eight octants, and `computeJitteredXVelocity` divides to scale a slope before folding in the RNG jitter described above — both steps in aiming projectiles at the player. The entry that clears the quotient accumulator and sets the eight-round counter (at 0x0048) and the compare/subtract body that follows it are gathered into this one routine.

Finally the frame heartbeat. Once per frame a vblank interrupt fires; its handler saves the working registers, acknowledges the interrupt by clearing the enable latch, does the frame's work, and ends in `rearmVblankInterruptAndRestoreRegs` [code]. That epilogue writes `IRQ_ENABLE` (0x7001) back to 1 to re-arm the latch so the next frame's vblank will interrupt again, then restores the six register pairs the handler saved on entry — IY, IX, HL, DE, BC, and finally AF, in the reverse of the order they were saved — and returns through the interrupted address, dropping the main loop back exactly where it left off. The re-arm is load-bearing rather than cosmetic: the handler deliberately cleared `IRQ_ENABLE` to acknowledge the current interrupt, and if this epilogue did not switch it back on, only the first frame's interrupt would ever fire and the per-frame loop would freeze forever. A humbler cousin is `loc_090b` [code], a deliberately-unnamed pure-stack epilogue used on the command-enqueue path: it restores the one saved pointer (HL) that its caller had stashed and returns, doing no work-RAM work of its own.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

Everything in this subsystem hangs off two nested selectors in work RAM. The outer one is `GAME_STATE` (0x4005), read once per frame and used to index a five-way jump into the top-level handlers: the boot fill, the attract loop, the "press start" screen, and the two in-play handlers. The inner one is `SEQUENCE_STATE` (0x400a), a sub-state counter that each top-level handler walks through its own list of per-step handlers. The whole machine advances by counting down timers and bumping these two bytes; almost every routine here either arms a timer, ticks one, or steps a selector when a timer expires.

### The dwell-timer cascade

Three consecutive cells form a single count-down cascade: the sub-timer `loc_4008`, the dwell tier `loc_4009`, and `SEQUENCE_STATE` (0x400a) right above them. The primitive that drives it is `tickCascadeCountdown` [seen]: it decrements the byte a pointer names, and — only on the frame that byte reaches zero — steps the pointer up one cell (staying inside the page) and *increments* the neighbour instead. Point it at `loc_4009` and its zero-crossing therefore bumps `SEQUENCE_STATE`; that is exactly how a step "expires" into the next step. `tickSequenceDwellTimer` [code] is the thin wrapper that aims the primitive at `loc_4009`, so it ticks the dwell tier once per frame and advances the sequence when the tier drains. `tickPrescaledSequenceTimer` [seen] adds one more prescaling tier in front: it counts `loc_4008` down every frame, and only when that sub-timer wraps does it reload it (to 60) and hand a single tick on into `loc_4009` — so the sequence advance is paced at one dwell tick per 60 frames rather than one per frame.

Arming the cascade is spread across small helpers. `reloadSequenceDwellTimer` [code] simply stamps `loc_4009` back to 80. `advanceSubstateAndReloadDwell` [code] bumps the sub-state counter its caller points at (always `SEQUENCE_STATE`) and then re-arms `loc_4009` through that same 80-frame reload — the canonical "move to the next step and give it a fresh dwell" action. `setSequenceStateByModeAndReloadDwell` [code] is the branching variant: it forces the counter to 4 or 14 depending on the mode bit `loc_4006`, then re-arms the dwell — used where a step must jump the sequence forward or back rather than merely increment it. `enterSequenceStep1` [code] is the hard reset of the cascade: it slams `SEQUENCE_STATE` to 1 and re-arms *both* tiers (`loc_4008` and `loc_4009`) to 3, so step 1 gets a very short countdown before it moves on.

### Boot configuration

Game state 0 runs `fillScreenThenLatchConfigAndAdvanceState` [seen]. Each frame it blanks a 32-cell slice of the tilemap at the fill cursor `VRAM_WRITE_PTR` (0x400b) and walks the cursor forward across the 0x5000-0x53ff page, while the per-state timer `loc_4008` counts down. When that timer expires the machine latches its configuration for the run: it resets the state cluster (`loc_4007`=1, mode bit `loc_4006`=0, `GAME_STATE`=1, `SEQUENCE_STATE`=0), folds DIP/input bits out of the input shadows into their flag cells — the two cabinet bits from `IN1_SHADOW` into `loc_4000`, one bit from `IN2_SHADOW` into `loc_401f`, and one from `IN0_SHADOW` into the flip flag `loc_400f` — and looks a coinage byte up from the four-entry table at `loc_0152`, indexed by the low two bits of `IN2_PORT` (0x7000), into `loc_40ac`. It then unpacks the packed formation bitmask at `loc_051b`, seeds the object-RAM shadow, writes the three player-1 status glyphs into VRAM at `PLAYER1_STATUS_VRAM` (0x5340) and its neighbours, and queues two deferred command words. Advancing `GAME_STATE` to 1 in the same breath hands the machine to the attract loop.

### The attract loop and its sub-states

Game state 1 is the attract sequence. Its top-level handler runs the per-frame formation/occupancy prep and then dispatches on `SEQUENCE_STATE` into a table of step handlers. Crucially, after whichever step runs, control falls into the credit check (described below) before the frame ends — so the attract loop is the place where an inserted coin is noticed.

The step handlers here are the entry and dwell states of the attract show. `initSequenceEnableStarfield` [seen] is the setup step: it queues two command words, raises `STARS_ENABLE` (0x7004) to switch the starfield on, clears the per-sequence work cells (`CURRENT_PLAYER` 0x400d, `loc_400e`, mode bit `loc_4006`, one-frame flag `loc_4019`), seeds the dwell cascade (`loc_4008`=96, `loc_4009`=16), and increments `SEQUENCE_STATE`. `armStepCountdownAndTickSequenceTimer` [seen] arms the one-frame countdown flag `loc_4019`=1 and then ticks the prescaled cascade; `loc_4019` is consumed by a later step that, on its expiry, advances the sequence and clears the flag block. Three further steps share an identical prologue — they each run the four per-frame subsystem updates (the strided-table clear, the sprite-shadow staging, the object-slot driver loop, and the periodic tile-column redraw) and then do their own timing work. `dwellThenAdvanceSequence` [code] does nothing after that prologue but tick the prescaled cascade — a pure dwell state that lets the attract animation play while the timer creeps toward the next step. `activateDescriptorSlotsThenAdvanceSequence` [seen] runs a two-phase countdown: when the sub-timer `loc_4008` expires it reloads it to 0xd2, activates the descriptor slot whose number sits in `loc_4009`, and bumps `DRAWN_COLUMN_COUNT` (0x4241); when the dwell tier then expires it reloads it, advances `SEQUENCE_STATE`, and clears `loc_4058`. `queueColumnDrawAndAdvanceSequence` [seen] counts `loc_4009` down and, on expiry, advances the sequence, clears `loc_4058`, re-arms the timer pair (`loc_4008`/`loc_4009` reset to 0x40/0x11), bumps `DRAWN_COLUMN_COUNT`, and enqueues a channel-6 column-draw command word.

### The credit transition

The credit count lives in `loc_4002`. During the attract loop, every step handler is followed by the credit test: if `loc_4002` is nonzero the machine advances `GAME_STATE` (1 → 2) and clears the attract sub-state cluster (`loc_4007`, `SEQUENCE_STATE`, the sweep countdown, the scroller enable). That single bump is what carries the machine out of the attract show and into the "press start" screen the moment a coin has been credited; a zero credit count leaves everything as it is and the attract loop simply repeats.

### The "press start" screen and starting a game

Game state 2 is handled by `runStartScreenAndLaunchGame` [code]. Each frame it runs the same formation-sweep and occupancy prep, dispatches on `SEQUENCE_STATE` (only 0..3 are reachable here, so a four-arm switch covers it) to reset object RAM, hold the start-button lamps, blank the screen rows, or drive the lamps, and then finishes by running the start-button launcher.

That launcher is `beginGameOnStartButton` [code]. It reads `IN1_SHADOW`: bit 0 begins a one-player game outright; bit 1, with at least two credits banked in `loc_4002`, spends two of them, blits the 32-byte ROM row template `loc_051b` into the saved-state snapshot `SAVED_STATE_SNAPSHOT` (0x41a0), optionally arms the state-advance gate when config bit `loc_401f` is set, and enters the round-start routine with a two-player spawn word. The one-player path is `startOnePlayerGame` [code]: with no credits it just forces `GAME_STATE` back to 1 (returning to attract); otherwise it spends a single credit, zeroes the saved-state snapshot, and enters the round-start with a null spawn word. Both paths funnel into the shared round-start setup, which stores the spawn word into `CURRENT_PLAYER`, blits the row template into `PACKED_FLAG_BITMAP` (0x4180), optionally arms the sub-state advance gate on `loc_401f`, resets `SEQUENCE_STATE`, sets `GAME_STATE`=3, raises the mode bit `loc_4006` and `loc_41d1`, and queues the start command words. Game state 3 is now live play.

### Play-field init and the play sub-states

The two in-play top-level handlers — game state 3 (single-player) and game state 4 (the restore-saved-game path) — each dispatch on `SEQUENCE_STATE` through their own step table, and the two tables share most entries.

`initPlayfieldState` [code] is step 0 of both. It turns both start lamps off, zero-fills the flag block `FLAG_BITS_BASE` (0x4100), the object/timer span from `OBJ_ACTIVE_FLAG` (0x4200), the template buffer `loc_4218`, and the object-record region from `loc_4260`, clears `loc_425f`, sets `loc_4226`=1, advances `SEQUENCE_STATE`, arms the dwell timer `loc_4009`=32, and points the VRAM fill cursor `VRAM_WRITE_PTR` back at `VRAM_BASE` (0x5000) so the next steps can repaint the field. `advanceSubstateAfterDwellAndQueue` [code] is a plain dwell step: tick `loc_4009`, and on its zero-cross reload it to 20, advance the sequence, and enqueue this step's command word (payload `loc_0682`).

The two board-entry steps diverge by player path. `restoreFormationAndEnterPlaySubstate` [seen] (state 3) unpacks the packed formation bitmap `PACKED_FLAG_BITMAP` into the flag grid, copies the trailing 8-byte board template into `loc_4218`, clears the status/flip/direction cells (`loc_425f`, `loc_4220`, `FLIP_SCREEN_X`/`FLIP_SCREEN_Y`, `loc_4018`), advances `SEQUENCE_STATE`, arms `loc_4009`=150, publishes the deferred-callback pointer `loc_0640` into `loc_4245`, and — when the sound gate `loc_4006` is open — cues the board-start sound. `restoreSavedStateAndEnterPlaySubstate` [code] (state 4) does the mirror: it expands the *saved* snapshot `SAVED_STATE_SNAPSHOT` into the flag block instead, copies its trailing template into `loc_4218`, and — when the flip flag `loc_400f` is set — mirrors it into the two display-flip latches, then advances the sequence, arms `loc_4009`=150, publishes callback pointer `loc_0830` into `loc_4245`, and queues five intro command words when the sound gate is open. Both routes let the paired-player flag `loc_400e` select the paired-player sound cue.

The step-6 handlers govern how a board resolves and either advances or loops. `stepPlaySubstate6` [code] (state 3) branches on the arm gate `loc_421d` and two mode flags: with the gate open it either advances the sub-state and re-arms the dwell, or sets the state by mode; with the gate closed it either runs the shared reset tail or — when both mode flags agree — inlines the advance itself, bumping `SEQUENCE_STATE`, arming `loc_4009`=130, and queuing two channel-6 command words when `loc_4006` is set. It keys its "advance" decision on the state-advance gate `loc_41b5`, which `armStateAdvanceGate` [code] stamps to the "armed" marker 3 so the handler reads it as nonzero. `stepAltPlaySubstate6` [code] (state 4) is the same shape keyed on `loc_4195` instead — the gate `armSubstateAdvanceGate` [seen] arms to 3 — re-arming the dwell to 80 on the show arm or 130 on the default arm. Both step-6 handlers share the reset tail `advanceDwellOrResetToState1` [code]: when the mode bit `loc_4006` is clear it just advances the sub-state and reloads the dwell, but when it is set it resets the whole machine to state 1 — `GAME_STATE`=1, clear `loc_4006` and `SEQUENCE_STATE`, silence the sound hardware and halt the interrupt and starfield, and queue command word 6 — which is how a finished game drops back toward attract.

### The command / event queue

Several routines above "queue a command word"; the queue itself is driven by `enqueueCommandWord` [seen]. It writes a 16-bit word (channel in the high byte, parameter in the low byte) into the queue block based at `loc_4000`, at the slot the write-head `loc_40a0` names — but only if that slot is still free (its bit 7 set). On a successful write it stores the two bytes, advances the head by two, and clamps it up to a floor of 0xc0 (so the live queue body sits from 0x40c0 upward). `commitQueueWriteHead` [seen] is the alternate exit that persists an already-advanced head back to `loc_40a0` and then returns through the shared stack epilogue `loc_090b` (a deliberately unnamed two-instruction tail that restores the caller's saved pointer and returns; it holds no state of its own). Two helpers post fixed bursts: `enqueueCommandWordBurst` [code] posts a five-word sound-cue burst (three words on the caller's channel and its successor, then two fixed channel-7 cues), and `queueBoardStartSoundBurst` [code] prefixes that burst with one channel-5 prologue word for the paired-player board-start cue.

### Per-frame gated timers inside play

The in-play update pipeline runs a long fixed list of subsystem updates every frame, and several of the timers in this subsystem live inside it. `armBehaviorGateOnInputOrTimer` [code] arms the player-shot behaviour gate `loc_4208`: it does nothing unless the subsystem is enabled (`OBJ_ACTIVE_FLAG` bit 0) and the gate is not already armed, then, on the timer path (mode `loc_4006` clear) it arms the gate only when the low five bits of the frame counter `loc_425f` are all zero — roughly once every 32 frames — while on the input path (mode set) it tests bit 4 of the selected input shadow (`IN0_SHADOW`/`IN1_SHADOW`, chosen by `loc_4018`) against its guard cell (`loc_4013`/`loc_4014`) and, on an active line, arms both the gate and the companion flag `loc_41cc`. Its counterpart `clearGateOnPendingRequest` [code] watches the retire-request flag `loc_420b`: when its bit 0 is pending it acknowledges the request (clears `loc_420b`) and clears the behaviour gate `loc_4208` the same pass.

`rampCounterToCeiling` [code] is the slow difficulty ramp: while the subsystem is enabled and the inhibit flag `loc_422b` is clear, it runs a two-tier prescaler (outer `loc_4218` reload 60, inner `loc_4219` reload 20) and, only on a full double-wrap, steps the 0..7 pace counter `loc_421a` up one, clamped at 7. That same inhibit flag `loc_422b` gates the delayed-event scheduler `scheduleDelayedEvent` [code], which — under three enable bits (`OBJ_ACTIVE_FLAG` and `loc_41ef` set, `loc_422b` clear) — runs its own two-tier timer (`loc_4245`/`loc_4246`) and, on a cascade elapse, arms the delayed-event triple: with the mode bit clear it arms fixed values (`DELAYED_EVENT_TIMER` 0x422f=90, `loc_424a`=45, `DELAYED_EVENT_ARMED` 0x422e=1); with it set it derives the payload from work-RAM word sums (`loc_4221`, or the byte-sums of `loc_4177` and `loc_421a`) and fans it into the triple by rotation. `fireDelayedEventRequest` [code] is the one-shot that consumes it: while `DELAYED_EVENT_ARMED` is set it counts `DELAYED_EVENT_TIMER` down, and on the zero tick it disarms and — only if both enable flags are still set — raises `DELAYED_EVENT_REQUEST` (0x4229) for the spawn dispatcher to act on. Finally `expireActivityGatedTimer` [code] closes an activity-gated phase: while the arm flag `loc_422b` is set and at least one activity gate is open (`loc_4224`, `loc_4221`, or `loc_4226` bit 0), it ticks the counter `loc_422c` and clears `loc_422b` when the counter reaches zero — releasing the inhibit that had been holding off the pace ramp and the delayed-event scheduler. After all these updates, the pipeline advances `SEQUENCE_STATE` only when the play field has gone quiescent, decrementing the dwell timer `loc_4009` and stepping the sequence on its zero-cross so the board can move to its next step once every attacker and shot has cleared.

### A shared clamp helper

`markValueOutOfRange` [code] stands slightly apart from the sequence machine: it is the saturation arm of a value clamp, forcing register B to the fixed 0x80 sentinel when a folded input is beyond range. The tile-variant computation uses it to mark an out-of-range index rather than wrap it, so a value at or above 112 saturates to the sentinel instead of producing a spurious low variant.

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

### One record array, several windows

Every alien, diving attacker, secondary, and descriptor the game tracks lives in one contiguous array of 32-byte object records beginning at SPRITE_SOURCE_OBJ_BASE (0x42b0). The code reaches into that array through several overlapping named windows, and the arithmetic makes the overlap exact: OBJ_TABLE (0x42d0) is the second record onward, DESCRIPTOR_SLOT_TABLE (0x4330) is records four through seven, and the launcher's scan-start loc_4391 (0x4391) is the header byte of the last record. A record's field layout is uniform throughout: byte 0 is the primary active flag, byte 2 the dispatch/phase index, bytes 3 and 4 the sprite X and Y, byte 5 the signed heading, byte 6 the direction bit, and byte 7 the packed grid cell (or source index). That one shared layout is what lets a handful of small routines seed, claim, position, and stage records interchangeably.

### The formation as a flag grid

The standing formation is not stored as coordinates but as a 128-cell flag block at FLAG_BITS_BASE (0x4100), one byte per cell, addressed by a packed index whose high nibble is the row and low nibble the column. unpackBitmaskToFlagBytes [seen] inflates a compact 16-byte bitmask at DE into those 128 bytes, writing a 1 for each set bit LSB-first and leaving DE pointing just past the mask so the caller can copy whatever data follows. packFlagBytesToBitmask [code] is its exact inverse — it reads bit 0 of the 128 bytes and re-packs them into a 16-byte bitmap, returning the pointer advanced by 16 so a block copy can chain on.

Those two primitives bracket the formation's save and restore. loadDescriptorAndAdvanceSequence [code] unpacks a ROM template at loc_051b into the flag block, copies the eight template bytes that follow it into the working buffer loc_4218, clears loc_425f, sets loc_421d, advances SEQUENCE_STATE (0x400a), publishes the deferred pointer loc_0640 into loc_4245, and — a small current-state quirk — stamps 150 into VRAM_WRITE_PTR (0x400b), reusing the byte named for the VRAM fill cursor as a plain dwell counter in this state. packFlagsToBitmapAndSwitchPlayerState [code] and saveFlagsToSnapshotAndSwitchPlayerState [code] are the two terminals that run the reverse: each ticks the dwell timer loc_4009 and, only on its zero-crossing, packs the live flag block back out — one into PACKED_FLAG_BITMAP (0x4180) and the other into SAVED_STATE_SNAPSHOT (0x41a0) — appends the eight-byte loc_4218 companion just after it, and hands off to the next phase (CURRENT_PLAYER = 1 with GAME_STATE = 4 for the first; CURRENT_PLAYER = 0 with GAME_STATE = 3 for the second). clearFlagBlockAndReseedObjectShadow [code] is the between-lives reset: it zero-fills the whole 128-byte block, clears loc_425f and loc_4238, arms loc_4009 to 64, and falls through to the shadow reseed described next.

### Seeding the object shadow

At screen and formation init the interleaved OBJRAM shadow is laid down by seedObjectRamShadowField [seen]: it copies 32 source bytes into every other cell of the field starting at loc_4021 — 0x4021, 0x4023, ... 0x405f — so each source byte occupies one field of a stride-2 record. seedObjectShadowFromRom [seen] is the fixed-source wrapper: it points that copier at STRIDED_TABLE_SRC (0x1d71) and runs it. advanceSequenceStateAndReseedObjectShadow [code] pairs the reseed with a state bump — it advances the low byte of the pointer it is given (staying in-page), increments the byte that pointer now names, then reseeds the shadow. Both callers arrive with the pointer at loc_4009, so the increment lands on 0x400a and steps SEQUENCE_STATE while the fresh object field is being laid, which is exactly what clearFlagBlockAndReseedObjectShadow relies on.

### Reading the field back: occupancy

summarizeFormationOccupancy [seen] is the per-frame reduction that turns the flag grid back into motion inputs. It reads a 6-row by 10-column window with a 16-byte row stride beginning at OCCUPANCY_GRID (0x4123) — and the counterintuitive current fact is that this window is the same physical block as FLAG_BITS_BASE: 0x4123 is 0x4100 plus the two guard rows and three guard columns, so the summarizer and the packed-cell code reach identical cells through two coordinate systems. It ORs each row into ROW_OCCUPANCY (0x41e8, sitting behind two always-zero guard cells) and each column into COLUMN_OCCUPANCY (0x41f0, behind three), then scans the column summaries inward from each end — one 16-unit step per empty column — to derive the horizontal travel limits, packing them into FORMATION_X_BOUNDS (0x4210) with the from-right bound in the low byte and the from-left bound in the high byte. Finally it folds four region "clear" flags: loc_4221 from the top four row summaries and loc_4220 from all six, loc_4226 from seven OBJ_TABLE (0x42d0) active-flag bytes and loc_4225 from eight sprite-source byte-1 fields based at loc_42b1. Each is stored inverted — bit 0 is the XOR of "any occupied," so a set bit 0 means that region is empty — which is why the launch and stage-advance gates downstream test these bits for clear.

### The side-to-side sweep

The whole formation's sway is one 16-bit number, the swept anchor loc_420e (0x420e). advanceFormationSweepOscillator [seen] moves it once every four frames (throttled on loc_425f's low two bits), one unit toward whichever FORMATION_X_BOUNDS edge the direction flag OBJ_SWEEP_DIRECTION (0x420d) selects. When the ascending phase reaches the upper bound it calls setSweepDescending [seen] (OBJ_SWEEP_DIRECTION = 1); when the descending phase reaches the lower bound it calls setSweepAscending [seen] (= 0). After each step it broadcasts the new offset across a nine-cell stride-2 per-column table at loc_4028 — 0x4028, 0x402a, ... 0x4038. That broadcast is the job of broadcastToStridedTable [seen], which stamps the byte in A into those nine cells; clearStridedTable [seen] is the zero case, run as a per-state reset; broadcastNegatedSweepToStridedTable [seen] broadcasts the two's-complement of a low byte; and broadcastNegatedFormationSweepToStridedTable [code] is the convenience that feeds it loc_420e's low byte. The oscillator carries a leading proximity gate: if the player shot is armed (loc_4208 bit 0), its position (loc_4209) lands in a narrow window, and the swept column (derived from loc_420a minus loc_420e) reads occupied in COLUMN_OCCUPANCY, it skips the step entirely and just re-broadcasts the current anchor — keeping the column aligned under a shot rather than swaying out from under it.

### Placing objects on the grid

positionObjectFromGridCell [code] converts a record's packed cell (byte 7) into its sprite X and Y, and it rotates the axes ninety degrees: the ROW bits (cell & 0x70) drive the X field (byte 3) as a fixed origin of 124 minus three-quarters of the row, while the COLUMN bits (cell & 0x0f) drive the Y field (byte 4) as the moving anchor loc_420e plus the column times sixteen plus a seven-pixel hotspot. So an object riding the formation inherits the sway through its Y field, and its grid column becomes a screen row.

Several state handlers build on that. settleObjectIntoFormationCell [code] runs an object flying back into place: it bumps the frame counter in byte 3, repositions from the cell, and compares the two; when the counter catches the positioned value it deactivates the object, sets that cell's flag in FLAG_BITS_BASE, and enqueues a command word carrying the cell, while a small even gap nudges the phase (byte 5) by the direction bit and a large or odd gap is left alone. initSpawnedObjectFromGridCell [code] is the first tick of a freshly launched attacker: it clears the step timer, raises the spawn flag loc_41c2, positions from the cell, enqueues a type-1 spawn word, and looks up the sprite number and flight-curve seed from SPAWN_RECORD_TABLE (0x1dd1) indexed by row; on the top row it also tallies its two look-ahead neighbour slots into ACTIVE_NEIGHBOR_COUNT (0x422a), then seeds the motion counters, advances the sub-state, and picks the signed heading (plus or minus 12) from the direction bit. reseedFormationObjectState [code] re-inits a formation object — X back to the left edge, heading cleared, leg counter ticked — and then branches on the packed cell: an ordinary cell rolls a fresh random Y and advances the state twice when the subsystem is enabled and an activity gate (loc_4224 or loc_4221) is open; the sentinel cell whose high bits are all set (0x70) instead recounts the two neighbour slots into ACTIVE_NEIGHBOR_COUNT and, once none remain, deactivates the object and ramps the phase counter loc_421e toward a ceiling of 2. The shared neighbour helper bumpCountIfNeighborsInactive [code] expresses the same look-ahead in the small — it returns its running count plus one only when both slots 32 and 64 bytes above the base are inactive. noopAnimDispatchSlot [code] is the empty terminal of the object-animation dispatch table, a valid do-nothing target for a spent sub-state.

### Pacing and launching attackers out of the formation

Launches are metered by paceEnemyLaunchTrigger [code], a gated prescaler that runs only while the play flag OBJ_ACTIVE_FLAG (0x4200) is set and the inhibits loc_4220 and loc_422b are clear. It ticks a master counter loc_424a and, until it expires, keeps the refill flag down. On expiry it reloads the master from SUBCOUNTER_RELOAD_TABLE (0x15e3) and sweeps a span of attacker sub-counters — the span widening with the pace counter loc_421a and the clamped stage loc_421b — refilling each that reaches zero and raising SUBCOUNTER_REFILL_FLAG (0x4228) if any did. launchAttackerFromFormation [code] consumes that one-shot: while the region-clear gate loc_4220 is clear, it derives a slot budget of one to four (folded from the pace counter and stage, so more attackers peel off as pacing climbs), claims the first free record scanning down from loc_4391 through the descriptor-slot pool, stamps the launch direction loc_4215 into byte 6 of the record, picks an occupied column from COLUMN_OCCUPANCY by direction (its grid geometry chosen by loc_41ef), then walks that column of FLAG_BITS_BASE for a filled cell — clears the cell, activates the record at phase 0 with the cell's low byte as its source index, and enqueues the type-1 spawn word. The formation grid is thus the single source of truth: an alien is "launched" by being cleared from the grid and re-embodied as a live diving record.

flagPlayerShotHitOnFormation [code] closes the loop from the player's side. While the shot gate loc_4208 is armed it bands the shot's Y (loc_4209) into a formation row through the same 7-then-5 spacing the grid uses, bands its X delta (loc_420a minus the anchor loc_420e) into a column, forms the packed index, and tests that FLAG_BITS_BASE cell; if it holds a live alien it clears it, stamps a hit record (loc_420b, loc_42b1, loc_42b2, and the shot's position word into loc_42b3), and enqueues two command words — a kind-1 word carrying the grid index and a kind-3 word carrying a column code — which carry the kill off to scoring and sound.

### Spawning families of objects

A cluster of small claimers turns trigger flags into live records. activateObjectSlotAndEnqueueSpawn [code] is the shared seeder: given a trigger cell and a record, it consumes the trigger (writes 0), marks the record active with a cleared phase, records the spawn code in byte 6 and the trigger pointer's low byte as the source index in byte 7, and enqueues the type-1 spawn word keyed by that index. spawnSecondaryObjectIntoSlot [code] is the same idea for a secondary record but guarded — it bails if either of the record's two live flags is already set, otherwise consumes the trigger, marks it alive, inherits byte 6 from a source record, stashes the trigger index in byte 7, and enqueues its word. spawnIntoFreeDescriptorSlot [code] scans the four descriptor slots at DESCRIPTOR_SLOT_TABLE (0x4330) high to low for one whose two header bytes are both zero and seeds that one. activateDescriptorSlot [seen] is a separate, fuller initialiser used elsewhere: it selects the (number minus one) slot in that same table and stamps its fixed init fields — byte 0 = 1 (active), byte 2 = 13, byte 5 = 12, byte 7 = the slot index — while leaving bytes 3 and 6 untouched.

Those leaves compose into the family spawners. spawnSecondaryObjectAndAdvanceWalk [code] is one step of a secondary walk: it spawns into the current record, advances the record pointer by 32 and the budget down, and when the budget hits zero forces the caller's loop counter to 1 so the walk ends after this pass. spawnPrimaryAndSecondaryObjects [code] spawns a primary into OBJ_TABLE (0x42d0), then walks three trigger flags backed up fifteen from the primary trigger's low byte and spawns a secondary into each following slot until a budget of two is spent. spawnObjectsFromTriggerFlags [code] scans the primary trigger block PRIMARY_TRIGGER_BLOCK (0x4176): the first set flag spawns a primary plus up to two secondaries from the secondary block SECONDARY_TRIGGER_BLOCK (0x4165); if no primary flag is set it scans the secondary block instead and seeds a free descriptor slot on the first hit. spawnObjectsOnDelayedEvent [code] is the per-frame dispatcher over all of this: it is gated on the region-clear flag loc_4220 being clear, OBJ_ACTIVE_FLAG set, and a pending DELAYED_EVENT_REQUEST (0x4229) which it consumes as a one-shot, and it holds while the OBJ_TABLE head word is odd; then the launch direction loc_4215 bit 0 routes either a full trigger-block spawn or a high-to-low scan of the primary block (spawn a primary plus secondaries) followed by the secondary window (seed a free descriptor slot).

### Advancing the stage

armFormationAdvanceTrigger [code] is the one-shot that schedules a stage change: only when both region-clear gates loc_4220 and loc_4225 have bit 0 set (the field is empty) and the pending word loc_4222 is not already armed does it write loc_4222 = 1 (enable byte 1, zeroed countdown). advanceStageAndReseedFormation [code] consumes it: on the tick the enable is set and its countdown loc_4223 lands at zero, it disarms the enable, rebuilds the 128-flag block from the packed template loc_051b, resets the pace counter loc_421a and loc_425f, reseeds the formation anchor loc_420e to 1, and steps the stage selector loc_421b — whose high byte counts stages upward while its low byte advances but saturates at 7 — then enqueues a command word and services a pending two-slot request in loc_421e by raising loc_4177 and, if a second remains, loc_4178.

### Staging records to sprites

Finally, stageObjectsToSpriteShadow [seen] is the per-frame bridge from records to hardware sprites: it renders eight consecutive object records at SPRITE_SOURCE_OBJ_BASE (0x42b0) into eight consecutive four-byte sprite-shadow records at SPRITE_SHADOW_BASE (0x4060), as a band of three followed by a band of five, at a Y offset the orientation bit loc_4018 selects (9 or 7 for the first band, both settling to 8 for the tail).

Several of these routines end their command-enqueue path through a shared return tail, loc_090b [code], which merely restores a saved register and returns without touching work RAM.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

This subsystem is the beating heart of a play frame: it moves the player's ship and its single shot, runs every attacker object through a sixteen-state behaviour machine, spawns and aims the enemy shots those attackers fire, and adjudicates every collision between the two sides. All of it hangs off one per-frame driver, `runGameplayFrameAndAdvanceOnFieldClear` [code], so it is easiest to read from the ship outward and end at that driver.

### The player ship and its shot

The ship's position lives in a single byte, `loc_4202` (0x4202) — the player-X reference that almost every routine in this section consults. `moveControlledObjectAndStageSprite` [code] owns it. Each frame, if the object subsystem is enabled (`OBJ_ACTIVE_FLAG`, 0x4200, bit 0), it picks a movement command from one of three sources: when the auto/demo bit `loc_4006` bit 0 is clear it takes the AI-generated command `OBJ_MOVE_CMD` (0x423f); otherwise it reads a live input port — `IN1_SHADOW` (0x4011) when the mirror flag `loc_4018` bit 0 is set, else `IN0_SHADOW` (0x4010). Command bit 3 nudges the ship one pixel toward the low end while it stays above 23, bit 2 nudges it up while it stays below 233 — so the same routine flies the ship for the attract-mode demo and for a human player, differing only in where the two move bits come from. Whatever the outcome, it then stages the *negated* position (one's-complement plus 128) together with a code byte as four identical `(value, code)` pairs into `OBJ_STAGE_BLOCK` (0x4054); an inactive ship either parks its position at zero (code 6) or, in the alternate mode flagged by `loc_4201`, stages the current position under code 7 without clamping.

The ship fires exactly one shot, tracked by a small block of cells. `advancePlayerShot` [code] services it: while the fire gate `loc_4208` bit 0 is armed it drains the shot's travel counter `loc_4209` by four every frame (the shot climbing the screen) and, on the frame that counter lands in the narrow window 14..17 — the top-of-travel band, which the original reaches through a chained double subtraction that borrows exactly across those four values — it raises the retire flag `loc_420b`. While the gate is clear the shot is parked: the counter is reset to 220 (the bottom) and the field cell `loc_420a` is seeded from the ship's X `loc_4202` whenever the subsystem is enabled, else zeroed. `advancePlayerShotAndStageSprite` [code] wraps that: after servicing the shot it reads the `{loc_4209, loc_420a}` pair back as a coordinate and writes the shot's two render cells, `loc_409f` (low byte, chosen by `loc_4018` bit 0 between `counter-1` and `~counter+252`) and `loc_409d` (the complemented field). So the shot's screen sprite is derived straight from its travel counter and its launch-time X.

### The attacker objects and the state machine that drives them

Attackers are fixed-size records laid out on a 0x20-byte stride. `driveAllObjectSlots` [code] walks eight of them starting at `SPRITE_SOURCE_OBJ_BASE` (0x42b0); the seven records the collision sweeps and target-pickers call the "object table" begin one stride later at `OBJ_TABLE` (0x42d0), so the eight driven slots are that lead slot plus the seven table entries. For each record `driveObjectSlot` [code] makes a three-way choice: a record whose death-anim flag (record+1, bit 0) is set is handed to the dying-object animator; an inactive record (record+0, bit 0 clear) is skipped; otherwise the record's state index (record+2, values 0..15) selects one of sixteen behaviour handlers. That index *is* the object's script: freshly-launched attackers begin at the spawn-init state, walk a canned path, cross toward the player, dive, fire, and either die or settle back into the formation, each transition written by the handler bumping record+2.

Two of those sixteen slots are the settle/hold handlers in this subsystem. `settleObjectXAtRest` [seen] (state 15) steps record+4 up one count per frame until the 8-bit-wrapped distance from the rest value 200 falls within 5, then holds — the object coasting to a fixed resting coordinate and parking there. `initObjectPhaseSteps` [seen] (state 13) is a phase-entry: it derives a step count `n = (~record+7) & 3`, records `n+1` at record+22 and a code byte `((n+1)<<4)+140` at record+3, arms the phase timer record+16 to 24, advances the sub-state, and clears the ready flag record+15 — re-arming it to 24 only when `n` came out zero.

### Choosing and committing a horizontal move

Several states share a small family of horizontal-target pickers. The primitive is `commitMoveToTargetX` [seen]: given a chosen target X it stores the target at record+0x19, records the signed per-frame delta `current-minus-target` at record+0x09, zeroes the three-byte move accumulator at record+0x1a, and advances the planner sub-state (record+2). `commitMoveAcrossPlayerX` [code] chooses that target so the object crosses to the *opposite* side of the ship: it signed-halves the gap between the actor's X (record+4) and `loc_4202`, applies a bias of 16, and clamps into the far band — 144..208 when the actor is left of the ship, 48..112 when at or right of it — then commits via `commitMoveToTargetX`. `commitMoveToStoredOrPlayerTargetX` [code] adds a branch: if the object table's own mode flag (`OBJ_TABLE` bit 0) is set it steers toward a target X stored at `OBJ_TABLE+0x19`, otherwise it falls back to the crossover pick. `advanceActorPhaseAndCommitMove` [code] (state 2) is the routine that decides between them per object: it ticks the actor's phase counter record+3, then routes by the kind field — record+7 masked to 0x70 equal to 0x60 uses the stored/player select, every other kind uses the plain crossover.

`beginObjectCrossPlayerMove` [code] is the shared tail used to *begin* a fresh crossover: it commits the cross-player move, then seeds the flight-curve step seed record+0x18 to 3 (which becomes four curve steps, see below) and the move throttle record+0x10 to 100. Two states enter through it. `armDirectedMoveWhenInWindow` [code] (state 8) ticks an arm counter record+3 and, until both that counter and the position record+4 sit inside the window [96,160), keeps cruising via `beginObjectCrossPlayerMove`; once both are in-window it jumps the sub-state forward by two, seeds the move timers (record+0x10=3, record+0x11=12), clears record+5 and record+0x13, and sets the direction bit record+6 from the `loc_4202` comparison. `restartObjectMoveRun` [code] (state 12) simply bumps record+3, forces the state back to 8, and re-enters `beginObjectCrossPlayerMove` — restarting the arm-window run.

### Walking the canned attack paths

The scripted swoop paths are tables of delta pairs at `PATH_STEP_TABLE` (0x1e00), walked by a per-object cursor. `advanceObjectPathStep` [code] (state 1) reads the cursor at record+0x13's sibling record+19, adds the first table byte to record+3, then adds the direction-controlled second byte to record+4 (subtracting when the direction bit record+6 says "toward the far edge", adding otherwise); if that coordinate plus a 7-pixel margin crosses below the near edge (14) it forces the fall-away state 5. Otherwise it advances the cursor, ticks the move throttle record+16 (reload 4) and on throttle expiry nudges the cross-step record+5 and ticks the leg counter record+17, advancing the state when the leg finishes. `advanceObjectPathStepDescending` [code] (state 10) is the subtract-direction mirror: it subtracts the table's X delta from record+3 and, unless the direction bit hands the vertical half off to the ascending arm, subtracts the Y delta from record+4, ticking the same throttle/leg counters and, on a finished leg, reloading throttle=3, leg=12, heading=12, cursor=0. `advanceObjectPathStepAscending` [code] is that ascending arm — it adds the table byte at the handed-in pointer to record+4, advances the cursor, and on a finished leg reloads the same trio but with heading 244 instead of 12 (the mirror-image angle). `advanceObjectPathStepAlias` [code] (state 11) is a bare trampoline that forwards, unchanged, to the state-1 path walker; it holds no state of its own.

### The flight curve, the dive, and the swoop

The organic-looking swoop comes from `advanceObjectFlightCurve` [code], a cross-coupled fixed-point rotation over two 16-bit accumulators held in the record (hi/lo at record+0x19/+0x1b and record+0x1a/+0x1c). It runs `((record+0x18 seed)&3)+1` integration steps; each step adds twice the *other* accumulator's sign-extended high byte into this one, with a guard that reverts any step whose result high byte lands on exactly 128. The high bytes those accumulators settle at become the swoop offset the dive and flight handlers fold into the screen coordinate — which is why `beginObjectCrossPlayerMove` seeds record+0x18 to 3, giving four rotation steps per frame.

`advanceObjectDiveStep` [code] (state 4) drives the plunge: it steps record+3 by one or two on the frame-parity bit `loc_425f`, and if that progress lands inside the window [6,9) it bumps the state and stops; otherwise it runs the flight curve and folds the curve heading (record+0x19) plus the per-object increment (record+9) into a new screen coordinate record+4 — but if that sum carries across the signed boundary (the swoop running off the bottom) it bumps the state instead of storing. `advanceObjectFlightAndFire` [seen] (state 3) is the airborne firing state: it bumps the counter record+3, runs the flight curve, sets record+4 to `increment + curve-heading`, and checks two exits — a too-high coordinate (folds below 0x0e) advances the state by two, a counter that has run out (record+3 ≥ 0xb8) advances it by one. Failing both, and gated by `OBJ_ACTIVE_FLAG` bit 0, it aims at the player and — unless the delayed-event inhibit `loc_422b` bit 0 is set — scans the firing-row table `loc_4213` for its counter value, firing an aimed shot on a match. `advanceHomingObjectFlightAndFire` [code] (state 9) is the same shape with a homing pre-step: per the mode byte record+0x17 (mode 4 homes only on odd frame parity, mode > 4 always, mode < 4 never) it walks the column field record+9 one step toward `loc_4202` before computing record+4; its exits enter fixed states 5 and 4 and, failing those, its move throttle record+0x10 advances the state on expiry, then it aims and fires exactly as the non-homing flight state does. `homeObjectXTowardPlayer` [code] (state 7) is the pure tracking state: it ticks record+3 and steers the object's 16-bit position:subpixel pair (record+4 high, record+9 low) by roughly four times the signed distance to `loc_4202` each frame — carrying a small rounding bias — and advances the state when the dwell timer record+16 drains to zero.

### Aiming and firing enemy shots

When a firing state decides to shoot, `aimObjectAtTarget` [seen] computes the heading: from the vertical drop `0xf0 - record+3` and the horizontal delta `loc_4202 - record+4` it derives a direction octant, mirroring the octant when the target is to the left, and stores it in the object's direction field record+5. The octant itself comes from `computeDirectionOctantFromSlope` [seen], which divides the slope's dividend by its divisor, clamps a top-bit-set (too-steep) quotient to 0x80, and returns the top three bits as a 0..7 octant. The actual shot is created by `spawnAimedProjectileAtPlayer` [code]: it claims the first free entry in the fourteen-slot enemy-shot table at `loc_4260` (0x4260, stride 5, active = entry[0] bit 0), copies the object's coordinates into the entry's Y and X, and stores a scaled X velocity toward the player (mirrored when the target is left). That velocity comes from `computeJitteredXVelocity` [code], which divides the slope for the deterministic part, adds a bounded PRNG draw (0..31) plus a floor of 6, and clamps to 0x7f on overflow — so aimed shots carry a small random spread rather than converging perfectly. The table is left untouched when it is already full.

### Building the sprites

`renderObjectSprite` [seen] turns one object record into one hardware sprite record. An active object (record+0 bit 0) copies its sprite number from record+0x16 and its position — sprite X = `record+3 - 8`, sprite Y = `~record+4 - yOffset` — then folds the signed heading record+5 into a display attribute: the fold rotates the heading by whole 24-count sectors down into the range [-12,+11], maps the settled value to a facing attribute added onto the base attribute record+0x0f, and nudges the sprite one pixel on the diagonal cases. A secondary-active object (record+1 bit 0) instead uses fixed sprite number 7 and the alternate attribute record+0x12. With both flags clear the sprite is parked off-screen at (248,248). The `yOffset` argument lets the caller lift a band of sprites, and the display axes here are rotated ninety degrees from the formation grid — record+3 driving the hardware X cell, record+4 the Y cell.

### Scheduling the dives and generating the demo's moves

Which attacker peels off, and in which direction, is decided by a few schedulers. `chooseNextAttackerDirection` [code] sets the shared launch/curve direction flag `loc_4215` to 0 or 1: the sign of the 16-bit formation anchor `loc_420e` picks which `FORMATION_X_BOUNDS` (0x4210) edge to measure the gap against, and within 28 pixels of that edge the flag is forced away from it (0 near the high bound, 1 near the low), otherwise a fresh random bit chooses. `selectAttackerRowScan` [code] chooses which formation row a diver will come from: seeded by the alt flag `loc_421b` (slot 2/base 157 when set, else slot 1/base 132), it scans up to four two-byte slots of `ROW_OCCUPANCY` (0x41e8), advancing past any slot whose two bytes both have bit 0 clear, and stores the resulting `(slot, base)` pair into `loc_4213` — the very pair the flight/homing firing states scan for their firing rows.

The attract-mode ship pilot is `computeControlledObjectMoveCommand` [code]. Once every 32 frames (keyed on `loc_425f`) and only while the demo enable `loc_4007` bit 0 and `OBJ_ACTIVE_FLAG` bit 0 are both set, it folds a position weight across both object tables via `accumulateObjectPositionWeight` [code], adds a scaled offset of the formation anchor `loc_420e` against the ship `loc_4202` plus a random ±1 nudge, and buckets the biased result into `OBJ_MOVE_CMD` = 0, 4, or 8 — the auto command that `moveControlledObjectAndStageSprite` reads. `accumulateObjectPositionWeight` is the per-object term: it contributes nothing unless the object is active, its vertical field sits in one of two 52-row bands from 128, and its X delta from `loc_4202` is in the lower half; when it qualifies it folds the flag bit and two X-delta bits into a 0..15 index and adds the signed step `OBJ_STEP_TABLE` (0x1a45)[index] to the running total. So the demo ship is drawn toward whichever side of the field carries the greater weighted threat.

### The dying-object animation

A record whose death-anim flag (record+1) is set is handed by `driveObjectSlot` to `dispatchDeactivatedObjectAnim` [code], which reads the animation sub-state record+2 and tail-dispatches to one of four phase handlers. Sub-state 0 seeds the animation and posts a sound request; sub-state 1 is `tickDeactivatedObjectAnim` [code], which counts a fast timer record+16 down (reloading it to 4 and bumping a companion record+18 on each elapse), then a slow timer record+17, and on the slow elapse either retires the object (clearing state byte record+1) or — when the position field record+7 has reached 112 — reloads the fast timer to 50, seeds the companion from the global `loc_422d` plus 32, and advances the sub-state. Sub-state 2 is `endObjectAnimOnTimerExpiry` [code], a plain dwell that ticks the expiry timer record+16 and clears the state byte record+1 to retire the object when it reaches zero; sub-state 3 is the no-op terminal slot.

### Collisions

Two symmetric sweeps handle the two sides. `flagPlayerShotHitsOnObjects` [code], gated by the shot gate `loc_4208` bit 0, box-tests the shot against each of the seven `OBJ_TABLE` records (stride 0x20) via `flagPlayerShotHitOnObject` [code]; that per-object test checks an active record's coordinates against the shot reference `{loc_4209, loc_420a}` inside a 6-wide by 12-tall box and, on an overlap, raises the shot-retire flag `loc_420b` and hands off to the kill-scoring/deactivation routine. `flagObjectHitsOnPlayer` [code], gated by `OBJ_ACTIVE_FLAG` bit 0, runs the mirror image via `flagObjectHitOnPlayer` [code]: it classifies each active object's record+3 (biased by 33) into a near window (< 5) or far window (< 17), tests the player-X delta `loc_4202 - record+4` against that window's band, and on an overlap raises `HIT_EVENT_FLAG` (0x4204) and hands off the kill.

The raised `HIT_EVENT_FLAG` is consumed by `handlePlayerHitEvent` [code], the routine that reacts to the player being struck. If the flag's bit 0 is clear it does nothing; otherwise it clears the flag, zeroes `OBJ_ACTIVE_FLAG` and sets `loc_4201`, arms the two death-sound pulse counters `loc_4205`=10 and `loc_4206`=4, queues the hit-sound command, decrements the pace counter `loc_421a` (floored at zero), steps the [0,5] cycle counter `loc_421d`, and — when the sound mode `loc_4006` bit 0 is set — pulses `SOUND_W_REG3` (0x6803). This is where a player death both silences the enemy field and winds the difficulty back one notch.

### Bringing the field up and running the frame

Two sequence-setup steps prepare the object subsystem before play. `resetObjectRamAndAdvanceSequence` [code] seeds the interleaved object-RAM shadow from the ROM template `loc_1d91`, zero-fills the sprite-shadow span `SPRITE_SHADOW_BASE` (0x4060) and a broad object-record region from `loc_4260`, clears status cells, points the VRAM cursor `VRAM_WRITE_PTR` two cells into the grid, arms the dwell tier `loc_4009`, and bumps `SEQUENCE_STATE`. `activateObjectsAndBeginPlayPhase` [code] is the state timer that actually turns the subsystem on: it ticks `loc_4009` and, on expiry, reloads it to 10, advances `SEQUENCE_STATE`, sets `OBJ_ACTIVE_FLAG`, centres the ship reference `loc_4202` at 128, refills the sixteen-byte enemy-launch sub-counter block `loc_424a` from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears the scratch cells `loc_4058`/`loc_405a`, and queues two display commands.

Once play is live, `runGameplayFrameAndAdvanceOnFieldClear` [code] runs the whole thing every frame. It executes twenty-seven subsystem updates in fixed order — the ship move-and-stage, the shot service-and-stage, the enemy-shot integrator, the eight-slot object driver `driveAllObjectSlots`, sprite staging, the behaviour-gate arm, all four collision flaggers, the spawn/launch/pace/delayed-event schedulers, `selectAttackerRowScan` and `chooseNextAttackerDirection`, the difficulty ramp, `handlePlayerHitEvent`, the sound drivers, the stage-advance/reseed, and finally `computeControlledObjectMoveCommand`. Only after all of that does it apply a three-part quiescence guard: it advances the board-clear timer solely when no live bit remains in `loc_4208`, `loc_4201`, or `OBJ_ACTIVE_FLAG`, the stage-advance side flag `loc_4225` bit 0 is set, and none of the fourteen five-byte enemy-shot records at `loc_4260` is still active. When the field is finally that quiet it ticks the sequence dwell `loc_4009` and, on its zero-crossing, advances `SEQUENCE_STATE` — the frame-level condition under which a cleared wave finally rolls forward. (The command-enqueue paths several of these routines use share a deliberately-unnamed return stub, `loc_090b` [code], that carries no gameplay state.)

## Sound

The sound hardware is a bank of discrete write registers that almost nothing touches directly: eight composite/latch registers at 0x6800-0x6807 (SOUND_W_REG0 through SOUND_W_REG7), four LFO-frequency latches at 0x6004-0x6007 (SOUND_LFO_FREQ), and a pitch latch at 0x7800 (SOUND_PITCH_W). Rather than write those ports scattershot, the machine composes each frame's sound into a small block of work-RAM shadows and latches them out in one pass. `driveSoundFrame` [code] is that once-per-frame heartbeat, pumped from the frame-service path (the audio+input tick and the main game-state dispatcher call it each frame). It opens on a clean slate — the composite flag byte at 0x41c0 (loc_41c0) zeroed and the staged-pitch shadow SOUND_PITCH (0x41c1) primed to 0xFF — then runs seven channel/effect updaters in a fixed order, each of which may write those two shadows, and finally latches the result: the composite byte goes to SOUND_W_REG6, its rotate-right to SOUND_W_REG7, and the staged pitch to the pitch latch SOUND_PITCH_W. The composite byte therefore ends the frame carrying a small code for which voice last claimed it (a sequence channel leaves 2, the pulse/flag path leaves 1, the ramp leaves 0), and reg6/reg7 receive that code and its bit-rotation.

**The seven updaters.** In order, `driveSoundFrame` runs `armSoundSequenceOnRequest` [seen], `updateSoundSweepVoice` [code], `armSoundSequenceBySelector` [code], `advanceAllSoundSequenceChannels` [code], `advancePulseToneEnvelope` [code], `driveRisingPitchRamp` [code], and `advanceGatedSquareTone` [code]. The first, third and fourth make up the sequence player; the second is the swept "voice"; the fifth through seventh are the pulse, ramp and square-tone envelopes.

**The sound-sequence player.** Three small one-byte descriptors act as channel slots — 0x41d2 (loc_41d2), 0x41cf (loc_41cf), and SOUND_SEQ_ACTIVE (0x41cd) — and each is armed by a different trigger. `armSoundSequenceOnRequest` watches a request gate at 0x41d1 (loc_41d1); when it holds exactly 1 the routine consumes it (writes 0), raises descriptor 0x41d2 and its companion 0x41d6 (loc_41d6), and publishes a data pointer into the 16-bit cursor SOUND_SEQ_PTR (0x41d3), aiming it at the ROM sequence at 0x1e68. `armSoundSequenceBySelector`, gated on the sound-driver enable bit (bit0 of 0x4006, loc_4006), reads the shared request cell at 0x41df (loc_41df): a value of 6 arms this sequence — unless SOUND_SEQ_ACTIVE is already set — by raising descriptor 0x41cf, setting 0x41d6, and pointing the cursor at the ROM table at 0x1ebd; any other value is handed to `armSoundSequenceForSelector16`, which acts only on the selector 0x16, arming the third slot (it clears 0x41cf, raises SOUND_SEQ_ACTIVE and 0x41d6, and points the cursor at the table at 0x1edf) and ignoring every other value. `advanceAllSoundSequenceChannels` then steps all three descriptors in turn — 0x41d2, then 0x41cf, then SOUND_SEQ_ACTIVE — through `advanceSoundSequenceChannel` [code].

`advanceSoundSequenceChannel` is where a sequence actually plays. A descriptor holding 0 is silent and does nothing. Otherwise it marks the composite byte 0x41c0 = 2, publishes the current tone from 0x41d5 (loc_41d5) into SOUND_PITCH, and ticks the duration companion 0x41d6 down; while duration remains, that is all. When duration expires it reads the next command byte at the cursor SOUND_SEQ_PTR: the end marker 0xE0 deactivates the channel (descriptor cleared to 0); any other byte is split — its low five bits index the tone table at SOUND_TONE_TABLE (0x17a9) to become the new tone in 0x41d5, and its high three bits index the duration table at SOUND_DURATION_TABLE (0x17c8) to reload 0x41d6 — and the cursor advances past it. A current-state subtlety worth naming: although there are three descriptor slots pointing at three different ROM tables, all three channels read and write the *same* tone cell (0x41d5), duration cell (0x41d6), and cursor (SOUND_SEQ_PTR), so they time-share a single sequence-playback state — the descriptor that fires picks which stream feeds that one shared player, and the arms set 0x41d6 = 1 so the very first step expires immediately and pulls the opening command byte.

**The swept voice.** `updateSoundSweepVoice` runs only while the driver-enable bit (0x4006 bit0) is set. Its control cell 0x41c2 (loc_41c2) is not a countdown that decrements in place — it is compared against 1: while 0x41c2 is not 1 the routine hands its pointer to the sound-counter manager `advanceSoundSweepAndStagePitch` [code]; on the tick it equals 1 the routine reloads an idle template instead (0x41c2 = 0, the swept cell 0x41c3 = 2, and the sound counter 0x41c4 (loc_41c4) = 160, parking the counter well past its ceiling so the sweep goes quiet until it decays). `advanceSoundSweepAndStagePitch` returns immediately while the region-clear gate 0x4226 (loc_4226) bit0 is set; otherwise it steps its pointer forward one cell (to the swept cell 0x41c3). If the frame-phase bit of 0x425f (loc_425f) is set it jumps straight to the pitch-selector dispatch; failing that it bumps the swept cell 0x41c3 upward, but only while the sound counter 0x41c4 stays below its ceiling of 96, then falls into `tickSoundCounterAndStagePitch` [seen]. That tail decrements the sound counter 0x41c4 when nonzero, stores it back, and — either way — stages the pitch through `stageSoundPitchBySelector` [code], keyed on the low two bits of the swept cell. `stageSoundPitchBySelector` reads those two bits: a nonzero selector recomputes the pitch from the sound counter via `stagePitchFromSoundCounter` [code]; a zero selector stages a fixed pitch of 96 through `stageSoundPitch` [seen]. `stagePitchFromSoundCounter` reads the counter 0x41c4 and, on an odd selector, applies a warble — bias the counter by 96 and rotate the biased sum right one bit, the add's carry rotating back into the top bit — while an even selector passes the counter through unchanged; the result is staged. `stageSoundPitch` is the common leaf: it simply parks its value byte into SOUND_PITCH for the frame's final latch.

**The pulse-tone envelope.** `advancePulseToneEnvelope` drives a two-byte envelope word at 0x41c7/0x41c8 (loc_41c7 low, loc_41c8 high). When bit0 of the low byte 0x41c7 is set, it re-arms the word to a high-bit sentinel (low = 0, high = 128) and stops; otherwise it hands the high byte to `pulseSoundToneFromCountdown` [code]. That routine idles when the high byte is zero; otherwise it stores the byte decremented back into 0x41c8 and stages a two-level pulse shape through `stagePitchAndRaiseSoundFlag` [code] — 129 when bit2 of the decremented byte is set, 0 otherwise, so the tone gates on and off as the countdown walks that bit. `stagePitchAndRaiseSoundFlag` stores (value - 1) mod 256 into SOUND_PITCH and raises the composite flag 0x41c0 to 1, marking the shadow pair filled for this frame. The envelope's trigger byte 0x41c7 is raised elsewhere by the bonus-marker award, making this the extra-life/bonus jingle.

**The rising pitch ramp.** `driveRisingPitchRamp` gates on an arm counter at 0x41c9 (loc_41c9), again by a predecrement-and-test that is not stored back while nonzero: while (0x41c9 - 1) is nonzero it advances the ramp one step via `advanceSoundPitchRamp` [seen]; at the reset point it clears 0x41c9 and reloads the {countdown, pitch} pair at 0x41ca (loc_41ca) — countdown 32, pitch 0. `advanceSoundPitchRamp` reads the countdown one byte past its pointer (0x41ca) and idles if drained; otherwise it consumes one count, adds a fixed step of 4 to the pitch byte at 0x41cb, stores it back, publishes it to SOUND_PITCH, and clears the composite flag 0x41c0 to 0. The arm byte 0x41c9 is raised to 1 by the credit/coin paths and by the audio+input service tick when an arm input is seen, so the rising ramp is the coin-insert / credit beep.

**The gated square tone.** `advanceGatedSquareTone` runs a phase counter at 0x41cc (loc_41cc), tested against 1 the same not-stored-back way: while (0x41cc - 1) is nonzero it drives the tone through `driveGatedSquareTone` [code]; at the expiry step it parks 0x41cc = 0 and re-arms the tone duration SOUND_TONE_DURATION (0x41ce) to 8. `driveGatedSquareTone` looks at that duration: while nonzero it counts one tick off it and drives a level equal to the frame-parity flag 0x4007 (loc_4007) with bit0 flipped — a bit that alternates every frame, so the output toggles into a square wave — writing that level to SOUND_W_REG5; once the duration is spent it writes 0 to that register, silencing the tone.

**The decaying sweep, the occupancy hum, and the LFO** are pumped outside `driveSoundFrame`. `driveDecayingSoundSweep` [code] runs on even frames only (0x4007 bit0 clear) and reads the same shared request cell 0x41df as a countdown: while it is nonzero it emits the countdown rotated right two bits to SOUND_W_REG4 and ticks it down one, so the emitted value shrinks toward silence over successive even frames. That cell 0x41df thus wears two hats in the current code — a sound-request selector read by `armSoundSequenceBySelector`, and a decay countdown consumed here — and it is written by the input-scan handlers (6 and 0x16), by the dying-object animation (7 or 0x17), and cleared on the credit-advance path. `driveSoundVoicesFromOccupancy` [code], likewise on even frames, sums the 6x10 OCCUPANCY_GRID (0x4123, row stride 16) into a tally seeded at 1, lights that many of the three latches SOUND_W_REG0..2 (capped at three), zeroes the rest, and raises the near-empty flag 0x4224 (loc_4224) when the tally has nearly run dry — a background hum whose density tracks how many aliens remain in formation. `driveSoundLfoLevel` [code], called each frame from the main dispatcher, checks the LFO reset-request flag SOUND_LFO_RESET_REQUEST (0x41d0): with no request pending it runs `decaySoundLfoLevel` [code], which — only on the once-in-256 tick where the frame counter 0x425f reads 0xFF, and only while the level shadow SOUND_LFO_LEVEL (0x421f) is nonzero — drops the level by one and fans it out; with a request pending it consumes the flag and slams the full level (15) out instead. Both routes fan the level through `broadcastSoundLfoLevel` [seen], which saves the level to SOUND_LFO_LEVEL and writes it across the four SOUND_LFO_FREQ latches (0x6004-0x6007), rotating the byte right one bit between writes so each latch receives a shifted copy.

**The death-step sequence.** `driveGatedSoundStepSequence` [code] runs from the gameplay pipeline, gated on bit0 of the enable flag 0x4201 (loc_4201). It is armed by the player-hit handler, which sets the prescaler 0x4205 (loc_4205) = 10 and the step 0x4206 (loc_4206) = 4. Each eligible frame the prescaler decrements; only on its tenth fire does the routine emit a command word — opcode 2 carrying the current step — to the game's command queue, then step 0x4206 down. When the step count drains, the sequence ends: it clears the enable 0x4201 and silences SOUND_W_REG3. (The command-word enqueue returns through a shared, do-nothing stack epilogue at 0x090b, which touches no sound state.)

**Requesting sounds and silencing them.** `armObjectAnimAndRequestSound` [code] is the entry phase of a deactivated object's death animation: it seeds that object's animation timers, advances its sub-state so the entry runs once, and posts a sound request into the shared cell 0x41df — the low selector 0x07 when the object's position byte is below 112, the high selector 0x17 at or above it. Finally, `silenceSoundAndDisableIrqStars` [code] is the hard-quiesce: it sets the four SOUND_LFO_FREQ latches to 1, clears all eight sound registers SOUND_W_REG0..7, drives the pitch latch SOUND_PITCH_W fully high (0xFF), and — going beyond audio — clears IRQ_ENABLE (0x7001) and STARS_ENABLE (0x7004), halting the vblank interrupt and the starfield along with the sound. It is invoked on the reset-to-state-1 path and on the attract/reset input-column init, whenever the machine needs the audio and frame interrupt brought to a stop.

## Coins, credits, the HUD, score display, and the message scroller

### Taking coins and banking credits

The coin front-end runs once per frame from `serviceCoinInputs` [seen]. It first reads the coinage/config mode byte at 0x4000: in mode 3 (free play) it hands off to `presetCreditCount` [code], which stamps the credit counter at 0x4002 to 9 and clears the coin-phase flag at 0x4001, so the machine behaves as though nine credits are permanently banked. In any other mode it folds the two input shadows together (IN0_SHADOW at 0x4010 OR'd with the guard cell 0x4013), complements the result, and masks it through the two DIP/guard cells 0x4015 and 0x4016. If bit 7 survives, that is a service credit and it calls `addCreditForCoin` [code]; otherwise the low two bits are coin-slot pulses, each of which bumps the coarse coin accumulator at 0x4004 (once for one slot, twice if both fired that frame).

`addCreditForCoin` is the direct-credit arm: while the credit counter 0x4002 is below its cap of 99 it increments it, raises the credit-ready flag at 0x41c9 (which arms the coin-insert pitch jingle elsewhere), and posts a channel-7 redraw so the on-screen credit line catches up; at the 99 cap it does nothing.

The coarse accumulator at 0x4004 is drained separately and at a metered rate by `tickCoinMeterAndAwardCredits` [seen]. While the pulse-width timer at 0x4003 is still counting it calls `pulseCoinCounter` [seen], which rotates the countdown value right three bits so bit 3 of the count lands on bit 0 of the hardware coin-meter output COIN_COUNTER_0_LATCH (0x6003), and ticks 0x4003 down — that timed pulse is what an electromechanical coin counter needs. Once 0x4003 reaches zero, if 0x4004 is already empty it does nothing; otherwise it decrements 0x4004, refills 0x4003 to 15, and awards credits according to the coinage mode at 0x4000: mode 3 awards nothing, mode 1 runs the two-coins-per-credit path `awardCreditEverySecondCoin` [code], mode 2 runs the credit step twice (one coin, two credits), and any other mode runs it once. `awardCreditEverySecondCoin` toggles the coin-phase flag 0x4001: the first coin of a pair raises it through `setCoinPhaseFlag` [code], and the second clears it and awards a credit through `incrementCreditCount` [code].

`incrementCreditCount` is the shared step toward the 99 ceiling: at 99 it stops, above 99 it pins the cell back with `clampCreditsToMax` [code], and below it it increments, raises the ready flag 0x41c9, and posts the channel-7 credit-line redraw. It is what every coinage path — the direct service credit and both metered modes — funnels through, so the counter is corroborated as the credit count by all of its callers.

While credits accumulate, `updateCoinLockoutFromCredits` [code] keeps the coin mechanism honest: at nine or more banked credits it releases the lockout coil through `clearCoinLockout` [code] (writing 0 to COIN_LOCKOUT at 0x6002), and below nine it engages it (writing 1). The machine physically refuses further coins once the bank is full. The two start-button lamps are driven from the same credit count by `driveStartButtonLamps` [code]: gated on bit 5 of the phase/status counter at 0x425f, a clear gate turns both lamps (START_LAMP_0 0x6000 and START_LAMP_1 0x6001) off, and otherwise zero credits leaves them, one credit lights lamp 0, and two or more lights both.

### From a credit to a running game

`advanceGameStateOnCredit` [code] is the transition out of attract: when a credit is banked (0x4002 is nonzero) it advances GAME_STATE (0x4005) and wipes the attract sub-state cluster — the frame flag 0x4007, SEQUENCE_STATE (0x400a), 0x41c2, the sound-sweep request 0x41df, and the scroller enable MESSAGE_SCROLL_ENABLE (0x40b0). A zero credit count leaves everything alone.

Several sequence-step handlers then carry the start along. `holdStartLampsThenAdvanceSequence` [code] ticks the countdown at 0x4019 and, while it stays nonzero, keeps the lamps in step with credits; on its zero-crossing it advances SEQUENCE_STATE and clears the 128-byte flag block at FLAG_BITS_BASE (0x4100). `blankVramRowsThenDriveStartLamps` [code] is sequence-state index 2: it fills two 28-cell blank-tile rows (tile 16) through the VRAM write cursor VRAM_WRITE_PTR (0x400b), skipping a four-cell gap so the rows land 32 apart, and ticks the dwell tier 0x4009; on the last row it advances SEQUENCE_STATE, clears the screen-flip latches FLIP_SCREEN_X/FLIP_SCREEN_Y (0x7006/0x7007) and the direction flag 0x4018, posts a channel-7 and a channel-6 command, and drives the lamps once more.

`startGameRoundAndClearScores` [code] is the round-start proper. It stores a 16-bit spawn word across CURRENT_PLAYER (0x400d) and the paired-player flag loc_400e — so the word encodes both the active player and whether player 2 is live — blits the 32-byte ROM row template at loc_051b into PACKED_FLAG_BITMAP (0x4180), arms the substate-advance gate when config bit loc_401f bit0 is set, and enters play with GAME_STATE=3, SEQUENCE_STATE=0, the mode gate loc_4006=1, and 0x41d1=1. It then posts a channel-6 start message and two channel-4 commands that clear the two players' score fields, which is where the round wipes the scores.

Two smaller sequence handlers keep the attract HUD ticking. `emitMessageColumnsThenAdvanceSequence` [seen] resets the strided table, then runs a two-tier dwell (low tier 0x4008, mid tier 0x4009): each low-tier expiry reloads 0x4008 to 80 and posts a channel-6 message-column command whose index tracks the descending mid count (mid + 6), painting the attract text one column at a time; the mid-tier expiry advances SEQUENCE_STATE, reloads the tiers to 32 and 4, clears the sprite-source block SPRITE_SOURCE_OBJ_BASE (0x42b0), and clears DRAWN_COLUMN_COUNT (0x4241). `postCreditAndMessageDrawsAndAdvance` [code] posts a channel-7 credit redraw and a channel-6 message, advances SEQUENCE_STATE, and re-arms the dwell cascade (0x4008=96, 0x4009=16).

### The draw-command queue

Many of the routines above never touch VRAM directly. Instead they post a (channel, parameter) word into the frame's draw-command queue in work RAM (write head at loc_40a0), and a dispatcher later drains that queue, indexing a small ROM handler table by the channel to reach the actual painter. The channels this subsystem uses are 3 for adding to the BCD score, 4 for clear-and-repaint of a score field, 5 for a plain score-field repaint, 6 for the message painter, and 7 for the coin/credit-and-status readout line. The enqueue path returns through a shared, deliberately-unnamed stack epilogue (loc_090b) that has no work-RAM effect. This queue is why a coin insert, an enemy kill, or a round start can all "request" a HUD update from anywhere and have it serviced uniformly.

### Score storage and BCD display

`byteToPackedBcd` [code] converts a binary byte to packed BCD — the value modulo 100, tens in the high nibble and units in the low. The digits are painted by `drawBcdDigit` [code], which maps a BCD nibble to a font tile (digit + 0x90, so the glyphs '0'..'9' are the contiguous tiles 0x90..0x99), writes it at the cursor, and advances the cursor by the stride. It carries a leading-zero blank budget: while that budget is positive a leading zero is drawn as the blank tile (the base 0x80 plus 0x90 wraps mod 256 to tile 0x10) and the budget drops, and the first significant digit ends suppression. `drawBcdNumberColumn` [code] walks three packed-BCD bytes downward from the source pointer and paints six digit tiles up a column (high nibble then low per byte, stepping one tile row up, -32, per digit) with a four-digit blank budget — scores are held most-significant byte last, so callers point the source at the field's top byte and it walks down.

`selectCurrentPlayerScore` [code] returns the active player's three-byte score field, PLAYER1_SCORE_BCD (0x40a2) when CURRENT_PLAYER (0x400d) is 0 and PLAYER2_SCORE_BCD (0x40a5) otherwise. `drawScoreToSelectedPlayerField` [code] chooses the VRAM digit-field cursor by a selector — the primary field DIGIT_FIELD_PRIMARY (0x5381) when zero, the alternate field DIGIT_FIELD_ALT (0x5121) otherwise — then paints the BCD column there; player 1's score shows in the primary field and player 2's in the alternate. `drawHighScoreDigits` [code] paints a six-digit number into the fixed high-score field at loc_5241.

`drawScoreFieldByIndex` [code] is the indexed repaint: index 0 repaints player 1's score (primary field), 1 repaints player 2's (only when the paired-player flag loc_400e is set, whose value also selects the alt field), and 2 repaints the high score from HIGH_SCORE_BCD (0x40a8); an index of 3 or more descends, repainting every field from index-1 down to 0. `clearAndRedrawScoreField` [seen] uses the same index scheme but first zeroes the field — the three digit bytes plus a per-player scratch companion (loc_40ad for player 1, loc_40ae for player 2; the high-score arm re-zeroes its own first byte) — before repainting through `drawScoreFieldByIndex`. The two channel-4 commands posted at round start drive exactly this.

### Scoring a kill, awarding a bonus ship, and the high score

`awardKillScoreByBandAndDeactivate` [code] fires when an object is shot: it deactivates the record (byte 0 = 0, byte 1 = 1, byte 2 = 0) and sizes the award by which of three bands the object's type/position field (record+7) falls into against the threshold 0x50 — each band it clears bumps the score-command parameter and drops the field by 16, and a matched band posts its channel-3 score-add command immediately with that parameter. If all three bands are exhausted it raises the inhibit word at loc_422b (to 0xf001), and when the active-neighbour count ACTIVE_NEIGHBOR_COUNT (0x422a) is exactly 2 it folds a neighbour bonus (recorded at loc_422d) into the parameter before posting the command.

The channel-3 command reaches the BCD score adder, which adds a three-byte increment (selected from a ROM table by the parameter) into the current player's score located through `selectCurrentPlayerScore`, repaints that score through `drawScoreToSelectedPlayerField`, awards a bonus marker when the running total crosses the stored threshold, and — when the new total beats the stored high — copies it into HIGH_SCORE_BCD (0x40a8) and repaints the high-score digits through `drawHighScoreDigits`. The extra-ship award itself is `awardBonusMarker` [code]: a one-shot per current player keyed through the flag table at loc_40ad indexed by CURRENT_PLAYER, it flags the player's slot on the first threshold trip, raises the sound-envelope trigger loc_41c7 (the extra-life jingle), increments the marker counter loc_421d, and repaints the reserve-ship row.

### The player-status column

Beside each score the machine keeps a three-cell status column. `selectPlayerStatusVram` [code] returns its base — PLAYER1_STATUS_VRAM (0x5340) for player 1 and PLAYER2_STATUS_VRAM (0x50e0) for player 2, at opposite ends of the screen — with no memory write. `paintPlayerStatusColumn` [code] paints the three cells from that base stepping by the caller's stride (top cell = code+1, middle tile 0x25, bottom tile 0x20); afterward, only when the caller's flag bit 4 is clear and the mode gate loc_4006 is zero, it clears the status flag loc_40ab.

`repaintPlayerStatusColumn` [code] drives it for the current player: with flag bit 4 clear it paints that player's column, and with bit 4 set it blanks the active column's three cells (tile 16, one row up per cell) and, only when the paired-player flag loc_400e is set, paints the other player's column too. `repaintPlayerStatusColumnIfSaved` [code] gates that whole repaint on the saved status byte loc_40ab being nonzero, and `repaintPlayerStatusColumnFromModeGate` [seen] latches the mode: when the mode gate loc_4006 is nonzero it saves that value into loc_40ab and repaints, and when the gate is zero it repaints only if loc_40ab was already set. Together these keep the status indicator alive across mode transitions without ever repainting a column that was never armed.

### The reserve-ship marker row

`drawMarkerRow` [code] paints the five-slot reserve-ship row at MARKER_ROW_VRAM (0x539e): it stamps `markers` marker tiles (tile 102) as blocks growing upward, then blanks the remaining slots, the loop ending when a signed slot counter goes negative. When OBJ_ACTIVE_FLAG (0x4200) is set — a ship is currently in play — the displayed count is dropped by one, and if that empties the count every slot is blanked instead. This row is reached both directly from `awardBonusMarker` and, through the channel-7 status dispatch, from the marker counter loc_421d.

### The message painter and scroller

`renderMessageColumn` [seen] is the message engine, indexed by A. The low bits pick a record from the message pointer table MESSAGE_PTR_TABLE (0x235c) — the record holds a VRAM destination word and the text — and the top two bits of A pick the mode. Bit 7 blanks the message: it overwrites each character's cell up the column (stride -32) with the blank tile (64) until the terminator character 63. Bit 6 is position setup, which draws nothing but arms the scroller: it records the destination and text pointers (MESSAGE_DEST_PTR 0x40b5, MESSAGE_TEXT_PTR 0x40b3), derives a per-column cursor cell at loc_4020 + column*2 and stores its address in MESSAGE_CURSOR_PTR (0x40b1), clears the whole 32-cell column to tile 16, seeds the cursor cell with a packed row byte, and raises MESSAGE_SCROLL_ENABLE (0x40b0). With neither top bit set it draws the whole string at once, each character mapped to its font tile (character - 48) up the column to the 63 terminator.

Once armed, `advanceMessageScroller` [seen] steps it one frame at a time while MESSAGE_SCROLL_ENABLE is set. The cursor cell it points at serves double duty as both the inter-glyph delay and the stop countdown: while the cell's low three bits are nonzero the scroller only ticks the counter, and when they reach zero it emits the next glyph — reading the source at MESSAGE_TEXT_PTR, mapping it to a tile into the cell at MESSAGE_DEST_PTR, then stepping the source forward one byte and the destination up one row (-32) — while the terminator character emits nothing. Either way it ticks the counter through `endMessageScrollOnExpiry` [seen], the shared tail that decrements the counter and, on the exact zero-crossing, clears MESSAGE_SCROLL_ENABLE to stop the scroller; `endMessageScrollOnExpiryFromDe` [seen] is just the entry that carries the counter pointer in DE and reaches the same tail. So a message climbs its column one glyph every few frames and halts itself when its cursor byte counts out.

`advanceObjectAndQueueMessageColumn` [seen] is how a moving attract object triggers a message: it bumps the object record's tick (record+4) and counts its dwell timer (record+16) down; while the timer runs it returns, and on expiry it posts a channel-6 message command carrying the object's payload selector (record+7 + 75) and advances the object's own state.

### The animated screen fill

During attract the background is painted as an animated tile strip. `advanceScreenFillStrip` [code] heads it each frame: it pets the watchdog (a read of SOUND_PITCH_W at 0x7800) and, if the strip gate 0x4008 is zero, has nothing to draw so it restarts the outer dwell through `restartScreenFillOnDwellExpiry`; otherwise it loads the VRAM write cursor VRAM_WRITE_PTR (0x400b) and draws the strip. `drawScreenFillStripFirstHalf` [code] stamps sixteen pairs of tiles (48, 50) forward from the cursor and falls into `drawScreenFillStripSecondHalf` [code], which stamps a further sixteen pairs of tiles (52, 54), saves the advanced cursor back to VRAM_WRITE_PTR, and ticks the strip dwell 0x4008; on that dwell's expiry it calls `restartScreenFillOnDwellExpiry` [seen], which ticks the high dwell tier 0x4009 and, when that reaches zero (or was already zero), re-seeds the whole fill through `resetScreenFillState` [seen]. That re-seed, unless IN0 bit 6 is asserted, rewinds the write cursor to VRAM_BASE (0x5000), re-arms the fill-length counter 0x4008 to a full page, clears the dispatch flag 0x401a, and resets GAME_STATE (0x4005) to 0 — so the fill animates down the page and loops.

### Attract text columns and the input scan

The three DIP-configured attract text columns and the per-frame sound/input service share one chain that runs in the attract game state. `driveSoundFrameAndScanInput` [code] leads it: it ticks the sound driver and the decaying sweep, pets the watchdog, reads IN0 (0x6000), and raises the pitch-ramp arm cell 0x41c9 if any of IN0 bits 7, 1, or 0 is set, then hands the raw IN0 down the chain. `requestSoundOnInput1AndContinueScan` [code] reads IN1 (0x6800) and, if either of its low two bits is set, seeds the sound-request selector 0x41df to 0x16; `requestSound6AndContinueInputScan` [code] seeds that same selector to 6 when either input byte has bit 2 or 3 set; and `armInputFlagAndDrawInputColumns` [code] raises the companion input flag 0x41cc when the folded input bytes share bit 4. The chain ends at `drawInputTextColumnsAndSeedScreenFill` [seen], which decodes three two-bit fields (IN1 bits 6-7, IN2 bits 0-1, and IN2 bit 2) into text-descriptor indices and paints each as a column, then — unless IN0 bit 6 is asserted — seeds the screen-fill state (mode flag loc_4006=0, loc_401a=2, the dwell pair 0x4008/0x4009 = 16/48, and the write cursor to VRAM_BASE), clears the four-byte lamp/coin latch block at START_LAMP_0, and silences the sound hardware.

Those columns are laid down by the text-column primitives. `drawTextColumnByIndex` [code] indexes the five-byte descriptor table TEXT_DESCRIPTOR_TABLE (0x1cf6) by A and hands that record to `drawTextColumnFromDescriptor` [code], which unpacks the descriptor's source word, destination word, and count byte and paints that many characters up a column (stride -32) through `drawTextColumn` [code] — the innermost loop that, for each of `count` characters, reads a source byte, maps it to a tile by subtracting the '0' code (48), stores it, and steps the source forward one byte and the destination by the negative up-a-column stride.

### A shared counter-refill helper

Finally, `reloadExpiredCounterAndTally` [seen] is a small shared primitive for re-arming an expired counter from a table: it copies the reload byte at the source pointer into the counter cell and returns the running refill tally bumped by one. It backs the enemy-launch pacing sub-counters rather than the coin meter, but it is the same "an expired counter reloads from its table and tallies the refill" shape that recurs across the machine's timers.

## Tile / VRAM drawing primitives and coordinate mapping

The tilemap lives at `VRAM_BASE` (0x5000) and spans a 32-cell-wide grid up through 0x53ff; every routine here ultimately writes tile codes into that grid (or, for the moving-object path at the end, into the sprite shadow). The whole family is built bottom-up from two one-cell primitives, a coordinate mapper, and a handful of composite block/column/row writers that the attract sequence and the display-list processor drive.

### Coordinate mapping

`mapPackedCoordToVram` [code] is the address arithmetic everything screen-positioned goes through. It takes one packed byte and shuffles its two nibbles into a cell address. The low nibble is rotated right two: the bottom two bits of that become the page/high byte (0..3, so the cell lands somewhere in 0x5000..0x53ff) and the top two bits become the seed for the low byte. The high nibble is treated as a three-bit field whose low bit falls out as the carry and whose upper two bits become the returned `A`; a complemented running sum of that field is folded into the low nibble and added to the low-byte seed. The routine hands back three live values the callers lean on: `HL` = the finished cell address, `A` = the coordinate's bits 6..5, and carry = the coordinate's bit 4. Callers branch on that carry to choose between a wide (block) figure and a tall (double-height) figure at the same spot.

### The two one-cell stamp primitives

`stampTilePair` [code] is the innermost writer: it stores `tile` at `(HL)` and `tile+1` at `(HL+1)`, then advances the pointer past the second cell by a caller-supplied stride and steps the tile code by two, handing the advanced code and pointer back so a caller can chain the next pair. Because the store is a byte, a `0xff` seed wraps the second cell to `0x00`. `drawDoubleHeightTile` [code] is its vertical sibling: it writes `tile` at `(HL)` and `tile+2` in the cell one tilemap row below (`+0x20`), forming the top/bottom halves of a tall glyph. These two are the only routines in the group that actually touch individual cells; everything larger is composed from them.

### 2x2 tile blocks

`drawTileBlock2x2` [code] lays a square block by calling the pair stamper twice with a stride of 31, so each pair's built-in `+1` plus the stride nets `+32` — one row down. The result is the top pair `(A, A+1)` and the bottom pair `(A+2, A+3)` directly beneath it, four consecutive tile codes, with `DE` left as the caller had it. `drawBottomTilePairRestoreDe` [code] is the shared tail several block writers fall into: it stamps the second (bottom) pair and then restores the `DE` the caller had saved before the block began. `drawTileBlock2x2Up` [code] is the upward-growing counterpart: it stamps the pairs with a −33 step (so the pointer moves one row *up* between pairs) and seeds the upper pair four codes below where the first stamp left off, so the block extends above the anchor instead of below it.

Two adapters re-target the block writer. `drawTileBlock2x2AtDe` [code] exchanges `DE` and `HL` so a destination that arrived in `DE` becomes the draw target (the old `HL` is handed back in `DE`), then draws the 2x2 block there. Four fixed-seed entry points bake in the decorative-glyph codes so callers needn't supply one: `drawFixedTileBlock2x2` [code] draws a 2x2 block seeded from tile 44 (0x2c), laying codes 0x2c..0x2f; `drawFixedTileBlock2x2Up` [code] draws the upward block from seed 46 and is used to blank the unused slots of the marker row; `drawFixedTilePairHorizontal` [code] feeds the fixed code 44 straight into the pair stamper (returning the advanced code/pointer so a caller's loop can continue); and `drawFixedTilePairVertical` [code] feeds 44 into the double-height writer to paint a tall fixed pair.

### 4x4 tile forms

`blankTileBlock4x4` [code] wipes a 4x4 region anchored at `loc_51da` (a fixed VRAM cell), writing the blank-tile code 0x40 to four rows of four cells, each row start 32 cells past the last. `blank4x4AndDraw2x2Icon` [code] blanks that same region and then overlays a 2x2 block seeded with tile 96 at `loc_51fc`, an icon inset into the cleared square. `draw4x4TileForm` [code] is the display-list handler that selects among three forms by its argument: form 0 is the blank-then-icon, form 1 is just the blank, and any other value folds `(form − 2)` into a complemented tile code laid over the fixed base 0xc0 and then stamps four 2x2 blocks — one at each corner of a contiguous 4x4 region at `loc_51da`, `loc_51dc`, `loc_521a`, `loc_521c` — with the seed code advancing four per block. This is how a numeric indicator (rendered as a 4x4 grid of block glyphs) is painted.

### Table-indexed and dispatched figures

`drawIndexedTileBlock` [code] looks a 2x2 block code up in `TILE_BLOCK_TABLE` (0x215b) by index and stamps that block at the pending destination through the DE adapter. `drawSelectedTileBlockOrFallback` [code] wraps it with a signed test on the selector: a non-negative selector goes through the table lookup, while a negative one stamps a fixed fallback block (tile 0xa4). `drawTileGlyphOrBlock` [code] is the two-way figure dispatcher keyed on the carry it is handed: with carry set it swaps `DE`/`HL` and stamps a selected block (fallback 0xa4 when the selector is negative); with carry clear it fetches the selector's tile code from the table at `loc_2157` and paints it as a double-height glyph at the incoming `HL`. The swap in the carry-set path only stashes `HL` across the pointer-clobbering table fetch, so the glyph destination is the original `HL`.

### Timer-animated tile variants

Two register-only folds pick which animation frame of a glyph to draw, without touching memory. `computeTileVariantFromTimer` [code] reduces its input to a 2-bit variant index: when the value is below 112 it adds the value, an incoming carry, and the nibble-swapped per-frame counter `loc_425f`, keeping the low two bits; at or above 112 it saturates to the 0x80 out-of-range marker. `computeTileVariantFromValueAndTimer` [code] is the front door to that fold: values at/above 112 saturate to 128, otherwise it takes the value's low nibble, sets a carry when the frame counter's low nibble is the smaller, and folds through the timer variant. The net effect is a glyph whose displayed variant cycles with the frame counter, so figures drawn through this path animate.

### Packed-coordinate figure draws (the display list)

A display-list processor works through a queue of two-byte commands; a command's low nibble selects one of eight draw handlers from the ROM jump table at 0x203d, and the command's second byte is the handler's coordinate/argument. The first three entries of that table are tile drawers covered here. `drawAnimatedTileFigureAtPackedCoord` [code] is entry 0: it maps the packed coordinate to its cell, folds that same coordinate into a timer-animated variant, and then — reading the mapper's carry live-out (the coordinate's bit 4) — draws a 2x2 block when the bit is set or a double-height glyph otherwise. `drawFixedTileFigureAtPackedCoord` [code] is entry 1, the un-animated twin: map the coordinate, then bit-4 set draws the fixed 0x2c-family 2x2 block and bit-4 clear draws the fixed vertical pair. `draw4x4TileForm` (entry 2, described above) rounds out the tile-drawing handlers.

### Column primitives and the periodic column redraw

`drawTileColumnTriple` [code] copies three source bytes *up* a VRAM column: each byte lands at the destination whose low address byte then steps up one row (`−0x20`) within a fixed page, and after the three the low byte advances `+0x62` (98) to line up the next column; it returns the advanced source and destination so column draws can be chained. `blankTileColumns` [code] is the erase counterpart: starting at `loc_5193` it stamps the blank code 16 (0x10) into three cells of a column (`−0x20` per row, borrowing into the high byte) and advances `+98` to the next column, counting down `B` columns with a wrap so a zero count means 256. `redrawTileColumnsPeriodically` [code] drives both, gated by `DRAWN_COLUMN_COUNT` (0x4241) and the frame phase (`loc_425f & 0x3f`): fewer than two counted columns does nothing; on phase 0 it wipes the columns, and on phase 32 it repaints them — the first column from the source row picked by the frame counter's top two bits (`TILE_COLUMN_TABLE`, 0x039a) into `loc_5193`, and each remaining column threaded forward from the consecutive source stream (`TILE_COLUMN_TABLE_CONT`, 0x03a6). Because `DRAWN_COLUMN_COUNT` is bumped as the attract sequence advances, the number of columns that animate grows over the course of the attract screen.

### Full-row VRAM fills tied to the sequence machine

Several sequence-state handlers clear the screen a row at a time, using `VRAM_WRITE_PTR` (0x400b) as a running fill cursor and the `loc_4009` dwell tier as a phase counter. `primeVramFillAndAdvanceStep` [seen] sets one of these phases up: it clears the 128-byte flag block at `FLAG_BITS_BASE` (0x4100) plus status bytes `loc_425f` and `loc_4224`, points the write cursor two cells into the grid (`VRAM_BASE + 2`), arms the tier to 32, and bumps `SEQUENCE_STATE` (0x400a). `blankScreenRowsThenAdvanceSequence` [code] then, per frame, blanks 32 cells of tile 16 at the cursor and steps it a full row on; while phases remain it simply waits, and on the last one it advances the sequence and reseeds the object shadow. `fillVramRowThenResetObjectState` [seen] is a heavier variant: each frame it paints a 28-cell strip of tile 16 and steps the cursor `+32`, and on the tier's expiry it advances `SEQUENCE_STATE`, re-arms the two-tier dwell cascade (`loc_4008`=64, `loc_4009`=4), clears the 48-byte `OBJ_ACTIVE_FLAG` block (0x4200), clears both screen-flip latches `FLIP_SCREEN_X`/`FLIP_SCREEN_Y` (0x7006/0x7007) and the direction flag `loc_4018`, raises `loc_4238`, and reseeds the object-shadow field from ROM template `OBJ_SHADOW_RESEED_TEMPLATE` (0x1db1). `blankVramRowThenResetSpriteState` [code] mirrors that shape one state further along: it first clears the strided table, blanks a 28-cell row and steps the cursor, and on expiry advances the sequence, clears the object-source block (`SPRITE_SOURCE_OBJ_BASE`, 0x42b0, a full 256-byte wipe) and the sprite shadow (`SPRITE_SHADOW_BASE`, 0x4060, 64 bytes), re-arms the dwell cascade, reseeds the object shadow, and queues command word 6 into the display list. Note the two blank codes in play differ by purpose: the page/row clears fill with tile 16 (0x10), while the 4x4-block clear uses tile 0x40.

### Moving-object integrate-and-render, and shot-vs-player collision

The last group is the projectile/moving-object path. It is a *rendering* path like the rest, but it writes the sprite shadow rather than the tilemap. `advanceAndRenderProjectiles` [code] walks seven records based at `loc_4260`, each holding two five-byte sub-slots; the phase bit in `loc_425f` picks which sub-slot leads this frame (the trailing one merely has its sub-position bumped `+2`). For the leading sub-slot, when active, it advances the sub-position (deactivating on overflow), integrates the 16-bit position by twice the signed velocity byte, and deactivates the slot if the position leaves the vertical window; deactivation zeros the active/sub-position/high bytes. It then emits each sprite's on-screen Y and tile code into the sprite shadow at `loc_4081`, mirroring the Y by the direction flag `loc_4018` and nudging the code by ±1 on the first three records. The collision half reuses the same base viewed as fourteen five-byte entries: `flagProjectileHitsOnPlayer` [code], only when projectiles are enabled (`OBJ_ACTIVE_FLAG` bit 0), box-tests all fourteen entries at `loc_4260` through `flagProjectileHitOnPlayer` [code], which compares an active entry's X against the player-X reference `loc_4202` across a near/far Y band and, on overlap, deactivates the struck entry and raises `HIT_EVENT_FLAG` (0x4204). The band delta the per-entry test uses is always the record stride 5, left in a register by the loop rather than supplied by an outside caller.

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs. Most recently lifted are the three top-level SEQUENCE_STATE dispatchers — the attract/sequence handler
  and the two play-state handlers (fresh board and restore-saved board) — each of which absorbs its rst-28 table
  into a direct switch over the now-idiomatic sub-state handlers; they are correct-by-equivalence but still carry
  `loc_<addr>` names and `[code]` certs pending their own understanding pass. What still runs as translated code is
  the NMI/main-loop spine that dispatches into them (the vblank vector, the top-level GAME_STATE selector, and the
  shared rst-28 primitive), which is the born-live spine handled separately.
