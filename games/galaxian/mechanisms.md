# Galaxian — mechanism map

A code-grounded model of how Galaxian plays, derived from the idiomatic + frozen-oracle routine bodies and
confirmed against the real ROM under MAME. This is a **living** document: it is regenerated whole as the
idiomatic decompile spiral climbs, and currently covers the **leaf helpers** lifted in decompile batches 1–9.
The higher-level per-frame orchestration that drives them — the main loop and the state dispatchers — is
translated but not yet idiomatically decompiled, so it is described here only as far as the leaves reveal it.

**Confidence tags** — never recalled, always grounded or derived: `[seen]` a MAME observation terminates the
chain (a write-tap value trajectory, a confirmed dispatch/consumer); `[code]` a confident reading from the
routine's behaviour with MAME not yet consulted for that specific claim (a register/VRAM/hardware-latch
output the work-RAM tap cannot see, or a state the captures did not reach); `[guess]` plausible, unverified.
The tag on each routine here is the one recorded in `idiomatic/names.js`, which is the single source for every
name/role/tag; this prose cites those names, never contradicts them. Cells named `loc_<addr>` are roles read
from the code but not yet promoted to a descriptive identifier — their role is described in prose regardless.

## System primitives: RNG, memory fill, table fetch, and the vblank interrupt

These are the small, heavily-reused helpers the rest of the machine leans on: a pseudo-random source, two RAM/table access primitives sitting on the processor's low restart vectors, an unsigned divide, the interrupt epilogue that keeps the frame clock running, and one trivial stack cleanup.

Randomness comes from a single stateful byte. advanceRandomSeed [seen] reads the seed held in RNG_SEED (0x401e), advances it one step of a linear-congruential generator — the new value is `seed*5 + 1` taken modulo 256 — writes it back, and hands the fresh byte to the caller as this draw's random value. RNG_SEED is therefore not a static base but a running counter that mutates on every draw; whatever sequence a given frame sees depends on how many times the routine has been called since power-on. Callers rarely want the whole byte. chooseNextAttackerDirection keeps only its low bit to pick a launch side, reseedFormationObjectState folds an entire fresh byte into an object's Y coordinate, and computeJitteredXVelocity masks it down to the range 0..31 to add bounded jitter onto a computed velocity. Because there is exactly one seed cell, all of these consumers share and perturb the same stream.

The arithmetic the aiming code needs is provided by divideUnsigned8 [code], an 8-bit unsigned divide of A by D. It runs eight rounds of compare-subtract-shift: each round, if the running remainder still holds the current divisor it subtracts the divisor and records a 1 quotient bit, otherwise it records 0, shifting that bit into the quotient. The counterintuitive part is that it is the divisor, not the dividend, that is walked down one bit per round; after the eighth round the quotient sits in C — the value callers read as the result — the remainder in A, and the fully-shifted divisor in D, with the round counter spent to zero. It touches no memory at all. Its two consumers both turn a slope into a heading: computeDirectionOctantFromSlope reduces a rise-over-run ratio to a 0–7 direction octant, and computeJitteredXVelocity scales a slope before adding the RNG jitter described above.

Two primitives ride the low restart vectors and do the machine's bulk memory work. fillMemoryBlock [code] is a store loop: given a destination pointer, a fill value, and a count, it writes the value into that many consecutive bytes, advancing the pointer as it goes, and returns with the pointer left just past the fill and the count spent to zero. A count of zero is not a no-op — it wraps around to a full 256-byte page fill, which resetObjectRamAndAdvanceSequence relies on to wipe an entire page of the object table (the block based at loc_4260) in a single call. This routine is the workhorse of every screen-clear and state-reset path: it zeroes the sprite shadow and the object records, clears flag blocks, and — because each byte is written straight through to its destination — paints blank tiles across VRAM rows and strips as well, so a hardware-latch address is a legitimate target.

fetchIndexedTableByte [code] is the read counterpart. It adds the 8-bit index in A to the 16-bit pointer in HL, propagating the carry into the high byte so the index may cross a 256-byte page boundary, then loads the byte found at the resulting address; it returns both that fetched byte and the advanced pointer. This is the standard table lookup used throughout the tile-drawing code — drawIndexedTileBlock pulls a 2×2 block code out of TILE_BLOCK_TABLE (0x215b) by index, and drawTileGlyphOrBlock indexes the glyph table based at loc_2157 — and it is also how fillScreenThenLatchConfigAndAdvanceState turns the low bits of the configuration port into a stored setting, indexing a small ROM table at loc_0152.

The frame clock itself is kept alive by rearmVblankInterruptAndRestoreRegs [code], the tail end of the per-frame vblank interrupt handler. On entry the handler had cleared IRQ_ENABLE (0x7001) to acknowledge the interrupt it is servicing and had saved six register pairs; this epilogue writes IRQ_ENABLE back to 1 so the next vblank will fire again, then restores those six pairs — IY, IX, HL, DE, BC, and finally AF — and returns through the address the interrupt had suspended. Restoring AF last is deliberate: it overwrites the accumulator that was just used to write the enable latch, so the interrupted code resumes with its own A and flags intact. Both entry paths into the frame handler — the state-dispatch handler at loc_0066 and the alternate handler at loc_1bcd — converge on this one epilogue. Without the re-arm the machine would take exactly one interrupt and then freeze; the deliberate opposite move, made by silenceSoundAndDisableIrqStars, clears IRQ_ENABLE to halt the interrupt (and the starfield) on purpose.

Finally, loc_090b [code] is a deliberately-unnamed one-line epilogue: it pops the caller's saved HL back off the stack and returns, touching no work RAM. It is the shared exit of the command-queue enqueue path — reached both when enqueueCommandWord finds its target slot occupied and after commitQueueWriteHead has persisted the advanced write head — where it simply restores the HL that path had saved on entry.

## The attract / sequence state machine, dwell timers, credit transition, boot config, and playfield init

The machine's top level is a state loop driven once per frame off the game-state byte `GAME_STATE` (0x4005): boot fills and configures, attract cycles a demo sequence, a press-start screen waits for a coin-holder to launch, and two play modes (one for single-player, one for the second player / two-player continuation) run the round. Each of those top-level states in turn walks its own inner sub-state machine off `SEQUENCE_STATE` (0x400a), and the whole thing is paced by one shared two-tier dwell cascade and fed by one command/event queue. This section traces that spine.

### The dwell cascade — how a state ever advances

The pacing spine lives in three consecutive work-RAM bytes: the sub-timer `loc_4008` (0x4008), the dwell tier `loc_4009` (0x4009), and `SEQUENCE_STATE` (0x400a) itself. The shared primitive is `tickCascadeCountdown` [seen]: it decrements the byte it is handed and, only when that byte reaches zero, steps to the very next byte in the same page and increments *that* one — a carry out of the low tier into the next tier up. Both of its callers hand it the dwell tier at 0x4009, so a dwell-tier expiry carries directly into 0x400a. That carry is literally how the sequence steps forward: run the dwell down, and the state number ticks up by one.

Two handlers run that primitive at different speeds. `tickSequenceDwellTimer` [code] points straight at the 0x4009 tier and ticks it once per frame, so a state built on it lingers for 0x4009 frames before advancing. `tickPrescaledSequenceTimer` [seen] is the slow variant: it decrements the sub-timer 0x4008 each frame and only when 0x4008 wraps does it reload it to 60 and then tick the 0x4009 tier — a roughly 60x longer dwell, used for the drawn-out attract steps.

Re-arming the timer is factored out. `reloadSequenceDwellTimer` [code] simply stamps 0x4009 back to 80. `advanceSubstateAndReloadDwell` [code] bumps the sub-state counter it is handed (its callers hand it `SEQUENCE_STATE`) and then reloads 0x4009 to 80, i.e. "move on and wait 80 frames." `setSequenceStateByModeAndReloadDwell` [code] instead forces the counter to either 4 or 14 depending on the mode bit `loc_4006` (0x4006) and then reloads 0x4009 to 80 — a conditional jump to one of two fixed sub-states. And `enterSequenceStep1` [code] is the hard reset into step 1: it sets `SEQUENCE_STATE` = 1 and seeds the cascade small, 0x4008 = 3 and 0x4009 = 3.

### Attract sub-steps

The attract sequence's opening sub-step is `initSequenceEnableStarfield` [seen]: it enqueues two setup command words, raises `loc_4007` (0x4007), turns the starfield on (`STARS_ENABLE`, 0x7004), advances `SEQUENCE_STATE`, and zeroes the per-sequence scratch — `CURRENT_PLAYER` (0x400d), the paired-player flag `loc_400e` (0x400e), the mode byte 0x4006, and the one-frame countdown `loc_4019` (0x4019) — before seeding the cascade to 0x4008 = 96 / 0x4009 = 16. A later sub-step, `armStepCountdownAndTickSequenceTimer` [seen], arms that one-frame flag (0x4019 = 1) and then runs `tickPrescaledSequenceTimer`; the 0x4019 flag is consumed downstream to advance the sequence and clear the flag block on its own expiry.

### Boot and configuration latch

Game-state 0 is `fillScreenThenLatchConfigAndAdvanceState` [seen]. Each frame it blanks a 32-cell tilemap strip at the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) and advances that cursor across the tile grid, while a per-state sub-timer at 0x4008 counts down. When the sub-timer elapses it has finished wiping the screen and it latches the cabinet's configuration in one shot: it resets the state cluster (0x4007 = 1, mode 0x4006 = 0, `GAME_STATE` = 1, `SEQUENCE_STATE` = 0); folds the coinage mode into `loc_4000` (0x4000, from `IN1_SHADOW` bits 6–7), a config bit into `loc_401f` (0x401f, from `IN2_SHADOW` bit 2), and the screen-flip flag into `loc_400f` (0x400f, from `IN0_SHADOW` bit 5); selects a coinage-table byte into `loc_40ac` (0x40ac) indexed by the low two bits of the `IN2_PORT` from the ROM table at `loc_0152`; unpacks the packed flag bitmask from ROM `loc_051b` into the flag block; seeds the object shadow; paints the player-1 status glyphs (`PLAYER1_STATUS_VRAM` 0x5340 plus 0x5320 and 0x5300); and enqueues two deferred command words (`loc_0604`, `loc_0503`). Setting `GAME_STATE` to 1 hands the machine into attract.

### The command / event queue

Almost every state above talks to the rest of the machine through one queue. `enqueueCommandWord` [seen] appends a 16-bit word — a channel in the high byte and a parameter in the low byte. The write-head index sits in `loc_40a0` (0x40a0); the target slot is at base `loc_4000` + head, and because the head is floored at 0xc0 the queue physically occupies the high tail 0x40c0–0x40ff. A word is written only when the target slot's bit 7 marks it free; the hi and lo bytes are then stored and the head advances by two and re-floors. `commitQueueWriteHead` [seen] is the standalone tail that persists the advanced head back to `loc_40a0` and returns through the shared epilogue `loc_090b` [code] — a bare return epilogue that restores the caller's saved register and writes no work RAM (it is deliberately left unnamed). For sound cues there is a canned burst: `enqueueCommandWordBurst` [code] posts five words in a fixed shape — (D,2), (D+1,2), (D+1,4), (7,3), (7,0) — where D is the caller's channel.

### The credit transition

While attract is running, the sequence dispatcher finishes each frame on the credit check `advanceGameStateOnCredit`: if the credit count `loc_4002` (0x4002) is nonzero it bumps `GAME_STATE` and scrubs the attract residue — `loc_4007`, `SEQUENCE_STATE`, `loc_41c2`, the sound-sweep countdown `loc_41df`, and the scroller enable `MESSAGE_SCROLL_ENABLE` (0x40b0). So dropping a coin is what lifts the machine out of attract (state 1) and into the press-start screen (state 2); a zero credit count leaves everything alone.

### Press-start and launching a game

Game-state 2 is `runStartScreenAndLaunchGame` [code]. It runs the per-frame formation prep, selects one of four start-screen sub-handlers by the current `SEQUENCE_STATE` (0..3), and then always finishes by running the round launcher `beginGameOnStartButton` [code]. The launcher reads `IN1_SHADOW`: bit 0 begins a one-player game outright via `startOnePlayerGame` [code]; bit 1, if at least two credits are banked, spends two, blits the 32-byte ROM row template (`loc_051b`) into the saved-state snapshot `SAVED_STATE_SNAPSHOT` (0x41a0), arms the state-advance gate (`armStateAdvanceGate`) when config bit `loc_401f` bit 0 is set, and enters the round with a two-player spawn word (0x0100). `startOnePlayerGame` itself is credit-gated the other way: with no credits it slams `GAME_STATE` back to 1 (attract); otherwise it spends one credit (0x4002--), zeroes the snapshot at 0x41a0, and enters the round with a null spawn word (0).

Both funnel into the round setup `startGameRoundAndClearScores`, and one detail there ties several later branches together: it stores the spawn word as a *16-bit* value across `CURRENT_PLAYER` (0x400d) and its neighbour 0x400e, so the spawn word's high byte lands in `loc_400e` — and that cell is the paired/two-player flag (1 for the two-player start, 0 for one-player). It also blits the row template into the packed flag bitmap `PACKED_FLAG_BITMAP` (0x4180), arms the sub-state-advance gate (`armSubstateAdvanceGate`) when config 0x401f bit 0 is set, enters play (`SEQUENCE_STATE` = 0, `GAME_STATE` = 3, mode byte 0x4006 = 1, `loc_41d1` = 1), and queues three spawn command words.

Those two gate-arm routines are how a config option pre-decides the state-6 branch below. `armStateAdvanceGate` [code] stamps the "armed" marker 3 into `loc_41b5` (0x41b5), the gate `stepPlaySubstate6` reads. `armSubstateAdvanceGate` [seen] stamps 3 into `loc_4195` (0x4195), the gate `stepAltPlaySubstate6` reads. A two-player launch therefore arms both gates (0x41b5 from the launcher, 0x4195 from the round-start), whereas a one-player launch arms only 0x4195.

### Playfield init and the play sub-state walk

Both play modes (game-states 3 and 4) walk a sub-state machine on `SEQUENCE_STATE`, and both begin at sub-state 0 with `initPlayfieldState` [code]. It turns both start lamps off, zeroes the 128-byte flag block at `FLAG_BITS_BASE` (0x4100), clears the frame counter `loc_425f` (0x425f), clears the object-state block spanning 0x4200–0x422f (written as two runs that skip the single byte at 0x4217) and the object-record region 0x4260–0x42a5, sets `loc_4226` (0x4226) = 1, advances `SEQUENCE_STATE`, arms the dwell tier 0x4009 = 32, and re-homes the VRAM fill cursor 0x400b to the tilemap base `VRAM_BASE` (0x5000).

Sub-state 2 is where the two play modes diverge. In game-state 3, `restoreFormationAndEnterPlaySubstate` [seen] rebuilds the round from the live packed bitmap at 0x4180: it expands that bitmap into the flag block, copies the 8-byte template that trails it into `loc_4218` (0x4218), clears the frame/status/flip/direction cells (0x425f, `loc_4220`, `FLIP_SCREEN_X` 0x7006, `FLIP_SCREEN_Y` 0x7007, `loc_4018`), advances `SEQUENCE_STATE`, arms a long 150-frame dwell (0x4009), and publishes a deferred-callback pointer (`loc_0640`) into the pointer cell `loc_4245` (0x4245). Then, only when the sound gate 0x4006 bit 0 is open, it cues the board-start sound: the paired-player burst through `queueBoardStartSoundBurst` [code] when the two-player flag 0x400e is set, otherwise a plain channel-5 prologue word plus the standard burst. `queueBoardStartSoundBurst` enqueues a channel-5 param-3 prologue word and then the five-word burst on channel 5. In game-state 4, `restoreSavedStateAndEnterPlaySubstate` [code] is the mirror that rebuilds instead from the saved-state snapshot at 0x41a0, additionally mirroring the flip flag 0x400f into 0x4018 and both flip latches when it is set, arming the same 150-frame dwell, publishing pointer `loc_0830` into 0x4245, and (sound gate open) queueing five intro command words.

Sub-state 3, `advanceSubstateAfterDwellAndQueue` [code], is a plain timed step: it ticks the dwell tier 0x4009 and, on its zero-cross, reloads it to 20, advances `SEQUENCE_STATE`, and queues this state's command word (`loc_0682`).

Sub-state 6 is where the mode and gate cells decide whether the round proceeds or the machine tears down. `stepPlaySubstate6` [code] (game-state 3) branches on the arm gate `loc_421d` (0x421d), the state gate 0x41b5, and the two-player flag 0x400e: with 0x421d set it either advances the sub-state (`advanceSubstateAndReloadDwell`, when both 0x41b5 and 0x400e hold) or jumps by mode (`setSequenceStateByModeAndReloadDwell`); with 0x421d clear and either gate byte zero it falls into the shared reset tail; otherwise it advances `SEQUENCE_STATE`, arms a 130-frame dwell (0x4009), and — when the mode bit 0x4006 is set — queues two channel-6 command words. `stepAltPlaySubstate6` [code] (game-state 4) is the mirror keyed on the sub-state gate 0x4195 and 0x421d, arming an 80- or 130-frame dwell on its two advance arms.

Both state-6 handlers share the tail `advanceDwellOrResetToState1` [code], which is also the play→attract exit. When the mode bit 0x4006 is clear it just advances the sub-state and reloads the 80-frame dwell; when 0x4006 is set it resets the whole machine to attract — `GAME_STATE` = 1, mode byte 0x4006 = 0, `SEQUENCE_STATE` = 0 — silences the sound hardware, halts the frame interrupt and starfield, and queues command word 6.

### Per-frame pacing timers during play

While a round runs, the play update pipeline drives a cluster of gated timers that share two guard cells: the object-enable flag `OBJ_ACTIVE_FLAG` (0x4200) and the inhibit flag `loc_422b` (0x422b). `rampCounterToCeiling` [code] is the slow difficulty ramp: while objects are enabled and inhibit is clear, a two-tier prescaler steps the pace counter `loc_421a` (0x421a) up by one per double-wrap, clamped at 7. Notably its two prescaler cells, `loc_4218` (0x4218, reload 60) and `loc_4219` (0x4219, reload 20), are the leading two bytes of that 8-byte template copied in at board start — so the board template's own bytes seed how fast the ramp runs.

`scheduleDelayedEvent` [code] carries a three-gate guard (0x4200 and `loc_41ef` set, 0x422b clear). On its mode-clear arm an outer/inner cascade (0x4245 reload 60, `loc_4246` reload 5) arms a fixed delayed-event triple — `DELAYED_EVENT_TIMER` (0x422f) = 90, `loc_424a` (0x424a) = 45, `DELAYED_EVENT_ARMED` (0x422e) = 1. On its mode-set arm it instead derives the triple from work-RAM word sums (of `loc_4177` and of the pace word at 0x421a) and fans the value out by rotations. Here again a cell wears two hats: 0x4245, which the play sub-state entries publish a deferred-callback pointer into, is reused as this scheduler's outer prescaler countdown during the running frame. `fireDelayedEventRequest` [code] is the one-shot that consumes the arm: while 0x422e holds it counts 0x422f down and, on the zero tick, disarms itself and — only if 0x4200 and 0x41ef both hold — raises `DELAYED_EVENT_REQUEST` (0x4229). `expireActivityGatedTimer` [code] ends an activity-gated phase: while 0x422b is armed and at least one activity gate is open (`loc_4224` nonzero, `loc_4221` nonzero, or 0x4226 bit 0), it ticks the counter `loc_422c` (0x422c) and clears the arm flag 0x422b when the counter reaches zero.

Two more manage a behavior gate at `loc_4208` (0x4208). `clearGateOnPendingRequest` [code] acknowledges an outstanding request: when the request flag `loc_420b` (0x420b) bit 0 is pending it clears both 0x420b and the gate 0x4208. `armBehaviorGateOnInputOrTimer` [code] arms that gate — only while objects are enabled and the gate is not already armed. On the timer path (mode 0x4006 bit 0 clear) it arms roughly every 32 frames, when the low five bits of the frame counter 0x425f are all clear. On the input path (mode set) it tests bit 4 of the selected input shadow (`IN0_SHADOW` 0x4010 or `IN1_SHADOW` 0x4011, chosen by 0x4018 and masked by its guard `loc_4013`/`loc_4014`) and, when the line reads active, arms both the gate 0x4208 and the companion flag `loc_41cc` (0x41cc).

### A clamp helper in the same family

Finally, `markValueOutOfRange` [code] is the odd member of this group — a value clamp rather than a sequence step. It is the saturation arm of the animated-tile-variant computation (`computeTileVariantFromTimer`): when the input value is out of range it snaps register B to the fixed 0x80 sentinel, which the caller reads as "no valid tile variant."

## The object / formation field: records, motion planning, sweep, occupancy, spawn/launch

Galaxian keeps its swarm in two parallel structures that hand aliens back and forth. One is a **flag grid** at FLAG_BITS_BASE (0x4100): 128 one-byte cells, each byte's bit 0 saying whether the alien belonging to that grid cell is still standing. The other is a small pool of **object records** — the seven-slot OBJ_TABLE (0x42d0) at 32 bytes per record, plus the descriptor slots at DESCRIPTOR_SLOT_TABLE (0x4330) — that hold the aliens which have broken formation and are flying. An alien lives in the flag grid while it holds formation and migrates into an object record when it launches; a record's fields describe one flyer's position, heading, and its point in a small per-object state machine keyed on the record's state byte (record + 2).

### Seeding and packing the field

At the start of a screen the interleaved object-RAM shadow is laid down by seedObjectRamShadowField [seen], which copies 32 source bytes into every other cell of a work-RAM field beginning at loc_4021 (0x4021, 0x4023, … 0x405f) — a stride-2 layout that leaves the alternate cells for a companion field. seedObjectShadowFromRom [seen] is the fixed-source form: it aims that same copier at the ROM template STRIDED_TABLE_SRC (0x1d71). advanceSequenceStateAndReseedObjectShadow [code] wraps the reseed with a tiny state nudge — it advances a pointer's low byte within its page and increments the byte that then lands under it (its callers arrive pointing just below SEQUENCE_STATE (0x400a), so that increment steps the sequence state) before reseeding the shadow. clearFlagBlockAndReseedObjectShadow [code] is the fuller reset used between screens: it zeroes the whole 128-byte flag grid, clears the status cells loc_425f and loc_4238, arms the mid-tier dwell timer loc_4009 to 64, then runs that same advance-and-reseed.

The flag grid has a packed twin. unpackBitmaskToFlagBytes [seen] expands a 16-byte packed bitmask into the 128 flag bytes, LSB first — one byte per bit, 1 for a live alien, 0 for a gap — and hands back the source pointer advanced past the 16 mask bytes, so the caller can pick up whatever data follows the mask. packFlagBytesToBitmask [code] is its exact inverse: it reads bit 0 of the 128 flag bytes and squeezes them back into a 16-byte bitmap, returning the destination advanced by 16 so a block copy can chain. Together they let the game store a whole formation compactly. loadDescriptorAndAdvanceSequence [code] uses the unpack side to install a fresh formation: it expands the packed row template at loc_051b into the flag grid, copies the 8-byte template that immediately follows into the buffer loc_4218, clears loc_425f, sets loc_421d to 1, steps SEQUENCE_STATE, stamps 150 into VRAM_WRITE_PTR (0x400b) — here reused as a plain counter seed rather than a VRAM cursor — and publishes the deferred pointer loc_0640 into loc_4245.

Two mirror-image terminal handlers use the pack side to freeze the formation when play pauses to switch players. packFlagsToBitmapAndSwitchPlayerState [code] ticks the dwell timer loc_4009 and, only on the tick it reaches zero, clears SEQUENCE_STATE and the status cells loc_4222/loc_422b, packs the current flag grid into PACKED_FLAG_BITMAP (0x4180), copies the 8-byte template from loc_4218 in right after it, sets CURRENT_PLAYER (0x400d) to 1 and moves GAME_STATE (0x4005) to 4. saveFlagsToSnapshotAndSwitchPlayerState [code] is the twin for the other player: same dwell gate, but it snapshots into SAVED_STATE_SNAPSHOT (0x41a0), sets CURRENT_PLAYER to 0 and GAME_STATE to 3. These packed forms are what let a two-player game suspend one board and resume it later.

### Occupancy: what is left, and where its edges are

Once per formation-prep pass summarizeFormationOccupancy [seen] boils the live grid down to the summaries the rest of the subsystem reads. It ORs each row of the OCCUPANCY_GRID (0x4123, 16-byte row pitch) into a per-row summary at ROW_OCCUPANCY (0x41e8) — behind two always-empty guard cells — and each column into COLUMN_OCCUPANCY (0x41f0), behind three guards. From the column summaries it derives the horizontal travel limits: scanning inward from the right end it counts empty columns to build one bound, scanning inward from the left it builds the other, and it stores the pair into FORMATION_X_BOUNDS (0x4210) with the from-right value in the low byte and the from-left value in the high byte — so as the outer columns empty out, the formation's side-to-side travel widens. Finally it folds four region-clear flags: the top four rows into loc_4221 and all six rows into loc_4220, and two object-table columns (seven slots of OBJ_TABLE, then eight slots from loc_42b1) into loc_4226 and loc_4225. Each flag is the OR with bit 0 inverted, so a set bit 0 means "that region is clear." Those clear flags gate launching, stage advance, and the sway shortcut downstream, and their opposite senses tie the whole subsystem together: while a region still holds aliens its flag reads clear-bit-low, which is exactly the condition the launcher needs, and only once it empties does the flag flip and enable the stage advance.

### The side-to-side sway

The whole standing formation slides left and right under advanceFormationSweepOscillator [seen]. The swept quantity is the 16-bit word at loc_420e — despite reading like a static anchor it is a counter that oscillates, and every object's formation column is measured against it. Once every four frames (throttled by the low bits of the frame counter loc_425f) the oscillator nudges that word one unit toward whichever end of the FORMATION_X_BOUNDS pair the current phase points at. OBJ_SWEEP_DIRECTION (0x420d) holds the phase: while it is zero the word climbs until it reaches the upper bound, where setSweepDescending [seen] flips the flag to 1; while it is one the word falls until it reaches the lower bound, where setSweepAscending [seen] clears it back to 0. After each step the low byte of the swept word is negated and fanned across a small per-column offset table.

That fan-out is done by a family of tiny broadcasters. broadcastToStridedTable [seen] writes one byte into nine cells at stride 2 starting at loc_4028 (0x4028 … 0x4038) — the per-column shear the formation renderer adds. clearStridedTable [seen] is just its zero case, used to blank the shear between phases. broadcastNegatedSweepToStridedTable [seen] broadcasts the two's-complement of a byte instead, and broadcastNegatedFormationSweepToStridedTable [code] is the convenience entry that reads the low byte of the swept word loc_420e and negates-and-fans it. The oscillator carries a proximity shortcut at its head: if the player shot is armed (loc_4208), its position (loc_4209) sits in a narrow window, and the swept column reads occupied in COLUMN_OCCUPANCY, it skips the step entirely and just refreshes the fan via that formation-broadcast entry — holding the swarm dead still for the frame a shot is about to land on a column.

### Advancing the stage

When a board is cleared the formation is rebuilt one difficulty step harder. armFormationAdvanceTrigger [code] is the one-shot that notices the board is empty: only when both region-clear gates loc_4220 and loc_4225 have bit 0 set (all rows and all objects gone) and the pending word loc_4222 is not already armed does it write loc_4222 = 1 — an enable byte of 1 with a zeroed countdown. advanceStageAndReseedFormation [code] later consumes it: each frame it checks loc_4222's enable and ticks the countdown loc_4223, and on the tick the countdown hits zero it disarms the enable, rebuilds the 128 flag bytes from the packed template loc_051b, resets the pace counter loc_421a and loc_425f, reseeds the swept word loc_420e to 1, and steps the stage selector loc_421b. Here is a counterintuitive detail: that selector's low byte advances but saturates at 7 while its high byte keeps counting, so the stage number rises without end even though the index that picks formation data tops out. It closes by servicing a pending two-slot request in loc_421e, raising loc_4177 and, if a second remains, loc_4178.

### Pacing and launching a diver

paceEnemyLaunchTrigger [code] is the metronome behind attacks. Gated on the object subsystem being live (OBJ_ACTIVE_FLAG (0x4200) bit 0) and two inhibits clear (loc_4220 and loc_422b), it ticks a master counter loc_424a; while the master is still counting it holds the refill flag low. On the master's expiry it reloads from the head of SUBCOUNTER_RELOAD_TABLE (0x15e3) and sweeps a span of attacker sub-counters — the span widening with the pace counter loc_421a and the clamped stage loc_421b — decrementing each and, for any that reach zero, refilling it from its matching reload-table entry and tallying the refill. If anything refilled it raises SUBCOUNTER_REFILL_FLAG (0x4228), the go-signal for a launch.

launchAttackerFromFormation [code] consumes that signal. On the frame the refill flag is set (and it is cleared here), and while the region-clear gate loc_4220 is still clear (aliens remain), it derives a slot budget of one to four from the folded pace counter, then scans the object slots downward from loc_4391 for the first entirely-empty one. It stamps the shared launch direction loc_4215 into the new slot, uses that direction to pick which end of COLUMN_OCCUPANCY to scan for an occupied column, then climbs that column of the flag grid looking for a live cell — the geometry of the climb (four rows from one base, five from another) chosen by the sweep-mode flag loc_41ef. On a hit it clears the formation cell, activates the slot (active byte to 1, state to 0, the found cell's low byte stashed as the slot's grid cell), and posts a spawn command so the flyer appears. In effect one alien is plucked out of the standing grid and handed to an object record to fly.

### The delayed-event spawn cascade

A second spawn path fires on demand rather than on the metronome. spawnObjectsOnDelayedEvent [code] runs each frame in the play update, gated on the region-clear flag loc_4220 clear, OBJ_ACTIVE_FLAG set, and a pending DELAYED_EVENT_REQUEST (0x4229) which it consumes as a one-shot; it also holds off unless the head word of OBJ_TABLE is even. When it fires it routes on the low bit of the launch direction loc_4215: a set bit runs the full trigger-block spawn spawnObjectsFromTriggerFlags [code]; a clear bit scans the primary trigger block PRIMARY_TRIGGER_BLOCK (0x4176) high-to-low and, on the first set flag, runs spawnPrimaryAndSecondaryObjects [code], and failing that scans the secondary window below it and seeds a free descriptor slot via spawnIntoFreeDescriptorSlot [code].

Those spawners share a small set of primitives. activateObjectSlotAndEnqueueSpawn [code] is the common seeder: it consumes the trigger flag it was found under, marks the object record active with a cleared phase, records the spawn code and the trigger pointer's low byte as the object's source index, and posts a type-1 spawn command keyed by that index. spawnIntoFreeDescriptorSlot [code] scans the four descriptor slots at DESCRIPTOR_SLOT_TABLE high-to-low for one whose two guard bytes are both zero and, on a hit, hands it to that seeder. spawnObjectsFromTriggerFlags [code] scans the four primary flags: the first set one spawns a primary into OBJ_TABLE and then walks the secondary block SECONDARY_TRIGGER_BLOCK (0x4165) for up to two secondaries; if no primary flag is set it instead seeds a free descriptor slot from the first set secondary flag. spawnPrimaryAndSecondaryObjects [code] does the primary spawn, then walks three trigger flags backed up from the primary trigger's low byte, spawning a secondary for each set one until a budget of two is spent. The secondaries themselves are laid down by spawnSecondaryObjectIntoSlot [code], which bails if either of the target slot's two live flags is already set, else consumes the trigger, marks the slot alive with a cleared state, inherits field 6 from the source record, stashes the trigger index, and posts an activation command. spawnSecondaryObjectAndAdvanceWalk [code] is the per-step wrapper of that walk: it spawns into the current slot, steps the slot pointer forward one record, counts the budget down, and — when the budget empties — forces the enclosing loop counter to one so the walk ends after this pass.

activateDescriptorSlot [seen] is the standalone initializer for one of those descriptor slots, called on a timed phase of a sequence handler: it reads a descriptor number at a pointer, indexes the slot as (number − 1) × 32 into DESCRIPTOR_SLOT_TABLE, and stamps its fixed init fields — active byte 1, byte 2 = 13, byte 5 = 12, byte 7 = the slot index — leaving bytes 3 and 6 untouched.

### An object's first frame and its formation states

Each flyer runs a small state machine on its state byte (record + 2). positionObjectFromGridCell [code] is the shared geometry step several states use: it unpacks the record's packed grid cell (record + 7) into the sprite position fields the renderer reads — and here is the axis surprise, the display is rotated ninety degrees from the formation grid, so the cell's row bits drive the sprite X field (record + 3 = 124 minus three-quarters of the row) while the column bits drive the sprite Y field (record + 4 = the low byte of the swept word loc_420e, plus the column times sixteen, plus a seven-pixel hotspot).

initSpawnedObjectFromGridCell [code] is the freshly-launched flyer's first frame: it clears the step timer, raises the spawn flag loc_41c2, positions the sprite from the grid cell, posts a type-1 spawn command, and looks up the object's sprite number and flight-curve seed from SPAWN_RECORD_TABLE (0x1dd1) indexed by the cell's row — the top row additionally tallies its two neighbour slots' active flags into ACTIVE_NEIGHBOR_COUNT (0x422a). It then seeds the motion counters, advances the state, and picks the signed heading (±12) from the object's direction bit.

settleObjectIntoFormationCell [code] is the state that eases a flyer back into its formation slot: each frame it repositions from the grid cell and bumps a frame counter, and when the counter catches up to the positioned value it deactivates the object, marks that flag-grid cell live again, and posts a command word — folding the alien back into the standing formation. A small even gap nudges the object's phase up or down by its direction bit; a large or odd gap it leaves alone.

reseedFormationObjectState [code] re-initializes a formation object: it parks X at the left edge (8), zeroes the heading, and ticks the leg counter. It then advances the object's state — and, when the subsystem is enabled and an activity gate (loc_4224 or loc_4221) is open, it first rolls a fresh random Y, arms a 40-tick hold timer, and advances the state an extra step. The exception is when the packed cell's high bits are all set and no active neighbours remain (neighbours are recounted into ACTIVE_NEIGHBOR_COUNT first): then it instead deactivates the object and ramps the phase counter loc_421e toward its ceiling of 2 — the marker that a region has fully cleared.

### Staging sprites, scoring bonuses, and the loose ends

Every frame the flying objects are copied into the hardware sprite shadow by stageObjectsToSpriteShadow [seen]: it renders eight consecutive source records from SPRITE_SOURCE_OBJ_BASE (0x42b0, 32-byte stride) into eight sprite-shadow records at SPRITE_SHADOW_BASE (0x4060, 4-byte stride), as a band of three then a band of five, with the first band's vertical offset (9 versus 7) picked by the orientation bit loc_4018 and the tail band settling at 8 either way.

flagPlayerShotHitOnFormation [code] is where the player's shot meets the standing swarm. While the shot gate loc_4208 is armed it bands the shot's Y position loc_4209 into a formation row (a repeating seven-then-five step down from the top) and its X delta from the swept word (loc_420a − loc_420e) into a column, indexes the flag grid, and if that cell holds a live alien clears it. It then stamps a hit record — the retire flag loc_420b, loc_42b1 = 1, loc_42b2 = 0, and the shot's position word into loc_42b3 — and posts two command words (a kind-1 carrying the grid index and a kind-3 carrying a column code) that drive the alien's death, scoring, and sound.

bumpCountIfNeighborsInactive [code] serves the kill-scoring path: given a running count and an object record it returns the count plus one only when both look-ahead slots (32 and 64 bytes past the record) are inactive, else the count unchanged — the neighbour bonus folded in when an alien is destroyed with its flanking slots already empty.

Two entries are deliberate do-nothings. noopAnimDispatchSlot [code] is the terminal state of the dying-object animation machine: once the animation runs out, the record's state byte parks on this handler, which does nothing, so the slot sits inert until it is reused. And loc_090b is the shared stack epilogue of the command-enqueue path — it restores the caller's saved register pair and returns, with no effect on work RAM.

## Player ship, projectiles, dive scheduling, object-AI paths, and collisions

This subsystem is the beating heart of a Galaxian round: the player's ship, the single shot it fires, the swarm of attacker objects that peel off the formation and dive, the aimed bullets those attackers rain down, and the box-tests that decide who dies. Almost everything here is driven once per frame from a single fixed-order update pipeline (the play-state per-frame handler at `0x0661`), so it helps to keep that ordering in mind: the ship is moved and its shot serviced first, then the attacker objects are stepped through their AI, then all sprites are staged, and only then are the collisions resolved and the hit consumed. The whole apparatus is armed by one master switch — `OBJ_ACTIVE_FLAG` (0x4200) — whose bit 0 gates the ship's controls, every collision sweep, the attacker launcher, and the AI's firing decisions; clearing that one cell freezes the entire object world at once.

Two RAM cells recur so often they deserve naming up front. `loc_4202` is the ship's horizontal position: the joystick handler writes it, and — the counterintuitive part — every attacker reads that same cell as the target to home on, aim at, and shoot toward. It is simultaneously "where the player is" and "where the enemies point." And `loc_425f` is the free-running per-frame counter whose low bits drive most of the phase/parity throttling below.

### The object records and their driver

Attacker objects live as fixed-layout records. The per-frame object driver walks eight consecutive records at `SPRITE_SOURCE_OBJ_BASE` (0x42b0) on a 32-byte stride, while the collision and move-planning code addresses the seven-record `OBJ_TABLE` (0x42d0), which begins one record later. Within a record, byte 0 is the primary-active flag, byte 1 the "dying" flag, byte 2 the AI state index, bytes 3 and 4 the position pair, byte 5 the signed heading, byte 6 a direction bit, byte 7 a packed grid-cell/type/kind field, byte 9 a per-object increment (or column, or sub-pixel, depending on state), byte 0x10 a move throttle, byte 0x11 a leg counter, byte 0x13 a walk cursor, and bytes 0x18–0x1c a flight-curve seed and two 16-bit accumulators.

For each of the eight slots the driver decides among three fates: if the record's dying flag (byte 1) is set it runs the death animation regardless of state; otherwise, if the active flag (byte 0) is clear it does nothing; otherwise it selects one of sixteen handlers from a table indexed by the object's state byte (byte 2). That sixteen-entry table is the spine of the attacker AI, and most of the routines below are its slots: state 1 walks a path, state 2 plans a horizontal move, state 3 flies and fires, state 4 dives, state 7 homes, state 8 arms a directed move, state 9 flies-and-fires while homing, state 10 walks a mirrored path, state 11 aliases back to state 1, state 12 restarts a move run, state 13 sets up a phase, and state 15 settles at rest.

### The player ship

`moveControlledObjectAndStageSprite` [code] is the ship's per-frame handler and the first thing the pipeline runs. When the ship is alive (`OBJ_ACTIVE_FLAG` bit 0 set), it chooses which byte supplies the movement bits: in automatic/demo play (mode cell `loc_4006` bit 0 clear) it reads the AI's computed command `OBJ_MOVE_CMD` (0x423f); in live play it reads one of the two input-port shadows, `IN1_SHADOW` (0x4011) or `IN0_SHADOW` (0x4010), selected by the direction flag `loc_4018`. Bit 3 of the chosen byte steps the ship's position (`loc_4202`) down while it stays above the floor 23, and bit 2 steps it up while it stays below the ceiling 233 — the two clamps that keep the ship on-screen. It then writes the ship's staged coordinate as four interleaved (value, code) pairs into `OBJ_STAGE_BLOCK` (0x4054), the value being the position folded through the hardware's inverted-coordinate convention (one's-complement plus 128). When the ship is not alive, one of two things happens: if the death/hold flag `loc_4201` is set it stages the current position under an alternate code (holding the wreck in place for the death animation), otherwise it parks the position at zero.

The automatic command that stands in for the joystick during attract mode comes from `computeControlledObjectMoveCommand` [code], a small dodging autopilot. It fires only once per 32-frame phase (keyed on `loc_425f`) and only while both the demo enable `loc_4007` and `OBJ_ACTIVE_FLAG` have bit 0 set. It folds a positional "threat weight" over every attacker in `OBJ_TABLE` (0x42d0) and every enemy bullet in the projectile table `loc_4260`, adds a term scaled from the formation anchor `loc_420e` against the ship's `loc_4202`, applies a random ±1 nudge, and buckets the result into `OBJ_MOVE_CMD` = 0 (stay), 4 (bit 2, up) or 8 (bit 3, down) — exactly the bits the ship handler reads. The per-object weight itself is `accumulateObjectPositionWeight` [code]: it contributes nothing unless the object is active, its Y sits in one of two 52-row bands above 128, and its X delta from `loc_4202` is in the near half; when it qualifies, it folds the object's flag bit and X-position bits plus the band into a 0–15 index and adds the signed step read from `OBJ_STEP_TABLE` (0x1a45) to the running total. In effect the autopilot leans away from the densest, nearest cluster of diving attackers.

### The player's shot

The ship has exactly one shot in flight at a time, tracked in a little block of cells. `advancePlayerShot` [code] services it: while the shot gate `loc_4208` bit 0 is armed (a shot is travelling), it drains the position counter `loc_4209` by 4 each frame and raises the retire flag `loc_420b` when the counter lands in the narrow window [14,17] — that is, the shot has reached the far end of its travel and is about to expire. When no shot is in flight it re-parks the counter at 220 and seeds the shot's X field `loc_420a` from the ship's `loc_4202` (so a freshly-fired shot inherits the ship's column), but only if the ship is alive; otherwise the field is zeroed. Note the counter counts *down* from 220, so a large value is "just fired at the bottom" and a small value is "near the top."

`advancePlayerShotAndStageSprite` [code] is the pipeline's actual entry point for the shot: it calls `advancePlayerShot`, then reads back the {counter, field} pair as a coordinate and writes the shot's two render cells `loc_409f` and `loc_409d`, complementing the field and choosing one of two low-byte X formulas by the direction flag `loc_4018`.

### The move planner: picking and committing a horizontal target

Several AI states share a chain of routines that decide where a diving attacker should slide horizontally. At the bottom is `commitMoveToTargetX` [seen]: given a chosen target X it stashes that target at record+0x19, records the signed move delta (current X minus target) at record+0x09, zeroes the three accumulator bytes at record+0x1a..0x1c, and bumps the planner's sub-state (record+2). This is where a subtle overlap matters: record+0x19 is *also* the flight curve's first accumulator high byte, so committing a horizontal target simultaneously seeds the swoop the attacker will fly.

`commitMoveAcrossPlayerX` [code] chooses that target so the attacker crosses to the *opposite* side of the ship: it signed-halves the gap between the actor's X (record+4) and the ship reference `loc_4202`, biases it by 16, and clamps to the far band — the right band [144,208] when the actor is left of the ship, the left band [48,112] when it is at or right of the ship — then commits it. `commitMoveToStoredOrPlayerTargetX` [code] is an alternate front-end: if the lead `OBJ_TABLE` record's bit 0 is set it steers toward that record's stored target (its byte 0x19), otherwise it falls back to the cross-player pick. `advanceActorPhaseAndCommitMove` [code] is the state-2 handler that ties these together — it ticks the actor's phase counter (record+3) and then, if the object's kind field (record+7, masked to 0x70) equals 0x60, uses the stored/player select, and otherwise the plain cross-player select.

`beginObjectCrossPlayerMove` [code] is the shared tail used when an object needs to start a fresh diving run: it commits a cross-player move and then arms the flight-curve step seed (record+0x18 = 3, which makes the curve run four integration steps) and a generous move throttle (record+0x10 = 100). `armDirectedMoveWhenInWindow` [code] is state 8: it ticks the arm counter (record+3) and, as long as either that counter or the position (record+4) is outside the window [96,160), keeps the object cruising cross-player via `beginObjectCrossPlayerMove`; once both are in the window it advances the state by two (into the mirrored path-walk), seeds the move timers (record+0x10 = 3, record+0x11 = 12), clears the heading and cursor, and sets the direction bit from whether the ship reference sits below the object's position. `restartObjectMoveRun` [code] is state 12: it bumps record+3, forces the state back to 8, and kicks off another cross-player move — the loop that sends an attacker back around for another pass.

### Path walking

Once a move is committed the object walks a table of step deltas. `advanceObjectPathStep` [code] (state 1) reads the per-object cursor (record+0x13) into `PATH_STEP_TABLE` (0x1e00), adds the first delta to Y (record+3) and the second — direction-controlled by record+6 bit 0 — to X (record+4). If X (plus a 7-pixel margin) crosses the near screen edge it forces the object into state 5 (fall-away); otherwise it advances the cursor, ticks the move throttle (record+0x10, reload 4), nudges the cross-step (record+5), ticks the leg counter (record+0x11) and, when a leg finishes, advances the state. `advanceObjectPathStepDescending` [code] (state 10) is the subtract-direction mirror: it subtracts this step's X delta from record+3, then — unless the direction bit hands the Y half off to the ascending arm — subtracts the Y delta from record+4, ticks throttle and leg, and on a finished leg advances the state while reloading throttle=3, leg=12, heading=12, cursor=0. `advanceObjectPathStepAscending` [code] is that ascending arm: it adds the step-table byte to record+4, advances the cursor, ticks throttle and leg, and on leg-finish advances the state reloading throttle=3, leg=12, heading=244 (i.e. −12), cursor=0. Finally `advanceObjectPathStepAlias` [code] (state 11) is a pure trampoline — it does no work of its own and simply forwards to `advanceObjectPathStep`, so two state slots share one path handler.

### Diving, the flight curve, homing, and settling

The dive proper is `advanceObjectDiveStep` [code] (state 4). Each frame it steps the object's position (record+3) by 1 or 2 depending on the parity bit of `loc_425f` — so the dive's descent rate alternates every frame — then window-checks it: inside the small window [6,9) it bumps the state and stops. Outside, it runs the flight curve and folds the curve's heading high byte (record+0x19) plus the per-object increment (record+9) into a new screen Y (record+4); a carry that crosses the signed boundary means the swoop has run off the bottom, and it bumps the state instead of storing the Y.

`advanceObjectFlightCurve` [code] is the swoop generator underlying every diving path. It runs ((seed & 3) + 1) integration steps over two 16-bit accumulators held in the record (hi/lo at 0x19/0x1b and 0x1a/0x1c). Each step adds twice the *other* accumulator's sign-extended high byte into this one, with a guard that treats a resulting high byte of exactly 128 as overflow and reverts it — a cross-coupled rotation that traces the curved dive path, its high bytes becoming the heading the dive and flight handlers add to screen Y.

`homeObjectXTowardPlayer` [code] (state 7) steers the object's 16-bit X:sub-pixel pair (record+4 high, record+9 low) toward `loc_4202` by roughly four times the signed distance each frame, carrying a small rounding bias, bumps the frame counter, and advances the state when the dwell timer (record+0x10) drains to zero. `initObjectPhaseSteps` [seen] (state 13) is a phase entry: it derives a step count n from the inverted low two bits of the type field (record+7), records n+1 as the step count (record+0x16) and a derived code byte at record+3, arms the phase timer (record+0x10 = 24), advances the sub-state, and clears the ready flag (record+0x0f) — re-arming it only when n is zero. `settleObjectXAtRest` [seen] (state 15) is how an object comes to rest in the formation: each frame it steps record+4 up one count until the wrapped distance from the rest value 200 falls within 5, then holds.

### Firing at the player

`advanceObjectFlightAndFire` [seen] (state 3) is where standing/diving attackers shoot. It bumps the object's counter (record+3), runs the flight curve, and computes screen Y = per-object increment (record+9) + curve heading (record+0x19). A Y that has climbed too high advances the state by two; a wrapped counter advances it by one; otherwise, gated by `OBJ_ACTIVE_FLAG`, it aims the object at the ship and — unless the inhibit bit `loc_422b` bit 0 is set — scans the firing schedule in `loc_4213` (a count/match-value pair) for its own counter value, spawning an aimed bullet on a match. `advanceHomingObjectFlightAndFire` [code] (state 9) is the same shape but, per the mode byte (record+0x17), first homes the object's column (record+9) toward the target column `loc_4202` — always for mode > 4, on odd frames for mode 4, never below 4 — and computes Y from that column plus the curve heading; its too-high and counter-wrapped cases jump to states 5 and 4, and otherwise a move throttle governs a state step before the same aim-and-fire path.

The aiming is `aimObjectAtTarget` [seen]: from the vertical drop (0xf0 minus the sprite Y, record+3) and the horizontal delta from the sprite X (record+4) to `loc_4202`, it derives a 0–7 direction octant and stores it in the object's heading field (record+5), mirroring the octant when the target is to the left. The octant math is `computeDirectionOctantFromSlope` [seen]: it divides the slope, clamps a steepest (top-bit-set) quotient to 0x80, and returns the top three bits. That stored heading is later what the sprite builder folds into a facing attribute.

When a firing row matches, `spawnAimedProjectileAtPlayer` [code] claims the first free slot in the 14-entry projectile table at `loc_4260` (stride 5, bit 0 of the first byte marking a slot live), marks it active, copies the object's sprite Y and X, and stores a scaled X velocity aimed at the ship (`loc_4202`), mirrored when the ship is to the left; it no-ops when the table is full. The velocity comes from `computeJitteredXVelocity` [code], which divides the slope, adds a bounded PRNG draw (0..31) plus a floor of 6, and clamps to 0x7f — so aimed shots spread with a little randomness rather than being pixel-perfect. Those spawned bullets are the same `loc_4260` pool the projectile integrator advances and renders each frame and that the player-collision sweep tests against the ship.

Two more routines shape *when* and *which way* attackers act. `selectAttackerRowScan` [code] rebuilds the firing schedule `loc_4213`: it seeds a slot index and base from the alt flag `loc_421b` (slot 2/base 157 when set, else slot 1/base 132) and scans up to four two-byte slots of `ROW_OCCUPANCY` (0x41e8), advancing while neither byte of a slot has bit 0 set, storing the resulting (slot, base) pair the flight handlers scan against. `chooseNextAttackerDirection` [code] sets the shared launch/curve direction flag `loc_4215`: the 16-bit formation anchor `loc_420e`'s sign picks which edge of `FORMATION_X_BOUNDS` (0x4210) to measure the gap against, and within 28 pixels of that edge the flag is forced away from it; otherwise a fresh random bit picks the direction.

### The dying-object animation

When an object's dying flag (record+1) is set, control goes to `dispatchDeactivatedObjectAnim` [code], which reads the animation sub-state (record+2) and hands off to one of four phase handlers — the sub-state-0 setup, the tick, the expiry, or a terminal no-op. `tickDeactivatedObjectAnim` [code] (sub-state 1) counts a fast timer (record+0x10) down, reloading it and bumping a companion (record+0x12) on elapse, then counts a slow timer (record+0x11); when the slow timer elapses it either retires the object (record+1 = 0) or — if the position field record+7 is past 112 — reloads the fast timer to 50, seeds the companion from the global `loc_422d` plus 32, and advances the sub-state. `endObjectAnimOnTimerExpiry` [code] (sub-state 2) simply counts the timer at record+0x10 down and clears the object's state byte (record+1) on the frame it reaches zero, ending the animation.

### Building the sprite

`renderObjectSprite` [seen] turns one object record into a hardware sprite record (Y, attr, sprite#, X). An active object copies its position — X = objX − 8, Y = the hardware's inverted objY minus a caller-supplied offset — and folds the signed heading (record+5) into a display attribute added onto the record's base attribute (record+0x0f), rotating the heading by whole 24-count sectors down into a facing value with small one-pixel diagonal nudges. A secondary-active object instead uses a fixed sprite number 7 and the record's alternate attribute (record+0x12). With both flags clear the sprite is parked off-screen at (248, 248). This is what gives a diving attacker its visibly-rotating orientation as its heading sweeps around.

### Collisions and the player-hit event

Collisions run as two sweeps in the pipeline. `flagPlayerShotHitsOnObjects` [code] fires only while the shot gate `loc_4208` bit 0 is armed, then box-tests the shot's coordinate cells (`loc_4209`/`loc_420a`) against each of the seven `OBJ_TABLE` records via `flagPlayerShotHitOnObject` [code], which — for an active object whose position (record+3/record+4) falls inside a 6-wide by 12-tall window around the shot — raises the shot-retire flag `loc_420b` and hands off to the kill-scorer to deactivate and score the object. The mirror sweep is `flagObjectHitsOnPlayer` [code], gated on `OBJ_ACTIVE_FLAG` bit 0, which box-tests each of the seven objects against the ship via `flagObjectHitOnPlayer` [code]: it classifies the object's position field (record+3, biased by 33) into a near or far proximity window, tests the ship reference `loc_4202` minus the object's X (record+4) against that window's band, and on overlap raises the player-hit flag `HIT_EVENT_FLAG` (0x4204) and hands off to the kill-scorer.

That hit is consumed later in the same frame by `handlePlayerHitEvent` [code], the sole reader of `HIT_EVENT_FLAG`. If the flag is clear it is a no-op; otherwise it clears the flag, zeroes `OBJ_ACTIVE_FLAG` (freezing the whole object world for the death sequence), sets the ship's death/hold flag `loc_4201` so the ship handler holds the wreck in place, arms the two pulse counters `loc_4205` = 10 and `loc_4206` = 4 that drive the death sound envelope, queues the hit-sound command, decrements the pace counter `loc_421a` (floored at zero), steps the [0,5] cycle counter `loc_421d`, and pulses the sound latch `SOUND_W_REG3` (0x6803) when the mode bit `loc_4006` is set.

### Round setup

Two sequence-state handlers stand the whole subsystem up. `resetObjectRamAndAdvanceSequence` [code] runs at start-screen time: it seeds the interleaved OBJRAM shadow from the ROM template `loc_1d91`, zeroes the 64-byte sprite-shadow span at `SPRITE_SHADOW_BASE` (0x4060) and a broad region from `loc_4260` (a full page plus an 80-byte tail, wiping both the projectile pool and the object records), clears status cells (`loc_4238`, `MESSAGE_SCROLL_ENABLE` at 0x40b0), points the VRAM write cursor `VRAM_WRITE_PTR` (0x400b) two cells into the grid at `VRAM_BASE`, arms the dwell timer `loc_4009`, and bumps `SEQUENCE_STATE` (0x400a). `activateObjectsAndBeginPlayPhase` [code] is the state-timer handler that finally switches play on: while its dwell (`loc_4009`) still runs it waits, and on expiry it reloads the timer, advances the sequence, sets `OBJ_ACTIVE_FLAG` to enable the object/AI/projectile/collision machinery, centers the ship reference `loc_4202` at 128, refills the 16-byte enemy-launch sub-counter block at `loc_424a` from `SUBCOUNTER_RELOAD_TABLE` (0x15e3), clears two scratch cells (`loc_4058`, `loc_405a`), and queues its display commands.

Finally, `loc_090b` [code] is a deliberately-unnamed one-instruction epilogue shared by the command-enqueue path — it restores the caller's saved pointer and returns, touching no work RAM.

## Sound

Galaxian's audio is a bank of discrete-sound hardware latches driven from work-RAM shadow cells: the eight write registers at 0x6800-0x6807 (SOUND_W_REG0 through SOUND_W_REG7), the four LFO-frequency latches at 0x6004-0x6007 (SOUND_LFO_FREQ), and the pitch latch at 0x7800 (SOUND_PITCH_W). No single routine owns the whole register file; instead a handful of per-frame drivers each claim a slice of it and compose their contribution from RAM state.

### The per-frame composition pass

The heart of the system is driveSoundFrame [code] (0x16f5). It opens each frame from a clean slate — it clears the composite flag byte at loc_41c0 and primes the staged-pitch shadow SOUND_PITCH (0x41c1) high, to 0xFF. It then runs seven channel/effect updaters in a fixed order, each free to write those two shadows, and finally latches the result to hardware: the composite byte loc_41c0 goes to SOUND_W_REG6 (0x6806), its rotate-right to SOUND_W_REG7 (0x6807), and the staged pitch SOUND_PITCH to the pitch latch SOUND_PITCH_W (0x7800). Because the updaters run one after another over the same pair of shadows, their order is a priority order — the last updater to touch loc_41c0 or SOUND_PITCH wins the frame. And loc_41c0 is not a mere on/off: the updaters stamp it with distinct small values (0, 1, or 2) that mark *which* effect is sounding, and that whole value, not just a level, is what reaches SOUND_W_REG6.

The seven updaters run in this fixed sequence.

1. **armSoundSequenceOnRequest [seen]** (0x1747) is a one-shot arm gated on the request byte at loc_41d1. Only when that byte holds 1 does it fire: it clears the request, raises the sequence's active flag at loc_41d2 while priming the shared duration timer loc_41d6 to 1, and points the sequence cursor SOUND_SEQ_PTR (0x41d3) at the note-command table beginning at loc_1e68. Any other value leaves the byte untouched.

2. **updateSoundSweepVoice [code]** (0x17d0) is the swept "counter" voice, gated on bit0 of the driver-enable flag loc_4006. While its state cell loc_41c2 reads anything but 1 it hands off to the counter manager; on the tick where loc_41c2 reads 1 it instead reloads an idle template — loc_41c2 back to 0, the sweep cell loc_41c3 to 2, and the sound counter loc_41c4 to 160, which parks that counter well past its ceiling so the sweep stops advancing until it decays. The manager head, advanceSoundSweepAndStagePitch [code] (0x17e5), returns at once while bit0 of the gate loc_4226 is set; otherwise it steps its pointer forward one cell (from loc_41c2 onto the sweep cell loc_41c3). If bit0 of the tick cell loc_425f is set it jumps straight to the pitch dispatcher; failing that, it bumps the sweep cell while the sound counter loc_41c4 is still below its ceiling of 96, then falls into the tail tickSoundCounterAndStagePitch [seen] (0x17f9), which decrements and stores back loc_41c4 whenever the counter is still running. Both paths end at the dispatcher stageSoundPitchBySelector [code] (0x1801): it reads the low two bits of the pointed cell — zero stages a fixed pitch of 96, nonzero recomputes the pitch from the counter via stagePitchFromSoundCounter [code] (0x180c). That recompute reads loc_41c4 and, on an odd selector, biases it by 96 and rotates the biased sum right (the add's carry folding back into the top bit) to make a warble; an even selector passes the counter straight through. Either way it lands in stageSoundPitch [seen] (0x1815), which simply parks the byte in SOUND_PITCH for the frame's latch.

3. **armSoundSequenceBySelector [code]** (0x1819) runs only while bit0 of the driver-enable flag loc_4006 is set. It reads the request selector at loc_41df: selector 6 arms this driver's own sequence (unless the active flag SOUND_SEQ_ACTIVE at 0x41cd is already raised) by setting loc_41cf, priming loc_41d6 to 1, and pointing SOUND_SEQ_PTR at the table at loc_1ebd. Any other selector is passed to armSoundSequenceForSelector16 [code] (0x183a), which handles only selector 0x16 and ignores everything else — on a match it clears loc_41cf, raises SOUND_SEQ_ACTIVE, primes loc_41d6, and points the cursor at the table at loc_1edf.

4. **advanceAllSoundSequenceChannels [code]** (0x175d) steps the sequence engine by running advanceSoundSequenceChannel [code] (0x176c) over three descriptor flags in turn — loc_41d2, loc_41cf, and SOUND_SEQ_ACTIVE. An inactive descriptor (byte 0) is skipped. For an active one it stamps loc_41c0 with 2 and publishes the current tone byte loc_41d5 to SOUND_PITCH, then ticks the duration timer loc_41d6; while that timer still runs there is nothing more to do. When it expires it reads the next command byte at the cursor SOUND_SEQ_PTR: the end marker 0xE0 deactivates that descriptor, while any other byte is split — its low five bits index the tone table SOUND_TONE_TABLE (0x17a9) to become the new current tone loc_41d5, and its high three bits index the duration table SOUND_DURATION_TABLE (0x17c8) to reload loc_41d6 — after which the cursor advances past it. Notably, all three descriptors share the one cursor, the one tone cell, and the one timer, so the three arm entry points really feed a single sequence voice, and whichever armed most recently owns the cursor the passes then read.

5. **advancePulseToneEnvelope [code]** (0x184f) ticks a two-byte envelope word (low byte loc_41c7, high byte loc_41c8). When bit0 of the low byte is set it re-arms the word to its sentinel — loc_41c7 to 0 and loc_41c8 to 128 — and stops; otherwise it hands the high byte to pulseSoundToneFromCountdown [code] (0x185e). That handler idles when the high byte is zero; otherwise it stores the byte decremented back into loc_41c8 and stages a two-level pulse through stagePitchAndRaiseSoundFlag [code] (0x186c) — value 129 when bit2 of the decremented byte is set, else 0. stagePitchAndRaiseSoundFlag stores that value minus one, modulo 256 (so 129 becomes 128 and 0 becomes 255), into SOUND_PITCH and raises the composite flag loc_41c0 to 1.

6. **driveRisingPitchRamp [code]** (0x1876) is a rising-pitch arm keyed on loc_41c9. While the arm byte has not reached its reset point it advances the ramp via advanceSoundPitchRamp [seen] (0x1886) — and the arm byte itself is only tested here, never stored back while it stays armed. advanceSoundPitchRamp treats the two cells just past the arm byte as a {countdown, pitch} pair (countdown at loc_41ca): while the countdown is nonzero it ticks it down, adds a fixed step of 4 to the pitch, publishes the new pitch to SOUND_PITCH, and clears the composite flag loc_41c0 to 0; a drained countdown is idle. When the arm reaches its reset point, driveRisingPitchRamp clears loc_41c9 and reloads the pair at loc_41ca to a countdown of 32 and pitch of 0.

7. **advanceGatedSquareTone [code]** (0x1723) uses a gate counter at loc_41cc to drive a square-wave toggle. While that counter is more than one step from expiry it calls driveGatedSquareTone [code] (0x1733) — again testing, not storing, the counter — and at the expiry step it parks loc_41cc at 0 and re-arms the tone duration SOUND_TONE_DURATION (0x41ce) to 8. driveGatedSquareTone itself runs the duration counter: while SOUND_TONE_DURATION is nonzero it counts one tick off it and writes SOUND_W_REG5 (0x6805) with the frame flag loc_4007 exclusive-ORed with 1 — since bit0 of loc_4007 alternates every frame, that yields a per-frame square toggle — and once the duration is spent it writes 0 to silence the register.

### Drivers outside the composition pass

Several sound drivers reach their hardware registers directly rather than through the composed shadow pair. driveSoundVoicesFromOccupancy [code] (0x16b8) is the formation "hum": on even frames only (bit0 of the frame flag loc_4007 clear) it sums the 6×10 OCCUPANCY_GRID (0x4123, row stride 16) into an eight-bit tally seeded at 1, then lights up to three of the sound-write latches SOUND_W_REG0..2 (0x6800-0x6802) — one per unit of tally, stopping the instant the tally drains and zeroing every latch past that point — so the hum thickens with the number of attackers still on screen. It also raises the near-empty flag loc_4224 once the tally has nearly run dry.

driveDecayingSoundSweep [code] (0x16a6) is a decaying sweep on SOUND_W_REG4 (0x6804), also gated to even frames. Counterintuitively its countdown lives in the very same request cell loc_41df that the sequence arms read as a selector: while that byte is nonzero it emits the byte rotated right two bits to SOUND_W_REG4 and ticks it down by one, so a posted request value plays out as a value that shrinks toward silence on that register.

driveGatedSoundStepSequence [code] (0x1327) is a step sequence gated by bit0 of the enable flag loc_4201. A prescaler at loc_4205 (reload 10) fires once every ten eligible frames; on each fire it enqueues a command word (opcode 2 carrying the current step) and steps the step counter loc_4206 down. When that counter reaches zero the sequence ends — it clears the enable flag loc_4201 and silences SOUND_W_REG3 (0x6803). The enqueue path it drives closes through the small deliberately-unnamed pure-stack epilogue loc_090b (0x090b), which restores the caller's pointer and returns.

driveSoundLfoLevel [code] (0x1898) manages the LFO frequency latches. With no reset pending — the request flag SOUND_LFO_RESET_REQUEST (0x41d0) clear — it runs the normal decay via decaySoundLfoLevel [code] (0x18a6), which, only on the tick where loc_425f reads 0xFF and the level SOUND_LFO_LEVEL (0x421f) is still nonzero, drops the level by one and re-broadcasts it. When a reset is pending it consumes the request and slams the full level of 15 out instead. Both paths funnel through broadcastSoundLfoLevel [seen] (0x18b2), which stores the level to SOUND_LFO_LEVEL and then fans it across the four SOUND_LFO_FREQ latches (0x6004-0x6007), rotating the byte right one bit between writes so each latch receives a successively rotated copy.

### Requests and silence

Sound requests originate outside the drivers. armObjectAnimAndRequestSound [code] (0x10f0) is the sub-state-0 entry of a deactivated object's animation: beyond seeding that object's animation timers and advancing its sub-state so the entry runs only once, it posts a sound request into loc_41df — the low effect 0x07 when the object's position byte is below 112, the high effect 0x17 at or above — which is precisely the value the decaying sweep then plays out on SOUND_W_REG4.

Finally, silenceSoundAndDisableIrqStars [code] (0x1cb5) is the hardware quiesce used when a screen is torn down: it sets the four SOUND_LFO_FREQ latches to 1, clears all eight sound write registers SOUND_W_REG0..7, clears the interrupt-enable latch IRQ_ENABLE (0x7001) and the starfield-enable latch STARS_ENABLE (0x7004), and drives the pitch latch SOUND_PITCH_W (0x7800) fully high — killing the audio and halting both the vblank interrupt and the starfield in a single pass.

## Coins, credits, the HUD, score display, and the message scroller

Everything the machine shows a waiting player -- the credit count it banks from the coin door, the lamps under the start buttons, the scores across the top of the screen, the reserve-ship markers, the scrolling attract text, and the animated tile wipe behind it -- is driven by the routines below. They share a small cluster of work-RAM cells around 0x4000 and a handful of write-only hardware latches at 0x6000, and they hand their drawing off through a command queue whose write head sits at 0x40a0: a routine posts a two-byte word `(channel, param)` and a later dispatcher services it (channel 6 draws message columns, channel 7 redraws the credit count, channel 4 clears score slots, channel 3 adds to a score).

### Coinage: from the coin door to a credit

Two per-frame steps turn coin pulses into credits. The front end is `serviceCoinInputs` [seen]. When the coinage mode cell loc_4000 reads 3 it defers entirely to `presetCreditCount` [code], which stows a fixed nine into the credit count loc_4002 and clears the coin-phase flag loc_4001 (its oracle writes the word 0x0900 across the pair in one store) -- a service/free-play preset. Otherwise it folds the two input shadows IN0_SHADOW (0x4010) and loc_4013 together, complements them, and masks the result through the two guard cells loc_4015 and loc_4016. A set bit 7 means a coin edge and routes straight to `addCreditForCoin` [code]; otherwise the low two bits each bump the coarse coin-pulse counter loc_4004 (up to twice in one pass). `addCreditForCoin` bumps loc_4002 while it stays under its ceiling of 99 (0x63), raises the event flag loc_41c9, and posts a channel-7 request so the on-screen credit count is redrawn; at the cap it does nothing.

The coarse pulses that pile up in loc_4004 are drained -- and metered -- by `tickCoinMeterAndAwardCredits` [seen]. It runs a small pulse-width timer in loc_4003: while that cell is nonzero it calls `pulseCoinCounter` [seen] and lets it count the cell down, and only when the timer reaches zero does it consume one coarse coin (loc_4004 nonzero), refill loc_4003 to fifteen, and award credit(s) according to loc_4000 -- mode 3 awards nothing, mode 1 runs the two-coins-per-credit path, mode 2 steps the credit count twice (two credits per coin), and any other mode steps it once. `pulseCoinCounter` is the electromechanical meter driver: it rotates the timer value right three bits so the value's bit 3 lands in bit 0 of the coin-counter latch COIN_COUNTER_0_LATCH (0x6003) -- only that low bit is wired -- so across the fifteen-frame refill window the meter output holds high while the count is eight or more and drops afterward, giving one clean pulse per coin, then decrements the caller's cell.

The two-coins-per-credit path is `awardCreditEverySecondCoin` [code], selected in mode 1. It treats loc_4001 as a phase toggle: on the first coin of a pair (bit 0 clear) it hands off to `setCoinPhaseFlag` [code], which simply raises that flag to 1; on the second coin it clears loc_4001 and calls `incrementCreditCount` [code] on loc_4002. `incrementCreditCount` is the shared credit-stepping core (mode 2 and the default path call it directly): at exactly 99 it stops, above 99 it defers to `clampCreditsToMax` [code] which pins the cell back to 99, and below 99 it increments, raises loc_41c9, and posts the same channel-7 credit-redraw request. That loc_4002 is genuinely the credit count -- not some anonymous counter -- is corroborated by every consumer that reads it: the clamp, the lamp driver, the lockout driver, and the attract-to-game advance.

The physical coin door is gated by `updateCoinLockoutFromCredits` [code], which drives the lockout latch COIN_LOCKOUT (0x6002) straight from loc_4002: once the count reaches nine it releases the latch through `clearCoinLockout` [code] (which writes 0 to 0x6002), and while the count is below nine it sets the latch to 1. `clearCoinLockout` doubles as the release tail for that decision.

### Start-button lamps and the credit-driven advance

`driveStartButtonLamps` [code] lights the two start-button lamp latches START_LAMP_0 (0x6000) and START_LAMP_1 (0x6001) from the credit count, gated on bit 5 of loc_425f: with that enable bit clear it forces both lamps off; otherwise zero credits leave the lamps as they are, one credit lights lamp 0, and two or more light both. This is the routine the attract sequence keeps calling so the lamps track credits as coins go in.

Dropping a coin is also what kicks the machine out of attract. `advanceGameStateOnCredit` [code] is the post-dispatch continuation of the top-level sequencer: it does nothing while loc_4002 is zero, but the moment a credit exists it advances the game-state index GAME_STATE (0x4005) and wipes the attract sub-state cluster -- loc_4007, the sequence step SEQUENCE_STATE (0x400a), loc_41c2, the sound-request byte loc_41df, and the scroller-enable MESSAGE_SCROLL_ENABLE (0x40b0) -- so the start sequence begins from a clean slate.

### The top-level attract/start sequence

A short chain of state handlers, selected by the sequence step in SEQUENCE_STATE, walks the machine from attract into a fresh game, re-arming a shared two-tier dwell timer (the byte pair loc_4008/loc_4009) at each step and posting redraw/sound requests as it goes. `holdStartLampsThenAdvanceSequence` [code] ticks the countdown loc_4019 and, while it runs, keeps the lamps in step via `driveStartButtonLamps`; on the zero-crossing it advances SEQUENCE_STATE and zero-fills the 128-byte flag-bits block at FLAG_BITS_BASE (0x4100). `blankVramRowsThenDriveStartLamps` [code] paints two 28-cell blank-tile rows through the VRAM write cursor VRAM_WRITE_PTR (0x400b) (skipping a four-cell gap between them), counts down the loc_4009 tier, and on the last row advances the state, clears the screen-flip latches FLIP_SCREEN_X (0x7006) and FLIP_SCREEN_Y (0x7007) plus loc_4018, posts two queue words, and drives the lamps once more. `postCreditAndMessageDrawsAndAdvance` [code] queues a channel-7 credit redraw and a channel-6 message draw, advances the step, and reloads the dwell pair to 96/16. `emitMessageColumnsThenAdvanceSequence` [seen] runs the shared strided-table reset, then on each low-tier (loc_4008) expiry reloads it to 80 and queues a channel-6 message-column request whose parameter tracks the mid-tier count in loc_4009; when the mid tier expires it advances the step, reloads both tiers to 32/4, clears the sprite-source object block at SPRITE_SOURCE_OBJ_BASE (0x42b0), and zeros the queued-column count DRAWN_COLUMN_COUNT (0x4241).

`startGameRoundAndClearScores` [code] is the round-start entry. It stores a 16-bit player/spawn word so that its low byte seeds the active-player index CURRENT_PLAYER (0x400d) and its high byte seeds the second-player-live flag loc_400e in one store; blits the 32-byte ROM row template loc_051b into the packed flag bitmap PACKED_FLAG_BITMAP (0x4180); arms the sub-state advance gate when loc_401f bit 0 is set; enters play by setting GAME_STATE to 3, SEQUENCE_STATE to 0, the mode/sound gate loc_4006 to 1, and loc_41d1 to 1; then queues a channel-6 start message and two channel-4 score-slot clears.

### Score display

Scores live as three-byte packed-BCD fields -- player 1 at PLAYER1_SCORE_BCD (0x40a2), player 2 at PLAYER2_SCORE_BCD (0x40a5), the high score at HIGH_SCORE_BCD (0x40a8) -- and are painted as digit tiles up VRAM columns. `byteToPackedBcd` [code] is the arithmetic helper that turns a binary byte into its two-decimal-digit packed form (value modulo 100, tens in the high nibble). The painting primitive is `drawBcdDigit` [code]: it maps a nibble to the contiguous digit tiles at 0x90..0x99, but suppresses leading zeros -- while a blank budget in C is nonzero a leading zero is drawn as the blank tile (the code adds 0x80 so 0x80+0x90 wraps to tile 0x10) and the budget is spent, and the first significant digit ends suppression -- then advances the cursor by its stride. `drawBcdNumberColumn` [code] wraps that into a six-digit render: it walks three BCD bytes downward from the most-significant end, drawing high nibble then low, stepping the VRAM cursor up one screen row (-32) per digit, with a four-digit blank budget so a small score shows without a row of leading zeros.

Which cursor and which field are chosen by a family of selectors. `selectPlayerStatusVram` [code] returns the status-column base for a player (player 1 at PLAYER1_STATUS_VRAM 0x5340, otherwise player 2 at PLAYER2_STATUS_VRAM 0x50e0), and `selectCurrentPlayerScore` [code] resolves the active player's score-field base into DE (0x40a2 or 0x40a5) from CURRENT_PLAYER. `drawScoreToSelectedPlayerField` [code] picks the digit-field cursor from a selector -- the primary field DIGIT_FIELD_PRIMARY (0x5381) when zero, else the alternate DIGIT_FIELD_ALT (0x5121) -- and paints the BCD column there; `drawHighScoreDigits` [code] points the same six-digit render at the fixed high-score field at loc_5241. `drawScoreFieldByIndex` [code] ties these together by a small index: 0 redraws player 1's score into the primary field, 2 redraws the high score, and 1 redraws player 2's score only when the live flag loc_400e is set -- and it passes that flag on as the field selector so the second player's score lands in the alternate VRAM field; an index of three or more recurses down, redrawing every field. Each of these feeds `drawBcdNumberColumn` the field top (base + 2) because the render walks downward. `clearAndRedrawScoreField` [seen] first zeros a field before repainting it through the same index scheme: index 0 clears player 1's three bytes plus its companion byte loc_40ad, index 1 clears player 2's plus loc_40ae, and index 2 clears the high score (re-zeroing its own first byte, as it has no separate companion), with the same descend-over-all-lower-fields behaviour. Those companion bytes are shared with the bonus-marker logic below, so clearing a player's score also re-arms their bonus award.

### The player-status column

A separate three-cell VRAM column shows which player is up. `paintPlayerStatusColumn` [code] stamps that column from a base pointer stepping by a stride: the top cell gets the player code plus one, then two fixed tiles (0x25 and 0x20); afterward, only when flags bit 4 is clear and the mode gate loc_4006 is zero, it clears the status flag loc_40ab. `repaintPlayerStatusColumn` [code] selects the active player's column via `selectPlayerStatusVram` and either paints it directly (flags bit 4 clear) or, in swap mode (bit 4 set), blanks the active column's three cells with tile 16 and -- only when the paired-player flag loc_400e is set -- paints the other player's column too. `repaintPlayerStatusColumnIfSaved` [code] guards that repaint behind a nonzero saved status byte loc_40ab, and `repaintPlayerStatusColumnFromModeGate` [seen] is the entry that latches the mode: when loc_4006 is nonzero it saves that value into loc_40ab and repaints, and when loc_4006 is zero it repaints only if loc_40ab is already set.

### Reserve markers and the bonus ship

The row of reserve-ship markers is drawn by `drawMarkerRow` [code] across five slots starting at MARKER_ROW_VRAM (0x539e): it paints the requested count of marker tiles (tile 102) as 2x2 blocks growing upward, then blanks the remaining slots until its signed slot counter goes negative. When the object-active flag OBJ_ACTIVE_FLAG (0x4200) is set -- the current ship is out in play -- the displayed count is dropped by one, and if that empties it the whole row is blanked instead. `awardBonusMarker` [code] is the one-shot bonus-ship award, keyed per current player through the flag table at loc_40ad indexed by CURRENT_PLAYER (so player 1 uses loc_40ad, player 2 loc_40ae -- the very bytes the score-clear re-zeroes): if this player's slot is already flagged it does nothing, otherwise it flags the slot, raises the sound-envelope trigger loc_41c7, increments the marker counter loc_421d, and repaints the marker row with the new count.

### Kill scoring

`awardKillScoreByBandAndDeactivate` [code] both retires a shot enemy and books its points. It deactivates the object (its first three slot bytes become 0, 1, 0), then scans three value bands of the object's type/position field (obj+7) against the threshold 0x50, seeding a score parameter at four: each band the field clears bumps the parameter and drops the field by sixteen, and the first band it falls under posts a channel-3 score-add request with the parameter reached. If all three bands are exhausted it raises the inhibit word loc_422b to 0xf001, and -- when the active-neighbour count ACTIVE_NEIGHBOR_COUNT (0x422a) is exactly two -- folds in a neighbour bonus, records it at loc_422d, and posts the folded channel-3 request. The channel-3 handler is what actually adds the value to the player's BCD score and rolls the high score.

### The message scroller and attract text columns

Static attract text is painted a column at a time. `drawTextColumn` [code] is the inner loop: for a run of characters it reads each source byte, subtracts the '0' code (0x30) to map it to a font tile, writes it, and steps the destination by a stride -- a -32 stride walks the text up one screen column. `drawTextColumnFromDescriptor` [code] unpacks a five-byte descriptor (source word, destination word, count) and drives that loop up a column, and `drawTextColumnByIndex` [code] indexes the ROM descriptor table TEXT_DESCRIPTOR_TABLE (0x1cf6) by a small index (five bytes per record) to pick which text to paint.

The scrolling message system is richer. `renderMessageColumn` [seen] is indexed by an accumulator whose top two bits select a mode after the low bits pick a record from the pointer table MESSAGE_PTR_TABLE (0x235c) (each record carries a VRAM destination word followed by the text): bit 7 blanks a message by overwriting each of its cells up the column with the blank tile 0x40 to the 63 terminator; bit 6 is position setup, recording the destination pointer into MESSAGE_DEST_PTR (0x40b5) and the text pointer into MESSAGE_TEXT_PTR (0x40b3), computing this column's cursor/countdown cell in the table based at loc_4020 and stashing its address in MESSAGE_CURSOR_PTR (0x40b1), clearing the whole column to tile 16, seeding the packed row byte, and raising MESSAGE_SCROLL_ENABLE (0x40b0); and with neither top bit set it simply draws each glyph up the column to the terminator. Once armed, `advanceMessageScroller` [seen] steps the message one glyph per eligible frame: it runs only while MESSAGE_SCROLL_ENABLE bit 0 is set, reads the control byte through MESSAGE_CURSOR_PTR, and if its low three bits are still counting just ticks it; at the text terminator (63) it ticks and finishes; otherwise it emits one glyph from MESSAGE_TEXT_PTR into the cell at MESSAGE_DEST_PTR, advances the source pointer, steps the destination up one row, and ticks. The tick itself is `endMessageScrollOnExpiry` [seen], which decrements the countdown byte and, on the exact zero-crossing, clears MESSAGE_SCROLL_ENABLE so the scroller stops; `endMessageScrollOnExpiryFromDe` [seen] is the same tail reached when the countdown pointer is carried in DE (it swaps it into place first). Message columns are also queued by object AI: `advanceObjectAndQueueMessageColumn` [seen] bumps an object's tick counter (ix+4) and counts down its dwell timer (ix+16), and on expiry posts a channel-6 request carrying the object's payload selector (ix+7 plus 75) -- which the dispatcher feeds to `renderMessageColumn` -- and advances the object's own state (ix+2).

### The animated screen-fill

Behind attract, the screen is wiped with a moving band of tiles. `advanceScreenFillStrip` [code] is the per-frame head: it pets the watchdog by reading SOUND_PITCH_W (0x7800), then checks the strip gate loc_4008 -- if it is zero there is no strip to draw so it goes to the outer-dwell handler, otherwise it loads the live cursor from VRAM_WRITE_PTR and draws the first sixteen tile pairs via `drawScreenFillStripFirstHalf` [code], which stamps its count of tile pairs 48/50 forward from the cursor (two cells per pass, a count of zero wrapping to 256) and falls into `drawScreenFillStripSecondHalf` [code]. The second half stamps a further run of tile pairs 52/54, saves the advanced cursor back to VRAM_WRITE_PTR, and ticks the strip countdown loc_4008; when that expires it defers to `restartScreenFillOnDwellExpiry` [code]. That routine ticks the high dwell tier loc_4009 (the byte just past loc_4008) and, when it is already zero or reaches zero on this tick, re-seeds the whole fill through `resetScreenFillState` [seen] -- which, unless IN0 (0x6000) bit 6 is asserted, rewinds VRAM_WRITE_PTR to VRAM_BASE (0x5000), re-arms loc_4008 to a full page of 32, and clears loc_401a and GAME_STATE.

### The attract input scan

While attract runs, a short fall-through chain reads the controls both to request sounds on player input and to keep the DIP-derived text columns and the screen-fill seeded. `requestSoundOnInput1AndContinueScan` [code] reads the IN1 port (0x6800) and, if either of its low two bits is set, seeds the sound-request byte loc_41df to 0x16, then continues into `requestSound6AndContinueInputScan` [code], which -- when either input port shows bit 2 or 3 -- seeds loc_41df to 6 and flows into `armInputFlagAndDrawInputColumns` [code], which raises the companion input flag loc_41cc when the folded ports show bit 4 and then falls into `drawInputTextColumnsAndSeedScreenFill` [seen]. That final step decodes three two-bit fields -- IN1 bits 6-7, IN2 (0x7000) bits 0-1, and IN2 bit 2 -- into text-descriptor indices and paints each column, and then, unless IN0 bit 6 is asserted, seeds the screen-fill state (mode gate loc_4006 to 0, loc_401a to 2, the dwell pair loc_4008/loc_4009, and VRAM_WRITE_PTR to VRAM_BASE), clears the four output latches from START_LAMP_0 through COIN_COUNTER_0_LATCH (0x6000-0x6003), and silences the sound hardware.

### Small shared helpers

Two utilities round out the cluster. `reloadExpiredCounterAndTally` [seen] is a tiny reload helper used by a table-driven loop: it copies a reload byte from a source cell into an expired counter cell, re-arming it, and returns the running refill tally incremented. And loc_090b is a deliberately unnamed pure-stack epilogue -- the shared exit of the command-queue enqueue path that restores the caller's saved pointer and returns, with no work-RAM effect of its own.

## Tile / VRAM drawing primitives and coordinate mapping

Every glyph, block, and cleared row this subsystem paints lands in the tilemap held at VRAM_BASE (0x5000), a grid of 32 cells per row. The routines here divide into a handful of atomic cell-stampers, a family of block builders layered over them, a couple of table- and animation-driven selectors, and the per-frame screen-fill and projectile drivers that move the cursor across that grid a row at a time.

**Packing a coordinate into a cell address.** `mapPackedCoordToVram` [code] is the shared address arithmetic the display-list draws lean on. It takes a single packed coordinate byte and shuffles its nibble fields into a VRAM cell address: the low nibble, rotated right two, supplies both the page (high) byte, held to 0..3, and the top two bits of the low byte, while the high nibble (masked to three bits) is folded — running-summed, complemented, and masked to four bits — into the remaining low-byte bits, and the whole offset is added onto 0x5000. Beyond the address itself it hands back two decisions its callers act on: register A carries the coordinate's upper field shifted down, and the carry flag is left holding the coordinate's bit 4. That carry is the single switch the figure-draw dispatchers use to choose between a compact and a tall glyph.

**The two atomic stamps.** `stampTilePair` [code] is the innermost primitive: it writes a tile code at the destination cell and that code plus one at the very next cell, then advances the pointer past the pair by a caller-supplied stride and bumps the tile code by two, returning the advanced pair so loops can chain. Because the store is a byte, a seed of 0xff wraps the second cell to 0x00. `drawDoubleHeightTile` [code] is the vertical counterpart — it paints the caller's tile at the destination and that tile plus two in the cell exactly one tilemap row (32 cells) below, forming the top and bottom halves of a double-height glyph.

**Two-by-two blocks built on the stamps.** `drawTileBlock2x2` [code] lays a full 2x2 block by calling `stampTilePair` twice with a stride of 31: since the stamp already steps +1 past its pair, +31 nets to a full 32-cell row, so the second pair (codes +2 and +3) lands directly beneath the first. `drawTileBlock2x2Up` [code] is the mirror that grows upward — it stamps with the unsigned step 65503 (−33), so after the pair's built-in +1 the pointer moves one row up, and it steps the tile code back by four before laying the upper pair. Both leave DE untouched for the caller. Their shared exit, `drawBottomTilePairRestoreDe` [code], is the two-cell tail that stamps the lower pair and then restores the DE the caller had saved before the block began. `drawTileBlock2x2AtDe` [code] is a small adapter that swaps the pointer arriving in DE into HL (handing the old HL back in DE) so a block can be drawn at a destination that was staged in DE. On top of these sit the fixed-seed entry points that need no code argument: `drawFixedTileBlock2x2` [code] draws a downward block seeded with glyph 44 (0x2c, laying codes 0x2c..0x2f), `drawFixedTileBlock2x2Up` [code] draws an upward block from the decorative seed 46 (it is what blanks the unused slots of the five-slot marker row at MARKER_ROW_VRAM, 0x539e), `drawFixedTilePairHorizontal` [code] stamps a single horizontal pair from seed 44 and returns the advanced pointer for a caller's loop, and `drawFixedTilePairVertical` [code] paints a double-height pair from that same seed 44.

**Selecting a block by table index or sign.** `drawIndexedTileBlock` [code] looks a block's base tile code up in TILE_BLOCK_TABLE (0x215b) by an index and stamps that block at the DE-staged destination. `drawSelectedTileBlockOrFallback` [code] wraps that lookup with a signed test on selector B: a non-negative selector indexes the table as above, while a negative one stamps a fixed fallback block seeded with tile 0xa4. `drawTileGlyphOrBlock` [code] is the higher dispatch that decides block-versus-glyph on the carry flag: carry set draws a selector-chosen 2x2 block (through `drawSelectedTileBlockOrFallback`, so a negative selector still yields the 0xa4 fallback), while carry clear fetches B's tile code from the index table at loc_2157 and paints it as a double-height glyph at the incoming destination.

**Timer-driven tile animation.** Two register-only helpers compute the animated variant index a glyph cycles through, without touching memory. `computeTileVariantFromTimer` [code] folds a value into a two-bit index by nibble-swapping the free-running per-frame counter loc_425f (0x425f), adding the value and an incoming carry, and keeping the low two bits — unless the value is 112 or above, in which case it saturates the index to the fixed 0x80 out-of-range marker via `markValueOutOfRange` (0x210a). `computeTileVariantFromValueAndTimer` [code] is the front end: it likewise saturates to 0x80 at or above 112, else takes the value's low nibble and sets a borrow when the frame counter's low nibble is smaller before delegating to `computeTileVariantFromTimer`. The net effect is a 0..3 variant that cycles with the frame counter, giving on-screen figures their animation.

**Drawing a figure at a packed coordinate.** Two sibling handlers combine the mapper with the block/glyph choice. `drawFixedTileFigureAtPackedCoord` [code] maps the coordinate to its cell, then — reading the mapper's bit-4 carry — stamps either a fixed 2x2 block (`drawFixedTileBlock2x2`) when bit 4 is set or a fixed vertical pair (`drawFixedTilePairVertical`) when it is clear. `drawAnimatedTileFigureAtPackedCoord` [code] is the animated twin: it maps the coordinate, folds that same coordinate through `computeTileVariantFromValueAndTimer` into a timer-animated variant, and hands the variant plus the bit-4 choice to `drawTileGlyphOrBlock`, so bit 4 set produces an animated 2x2 block at the mapped cell and bit 4 clear an animated double-height glyph there.

**Four-by-four indicator forms.** `blankTileBlock4x4` [code] clears a 4x4 region at loc_51da (0x51da) by writing the blank code 0x40 to four rows of four cells, stepping one full row (32 cells) between row starts — note this blank uses tile 0x40, distinct from the 0x10 the row/column clears use below. `blank4x4AndDraw2x2Icon` [code] clears that block and overlays a 2x2 icon seeded with tile 96 at loc_51fc (0x51fc). `draw4x4TileForm` [code] is the form selector for that indicator region: form 0 blanks-and-overlays the icon, form 1 only blanks the block, and any other form folds (form−2) into a tile code (its middle bits, complemented, over a fixed 0xc0 base) and stamps four consecutive 2x2 blocks — the seed advancing four codes per block — across the four corners at loc_51da, loc_51dc (0x51dc), loc_521a (0x521a) and loc_521c (0x521c), a contiguous 4x4 cell region.

**Column strips and their periodic refresh.** `drawTileColumnTriple` [code] copies three consecutive source bytes up a VRAM column: each byte is written at the destination whose low address byte then steps −32 (one row up) while the page byte stays fixed, and after the third the low byte advances +98 (0x62) to line up the next column, returning the advanced source and destination so columns can be threaded end to end. `blankTileColumns` [code] is the erase counterpart, stamping the blank tile 0x10 into three cells per column starting at loc_5193 (0x5193) with the same +98 column advance; a current asymmetry worth noting is that its per-row step is a full 16-bit subtract that can borrow into the page byte, whereas the draw primitive's row step stays inside the fixed page — the blank walk can cross a page boundary that the draw walk cannot. `redrawTileColumnsPeriodically` [code] drives both on a schedule keyed to two things: the running column tally DRAWN_COLUMN_COUNT (0x4241) and the frame counter loc_425f. With fewer than two columns counted it does nothing; otherwise it acts only on two phases of the low six bits of the frame counter — phase 0 wipes the columns via `blankTileColumns`, and phase 32 repaints them, drawing the first column from a source row in TILE_COLUMN_TABLE (0x039a) chosen by the frame counter's top two bits into the VRAM start at loc_5193, then the remaining columns from the continuation stream TILE_COLUMN_TABLE_CONT (0x03a6), each `drawTileColumnTriple` threading source and destination into the next.

**Per-frame screen fill and clear steps.** A cluster of sequence handlers walks a running cursor VRAM_WRITE_PTR (0x400b) down the screen, one row per frame, while ticking a dwell timer and, on its expiry, both stepping the top-level sequence index SEQUENCE_STATE (0x400a) and resetting a swath of object/sprite state. `primeVramFillAndAdvanceStep` [seen] is the setup step: it clears the 128-byte flag block at FLAG_BITS_BASE (0x4100) and the two status bytes loc_425f and loc_4224, points the write cursor two cells into the grid (0x5002), arms the dwell tier loc_4009 (0x4009) to 32 pages, and bumps SEQUENCE_STATE. `fillVramRowThenResetObjectState` [seen] then paints a 28-cell strip of tile 0x10 at the cursor each frame and advances it a full 32-cell row; when the dwell tier reaches zero it advances the sequence, re-arms the two-tier dwell cascade (loc_4008 = 64, loc_4009 = 4), clears the 48-byte active-object block at OBJ_ACTIVE_FLAG (0x4200), zeroes the screen-flip latches FLIP_SCREEN_X (0x7006) and FLIP_SCREEN_Y (0x7007) and the direction flag loc_4018, raises loc_4238, and reseeds the object-shadow field from the ROM template OBJ_SHADOW_RESEED_TEMPLATE (0x1db1). `blankVramRowThenResetSpriteState` [code] is the parallel clear step: each frame it clears the strided work-RAM table and blanks a 28-cell row of tile 0x10 at the cursor (stepping +32), and on dwell expiry advances the sequence, wipes the object-source block at SPRITE_SOURCE_OBJ_BASE (0x42b0, a full 256-byte clear) and the sprite shadow at SPRITE_SHADOW_BASE (0x4060, 64 bytes), re-arms the same two-tier dwell, reseeds the object shadow from ROM, and queues command word 6. `blankScreenRowsThenAdvanceSequence` [code] is the leaner progressive clear used by the play tables: it blanks a full 32-cell row of tile 0x10 at the cursor, advances +32, and ticks the phase counter loc_4009, only on the final phase advancing the sequence state and reseeding the object shadow.

**Projectile integration, rendering, and collision.** `advanceAndRenderProjectiles` [code] both moves and draws the seven moving-object records based at loc_4260 (0x4260). Each record holds two five-byte sub-slots, and the low bit of the frame counter loc_425f picks which sub-slot leads this frame — when it is clear the routine first bumps the leading slot's sub-position by two and starts on the second slot. For each of the seven, if the leading sub-slot is active it advances the sub-position (deactivating on overflow), integrates the 16-bit position by twice the signed velocity byte, and deactivates the slot when the position leaves the vertical window; deactivation zeros the active, sub-position, and high bytes. It then writes each sprite's Y and code into the sprite shadow at loc_4081 (0x4081), mirroring the Y by the direction flag loc_4018 and applying a ±1 code nudge to the first three records, before stepping past the leading sub-slot, bumping the trailing sub-slot, and moving to the next record and sprite entry. Collision is a separate pass. `flagProjectileHitOnPlayer` [code] is the per-entry box test: for an active entry it measures the entry's X against the player-X reference loc_4202 (0x4202) and its Y across a near/far band, and on overlap deactivates the entry and raises HIT_EVENT_FLAG (0x4204). `flagProjectileHitsOnPlayer` [code] is the loop that runs it — only when projectiles are enabled (OBJ_ACTIVE_FLAG bit 0 set) — over all fourteen five-byte entries from loc_4260, passing each the band delta 5 (the record stride the register happens to carry through the loop).

## Open questions

- The per-frame orchestration — the main loop and the top-level state dispatchers (the rst-28 handler and the
  jp(hl) dispatcher that select the sequence, formation, combat, and sound handlers each frame) — is translated
  but not yet idiomatically decompiled, so the way the handlers above are scheduled is inferred from the leaves
  they call, not yet read directly. Those dispatchers are the next spine to lift, and are what most of the
  remaining translated routines are reached through.
- Many handlers stay `[code]` because their state was not reached by the attract + coin/one-player captures (a
  deep formation/dive state, a later board), or because their only side effect lands in VRAM or a hardware latch
  the work-RAM tap cannot see; a deeper poke-cycle / video-visible capture is owed to lift them.
- Many work-RAM cells are still named `loc_<addr>`: their role is understood from the routines that touch them
  (described above) but a descriptive identifier is deferred to the cleanup phase rather than promoted piecemeal.
- A further tier of routines remains translated (not yet decompiled); the map grows to cover them as the spiral
  climbs.
