# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (the dispatcher spine and one register-thread caller)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each animated object on the tube is driven not by open-coded movement but by a small byte-coded **motion script**: a stream of one-byte opcodes and their operands laid out in the `loc_a0f7` table (with `loc_a0f8` being the very next byte, so a routine that reads `loc_a0f8[i]` picks up the operand that trails opcode slot `i`). A surrounding walk fetches the next script byte and hands control to one of the opcode handlers below; the handler mutates the engine's shared registers — the **rolling instruction pointer** `loc_10b` (`$010b`), the **branch/gate flag** `loc_10c` (`$010c`), and the currently selected object's per-slot cell `loc_298,x` (`$0298,x`) — and returns for the next fetch. All three are the persistent working state of one script pass; the handlers cooperate purely through them.

### Load opcodes — writing a value into the object's slot

Two opcodes advance the instruction pointer and deposit a byte into the active object's slot, differing only in how they source that byte. `loc_9bd0` [seen] is the **immediate load**: it forms `index = (loc_10b + 1) & 0xff`, writes that back to `loc_10b`, then copies the table byte `loc_a0f7[index]` straight into `loc_298,x`. It is exercised across the capture — the pointer bump at `$9bd0` and the slot store at `$9bd9` both fire, the store landing in the `$0298`-`$029e` slot range for whichever object index `x` is live. `loc_9bdd` [seen] is the **indirect load**: it likewise bumps `loc_10b` by one and uses the new value to fetch a table byte `loc_a0f7[idx]`, but treats that byte as a **zero-page address**, reading the live variable at `loc_00 + ptr` (`$0000 + ptr`) and copying *that* into `loc_298,x`. So `loc_9bd0` plants a constant chosen by the script, while `loc_9bdd` plants whatever the referenced zero-page cell currently holds — a variable coupling one object's motion to another live quantity. Its pointer advance at `$9bdd` and slot write at `$9bea` are both observed.

### Conditional opcodes — the gate flag gates flow

Two opcodes read the branch/gate flag `loc_10c` to decide whether to move the pointer. `loc_9bee` [seen] is a **skip-when-clear**: if `loc_10c` is nonzero it does nothing (the operand is consumed by falling through elsewhere), and only when the gate is clear does it step `loc_10b` forward by two — `loc_10b = (loc_10b + 2) & 0xff` — skipping a two-byte operand. Both increments at `$9bf3` and `$9bf6` are seen changing. `loc_9bfa` [seen] is a **conditional jump**: it first bumps `loc_10b` by one unconditionally (`(loc_10b + 1) & 0xff`), then, only while the gate `loc_10c` is clear, reloads the pointer from the operand — `loc_10b = loc_a0f7[loc_10b]` — redirecting the script to a new position. When the gate is set it leaves the pointer at the post-increment value and simply continues. The unconditional bump at `$9bfa` fires broadly and the table-reload write at `$9c08` fires on the taken branches.

### Unconditional flow and per-slot timing

`loc_9c17` [seen] is the **unconditional goto / state step**: it reloads `loc_10b = loc_a0f8[loc_10b]`, i.e. it replaces the current index with the byte the script places just past the current opcode, walking the script to its next scripted state. Its pointer reload at `$9c1d` is heavily exercised, the loaded index pulsing across a low range as scripts cycle through their states. `loc_9c0c` [seen] wraps that step with a **dwell timer**: it treats the object's own slot cell `loc_298,x` as a countdown, decrements it by one, and while it remains nonzero it hands directly to `loc_9c17` to take one state step and returns — so an object lingers in its current scripted state, ticking the state machine forward, for as many frames as the timer holds. Only when the timer reaches zero does `loc_9c0c` instead bump the shared counter `loc_10b` by one, releasing the script to move past the timed opcode. This timer path is heavily exercised.

### The walk-continuation flag

`loc_9bca` [seen] is a leaf that clears the continuation flag `loc_10a` to zero (`lda #0 / sta $010a`). The clear is observed firing frequently; `loc_10a` reads as a walk-continuation latch that a driver loop tests, but no decompiled routine reads it yet, so that role is inferred from the write alone.

### Test opcodes — producers of the gate flag (not observed here)

Two opcodes exist to *set* the branch flag `loc_10c` that the conditional opcodes above read, but neither's own store landed in the capture; during the captured window the gate value that `loc_9bee`/`loc_9bfa` consumed was produced elsewhere (a store at `$9e2b`), so both stay honestly tagged [code]. `loc_9c21` [code] is the **segment-boundary test**: for the active slot it reads the object's segment `loc_2b9,x` (`$02b9,x`), looks up that segment's boundary `loc_3ac[segment]` (`$03ac[seg]`, where a stored **zero reads as the maximum, 0xff**), compares it against the object's coordinate `loc_2df,x` (`$02df,x`), and sets `loc_10c = 1` when the boundary is at or beyond the coordinate (`bound >= position`), else `0` — a "has this object reached its lane's limit" query. Its store to `loc_10c` at `$9c3a` is absent from the trace, so it is not reached in the capture. `loc_9c3b` [code] is the **accumulator-phase test**: it derives the flag from the `loc_147`/`loc_148` (`$0147`/`$0148`) accumulator pair as `loc_10c = ((((loc_147 << 2) & 0xff) + loc_148) & loc_148 & 0x80) ^ 0x80`, which yields `0x00` when that resulting bit 7 is set and `0x80` when it is clear — a sign/phase probe of the accumulator. Its store to `loc_10c` at `$9c4e` is likewise absent, so it too is not reached in the capture.

### Packed-record skip

`loc_96c7` [code] is a register-only cursor advance used to step over a packed list record without reading it: entering at `loc_96c7` advances the cursor `y` by three (a single increment, then delegating to `loc_96c8` with `y` already bumped by one, which adds two more), while entering at `loc_96c8` advances `y` by only two. It performs no memory writes at all — there is nothing to observe — and it is reached only through the computed-jump table at `$969d` (via the `loc_9683` dispatch on `$015e`); it is not reached in the capture, consistent with its [code] tag.

## Vector coordinate lists and the display cursor

Tempest draws everything — the tube, the enemies, the score text — as a list of opcodes that the color vector generator reads out of display RAM in the `$2000-$2fff` window. Two independent pointers govern that traffic. One, the pair `loc_2c`/`loc_2d`, is a *read* pointer aimed at packed coordinate lists sitting in ROM; the routines below walk it to pull successive points out of a shape. The other, the pair `loc_74`/`loc_75`, is the *write* cursor into display RAM; a family of small emitters lay opcode words down at that cursor and then bump it forward. This section covers both pointers and the machinery hung off each.

### Selecting and seeding a coordinate list

`loc_9aee` [seen] arms the read pointer. Indexed by Y, it pulls the low byte of a list address from the ROM table at `loc_9b02` into `loc_2c` and the high byte from the parallel table at `loc_9afd` into `loc_2d`, then records the chosen index in `loc_2b` and reloads A from the holding cell `loc_29` before returning. All three of its stores were observed — the low byte settling to values such as `0x41`, the high byte to `0x07`, and the index into `loc_2b` — so it is grounded as the machine picking one of a set of coordinate lists by table index and pointing the walkers at it.

`loc_9a9d` [code] is the special-case seed of that same pointer for the fixed first list: rather than indexing, it takes the low byte straight from the base of the `loc_9b02` table, takes the high byte from the held source cell `loc_15d`, forces the index in `loc_2b` to zero, and reloads A from `loc_29`. Its writes do appear in the capture but the values it lays down are constant, so its role rests on the code rather than on any observed variation; the tag stays [code].

### Walking the coordinate list

Once `loc_2c`/`loc_2d` points at a list, three helpers step along it, each entered through the computed-jump vector generators that dispatch off the `$968f`/`$969d` tables.

`loc_96cb` [seen] is the inter-entry step. Through the `loc_2c`/`loc_2d` pointer it reads the entry under the cursor Y and its immediate predecessor at Y-1, stores their difference `cur - prev` at `loc_29` as the step delta, and then returns A = Y + delta while advancing Y to Y + delta + 2 — that is, the cursor jumps forward by the delta plus two. Its single own write, the delta into `loc_29`, was seen ranging across `0x01..0x0f`, real inter-entry steps drawn from the list, which is what grounds it. It is reached through the `$969d` dispatch.

`loc_96ab` [seen] is a re-indexing coordinate helper with two heads over a shared body. The body first stashes the incoming Y into the scratch cell `loc_29`, then computes a new offset by subtracting the list entry two positions back — `mem[ptr + (Y-2)]` through the `loc_2c` pointer — from an argument value and adding the stashed Y back in; it then re-indexes the list at that computed offset, returning the entry it lands on in A and the offset itself as the new Y. The `loc_96ab` head forms the argument from the stored list index as `((loc_2b - 1) & 0x0f) + 1`, wrapping the decremented index into a nibble; the alternate head `loc_96b7` uses the raw `loc_2b` instead; and the small sibling `loc_96c4` is the plain reader that just fetches `mem[ptr + Y]` with no arithmetic. The body's only own write is the Y-stash into `loc_29`, observed on essentially every pass, and its A/Y output feeds the `$968f`/`$969d` computed-jump vector-coordinate generator — enough to ground it [seen] as a reached compute helper.

`loc_96db` [code] resolves one list entry to an absolute coordinate: it reads the byte at `mem[ptr + Y]` through the `loc_2c`/`loc_2d` pointer, adds the base value held in `loc_160`, and returns the 8-bit sum in A. It performs no memory write of its own, so the write-tap has nothing to catch and its role rests entirely on the code; it is reached only through the `$968f` computed dispatch (via `loc_9677`). The tag stays [code].

### Advancing the display write cursor

`loc_df5f` [seen] is the one primitive that moves the display write cursor. It takes a stride in Y, forms `loc_74 + Y + 1` (the carry into the add is forced set, so the increment is always the stride *plus one*), stores the result back into `loc_74`, and on an 8-bit overflow increments the high byte `loc_75`. It is exercised on essentially every emit and heavily so; both its stores were observed pulsing — the low byte `loc_74` sweeping widely and `loc_75` climbing through the `0x25..0x2a` display-RAM pages — which is what grounds it. Every emitter below ends by calling it to step the cursor past the bytes it just wrote.

### Emitters that write through the cursor

`loc_df59` [seen] is the core word emitter: it stores the pair {A, X} at the cursor offsets Y and Y+1, then advances the cursor by Y+1 (which `loc_df5f` turns into Y+2). Its two stores were seen writing many rows of genuine vector data across `$2000-$2fff` with wide value ranges, so it is the role-defining opcode-pair write. Several draw sites jump straight into it.

`loc_df53` [seen] is a fixed-header producer built on that emitter's tail: it lays the constant word {`0x40`, `0x80`} at the cursor's first two bytes and then advances by two. Both header bytes were observed in the emit stream, including an adjacent `0x40`/`0x80` pair landing at `$224a`/`$224b`.

`loc_df19` [seen] appends a word chosen from a ROM word-table. It derives an index from the low nibble of A — with carry set and the nibble zero the index is 0, otherwise it is nibble + 1 — doubles it, reads the two bytes of `loc_31e4[idx]`, copies them to the cursor, and steps forward by two. Its stores were seen writing real AVG opcode bytes into the `$2000-$2fff` window.

`loc_df1f` [seen] is the thin index variant: it forms the index as `(A & 0x0f) + 1` and hands off to the same copy-and-advance tail (`loc_df24`) that `loc_df19` uses — read `loc_31e4[idx]`, write the two bytes at the cursor, advance. Its own arm does only arithmetic and leaves no write of its own, but it is grounded [seen] as a reached index helper by the shared emit stores.

`loc_c772` [seen] emits an object's position as an absolute point. Entering with the cursor offset at zero (`loc_c774` is the general form that takes a running offset), it lays a fixed {`0x40`, `0x80`} header word, then the point's X word taken from the zeropage pair at `loc_2`/`loc_3` indexed by X — the low byte written straight, the high byte masked to its low 5 bits — followed by the Y word from the pair at `loc_00`/`loc_1`, again low byte straight and high byte masked to 5 bits. As it goes it caches the four *raw* (unmasked) source bytes into `loc_6a` (Y low), `loc_6b` (Y high), `loc_6c` (X low) and `loc_6d` (X high) as the "previous point" anchor, then advances the cursor past the six bytes it wrote. It is a heavily reached producer, grounded on those observed writes.

`loc_aef8` [seen] emits a short run of text glyphs. It sets up a countdown — `loc_38` = A + 2 as the source index into the `loc_606` character buffer and `loc_39` = 2 as the iteration counter — snapshots the write cursor once, and then loops three times: each pass reads a character code from `loc_606[loc_38]`, replaces any code of `0x1e` or higher with `0x1a` (the clamp), doubles it to index the glyph word-table at `loc_31fa`, and copies that entry's two bytes into the display list; it decrements both the source index and the counter and continues while the counter stays non-negative. After the third glyph it advances the cursor past everything written. Its store into the display list was observed laying glyph words across the `$234a-$2b71` range with the high byte `0xa8` — the vector-draw opcode — confirming the text-emit role.

Taken together, the coordinate-list side (`loc_9aee`/`loc_9a9d` arming `loc_2c`/`loc_2d`, walked by `loc_96cb`/`loc_96ab`/`loc_96db`) supplies the geometry points, while the display-cursor side (`loc_74`/`loc_75` moved by `loc_df5f`, written through by `loc_df59`, `loc_df53`, `loc_df19`, `loc_df1f`, `loc_c772` and `loc_aef8`) turns those points and text codes into the opcode stream the vector generator scans out to the screen.

## Draw-pointer setup and vector emission

Everything Tempest puts on its vector monitor passes through this subsystem. The screen is refreshed from vector RAM in the 0x2000-0x2fff window: each drawn object is a run of two-byte words whose low byte carries a coordinate or count and whose high byte carries the vector-generator opcode field. The whole subsystem is organized around an indirect write cursor — the little-endian pointer pair `loc_74`/`loc_75` (with a running byte offset in `loc_a9`, or the Y index the emitters thread between calls) — plus two secondary cursors `loc_3b`/`loc_3c` and `loc_2a`/`loc_2b` used for text/glyph work. The routines here split into three jobs: aiming a cursor at the right record template, laying down glyph/digit runs, and laying down coordinate/delta records; a fourth cluster wraps those emitters for the perspective-projected tube objects.

### Aiming the draw cursor

`loc_b2be` is the per-subsystem draw-pointer setup [seen]. Given a selector in A it forms a two-byte stride `2*A` and reads a 16-bit pointer out of one of two ROM pointer tables, choosing `loc_ce68` when the per-index flag `loc_415`+A is nonzero and `loc_ce7a` when it is zero, then publishes that pointer into `loc_74`/`loc_75` and clears the status/offset cell `loc_a9`. Its low/high bytes were observed changing across a wide range as different subsystems were set up. `loc_b2de` is the same idea with two deliberate differences [seen]: it selects with the *opposite* polarity (`loc_ce7a` when the flag is nonzero, else `loc_ce68`) and publishes into the *text* cursor `loc_3b`/`loc_3c` rather than `loc_74`/`loc_75`, again clearing `loc_a9`; its published pointer bytes were seen taking real changing values. `loc_91b5` seats the third cursor [seen]: it doubles its selector into a word index, clears the paired flag byte `loc_29`, and copies the little-endian pointer at the in-page ROM table `loc_91c6` (low) / `loc_91c7` (high) into `loc_2a`/`loc_2b` — observed publishing the pointer 0x0540 and clearing `loc_29`.

`loc_b332` maintains the link between one draw record and the next [seen]. It first compares the live source byte `loc_cec4` against a checkpoint held at `loc_2000`; when they differ it latches the new value into `loc_2000` and returns carry set, the caller's signal that the frame changed and the list must be rebuilt. Otherwise it emits a two-byte word from `loc_ce9e`+x through the current `loc_74` cursor (x = 0x08 when `loc_415` is nonzero, else 0x02), clears `loc_16e`, then reloads `loc_74`/`loc_75` from `loc_ce68`+x so the cursor now points at the following record, returning carry clear. Both the emit and the pointer reload were observed with real changing values.

`loc_b84e` is a computed dispatcher over four draw-pointer targets `loc_b85f`, `loc_b875`, `loc_b888`, `loc_b896` [code]; the caller hands it Y as a byte offset (0, 2, 4, 6) selecting the entry, and it tail-returns that routine's result — so those targets, including the tail terminator `loc_b896`, are reached only through this dispatcher. `loc_b896` writes the terminating record for a vector list [code]: it stores the 16-bit cursor `loc_139`/`loc_13a` into vector RAM as `loc_2ffc` = low, `loc_2ffd` = high OR'd with 0x70, and `loc_2fff` = 0xc0 (the halt/return marker for the vector generator), then steps the cursor down by 0x20 with a 16-bit borrow into `loc_13a` and masks the low byte to 0x7f. This routine was not reached in the capture, so those five targets never took a value there. `loc_b944` swaps the two pointer pairs `loc_74`/`loc_75` with `loc_76`/`loc_77` so the shared cursor addresses the alternate structure [code], and `loc_b967` selects an (A, X) pair from ROM — `loc_ce87`/`loc_ce86` when `loc_415` is zero, else `loc_ce6f`/`loc_ce6e` [code]. Both belong to an object-draw path whose body did not execute in the capture (the selecting flag `loc_415` itself is exercised elsewhere, but neither routine's own body ran).

### Glyph and digit runs

Text and score digits are emitted as packed nibble runs against a ROM stroke/font table at `loc_31e4` (two bytes per glyph entry). `loc_dfb1` is the run driver [seen], reached extensively: it walks `loc_ae`+1 zeropage bytes from a top source index (`A + Y - 1`) downward, and for each byte emits its high nibble then its low nibble through `loc_df19`. It threads a carry the whole way so that only the final low nibble sees carry cleared — that cleared-carry nibble is how the run marks its own terminator. `loc_df19` maps a low nibble to a word-table index (0 when carry is set and the nibble is zero, otherwise nibble+1), copies that entry's two bytes from `loc_31e4` into the `loc_74` list, and steps the cursor past them.

The parallel path that builds into the dedicated text buffer at `loc_2f60` is `loc_a9fc` [seen]: it maps A's low nibble through the same beq/clc/bcs carry dance (y = nibble+1, or 0 for a zero nibble with carry set) to a byte from `loc_31e4` at index `2*y`, stores that **single** byte at `loc_2f60`+x, and advances x by two — so it writes one byte and leaves the odd slot at `loc_2f60`+x+1 untouched. Its stored bytes were observed taking real varying table values. `loc_a9d7` drives it [seen]: seeding a three-pass counter in `loc_2a` (2 down to 0, one pass per source byte) it reads each glyph byte through `loc_3b`/`loc_3c`, emits high then low nibble via `loc_a9fc`, and walks the source pointer `loc_3b` backward one byte each pass. Its own writes are only that loop state; the role output is the stroke bytes `loc_a9fc` lays down. `loc_a97f` sits above both [seen]: keyed by Y it lays a header entry OR'd with 0x70 (the head value is zeroed only when Y equals the marker `loc_3d` and `loc_5` bit7 is set, giving 0x70) into the `loc_2f60` buffer, fills six glyph slots (row count from `loc_48`+Y, one short at the marker; rows past the count use the alternate glyph `loc_3286` rather than `loc_3284`), then — unless state `loc_00` is 4 away from the marker, which returns early — seeds the glyph pointer `loc_3b` from `loc_a97d`+Y with `loc_3c` = 0 and hands off to `loc_a9d7`.

Three small callers wrap the run driver. `loc_af77` converts a byte to packed BCD through `loc_aaf5` (which writes the same BCD value into both `loc_29` and `loc_2c`, each ranging 0x00..0x99) and then emits the single byte `loc_29` as two nibble digits via `loc_dfb1` [code]. `loc_b0c6` selects a pointer by index through `loc_91b5` and then emits a three-byte run from `loc_29` [code]. `loc_aa9e` increments the slot index, publishes it into `loc_61`, and emits that one byte as a single-entry run [code]. None of these three took a role-defining own write in the capture; their effect rests on the emitters they drive.

### Coordinate and delta records

The main vector emitter is `loc_df59`/`loc_df5f` [seen]: `loc_df59` stores an {A, X} pair at cursor offsets Y and Y+1 and `loc_df5f` folds the offset back into the 16-bit `loc_74`/`loc_75` cursor (advancing by stride+1 with carry into the high byte). Many callers land here with real vector data. `loc_df92` emits a four-byte coordinate record through the cursor [seen]: byte 0 from `loc_2`+x, byte 1 from `loc_3`+x masked to 0x1f, byte 2 from `loc_0`+x, and a key-folded last byte `((loc_1+x XOR loc_73) & 0x1f) XOR loc_73`, handed to `loc_dfac`, which stores it at the next cursor slot and either advances the cursor or, if the slot index wrapped to zero, runs the terminating byte-run. `loc_df75` widens two inputs [seen]: it scales each by four with sign extension (low = v<<2, high = (signHi<<1) | (v>>6)&1) into the little-endian delta pairs `loc_6e`/`loc_6f` and `loc_70`/`loc_71`, then emits through `loc_df92`. `loc_df73` stashes a key byte into `loc_73` and then runs that scale-and-emit [code]. `loc_d8a9` stashes A into `loc_29`, scales the two coordinates via `loc_df75`, and emits that stashed byte as a one-entry run [code]. `loc_dd2b` stashes a byte into `loc_35`, scales via `loc_df75`, then shifts `loc_35` left MSB-first eight times (`loc_37` counting 7 down through borrow), emitting each bit as one vector digit via `loc_df1f` [code]. These last three took no role-defining own write in the capture and rest on the code.

Two producers snapshot object attributes into the working block before a delta emit. `loc_c43c` reads the slot index `loc_37` and copies that column of four parallel object tables — `loc_36a`→`loc_61`, `loc_35a`→`loc_62`, `loc_38a`→`loc_63`, `loc_37a`→`loc_64` — all observed changing [seen]. `loc_c423` does the same from a different table family — `loc_32a`→`loc_61`, `loc_31a`→`loc_62`, `loc_34a`→`loc_63`, `loc_33a`→`loc_64` — then drives `loc_c3ba` [seen]. `loc_c3ba` computes two 16-bit differences of the current block minus the previous (`loc_61`/`loc_62` − `loc_6a`/`loc_6b` into `loc_6e`/`loc_6f`; `loc_63`/`loc_64` − `loc_6c`/`loc_6d` into `loc_70`/`loc_71`), emits the record through `loc_df92`, then latches the current values into the previous slots `loc_6a`..`loc_6d` and sets the ready flag `loc_73` = 0xc0 [seen].

Two more producers write coordinate words directly through the `loc_74` cursor at the `loc_a9` offset. `loc_c66d` builds a lane-midpoint vertex [seen]: it takes slot `loc_38`'s two coordinate pairs and its wrap-around neighbour (`(loc_38 + 1) & 0x0f`), forms the round-up signed average of each pair into midpoints `loc_61`/`loc_62` and `loc_63`/`loc_64`, appends the four midpoint bytes through the pointer at the running cursor (each high byte masked to 0x1f), and mirrors all four into the scratch block `loc_6a`..`loc_6d`. `loc_c73c` emits two 16-bit differences at the running cursor [seen]: first `(loc_63:loc_64) − (loc_6c:loc_6d)`, then `(loc_61:loc_62) − (loc_6a:loc_6b)`; each difference's high byte is kept to five bits and the *second* one is additionally OR'd with 0xa0 (a vector-generator opcode), and the cursor `loc_a9` advances by four.

### Perspective-projected tube objects

The projected enemies and markers on the tube use a shared header/append sequence. `loc_c765` is an alternate entry that lays the fixed two-byte header {0x00, 0x71} at the cursor start and resumes the shared coordinate build from slot two [seen]; its header bytes were observed landing at thousands of distinct cursor addresses in the 0x2xxx display RAM. The append itself is `loc_bd3e` [seen], which turns a depth-scaled value into a (mantissa, exponent) pair. For a small input (`loc_57` < 0x10) it emits the trivial pair (mantissa byte 1, exponent 0); otherwise it drives the math coprocessor — writing the 16-bit difference `loc_57`−`loc_5f`/`loc_5b` into operands `loc_6095`/`loc_6096`, issuing with `loc_608c` = 0x18 and `loc_608e`/`loc_6094` = `loc_a0`, spinning on `loc_6040` bit7, reading results `loc_6060`/`loc_6070` into `loc_79`/`loc_7a` — then normalizes `loc_79` by a rotate loop that counts the mantissa shift into `loc_78` and folds the exponent. It stores the pair through the `loc_74` cursor at offset `loc_a9` (the exponent byte, then the shift count OR'd with 0x70) and returns the exit cursor `loc_a9 + 2`, which its callers thread onward.

`loc_c6c7` emits one enemy slot's vector entry [seen]. For an inactive slot (`loc_3ac`+x == 0) it appends four blank+0x71 pairs from the current cursor. For an active slot it seats `loc_57` from `loc_3ac`+x, clamps it toward the depth reference through `loc_c453`, seats `loc_56` from `loc_435`+x and `loc_58` from `loc_445`+x, runs the delta/coprocessor pass `loc_c098`, then emits the delta pair via `loc_c73c`. ## Enemy spawning and lane selection

Two pools feed the tube with attackers. A primary slot pool tracks the enemies climbing the well through a set of parallel per-slot arrays — depth `loc_2df`, segment index `loc_2b9`, successor/direction field `loc_2cc`, timer `loc_2a6`, and the two flag bytes `loc_28a` and `loc_283` — while a second array (`loc_2db`/`loc_2b5`/`loc_2c8`, counted by `loc_a6`) and a small eight-entry timed-object table (`loc_2fa`/`loc_302`/`loc_30a`/`loc_312`) hold what those enemies promote or decay into. ## Enemy motion and the pursuit AI

The enemies that climb the tube toward the rim are carried in a bank of sixteen slots, and one routine drives the whole bank once per frame. `loc_a618` [code] opens by copying the spawn budget `loc_10e` into the frame-active flag `loc_10d`, then walks the slots from index 0x0f down to 0. A slot is live when its whole-coordinate/active cell `loc_283,x` is nonzero; for each such slot it first integrates the slot's motion (`loc_a6a9`) and then decays that motion toward rest (`loc_a721`), and it stamps `loc_10d` to 0xff to record that something moved. A slot whose `loc_283,x` is zero is free, and while the countdown `loc_10e` is still nonzero the walk spawns a fresh enemy into it (`loc_a65b`). After the walk it settles the slot counter `loc_37` to 0xff, and on even frames only (`loc_3` bit 0 clear) with budget remaining it ticks `loc_10e` down by one. If the walk found nothing live and spawned nothing — `loc_10d` left at 0 — it raises the mode-request byte `loc_0` to 0x12, the signal that the wave is empty.

Motion integration lives in `loc_a6a9` [code]. It advances slot x along three parallel axes, each axis a signed 16-bit position built from a low fraction, a whole coordinate, and a low/whole velocity pair. Axis 0 folds velocity-low `loc_2e3,x` into fraction `loc_223,x` (keeping the carry), then adds that carry, the whole velocity `loc_343,x`, and the whole coordinate `loc_283,x`; axis 1 works `loc_2c3`/`loc_203`/`loc_323` into `loc_263`; axis 2 works `loc_303`/`loc_243`/`loc_363` into `loc_2a3`. Each axis is clamped to the tube ring: when the whole velocity's sign bit is set (a falling axis) an overflow is a result below 0x10, and otherwise (a rising axis) an overflow is a result at or above 0xf0. Axis 0's new whole is the routine's carried-out value, and it is forced to 0 if any of the three axes overflowed the ring; that forced value is written back to `loc_283,x`. Because `loc_283,x` is the very cell `loc_a618` reads to decide liveness, an axis that runs off the ring end zeroes the slot and so retires that enemy. Axes 1 and 2 write their new wholes to `loc_263,x` and `loc_2a3,x` unconditionally.

The decay pass is `loc_a721` [code], which seeds the saturation counter `loc_29` to 0xfd and steps each of the three axis velocities one increment toward zero through `loc_a75d`, storing the returned low and whole back into `loc_2c3`/`loc_323`, `loc_2e3`/`loc_343`, and `loc_303`/`loc_363` in turn. If all three axes saturated — the counter, bumped once per saturating axis, wraps from 0xfd through 0x100 to 0 — it clears the slot's whole coordinate `loc_283,x` to 0x00, again retiring the slot. The per-axis worker `loc_a75d` [code] is not reached in the capture; from the code it pulls the fixed increment `loc_a788` (0x20) and, treating the incoming whole/low as a signed 16-bit value, adds 0x20 when the whole is negative or subtracts 0x20 otherwise. On crossing zero (a carry or borrow out of the 16-bit result) it snaps both bytes to zero and increments the saturation counter `loc_29`; along the way it stashes the incoming whole in `loc_2b` and the resulting low in `loc_2a`.

Spawning into a free slot is `loc_a65b` [code], which did not run in this capture. It marks the slot active by writing 0x80 into the three state bytes `loc_263,x`, `loc_283,x`, and `loc_2a3,x`, then fills the three velocity pairs from the random sources `loc_60da` and `loc_60ca`: the low bytes take the raw random value and the whole bytes take a signed random step from `loc_a69b`, with the middle axis's step forced non-positive (negated if it came back positive). It closes by handing the slot to the sound cue `loc_ccc1`. The signed-step helper `loc_a69b` [code] is a pure compute leaf — it never writes memory, so it can never appear in a write trace — that reads a 3-bit random magnitude (`loc_60da & 0x07`, giving 0..7) and negates it when the incoming value's bit 0 is set, yielding a nudge in [-7, +7].

The pursuit logic that steers the player's aim and the enemies' rim travel turns on a shared reference segment held in `loc_200`. `loc_97c5` [seen], the auto-aim step, scans the per-slot depth table `loc_2df` from index `loc_11c` downward for the smallest nonzero entry — the nearest object in the tube — keeping that minimum in `loc_29` and its slot index in `loc_2a` (both preset to 0xff to mean "none"). If nothing nonzero is found it returns the last entry it saw; otherwise it takes that slot's segment `loc_2b9[idx]`, differences it against the player reference `loc_200` through `loc_a7a6`, and returns a rotational direction code by the sign of that difference: 0x00 when aligned, 0x09 when the target sits negative, 0xf7 when positive. Its caller `loc_9749` consumes that code as the spinner delta, so the player's claw is nudged toward the nearest enemy's lane. The difference engine `loc_a7a6` [seen] is heavily exercised: it computes A minus Y, stashes the raw result in `loc_2a`, and then — gated on flag `loc_111`'s high bit — either keeps the full signed byte or masks to the low nibble and sign-extends bit 3 into a signed byte, which folds a wrap-around segment distance onto a short tube's segment count.

Two routines apply that same reference to the enemies' choice of which way to walk the rim. `loc_9d67` [code] fetches slot x's target segment `loc_2b9,x`, differences the reference `loc_200` against it through `loc_a7a6`, and records the side the target lies on in bit 6 of the slot flag `loc_283,x`: it clears bit 6 when the difference's top bit is set and sets bit 6 otherwise. The direction bit itself is toggled in place by `loc_9c4f` [seen] — an exclusive-or of 0x40 against `loc_283,x`, written back and returned — and this bit-6 flip of `loc_283` is observed changing in the capture; its callers (`loc_9f81`'s per-slot segment-flag step, and `loc_9d06`) read bit 6 of `loc_283,x` as the flip/travel-direction flag of an enemy walking the rim. The heavier per-slot step is `loc_9d06` [seen]: it stashes the shared byte `loc_202` into the slot's depth cell `loc_2df,x`, then branches on the slot's kind. A kind-1 slot (low three bits of `loc_283,x` equal to 1) with the gate byte `loc_3ab` nonzero simply flips bit 7 of `loc_28a,x` and stops; a slot whose flag has its top bit set just bumps its stashed depth `loc_2df,x` by one and stops. Otherwise it decrements `loc_108`, and when `loc_109` equals 1 it scans slots 6..0 for a non-empty, non-self entry whose stashed byte matches the shared one, recording the survivor index in `loc_38` and copying that slot's bit 6 (inverted) into `loc_283,x`; when `loc_109` is anything else it defers to `loc_9d67` to set the side bit from the reference. It finishes by writing 0x41 to `loc_10b` and incrementing `loc_109`. This is the settle step for a tube object whose climbing depth has reached the shared target `loc_202`, reached from `loc_9c58`.

The rim-object dispatch and its pacing sit in a small cluster. `loc_c9af` [seen], reached through a computed jump rather than a textual call, clears `loc_4`, decrements the active slot's countdown `loc_48,x` (x from `loc_3d`), and when the `loc_48`/`loc_49` pair is fully spent finalizes through `loc_c9f1`. ## The mathbox: projection and level tables

The tube geometry that Tempest draws in perspective is computed by a hardware math coprocessor — the "mathbox" — that the 6502 drives through a block of memory-mapped registers around `loc_6080`. The CPU loads signed operands into the input registers, sets a control byte, spins until the busy flag clears, and reads the scaled result back out. This subsystem wraps that coprocessor in a projection driver, then uses it to turn each level's packed ROM shape tables into the concrete per-lane screen coordinates the vector generator consumes.

**Priming the coprocessor.** `loc_c1c3` [seen] clears the work area before a projection run. It zeroes the zero-page accumulator scratch (`loc_81`, `loc_91`, `loc_80`, `loc_78`, `loc_90`, `loc_88`) and then the mathbox input block — `loc_6080`, `loc_6081`, `loc_6083`, `loc_6084`, `loc_6085`, `loc_6086`, `loc_6087`, `loc_6089`, `loc_608d`, `loc_608e`, `loc_608f`, `loc_6090` — before writing the control register `loc_608c` to `0x0f`. Note that it deliberately leaves `loc_6082`, `loc_6088`, `loc_608a`, and `loc_608b` untouched; only the listed subset is cleared. It runs on essentially every projection pass. A grounding caveat applies here: because the target cells were already zero throughout the capture, every observed write was a constant `0->0` transition (and `loc_608c` `0xf->0xf`), so the routine's clearing effect is confirmed present at all its write sites but was never seen changing a nonzero cell to zero.

**The projection driver.** `loc_c098` [seen] is the point projector — it feeds a signed X/Y delta through the coprocessor and folds the scaled results into two 16-bit accumulators. It first forms the 16-bit difference of `loc_57 - loc_5f` (low) with `loc_5b` supplying the high borrow, storing the pair to `loc_6095`/`loc_6096`; if that difference comes out negative (high byte bit 7 set) it clamps the whole value up to `+1` (`loc_6096=0x00`, `loc_6095=0x01`). It then computes the absolute horizontal magnitude `|loc_58 - loc_60|` with its sign captured in `loc_33` (`0x00`/`0xff`) and the absolute vertical magnitude `|loc_56 - loc_5e|` into `loc_32` with sign `loc_34`. The horizontal magnitude is issued to the coprocessor via `loc_608e`/`loc_6094`, and the routine spins while `loc_6040` bit 7 stays set (the coprocessor-busy flag). When the first result is ready it reads `loc_6060`/`loc_6070` into `loc_63`/`loc_64`, re-issues the vertical magnitude `loc_32` through `loc_608e`/`loc_6094`, and — gated by the horizontal sign in `loc_33` — either subtracts or adds the offset pair `loc_68`/`loc_69` into `loc_63`/`loc_64`, saturating at `0x8000` on overflow (subtract) or `0x7fff` (add). After a second busy-wait it reads the next result into `loc_61`/`loc_62` and, gated by the vertical sign in `loc_34`, folds the offset pair `loc_66`/`loc_67` into `loc_61`/`loc_62` with the same saturation. The two accumulators `loc_63`/`loc_64` and `loc_61`/`loc_62` are the projected point handed back to the caller.

**Snapping an operand to a reference.** `loc_c453` [seen] conditions one of the projection operands before it is used. Guarded off entirely when `loc_5b` is nonzero, and skipped when `loc_57` already sits `0x0c` or more above the reference `loc_5f`, it otherwise snaps `loc_57` up to `loc_5f + 0x0f`, capped at a ceiling of `0xf0`. The role write was seen as a large upward jump of `loc_57` (e.g. `0x14 -> 0xe7`), and `loc_57` was independently observed pulsing across a wide range. Its callers feed it the same `loc_57`/`loc_5b`/`loc_5f` operands that go into the projection driver.

**Projecting a whole tube's lanes.** `loc_c473` [seen] drives `loc_c098` sixteen times to lay down the on-screen coordinates for every lane of the current tube. Seeded with an incoming reference in `loc_57` and a write index in `loc_38`, and clearing a clamp tally in `loc_59`, it walks a column counter `loc_37` from `0x0f` down to `0` (breaking when it underflows past zero). Each pass loads that lane's base coordinates from `loc_3ce + col` into `loc_56` and `loc_3de + col` into `loc_58`, runs the projection driver, then clamps each of the two projected signed pairs into the window `[-4..+3]` (i.e. `0xfc..0x03`): a value below `0xfc` pins to `0xfc` with sign `0x01`, a value at or above `0x04` pins to `0x03` with sign `0xff`, and any clamp bumps `loc_59`. The clamped value/sign for the first pair (`loc_62`/`loc_61`) is written to `loc_31a + out`/`loc_32a + out` and for the second pair (`loc_64`/`loc_63`) to `loc_33a + out`/`loc_34a + out`, both indexed by the decrementing `loc_38`. It returns the accumulated clamp count in `loc_59`. This is heavily exercised — it is the per-frame producer of the tube's projected lane geometry.

**Unpacking the per-level nibble tables.** `loc_c196` [seen] turns the selected level into four small tables of shape/colour parameters. It clamps the selector `loc_9f & 0x70` to at most `0x5f`, forms an index `x = (sel >> 1) | 0x07`, and for `y` running `7` down to `0` reads the packed ROM byte at `loc_c1fd + x`, splitting it: the low nibble goes to both `loc_19 + y` and its display mirror `loc_800 + y`, and the high nibble to both `loc_21 + y` and mirror `loc_808 + y`. A single pass fills all four tables with real, varying values.

**The level-table loader.** `loc_b888` [code] is the level-setup entry that rebuilds those tables and then arms the vector list's tail. It runs `loc_c196` to unpack the per-level shape/colour tables, then seats the two-byte vector-tail cursor by writing `loc_139 = 0x7f` and `loc_13a = 0x04`. This routine was not reached in the capture, so its own writes at `loc_139`/`loc_13a` were never observed firing; no direct caller was found, so it is most likely reached only through a computed-dispatch/jump-table target — its tag stays [code].

**Packing a table byte.** `loc_c2e8` [seen] reduces an input value into a packed table byte. Any value of `0x62` or greater is replaced by a masked hardware byte, `loc_60ca & 0x5f` (a random/timer fallback). It then splits the value into a quotient `v >> 4` and remainder `v & 0x0f`, looks the remainder up in the ROM table at `loc_bc7c + remainder`, stores that entry to `loc_112`, and returns the packed byte `(entry << 4) | 0x0f` — table entry in the high nibble, low nibble forced to `0xf` — along with the quotient in X and remainder in Y. Its store to `loc_112` was observed.

**Building the tube's lane coordinates.** `loc_c235` [seen] assembles the current level's full per-lane tube geometry, once per level setup. It first reduces the selected slot by running `loc_c2e8` on `loc_46 + loc_3d`, taking the returned packed byte as a seed and the stored table entry from `loc_112` as the index `y`. From the ROM level tables it derives the span operands: `loc_bc8c + y` is negated into both `loc_5f` and `loc_5d`, `loc_a0` is set to `0x10` minus that value, `loc_5b` is set to `0xff`, `loc_60` takes `loc_bc9c + y`, and `loc_111` takes `loc_bccc + y`. The offset pair is then formed one of two ways: when `loc_2` equals `0x1e` it copies `loc_bcac + y`/`loc_bcbc + y` straight into `loc_68`/`loc_69`; otherwise it forms the signed 16-bit difference `{loc_bcbc:loc_bcac} - {loc_69:loc_68}`, shifts it right four times keeping the low byte, and stores that into the level geometry scale `loc_121`. It then clears the running offset accumulators `loc_66`, `loc_67`, `loc_10f`, `loc_110` and sets `loc_113 = 0x2c`. Two loops finish the geometry: the first walks `x` from `0x0f` down to `0`, seeding each column's base-coordinate tables `loc_3ce + x` from `loc_b97c + ny` and `loc_3de + x` from `loc_ba7c + ny`, zeroing the projected-output arrays `loc_31a + x`/`loc_33a + x`/`loc_39a + x`, and filling `loc_3ee + x` from `loc_bb7c + ny`, with the neighbour index `ny` walking down from the seed. The second loop rounding-averages each column with its wrapping next neighbour (`(x + 1) & 0x0f`) — adding the two bytes plus one and rotating right, carrying the ninth bit into bit 7 — into the neighbour-midpoint tables `loc_435 + x` (from the `loc_3ce` base) and `loc_445 + x` (from the `loc_3de` base). The base tables `loc_3ce`/`loc_3de`, the midpoint tables `loc_435`/`loc_445`, and the scale `loc_121` were all observed filled with symmetric tube-vertex coordinates.

**A mode flag and scale byte.** `loc_ca48` [seen] produces a flag bit and a paired scale value from two gates. By default it chooses `(a, y) = (0x00, 0x10)`; only when both `loc_117` and `loc_3d` are nonzero does it switch to `(0x04, 0x08)`. It then folds bit 2 of the chosen `a` into flag `loc_a1`, preserving every other bit, and stores `y` to the scale byte `loc_b4`. Both role writes were observed, but only the default branch was exercised in the capture — `loc_a1` was seen written with bit 2 staying clear, and the alternate `a = 0x04` path (both gates open) did not fire — so while the routine's write sites are confirmed, the alternate-scale behaviour is supported by the code but not by an observed transition.

## Sound, POKEY and the interrupt heartbeat

Two of this subsystem's routines run on every interrupt, back to back: the counter/accumulator stepper `loc_cf24` and then the sound-voice engine `loc_cd0a`. Both are reached from the machine's interrupt handler at `loc_d704` (that handler saves the registers, kicks the watchdog, folds coin/switch bits, then calls `loc_cf24` immediately followed by `loc_cd0a` before advancing its own frame/timer cascades and returning). Everything else in this section either feeds those two — the sound-request registrar and its family of fixed-id triggers, the POKEY reset — or sits adjacent to them touching the same hardware page.

### The three gated lane counters — `loc_cf24` [seen]

On each interrupt `loc_cf24` walks three parallel lanes indexed `x = 2,1,0`, each armed by one bit of control byte `loc_8`: lane `x=2` by bit0, lane `x=1` by bit1, lane `x=0` by bit2 (the routine shifts `loc_8` right once, twice, or three times respectively and tests the shifted-out carry). For each armed lane it advances a position byte `loc_d + x` (that is `$0d`, `$0e`, `$0f`), masking it to five bits and, on wrap, either advancing/blanking it or reloading `0x1f`; the wrap path also reloads the per-lane timer `loc_10 + x` with `0x78` and, when the timer expires, folds a small step (derived from bits of `loc_9`) into a running pair of accumulators `loc_16`/`loc_17` and bumps the per-lane counter `loc_13 + x`. A later block subtracts a `loc_cfd9`-table threshold from `loc_16`, carrying overflow into `loc_18` and occasionally into `loc_6`. The position write at `$0d/$0e/$0f`, the timer at `$10`, and the counter at `$13` are all observed changing, grounding this as the exercised per-interrupt stepper.

Its two tail passes over the `loc_13` lane triple are distinct and must not be conflated: the **first** pass (block `b_d00d`) is gated on the entry being `>= 0x10` and subtracts `0x10` (it adds `0xef` with carry already set); the **second** pass (block `b_d022`) is gated on the entry being nonzero and subtracts `0x11` (it adds `0xef` with carry clear). The routine also carries an unreachable-state guard that throws if it ever runs off the end into the embedded data table.

### The per-frame voice engine to POKEY — `loc_cd0a` [seen]

`loc_cd0a` is the sound engine's per-interrupt tick. It sweeps 16 voice slots `x = 0x0f..0`, skipping any slot whose value byte `loc_c0 + x` is zero (idle) or whose index equals the reserved-slot pointer `loc_bf`. For a live slot it counts down a fast timer `loc_e0 + x`; only when that reaches zero does it count down the slow timer `loc_f0 + x`. If the slow timer is still running it takes a single animation step — choosing the high-half tables `loc_cccc`/`loc_cccd` or the low-half tables `loc_cbcc`/`loc_cbcd` by the sign bit of the current value, reloading the fast timer and folding the table byte into the slot's level `loc_d0 + x` (odd slots preserve the prior high nibble of that level byte). If both timers have expired it walks the frame index `loc_c0 + x` forward (in steps of two) through the `loc_cbcb`/`loc_cbce` or `loc_cccb`/`loc_ccce` tables until a nonzero frame lands. Finally it publishes the slot's level byte `loc_d0 + x` to a POKEY audio register: slots `0..7` write `loc_60c0 + x` (POKEY 1's eight audio registers `$60c0-$60c7`), slots `8..15` write `loc_60c8 + x` (landing in POKEY 2's `$60d0-$60d7`). The POKEY writes are observed, grounding it as the routine that actually drives sound to the hardware.

### The sound registrar and its enable gate — `loc_ccc7` [seen], `loc_ccc3` [code]

`loc_ccc7` is where a sound request becomes a set of claimed voice slots. It first stashes the caller's X and Y into `loc_31`/`loc_32`, then takes the sound id in A and walks 16 channel slots `x = 0x0f..0`, reading one byte per slot from the ROM row `loc_cb01` indexed by a descending id. Each **nonzero** row byte claims that slot: it points `loc_bf` at the slot, stamps the row byte into the value table `loc_c0 + slot`, arms both live-timer flags `loc_e0 + slot = 1` and `loc_f0 + slot = 1`, then restores `loc_bf` to its `0xff` sentinel. The slot-pointer, value-table, and timer-flag writes are all observed with real, varying data, so this registrar is heavily exercised — it is the producer that `loc_cd0a` later drains. On exit it restores X/Y from `loc_31`/`loc_32`.

Most sound requests reach `loc_ccc7` through the enable gate `loc_ccc3`, which tests bit7 of flag `loc_5` and simply returns without registering anything when that bit is clear, otherwise passing the id (and caller X/Y) straight through. The gate carries no own memory write, so a write-tap cannot witness its own vectoring; it is tagged [code], while its downstream registrar `loc_ccc7` is [seen].

### The fixed-id sound triggers [code]

A family of thin trampolines each load one constant sound id and hand it to the gate `loc_ccc3` (and so to `loc_ccc7`): `loc_ccb5` fires id `0x0f`, `loc_ccc1` id `0x1f`, `loc_ccea` id `0x2f`, `loc_cd02` id `0x3f`, `loc_ccb9` id `0x4f`, `loc_ccb0` id `0x5f`, `loc_ccee` id `0x6f`, `loc_ccf2` id `0x7f`, `loc_ccbd` id `0x8f`, `loc_ccf6` id `0x9f`, `loc_ccfe` id `0xbf`, and `loc_cd06` id `0xcf`; most preserve the caller's X/Y through the gate. Distinct from these, `loc_ccfa` loads id `0xaf` and calls the registrar `loc_ccc7` **directly**, bypassing the `loc_5` enable gate entirely — so this one cue is registered unconditionally. Each trampoline is a fixed-id call site with no own memory write, so a write-tap cannot attribute an individual trampoline's firing; all are tagged [code], while the shared `loc_ccc7` they funnel into is [seen]. Which in-game event each id denotes is not settled here — the routines are named by the id they queue, not by a confirmed effect.

### Dual-POKEY reset and RANDOM self-test — `loc_cd95` [seen]

`loc_cd95` is a textbook dual-POKEY (re)initialisation. It first clears the SKCTL registers `loc_60cf`/`loc_60df` and the latch `loc_720`, then samples the two POKEY RANDOM registers `loc_60ca` (POKEY 1) and `loc_60da` (POKEY 2) across a five-iteration poll, latching the first sample into `loc_720` the moment either register is seen to change — a liveness self-test of the noise generators. It then writes the canonical SKCTL init value `7` to `loc_60cf`/`loc_60df`, zeroes the eight audio registers of each POKEY (`loc_60c0 + x` and `loc_60d0 + x` for `x = 7..0`) alongside the mirror value/level tables `loc_c0 + x`/`loc_d0 + x`, and finally clears both AUDCTL registers `loc_60c8`/`loc_60d8`. All of these writes are observed, grounding it as the actual reset path.

### Option switches into game config — `loc_d6bb` [seen], `loc_dbe0` [code]

`loc_d6bb` reads the option/DIP inputs and turns them into configuration cells. From input port `loc_e00` it slices three fields through ROM lookup tables — bits 5-3 via `loc_d6f7` into `loc_156`, bits 7-6 via `loc_d6ff` into `loc_158`, and bits 2-1 via the `loc_d6b3`/`loc_d6b4` pair into `loc_ac`/`loc_ad` — mirroring the raw port into `loc_a`. It also reads the coin/switch port `loc_d00`, stores it XOR `0x02` into `loc_9`, and folds the `loc_ad` result through `loc_dbe0`, recording the merged nibble in `loc_16a`. These writes are observed, grounding the decode.

`loc_dbe0` is the small bit-packer `loc_d6bb` finishes with. It stores its incoming A into POKEY-page cell `loc_60db`, copies the low three bits of `loc_60d8` into scratch `loc_37` **and** into `loc_60cb`, and **returns** those three bits merged with one relocated bit — bit5 of `loc_60c8`, shifted down two places into bit3 (`(loc_60c8 & 0x20) >> 2`). The mirrored value written to `loc_37`/`loc_60cb` is only the low three bits; the extra relocated bit rides on the return value alone. It is reached, but every observed write was a constant in the capture, so the packing role itself was not exercised — tagged [code].

### Math-coprocessor query helper — `loc_dce6` [code]

Grouped here by its POKEY-adjacent page but functionally a math-box query, `loc_dce6` primes the coprocessor's operand and count registers (`loc_608e = A`, `loc_608f = X`, count `loc_608c`/`loc_6094 = 0x10`, clearing `loc_73`/`loc_414`/`loc_6090`), kicks it off, then scans a 16-step window of the status port `loc_6040` for the first slot with its high (busy) bit clear and hands back that slot's result pair `loc_6060` (low → A) / `loc_6070` (high → Y), or exits with the counter run past the end. It is not reached in the capture — tagged [code].

### Channel-record sort and slot pacing — `loc_ac3f` [seen], `loc_ad6e` [code]

`loc_ac3f` maintains a set of ordered channel records and derives a request from them. It clears bit6 of `loc_5`, optionally pre-clears the six-byte staging block `$40-$45` via `loc_ca62` when `(loc_9 & 0x43) == 0x40`, queues an EAROM request through `loc_ddfb`, and zeroes `loc_601`. It then processes one channel at a time (channel `0` when `loc_3e`==0, else channel `3`), seeding the key triple `loc_2c`/`loc_2d`/`loc_2e` from `loc_42`/`loc_41`/`loc_40 + channel` and bubble-sorting the stored row tables `loc_620`/`loc_61f`/`loc_61e` (with the parallel payload rows `loc_51e`/`loc_51f`/`loc_520`) into lexicographic order, counting the settling passes in `loc_605` and recording that count per channel into `loc_600 + channel`. After both channels it nudges the running total `loc_601` (bumped when it is `>= loc_600` and below `0x63`), then derives the packed request byte `loc_603` from flag `loc_3d` — `request = ((flag ^ 0x01) << 2) | flag`, then `+ 0x05 + ((flag >> 6) & 1)` — and hands off to the request walker `loc_ad22`. The pass counter climb, the per-channel store, and the sorted rows are observed, so the sort machinery is grounded [seen]; its precise game-vocabulary role (what these channel records ultimately represent) is not settled from the code alone.

`loc_ad6e` is the per-frame tick of the active slot that `loc_ad22` arms. It seeds `loc_1 = 0x06`; when `(loc_3 & 0x1f) == 0` it counts down `loc_605`, and on that countdown reaching zero it forces `loc_00 = 0x14` and returns. Otherwise it clamps the active slot's value `loc_606 + loc_602` through `loc_adce` to its rails (a positive result `>= 0x1b` snaps to `0`, a negative result snaps to `0x1a`), gates on bits 3-4 of mode byte `loc_4e` (masking `loc_4e` down to `& 0x67`), and steps the two counters `loc_602` and `loc_604`; when the `loc_604` step underflows negative it re-arms via `loc_ad22` unconditionally, and additionally via `loc_ddf7` only when `loc_600 + loc_3d < 4`, and otherwise clears the retired slot `loc_606 + (slot-1)`. None of these paths fired — the routine is not reached in the capture, so it is tagged [code] and read from the code alone.

## The EAROM high-score store

Tempest keeps its high-score table (and the initials entered against it) in a small serial NVRAM — the ER-2055 EAROM — that survives power-off, per the outside-in note that the table "persists across power-off." This subsystem is split in two: a lightweight request layer that stamps a small block of zero-page-adjacent flag bytes to say *which* regions of that store want servicing and in which direction, and a single bit-serial state machine, `loc_de1b`, that actually walks the EAROM port block one byte at a time to move data in or out.

### The request queue and its setters

Three flag cells form the queue that the state machine consumes. `loc_1c7` is the request-pending bitmask — each set bit marks one region of the store as wanting service. `loc_1c8` is the parallel direction bitmask, where a set bit for a region means *write out* and a clear bit means *read in*. `loc_1c6` is the blank/index byte: when it is nonzero the write path zeroes each source cell before latching it, so the region is erased (zeros pushed to the EAROM) rather than saved.

The setters all converge on one shared tail: it stores its index argument into `loc_1c6` and ORs its mask argument into *both* `loc_1c7` and `loc_1c8`. Because the mask is folded into the direction byte as well as the request byte, every one of these merge-family setters queues a **write** for the regions it names; only `loc_de11` (below) queues reads.

- **`loc_ddf1`** [code] is the fixed "save every block" entry: it forces index `0xff` into `loc_1c6` and ORs `0x07` into both `loc_1c7` and `loc_1c8`, i.e. all three regions, write direction, blank mode — a save-and-clear of the whole table. The shared request cells `loc_1c7`/`loc_1c8` are seen changing during the capture, but only through the mask-`0x04` entry below; the particular values this routine writes (index `0xff`, mask `0x07`) were never observed, so its own all-blocks path rests on the code.
- **`loc_ddfb`** [seen] supplies mask `0x04` with a zeroed index, then runs the shared tail — a write request for the single region whose bit is `0x04`, without blanking. Its writes into `loc_1c7`/`loc_1c8` (value `0x04`) are the observed exercising of the merge tail. Its two internal entry points let a caller either accept the fixed mask `0x04`, hand in an arbitrary mask against a zeroed index, or drive the tail directly with both mask and index chosen by the caller.
- **`loc_ddf3`** [code] forces the index byte to `0xff` and runs the tail with a caller-supplied mask, i.e. it requests that the named regions be written out in blank (erase) mode. Its `0xff`-index path was not seen in the capture.
- **`loc_ddf7`** [code] supplies the constant mask `0x03` against a zeroed index — a save request for the two low regions. The merge cells were only observed taking value `0x04`, never `0x03`, so this mask-3 path is not reached in the capture.
- **`loc_dde9`** [code] is the thinnest of these: it hands mask `0x04` into the blank-mode (`loc_ddf3`) path, requesting region `0x04` be written out with its source cleared. Its blank-index-`0xff` variant of region 4 was not observed and rests on the code.

### Seeding a full read

**`loc_de11`** [seen] is the counterpart initiator on the read side. Rather than ORing bits, it *sets* `loc_1c7` outright to `0x07` (all three regions) and clears `loc_1c8` to `0x00`, so every region's direction bit is clear — a request to **load** all three high-score blocks from the EAROM — and then falls straight through into `loc_de1b` to run the walk. Both of its own writes (`loc_1c7 = 0x07`, `loc_1c8 = 0x00`) are observed, which distinguishes it as the mode-7 read initiator; the surrounding startup guard `loc_db5a` [code] reaches it only when the store is idle (both `loc_1ca` and `loc_1c7` clear).

### The transfer state machine

**`loc_de1b`** [seen] is the EAROM transfer engine, and it is heavily exercised — reached on essentially every service pass. It drives its work through a run of zero-page cells (`loc_1ca` the mode/phase byte, `loc_1cb` the byte cursor, `loc_1cc` the port offset, `loc_1cd` the region limit, `loc_1ce` the walking-bit mask, `loc_1cf` the running checksum, `loc_1c9` the load-failure flags) and a row pointer held in `loc_bd`/`loc_be`, and it talks to the EAROM through the port block at `loc_6000` (address/data latch, offset by the cursor), `loc_6040` (the control-strobe port) and `loc_6050` (the read-back data port).

**Picking a region.** When the mode byte `loc_1ca` is `0` and there is a pending request (`loc_1c7 != 0`), the machine starts a fresh region. It clears the byte cursor `loc_1cb`, the checksum `loc_1cf` and the mask `loc_1ce`, then rebuilds `loc_1ce` as a single walking bit by rotating it rightward while shifting `loc_1c7` leftward until a set bit falls out of the top — so it isolates the **highest** set request bit and leaves the count of shifts in a temporary that it doubles to index the parameter tables. The chosen region's direction is read as `(loc_1ce & loc_1c8) != 0 ? 0x80 : 0x20` and stamped into `loc_1ca` (write phase begins at `0x80`, read phase at `0x20`). The serviced bit is then cleared from the request word via `loc_1c7 = loc_1ce ^ loc_1c7`. Finally the four parallel per-region parameter arrays are read at the doubled index: `loc_1cc` (the starting port offset) from `loc_dddd`, `loc_1cd` (the ending/limit offset) from `loc_ddde`, and the RAM row pointer low/high (`loc_bd` from `loc_dde3`, `loc_be` from `loc_dde4`).

**Per-pass work.** Each pass first drops the control port `loc_6040` to `0`; if the mode byte is now clear the machine returns. Otherwise it shifts the mode byte left to select a sub-phase:

- *Address/command phase* (mode `0x80`, top bit set): it latches the shifted mode value at `loc_6000 + cursor`, advances the mode to `0x40`, and raises `loc_6040` to `0x0e` before returning to let the EAROM settle.
- *Write-data phase* (mode `0x40`): it sets the mode to `0x80` for the next entry; if the blank byte `loc_1c6` is nonzero it zeros the source RAM cell first, then reads the byte through the row pointer. When the cursor has reached the region limit `loc_1cd` it retires the mode (`loc_1ca = 0`) and substitutes the running checksum `loc_1cf` as the final byte — so the last thing written to each region is its checksum. The byte is latched at `loc_6000 + cursor`, and the control port is raised to `0x0c`.
- *Read phase* (mode `0x20`): it runs the EAROM read handshake on `loc_6040` (`0x08`, then `0x09`, back to `0x08`, with `0x08` also latched at the data offset) and reads the byte back from `loc_6050`. Below the limit, the byte is stored through the row pointer into RAM. At the limit the read-back byte (the stored checksum) is XORed against the freshly accumulated `loc_1cf`: a zero result means the region's data verified, so it simply retires; a nonzero result means the stored table is corrupt, so the machine walks the row pointer backward zeroing every cell of the region and sets that region's bit in `loc_1c9` (`loc_1c9 = loc_1ce | loc_1c9`) to flag that the load failed and defaults must stand in.

After a data or read entry the machine folds the byte into the checksum (`loc_1cf = (byte + loc_1cf) & 0xff`) and bumps both the byte cursor `loc_1cb` and the port offset `loc_1cc`. It writes the phase delay value it computed into `loc_6040`; a nonzero value returns control to the caller (the EAROM needs real time between operations), while a zero value loops straight on to the next entry. In this way one call advances the transfer by a single EAROM access, and the whole store is moved across many re-entries — the request setters queue *what* to save or clear, `loc_de11` queues a full load, and `loc_de1b` grinds each queued region through the port a byte at a time, guarding every loaded region with the trailing checksum so a corrupted EAROM surfaces as a failure bit in `loc_1c9` rather than a garbled high-score table.

## State-reset, init and per-frame update chains

This subsystem is the machine's cold-start plumbing: the routines that wipe the tables enemies and shots live in, plant the fixed constants a fresh game or wave runs on, and — once the game is live — the one handler that ages the tube state each frame and the small family that keeps a pair of geometry blocks in step with the operator switches.

### Cold-start constant seeders

A handful of straight-line leaves do nothing but stamp fixed values into work RAM as the reset driver walks its call list. `loc_921b` [seen] seeds the core control quintet: it writes `loc_200`=0x0e, `loc_51`=0xf0, `loc_106`=0, `loc_201`=0x0f and `loc_202`=0x10. Two of those — `loc_200` and `loc_201` — are the signed control bytes the rest of the game steers by (the per-frame handler below reads the sign of `loc_201`, which this routine leaves positive at 0x0f), and `loc_202` is the countdown target that same handler drives toward 0xf0. `loc_b0e7` [seen] plants a second startup set — `loc_0`=0x0a, `loc_2`=0x00, `loc_4`=0xdf, `loc_1`=0x12, `loc_14e`=0x19, `loc_14d`=0x18 — and both were observed writing their constants, so the seeding really runs.

The low zero-page config quartet `loc_0`/`loc_1`/`loc_2`/`loc_4` is re-seeded by several different state-entry leaves, each with its own constant set for the state it precedes: `loc_c97b` [seen] writes `loc_2`=0x04, `loc_1`=0x00, `loc_0`=0x0a, `loc_4`=0x14; `loc_ca18` [seen] first masks `loc_5` down to its low six bits (`loc_5 &= 0x3f`, clearing the top two flag bits) and then lays `loc_3e`=0, `loc_2`=0x1a, `loc_0`=0x0a, `loc_4`=0xa0, `loc_16b`=0x01, `loc_1`=0x0a. Both are reached; because they overlap on the same cells they are alternative entry seeders rather than a single init — whichever state is being entered supplies its own timing and pointer constants through this shared quartet.

### Table and flag clears

Several reset leaves exist purely to blank an array plus a scatter of associated flags to a known baseline. `loc_926f` [seen] zeros the seven bytes `loc_2df..loc_2df+6` (the head of the slot/shot depth table) and then clears `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146`. `loc_928f` [seen] zeros the twelve-byte block `loc_2d3..loc_2de` and clears `loc_135` and `loc_a6`; this one is also pulled in mid-flight by the per-frame handler as its "shot state" wipe, not only at cold start. `loc_929f` [seen] zeros the eight-byte table `loc_30a..loc_30a+7` and clears the flag `loc_116`. `loc_92ad` [seen] does the minimal job of clearing the single state byte `loc_50` to 0. `loc_a831` [seen] clears the pair `loc_3aa` and `loc_125` together — `loc_125` is a latch that other code arms to 0xff, so zeroing it here is the role-defining reset. `loc_ca62` [seen] zeros the six-byte scratch block `loc_40..loc_45`; that block is later used both as draw-request staging and, by the score routine below, as two three-byte BCD accumulators, so this is its pre-clear.

`loc_9234` [seen] seeds a seventeen-cell parameter block rather than clearing one: it copies the source byte `loc_15b` into the header cell `loc_3ab`, then fills the sixteen body cells `loc_3ac..loc_3ac+0x0f` (counting x from 0x0f down to 0) all with the source byte `loc_15a`. The header `loc_3ab` was observed taking a varying source value, and the `loc_3ac` array is the per-lane/segment table the wave-init routine below later tallies.

`loc_a7bd` [seen] resets an eight-byte object table and arms it: it zeros `loc_3fe..loc_3fe+7`, then overwrites the last slot `loc_405` with 0xf0 and raises the flag `loc_115` to 0xff. All three writes were observed inside the body.

`loc_a789` [code] would zero the sixteen-byte per-slot state/flags table `loc_283..loc_283+0x0f` and then re-seed the scalars `loc_10e`=`loc_10d`=0x20, `loc_1`=0x04, and `loc_68`=`loc_69`=0 — but it was **not reached in the capture** (its body produced no writes), so this reset is described from the code only.

### Wave / level (re)initialization

`loc_a5cb` [seen] is the wave-start reset that also measures the board. It sets `loc_0`=0x20, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c` and `loc_123`, and sets `loc_105`=0x02. It then counts how many of the sixteen `loc_3ac` lane cells are nonzero, accumulating that tally into `loc_123` (observed climbing 0 -> 6, a real count of occupied lanes). If any lane is occupied **and** the level cell `loc_9f` is below 0x07, it loads an intro parameter block — `loc_4`=0x1e, `loc_0`=0x0a, `loc_2`=0x20, `loc_123`=0x80 — so the tally doubles as a "first few levels get the intro" gate. It always finishes by latching `loc_125`=0xff. This routine is invoked from the per-frame handler's reset arms below.

`loc_ad22` [seen] drains a packed request word to bring the next slot online. It reads the word `loc_603`: an all-zero word means nothing pending, so it writes the idle exit status `loc_0`=0x14 and returns. Otherwise it takes the low two bits as a slot index (`loc_3d` = (`loc_603` & 3) − 1), shifts the word right twice to consume that field, and looks up the slot byte `n` = `loc_600`+`loc_3d`. Bytes of 0 or ≥0x09 are skipped (the drain loops to the next field); a byte in 1..8 is turned into a scaled parameter — `a` = ((3·n) XOR 0xff) − 0xe5 — stored to `loc_602`. It then arms the two dependent subsystems by running `loc_ca48` (the mode-flag/scale setter) and `loc_a789` (the slot-table reset above), seeds `loc_605`=0x60, `loc_4e`=0, `loc_50`=0, `loc_604`=0x02, and writes the armed exit status `loc_0`=0x24 before returning. The request-word drain and slot-index writes were observed.

### Per-frame update handler

`loc_a504` [seen] is the frame tick whose two arms are chosen by the sign of the control byte `loc_201`. When `loc_201` is positive (< 0x80) it takes the **positive arm**: if the gate `(loc_455 | loc_11b)` is nonzero and `loc_42` exceeds 0x17, it bumps the per-slot timer cell `loc_0`+`loc_40`; it returns early if `loc_106` is set; and if `(loc_3ab | loc_116)` is zero it scans the depth table `loc_2df` for any live entry that has already grown to ≥0x11, and only when none has does it run the wave reset pair `loc_a5cb` then `loc_928f`. Three further gates — `loc_4d` & 0x60 nonzero, `loc_5` bit 7 set, and `(loc_9 & 0x43) == 0x40` — must all hold for a final `loc_a5cb` reset.

When `loc_201` is negative the handler takes the **negative arm**, which is the one exercised in the capture. Guarded off if any of `loc_135`, `loc_a6` or `loc_116` is set, it otherwise ages every live shot: for each entry of `loc_2df` (indexed from `loc_11c` down through the 0x80 wrap) a nonzero value is advanced by +0x0f and snapped to 0x00 once it reaches the 0xf0 ceiling — objects that reach the far end expire. It then advances one of two clocks depending on the per-slot byte `loc_48`+`loc_3d`: if that byte is not 1 it steps the single counter `loc_202` by +0x0f and proceeds once the sum crosses 0xf0; if it is 1 it resets `loc_10f`=0 and `loc_114`=1 and steps the 16-bit countdown `loc_5b`:`loc_5f` down by 0x20 (borrowing the low byte into the high byte), proceeding when the high byte lands on the marker 0xfa. On either proceed it writes `loc_0`=0x06, runs `loc_928f`, and folds a running total `loc_108 + loc_109 + loc_3ab` back into `loc_3ab`, clamped to a 0x3f ceiling.

### Control-block rebuild chain

A small family keeps two adjacent geometry/control blocks re-derived whenever the operator switch snapshot moves. `loc_ac20` [code] first refreshes the live snapshot through `loc_d6bb` (which decodes the option-switch ports into the config cells), then compares `(loc_a & 0xf8)` against the cached `loc_71e` and `(loc_16a & 0x03)` against the cached `loc_71f`; a match tail-calls the shared no-op return `loc_ac3e`, a mismatch falls to `loc_ac36` to raise both rebuild-request bits. In the capture only the match (no-op) path fired, so the mismatch/request arm is code-only — the routine was reached but the switch state never changed.

`loc_aba2` [code] refreshes the snapshot via `loc_ac20` and then branches on the low two request bits of `loc_1c9`: idle (both bits clear) takes the no-op return `loc_ac07`, otherwise it runs the rebuild path `loc_abac`. `loc_d7e1` [code] arms two mode bytes (`loc_5`=0, `loc_1`=0x02) and then rebuilds only while the machine is idle, enabled, and unbusy: it returns if `loc_1ca` is nonzero, returns if bit 4 of `loc_c00` is clear, writes `loc_0`=0, returns if the low two request bits of `loc_1c9` are clear, and only then calls `loc_abac`. Both of these guard routines had constant writes in the capture (their conditions held their state), so their branch behavior rests on the code.

`loc_abac` [seen] is the actual rebuild, and its rebuild path did fire. It refreshes the snapshot through `loc_ac20`, sets `loc_100`=0x08, and if all three edge cells `(loc_71b | loc_71c | loc_71d)` are zero it requests both rebuilds via `loc_ac36`. It then reads the request flags `loc_1c9`: bit 0 selects a copy span (0x17 when set, else 0x0e) and copies that many bytes of the ROM template `loc_ac08` into the block `loc_606`; bit 1 selects a fill span the same way and fills that run of `loc_706` with 0x01. If either request bit was set it latches the snapshot forward — `loc_71e` = `loc_a` & 0xf8 and `loc_71f` = `loc_16a` & 0x03 — and finally clears the two request bits (`loc_1c9 &= 0xfc`). The template copy and the flag writes were observed, so this producer is grounded [seen].

### Score accumulation and bonus-life threshold

`loc_ca6c` [seen for the score add] adds a three-byte BCD amount into a score triplet and runs a bonus-life threshold check. It is gated off unless bit 7 of `loc_5` is set. The destination triplet is selected by `loc_3d`: when zero it targets `loc_40`/`loc_41`/`loc_42`, otherwise the offset-3 triplet `loc_43`/`loc_44`/`loc_45` (the same six-byte block `loc_ca62` pre-clears). When the slot index `x` is below 8 the two low bytes of the addend come from the fixed ROM tables `loc_caf1`+x and `loc_caf9`+x; otherwise they come from the live operand pair `loc_29`/`loc_2a` with the third byte from `loc_2b`. Each byte is BCD-added with carry chaining into the corresponding score cell, and these score-cell writes were observed changing — so the add half is grounded [seen].

The threshold state machine then reads the interval byte `loc_156` (the DIP-selected bonus-life interval): a small interval is tested directly (values below 3, with the parity of the high byte deciding the 0x02 case), and a larger interval is checked by repeatedly BCD-subtracting `loc_156` from the accumulated high byte, awarding on an exact multiple. The award itself — `doAward`, which bumps the per-slot counter `loc_48`+`loc_3d` while it is still under six, fires sound 0x4f through `loc_ccc3`, and raises `loc_124`=0x20 — did **not** fire in the capture, so that bonus-life half is described from the code only.

## Utilities and shared tails

This subsystem gathers the small, reusable leaves that the rest of the machine leans on: a binary-to-decimal converter for on-screen numbers, a couple of byte-partitioning helpers, two parallel-table maintenance passes, the geometry rebuild-request tail, and a handful of bare-return stubs that let callers exit cleanly along a "nothing to do" branch.

### Binary-to-BCD conversion for the display

`loc_aaf5` [seen] is the machine's binary-to-packed-BCD converter and is heavily exercised. It takes the raw binary byte in A and runs the classic double-dabble: eight passes, each shifting the top bit out of a working copy of the source and doubling a BCD accumulator in decimal arithmetic so that bit folds into the running decimal total. The converter stores the identical packed-BCD result to **both** `loc_29` and `loc_2c` — the two cells receive the same value, so both range across `0x00..0x99` (the `0x00..0x63` span belongs to the *raw binary input* fed in, not to the BCD output written out). The result is also left in A for the immediate caller. Its caller `loc_af77` runs this conversion and then emits the packed byte at `loc_29` as separate nibbles for drawing.

`loc_af71` [code] is the clamped front door to that same pack-and-emit path: it caps the incoming byte to a maximum of `0x63` and hands the clamped value to `loc_af77`, which converts it through `loc_aaf5` and streams it out. `loc_af71` performs no role-defining write of its own — its role is entirely the clamp-then-convert-and-draw chain it drives, keeping any displayed quantity from exceeding decimal 99 once converted.

### Byte-partitioning helper

`loc_93e0` [seen] splits an input byte into a fine value and a coarse index, and is reached exclusively through the three sites inside `loc_92c5`. It seeds a working value of `0xff` and, across three passes, folds A's top three bits (most-significant first) into that seed's low bits while shifting A left; the seed is stashed in the `loc_29` scratch cell (its own only memory write). The routine returns three live values to its caller: A holds the input shifted left three times (the fine value), Y holds the assembled seed, and X is derived from the seed's complement as `((seed ^ 0xff) + 0x0d) >> 1`, giving a coarse index. With only the `loc_29` scratch write of its own, it is grounded as a reached compute helper whose real product is the register triple it hands back.

### Parallel-table maintenance

`loc_92b2` [code] is a slot-for-slot swap of two parallel 18-entry tables: for each index from `0x11` down to `0`, it exchanges the byte at `loc_3aa + x` with the byte at `loc_3bc + x`, so each slot ends holding what its sibling held. It was **not reached in the capture** — neither store fired — so its swapping role rests on the code rather than an observed write.

`loc_b85f` [code] is a straight-line seeder for a pair of three-entry arrays, writing the fixed ramp `0x00, 0x04, 0x0c` into both halves: `loc_22`/`loc_809` get `0x00`, `loc_23`/`loc_80a` get `0x04`, and `loc_24`/`loc_80b` get `0x0c`, leaving A at 0 on exit. It too was **not reached in the capture** (no role writes observed), so it is accounted as an initializer that simply did not run during this recording; the body is readable and unambiguous.

### Geometry rebuild-request tail

`loc_ac36` [seen] is the "flag both blocks for rebuild" tail. It ORs `0x03` into the working flags cell `loc_1c9` — setting the two pending-rebuild request bits — and writes the merged value back (observed producing `0x07`, i.e. the two request bits alongside a bit already present), then falls into the shared return at `loc_ac3e`. It is entered when a rebuild is warranted: `loc_ac20` drops here on a control-snapshot mismatch, and `loc_abac` also routes through it to raise the request. Those request bits are later consumed downstream where bit 0 drives one block copy and bit 1 the other.

`loc_ac3e` [code] is the lone shared return that `loc_ac36` falls into, and it is also the branch target `loc_ac20` takes when the live geometry state already matches its latch (no rebuild needed); it holds no write to ground. In the capture, `loc_ac20` was reached but only ever took this match path into the no-op return — the rebuild-request side of it did not fire.

`loc_ac07` [code] is the sibling no-op return on the "nothing to rebuild" branch: `loc_aba2` tail-branches here when its control-word masked with 3 is zero, giving an early clean exit with no memory effect to observe.

### Bare-return stubs and shared exits

`loc_9bcf` [code] is a do-nothing handler slot: a single bare return occupying an entry in a computed-dispatch table, so an index landing on it returns immediately and lets the dispatcher's own return unwind. Reach cannot be confirmed from a write-tap because it writes nothing; its role is legible from being a valid table entry rather than from a trace.

`loc_af6e` [code] is the exposed return tail of the `loc_af3f` draw routine. `loc_af26` tail-branches here when both draw slots are empty — that is, when `loc_600` OR `loc_601` is zero — meaning there is nothing to draw, and the routine simply returns. No write to ground.

`loc_b955` [code] is a register-only constant leaf that is easy to misread. It reads `loc_57` and runs a shift-and-count loop over it, **but the loop's result is discarded**: the code clears carry and adds 2 to a zeroed accumulator and reloads Y with 0, so it *always* returns the fixed pair A = `0x02`, Y = `0x00` regardless of `loc_57`'s contents. It is a constant-pair provider, not a bit-count or logarithm of `loc_57`, despite the vestigial counting loop in its body.

## Still on the frozen oracle

The subsystems above are the idiomatic layer's decompiled set — the leaves, the caller routines that drive
them, and the first computed-jump dispatcher (`loc_b84e`, described above). The rest of the reachable call
graph still runs as the frozen translated oracle: the deeper callers whose callees are not yet decompiled,
and the remaining computed-jump dispatchers that form the game's spine (each is decompiled only once all of
its jump-table targets are idiomatic). Two register-thread callers remain deferred, each needing a register
an intervening frozen leaf leaves that cannot yet be faithfully modelled: `loc_c891` (whose call to
`loc_ccfa` needs the X/Y left by a leaf with too many exit paths) and `loc_9749` (whose call to `loc_ccb5`
needs the Y left by `loc_97c5`, not yet extended to return it). Both stay on the oracle until that leaf is
resolved. Deep-tail roles tagged `[code]` lift to `[seen]` once a capture drives the states that exercise them.
