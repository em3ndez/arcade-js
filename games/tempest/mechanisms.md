# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (deeper callers and the rest of the dispatcher spine)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Every animated object on the well carries its own little program: a stream of bytes in the ROM table `loc_a0f7` that a per-frame driver walks one instruction at a time. The driver holds the walk in three shared cells. `loc_10b` is the script instruction pointer — the offset of the byte currently being read; `loc_10a` is the "keep walking" flag that gates the driver's inner loop; and `loc_10c` is the one-bit branch flag that the TEST opcodes set and the conditional opcodes consume. The driver seeds `loc_10b` from the object's saved pointer, sets `loc_10a` to 1, and then repeats: fetch the script byte `loc_a0f7[loc_10b]`, use that byte to select and run one of the opcode handlers below, bump `loc_10b` past the byte it just read, and loop again for as long as `loc_10a` stays nonzero. When a handler clears `loc_10a`, the walk stops and the advanced pointer is stored back so the object resumes from there next frame. The handlers themselves are the instruction set, and each is free to advance `loc_10b` further to swallow its own operands.

Two opcodes load a value into the object's working slot at `loc_298 + x`, the per-object cell that later opcodes read as a timer and that other machinery reads as motion state. **loc_9bd0** [seen] is the immediate store: it steps the pointer forward by one — `loc_10b = (loc_10b + 1) & 0xff` — and copies the byte that now sits under the pointer, `loc_a0f7[loc_10b]`, straight into `loc_298 + x`. The pointer advance was watched incrementing (e.g. 0x42→0x43) and the slot write was watched landing across the several active object slots in the `loc_298` band. **loc_9bdd** [seen] is the indirect store: it likewise advances `loc_10b` by one, but treats the fetched table byte `loc_a0f7[loc_10b]` not as the value but as a zero-page address, reads the live variable sitting at `loc_00 + ptr`, and copies *that* into `loc_298 + x`. So loc_9bd0 plants a literal from the script while loc_9bdd plants whatever a chosen zero-page variable currently holds — a constant versus a live feed into the same slot. Its pointer advance (0x4a→0x4b) and slot writes were both observed.

Three opcodes steer the pointer itself. **loc_9c17** [seen] is the unconditional goto: it reads the current `loc_10b`, fetches `loc_a0f8[loc_10b]` — the byte one past the opcode, i.e. the goto's target operand — and writes it back as the new `loc_10b`, so the walk resumes at the operand-named position. Its pointer reload was heavily exercised. **loc_9bee** [seen] is the conditional skip: if the branch flag `loc_10c` is nonzero it does nothing, otherwise it advances `loc_10b` by two (`(loc_10b + 2) & 0xff`), stepping the walk past a two-byte operand it chose to jump over. Both increments were watched (0x1f→0x20 then 0x20→0x21). **loc_9bfa** [seen] is the conditional goto: it *always* bumps `loc_10b` by one first, and then, only while `loc_10c` is zero, replaces the pointer with `loc_a0f7[loc_10b]` — a jump to the operand target that is taken when the flag is clear and falls through (leaving just the +1 advance) when the flag is set. Its unconditional +1 (0x4d→0x4e) and its taken-branch reload were both observed.

**loc_9c0c** [seen] is the timer/wait opcode, and it drives loc_9c17 to do its looping. It decrements the object's slot cell `loc_298 + x`; while that countdown remains nonzero it runs loc_9c17 (jumping `loc_10b` to `loc_a0f8[loc_10b]`, i.e. looping the walk back to the same waiting point), and only when the cell reaches zero does it instead advance past by incrementing the shared pointer `loc_10b` and returning. The effect is that an object parks at a script position, re-executing the same goto target every frame, until its per-slot timer expires and lets the script move on. Its decrement and the fall-through advance were both seen (the pair is reached on essentially every pass through an active object).

**loc_9bca** [seen] is the terminator: it writes zero into `loc_10a`, clearing the driver's "keep walking" flag so the inner loop ends and this object's script yields for the frame. Its single write of `loc_10a = 0` was observed.

Two TEST opcodes exist to produce the branch flag `loc_10c` that the conditional opcodes above read, but neither was seen firing in the captured window — during that window the value in `loc_10c` was produced elsewhere — so both are carried honestly as [code]. **loc_9c21** [code] compares the object against its lane's depth boundary: it reads the object's segment from `loc_2b9 + x`, looks up that segment's boundary in `loc_3ac + segment` (a stored zero there is read as the maximum, 0xff), and sets `loc_10c = 1` when the boundary is at or beyond the object's depth coordinate `loc_2df + x`, else `loc_10c = 0`. **loc_9c3b** [code] tests the shared phase accumulator: it computes `a = ((loc_147 << 2) + loc_148) & loc_148 & 0x80`, all wrapping to a byte, then stores `a ^ 0x80` into `loc_10c` — yielding 0x00 when that high bit came out set and 0x80 when it came out clear. `loc_148` is the signed phase accumulator that the driver's per-frame tail advances by the signed step `loc_147` (flipping the step's sign at its clamp bounds to make it oscillate), so this opcode branches on the accumulator's swing.

Finally, **loc_96c7** [code] is a cursor-skip helper reached through a separate list-walking path rather than the byte-fetch loop above: it advances a list read-cursor over a packed record without reading it. Its first entry steps the cursor `y` forward by three (adding one and continuing into the second), and the second entry steps by two; it touches only the register cursor and writes no memory, so with only the register motion to see there is nothing to ground and it stays [code].

## Vector coordinate lists and the display cursor

Tempest draws its tube, its enemies, and its text as an Atari Analog Vector Generator program built up in the $2000-$2FFF display RAM. Two pieces of shared machinery underlie all of that drawing. On the input side, a small family of routines chases *packed coordinate lists* — compact tables in which each entry is a step or offset rather than an absolute coordinate — through a zero-page indirect pointer. On the output side, every routine that lays bytes into the vector RAM does so through a single little-endian *display cursor* held in `loc_74`/`loc_75`, and every one of them hands the cursor to the same advance routine when it is done. This section covers both halves.

### Selecting a coordinate list

`loc_9aee` [seen] is the entry that arms the coordinate-list pointer. Given an index in Y it reads a two-table pointer out of ROM — the low byte from the table at `loc_9b02` and the high byte from the table at `loc_9afd`, both indexed by that same Y — and publishes the pair into the working pointer `loc_2c`/`loc_2d`. It also records which list was chosen by stashing Y into `loc_2b`, and reloads A from the holding cell `loc_29` on the way out. The observed writes bear this out: the pointer bytes land in `loc_2c` and `loc_2d` and `loc_2b` takes the selected index, so this is genuinely the list-selection step, not a no-op.

`loc_9a9d` [code] is a specialised sibling used on a demo/attract path. Rather than indexing both ROM tables by Y, it takes the *first* low byte of the `loc_9b02` table into `loc_2c`, forces the selected-index cell `loc_2b` to zero, and — the distinctive part — takes the pointer's high byte not from ROM but from the live source cell `loc_15d`, before reloading A from `loc_29`. It is a straight-line leaf with no branching; its one own write in the capture was constant, so its role rests on the code reading rather than an observed value change, and the tag stays [code].

### Walking a list to a coordinate

Once the pointer is armed, three routines read entries out of the list. They are reached as the selected step-kind of a computed dispatch (keyed off `loc_15e`) that generates vector coordinates, so the game picks which of these behaviours applies as it advances along a list.

`loc_96cb` [seen] treats the list as a run of *inter-entry deltas*. Through the `loc_2c`/`loc_2d` pointer it reads the entry at the cursor Y and its immediate predecessor at Y-1, stores their difference in the delta cell `loc_29`, and then advances the cursor: it returns a new Y equal to the old Y plus that delta plus two (the intermediate value it hands back in A is the old Y plus the delta, and the returned Y is that plus two). The delta values written to `loc_29` were observed ranging across the low nibble (roughly 1..0xf), confirming these are real inter-entry steps.

`loc_96db` [code] converts a single list entry into an absolute coordinate. It reads the byte at the pointer offset by Y, adds the base value in `loc_160`, and returns the 8-bit sum in A. It performs no memory write of its own — it is a pure compute helper — so a write-tap cannot confirm its reach and the tag is [code]; the role is read from the code.

`loc_96ab` [seen] is the more elaborate walker, sharing a common body with its sibling entries. It first derives a value from the selected-index cell by wrapping it into the low nibble and adding one — `((loc_2b − 1) & 0x0f) + 1` — and passes that in as the starting accumulator. The body stashes the incoming cursor Y into the scratch cell `loc_29`, then computes a new index: it subtracts the list entry two positions back (at Y-2) from that accumulator and adds the saved cursor value back in. It re-indexes the list by the result, returning the entry it lands on in A and the new index in Y. Its only own write is the `loc_29` scratch, and that write is observed, so it is grounded [seen] as a compute helper feeding the coordinate generator.

### The display cursor and its spine

Everything that writes into the vector display RAM shares one cursor and one advance routine. `loc_df5f` [seen] is that spine: given a stride in Y it advances the little-endian 16-bit pointer `loc_74`/`loc_75` by Y **plus one** (the routine forces a carry into the low-byte add, so the effective step is Y+1), carrying into the high byte `loc_75` on overflow. Both bytes are heavily exercised — `loc_74` pulses across essentially its whole range as the cursor sweeps a display frame, and `loc_75` steps through the $20-$2F page bytes as each carry rolls it forward. Every emitter below tail-calls this routine to leave the cursor sitting just past the bytes it wrote, ready for the next record.

### Emitting vector records

`loc_df59` [seen] is the core two-byte emitter. It stores the pair {A, X} at the cursor offsets Y and Y+1, then advances the cursor past them by handing `loc_df5f` a stride of Y+1 (so the pointer moves forward by Y+2). Its stores were observed writing real, wide-ranging vector data throughout $2000-$2FFF, which is what marks it [seen].

`loc_df53` [seen] is a fixed-header producer built on that emitter's tail: it writes the constant word {0x40, 0x80} at the current cursor's first two bytes and then advances by two (it passes `loc_df5f` a stride of 1). The 0x40/0x80 pair appears in the emitted stream, so it is grounded [seen], though the attribution is to the shared store tail it shares with `loc_df59`.

`loc_df19` [seen] and `loc_df1f` [seen] both append a glyph/stroke word chosen from the ROM word-table at `loc_31e4`, differing only in how they pick the index. `loc_df19` derives the index from the low nibble of A: if the carry is set **and** that nibble is exactly zero it uses index 0, otherwise it uses nibble+1. `loc_df1f` is the plainer variant — it always uses (A & 0x0f) + 1, with no carry special case — and then shares `loc_df19`'s emit tail. Either way the chosen index is doubled (each table entry is a 2-byte word), the two bytes of `loc_31e4[index]` are copied to the cursor's first two positions, and the cursor advances by two via `loc_df5f`. The copied bytes were observed landing in vector RAM as genuine AVG opcode words, so both are [seen] (with `loc_df1f`'s own index-forming arm being compute-only, reached through the shared tail).

`loc_c772` [seen] emits an object's absolute position as a vector record. It is the entry point that starts the within-record offset at zero and falls into the shared body. The body lays a fixed {0x40, 0x80} header word, then an X coordinate word and a Y coordinate word drawn from two zero-page coordinate pairs indexed by the object's slot X: the X low byte from `loc_2 + X` and X high byte from `loc_3 + X`, the Y low byte from `loc_00 + X` and Y high byte from `loc_1 + X`. Each coordinate's **high** byte is masked to five bits (`& 0x1f`) before being written into the list — the top bits are reserved for the vector opcode field — while the raw, *unmasked* bytes are cached into the "previous point" registers `loc_6c`/`loc_6d` (X low/high) and `loc_6a`/`loc_6b` (Y low/high). That cached point is the anchor from which the stroke-delta emitter subtracts to draw the object's outline relative to this seated position. Having written six bytes (header plus two coordinate words), it advances the cursor by six through `loc_df5f`. It is heavily reached with all coordinate stores observed, hence [seen].

`loc_aef8` [seen] is the text producer of the group: it turns a short run of character codes into glyph words in the display list. It seeds a source index into the character-code buffer `loc_606` (starting at the argument plus two) and a pass counter `loc_39` of 2, then runs three passes over three consecutive source bytes, walking the buffer index `loc_38` backward. Each character code is clamped before use — any code of 0x1e or greater is replaced by 0x1a — and the clamped code is doubled to index the text glyph table at `loc_31fa`, whose two bytes are copied into the display list at the running cursor offset. The loop continues while the decremented pass counter stays non-negative and stops when it underflows past zero. After the three glyph words are laid down (six bytes), it advances the cursor by handing `loc_df5f` the final offset. Its output writes into the vector RAM were observed, grounding it [seen].

## Draw-pointer setup and vector emission

Everything Tempest puts on the screen is a list of records assembled in the AVG vector RAM (`loc_2000`-`0x2fff`) and walked by the analog vector generator. This subsystem does two jobs: it aims a small family of shared cursors at the right stretch of that RAM (and at the ROM shape/glyph tables that feed it), and it appends the actual coordinate, delta, header, and glyph records those cursors point at. The three cursors it juggles are the little-endian output pointer `loc_74`/`loc_75` with its byte offset `loc_a9`, the parallel pointer `loc_3b`/`loc_3c` used by the glyph path, and the working pointer `loc_2a`/`loc_2b`; a fourth 16-bit value `loc_139`/`loc_13a` addresses the far (high-address) tail of the list.

### Aiming the draw pointer

Two nearly-identical selectors publish a ROM pointer into a cursor from one of two tables, choosing between them on the per-index flag byte `loc_415`. `loc_b2be` [seen] takes a selector in A, forms a two-byte stride `(A<<1)&0xff`, reads `loc_415`+A, and when that flag is nonzero copies the 16-bit little-endian pointer out of table `loc_ce68` (else out of `loc_ce7a`) into `loc_74`/`loc_75`, finally clearing the status cell `loc_a9`. `loc_b2de` [seen] is the same shape but publishes into the *other* cursor `loc_3b`/`loc_3c` and reads the tables the opposite way round — nonzero flag picks `loc_ce7a`, zero picks `loc_ce68` — again clearing `loc_a9`. Both are exercised, writing genuinely varying pointer bytes as the frame moves through its subsystems. A third, `loc_91b5` [seen], doubles its A selector into a word index, clears the paired flag `loc_29`, and copies the pointer at `loc_91c6`+index (low) / `loc_91c7`+index (high) into the working pointer `loc_2a`/`loc_2b`; the observed load seats a `$0540` pointer, confirming it hands a general indirect pointer to whatever consumes `loc_2a`/`loc_2b`.

Two more pointer helpers exist but were not entered in this capture. `loc_b967` [code] selects an (A,X) pair by the flag `loc_415`: flag zero returns `(loc_ce87, loc_ce86)`, nonzero returns `(loc_ce6f, loc_ce6e)` — a pair of ROM pointer-table entries the object-draw loop stores as a draw-struct pointer. `loc_b944` [code] swaps the two 16-bit pointers `loc_74`/`loc_75` and `loc_76`/`loc_77` so the shared cursor re-aims at the other structure. Neither ran because their sole caller (the `loc_b8ba` object-draw loop) never executed in the captured window, so their flag/swap values are read from code, not witnessed.

`loc_b332` [seen] both watches for a mid-frame change and re-links the list. It compares the source byte `loc_cec4` against the checkpoint byte at `loc_2000` (the first byte of vector RAM, reused here as a frame-change latch); when they differ it latches the new value into `loc_2000` and returns carry set, signalling the caller to redo the frame. When they match it emits a two-byte record: it picks slot index 8 when `loc_415` is nonzero (else 2), clears `loc_16e`, copies the word `loc_ce9e`+slot through the `loc_74`/`loc_75` cursor, then reloads that cursor from `loc_ce68`+slot — advancing the list to its next linked segment — and returns carry clear. Both the change-detect latch and the copy-and-relink path are exercised.

`loc_b84e` [code] is a computed dispatcher: its caller passes Y as a byte offset (0,2,4,6) into a four-entry table, and it tail-returns `loc_b85f`, `loc_b875`, `loc_b888`, or the vector-tail emitter `loc_b896` selected by `Y>>1` — i.e. it routes to one of four draw-list/vector-setup targets. It has no own write and was reached only through paths that did not fire these arms in this capture, so its role rests on the code.

### Low-level vector-list append primitives

The simplest emitter, `loc_b56a` [seen], writes the four bytes `0,0,0,A` at the `loc_74`/`loc_75` cursor and advances that pointer by four (carrying into the high byte). It is strongly exercised, laying its records with the caller-supplied fourth byte across the whole span of the vector buffer. `loc_c765` [seen] is an alternate entry that first lays the fixed two-byte header `{0x00,0x71}` at the cursor's first two slots, then resumes the shared object-vector build (`loc_c774`) from cursor slot two; its header stores are observed at thousands of distinct cursor addresses.

`loc_c66d` [seen] emits a tube-slot midpoint vertex. For slot `loc_38` and its wrap-around neighbour `(slot+1)&0x0f` it forms a round-up signed average (add the two low bytes plus one, fold the carry into the high sum, then arithmetic-shift each half right one, preserving the sign bit) of the slot's two 16-bit coordinate pairs `loc_36a`/`loc_35a` and `loc_38a`/`loc_37a`. It stashes the two midpoints into `loc_61`/`loc_62` and `loc_63`/`loc_64`, then appends four bytes through the `loc_74` pointer at cursor `loc_a9` — low2, high2 masked to five bits (`&0x1f`, the vector-opcode field), low1, high1 masked — mirrors all four into the previous-point scratch `loc_6a`-`loc_6d`, and advances `loc_a9` by four.

`loc_c73c` [seen] emits two 16-bit differences through the `loc_74`/`loc_75` pointer at cursor `loc_a9`: the first difference is `(loc_63:loc_64) - (loc_6c:loc_6d)` written as raw low byte then high byte masked to five bits; the second is `(loc_61:loc_62) - (loc_6a:loc_6b)` written as raw low byte then high byte masked to five bits **and OR'd with 0xa0** (the draw/stroke vector-generator opcode). The cursor `loc_a9` advances by four. This is the stroke pair that connects the current point to the previous point recorded in `loc_6a`-`loc_6d`.

`loc_df92` [seen] emits a four-byte coordinate record from an interleaved zeropage quad selected by its index argument x, reading `loc_2+x`, `loc_3+x`, `loc_0+x`, `loc_1+x`. It writes `mem[loc_2+x]` to cursor+0, `mem[loc_3+x]&0x1f` to cursor+1, `mem[loc_0+x]` to cursor+2, and a key-folded last byte `((mem[loc_1+x] ^ key) & 0x1f) ^ key` — where `key` is `loc_73` — to cursor+3 via its tail `loc_dfac`. That fold keeps the coordinate's low five bits while carrying the top three bits (the vector opcode) from the running key. `loc_dfac` then advances the cursor (via `loc_df5f`) unless the slot index wrapped to zero, in which case it runs the terminating nibble emitter `loc_dfb1` instead. Both callers pass x=`loc_6e`, so the quad read is `loc_6e`..`loc_71`.

Two routines feed `loc_df92`. `loc_c3ba` [seen] is the incremental stroke emitter: it forms the current-minus-previous differences `loc_61-loc_6a` (with borrow into `loc_62-loc_6b`) into `loc_6e`/`loc_6f` and `loc_63-loc_6c` (with borrow into `loc_64-loc_6d`) into `loc_70`/`loc_71`, emits the record through `loc_df92`, then latches the current point `loc_61`-`loc_64` into the previous-point slots `loc_6a`-`loc_6d` and writes the opcode key `loc_73 = 0xc0` for the next fold. `loc_df75` [seen] instead scales its two register inputs by four with sign extension — each value becomes a little-endian pair `((v<<2)&0xff, ((0xff-or-0<<1)|((v>>6)&1))&0xff)` — placed into `loc_6e`/`loc_6f` and `loc_70`/`loc_71`, then emits the record they anchor through `loc_df92`. Both drive real vector data across a wide value range into the display RAM.

### Math-box normalized entry

`loc_bd3e` [seen] appends a (mantissa, exponent) pair derived from the math coprocessor. For a small input (`loc_57 < 0x10`) it uses the trivial pair a=1, y=0. Otherwise it forms the 16-bit difference `loc_57 - loc_5f` (with borrow into `-loc_5b`) into the coprocessor operands `loc_6095`/`loc_6096`, issues the operation via `loc_608c`/`loc_608e`/`loc_6094`, spins while `loc_6040` bit7 is set, and reads the results `loc_6060`/`loc_6070` into `loc_79`/`loc_7a`. It then normalizes: it decrements the high result, and rolls `loc_79` left one bit at a time (feeding the shifted-out bit into the accumulator) counting shifts in x until a 1 rolls out of the top, producing an exponent `y = (((a>>1) ^ 0x7f) + 1) & 0xff` and a mantissa shift count `x`. The shift count is stored to `loc_78`, and the pair is written at the `loc_74`/`loc_75` cursor+`loc_a9` as exponent then `(count | 0x70)` (the 0x70 opcode bits). It leaves `loc_a9` unchanged, letting its caller manage the cursor (and, in `loc_c6c7`, sometimes overwrite the two bytes with a table word).

### Object- and enemy-slot emission

`loc_c43c` [seen] is the attribute gatherer that primes the draw block: it reads the slot index `loc_37` and copies that column of four parallel object-attribute tables into the working block — `loc_61 = loc_36a[x]`, `loc_62 = loc_35a[x]`, `loc_63 = loc_38a[x]`, `loc_64 = loc_37a[x]` — pairing `(loc_35a,loc_36a)` and `(loc_37a,loc_38a)` as two 16-bit coordinates for the emitters above to difference.

`loc_c6c7` [seen] emits one enemy-slot entry into the vector list, driving several of the helpers above. It reads the slot `loc_38` and the base cursor `loc_74`/`loc_75`. If the slot's occupancy byte `loc_3ac`+slot is zero it writes four blank+`0x71` pairs (eight bytes) from cursor `loc_a9` and returns — an inactive-slot placeholder. Otherwise it seats the depth scratch `loc_57 = loc_3ac[slot]`, snaps it toward the reference depth via `loc_c453`, seats the base coordinates `loc_56 = loc_435[slot]` and `loc_58 = loc_445[slot]`, runs the math-box projection `loc_c098`, and emits the stroke deltas via `loc_c73c`. It then examines bit6 of `loc_39a`+slot: if set it runs the normalization `loc_bd3e` and overwrites the two cursor bytes with a randomly chosen table word — a random even offset `(loc_60ca & 0x02) + 0x1c` selects one of two adjacent words from `loc_cec8`/`loc_cec9` — advancing `loc_a9` by two; if clear it writes the fixed marker word `0x00, 0x68, loc_3db2, loc_3db3` and advances `loc_a9` by four.

### Glyph and numeric-run emission

The text/glyph path emits packed characters into the glyph region of vector RAM at `loc_2f60`, keyed off the stroke-word table `loc_31e4`. Its core stroke writer `loc_a9fc` [seen] maps the low nibble of A to a table index: through the branch dance it forms `y = nibble+1` normally, or `y = 0` for a zero nibble arriving with carry set, then reads **a single byte** at `loc_31e4 + ((y<<1)&0xff)` — that is, the low byte of the word slot, *not* a 16-bit word — stores it at cursor `loc_2f60`+x, and advances x by two, deliberately stepping past the odd slot `loc_2f60`+x+1 and leaving it untouched. Its role write into the glyph buffer is observed with real varying stroke bytes.

`loc_a9d7` [seen] drives that writer over three source bytes: it seeds the pass counter `loc_2a = 2`, and for each pass reads the byte at the source pointer `loc_3b`/`loc_3c`, emits its high nibble then its low nibble through `loc_a9fc`, decrements the source pointer `loc_3b` by one and the counter, and stops after the counter underflows past zero. The carry it threads controls leading-blank suppression (a zero nibble under carry selects table entry 0), and it forces carry clear on the final pass so a trailing zero still draws. Its own writes are only the loop state; the glyph bytes themselves are laid by `loc_a9fc`.

`loc_a97f` [seen] builds a marker-row vector list before that emitter runs. Given a row selector y (stashed in `loc_2b`) it lays a header byte `A | 0x70` at `loc_2f60`+`loc_cdde`[y], where A is forced to zero only when y equals the marker index `loc_3d` and `loc_5` bit7 is set. It then takes a row count from `loc_48`[y] (into `loc_38`, decremented by one at the marker index) and fills six rows: each row past the count gets the alternate glyph `loc_3286`, otherwise the primary glyph `loc_3284`, stepping the cursor by two per row. Unless the game is in state 4 away from the marker (an early-out that emits no string), it finally seeds the glyph pointer `loc_3b = loc_a97d[y]`, `loc_3c = 0`, and hands off to `loc_a9d7` to spill the packed string. Its `0x71` header and `0x3f` glyph stores into the `loc_2f60` buffer are observed.

The numeric-run driver `loc_dfb1` [seen] renders a run of `loc_ae`+1 zeropage bytes (count = y-1, saved in `loc_ae`) starting at top source index `a + count` and working downward. For each byte it publishes the current source index into `loc_af`, reads `loc_0`+index, and emits the high nibble then the low nibble through `loc_df19` (its only caller of that emitter, which looks up `loc_31e4`+2*index and copies the glyph word-pair through the `loc_74` cursor). It chains carry so leading zeros are suppressed until the first nonzero nibble, and forces the very last byte's low nibble to emit unconditionally (the terminator). It is exercised extensively as the number/score renderer.

Three thin callers wrap that run driver, and none had a role-defining own write in the capture (their effect lands entirely in the helpers), so they read from code. `loc_aa9e` [code] increments the slot index, publishes it into `loc_61`, and emits that one byte as nibbles via `loc_dfb1(0x61, 1)`. `loc_af77` [code] packs its input to BCD via `loc_aaf5` — which leaves the same packed BCD (range `0x00`..`0x99`) in `loc_29` — then emits that single zeropage byte as nibbles via `loc_dfb1(0x29, 1)`. `loc_b0c6` [code] seeds the working pointer by index through `loc_91b5`, then emits a three-byte zeropage run starting at `loc_29` via `loc_dfb1(0x29, 3)`.

### Vector-list tail terminator

`loc_b896` [code] writes the far-end terminator of the list from the 16-bit tail cursor `loc_139`/`loc_13a`: it stores `loc_139` (low) at `loc_2ffc`, `loc_13a | 0x70` (high, tagged) at `loc_2ffd`, and the terminator byte `0xc0` at `loc_2fff`. ### Off-theme NVRAM-request routines grouped here

## Enemy spawning and lane selection

Enemies are born in two staged tables that this subsystem fills and drains: a bank of
per-segment *spawner* slots that decide *where around the rim* an enemy will appear and how deep
in the tube it starts, and a downstream table of *active climbers* that the spawner slots emit
into once their timers ripen. A third, eight-entry table of short-lived *timed objects* rides
alongside, seeded by the same insert primitive and drained on its own per-type clock. Lane
selection — which of the tube's sixteen segments a spawner targets and how it hops between
adjacent lanes — is handled by a small cluster of column-scan and direction-lookup helpers.

### Allocating a spawner slot

`loc_994d` **[seen]** is the allocator that stands up a new spawner slot. It first parks the
incoming index in the scratch byte `loc_36`, then walks the slot table `loc_2df` downward from
the running index `loc_11c`, treating a zero entry as free; if the scan steps below index 0 it
returns 0x00 to signal "no room", otherwise it returns 0x10 for success. On a hit it seeds the
parallel per-slot arrays at the found index: the slot key `loc_2df` takes `loc_29`; the segment
`loc_2b9` takes `loc_2a`, except that when `loc_2a` is exactly 0x0f and bit7 of the global gate
`loc_111` is set the segment is instead drawn from the POKEY random source as `loc_60ca & 0x0e`
(an even segment), so a "wildcard" request lands on a random lane; the successor segment
`loc_2cc` is set to `(segment + 1) & 0x0f`, the adjacent lane used later for flipping. The spawn
timer `loc_2a6` is zeroed, the packed coordinate/state byte `loc_28a` is seeded from `loc_2c`
and its high companion `loc_291` from `loc_2d`, the active-slot count `loc_108` is bumped, and
the lane/flags byte `loc_283` is seeded from `loc_2b`. Finally the low three bits of that byte
select a lane (`loc_2b & 0x07`) and the corresponding per-lane occupancy counter
`loc_142 + lane` is incremented; `loc_36` is restored to the caller's other index before return.

`loc_9246` **[seen]** prepares the random-tag scratch used when many slots are seeded at once.
It clears the 64-byte tag table `loc_243` (indices 0x3f..0), then for each active slot from
`loc_3ab - 1` down to 0 it draws a 4-bit POKEY random `loc_60ca & 0x0f`, stores that nibble in
`loc_203`, and packs the slot index with the nibble as `(index << 4) | nibble` into `loc_243`,
substituting 0x0f whenever that pack would be zero so no live slot carries an all-zero tag. The
packed tags observed fill in the 0x1..0xf range.

### Choosing the lane and driving depth

`loc_a028` **[code]** picks a fresh target segment for a spawner slot by finding the *deepest*
column of the tube. It zeroes the best-so-far accumulator `loc_2d`, seeds the loop counter
`loc_140` to 0x0f, and starts the scan at a random column `loc_60da & 0x0f` drawn from the
second POKEY random source. Walking sixteen columns of the per-column depth table `loc_3ac`, it
reads each column's depth (a zero depth is treated as 0xff, i.e. maximal/empty) and keeps the
column with the largest such value in `loc_2d`, recording that column index in `loc_29`; the
last column (0x0f) is skipped whenever the gate `loc_111` is nonzero. The winning column is
written as the slot's segment `loc_2b9 + x` and its successor `loc_2cc + x = (winner + 1) &
0x0f`, and bit7 of the slot flag `loc_28a + x` is cleared. The routine was not reached in the
capture — none of its own writes were observed — so its role rests on the code and it is
tagged **[code]**.

`loc_9fc4` **[seen]** advances one spawner slot toward its chosen column and re-targets it once
it passes the far limit. It raises the per-frame flag `loc_10c` to 1, reads the slot's column
from `loc_2b9 + x`, and if that column's depth cell `loc_3ac + col` is empty seeds it to 0xf1.
It then keeps `loc_3ac + col` as the running *minimum* of the slot's depth `loc_2df + x`,
tagging `loc_39a + col = 0x80` whenever a fresh minimum is set (the marker later drawn as the
lane's spike/near-front). If the slot depth is below 0x20 it flags the slot by setting bit7 of
`loc_28a + x`, clamps the depth up to 0x20, and returns; a depth between 0x20 and 0xf2 needs
nothing further. Only when the depth reaches 0xf2 or more does it re-target: it calls `loc_a028`
to choose a new deepest column, reparks the depth to 0xf0, and — provided the global counter
`loc_3ab` is zero — rewrites the slot's low state bits, setting `loc_28a + x` to
`(… & 0xfc) | 0x01` and `loc_283 + x` to `(… & 0xf8) | 0x02`, and drops `loc_10c` back to 0.

`loc_9abb` **[seen]** selects a candidate lane from a short list. It draws a random starting
lane `loc_60ca & 0x03`, primes a four-step countdown in `loc_2b`, and stashes the caller index
in `loc_39`. Each pass decrements the countdown (returning 0x00 on underflow), steps the
wrapping index `y` back one within 0..3, and reads a lane id from the candidate table
`loc_149 + y`, remapping the id 0x03 to 0x05; it accepts the first lane whose occupancy entry
`loc_13c + idx` is nonzero. On a hit it builds the list pointer `loc_2c = loc_149[y] | 0x40`,
sets `loc_2b` to 2, loads the list-high byte from `loc_9afd + 2` into `loc_2d`, and returns the
value in `loc_29`. Its observed own-body writes are the `loc_2b` countdown and the `loc_39`
stash.

### Emitting active climbers

`loc_a2a6` **[seen]** is the enemy emitter that turns ripe spawner slots into climbing enemies.
It holds off entirely while a top-priority object is being primed — if bit7 of `loc_201` is set
it returns immediately. Otherwise it walks the seven source slots (x = 6..0), skipping any slot
whose key `loc_2df + x` is zero (empty) or below 0x30 (not yet deep enough), and any slot not
armed via bit6 of `loc_28a + x`. For a qualifying slot it decrements the spawn timer
`loc_2a6 + x` and fires only on the pass where that decrement underflows past zero (the high bit
of the result sets), restoring the timer to 0 afterward. It then skips a slot whose lane/flags
byte `loc_283 + x` has bit7 set, and applies the per-wave difficulty gate: the spawn is
suppressed unless the POKEY random `loc_60ca` is at least the threshold `loc_a304 + loc_a6`,
where `loc_a6` is the current count of live climbers — so the more enemies already out, the
higher the bar to add another. When all gates pass it scans the destination table from `loc_11a`
for the first free entry (`loc_2db + y == 0`) and copies the spawn fields across: the source key
`loc_2df + x` into `loc_2db + y`, the segment `loc_2b9 + x` into `loc_2b5 + y`, and the
successor `loc_2cc + x` into `loc_2c8 + y`. It reseeds the source timer `loc_2a6 + x` from the
reload constant `loc_119`, rings the spawn cue, and bumps the live count `loc_a6`. The observed
writes include the destination-table fills and the timer decrement/reload.

### The timed-object table

`loc_a3d6` **[seen]** is the shared insert primitive for the eight-slot timed-object table. It
saves the caller indices in `loc_35`/`loc_36`, zeroes the eviction trackers `loc_2a`/`loc_2b`,
then scans slots 7..0: it takes the first slot whose position key `loc_30a + i` is zero, and
failing that remembers the slot holding the *largest* age counter `loc_312 + i` as the eviction
victim. When no slot is free it evicts that oldest slot and drops the live count `loc_116` by
one first. The chosen slot's four parallel fields are then written — age `loc_312` reset to 0,
type `loc_302` from `loc_2c`, position `loc_30a` from `loc_29`, lane `loc_2fa` from `loc_2d` —
and `loc_116` is incremented. `loc_a3d4` **[code]** is a one-line front door that stores its
argument into the type-scratch `loc_2c` and falls straight into `loc_a3d6`; its only own write,
the store to `loc_2c`, was seen only as a constant 0, so it is tagged **[code]**.

`loc_a416` **[seen]** ages that table each pass. If the pending flag `loc_116` is zero it does
nothing; otherwise it clears the flag and, for every live slot (`loc_30a + i != 0`), advances
the counter `loc_312 + i` by the per-type step `loc_a44e[type]` where the type comes from
`loc_302 + i`. A slot whose counter is still below the per-type limit `loc_a448[type]`
re-raises `loc_116` so the next pass revisits it; a slot that has reached its limit is freed by
zeroing `loc_30a + i`.

Three cue callers drive that table through the insert primitive. `loc_a34b` **[code]** primes a
fresh top-priority object: it writes the marker `loc_13b = 0xff`, sets the type-scratch
`loc_2c = 0x01`, stages the source `loc_29` from `loc_202` and the target `loc_2d` from
`loc_200`, fires the sound gate, inserts through `loc_a3d6`, and raises the ready flags
`loc_201 = 0x81` and `loc_13c = 0x01`. In the capture only the shared insert tail was exercised
— its distinctive head (the `loc_13b = 0xff` marker and the type-0x01 store into `loc_2c`) was
not observed — so it is tagged **[code]**. `loc_a1e4` **[code]** is the guard that would reach
that primer: it primes the top object only when the live byte `loc_200` matches slot x's target
`loc_2ad + x` and the ready flag `loc_201` does not already have bit7 set, then latches
`loc_201 = 0x81`; its guard did not pass in the capture, so it too is **[code]** and carries no
role-defining own write.

`loc_a36f` **[seen]** retires the climber in slot Y: it rings the sound cue, stages the source
`loc_29` from `loc_2db + y` and target `loc_2d` from `loc_2b5 + y`, re-inserts a zeroed object
through `loc_a3d4(0)`, clears the climber's key `loc_2db + y`, drops the live climber count
`loc_a6`, and marks lane X spent by writing `loc_2f2 + x = 0xff`. `loc_a3ca` **[seen]** rings

### Flip direction and lane state helpers

`loc_9ed7` **[code]** is a pure direction lookup used when an enemy turns between lanes. It

It has no own write and its reachability was not established in the capture, so it is **[code]**.

## Enemy motion and the pursuit AI

Each active adversary occupies one of the eight object slots, and this subsystem is what walks that slot up the tube toward the player, decides which way around the rim it should turn to chase the Blaster, and reduces all of that to a point on the screen. The routines split into three concerns that share the slot tables: the segment-difference primitives that answer "which rotational side is the player on", the fixed-point integrators that actually advance a slot's coordinates each frame, and a small pacer that decides which slot gets serviced next.

### The rotational-difference primitive

Everything about turning toward the player bottoms out in `loc_a7a6` `[seen]`, which takes two segment numbers in A and Y, computes the signed difference `A − Y`, and stashes the raw byte in `loc_2a`. It then consults `loc_111`: when that flag's high bit is set it keeps the full 8-bit difference, and otherwise it masks the result to the low nibble and sign-extends bit 3 (`a & 0x08 ? a | 0xf8`), so a closed tube with sixteen segments wraps its distances into the range −8..+7 instead of measuring the long way around. Both of its role writes to `loc_2a` are observed changing in the capture. The mask branch is what makes "adjacent segment" arithmetic behave on a ring, and the two callers feed it in opposite argument orders, so the sign of the answer means "player is clockwise of the slot" in one and "target is clockwise of the player" in the other.

`loc_97c5` `[seen]` is the auto-aim brain. It walks the per-slot tube-depth table `loc_2df` from index `loc_11c` (the live slot count) downward until the index wraps negative, keeping the smallest *nonzero* depth in `loc_29` and its slot index in `loc_2a` — i.e. it locks onto whichever enemy has climbed nearest the rim. If nothing nonzero is found it just returns the last depth byte it saw. Having chosen a target slot, it takes that slot's segment from `loc_2b9` and diffs it against the player's own segment `loc_200` through `loc_a7a6`, then collapses the sign into a spinner-style direction code: `0x00` when the target is already on the player's segment, `0x09` when the difference is negative, and `0xf7` otherwise. Its caller consumes that byte as a rotation delta, which is exactly the demonstration/auto-aim behaviour of steering the Blaster toward the closest threat.

`loc_9d67` `[code]` records the chase direction *into a slot* rather than driving the player. It reads slot x's target segment `loc_2b9,x`, diffs the player segment `loc_200` against it via `loc_a7a6`, and then edits bit 6 of the slot's state byte `loc_283,x`: it clears bit 6 (`&= 0xbf`) when the difference's top bit is set and sets it (`|= 0x40`) otherwise, so bit 6 ends up encoding which way around the rim that enemy must flip to reach the player. Its companion `loc_9c4f` `[seen]` simply toggles that same bit 6 in place (`loc_283,x ^= 0x40`) and returns the new byte; the XOR of `loc_283` is observed changing in the capture. Toggling rather than recomputing is how a rim-walker reverses its travel direction — a flip step that alternates sides without re-consulting the player's position.

`loc_9d06` `[seen]` is the per-slot state step that ties the depth table to those direction flags. It first copies the shared target depth `loc_202` into the slot's depth cell `loc_2df,x`. It then branches on the slot's kind: a slot whose low three bits of `loc_283,x` equal 1 while the gate byte `loc_3ab` is nonzero just flips bit 7 of `loc_28a,x` and returns, and a slot whose state byte `loc_283,x` has its top bit set merely bumps its stashed depth by one and returns. Otherwise it decrements the shared counter `loc_108` and does one of two things according to `loc_109`: when `loc_109` equals 1 it scans slots 6..0 for a non-empty entry (`loc_2df,y != 0`), remembering the last such index in `loc_38`, and breaks on the first that is a different slot whose stashed depth matches the shared value — then it copies that matched slot's bit 6, inverted (`(loc_283,y & 0x40) ^ 0x40`), into `loc_283,x`, so a follower adopts the opposite turn of its partner; when `loc_109` is anything else it defers the side decision to `loc_9d67`. Either way it finishes by writing `loc_10b = 0x41` and incrementing `loc_109`.

### Advancing a slot's coordinates

`loc_a6a9` `[code]` is the three-axis position integrator. For each axis it adds a low velocity byte into a fraction cell, keeping the wrap in that fraction, then folds the carry-out plus a signed whole-velocity byte into a whole coordinate. Axis 0 works `loc_2e3`→`loc_223` (fraction) with sign/whole `loc_343`/`loc_283`; axis 1 works `loc_2c3`→`loc_203` with `loc_323`/`loc_263`; axis 2 works `loc_303`→`loc_243` with `loc_363`/`loc_2a3`. Each axis tests for a ring overflow by the sign of its whole-velocity byte: a rising axis (sign bit clear) overflows when the new whole reaches `0xf0`, a falling one (sign bit set) when it drops below `0x10`, which clamps every axis to the tube ring `[0x10, 0xf0)`. Axes 1 and 2 write their results straight to `loc_263,x` and `loc_2a3,x`, but axis 0's whole is held back: it lands in the shared state byte `loc_283,x` only at the very end, and is forced to `0x00` if axis 0, axis 1, *or* axis 2 overflowed — so any axis running off the ring collapses the slot's primary coordinate to zero.

`loc_a721` `[code]` is the deceleration step that runs the same three axes toward rest. It seeds the saturation counter `loc_29 = 0xfd`, then for each axis calls `loc_a75d` on the (low, whole) velocity pair — `loc_2c3`/`loc_323`, `loc_2e3`/`loc_343`, `loc_303`/`loc_363` — and stores the stepped pair back. Because the seed is `0xfd`, the counter reaches zero only if `loc_a75d` bumped it on all three axes; when it does, the slot's whole coordinate `loc_283,x` is zeroed.

`loc_a75d` `[code]` is that per-axis brake. It stashes the incoming whole in `loc_2b`, reads the fixed increment from `loc_a788` (= `0x20`), and moves the signed 16-bit velocity one increment toward zero: a negative whole *adds* the increment, a non-negative whole *subtracts* it, propagating the borrow/carry between the low byte `loc_2a` and the whole. When the step crosses zero — a carry out of a negative value or a borrow out of a non-negative one — it snaps both bytes to zero and increments the saturation counter `loc_29`. It is not reached in this capture (no own-cell writes across its body), so its role rests on the code.

The spawn path `loc_a65b` `[code]` is what first stocks those velocity/coordinate tables. It marks a slot active by writing `0x80` into `loc_263,x`, `loc_283,x`, and `loc_2a3,x`, then fills each axis: it copies an RNG byte `loc_60da` into `loc_2c3,x` and derives the paired whole from `loc_a69b`; copies `loc_60ca` into `loc_2e3,x` and forces the middle whole `loc_343,x` non-positive (negating it whenever `loc_a69b` returned a non-negative value); and copies `loc_60ca` again into `loc_303,x` with its whole from `loc_a69b`. It closes by handing off to the sound cue `loc_ccc1`. Its own capture shows no role-defining write — the effect lands through its helpers — so it is tagged from the code.

`loc_a69b` `[code]` is that random-step helper: it reads a three-bit magnitude (`loc_60da & 0x07`, so 0..7) and negates it when the caller's incoming value has bit 0 set, yielding a signed nudge in −7..+7. It is a pure compute leaf with no memory write of its own, so its tag rests on the code and on its consumer.

Two more integrators serve a single shared cell rather than the slot tables. `loc_adce` `[code]` is a fractional accumulator step: it folds a signed sub-step times eight into the low cell (`loc_51 = ((loc_50 << 3) & 0xff) + loc_51`), carries that fold-carry plus the sign of `loc_50` up into A (a negative step contributes `0xff` as the high byte), and then clears the step cell `loc_50`. It is reached but the fold never carried a nonzero step in the capture, so its role writes appear only as `0x0`→`0x0` no-ops — the mechanism is clear from the code but unconfirmed by movement. `loc_b0ab` `[code]` wraps it to move a position: it nudges `loc_200` by that signed step through `loc_adce`, then clamps the result into `[0, loc_127]` — a value with its top bit set floors to `0x00`, and anything at or above the ceiling `loc_127` is pinned to `loc_127` — writing the clamped value back to `loc_200` and returning it in both A and Y. `loc_200` was written only `0x0`→`0x0` in the capture, so this too is tagged from the code even though it was reached.

`loc_b6fa` `[code]` scales a signed value by a slot's phase fraction. It stashes A in `loc_29`, takes the low three bits of the phase counter `loc_2cc,x` into `loc_2c`, and runs three rounds of shift-add: each round consumes the fraction's LSB, conditionally adds the input, and applies a sign-preserving right shift (`(acc >> 1) | (acc & 0x80)`), leaving the scaled magnitude in A. It is not reached in this capture (no own-cell writes from its range), so the role stands on the code.

`loc_b634` `[seen]` turns a slot into a drawable point and is heavily exercised, with all of its role writes observed changing. It copies `loc_57` into `loc_2f`, uses the slot's segment index `loc_2b9,x` to fetch a base coordinate pair from `loc_3ce`/`loc_3de` into `loc_56`/`loc_58`, and takes the low nibble of the phase counter `loc_2cc,x` as an offset index into the signed delta tables `loc_b68b`/`loc_b687`. It offsets each base by its delta through a `0x80`-biased signed-saturating add (bias in, saturate to `0x7f`/`0x80` on signed overflow, bias back out), writing the screen X to `loc_2e` and the screen Y to `loc_30`, and finally loads a style byte pair from `loc_bcdc`/`loc_bcec` at index `loc_112` into `loc_59`/`loc_5a`. The phase nibble sliding the point between two base coordinates is how a rim-walker is animated smoothly between segment boundaries.

`loc_b875` `[code]` rotates a three-entry array down by one with wrap — threading `loc_22`'s value around as it shifts `loc_22..loc_24` — and mirrors each new entry into the paired array `loc_809..loc_80b`. It is reached only through the computed dispatch `loc_b84e` (table index 1) and makes no write in the capture, so while the shift/mirror mechanics are unambiguous in the code, its actual game role is unconfirmed and the tag is `[code]`.

### Scheduling which slot moves

A small pacer decides, each tick, which slot the mover services. `loc_c9af` `[seen]` clears `loc_4`, decrements the active slot's countdown `loc_48,x` (with `x = loc_3d`), and checks the paired gate bytes: when `loc_48 | loc_49` is fully spent it finalizes through `loc_c9f1` and returns. Otherwise, if the current slot's countdown has hit zero it arms `loc_1 = 0x0c` and `loc_4 = 0x28`, then advances: gated by `loc_3e` it toggles the selector `loc_3f` (`^= 0x01`) and skips forward until it finds a slot whose `loc_48` countdown is non-empty. For that chosen slot it reads `loc_46` + 1 and sets `loc_2` to `0x1c` when that wrapped to zero, else `0x02`, and sets `loc_0 = 0x0a`.

`loc_c9f1` `[seen]` is the finalizer it calls: starting from cursor `loc_3e` it scans the zero-page window `loc_46,x` downward to index 0, taking the maximum into `loc_126`, then stores that max decremented by one when nonzero (MAME shows real values 0..7 moving through `loc_126`), and sets the timer cell `loc_0` to `0x14`, or to `0x10` when the status byte `loc_5` is negative.

`loc_c81b` `[seen]` derives how many steps of pending work to apply from a two-bit gate in `loc_4e` (bits 5 and 6) combined with a `>= 2` test on the counter `loc_6`, and drains `loc_6` by that amount. It clears `loc_4e` up front. With the gate clear it may seed four intro cells (`loc_1 = 0x10`, `loc_4 = 0x20`, `loc_0 = 0x0a`, `loc_2 = 0x14`) guarded by `loc_50` and the sign of `loc_5`, and returns. With the gate set it computes a step of 0..2, stores it in `loc_3e`, and — only when the step is nonzero — sets `loc_5 |= 0xc0`, zeroes `loc_16`/`loc_18`/`loc_0`, decrements `loc_3e` to `step − 1`, and uses that (forced to 3 when nonzero) as the index into the 16-bit tally at `loc_40c`/`loc_40d`, incrementing the low byte and carrying into the high byte on wrap. It closes by clamping `loc_100 + step` to a ceiling of `0x63` (because `loc_3e` has already been decremented, the expression `loc_100 + loc_3e + 1` equals `loc_100 + step`, not `+ step + 1`) and writing it back to `loc_100`. MAME confirms the stepping mechanics, but the game-vocabulary meaning of the tally and the clamped `loc_100` value remains unresolved.

## The mathbox: projection and level tables

Tempest draws its tube in perspective by handing coordinate arithmetic to a hardware math coprocessor — the "mathbox" — mapped into the $6080–$6096 input window with its busy/status flag at `loc_6040` (bit 7 high while it works) and its two result bytes at `loc_6060` (low) and `loc_6070` (high). The routines in this subsystem prime that coprocessor, drive it once per tube lane to project a well point into screen space, and build the per-level ROM-derived tables that feed it.

**Priming the coprocessor and accumulators.** `loc_c1c3` ([seen]) is the reset that precedes a projection run. It clears the zero-page working cells `loc_78`, `loc_80`, `loc_81`, `loc_88`, `loc_90` and `loc_91`, then walks the coprocessor input block writing zero to `loc_6080`, `loc_6081`, `loc_6083`, `loc_6084`, `loc_6085`, `loc_6086`, `loc_6087`, `loc_6089`, `loc_608d`, `loc_608e`, `loc_608f` and `loc_6090`, and finally seats the control byte `loc_608c` = 0x0f. It deliberately steps over `loc_6082`, `loc_6088`, `loc_608a` and `loc_608b`, leaving those four registers untouched rather than blanketing the whole $6080–$6090 span. Every write observed in the capture was a no-op transition (the targets already held zero, and `loc_608c` was already 0x0f), so while the routine is reached the *values* it deposits are not independently confirmed as changes — the tag rests on the cells being live and written on each pass.

**The projection driver.** `loc_c098` ([seen]) is the core mathbox routine: it turns a pair of well-space coordinate operands into two saturating 16-bit screen accumulators. It first forms the signed 16-bit difference `loc_57 − loc_5f` (low byte) with `loc_5b` supplying the high byte, depositing the low byte in `loc_6095` and the borrow-adjusted high byte in `loc_6096`; if that high byte comes out negative (bit 7 set) the delta is clamped up to +1 (`loc_6096` = 0x00, `loc_6095` = 0x01). It then computes the unsigned magnitude `|loc_58 − loc_60|` with a sign flag in `loc_33` (0xff when `loc_58 < loc_60`), issuing that magnitude to the coprocessor inputs `loc_608e`/`loc_6094`, and the magnitude `|loc_56 − loc_5e|` with its sign flag in `loc_34`, holding that magnitude in `loc_32` for the second pass. After spinning on `loc_6040` bit 7 until the coprocessor finishes, it reads the product from `loc_6060`/`loc_6070` into `loc_63`/`loc_64`, re-issues the held magnitude `loc_32` into `loc_608e`/`loc_6094` for the next multiply, and folds the offset pair `loc_68`/`loc_69` into `loc_63`/`loc_64` — subtracting when the `loc_33` sign flag is set, otherwise adding — with saturating limits (subtraction underflow pins the accumulator to `loc_63`=0x00,`loc_64`=0x80; addition overflow pins it to `loc_63`=0xff,`loc_64`=0x7f). It waits on the coprocessor a second time, reads the second product into `loc_61`/`loc_62`, and folds the offset pair `loc_66`/`loc_67` into that accumulator under the `loc_34` sign flag with the same saturating clamps (0x00/0x80 on underflow, 0xff/0x7f on overflow). The result is the two projected coordinates carried in `loc_63`/`loc_64` (high byte `loc_64`) and `loc_61`/`loc_62` (high byte `loc_62`).

**Projecting every lane into the slot tables.** `loc_c473` ([seen]) is the per-lane loop that turns the base geometry of the whole tube into on-screen slot coordinates. It seeds its projection reference from its incoming operands (`loc_57` and the output index `loc_38`), zeroes the clamp tally `loc_59`, and counts sixteen columns down through `loc_37` from 0x0f to 0. On each column it reads that lane's base coordinates `loc_3ce+col` and `loc_3de+col` into `loc_56` and `loc_58` and calls `loc_c098` to project them. It then squeezes each of the two projected pairs into the signed window [−4..+3] (0xfc..0x03): a negative high byte below 0xfc snaps to 0xfc with companion 0x01, and a non-negative high byte at or above 0x04 snaps to 0x03 with companion 0xff; anything already inside the window passes through unchanged. The first pair (high `loc_62`, low `loc_61`) is written to `loc_31a+out`/`loc_32a+out` and the second (high `loc_64`, low `loc_63`) to `loc_33a+out`/`loc_34a+out`, indexed by the descending output cursor `loc_38`, and every column that had to be clamped bumps `loc_59`. When the column index underflows past zero the loop ends and `loc_59` — the count of clamped lanes — is handed back.

**Unpacking the per-level nibble tables.** `loc_c196` ([seen]) rebuilds the small per-level shape/colour tables from packed ROM. It takes the level selector `loc_9f & 0x70`, clamps it to at most 0x5f, and forms the ROM index `x = (sel >> 1) | 0x07`. Walking `y` from 7 down to 0, it reads a packed byte from `loc_c1fd + x` and splits it: the low nibble lands in both the zero-page table `loc_19+y` and its display-list mirror in colour RAM `loc_800+y`, while the high nibble lands in `loc_21+y` and its mirror `loc_808+y`, the ROM index decrementing alongside `y`. One pass fills all four tables from a single level's packed row. `loc_b888` ([code]) is the level-setup wrapper around it: it rebuilds those nibble tables through `loc_c196` and then seats the vector-list tail cursor, writing `loc_139` = 0x7f and `loc_13a` = 0x04. Those two tail writes were never observed firing in the capture, so the routine and its cursor values carry the [code] tag rather than a confirmed role.

**Packing a table byte.** `loc_c2e8` ([seen]) is a small table-lookup packer used during level geometry setup. Given an input byte, it substitutes a masked hardware value `loc_60ca & 0x5f` whenever the input is 0x62 or larger (a random/timer fallback for out-of-range selectors), then splits the value into a quotient `value >> 4` and a remainder `value & 0x0f`. The remainder indexes the ROM table `loc_bc7c`, and that table entry is stored to `loc_112`; the routine returns the entry repacked as `(entry << 4) | 0x0f` (the table entry in the high nibble, the low nibble forced to 0xf) together with the quotient and remainder for the caller.

**Building the tube's lane geometry.** `loc_c235` ([seen]) assembles the current level's tube coordinate tables once per level. It first packs a seed through `loc_c2e8`, feeding it the value at `loc_46 + loc_3d`, and takes the stored table entry `loc_112` as the row index `y` into a family of ROM tables. From those it derives the span cells: the negated `loc_bc8c+y` becomes `loc_5f` and `loc_5d`, its complement `0x10 − neg` becomes `loc_a0`, the guard `loc_5b` is set to 0xff, `loc_60` takes `loc_bc9c+y`, and `loc_111` takes `loc_bccc+y`. The offset pair is then set one of two ways: when `loc_2` equals 0x1e it is copied straight from `loc_bcac+y`/`loc_bcbc+y` into `loc_68`/`loc_69`; otherwise the routine forms the signed 16-bit difference {`loc_bcbc`:`loc_bcac`} − {`loc_69`:`loc_68`}, shifts it right by four bits (bringing each low bit of the high byte into bit 7 of the low byte), and stores the resulting low byte as the level geometry scale `loc_121`. It clears `loc_66`, `loc_67`, `loc_10f`, `loc_110` and sets `loc_113` = 0x2c. Then, walking sixteen columns from 0x0f down to 0, it seeds each lane's base coordinates `loc_3ce+x` from `loc_b97c+ny` and `loc_3de+x` from `loc_ba7c+ny`, clears the projected-slot arrays `loc_31a+x`, `loc_33a+x` and `loc_39a+x`, and copies `loc_bb7c+ny` into `loc_3ee+x`, the ROM neighbour index `ny` walking down from the packed seed. A final pass computes the rounded midpoint of each column and its wrapping next neighbour — `(a + b + 1)` rotated right so the ninth bit re-enters as bit 7 — writing the two averaged tables `loc_435+x` (from the `loc_3ce` coordinates) and `loc_445+x` (from the `loc_3de` coordinates). The base tables span 0x3ce–0x3dd and 0x3de–0x3ed, the midpoint tables 0x435–0x444 and 0x445–0x454.

**Conditioning the projection operands.** Two small routines groom the operands and mode state around a projection. `loc_c453` ([seen]) snaps the coordinate `loc_57` up toward its reference: it does nothing while the guard `loc_5b` is nonzero, and nothing when `loc_57` already sits 0x0c or more above `loc_5f`; otherwise it raises `loc_57` to `loc_5f + 0x0f`, capped at a ceiling of 0xf0. These are the same `loc_57`/`loc_5b`/`loc_5f` operands the mathbox delta consumes, so the routine is a pre-projection nudge that keeps the near coordinate a fixed distance ahead of its reference. `loc_ca48` ([seen]) sets a mode flag and its paired scale byte: it defaults to (a, y) = (0x00, 0x10) and switches to (0x04, 0x08) only when both gates `loc_117` and `loc_3d` are nonzero, then folds bit 2 of the chosen `a` into the flag `loc_a1` while preserving that byte's other bits, and stores the scale `y` to `loc_b4`. Only the default branch was exercised in the capture — `loc_a1` was seen written but its bit 2 stayed clear and the alternate scale path was not observed — so the flag-set behaviour is confirmed reached while the alternate (a=0x04) outcome remains code-level.

## Sound, POKEY, and the interrupt heartbeat

Tempest's audio and its per-frame timekeeping both live on the $6000 hardware page, where two POKEY chips sit side by side — POKEY1 with its audio registers at `loc_60c0`..$60c7 and POKEY2's at `loc_60d0`..$60d7, each chip's AUDCTL/ALLPOT at `loc_60c8`/`loc_60d8`, RANDOM at `loc_60ca`/`loc_60da`, POTGO at `loc_60cb`/`loc_60db`, and SKCTL at `loc_60cf`/`loc_60df`. The routines below bring those chips up, turn abstract sound-effect requests into register writes, and ride the CPU interrupt to keep everything ticking.

### Bringing the POKEYs up

`loc_cd95` [seen] is the dual-POKEY reset. It first drops both SKCTL registers to zero (`loc_60cf`, `loc_60df`) and clears the random-latch cell `loc_720`, then runs a small liveness check: it samples POKEY1's RANDOM (`loc_60ca`) and POKEY2's RANDOM (`loc_60da`) once, and up to five more times watches whether either register has moved; on the first observed change it latches POKEY1's original sample into `loc_720`, confirming the LFSR is actually running. It then writes the canonical SKCTL init value 7 into both `loc_60cf` and `loc_60df`, zeroes the low eight audio registers of each chip (`loc_60c0`+x and `loc_60d0`+x for x=7..0) together with the matching low-eight entries of the voice-frame table `loc_c0` and the voice-level table `loc_d0`, and finally clears both AUDCTL registers (`loc_60c8`, `loc_60d8`). It leaves the chips silent, self-tested, and the voice bookkeeping cleared.

### Requesting a sound

A large family of tiny fixed-id triggers is the game's vocabulary of sound effects. Each loads one constant effect id and hands it toward the registrar: `loc_ccc1` (0x1f), `loc_ccea` (0x2f), `loc_cd02` (0x3f), `loc_ccb9` (0x4f), `loc_ccb0` (0x5f), `loc_ccee` (0x6f), `loc_ccf2` (0x7f), `loc_ccbd` (0x8f), `loc_ccf6` (0x9f), `loc_ccfe` (0xbf), and `loc_cd06` (0xcf) — all [code], each a leaf that supplies its id and lets the gate below decide. Every one of these routes through the enable gate `loc_ccc3` [code], which tests the sound/state flag `loc_5`: only when its high bit (bit7) is set does the request fall through into the registrar; otherwise the effect is dropped. The one member of the family that skips the gate is `loc_ccfa` [code] (id 0xaf), which goes straight to the registrar unconditionally — that effect always plays regardless of the enable flag. (These leaves make no memory write of their own, so the tap cannot witness each individual trampoline; their shared registrar downstream is what carries the [seen] evidence.)

The registrar is `loc_ccc7` [seen]. Given an effect id in A, it treats that id as an index into the ROM sound-descriptor table `loc_cb01` and walks sixteen consecutive entries downward (id, id-1, … as it counts the sixteen voice slots x=0x0f..0). Any nonzero descriptor byte claims that slot: it stamps the byte into the voice-frame table `loc_c0`+x, arms both per-slot timers `loc_e0`+x and `loc_f0`+x to 1, and brackets the write by setting the reservation cell `loc_bf` to the slot index and then back to the 0xff sentinel. That `loc_bf` reservation is a deliberate interlock with the interrupt-driven voice stepper below, which honors it to avoid touching a slot mid-registration. The routine also stashes and would restore the caller's X/Y through `loc_31`/`loc_32`.

### Driving the voices out to POKEY

`loc_cd0a` [seen] is the per-frame voice engine, run heavily from the interrupt. For each of the sixteen slots x=0x0f..0 it skips any idle slot (frame byte `loc_c0`+x zero) and skips the slot currently reserved in `loc_bf`. Otherwise it counts down the fast timer `loc_e0`+x; while that is still running the slot is left alone. When the fast timer expires it counts down the slow timer `loc_f0`+x. With the slow timer still running, it takes a single animation step: the sign bit of the current frame byte selects between the two ROM step tables — the low table pair at `loc_cbcc`/`loc_cbcd` or the high pair at `loc_cccc`/`loc_cccd` — reloading the fast timer from the first and folding the second (a signed level delta) into the level byte `loc_d0`+x; for odd slots it then restores the prior high nibble of that level byte, keeping only the low nibble fresh. When both timers expire it instead walks the frame forward (stepping `loc_c0`+x by two) and reloads the whole slot from the four-wide table rows at `loc_cbcb`/`loc_cbcc`/`loc_cbce` (or `loc_cccb`/`loc_cccc`/`loc_ccce` for a sign-set frame) — level, fast timer, slow timer — repeating until a nonzero frame lands (or the level reaches zero, ending the effect). Finally it publishes the slot's level byte to hardware: the low eight slots to POKEY1's audio registers at `loc_60c0`+x, the high eight to POKEY2's at `loc_60d0`..$60d7 (reached through the `loc_60c8` base with x=8..15). This is the point where the abstract voice tables actually become sound.

### The interrupt heartbeat

The interrupt handler `loc_d704` (ROM 0xd704-0xd7dc) is the heartbeat that paces all of the above. On each interrupt it saves the registers, checks a stack-depth guard (comparing the stack pointer against 0xd0) and the sign of `loc_53`; on either failure it takes a BRK/watchdog reinit path. On the normal path it kicks the watchdog at $5000, writes POKEY1's POTGO (`loc_60cb`) to start a pot scan, reads POKEY1's ALLPOT (`loc_60c8`) to derive a frame delta that it folds into the frame accumulator `loc_50`/`loc_52` and a bit into `loc_117`, writes POKEY2's POTGO (`loc_60db`), loads the input port $0c00 into the control byte `loc_8`, folds the coin/switch bits through the `loc_4c`..`loc_4f` cascade, and reflects the sign of the counter triple `loc_13`/`loc_14`/`loc_15` into the output latch at $4000. It then calls `loc_cf24` and immediately afterward `loc_cd0a` — the counter engine first, the voice engine second — before incrementing the frame/timer counters `loc_53`, `loc_7`, and the `loc_406`..`loc_408` and `loc_409`..`loc_40b` cascades, and finally restoring the registers and returning.

`loc_cf24` [seen] is that counter engine, run on essentially every interrupt. It maintains three parallel lanes, indexed x=2..0, each enabled by a distinct bit of the control byte `loc_8` that the handler had just loaded from the input port: lane x=2 by bit0, lane x=1 by bit1, lane x=0 by bit2. For an enabled lane it advances the lane's phase position `loc_d`+x (`loc_d`/`loc_e`/`loc_f`), which is kept as a five-bit quantity wrapping at 0x1f (mod 0x20); it counts down that lane's timer `loc_10`+x, reloading it to 0x78 on expiry; and on expiry it bumps the lane's counter `loc_13`+x. When a lane fires it also derives a small value from bits of the config byte `loc_9` (its 0x0c and 0x10 fields) and folds it into the running accumulators `loc_16`/`loc_17`, incrementing the lane counter. A tail decode reads the top bits of `loc_9` as an index into ROM table `loc_cfd9`, subtracts that table entry from `loc_16`, and on a non-negative result carries into `loc_18` and `loc_6`. The routine closes with two relaxation passes over the `loc_13` counter triple that subtract **different** constants: the first pass, gated on entries `>= 0x10`, subtracts **0x10** from each qualifying entry and counts how many it touched; only if that count is zero does the second pass run, subtracting **0x11** from each nonzero entry until one would go negative. The write-tap confirms the mechanism (real position wraps at 0x1f, timers reloading, counters climbing), but the exact game role of the three lanes is not pinned by the tap alone — the surrounding handler treats the lane counters (`loc_13`..`loc_15`) as things that toggle output-latch bits at $4000 and gates the lanes from the $0c00 input port, consistent with an interrupt-rate input-switch counting/timing engine rather than any sound function.

### POKEY-page and option-switch helpers

`loc_d6bb` [seen] decodes the machine's option switches into configuration cells. It reads the option port $0e00 into `loc_a`, slices its bits5-3 through ROM table `loc_d6f7` into `loc_156` and its bits7-6 through `loc_d6ff` into `loc_158`, reads the second port $0d00 XOR 0x02 into the config byte `loc_9` (the same byte `loc_cf24` later consults), and takes bits2-1 (mask 0x06) to index the paired tables `loc_d6b3`/`loc_d6b4` into `loc_ac`/`loc_ad`. It then folds `loc_ad` through `loc_dbe0` and records the merged result into `loc_16a`.

`loc_dbe0` [code] is that small merge, and it also pokes the hardware page. It writes the incoming value to POKEY2's POTGO (`loc_60db`), reads the low three bits of POKEY2's AUDCTL/ALLPOT (`loc_60d8`) and mirrors **only those three bits** into both the scratch byte `loc_37` and POKEY1's POTGO (`loc_60cb`). The value it **returns** is those low three bits OR'd with one relocated bit — bit5 of POKEY1's `loc_60c8` shifted down into bit3 — a bit that the mirrored copies in `loc_37`/`loc_60cb` do **not** carry. In this capture every observed write was constant, so the packing role rests on the code, not the tap.

`loc_dce6` [code] happens to share the $6000 page but is not part of the sound path: it drives the vector math coprocessor rather than a POKEY. It clears `loc_73`/`loc_414`/`loc_6090`, loads the operands `loc_608e`/`loc_608f` from A/X, sets the step count `loc_608c`/`loc_6094` to 0x10, kicks the divide, then scans the sixteen status slots at `loc_6040` for the first that is ready (high bit clear) and returns that slot's low/high result from `loc_6060`/`loc_6070`. It was not reached in this capture, so its role rests on the code.

### Frame-paced message scheduling

Two routines ride the same frame cadence to manage a queue of display slots (the `loc_606` buffer whose bytes the on-screen glyph emitter later reads and clamps to the same 0x1a ceiling, marking these as an animated text/character scheduler rather than a sound path). `loc_ac3f` [seen] clears bit6 of the state flag `loc_5`, optionally pre-clears the `loc_40`..`loc_45` staging block, queues an EAROM request, and then, for each channel (0 then 3, selected via `loc_3e`/`loc_36`), bubble-sorts that channel's record triples in the `loc_620`/`loc_61f`/`loc_61e` tables (with the parallel payload in `loc_520`) against a key triple held in `loc_2c`/`loc_2d`/`loc_2e`, counting the passes it takes to settle into `loc_605` and recording that per-channel count into `loc_600`. It nudges the running total `loc_601` (bumping it when it is at least the channel count and below 0x63), then derives a packed request byte in `loc_603` from the flag `loc_3d` and hands off to the slot-request walker `loc_ad22`.

`loc_ad6e` [code] is the per-frame tick of the active slot. It seeds `loc_1` to 6; while the timing gate `loc_3` (low five bits) is idle it counts the countdown `loc_605` down and, on expiry, resets by writing 0x14 to `loc_00` and returning. Otherwise it clamps the active slot's value `loc_606`+`loc_602` (through the fractional integrator `loc_adce`) into the rail range — values with the high bit set snap to 0x1a, values at or above 0x1b snap to 0x00 — writes it back, then gates on bits3-4 of `loc_4e` (masking that byte to 0x67 as it goes). When enabled it steps the slot index `loc_602` down and decrements the step counter `loc_604`; if the step underflows it re-arms — requesting an EAROM operation via `loc_ddf7` when the channel count `loc_600` is below 4 and re-entering the request walker `loc_ad22` — otherwise it retires the slot by zeroing `loc_606`+(slot-1). This routine was not exercised in the capture, so its role rests on the code.

## The EAROM high-score store

Tempest keeps its high-score table — the ranked scores and the three-letter initials the player enters at game-over — in the cabinet's ER-2055 EAROM, a small non-volatile store that survives power-off (`gameplay.md`: the initials are "saved in the machine's NVRAM — persists across power-off"). Because the EAROM is written and read one entry at a time through a slow port handshake, the game never touches it directly from gameplay code. Instead it *queues* a transfer by setting a few flag bytes at `$01c6`–`$01c8`, and a background service step, `loc_de1b`, drains that queue a little on each pass. This section covers the request setters that fill the queue and the state machine that empties it.

### The request queue and its setters

Three RAM bytes hold the pending work. `loc_1c8` is a per-region *direction* bitmask: a region whose bit is set is to be written out (RAM → EAROM), a region whose bit is clear is to be read in (EAROM → RAM). `loc_1c7` is the *pending* bitmask — which regions still need servicing — and the state machine clears each bit as it finishes that region. `loc_1c6` is a blank-mode flag: when it is nonzero the transfer engine zeroes each source RAM cell as it goes, so the region is wiped rather than preserved. All of the requests Tempest can raise are variants of "set some bits in `loc_1c7` and `loc_1c8`, and stamp a value into `loc_1c6`," and they are produced by a small family of setters that all funnel into one shared tail.

That shared tail is `loc_ddff` (reached through `loc_ddfb`), which does exactly three writes: it stores its `y` argument into `loc_1c6`, and ORs its `a` argument into both `loc_1c7` and `loc_1c8`. Because it *ORs* rather than assigns, several requests can accumulate before the machine gets a chance to run. `loc_ddfd` is the same tail with the index byte pre-forced to `y=0x00` (leave blank-mode off) and the mask taken from `a`; `loc_ddfb` narrows that further to the fixed mask `a=0x04` with `y=0x00`, queueing region-2 (`0x04`) for a write-out with no blanking — the ordinary "save this block" request. The write-tap confirms this path running: the OR merges into `loc_1c7` and `loc_1c8` are observed carrying the value `0x04`, so `loc_ddfb` is **[seen]**.

The remaining entry points wrap that tail with fixed constants and are grounded only through the code, because the tap never caught their particular masks. `loc_ddf3` runs the tail with the index byte forced to `y=0xff` (blank mode on) and the mask left as its live-in `a`, i.e. "write these regions out and wipe their RAM as you do it"; it carries the tag **[code]**. `loc_dde9` is a one-line trampoline into `loc_ddf3` with `a=0x04`, so it requests the region-2 block be written and blanked — again **[code]**, its `a=0x04`/`y=0xff` combination unseen. `loc_ddf7` supplies the constant mask `a=0x03` (regions 0 and 1 together) into the zeroed-index merge; because the merge PCs were only ever seen with `0x04` and never with `0x03`, this path is unexercised and stays **[code]**. `loc_ddf1` is the "everything" setter: it drives the tail toward `loc_1c6=0xff` with the mask `0x07` ORed into both `loc_1c7` and `loc_1c8` — all three regions, write direction, blank mode. That full `0x07`/`0xff` combination was never observed in capture (only the `loc_ddfb` `0x04` path reaches the merge), so despite its clear role it is honestly tagged **[code]**, not seen.

Set against that OR-based family is `loc_de11`, which does not merge but *assigns*: it writes `loc_1c7 = 0x07` and `loc_1c8 = 0x00` outright — all three regions pending, all in the read-in direction — and then falls straight into the service step. This is the restore path: request every block, direction read, and run the machine to pull the stored high-score table back out of the EAROM into RAM. Both of its stores are caught by the write-tap (`$01c7`←`0x07`, `$01c8`←`0x00`), so `loc_de11` is **[seen]**. The distinction from the merge family is real and load-bearing: `loc_de11` *sets* the queue to a known state, while the `loc_ddff` group only *adds* bits to whatever is already pending.

### The transfer state machine — `loc_de1b`

`loc_de1b` **[seen]** is the worker that actually clocks bytes through the EAROM, and it is exercised on essentially every service pass. It talks to three ports: `loc_6000` is the data port, indexed by an offset so consecutive bytes of a region land at `loc_6000+x`; `loc_6040` is the control/clock line; and `loc_6050` is the read-back line. Its own working state lives in the block `loc_1ca`–`loc_1cf`: `loc_1ca` is the mode byte (0 = idle), `loc_1cb` is the per-region entry cursor, `loc_1cc` is the current port index, `loc_1cd` is the region's length/limit, `loc_1ce` is a one-hot walking mask selecting the region under service, and `loc_1cf` is a running checksum accumulated across the region's bytes. The pointer pair `loc_bd`/`loc_be` forms the 16-bit RAM address of the region being copied.

When the machine finds itself idle with work outstanding — `loc_1ca == 0` and `loc_1c7 != 0` — it starts a fresh region. It clears `loc_1cb`, `loc_1cf`, and `loc_1ce`, then rebuilds `loc_1ce` into a single-bit mask by rotating: seeded with a carry, it rotates that carry into the top of `loc_1ce` while shifting `loc_1c7` left through carry, decrementing a pass counter from `0x08` until a set request bit falls out. The result is a one-hot `loc_1ce` isolating one of the pending regions, with the pass counter left encoding that bit's position. The transfer direction for this region is chosen by testing that mask against the direction bitmask — `y = (loc_1ce & loc_1c8) != 0 ? 0x80 : 0x20` — and stored as the new mode in `loc_1ca` (`0x80` = write-out, `0x20` = read-in). The serviced bit is then struck from the pending set with `loc_1c7 = loc_1ce ^ loc_1c7`. The pass counter is doubled (`x <<= 1`) to give a two-byte stride, and four packed tables are read at that index to lay out the region: `loc_1cc` ← `loc_dddd[x]` (starting port index), `loc_1cd` ← `loc_ddde[x]` (length), and `loc_bd`/`loc_be` ← `loc_dde3[x]`/`loc_dde4[x]` (the RAM address low/high). Those four tables are therefore the region descriptor map — where each high-score block lives in RAM, how long it is, and where it maps into the EAROM address space.

Every pass then runs a common block that first resets the control port (`loc_6040 = 0`) and bails immediately if the mode byte is clear. Otherwise it loads the row cursor `y = loc_1cb` and port index `x = loc_1cc`, pulls the top bit of the mode into carry, and shifts the mode left. From there control forks on the phase:

- **Start/write phase** (carry set): it writes the shifted mode value to `loc_6000+x`, advances the mode to `0x40`, and tails out with `loc_6040 = 0x0e`, returning to let the chip settle.
- **Emit phase** (top bit of the shifted mode set): it advances the mode to `0x80`; if blank mode `loc_1c6` is nonzero it first zeroes the source RAM cell at `(loc_bd/loc_be)+y`; it then reads that RAM cell as the byte to emit. If the port index has reached the region length (`x >= loc_1cd`) the region is done — mode is cleared and the accumulated checksum `loc_1cf` is emitted in place of a data byte — otherwise the data byte itself goes to `loc_6000+x`. It tails with `loc_6040 = 0x0c`, folds the emitted byte into the checksum, and bumps both cursors.
- **Read-back phase** (otherwise): it performs the EAROM read handshake by pulsing the control line (`loc_6040` stepped `0x08`→`0x09`→`0x08`) with `0x08` first written to the data port, then samples `loc_6050`. If the index has not yet reached the region length the sampled byte is a data byte, stored back through the RAM pointer at `(loc_bd/loc_be)+y`; the checksum folds it in and the cursors advance. If the index *is* at the length, the sample is the stored checksum, and it is XORed against the freshly accumulated `loc_1cf`: a zero result means the region read back intact, while a nonzero result is a verify failure — the machine then walks the cursor back down through the region zeroing every RAM cell it wrote, and records the failure by ORing this region's mask into `loc_1c9` (so `loc_1c9` accumulates which blocks failed their integrity check and had to be discarded).

After each phase the machine writes its tail value to `loc_6040`; a nonzero value means "return and wait for the chip," while a zero means it re-enters from the top of the outer loop to pick up the next region, draining `loc_1c7` bit by bit until the queue is empty and `loc_1ca` falls back to idle. Taken together, the setters stamp the request bytes and the state machine copies each described block between RAM and the ER-2055 with a running checksum, verifying reads and blanking or discarding a block when its stored checksum does not match — the mechanism by which Tempest's high-score table and entered initials persist across power cycles.

## State-reset, init and per-frame update chains

This section covers the machinery that wipes state clean at power-up and level entry, stamps the shared work cells with the constants a given mode expects, and — once the game is running — the per-frame passes that age objects, drain the pending-slot queue, and keep the option-switch-driven control blocks in sync. The routines split into four families: the cold-init clear/seed leaves fanned out by the reset driver, a set of standalone state-entry seeders, the wave/level-entry initializer, and the per-frame update and control-block-rebuild chains.

### Cold-init clear and seed leaves

At power-up the reset driver walks a fixed list of small leaf routines, each responsible for one region of state. `loc_921b` [seen] seeds the per-frame control bytes the running game will later drive: it writes `loc_200`=0x0e, `loc_51`=0xf0, `loc_106`=0x00, `loc_201`=0x0f, and `loc_202`=0x10. Two of these — `loc_201` (the sign-gated control byte whose top bit selects which arm the per-frame updater runs) and `loc_202` (a counter that same updater advances) — are exactly the cells `loc_a504` steers once play begins, so this leaf hands the update chain its starting values.

`loc_9234` [seen] builds the per-lane geometry/state block: it copies the source byte `loc_15b` into the header cell `loc_3ab`, then fills the 16-entry lane array `loc_3ac`..`loc_3bb` (looping the index from 0x0f down to 0) with the source byte `loc_15a`. This is the same 16-lane array the wave initializer later tallies and the per-lane logic reads throughout a level.

Three routines are pure block-and-flag wipers. `loc_926f` [seen] zeroes the 7-byte array `loc_2df`..`loc_2e5` (index 6 down to 0) and then clears seven scattered flag cells — `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, and `loc_146`. `loc_928f` [seen] zeroes the 12-byte array `loc_2d3`..`loc_2de` (index 0x0b down to 0), then clears `loc_135` and `loc_a6`. `loc_929f` [seen] zeroes the 8-byte table `loc_30a`..`loc_311` (index 7 down to 0), then clears the single flag `loc_116`. Because several of these targets (`loc_108`, `loc_142`, the array heads, `loc_135`, `loc_a6`, `loc_116`) carry live non-zero values while the game runs, each wipe is a genuine reset rather than a no-op. The smallest of the family, `loc_92ad` [seen], simply clears the single state cell `loc_50` to zero — a cell that swings widely elsewhere, so the reset is real.

### Standalone state-entry seeders

Several leaves exist to stamp the shared low work cells with mode-specific constants when the game changes state. `loc_b0e7` [seen] writes a startup constant set: `loc_0`=0x0a, `loc_2`=0x00, `loc_4`=0xdf, `loc_1`=0x12, `loc_14e`=0x19, and `loc_14d`=0x18. `loc_c97b` [seen] seeds a shorter config set — `loc_2`=0x04, `loc_1`=0x00, `loc_0`=0x0a, `loc_4`=0x14 — and `loc_ca18` [seen] first masks `loc_5` down to its low six bits (`loc_5 &= 0x3f`, clearing the top two flag bits) and then stamps `loc_3e`=0x00, `loc_2`=0x1a, `loc_0`=0x0a, `loc_4`=0xa0, `loc_16b`=0x01, and `loc_1`=0x0a. The three overlap on `loc_0`/`loc_1`/`loc_2`/`loc_4`, each imprinting a different constant profile, so which of them runs selects the timing/mode context the following state inherits.

`loc_a789` [code] resets the per-slot object state: it zeroes the 16-byte table `loc_283`..`loc_292` (index 0x0f down to 0), then re-seeds `loc_10e` and `loc_10d` to 0x20, `loc_1` to 0x04, and both `loc_68` and `loc_69` to 0. Its own writes were not observed in the capture (the `loc_283` cell was only touched by other code), so it carries the [code] tag; the reading rests on the source. It is invoked from the slot-init path in `loc_ad22` (below).

`loc_ca62` [seen] zeroes a six-byte working block `loc_40`..`loc_45` (index 5 down to 0, addressing wrapped in the zero page); it is used as an optional pre-clear ahead of routines that stage three-byte entries into that block. `loc_a831` [seen] clears the pair `loc_3aa` and `loc_125` together — notably, `loc_125` is the same latch the wave initializer arms to 0xff at its tail, so this leaf is the counterpart that releases it. `loc_a7bd` [seen] resets an eight-entry table: it zeroes `loc_3fe`..`loc_405` (index 7 down to 0), then overwrites the last slot `loc_405` with 0xf0 (a rail value) and arms the flag `loc_115` to 0xff. It runs from the per-frame step of the descending spike/pulsar object once that object passes a depth threshold while `loc_115` is still clear, re-seeding this eight-entry table for the next pass.

### Wave / level-entry initializer

`loc_a5cb` [seen] is the level-entry setup. It writes `loc_0`=0x20, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c`, and `loc_123`, and sets `loc_105`=0x02. It then tallies the tube: looping the index from 0x0f down to 0 over the 16-lane array `loc_3ac`, it increments `loc_123` for every non-zero entry — counting how many of the sixteen lanes hold a spiked/occupied value. If that count is non-zero and the level cell `loc_9f` is below 0x07 (the early levels), it loads an intro/parameter block by writing `loc_4`=0x1e, `loc_0`=0x0a, `loc_2`=0x20, and forcing `loc_123`=0x80. It always finishes by latching `loc_125`=0xff — the same latch `loc_a831` later clears — marking the block ready.

### Per-frame update chain

`loc_a504` [seen] is a per-frame pass run from the frame dispatcher, and again from a caller when the control byte is negative. The sign of `loc_201` selects one of two arms. In the positive arm (`loc_201` < 0x80), when the gate `(loc_455 | loc_11b)` is non-zero and the limit cell `loc_42` exceeds 0x17, it bumps the per-slot timer cell at base `loc_00` offset by the index in `loc_40`; it then returns early if `loc_106` is set. Otherwise, when `(loc_3ab | loc_116)` is zero, it scans the shot/object depth table from index `loc_11c` downward looking for any live entry that has already grown to 0x11 or more, and only if none has does it re-run the wave initializer `loc_a5cb` followed by the 12-byte wipe `loc_928f`. A further chain of gates on `loc_4d` (bit-mask 0x60), `loc_5` (bit 7), and `loc_9` (`& 0x43 == 0x40`) can trigger `loc_a5cb` again.

The negative arm (`loc_201` >= 0x80) is the one exercised in the capture and returns immediately if any of `loc_135`, `loc_a6`, or `loc_116` is set. It ages every live entry in the depth table `loc_2df` (from index `loc_11c` downward): each non-zero entry gains 0x0f and snaps to 0x00 on reaching the 0xf0 ceiling — objects that reach the far end of the tube expire. It then splits on the per-slot byte `loc_48` indexed by `loc_3d`: if that byte is not 0x01 it advances `loc_202` by 0x0f and proceeds once the sum reaches 0xf0; if it is 0x01 it clears `loc_10f`, sets `loc_114`=0x01, and steps the 16-bit countdown clock (low byte `loc_5f`, high byte `loc_5b`) down by 0x20 with borrow, proceeding when the high byte reaches 0xfa. When either path proceeds it writes `loc_00`=0x06, runs the 12-byte wipe `loc_928f`, and clamps a running total: it sums `loc_108`+`loc_109`+`loc_3ab` and stores it back into `loc_3ab`, capped at 0x3f.

`loc_ad22` [seen] drains the pending-slot request word `loc_603` two bits at a time. Each pass, if `loc_603` is zero it stamps the exhausted status `loc_0`=0x14 and returns. Otherwise it takes the low two bits as the slot index (`loc_3d = (loc_603 & 0x03) - 1`), shifts `loc_603` right twice to consume them, and reads that slot's byte `n` from `loc_600`+index; a byte of 0 or of 0x09-or-more is skipped and the drain continues. For a byte in range 1..8 it derives the paired value by tripling it, complementing it, and offsetting — `a = ((n<<1) + n)`, then `a ^= 0xff`, then `a -= 0xe5` — and stores the result in `loc_602`. It then arms two subsystems: `loc_ca48` (the mode-flag/scale setter) and, after seeding `loc_605`=0x60, `loc_4e`=0x00, `loc_50`=0x00, and `loc_604`=0x02, the per-slot reset `loc_a789`. Finally it stamps the armed status `loc_0`=0x24 and returns, so exactly one slot is initialized per invocation.

### Control-block rebuild chain

A short chain keeps two control blocks aligned with the decoded option-switch snapshot. `loc_ac20` [code] refreshes that snapshot by running the option-switch decoder `loc_d6bb`, then checks whether the live state still matches the cached targets: `(loc_a & 0xf8)` against `loc_71e` and `(loc_16a & 0x03)` against `loc_71f`. On a match it takes the no-op return `loc_ac3e`; on a mismatch it calls `loc_ac36`, which ORs 0x03 into the request word `loc_1c9` to raise both rebuild-request bits. In the capture only the matching (no-op) path fired, hence the [code] tag.

`loc_abac` [code] is the rebuild worker. It first refreshes state through `loc_ac20`, writes `loc_100`=0x08, and, when the trio `loc_71b`/`loc_71c`/`loc_71d` is all zero, raises the rebuild request via `loc_ac36`. It then reads the request flags from `loc_1c9`: if bit 0 is set it copies a 0x18-byte template (index 0x17 down to 0), otherwise a 0x0f-byte template (index 0x0e down to 0), from ROM block `loc_ac08` into the destination block `loc_606`; and if bit 1 is set it fills 0x18 bytes of `loc_706` with 0x01, otherwise 0x0f bytes. If either request bit was set (`flags & 0x03`) it latches the fresh snapshot back into the cache — `loc_71e = loc_a & 0xf8` and `loc_71f = loc_16a & 0x03` — and finally clears the two request bits with `loc_1c9 &= 0xfc`. Its writes were constant in the capture (the switch state never moved), so it stays [code].

Two entry points gate that worker. `loc_aba2` [code] refreshes the snapshot via `loc_ac20`, then branches on the low two request bits of `loc_1c9`: if they are clear it takes the no-op tail `loc_ac07`, otherwise it runs the rebuild `loc_abac`. `loc_d7e1` [code] first arms two mode bytes — `loc_5`=0x00 and `loc_1`=0x02 — then guards the rebuild behind three conditions: it returns if `loc_1ca` is non-zero (busy), returns if bit 4 of the input port `loc_c00` is clear (not enabled), and only then writes `loc_0`=0x00; it still returns without rebuilding unless the low two bits of `loc_1c9` are set, and otherwise calls `loc_abac`. Both callers' own writes were constant across the capture, so both carry the [code] tag with their roles read from the source.

## Utilities and shared tails

This subsystem gathers the small, widely-shared leaves the rest of the machine leans on: a binary-to-decimal converter and the clamp that feeds it, the flag-poke that requests geometry rebuilds, a scattering of bare return tails that let various handlers bail out cheaply, two array helpers, a byte-splitting compute helper, and one register-only constant leaf.

### Binary-to-BCD conversion and the counter/score emit path

`loc_aaf5` [seen] is the machine's binary-to-packed-BCD converter, a textbook double-dabble. It takes the incoming byte in A and runs eight passes; each pass shifts the top bit out of the source and doubles a BCD accumulator in decimal mode, folding that shifted-out bit in as the carry (the helper `bcdDouble` performs the decimal-mode `x + x + carryIn`, applying the +6/+0x60 nibble corrections). When the eight passes finish, the routine writes the *same* packed-BCD result to **both** `loc_29` and `loc_2c`, and returns it in A. Because it is the identical BCD value in each cell, both `loc_29` and `loc_2c` range over `0x00..0x99`; the `0x00..0x63` span belongs to the raw binary *input*, not to either output cell. This routine is heavily exercised, and its own writes to `loc_29`/`loc_2c` are observed inside the body, hence [seen].

`loc_af71` [code] is the front door to the two-digit display path. It clamps its incoming byte to a maximum of `0x63` (i.e. 99 decimal) and then hands the clamped value on to be packed and shown. It performs no role-defining write of its own — its behavior rests entirely on what it forwards — so it stays [code]. The chain behind it is the glue: the packer runs `loc_aaf5` to leave the BCD digit in `loc_29`, then the nibble emitter walks that zeropage byte out as its high nibble followed by its low nibble, so a clamped 0..99 count lands on screen as two decimal digits.

### Rebuild request and the family of bail-out tails

`loc_ac36` [seen] is how the machine asks for a geometry rebuild. It ORs `0x03` into the working request-flags cell `loc_1c9`, lighting the two low pending-rebuild request bits, and returns the merged value. The write to `loc_1c9` is observed in the body (the cell carrying its bits0-1 set), which grounds it [seen]. Its callers reach it when they detect that a rebuild is warranted — the control-snapshot comparison in `loc_ac20` drops here on a state mismatch — and the request bits it sets are later consumed by the rebuild consumer, where bit0 and bit1 each drive the copy of one geometry block. After setting the bits it falls straight into the shared return tail below.

That shared tail, `loc_ac3e` [code], is a lone `rts`. It is the "already up to date" exit: `loc_ac20` branches here directly when the live geometry state already matches its cached latch — that is, when `(loc_a & 0xf8)` still equals the cached `loc_71e` and `(loc_16a & 3)` still equals the cached `loc_71f` — so no rebuild is needed. With no write to ground it remains [code].

Two sibling tails mirror this pattern in other subsystems. `loc_ac07` [code] is a bare `rts` that the rebuild consumer branches to on the nothing-to-rebuild path, when `loc_1c9 & 3 == 0` and there is consequently no pending request to service. `loc_af6e` [code] is the exposed `rts` tail of the draw routine at `loc_af3f`; its caller tail-branches here when both draw slots are empty — `loc_600 | loc_601 == 0` — meaning there is nothing to draw this pass. Neither writes anything, so both are [code].

Rounding out the no-op family, `loc_9bcf` [code] is a single bare `rts` occupying a slot in a computed-dispatch table. When the dispatch selects that slot it returns immediately, letting the calling machinery unwind with nothing done — a deliberate do-nothing handler entry. It performs no write and cannot be confirmed reached from a write-tap, so [code].

### Table and array helpers

`loc_92b2` [code] swaps two parallel 18-entry tables slot for slot: for each index from `0x11` down to `0`, it exchanges `loc_3aa + x` with its sibling `loc_3bc + x`, so afterward each slot holds what the other held. The swap stores were not observed firing in this capture, so the routine is accounted not-reached here and stays [code].

`loc_b85f` [code] straight-line-seeds a pair of three-entry arrays with the fixed values 0, 4, and 12: it writes `0x00` to `loc_22` and `loc_809`, `0x04` to `loc_23` and `loc_80a`, and `0x0c` to `loc_24` and `loc_80b`, leaving A = 0. None of these seed writes were observed across the capture, so despite the readable body it is accounted not-exercised and tagged [code].

### Byte-splitting compute helper

`loc_93e0` [seen] partitions a byte into a fine part and a coarse index. Starting from a seed accumulator of `0xff`, it runs three passes, each shifting A left one bit and rolling the bit that fell out into the low end of the accumulator; after three passes the accumulator is `0xf8` merged with the input's top three bits, and this seed is written to `loc_29`. The routine hands back three register live-outs so its caller sees all of them: A holds the input shifted left three times (its low five bits promoted), Y holds the seed, and X is derived as `((acc ^ 0xff) + 0x0d) >> 1`, a small coarse-bucket index computed from the seed's complement. It is reached through its caller's three entry points, and the write to `loc_29` is observed, so [seen].

### Constant-return leaf (proposer trap)

`loc_b955` [code] looks like a bit-population helper and is not one — it is a trap for a blind reader. It reads `loc_57`, shifts it right by four, and runs an increment/shift/branch loop that counts bits, **but the loop's result is discarded**: the following `clc`/`adc #2` leaves A = `0 + 2 = 2`, and `ldy #0` forces Y = 0. So the routine *always* returns the constant pair A = 2, Y = 0, regardless of the value in `loc_57`, and it touches no memory. Naming it a log2 or bit-count of `loc_57` would be wrong; the code discards that computation. With no write to ground and a register-only constant result, it is [code].

## Still on the frozen oracle

The subsystems above are the idiomatic layer's decompiled set — the leaves, the caller routines that drive
them, and the first computed-jump dispatcher (`loc_b84e`, described above). The rest of the reachable call
graph still runs as the frozen translated oracle: the deeper callers whose callees are not yet decompiled,
and the remaining computed-jump dispatchers that form the game's spine (each is decompiled only once all of
its jump-table targets are idiomatic). Deferred to dedicated commits: `loc_9e5c` (a caller that falls into
the shared mid-entry `loc_9e5f`, a 2-entry split); `loc_c891` (whose call to `loc_ccfa` needs the X/Y left
by intervening frozen leaves threaded through as returns); `loc_b69b`/`loc_bd09` (whose call to `loc_bd3e`
has the same intervening-clobber register thread); and `loc_a618` (whose call to `loc_a65b` needs the Y left
by the intervening frozen motion steppers `loc_a6a9`/`loc_a721`). Deep-tail roles tagged `[code]` lift to
`[seen]` once a capture drives the states that exercise them.
