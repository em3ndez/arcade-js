# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (the dispatcher spine and two register-thread callers)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each animated object in the well is driven by a small byte-coded motion script: a stream of one-byte opcodes, some carrying operands, that a per-object walker interprets one step at a time to push the object along its lane, load its animation cells, and branch on the object's position or on a running phase clock. The walker `loc_9b1e` seeds a continuation flag `loc_10a = 1` and then loops, on each turn fetching the next script byte out of the `loc_a0f7` stream and taking a computed jump through the `loc_9b98` table so that the fetched byte selects which of the handlers below runs; the loop keeps going while `loc_10a` stays nonzero. The routines in this section are those handlers plus the shared cursor, gate, and test cells they read and write. Two ROM tables back the stream: `loc_a0f7` is the byte stream read at the cursor, and `loc_a0f8` sits exactly one byte higher (0xa0f8 = 0xa0f7 + 1), so a fetch at the same index through `loc_a0f8` returns the byte *following* the one at `loc_a0f7` — the mechanism by which an opcode reaches its trailing operand.

The rolling cursor is `loc_10b`; every handler that consumes stream bytes advances it, and it doubles as the index for both tables. The condition/branch flag is `loc_10c`, produced by the TEST opcodes and consumed by the skip/goto opcodes.

**Loading a value into the object slot.** `loc_9bd0` (`[seen]`) is the immediate-load opcode: it bumps the cursor by one — `index = (loc_10b + 1) & 0xff`, written back to `loc_10b` — and copies the stream byte `loc_a0f7[index]` straight into this object's slot cell `loc_298 + x` (with X selecting the slot, the observed writes landing at 0x29b through 0x29e). `loc_9bdd` (`[seen]`) is the indirect variant: it advances `loc_10b` by one, reads the stream byte `loc_a0f7[loc_10b]`, but treats that byte as a zero-page address and copies the *live variable* it points at — `mem[loc_00 + ptr]` — into the same slot `loc_298 + x`. So `loc_9bd0` writes a constant baked into the script while `loc_9bdd` writes whatever a named game variable currently holds, both landing in the object's slot.

**Conditional flow.** `loc_9bee` (`[seen]`) is a skip: if the flag `loc_10c` is nonzero it does nothing, and only while `loc_10c` is zero does it push the cursor forward by two (`loc_10b = (loc_10b + 2) & 0xff`), stepping over a two-byte operand it declines to execute. `loc_9bfa` (`[seen]`) is the conditional goto: it first advances `loc_10b` by one; if `loc_10c` is nonzero it returns and lets the walk continue in place, but while `loc_10c` is zero it reloads the cursor from the stream — `loc_10b = loc_a0f7[loc_10b]` — jumping to the operand-named target. `loc_9c17` (`[seen]`) is the unconditional goto, and it is heavily exercised: it takes the current cursor as an index and reloads `loc_10b = loc_a0f8[loc_10b]`, i.e. jumps to the target byte that follows the current opcode in the stream. Because both conditional handlers act only "while the flag is clear," a nonzero `loc_10c` deposited by a preceding TEST means the guarded operand is executed in place rather than skipped or jumped over, and a zero flag lets the skip/jump fire.

**The per-slot timer opcode.** `loc_9c0c` (`[seen]`) holds an object in its current script state for a spell: it decrements the slot's timer byte at `loc_298 + x`, and while that byte remains nonzero it delegates to `loc_9c17` to take the table-driven state step (advancing the cursor through `loc_a0f8`); only when the timer reaches zero does it instead bump the shared cursor `loc_10b` by one, releasing the object to the next opcode. `loc_9c17` is thus both a standalone goto and the loop-back tail of the timer opcode.

**The TEST opcodes** deposit into the branch flag `loc_10c` for the skip/goto opcodes to read. `loc_9c21` (`[code]`) is the position test: it reads the slot's segment `loc_2b9 + x`, looks up that segment's boundary in `loc_3ac[segment]` — where a stored zero is read as the maximum 0xff — and sets `loc_10c = 1` when that boundary is at or beyond the slot's depth `loc_2df + x`, else `loc_10c = 0`. This compares an object's progress along its lane against a per-segment limit. It is not reached in the capture — its store to `loc_10c` is absent from the trace, the flag having been produced elsewhere during the captured window — so it carries the `[code]` tag. `loc_9c3b` (`[code]`) is the phase test, drawing on the signed accumulator pair whose value `loc_148` the walker's tail advances by `loc_147` each pass: it forms `a = ((loc_147 << 2) + loc_148) & 0xff`, then `loc_10c = (a & loc_148 & 0x80) ^ 0x80`, yielding 0x00 when that combined high bit is set and 0x80 when it is clear — a test on the sign/high bit of the oscillating phase clock. It too is not reached in the capture (its store to `loc_10c` is absent), tag `[code]`.

**Ending the walk.** `loc_9bca` (`[seen]`) is the terminator: it clears `loc_10a` to zero, which breaks `loc_9b1e`'s continuation loop and ends the object's script pass for this frame. It is a leaf reached through the computed dispatch and runs frequently.

**Skipping a packed record.** `loc_96c7` (`[code]`) belongs to a separate list walk rather than the motion-stream dispatch: it advances a list cursor held in the Y register past a packed record without reading it. Entered at `loc_96c7` it steps Y forward by three — delegating to its second entry `loc_96c8` with Y already bumped by one — while entering at `loc_96c8` steps Y by two. It is register-only with no memory writes, so there is nothing to observe and it carries the `[code]` tag; it is reached only through the `loc_9683` computed dispatch (the `loc_969d` table selected by `loc_15e`), not by any direct call.

## Vector coordinate lists and the display cursor

Tempest builds every frame as a stream of vector-generator opcodes written into display RAM ($2000-$2fff). Two zero-page pointer pairs organize that work: the **write cursor** at `loc_74`/`loc_75` (a little-endian 16-bit pointer into the display list, the destination every emitter appends to), and the **coordinate-list pointer** at `loc_2c`/`loc_2d` (the source, aimed at a packed list of coordinate entries in ROM). This section covers the cursor-advance primitive, the family of routines that emit words through the cursor, and the walkers that chase the coordinate-list pointer.

### The write cursor and its advance primitive

Every emitter in this subsystem ends by nudging the cursor forward, and they all funnel that through `loc_df5f` (advanceDisplayListCursor, [seen]). It computes `sum = mem8[loc_74] + y + 1`, stores the low byte back into `loc_74`, and — only when the sum overflows past 0xff — increments the high byte `loc_75`. The "+1" is unconditional: the routine always steps the cursor by its stride argument *plus one*, so a caller that has written N bytes and wants the cursor left just past them passes `y = N-1`. The write-tap shows `loc_74` pulsing across its full 0x00..0xfe range and `loc_75` walking its high range as the cursor sweeps the $22xx-$2xxx display region, confirming this is the pointer that steps through vector RAM on essentially every emit.

### Emitting words through the cursor

The lowest-level emitter is `loc_df59` (appendVectorPair, [seen]). Given a register pair {A, X} and a start offset Y, it stores A at `(loc_74)+Y` and X at `(loc_74)+(Y+1)`, then calls `loc_df5f` with `next = Y+1` — which, with the primitive's built-in "+1", advances the cursor by Y+2 past the two bytes just written. The write-tap sees both stores landing real vector data across $2000-$2fff (e.g. $2202<-0x3c, $2203<-0x72), with wide value ranges, so this is the core word-writer other producers converge on.

`loc_df53` (appendVectorHeader4080, [seen]) is the fixed-header case: it writes the constant pair {0x40, 0x80} at the cursor (byte 0x40 at `mem16[loc_74]`, 0x80 at the next address) and steps the cursor by two via `loc_df5f(m, 1)`. The 0x40/0x80 pair is observed in the emit stream (adjacent 0x40/0x80 at $224a/$224b), the recurring word that opens a vector record.

Two closely related routines look an index into the ROM word-table at `loc_31e4` and copy the selected 2-byte entry through the cursor. `loc_df19` (appendVectorEntryByNibble, [seen]) derives the table index from the low nibble of A together with the carry flag: when carry is set **and** the nibble is exactly zero the index is 0, otherwise the index is `nibble + 1`. It then reads `loc_31e4[index*2]` and `loc_31e4[index*2 + 1]` and stores those two bytes at the cursor and cursor+1, advancing by two through `loc_df5f(m, 1)`. `loc_df1f` (appendVectorEntryNibblePlus1, [seen]) is the simpler sibling: it forms the index as `(A & 0x0f) + 1` unconditionally and then falls into the same shared copy tail (`loc_df24`) that `loc_df19` uses, so the two share their `loc_31e4`-lookup-and-emit code. `loc_df1f`'s own index arm computes rather than writes memory, so it leaves no store of its own in the trace; it is grounded [seen] as an index helper reached through that shared emit tail, whose `loc_31e4` reads and cursor stores are observed producing real vector-opcode bytes into $2000-$2fff.

`loc_df0d` (header-plus-fixed-body, [code]) and `loc_df12` (shared body-byte entry, [code]) form a small record-writing path. `loc_df0d` first emits the {0x40,0x80} header via `loc_df53`, then hands a fixed body byte 0x20 to `loc_df12`. `loc_df12` stores its input byte at the **cursor origin** — `mem8[mem16[loc_74]]`, i.e. offset 0 — and then continues into the shared record tail at `loc_dfac`. `loc_df0d` itself is not reached in the capture. `loc_df12`, on the other hand, does run — through the `loc_df09` path, which presets the body byte to 0xc0 and enters it — and its cursor-origin store is observed emitting that fixed 0xc0 into the display list across the frame. Because that emit never varies its value in the capture, the role rests on the code and both keep the [code] tag.

### Composite producers

Higher-level producers assemble a whole vector record and then leave the cursor parked past it.

`loc_c772` (emitObjectPositionVector, [seen]) draws an object at an absolute screen position. `loc_c772` is the entry that starts the record at cursor offset 0 (it tail-calls `loc_c774` with Y=0). The record is a fixed header word followed by two coordinate words: it writes {0x40, 0x80}, then the X word — low byte from `mem8[loc_2 + x]` (cached raw into `loc_6c`) and high byte from `mem8[loc_3 + x]` masked to five bits (`& 0x1f`) — then the Y word — low byte from `mem8[loc_00 + x]` (cached raw into `loc_6a`) and high byte from `mem8[loc_1 + x]` also masked `& 0x1f`. The high-byte mask keeps only the low five position bits; the raw (unmasked) bytes are stashed into `loc_6a`-`loc_6d` as the object's "previous point" so later stroke deltas can subtract from it. Six bytes go out and the cursor is advanced past all six via `loc_df5f`. The tap shows this producer heavily reached, emitting object-position vectors on essentially every relevant pass.

`loc_aef8` (emitTextGlyphsToVectorList, [seen]) turns three character codes into three glyph words. It seeds a descending source index `loc_38 = A + 2` and a countdown `loc_39 = 0x02`, then loops three times: each pass reads the character code at `mem8[loc_606 + loc_38]`, clamps any code of 0x1e or higher down to 0x1a (codes below 0x1e pass through unchanged), forms a table index `clamped << 1`, and copies the two bytes of `loc_31fa[index]` and `loc_31fa[index+1]` into consecutive cursor offsets. Both `loc_38` and `loc_39` decrement each pass; the loop continues while `loc_39` stays non-negative (0x02, 0x01, 0x00) and breaks when it wraps to 0xff — three glyphs, six bytes. It then advances the cursor by the six bytes written (`y-1` handed to `loc_df5f`). The tap sees the interior store hitting $2343-$2b71 with high byte 0xa8, the vector-draw opcode for a glyph word, confirming this as the text/glyph emitter into the display list.

### Walking the coordinate-list pointer

The `loc_2c`/`loc_2d` pointer is aimed at a packed coordinate list, then walked entry by entry.

`loc_9aee` (selectCoordListPointer, [seen]) selects which list. Indexed by Y, it loads the low pointer byte from ROM table `loc_9b02[y]` into `loc_2c` and the high byte from `loc_9afd[y]` into `loc_2d`, stashes the chosen index Y into `loc_2b`, and reloads A from `loc_29`. All three stores are observed (`loc_2c`<-0x41, `loc_2d`<-0x07, `loc_2b`<-index), so this is the confirmed pointer-setup step ahead of the walkers. Its sibling `loc_9a9d` ([code]) seeds a fixed list instead: it takes the low pointer byte from `loc_9b02` at index 0, forces the index `loc_2b` to zero, takes the high byte from the held source cell `loc_15d`, and reloads A from `loc_29`. Its lone capture write was constant, so the role rests on the code rather than on an observed range; it carries the [code] tag.

Once the pointer is aimed, three walkers step through the list. `loc_96cb` (stepCoordListCursorByEntryDelta, [seen]) reads the entry at the cursor `(loc_2c),y` and its predecessor `(loc_2c),y-1`, stores their difference as the step delta at `loc_29`, and advances: it returns `A = (y-1) + delta + 1` (that is, `y + delta`) and `Y = A + 2`, so the cursor moves forward by `delta + 2`. The tap observes `loc_29` taking real inter-entry step values across 0x01..0x0f, confirming these are genuine coordinate-list strides. `loc_96db` (resolveListEntryToCoord, [code]) resolves one entry to an absolute coordinate: it reads the byte at `(loc_2c) + y`, adds the base value in `loc_160`, and returns the sum masked to a byte in A. It performs no memory write of its own (a pure compute helper), and its reach is through a computed jump that a write-tap cannot confirm, so it stays honestly [code].

`loc_96ab` (walkVectorListCoordDelta, [seen]) is the delta re-indexer, with several entry points into a shared body. The `loc_96ab` entry passes a counter-derived seed `((loc_2b - 1) & 0x0f) + 1`; the `loc_96b7` entry passes the raw `loc_2b` instead. The shared body first stashes the incoming cursor Y into `loc_29`, then computes `a = seed - mem8[(loc_2c) + (y-2)]` (subtracting the list entry two positions back), adds `loc_29` back in, and finally loads and returns the entry at `(loc_2c) + a` while leaving Y equal to that computed index — its only own write is the `loc_29` scratch. A third entry, `loc_96c4`, is the plain fetch: it simply returns `mem8[(loc_2c) + y]`. The body is reached and its computed-index output feeds the `$968f`/`$969d` computed-jump vector-coordinate generator, so the delta re-index is grounded [seen] as a coordinate helper.

## Draw-pointer setup and vector emission

Everything the game shows is a list of records the AVG (analog vector generator) reads out of vector RAM at 0x2000-0x2fff. This subsystem is the back half of that pipeline: first it points a shared write cursor at the right place in that RAM (or at the 0x2f60 glyph buffer), then a family of emitters walks over game state and lays down vector records — headers, coordinate pairs, packed-nibble glyph runs, and perspective-projected vertices — advancing the cursor as it goes. The cursor itself lives in the zero-page pointer `loc_74`/`loc_75` (a little-endian 16-bit address), with a running byte offset in `loc_a9` for the routines that index off a fixed base, and a second pointer `loc_3b`/`loc_3c` used both as an alternate draw pointer and as a glyph-source pointer.

### Pointing the cursor at a structure

`loc_b2be` [seen] is the per-subsystem draw-pointer setup. From an index in A it forms the two-byte stride `(A<<1)&0xff`, then chooses a source table by the per-index flag `loc_415[idx]`: a nonzero flag selects ROM table `loc_ce68`, a zero flag selects `loc_ce7a`. It copies that table entry's low and high bytes into `loc_74`/`loc_75` and clears the status/offset cell `loc_a9`, so a subsequent emitter starts writing at offset zero of the chosen structure. `loc_b2de` [seen] is the sibling that publishes the selected pointer into `loc_3b`/`loc_3c` instead, and it inverts the table choice — here a nonzero `loc_415[idx]` selects `loc_ce7a` and zero selects `loc_ce68` — again clearing `loc_a9`. `loc_91b5` [seen] serves the other working pointer: it doubles A into a word index, clears the paired flag byte `loc_29`, and copies the little-endian pointer from the in-page ROM table at `loc_91c6`+index into `loc_2a`/`loc_2b`, which then acts as a general indirect source pointer for the nibble-run emitters.

`loc_b332` [seen] is a frame-synchronization gate wrapped around a draw-list link. It compares the live source byte `loc_cec4` against the checkpoint `loc_2000`; if they differ it latches the new value into `loc_2000` and returns carry set, signalling the caller that the frame changed and the list must be rebuilt. When they match, it selects a record slot `x = loc_415 != 0 ? 0x08 : 0x02`, clears `loc_16e`, copies the two-byte record from `loc_ce9e[x]` out through the `loc_74` cursor, reloads `loc_74`/`loc_75` from `loc_ce68[x]`, and returns carry clear.

Two more pointer helpers are present in code but were **not reached in the capture** because their common caller (the object-draw loop at `loc_b8ba`) never executed. `loc_b944` [code] swaps the `loc_74`/`loc_75` pointer with `loc_76`/`loc_77` (via a saved low/high pair) so the shared cursor addresses the other of two structures. `loc_b967` [code] picks an (A,X) pointer pair by the flag `loc_415`: zero yields (`loc_ce87`, `loc_ce86`), nonzero yields (`loc_ce6f`, `loc_ce6e`); the flag itself is exercised elsewhere but this selection body is not reached in the capture. `loc_b84e` [code] is the computed-jump dispatcher over four draw-pointer targets — it treats Y as a byte offset (0,2,4,6) into a two-entry-stride table and tail-calls `loc_b85f`, `loc_b875`, `loc_b888`, or `loc_b896`; those targets are reachable only through this dispatcher, not from independent callers.

### The low-level cursor primitives

The simplest emitters write a fixed shape at the cursor and step it. `loc_b56a` [seen] appends a four-byte record `{0, 0, 0, A}` through the `loc_74`/`loc_75` cursor and advances the pointer by four, carrying into the high byte on low-byte overflow; it is heavily exercised, filling long spans of the vector buffer. `loc_c765` [seen] is an alternate entry that lays a fixed two-byte header `{0x00, 0x71}` at the very start of the cursor's structure and then resumes the shared six-byte coordinate build from cursor slot two (its continuation `loc_c774` writes the `{0x40,0x80}` header word and two coordinate words, each high byte clamped to five bits, caching the raw bytes into `loc_6a`-`loc_6d` and stepping the cursor past all six).

`loc_b896` [code] emits a tail record from the separate 16-bit cursor `loc_139`/`loc_13a`: it stores the cursor low byte into `loc_2ffc`, the high byte OR'd with `0x70` into `loc_2ffd`, and the terminator `0xc0` into `loc_2fff` (the top of the AVG vector RAM), then decrements the cursor by `0x20` with a 16-bit borrow into `loc_13a` and masks the low byte to `0x7f`. This emit path is not reached in the capture; its role rests on the code.

### Packed-nibble glyph and digit runs

Text and score digits are emitted as glyph runs: each source byte is split into its high nibble and its low nibble, and each nibble indexes a stroke/font word table at `loc_31e4`. `loc_a9fc` [seen] is the innermost step for the `loc_2f60` glyph buffer: it maps A's low nibble to an index `y` — a zero nibble with carry set indexes entry 0, otherwise `nibble+1` — and stores a **single byte** read from `loc_31e4` at index `2*y` into the buffer at `loc_2f60[x]`, then advances X by two (writing the even slot and stepping past the odd one). `loc_a9d7` [seen] drives it over a packed string: it seeds the pass counter `loc_2a` to 2 (a three-byte, three-pass loop), reads each source byte through the pointer `loc_3b`/`loc_3c`, emits its high nibble then its low nibble via `loc_a9fc`, chains the carry so that only a zero nibble preserves it, forces the carry clear before the final byte's low nibble, and walks the source pointer backward one byte per pass. Its own writes are only that loop state; the visible output is the glyph bytes `loc_a9fc` lays down.

`loc_a97f` [seen] builds a marker/status row (used for the on-rim indicator rows) into the `loc_2f60` buffer. Keyed by Y it stores a header byte (A OR'd with `0x70`, zeroed only when Y hits the marker index `loc_3d` and `loc_5` bit7 is set) at `loc_2f60[loc_cdde[y]]`, then fills six glyph slots — rows past the count `loc_48[y]` (reduced by one at the marker) use the alternate glyph `loc_3286`, earlier rows use `loc_3284` — stepping X by two each. It early-exits with no glyph emission when the game-state byte `loc_00` is 4 and Y is away from the marker; otherwise it seeds the glyph pointer `loc_3b` = `loc_a97d[y]`, `loc_3c` = 0, and hands off to `loc_a9d7` to emit the packed string.

The vector-list side of glyph emission runs through `loc_dfb1` [seen], reached extensively. It emits a run of zero-page bytes — `loc_ae` counts `y-1` down through zero, and the source index in `loc_af` starts at `(a + count)` and walks down — pushing each byte's high then low nibble through `loc_df19` (of which `loc_dfb1` is the sole caller). `loc_df19` copies a **two-byte word** from `loc_31e4` (index 0 when carry-set and the nibble is zero, else `nibble+1`) out through the `loc_74` cursor and steps the cursor past it; the carry is chained so only the final low nibble sees it cleared, marking the run's terminator. Several thin callers feed this driver: `loc_aa9e` [code] increments the slot index, publishes it into `loc_61`, and emits that single byte; `loc_af77` [code] packs its incoming byte to BCD into `loc_29` and emits that one byte as nibbles; `loc_b0c6` [code] selects a pointer by index through `loc_91b5` and then emits a three-byte zero-page run. These caller roles rest on the code, as their own writes are constant in the capture.

### Coordinate records and scaled deltas

A second emitter family lays down coordinate records rather than glyphs. `loc_df92` [seen] emits a four-byte record through the cursor from four zero-page slots offset by X: byte 0 is `loc_2[x]`, byte 1 is `loc_3[x]` masked to five bits, byte 2 is `loc_0[x]`, and the last byte is key-folded as `((loc_1[x] ^ key) & 0x1f) ^ key` where the key is `loc_73`; its continuation stores that byte at the next cursor slot and either advances the cursor or, when the slot index wraps to zero, runs the terminating byte run. `loc_c3ba` [seen] computes two 16-bit differences of the current work block minus the previous one — `loc_61:loc_62` minus `loc_6a:loc_6b` into `loc_6e:loc_6f`, and `loc_63:loc_64` minus `loc_6c:loc_6d` into `loc_70:loc_71` — emits the record through `loc_df92` starting at `loc_6e`, then latches the current values into the previous block (`loc_6a`-`loc_6d`) and flags it ready with `loc_73` = `0xc0`. `loc_c423` [seen] feeds it: it snapshots the four indexed cells `loc_32a`/`loc_31a`/`loc_34a`/`loc_33a` at slot `loc_37` into the work header `loc_61`-`loc_64` and then drives `loc_c3ba`.

`loc_df75` [seen] widens two input bytes by a factor of four with sign extension — low byte `(v<<2)&0xff`, high byte `((signHi<<1) | ((v>>6)&1))&0xff` where `signHi` is `0xff` for a negative input — placing them into the delta pair `loc_6e`-`loc_71`, then emits the anchored record via `loc_df92`. `loc_df73` [code] is a front for it that first stashes the index byte into the key cell `loc_73`. `loc_d8a9` [code] stashes A into `loc_29`, scales its two coordinates through `loc_df75`, then emits that one stashed byte as a single-entry run via `loc_dfb1`. `loc_dd2b` [code] scales the coordinates through `loc_df75`, then shifts the stashed byte in `loc_35` out MSB-first over eight passes, emitting each bit as one vector digit through `loc_df1f` (which turns `nibble+1` into a `loc_31e4` word entry). `loc_dd27` [code] and `loc_dd29` [code] are fixed-operand fronts for `loc_dd2b`: `loc_dd27` presets the first coordinate delta `A = 0xd0`, falls through `loc_dd29` which presets the second `X = 0xf8`, and drops into `loc_dd2b` with those two deltas — the byte that gets shifted out as the eight bit-digits is the caller's live-in stashed in `loc_35`, not either constant. Both roles rest on the code.

`loc_c36e` [seen] is a gated multi-record loop: it returns immediately when its gate byte A is nonzero, otherwise it seats the four record fields `loc_61`-`loc_64` from the indexed tables `loc_32a`/`loc_31a`/`loc_34a`/`loc_33a` at Y, emits the header through `loc_c772`, caches the resulting cursor into `loc_b0`/`loc_b1`, and then draws one record per pass — count `0x0e` when `loc_111` is nonzero else `0x0f`, key `loc_73` = `0xc0` — decrementing the slot index `loc_37` each pass and bumping it by `0x10` whenever the low nibble saturates to `0xf`, calling `loc_c423` to emit each record until the loop counter underflows.

### Perspective vertices and the math box

The tube's slots are projected into screen space through the math coprocessor. `loc_bd3e` [seen] is the appender that produces a (mantissa, exponent) pair. ## Enemy spawning and lane selection

This subsystem stocks two parallel object populations — the enemies that climb the tube, kept in the active-slot arrays indexed off `loc_2df`, and a smaller eight-entry timed-object table indexed off `loc_30a` — and it decides which lane around the rim each new arrival is dropped into. Both draw their randomness from the POKEY hardware random registers `loc_60ca` and `loc_60da`.

### Allocating an active enemy slot

`loc_994d` [seen] is the allocator for the climbing-enemy population. ### Choosing a candidate lane

`loc_9abb` [seen] picks the lane a new object will occupy from a short candidate list. It seeds a wrapping index from a POKEY draw (`loc_60ca & 0x03`), primes a four-step countdown in `loc_2b` to 0x04, and stashes the caller's X in `loc_39`. Each pass decrements the countdown into `loc_2b` and bails with A = 0x00 if it underflows (bit7 set); otherwise it steps the index down, wrapping to 0x03 when it goes negative, reads a lane id from the `loc_149` candidate table (mapping the raw id 0x03 to 0x05), and stops as soon as that lane's occupancy byte `loc_13c[idx]` is non-empty. On a qualifying lane it builds the selection: the chosen `loc_149` entry with bit6 forced on is written to `loc_2c`, the list-hi byte `loc_9afd[2]` is written to `loc_2d`, `loc_2b` is left at 2, and it returns A = `loc_29`.

### Seeding the per-slot tag table at wave start

`loc_9246` [seen] runs from the wave-init chain to lay down the random per-slot tags. It first clears the 64-byte tag table `loc_243`..`loc_243+0x3f` to zero, then walks each slot from `loc_3ab - 1` down to 0: for each it stores a fresh 4-bit POKEY draw (`loc_60ca & 0x0f`, observed pulsing across 0x0–0xe) into `loc_203,x`, and packs the slot index with that nibble into `loc_243,x = (x << 4) | nibble`, substituting 0x0f whenever that packed byte would be zero so no slot carries an all-zero tag.

### Picking the target segment down the tube

`loc_a028` [code] chooses a slot's target segment by finding the deepest column of the sixteen-entry tube-depth table `loc_3ac`. Starting from a POKEY-2 random column (`loc_60da & 0x0f`) and counting sixteen columns down through a wrapping index (loop counter in `loc_140`), it tracks the largest depth in `loc_2d` and its column in `loc_29`, treating an empty column (depth 0) as maximal (0xff); the last column (0x0f) is skipped while the gate `loc_111` is non-zero. This routine is reached only through `loc_9fc4`'s far-limit branch and was not reached in the capture, so its role rests on the code.

`loc_9fc4` [seen] is the per-slot approach step that advances one climber toward its column and maintains the running nearest-depth record. ### Stepping a slot around the rim (lane flip)

## Enemy motion and the pursuit AI

Enemies reach the near rim two different ways, and the code keeps two distinct machineries for them: a *segment stepper* that walks an enemy lane-to-lane around the rim in discrete flips, and a *continuous integrator* that folds per-axis velocities into a free-flight coordinate. Over both sits the aiming logic that decides which way to turn — for the enemies, toward the player's segment; for the auto-playing demo blaster, toward the nearest enemy.

### The signed segment distance

Almost every turning decision funnels through **loc_a7a6** [seen], which computes the signed rotational distance between two segment indices. It takes `A - Y` (mod 0x100), stashes the raw difference at loc_2a, then branches on loc_111: when loc_111's bit 7 is set it returns the full byte, but otherwise it keeps only the low nibble and sign-extends bit 3 (`if (a & 0x08) a |= 0xf8`), collapsing the answer into a signed lane offset in roughly [-8, +7]. That nibble form is what a 16-lane closed rim needs — the shorter of the two ways around. Its callers read back the value the routine leaves in the accumulator.

**loc_97c5** [seen] is the clearest piece of pursuit logic in the group, and it points the *player's* claw rather than an enemy: it is the demo/auto-aim step. It sweeps the per-slot depth table loc_2df for x from loc_11c down through 0, tracking the smallest nonzero depth in loc_29 and its slot index in loc_2a (0xff meaning "none seen"). The smallest nonzero depth is the closest enemy up the tube. If no live slot was found it just returns the last byte it read; otherwise it feeds that slot's target segment loc_2b9[idx] and the player segment loc_200 to loc_a7a6 and turns the signed result into a spinner command — 0x00 when the enemy is already on the player's lane, 0x09 when it lies to one side, 0xf7 (−9) when it lies to the other. Those two step codes are the auto-aim's left/right nudge back onto the threatening lane.

### Rim-walking enemies (the lane-flip steppers)

The enemies that flip from lane to adjacent lane are driven by a cluster keyed on the per-slot flag byte loc_283 and the per-slot target segment loc_2b9. **loc_9c4f** [seen] is the primitive at the bottom: it toggles bit 6 of loc_283[x] in place (`^ 0x40`) and returns the new byte. Bit 6 is the travel-direction / which-side flag for a slot walking the rim, and the write is genuinely exercised, hence the [seen] grounding.

**loc_9d67** [code] decides which side of the enemy the player currently sits on: it fetches the slot's target segment loc_2b9[x], differences it against the shared segment byte loc_200 through loc_a7a6, and then forces bit 6 of loc_283[x] — clearing it when the difference is negative (top bit set), setting it otherwise. In other words it records the rotational side of loc_200 relative to the enemy, which is the raw ingredient of a flipper chasing the player around the rim. Its bit-6 write to loc_283[x] does fire, but the routine is graded [code]: the discriminating head of the path was not exercised in the capture, so its game role is not confirmed from the trace.

**loc_9f81** [code] is a multi-entry per-slot segment step. Its front door (loc_9f81) re-derives the slot's side flag by calling loc_9d67, then unconditionally toggles bit 6 with loc_9c4f, then falls into the shared tail. A sibling entry, loc_9f8a, instead reseeds bit 6 from a fresh POKEY random draw — it clears bit 6 of loc_283[x] and re-sets it only when loc_60ca's bit 6 is set, i.e. a coin-flip on the initial travel direction. The shared tail (step9f99) is where the actual flip criterion lives: only on a live board (loc_111 ≠ 0) it may flip bit 6 again based on depth — if bit 6 is currently set it flips once the slot reaches the near end (loc_2b9-relative depth loc_2b9... via loc_2b9[x] read as depth == 0), and if bit 6 is clear it flips once depth ≥ 0x0f — then it stamps loc_10b = 0x66 and hands off to the segment-advance body loc_9e5f. The routine is [code]: it is not reached in the capture — its tail's stamp `loc_10b = 0x66` never appears there and its fire gate `loc_9f5f` shows no writes — so its role rests on the code.

Which slots even attempt a flip on a given pass is decided by **loc_9f5f** [code], a per-slot fire gate that was not reached in the capture. It fires only when the slot's fire bit is set — bit 5 (0x20) of loc_2df[x] — *and* a fresh POKEY random draw clears a threshold, i.e. `loc_60da >= loc_15f` (it returns early when the draw is below loc_15f). When both conditions hold it dispatches to one of the two step entries: if bit 6 of loc_159 is clear it always takes loc_9f8a (random reseed); with that flag set it splits on slot parity, sending even slots to loc_9f8a and odd slots to loc_9f81. It never performs the rim walk itself — loc_9f81 does — it only gates the attempt and picks which flavor of step runs.

**loc_9d82** [seen] advances a slot's turn animation, the smooth interpolation between two lanes while a flip is in progress. It first steps the slot's phase counter loc_2cc[x] one increment — down when bit 6 of loc_283[x] is set, up otherwise — then re-packs it as `(phase & 0x0f) | 0x80`, keeping four bits of phase with the high bit forced. It then branches on the low three bits of loc_283[x]. When that state field is *not* 4, it re-derives the target turn direction through loc_9ed7 (fed loc_283[x] ^ 0x40 and the segment loc_2b9[x]) and acts only when that direction equals the current phase byte: it drops bit 7 of loc_283[x] and either seats loc_2cc[x] from loc_2b9[x]+1 (if bit 6 survived) or walks the coordinate one lane, setting loc_2cc[x] to the old segment and decrementing loc_2b9[x] by one (mod 16). When the state field *is* 4 and the phase has reached a step boundary (low three bits zero), it settles the turn: it rotates loc_2b9[x] up by one if phase bit 3 is set, clears bit 7 of loc_283[x], reseeds loc_2cc[x] = 0x20, flips the sign bit (bit 7) of loc_28a[x], and — only while loc_3ab is zero — either kicks the next segment step via loc_9f81 (when the slot's depth loc_2df[x] has reached the shared target loc_202) or isolates the sign bit of loc_28a[x]. Every exit stashes bit 7 of loc_283[x] into the shared branch flag loc_10c.

**loc_9d06** [seen] is the per-slot step that settles a tube object once it arrives at the shared target depth. It first stamps the shared byte loc_202 into loc_2df[x]. If the slot's low-three-bit kind is 1 and the gate byte loc_3ab is nonzero, it just flips bit 7 of loc_28a[x] and stops. A slot already flagged negative (bit 7 of loc_283[x]) simply bumps its stashed depth loc_2df[x] by one and stops. Otherwise it decrements loc_108, and when loc_109 == 1 it scans slots 6..0 for a non-empty, non-self entry whose stashed byte matches loc_202, remembering the scanned index in loc_38 and breaking on a match (the losing index leaks through when none matches), then copies that slot's bit 6 — inverted — into loc_283[x]; when loc_109 ≠ 1 it re-derives the side flag through loc_9d67 instead. It closes by stamping loc_10b = 0x41 and incrementing loc_109. The effect is that a settling enemy adopts a travel direction consistent with a neighbor already heading the same way.

### Free-flight enemy physics (the continuous integrator)

The other motion family gives an enemy a real velocity and integrates it every frame. **loc_a618** [code] is the per-frame walk over all sixteen slots. It seeds the frame-active flag loc_10d from the spawn budget loc_10e, then loops x from 0x0f down to 0. A slot is "live" when loc_283[x] ≠ 0: for a live slot it integrates the position with loc_a6a9, steps the velocities toward rest with loc_a721, and raises loc_10d to 0xff; a *free* slot (loc_283[x] == 0) spawns a new enemy through loc_a65b whenever the budget loc_10e is still nonzero. loc_a721 leaves its last-axis whole byte in a register that rides forward into each subsequent spawn's sound cue. After the sweep it settles the slot counter loc_37 = 0xff, decrements the spawn countdown loc_10e on even frames (loc_3 bit 0 clear), and — if nothing was live or spawned (loc_10d still 0) — raises the mode-request byte loc_0 = 0x12. It is graded [code]: its entry and post-loop stores (`loc_10d`, `loc_37 = 0xff`) do not appear in the capture, so the routine is not reached there and its role rests on the code.

**loc_a6a9** [code] (not reached in the capture) integrates a slot's three motion axes. Each axis folds a low-byte velocity into a fraction cell (keeping the carry) and then folds that carry plus a signed whole-byte velocity into a whole coordinate. Concretely: axis 0 uses fraction loc_223, velocity-low loc_2e3, sign/whole-velocity loc_343, coordinate loc_283; axis 1 uses loc_203 / loc_2c3 / loc_323 / loc_263; axis 2 uses loc_243 / loc_303 / loc_363 / loc_2a3. Each whole result is clamped to the tube ring: for a rising axis (sign byte's bit 7 clear) reaching ≥ 0xf0 counts as overflow, and for a falling axis (bit 7 set) dropping below 0x10 counts as overflow. Axis 0's whole is committed to the shared coordinate cell loc_283[x] only at the end, and it is forced to 0 whenever *any* of the three axes overflowed the ring — an off-ring enemy has its primary coordinate collapsed. The axis-0 whole is also handed back as the routine's live-out.

**loc_a721** [code] (not reached) bleeds those same velocities back toward rest each frame. It seeds a saturation counter loc_29 = 0xfd and then, for each of the three axes, calls loc_a75d on the (velocity-low, velocity-whole) pair — axis pairs (loc_2c3, loc_323), (loc_2e3, loc_343), (loc_303, loc_363) — storing the stepped low and whole back. loc_a75d increments loc_29 whenever an axis crosses zero, so after three axes the counter reaches 0 only if all three saturated at once; in that case the slot's whole coordinate loc_283[x] is zeroed. The last axis's stepped whole is the returned register value.

**loc_a75d** [code] (not reached) is the single-axis decay: it drives a signed 16-bit velocity (whole in Y, low in A) one fixed increment toward zero. The increment is the ROM constant at loc_a788 (0x20). A negative whole (bit 7 set) *adds* 0x20; a non-negative whole *subtracts* it; and on crossing zero — a carry out of the 16-bit add, or a borrow out of the subtract — it saturates: it bumps loc_29 and forces both the low byte (loc_2a) and the returned pair to zero.

New free-flight enemies come from **loc_a65b** [code] (not reached), the spawner. It marks the slot active by writing 0x80 into all three whole coordinates loc_263, loc_283, loc_2a3 (mid-ring), then fills the three velocity pairs from the hardware RNG: velocity-low loc_2c3 = loc_60da with whole loc_323 from loc_a69b; velocity-low loc_2e3 = loc_60ca with whole loc_343 from loc_a69b *forced non-positive* (`if ((step & 0x80) === 0) step = -step` — an already-negative draw is kept, a positive one is negated); velocity-low loc_303 = loc_60ca with whole loc_363 from loc_a69b. It closes by ringing the spawn sound cue through loc_ccc1. The forced-negative middle axis biases every fresh enemy to travel one way along that axis. **loc_a69b** [code] (not reached) is the signed-random helper it leans on: it reads a 3-bit magnitude (`loc_60da & 0x07`, so 0..7) and negates it when the caller's incoming value has bit 0 set, yielding a signed nudge in [-7, +7].

### A second moving-object population

**loc_a18f** [seen] advances a separate twelve-slot moving-object table (x from 0x0b down to 0), and it splits into two regimes by slot index. Slots 8 and up carry a true 16-bit velocity: the low byte loc_2e6[x] takes the shared step loc_120, the high byte loc_2d3[x] takes loc_118 plus the fold carry, and while that high byte stays ≥ the limit loc_202 it is written back — but once it falls below the limit the object has passed the edge, so the routine decrements the count loc_a6, runs the teardown loc_a1e4, and clears loc_2d3[x]. Slots below 8 instead step a counter: loc_2d3[x] += 0x09, less 4 when the slot's flag loc_2f2[x] is set, then loc_a1fa returns an effective index and, if that slot's loc_2d3 has reached 0xf0, the count loc_135 is decremented and the slot cleared. The two regimes distinguish objects that fly with a velocity from objects that merely age a per-slot timer to a limit.

### Spike-column remap toward a rail

**loc_a7d2** [seen] remaps the eight-entry table loc_3fe — the moving spike/pulsar column set — against the reference/arm byte loc_115, and is a no-op when loc_115 is already zero. Walking x from 7 down to 0, a large entry (≥ 0x17) shrinks by a fixed 7; a mid entry (nonzero, < 0x17) snaps to a rail — 0xf0 when loc_115 is negative, else 0; and a zero entry adopts a rail from its forward neighbor (the wrap-around next slot), taking 0xf0 only while loc_115 is negative and that neighbor is nonzero and below 0xd5. Each result is OR-folded into an accumulator that lands in loc_29, loc_37 is stamped 0xff, and if every entry collapsed to zero the reference loc_115 itself is cleared, disarming the pass.

### Perspective point for a moving slot

Two helpers turn a slot's segment-plus-phase state into a screen point as it moves. **loc_b634** [seen] builds the point for slot x: it copies loc_57 into loc_2f, indexes the base-coordinate tables loc_3ce / loc_3de by the slot's segment loc_2b9[x] into loc_56 / loc_58, then offsets each by a signed delta drawn from tables loc_b68b / loc_b687 at the slot's phase low-nibble loc_2cc[x] & 0x0f, using a 0x80-biased signed-saturating add that clamps toward whichever sign overflowed; the results land in loc_2e (x) and loc_30 (y), loc_57 is mirrored to loc_2f, and a style pair loc_bcdc / loc_bcec indexed by loc_112 goes to loc_59 / loc_5a. **loc_b6fa** [code] (not reached in the capture) scales a delta by the fractional part of a slot's phase: it stashes the input in loc_29, takes the low three bits of loc_2cc[x] as a fraction in loc_2c, and runs three rounds of consume-LSB / conditional-add / arithmetic (sign-preserving) shift-right, returning the scaled byte — the sub-lane interpolation weight for an enemy caught between segments.

### Player rim motion (the shared reference)

The segment the enemies chase, loc_200, is itself an integrated value. **loc_b0ab** [code] nudges loc_200 by its pending signed sub-step and clamps it into [0, loc_127] (loc_127 being the top lane index for the current tube), publishing the clamped value both to loc_200 and to the returned accumulator/index live-outs; a value that came back negative floors to 0, and anything at or above loc_127 is pinned to loc_127. The sub-step itself is produced by **loc_adce** [code], a fixed-point integrator that folds a signed step times eight into a fractional accumulator: `loc_51 = ((loc_50 << 3) & 0xff) + loc_51`, carries the fold-carry plus the sign of loc_50 up into the returned byte (a negative step contributing 0xff as the high byte), and then clears loc_50. Both are reached but graded [code] because in the captured window the spinner was idle: loc_200 never moved off its value and loc_50/loc_51 stayed at their constants, so the fold carried nothing.

### Slot pacing and pending-step accounting

A small state-machine paces which slot advances and accumulates deferred steps; its mechanism is clear from the code even where the game-vocabulary role is not fully settled. **loc_c9af** [seen] ticks the active slot's countdown: it clears loc_4, decrements the current slot's timer loc_48[x] (x = loc_3d), and when the paired gate bytes loc_48 and loc_49 are both spent it finalizes through loc_c9f1. Otherwise, if the current slot's timer has hit zero it stamps loc_1 = 0x0c and loc_4 = 0x28, then walks the toggle loc_3f (flipping bit 0 whenever loc_3e is nonzero) until it lands on a non-empty slot, arms that slot's next interval from loc_46[x]+1 into loc_2 (0x1c on wrap to zero, else 0x02), and sets the frame timer loc_0 = 0x0a. **loc_c9f1** [seen] is the finalizer it calls: it scans the zero-page window loc_46 for x from loc_3e down to 0, keeps the maximum in loc_126 (stored decremented by one when nonzero), and sets loc_0 to 0x14, or to 0x10 when the status byte loc_5 is negative.

**loc_c81b** [seen] applies the accumulated pending steps and bumps a running tally; the code is precise even though its game-vocabulary meaning is not resolved (flagged). From the two-bit gate in bits 5/6 of loc_4e and a ≥ 2 test on the counter loc_6 it derives a step of 0..2, then clears loc_4e. When the gate is clear it optionally seeds four intro cells (loc_1 = 0x10, loc_4 = 0x20, loc_0 = 0x0a, loc_2 = 0x14, clearing loc_50 and loc_123) and returns a zero step. When the gate is set it drains loc_6 by the step (one decrement for the low gate bit, a second when bit 6 is also set), stores the step at loc_3e, and — only when the step is nonzero — ORs 0xc0 into the status byte loc_5, zeroes loc_16 / loc_18 / loc_0, decrements loc_3e by one (leaving step−1, forced to 3 when nonzero) as the tally index x, bumps a 16-bit tally at loc_40c[x] / loc_40d[x], and clamps loc_100 upward: `sum = loc_100 + loc_3e + 1`, i.e. **loc_100 + step**, pinned to a ceiling of 0x63. Its two register live-outs (the tally index and the step) are threaded onward by a deferred caller.

### A triad rotation with no confirmed role

**loc_b875** [code] rotates the three-entry array loc_22..loc_24 down by one — threading the displaced head value around the wrap — and mirrors each new entry into the paired array loc_809..loc_80b. It did not run in the capture, and it carries no direct call site; like other computed-jump table targets it is reachable only through a dispatcher (e.g. loc_b84e) rather than a plain call. Because its arrays are seeded elsewhere (to 0x00 / 0x04 / 0x0c) and it was never exercised, its role in the game's terms is not confirmed from the trace.

## The mathbox: projection and level tables

Tempest draws its tube in perspective by handing point coordinates to a hardware
math coprocessor (the "mathbox") mapped into the I/O page at `loc_6080`–`loc_6096`,
polling its busy line at `loc_6040`, and reading results back from `loc_6060`/`loc_6070`.
This subsystem is the machinery that turns a level's packed shape description into
the per-lane screen coordinates the vector renderer walks, and it is heavily
exercised: the projection driver runs on essentially every geometry pass.

### Projecting a point — `loc_c098` [seen]

`loc_c098` is the projection driver that pushes one point through the mathbox and
folds the result into two running 16-bit accumulators. It first forms a 16-bit
delta from the coordinate operands: the low byte is `loc_57 − loc_5f`, written to
the mathbox input `loc_6095`, and the high byte is the borrow-extended
`0 − loc_5b − (1 − carry)`, written to `loc_6096`; when that high byte comes out
negative (bit 7 set) the delta is clamped up to +1 (`loc_6096 = 0x00`,
`loc_6095 = 0x01`). It then computes two unsigned magnitudes with sign flags:
`|loc_58 − loc_60|` with its sign captured in `loc_33`, and `|loc_56 − loc_5e|`
with its magnitude also stashed in `loc_32` and its sign in `loc_34`. The first
magnitude is issued to the multiplier inputs `loc_608e`/`loc_6094`, after which the
routine spins on `loc_6040` bit 7 until the coprocessor is done. When it clears,
the two product bytes at `loc_6060`/`loc_6070` are read into `loc_63`/`loc_64`, the
`loc_32` magnitude is re-issued through `loc_608e`/`loc_6094`, and a second spin on
`loc_6040` bit 7 follows before `loc_6060`/`loc_6070` are read into `loc_61`/`loc_62`.

Each of the two reads is then folded into an accumulator with a saturating
signed add-or-subtract chosen by a sign flag. Gated on `loc_33` bit 7, the first
fold combines the offset pair `loc_68`/`loc_69` with `loc_63`/`loc_64`; on the
subtract path an overflow pins the accumulator to `0x0080` (low `0x00`, high
`0x80`), and on the add path an overflow pins it to `0x7fff` (low `0xff`, high
`0x7f`). Gated on `loc_34` bit 7, the second fold combines `loc_66`/`loc_67` with
`loc_61`/`loc_62` under the same saturation limits. The output pair `loc_61`/`loc_62`
and `loc_63`/`loc_64` are what the caller clamps and stores.

### Resetting the coprocessor — `loc_c1c3` [seen]

`loc_c1c3` prepares a clean state before a projection run. It zeroes the zero-page
work cells `loc_81`, `loc_91`, `loc_80`, `loc_78`, `loc_90`, and `loc_88`, then
clears the mathbox input block — `loc_6080`, `loc_6081`, `loc_6083`, `loc_6084`,
`loc_6085`, `loc_6086`, `loc_6087`, `loc_6089`, `loc_608d`, `loc_608e`, `loc_608f`,
and `loc_6090` — and finally writes the control register `loc_608c = 0x0f`. It
deliberately leaves `loc_6082`, `loc_6088`, `loc_608a`, and `loc_608b` untouched;
those registers are not part of what this reset covers. The routine is reached on
essentially every setup pass, but in the capture every observed transition is a
constant (the cleared cells were already zero, and `loc_608c` moved `0x0f → 0x0f`),
so the reset is confirmed to run while its clearing effect on nonzero state was not
directly witnessed.

### Unpacking the per-level nibble tables — `loc_c196` [seen]

`loc_c196` expands one level's packed shape/colour description into four parallel
byte tables. It takes the level selector `loc_9f & 0x70`, clamps it to at most
`0x5f`, and forms an index `X = (selector >> 1) | 0x07`. Walking `y` from 7 down to
0, it reads a packed ROM byte at `loc_c1fd + X` and splits it: the low nibble goes
to `loc_19 + y` and its display mirror `loc_800 + y`, while the high nibble goes to
`loc_21 + y` and its mirror `loc_808 + y`, with `X` decrementing each pass. The
`loc_800`/`loc_808` writes are the colour-RAM mirror of the two zero-page tables.
The trace confirms all four tables filled with varying real values in a single pass.

### Building a level's tube geometry — `loc_c235` [seen]

`loc_c235` is the once-per-level-setup routine that lays down the current tube's
lane geometry. It first derives a table seed by passing `[loc_46 + loc_3d]` through
`loc_c2e8` and taking `loc_112` as the row index `y`. From the level ROM tables it
sets `loc_5f` and `loc_5d` to the negated span `−[loc_bc8c + y]`, computes
`loc_a0 = 0x10 − that span`, marks the guard `loc_5b = 0xff`, loads
`loc_60 = [loc_bc9c + y]`, and `loc_111 = [loc_bccc + y]`. The offset pair is chosen
by mode: when `loc_2 == 0x1e` it copies `loc_68 = [loc_bcac + y]` and
`loc_69 = [loc_bcbc + y]` directly; otherwise it forms the signed 16-bit difference
`{loc_bcbc:loc_bcac} − {loc_69:loc_68}`, shifts it right four times keeping the low
byte, and stores that as the level geometry scale `loc_121`. It then clears
`loc_66`, `loc_67`, `loc_10f`, `loc_110`, and sets `loc_113 = 0x2c`.

Two loops build the coordinate arrays. The first walks the sixteen lanes `x` from
`0x0f` down to 0 with a neighbour index `ny` starting at the seed and decrementing:
it seeds base-coordinate tables `loc_3ce + x = [loc_b97c + ny]` and
`loc_3de + x = [loc_ba7c + ny]`, clears the projected-slot arrays
`loc_31a + x`, `loc_33a + x`, and `loc_39a + x`, and loads a third geometry table
`loc_3ee + x = [loc_bb7c + ny]`. The second loop fills the midpoint tables: for each
lane it rounding-averages a coordinate with its wrapping next neighbour
(`nx = (x + 1) & 0x0f`), writing `loc_435 + x = avg([loc_3ce + nx], [loc_3ce + x])`
and `loc_445 + x = avg([loc_3de + nx], [loc_3de + x])`. The average adds the two
bytes plus one and rotates the nine-bit sum right, carrying bit 8 into bit 7 — a
rounded midpoint between adjacent tube vertices.

### Packing a table byte — `loc_c2e8` [seen]

`loc_c2e8` reduces an input byte into a packed table lookup used by the geometry
seeding above. If the value is `>= 0x62` it is replaced by a masked hardware read
`loc_60ca & 0x5f` (a random/timer fallback). It splits the value into a quotient
`v >> 4` and remainder `v & 0x0f`, indexes the ROM table `loc_bc7c + remainder`,
stores that entry byte to `loc_112`, and returns the packed byte `(entry << 4) | 0x0f`
in A with the quotient in X and the remainder in Y — the high nibble carries the
table entry and the low nibble is forced to `0xf`.

### Projecting all sixteen lanes — `loc_c473` [seen]

`loc_c473` drives the whole tube through the projection pipeline to fill the
per-lane screen-coordinate slots. It stores its arguments into `loc_57` and the
output index `loc_38`, clears the clamp tally `loc_59`, and runs the lane counter
`loc_37` from `0x0f` down to 0. Each pass loads the lane's base coordinates
`loc_56 = [loc_3ce + col]` and `loc_58 = [loc_3de + col]`, calls `loc_c098` to
project them, then clamps the two returned signed pairs into the window
`[−4..+3]` (`0xfc..0x03`). The first pair (`loc_62`/`loc_61`) is written as value to
`loc_31a + out` and sign to `loc_32a + out`; the second pair (`loc_64`/`loc_63`) as
value to `loc_33a + out` and sign to `loc_34a + out`. Any clamp increments `loc_59`,
and the routine returns that clamp count. The clamp itself pins a negative value
below `0xfc` up to `0xfc` (sign `0x01`), pins a non-negative value at or above `0x04`
down to `0x03` (sign `0xff`), and otherwise passes the value and sign through.

### Snapping a coordinate to a reference — `loc_c453` [seen]

`loc_c453` nudges a coordinate up toward a reference during geometry work. It
returns immediately if the guard `loc_5b` is nonzero, or if `loc_57 − loc_5f` is
already `>= 0x0c`; otherwise it sets `loc_57` to `loc_5f + 0x0f`, capped at a
ceiling of `0xf0`. These are the same `loc_57`/`loc_5b`/`loc_5f` operands fed to the
projection driver, so the effect is to snap the working coordinate up to
reference-plus-`0x0f` when it has fallen too close to the reference. The observed
role write is a large jump snapping `loc_57` up, and `loc_57` independently pulses
across a wide range in the capture.

### Mode flag and scale — `loc_ca48` [code]

`loc_ca48` sets a mode flag bit and a paired scale byte from two gates. By default
it picks `a = 0x00`, `y = 0x10`; only when both `loc_117` and `loc_3d` are nonzero
does it select the alternate `a = 0x04`, `y = 0x08`. It copies bit 2 of the chosen
`a` into flag `loc_a1` while preserving the flag's other bits, and stores `y` to the
scale byte `loc_b4`. In the capture only the default branch ran and neither write
changed its cell — `loc_a1` kept bit 2 clear (`0x3 → 0x3`) and `loc_b4` held the
literal `0x10 → 0x10` — and the gated alternate path was not exercised, so the role
rests on the code.

### Loading level tables and arming the vector tail — `loc_b888` [code]

`loc_b888` rebuilds the level nibble tables and then seats the vector-list tail
cursor. It calls `loc_c196` to unpack the per-level shape/colour tables, then writes
`loc_139 = 0x7f` and `loc_13a = 0x04`. It carries no direct caller in the translated
set and is reached only through the level-setup computed dispatch. It was not reached
in the capture — the `loc_139`/`loc_13a` writes never fired — so its tail-cursor
seeding is code-level, MAME-grounding pending, and only inferred from the
instructions rather than observed.

## Sound, POKEY and the interrupt heartbeat

Tempest drives its audio through two POKEY chips mapped into the shared $60xx I/O page (POKEY1's audio registers at loc_60c0..loc_60c7 with control at loc_60c8, POKEY2's at loc_60d0..loc_60d7 with control at loc_60d8). The game never writes those registers directly from gameplay code; instead a sound event is requested by number, parked in a bank of sixteen software voice slots, and then ground down onto the POKEY registers a little at a time by a stepper that the interrupt handler calls on every pass. The same interrupt entry first runs a three-lane counter engine and then the voice stepper, so the two together form the machine's audio-and-timing heartbeat.

### Requesting a sound

Every in-game sound is asked for by a fixed request routine that loads one constant identifier and passes it toward the registrar. The bulk of them route through the enable gate loc_ccc3 (`[code]`), which reads the master audio-enable flag loc_5 and, only when its high bit (0x80) is set, falls through into the registrar loc_ccc7 — with sound muted the request is simply dropped. These triggers form a family spaced sixteen apart in identifier value, because (as the registrar shows below) each identifier is the top index of a sixteen-byte descriptor block: loc_ccb5 requests id 0x0f, loc_ccc1 id 0x1f, loc_ccea id 0x2f, loc_cd02 id 0x3f, loc_ccb9 id 0x4f, loc_ccb0 id 0x5f, loc_ccee id 0x6f, loc_ccf2 id 0x7f, loc_ccbd id 0x8f, loc_ccf6 id 0x9f, loc_ccfe id 0xbf, and loc_cd06 id 0xcf; several of them (loc_ccb0, loc_ccb5, loc_ccc1, loc_ccbd, loc_ccee, loc_ccf2, loc_ccf6) additionally thread the caller's X and Y through the gate so the registrar can restore them. All of these are `[code]`: each is a bare pass-through with no memory write of its own, so a write-tap cannot attribute the tail-call, though the registrar they reach is heavily `[seen]`. One member, loc_ccfa (`[code]`), is the exception that proves the rule — it loads id 0xaf and jumps straight to loc_ccc7, bypassing the loc_5 enable gate entirely, so that particular cue plays regardless of the mute flag. It was not reached in the capture.

The registrar loc_ccc7 (`[seen]`) turns an identifier into claimed voices. It stashes the caller's X and Y in loc_31/loc_32, then walks the sixteen voice slots from 0x0f down to 0, reading one descriptor byte per slot from the ROM table loc_cb01 at the identifier index and decrementing that index each step — so an identifier at value 0xaf reads the block loc_cb01+0xa0 through loc_cb01+0xaf, one entry per slot. A zero entry leaves its slot untouched; a nonzero entry claims the slot by momentarily writing the slot number into loc_bf, stamping the descriptor byte into that slot's frame cell loc_c0+slot, arming both of the slot's countdown timers (fast timer loc_e0+slot = 1 and slow timer loc_f0+slot = 1), and finally restoring loc_bf to the 0xff sentinel. The heavily-exercised writes into loc_bf, loc_c0+slot, loc_e0+slot and loc_f0+slot ground its role as the request loader that seats a sound's per-voice parameters.

### Stepping the voices onto POKEY

loc_cd0a (`[seen]`) is the per-interrupt sound engine step. It sweeps the sixteen slots from 0x0f down to 0, skipping any slot whose frame cell loc_c0+x is zero (idle) and the one slot whose index equals the loc_bf sentinel. For a live slot it decrements the fast timer loc_e0+x and does nothing further while that timer is still running; when the fast timer reaches zero it decrements the slow timer loc_f0+x. With the fast timer expired but the slow timer still alive it performs a single animation step: the current frame's high bit selects between the ROM pair loc_cbcc/loc_cbcd and the pair loc_cccc/loc_cccd, reloads the fast timer from the chosen table, adds the previous level held in loc_d0+x, and stores the new level. On odd slots it then keeps the prior high nibble while taking the new low nibble — consistent with odd slots mapping to POKEY's AUDC control registers, where the high nibble is the waveform/distortion and the low nibble the volume, so the animation drives level without disturbing timbre. When both timers have expired it instead walks the frame cell loc_c0+x forward by two repeatedly, each step pulling level and timer reloads from loc_cbcb/loc_cbce (or loc_cccb/loc_ccce for a high-bit frame), until a nonzero entry lands or the frame collapses to zero. In every case it finishes by publishing the slot's level loc_d0+x to a POKEY register: slots 0..7 to loc_60c0+x (POKEY1's eight audio registers) and slots 8..15 to loc_60c8+x (which lands at loc_60d0.. — POKEY2's eight). The observed POKEY-register writes and the level/timer churn ground it as the routine that actually renders the software voices to hardware.

loc_cd95 (`[seen]`) is the dual-POKEY reset. It first zeroes both SKCTL registers (loc_60cf and loc_60df) and the latch loc_720, then samples the two RANDOM registers loc_60ca and loc_60da once and re-reads them across a short five-poll loop; if either value has moved it latches the first sample into loc_720 — a working-generator self-test of the POKEY noise sources. It then writes the canonical SKCTL init value 7 to both loc_60cf and loc_60df, clears the eight audio registers of each chip (loc_60c0..loc_60c7 and loc_60d0..loc_60d7) along with the paired software voice-state arrays loc_c0.. and loc_d0.., and finally zeroes both AUDCTL registers loc_60c8 and loc_60d8. It is the from-cold silence-and-arm of the whole sound subsystem.

### The interrupt counter engine

loc_cf24 (`[seen]`) runs on every interrupt immediately ahead of the voice stepper. It maintains three parallel lanes indexed X = 2,1,0, each associated with one bit of the control byte loc_8 (lane 2 keys on bit0, lane 1 on bit1, lane 0 on bit2, extracted by a staged shift sequence). The shifted-out bit selects how the lane's five-bit position loc_d+x moves: on one branch the position is decremented (gated so it only steps while in range, with an additional condition on the low three bits of loc_7 reaching 7), and on the other it is advanced by 0x20 with wrap and clamped up to the maximum 0x1f. A clear bit3 of loc_8 forces the shared counter loc_c to 0xf0; while loc_c is nonzero it drains and blanks the lane's position loc_d+x and reload timer loc_10+x. The per-lane reload timer loc_10+x counts down and, on reaching zero or on a position tick, reloads to 0x78 and flags the lane as having ticked. A tick folds a small per-lane value into the two running accumulators loc_16 and loc_17 (each a value+1 add carrying forward) and bumps the lane counter loc_13+x; that per-lane value depends on X: lane 0 (X = 0) contributes zero; lane 1 (X = 1) contributes 0x01 when loc_9 bit 4 (mask 0x10) is set, else 0; lane 2 (X = 2) contributes ((loc_9 & 0x0c) >> 2) + 2 (plus any carry) when that is nonzero, else 0 — loc_9's bits gate each lane while the added magnitude stays small. After the three lanes it uses the top three bits of loc_9 to index the ROM table loc_cfd9, subtracts that entry from accumulator loc_16, and while the result stays non-negative advances loc_18; the low two bits of loc_9 then drive a signed combine of loc_17 and loc_18 that can bump loc_6. Finally, gated by a clear bit0 of loc_7, it makes two clamp passes over the lane-counter triple loc_13/loc_14/loc_15: the first pass subtracts **0x10** from any entry that is at least 0x10 (via an add of 0xef with carry set) and stops the whole clamp the moment any entry is reduced, and the second pass subtracts **0x11** from each nonzero entry (an add of 0xef with carry clear) until one goes negative — the two passes deliberately use different decrements. The write-tap confirms the position, timer and counter cells cycling as described; the mechanism is a clean interrupt-time counter/accumulator engine, but the code alone does not settle the game-facing meaning of the accumulators, so no confident role is claimed here beyond "the interrupt heartbeat's counter step."

### POKEY-control and math-box helpers on the shared page

loc_dbe0 (`[code]`) is a small bit-packer over the two AUDCTL registers. It stores its incoming byte into loc_60db, copies only the low three bits of loc_60d8 into both the scratch cell loc_37 and loc_60cb, and returns those three bits merged with one relocated bit — bit5 of loc_60c8 shifted down into bit3. Note that the mirror into loc_37/loc_60cb carries only the low three bits; the extra relocated bit appears in the returned value alone, not in the mirrored copy. loc_dce6 (`[code]`) is a driver for the math coprocessor that shares the same $60xx page as the POKEYs (it is grouped here only by that shared I/O region). ### Option-switch decode

loc_d6bb (`[seen]`) reads the cabinet's option/DIP inputs and unpacks them into configuration cells. It copies the option port loc_e00 into loc_a, then slices that byte three ways through ROM lookup tables: bits5-3 index loc_d6f7 into loc_156, bits7-6 index loc_d6ff into loc_158, and bits2-1 index the paired tables loc_d6b3/loc_d6b4 into loc_ac and loc_ad. Its caller re-runs this decode and compares the freshly read snapshot against a cached copy to notice when the operator settings change; the observed writes into the config cells ground its role as the settings decoder.

### The sorted-record request engine

loc_ac3f (`[seen]`) and loc_ad6e (`[code]`) operate a per-channel sorted-record queue over the loc_600 block; the machinery is fully visible in the code, though the code alone does not fix which game-facing subsystem it ultimately feeds. loc_ac3f clears bit6 of loc_5, optionally pre-clears a scratch block through loc_ca62 when loc_9 & 0x43 equals exactly 0x40, queues a request through loc_ddfb, and zeroes loc_601. For each channel it bubble-sorts the record rows keyed lexicographically on the triple tables loc_620/loc_61f/loc_61e — carrying a parallel payload through loc_51e/loc_51f/loc_520 for rows above a threshold — walking a cursor downward by two entries at a time (three while it is still high, at or above 0x55) and tallying the number of settling passes into loc_605, which it then stores into loc_600 indexed by parity. The observed pass-count and per-channel writes ground the sort as real work.

loc_ad6e (`[code]`) is the per-frame tick of the currently active request slot, and it was not reached in the capture (its gating conditions were never met), so its behaviour is read from the code only. It seeds loc_1 to 0x06; when the low five bits of loc_3 are zero it decrements the countdown loc_605 and, if that expires, sets loc_00 to 0x14 and returns. ## The EAROM high-score store

The cabinet keeps its high-score table in a small non-volatile EAROM (an ER-2055-class part) that survives power-off, so the initials a player enters after a good run are still there at the next power-up. Software never touches that chip directly on the frame it wants to: it *queues* a transfer by setting three request cells and then lets a state machine, `loc_de1b`, grind through the slow serial access one small step at a time across many frames. The three request cells are `loc_1c6` (the index / blank-mode byte), `loc_1c7` (the per-region pending-request bits), and `loc_1c8` (the per-region direction bits — set means write-out, clear means read-back for that region).

### Queuing a request — the setter family

Everything that wants EAROM work funnels through one shared tail, `loc_ddff`, which stamps its `Y` argument into `loc_1c6` and then *OR*s its `A` argument into both `loc_1c7` and `loc_1c8`. Because it ORs rather than assigns, several requests can accumulate into the same pending bitmap before the machine drains them. The two intermediate hops preset that pair of arguments: `loc_ddfd` forces the index byte to `0x00` and passes a caller-chosen mask through to the tail, and `loc_ddfb` is the fixed-mask-`0x04`, zero-index entry (queue region-bit 2 with a clean index). `loc_ddfb`'s mask-`0x04` writes into `loc_1c7`/`loc_1c8` are the ones actually seen in the capture, so this alt-entry chain is grounded — **`loc_ddfb` [seen]**.

The remaining entry points are variations on the same tail that did not fire in the capture. `loc_ddf1` is the "all blocks, write mode" fixed entry: it drives the index byte to `0xff` and ORs the full mask `0x07` (all three region bits) into `loc_1c7` and `loc_1c8`. That particular pairing — index `0xff` together with mask `0x07` — was never observed on the wire; only the mask-`0x04` traffic from `loc_ddfb` reached the shared cells, so this entry stays code-level — **`loc_ddf1` [code]**. `loc_ddf3` forces the index byte to `0xff` (blank/erase mode) and lets the caller's live-in mask flow through the tail unchanged, requesting that the named regions be written out with their source RAM cleared as they go; it was not exercised — **`loc_ddf3` [code]**. `loc_ddf7` supplies the constant mask `0x03` (regions 0 and 1) into the zero-index merge; mask `0x03` is never seen arriving at the merge, so this path is unexercised — **`loc_ddf7` [code]**. Finally `loc_dde9` is a thin trampoline that hands the fixed mask `0x04` into `loc_ddf3`, i.e. queue region-bit 2 in blank/erase (index `0xff`) mode; it has no writes of its own and did not run — **`loc_dde9` [code]**.

### Kicking off a full save — `loc_de11`

`loc_de11` is the one caller that seeds the machine outright rather than OR-merging into it: it *assigns* `loc_1c7 = 0x07` (mark all three regions pending) and `loc_1c8 = 0x00` (all directions cleared), then falls straight into `loc_de1b` to begin servicing. Because it plants the state directly and its two writes (the `0x07` into `loc_1c7`, the `0x00` into `loc_1c8`) are observed, it is grounded as the full-table initiator — **`loc_de11` [seen]**. The `SET`-not-`OR` behaviour is what distinguishes it from the request-setter family above.

### Servicing the transfer — `loc_de1b`

`loc_de1b` is the EAROM/high-score transfer state machine, and it is the heavily-exercised heart of this subsystem — **`loc_de1b` [seen]**. It is written to do a little work and return, so the expensive serial handshake is spread over frames: an outer loop re-enters from the top only when a phase finishes cleanly, otherwise each phase writes the control strobe and returns.

When it finds itself idle with work pending (`loc_1ca == 0` and `loc_1c7 != 0`) it starts a fresh region. It clears the entry cursor `loc_1cb`, the running checksum `loc_1cf`, and the walking-bit mask `loc_1ce`, then isolates a single region to service. It does this by seeding a carry and rotating: on each pass it rotates that carry into the top of `loc_1ce` (shifting `loc_1ce` right) while shifting `loc_1c7` left and testing what falls out of bit 7, stopping the instant a set bit carries out. Because it shifts the request mask *left* and breaks on the first bit-7 carry-out, it isolates the **highest (most-significant) set bit** of `loc_1c7` — the top-most pending region is always serviced first, never the lowest. The loop counter `x` (started at `0x08`, decremented each pass) records how far it walked; doubled (`x << 1`) it becomes the index into four packed ROM tables: `loc_dddd` seeds the port sub-index `loc_1cc`, `loc_ddde` seeds the end index `loc_1cd`, and `loc_dde3`/`loc_dde4` load the low/high halves of the row pointer into `loc_bd`/`loc_be` (that `(loc_be:loc_bd)+y` pointer is how the machine reaches the region's bytes in RAM). The mode byte `loc_1ca` is set to `0x80` when this region's `loc_1c8` direction bit is set (write-out) or `0x20` when it is clear (read-back) — the test is `loc_1ce & loc_1c8`. It then clears the region's bit out of the pending map with `loc_1c7 = loc_1ce ^ loc_1c7`, so the next fresh start finds the next-highest region.

With a region selected, the common block resets the control port `loc_6040` to `0` and bails out entirely if the mode byte `loc_1ca` has gone to zero (nothing live). Otherwise it loads the entry cursor `loc_1cb` into `y`, the port sub-index `loc_1cc` into `x`, and rotates `loc_1ca` left to decide which phase runs this pass:

- **Setup phase.** If the carry rotated out of `loc_1ca` (the `0x80` init state), it emits the shifted mode byte to the addressed EAROM cell `loc_6000 + x`, drops `loc_1ca` to `0x40`, writes control strobe `0x0e` to `loc_6040`, and returns.
- **Write-out phase.** Otherwise, if the shifted mode still has bit 7 set, `loc_1ca` is forced to `0x80` and the source byte is pushed to the chip. If the blank-mode byte `loc_1c6` is nonzero, the source RAM cell reached through the row pointer at offset `y` is first zeroed (the erase-as-you-write behaviour that `loc_ddf3`/`loc_dde9` request), then read; when the port sub-index reaches the region's end (`x >= loc_1cd`, the last cell) the machine instead retires the region (`loc_1ca = 0`) and writes the accumulated checksum `loc_1cf` as that final byte. Either way the byte lands at `loc_6000 + x`, the control strobe becomes `0x0c`, and before returning the byte is folded into the running checksum `loc_1cf` and both cursors (`loc_1cb`, `loc_1cc`) advance.
- **Read-back / verify phase.** If neither carry was set, the machine performs the EAROM read handshake — pulsing `loc_6040` through `0x08 → 0x09 → 0x08` while addressing `loc_6000 + x` — and takes the data out of the read register `loc_6050`. For an ordinary cell it stores that byte back into RAM through the row pointer and folds it into `loc_1cf`. For the region's final cell it treats the read byte as a checksum: it XORs it against the accumulated `loc_1cf`, and if the result is zero the region verified good and is retired. If the result is nonzero the region is corrupt — the machine walks the entry cursor `y` back down from `loc_1cb` to zero, wiping every RAM cell of that region through the row pointer, and records the failed region by OR-ing its walking bit into `loc_1c9`. So `loc_1c9` is the "region failed verification and was cleared" flag, and `loc_1cf` is the checksum that guards the stored table.

Each completed non-terminal step writes a nonzero value to the control strobe `loc_6040` and returns; only when a step finishes with a zero strobe does the outer loop fall through to process the next entry within the same call, which is how the machine bounds the work it does per invocation while still draining a whole region over time.

## State-reset, init and per-frame update chains

This subsystem is the machine's plumbing for entering and maintaining a playing state: the cold seeders that stamp fixed constants into work RAM at state entry, the reset leaves that blank per-object tables and their flags between waves and lives, the wave/mode (re)init that rebuilds the per-segment arrays and tallies them, the per-frame maintenance that ages objects and steps the phase clock, the scoring passes, and the configuration-snapshot rebuild that keeps two control blocks matched to the option switches. Several of these are callers that reach their work through direct calls to the leaves below; they are described here as the game machine driving its own helpers.

### Cold seeders

`loc_921b` [seen] is reached through the boot chain (`loc_9025` falling into `loc_902b`) and seeds five cells with fixed values: `loc_200` to `0x0e`, `loc_51` to `0xf0`, `loc_106` to `0x00`, `loc_201` to `0x0f`, and `loc_202` to `0x10`. `loc_200` and `loc_51` vary elsewhere, so these are genuine state cells getting their startup values; `loc_201` is the sign-gated control byte and `loc_202` the counter that the per-frame pass `loc_a504` later drives.

Three more seeders overlap on the zero-page work cells `loc_0` through `loc_4`, each loading them for whatever mode is being entered. `loc_b0e7` [seen] runs straight through, writing `loc_0=0x0a`, `loc_2=0x00`, `loc_4=0xdf`, `loc_1=0x12`, and the pair `loc_14e=0x19`/`loc_14d=0x18`, with all six writes observed at their own PCs. `loc_c97b` [seen], reached only through computed dispatch (no static call site), lays down a smaller block: `loc_2=0x04`, `loc_1=0x00`, `loc_0=0x0a`, `loc_4=0x14`. `loc_ca18` [seen] first masks `loc_5 &= 0x3f` to drop its top two flag bits, then seeds `loc_3e=0x00`, `loc_2=0x1a`, `loc_0=0x0a`, `loc_4=0xa0`, `loc_16b=0x01`, and `loc_1=0x0a`. A family of leaves blanks a contiguous per-object table and then clears the scattered flags that go with it. `loc_926f` [seen] zeroes the seven bytes `loc_2df`..`loc_2df+6` top-down before clearing `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, and `loc_146` — several of these hold non-zero values elsewhere, so the reset is meaningful rather than a no-op. `loc_928f` [seen] blanks the twelve bytes `loc_2d3`..`loc_2d3+0x0b` and then clears `loc_135` and `loc_a6`; `loc_2d3` is the per-slot counter block that the scoring pass `loc_a1fa` reads and resets, and `loc_135` is the state cell that same pass decrements. `loc_929f` [seen] zeroes the eight-byte table `loc_30a`..`loc_30a+7` and clears the trailing flag `loc_116`. The smallest of these, `loc_92ad` [seen], makes a single meaningful write, clearing `loc_50` (a cell that ranges widely elsewhere) to zero at init.

`loc_ca62` [seen] zeroes the six-byte scratch block `loc_40`..`loc_40+5`, which its callers then re-stage as three-byte entries. `loc_a831` [seen] clears `loc_3aa` and `loc_125` together; `loc_125` is the block-ready latch that the wave reset `loc_a5cb` drives to `0xff`, so clearing it here is role-defining. `loc_a7bd` [seen] blanks the eight-byte table `loc_3fe`..`loc_3fe+7`, then overwrites the last slot `loc_405` with `0xf0` and arms the flag `loc_115` to `0xff`; its per-frame caller runs this once a descending object crosses a threshold while `loc_115` is still clear, so it resets the spike table and re-arms in one shot.

### Wave and mode (re)init

`loc_9234` [seen] rebuilds the per-segment array that the rest of the round reads. It writes the header `loc_3ab` from `loc_15b` (observed varying, `0xf`→`0xc`), then fills the sixteen entries `loc_3ac`..`loc_3ac+0x0f` with the byte in `loc_15a`; in the capture `loc_15a` was 0 so the body stayed 0, but `loc_3ab` is a real changing cell that drains elsewhere. That `loc_3ac` array is the segment-height/limit table which `loc_a5cb` tallies and `loc_a1fa` reads as a per-target limit.

`loc_a5cb` [seen] is the wave-state reset with a spiked-segment tally. It sets `loc_0=0x20`, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c`, and `loc_123`, and sets `loc_105=0x02`. It then counts how many of the sixteen `loc_3ac` entries are non-zero into `loc_123` — observed climbing `0x0`→`0x6`, a real tally of occupied segments. If any are occupied and the level in `loc_9f` is below `0x07`, it loads an intro parameter block (`loc_4=0x1e`, `loc_0=0x0a`, `loc_2=0x20`, `loc_123=0x80`). It finishes by driving `loc_125` to `0xff` to mark the block ready.

`loc_ad22` [seen] drains a packed request word two bits at a time to spawn the next requested slot. On each pass it derives the slot index into `loc_3d` from the low two bits of `loc_603` minus one, then shifts `loc_603` right twice to consume them; a pass whose slot byte `loc_600+index` is zero or `0x09` or higher is skipped. For a live slot (`1`..`8`) it triples that byte, XORs the result with `0xff`, and subtracts `0xe5`, storing the value in `loc_602`; it then arms the paired subsystem through `loc_ca48`, seeds `loc_605=0x60`, `loc_4e=0x00`, `loc_50=0x00`, and `loc_604=0x02`, initializes the per-slot table through `loc_a789`, and marks `loc_0=0x24` (armed) before returning. When the word is exhausted (`loc_603` reads 0) it exits idle with `loc_0=0x14`.

### Per-frame maintenance

`loc_a504` [seen] is the tail-of-frame update, split by the sign of the control byte `loc_201`. The negative arm (the one exercised) first bails if any of `loc_135`, `loc_a6`, or `loc_116` is set. Otherwise it ages every live shot in `loc_2df`, walking down from index `loc_11c`, by adding `0x0f` to each non-zero entry and snapping it to `0x00` once the sum reaches `0xf0` (objects reaching the far end expire). It then branches on the slot flag `loc_48[loc_3d]`: when that flag is not `0x01` it bumps `loc_202` by `0x0f` and proceeds once it reaches `0xf0`; when it is `0x01` it clears `loc_10f`, sets `loc_114=0x01`, and steps the sixteen-bit clock `loc_5b`:`loc_5f` down by `0x20`, proceeding when the high byte `loc_5b` reaches `0xfa`. On proceed it sets `loc_00=0x06`, runs the reset leaf `loc_928f`, and folds `loc_108 + loc_109 + loc_3ab` back into `loc_3ab`, clamped to `0x3f`. The positive arm bumps a timer in the `loc_00`-based array at index `loc_40` (only when `loc_455|loc_11b` is non-zero and `loc_42` exceeds `0x17`); then, unless `loc_106` is set, when `loc_3ab|loc_116` is clear it scans `loc_2df` from `loc_11c` for any shot at or above `0x11` and, finding none, runs `loc_a5cb` followed by `loc_928f`; three further gates (`loc_4d & 0x60` non-zero, `loc_5` bit 7 set, and `loc_9 & 0x43 == 0x40`) can instead trigger `loc_a5cb` alone.

`loc_a1fa` [seen] is the per-slot scoring and hit pass. It reads the slot's target index `y = loc_2ad[x]` and the per-target limit `loc_3ac[y]`, returning the slot unchanged when the limit is 0. `loc_ca6c` [seen for the score add; award path code-only] is the multi-byte BCD score adder with a bonus-life threshold machine. It is gated on `loc_5` bit 7. It selects the score-cell triplet base from `loc_3d` — `loc_40`/`loc_41`/`loc_42` when `loc_3d` is zero, the `+3` triplet otherwise. That award and bonus-life half did not fire in the capture, so it stands code-only.

## Utilities and shared tails

This subsystem gathers the small leaf helpers the rest of the machine leans on: a binary-to-decimal converter used when a raw count has to become a display number, a couple of table seeds, several bare return stubs that give branch-happy callers a clean exit, and one register-only constant provider. They do little on their own but shape how their callers behave.

### Decimal conversion and score-style emission

The workhorse of the group is **loc_aaf5** ([seen]), a classic double-dabble binary-to-BCD converter. It takes the byte in A and runs eight passes: each pass shifts the top bit out of the source and doubles a decimal accumulator, folding the shifted-out bit back in as the low carry (the `bcdDouble` helper does the decimal-mode double, adding 0x06 to a nibble that overflows past 9 and 0x60 to a byte that overflows past 0x99). When the loop finishes it writes the finished packed-BCD value to **both** `loc_29` and `loc_2c` — the same value lands in both cells, so both range across the full BCD span 0x00..0x99. (The narrower 0x00..0x63 span belongs to the *raw binary input* that callers feed in, not to this routine's BCD output.) The write-tap confirms this heavily-exercised routine actively storing digits into `loc_29` and `loc_2c`.

That converter is wrapped by two callers that turn "I have a number" into "put this number on the tube." **loc_af71** ([code]) first clamps its incoming byte to a maximum of 0x63 (`Math.min(a, 0x63)`) and then packs-and-emits it: it drives `loc_af77`, which runs `loc_aaf5` to convert the byte to BCD in `loc_29` and then calls `loc_dfb1` to shovel that single zeropage byte out as vector-display nibbles. So loc_af71's job is the guard-and-display step — cap the value at a two-digit decimal ceiling, convert, draw — with no role-defining write of its own; its role rests on the code path it drives rather than any cell it touches, hence the [code] tag.

**loc_93e0** ([seen]) is the machine's byte-splitter, reached exclusively through the three call sites in loc_92c5 (0x9387, 0x9396, 0x93a4). It folds A's top three bits, MSB first, into the low bits of a 0xff seed: three iterations each shift A left one place while rotating the popped bit into an accumulator that starts at 0xff, so the accumulator ends up as `0xf8 | (top three bits of the input)` and is stashed to `loc_29` (its only own-cell write — the observed seed write, e.g. 0xff rolling toward 0xfe). The register live-outs carry the real payload: A holds the input shifted left three times (the low five bits promoted up — a fine value), Y holds the seed, and X is derived as `((acc ^ 0xff) + 0x0d) >> 1`, which lands in {6..10} as a coarse index (acc ∈ {0xf8..0xff}, so `acc ^ 0xff` ∈ {0..7}). It is a pure compute helper — one scratch write, three register results the caller consumes.

### Geometry-rebuild request tail

**loc_ac36** ([seen]) is the "flag both blocks for rebuild" tail. It ORs 0x03 into `loc_1c9` and returns the merged value, setting the two low pending-rebuild request bits; the write-tap caught this store landing 0x7 into `loc_1c9` (bits 0-1 present alongside a pre-existing bit). It is reached from loc_ac20 (when the live geometry snapshot no longer matches its cached latch) and from loc_abac, and the bits it raises are later consumed inside loc_abac, whose bit-0 and bit-1 paths perform the actual block rebuilds. After raising the flags loc_ac36 continues into the shared return **loc_ac3e** ([code]), a lone RTS that also serves as loc_ac20's no-op exit: when loc_ac20 finds the live geometry state (`loc_a & 0xf8` versus cached `loc_71e`, and `loc_16a & 3` versus cached `loc_71f`) already matching the latch, it branches straight here with nothing to rebuild. It has no write to ground, so it stays [code], and in the capture only that match-to-ac3e no-op path was exercised.

### Bare return stubs

Several routines exist purely to give a branching caller a clean landing spot, and none has a groundable write, so all carry [code]. **loc_ac07** is the "nothing to rebuild" exit for loc_aba2: when `loc_1c9 & 3 == 0` (no pending request bits) loc_aba2 tail-branches here and returns. **loc_af6e** is the exposed RTS tail of the loc_af3f draw routine; loc_af26 branches to it when `loc_600 | loc_601 == 0`, i.e. both draw slots are empty and there is nothing to draw. **loc_9bcf** is a do-nothing handler slot inside a computed-dispatch table: it returns immediately, letting the caller's own return unwind — it is reachable only through its dispatcher (never callerless), just unexercised through it in the capture, and a write-tap cannot confirm reach for a routine that writes nothing. All three are honest no-ops whose only "behavior" is to end the call.

### Constant provider (proposer trap)

**loc_b955** ([code]) looks like a bit-population helper but is not. It reads `loc_57`, shifts it right four places, and runs a count-style `iny`/`lsr`/`bne` loop — but the loop's result is thrown away: the following `clc`/`adc #2` computes `0 + 2` and `ldy #0` clears Y, so the routine **always** returns the constant pair A = 2, Y = 0 regardless of the value in `loc_57`. The idiomatic form makes this explicit, returning the fixed pair and touching no memory. A blind reader may mislabel it as "log2 / bit-count of loc_57"; the code shows it is a constant provider, and it was not reached in the capture.

### Table seeds

Two straight-line seeders prime paired arrays and both went unreached in the capture ([code]). **loc_b85f** loads a matched pair of three-entry arrays with the fixed ramp 0, 4, 12: it writes `loc_22`/`loc_809` = 0x00, `loc_23`/`loc_80a` = 0x04, and `loc_24`/`loc_80b` = 0x0c, then returns with A = 0. It is a computed-jump target of the `loc_b84e` dispatcher (the `y >> 1 == 0` arm) but is not reached in the capture — none of its stores fired. **loc_92b2** swaps two parallel 18-entry tables slot for slot, exchanging `loc_3aa + x` with `loc_3bc + x` for x from 0x11 down to 0 using a temporary — after it runs, each slot holds what its sibling held. Its two swap stores (the writes to `loc_3bc` and `loc_3aa`) never fired, so it too is not reached in the capture; the cells appear in the trace only as constant zero at unrelated points, which is consistent with a swap that never ran.
