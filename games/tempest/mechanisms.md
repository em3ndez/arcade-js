# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
object-record draw loop, the mathbox projection, sound, and the EAROM — down to the caller routines that
drive them and the computed-jump dispatchers (`loc_b84e`, `loc_b5d7`, `loc_9a88`); the frozen-oracle
remainder (the remaining dispatcher spine and the deferred register-thread callers) is noted at the end.
The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM (`0x2000-0x2FFF`)
each frame and the Analog Vector Generator draws it, with the vblank interrupt as the per-frame heartbeat
and a game-state index driving a computed-jump dispatch that selects the mode handler (attract, coin-in,
play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each moving object is driven by a small byte-script rather than by open-coded logic. The script bytes live in the table `MOTION_SCRIPT_TABLE`, a rolling cursor `SCRIPT_CURSOR` names the current position within it, a branch flag `SCRIPT_BRANCH_FLAG` records the outcome of the most recent test, and a walk-continuation flag `SCRIPT_WALK_CONTINUE` keeps the driving walk alive. The routines here are the opcode handlers: the script-walker `runObjectMotionScripts` fetches a script byte and hands control to one of them, so each is reached through the walker's computed dispatch rather than by a fixed caller. Together they form a tiny instruction set — load, jump, test, and time — that steers an object's per-slot cells.

**Loading operands into a slot.** The two store opcodes both begin by stepping the cursor forward and then deposit a value into the acting object's cell `loc_298,x`. `writeScriptConstantToSlot` [seen] does the immediate form: it advances `SCRIPT_CURSOR` by one (wrapping to a byte) and copies the script byte it now points at, `MOTION_SCRIPT_TABLE[SCRIPT_CURSOR]`, straight into `loc_298,x` — the operand written verbatim into the slot. `writeScriptVariableToSlot` [seen] is the indirect form: after the same one-step advance it treats the fetched script byte `MOTION_SCRIPT_TABLE[SCRIPT_CURSOR]` as a zero-page address and copies the *live variable* found at `GAME_MODE + ptr` into `loc_298,x`, so the slot receives a runtime value chosen by pointer rather than a constant baked into the script. Both are confirmed by the cursor-advance write and by the slot writes landing across `loc_298,x`'s object cells.

**Control flow.** Three opcodes move the cursor conditionally or unconditionally. `skipScriptOperandWhenFlagClear` [seen] is the conditional skip: if the branch flag `SCRIPT_BRANCH_FLAG` is nonzero it does nothing, and otherwise it advances `SCRIPT_CURSOR` by two, stepping the cursor past a two-byte operand — the two increments were both observed. `jumpScriptCursorWhenFlagClear` [seen] is the conditional jump: it first advances `SCRIPT_CURSOR` by one, then, only while `SCRIPT_BRANCH_FLAG` is zero, replaces the cursor entirely with the operand target `MOTION_SCRIPT_TABLE[SCRIPT_CURSOR]`, reloading the program counter to jump; a nonzero flag lets execution fall through past the operand. `followScriptGoto` [seen] is the unconditional goto, and it is exercised heavily: it uses the current cursor value to index the *parallel* table `MOTION_SCRIPT_GOTO` and writes `MOTION_SCRIPT_GOTO[SCRIPT_CURSOR]` back as the new cursor, following the operand chained after the current opcode. This same tail is shared as the continuation of the timer opcode below.

**Tests that set the branch flag.** Two opcodes compute `SCRIPT_BRANCH_FLAG` for the conditional skip and jump to consume. `setFlagIfSlotPastSegmentBound` [code] tests position against a segment boundary: it reads the slot's segment `ENEMY_SEGMENT,x`, looks up that segment's boundary in `LANE_LIMIT` (an entry of zero reads as the maximum `0xff`), and sets `SCRIPT_BRANCH_FLAG` to 1 when the boundary is at or beyond the slot's depth `ENEMY_DEPTH,x`, else 0 — a "have we crossed the edge" test. Its store to `SCRIPT_BRANCH_FLAG` was not reached in the capture (the flag was produced elsewhere during the captured window), so it stands [code]. `setFlagFromPhaseAccumulatorSign` [code] tests a phase accumulator instead: it forms `((ENEMY_ANIM_DELTA << 2) + ENEMY_ANIM_ACCUM) & ENEMY_ANIM_ACCUM & 0x80`, then exclusive-ORs that against `0x80`, so `SCRIPT_BRANCH_FLAG` becomes `0x00` when the resulting high bit is set and `0x80` when it is clear — a sign/phase probe on the `ENEMY_ANIM_DELTA`/`ENEMY_ANIM_ACCUM` accumulator pair. All arithmetic wraps to a byte. Its store to `SCRIPT_BRANCH_FLAG` was likewise not reached in the capture, hence [code].

**Timing.** `holdSlotPoseUntilTimerExpires` [seen] is the dwell opcode. It decrements the acting slot's timer `loc_298,x`; while that timer remains nonzero it delegates to `followScriptGoto`, running the `MOTION_SCRIPT_GOTO`-driven goto step so the object keeps cycling through its current state; only when the timer reaches zero does it bump the shared cursor `SCRIPT_CURSOR`, releasing the script to advance to the next instruction. This is the mechanism by which a scripted object holds a pose for a fixed number of frames before moving on.

**Housekeeping.** `endObjectMotionScript` [seen] is a one-line leaf that clears the walk-continuation flag by writing `SCRIPT_WALK_CONTINUE = 0`; it is reached often, ending the walker's inner loop over script entries so the per-object pass terminates. `advanceCursorPastPackedRecord` [code] is a cursor-skip helper that advances the list cursor by a fixed run to step over a packed record without reading it — its first entry moves the cursor forward by three (it bumps by one and falls into the second entry) and its second entry moves it by two. It touches only the cursor register and writes no memory, so there is nothing observable to lift it past [code].

## Vector coordinate lists and the display cursor

Two zero-page pointers govern this subsystem: `COORD_LIST_PTR_LO`/`COORD_LIST_PTR_HI` names the current *coordinate list* being walked, and `DRAW_CURSOR_LO`/`DRAW_CURSOR_HI` is the *display cursor* — the write head that lays vector words into the AVG display RAM at `$2000`-`$2fff`. One family of routines seats and walks the coordinate-list pointer; another family emits words through the display cursor and steps it forward.

### Seating the coordinate-list pointer

`seatCoordListPointer` [seen] is the pointer-seating core. Indexed by the incoming Y, it reads the low byte of a list pointer from the ROM table at `LIST_PTR_TABLE_LO`+Y into `COORD_LIST_PTR_LO` and the high byte from `LIST_PTR_TABLE_HI`+Y into `COORD_LIST_PTR_HI`, records the chosen index at `loc_2b`, and reloads the accumulator from its holding cell `loc_29`. `seatCoordListPointerWithLowByte` [seen] is the same setup entered one step in: the caller has already computed the low pointer byte, so it stores that directly into `COORD_LIST_PTR_LO`, still pulls the high byte from `LIST_PTR_TABLE_HI`+Y, still stashes the index at `loc_2b`, and still reloads `loc_29`. `seatCoordListPointerWithHighByte` [seen] is the deepest entry, past both table loads: the caller has already parked the low pointer at `COORD_LIST_PTR_LO`, so it takes the high pointer straight from the accumulator into `COORD_LIST_PTR_HI`, stashes the index at `loc_2b`, and reloads `loc_29`. Reached (n=35), with its role-defining writes observed — the index stash into `loc_2b` (pc 0x9af6) and the high-pointer store into `COORD_LIST_PTR_HI` (pc 0x9af8). The effect either way is a 16-bit pointer parked at `COORD_LIST_PTR_LO`/`COORD_LIST_PTR_HI` aimed at a packed coordinate list, with the index that selected it remembered at `loc_2b`.

`loc_9a88` [seen] is a computed-jump dispatcher: the incoming value picks one of five list-setup entries — `seatDemoCoordListPointer`, `loc_9aa9`, `selectClimberSpawnLane`, `seatCoordListPointerAtIndex3`, `loc_9ab3` — and runs it (any of these being a computed-jump target, it is reached through this dispatcher, never callerless). Each entry front-loads a specific index or low-byte source and falls into the shared `seatCoordListPointer`/`seatCoordListPointerWithLowByte` seating. Only index 0, `seatDemoCoordListPointer`, is exercised in the capture; the rest are [code], not reached. `seatDemoCoordListPointer` [code] seeds the low pointer from the fixed table byte `LIST_PTR_TABLE_LO`, marks the index zero at `loc_2b`, takes the high pointer from the held source cell `LIST_PTR_HI`, and reloads `loc_29`. `loc_9aa9` [code] (index 1) folds two held bytes into the low pointer by OR-ing `LIST_PTR_TABLE_LO1` with `LIST_SELECT_FLAGS`, presets index 1, and runs the `seatCoordListPointerWithLowByte` seating. `seatCoordListPointerAtIndex3` [code] (index 3) presets index 3 and runs the `seatCoordListPointer` seating; `loc_9ab3` [code] (index 4) presets index 4 and does likewise. (Index 2, `selectClimberSpawnLane`, is a sibling entry belonging to another subsystem.)

### Walking the coordinate list

With the pointer seated, several helpers read the packed list. `advanceCoordListByEntryStride` [seen] steps the cursor by an inter-entry delta: through the `COORD_LIST_PTR_LO`/`COORD_LIST_PTR_HI` pointer it reads the entry at Y and its predecessor at Y-1, stores their difference (`cur - prev`) at `loc_29` as the step delta, and advances Y by that delta plus two. Observed deltas run 1..0x0f, the genuine inter-entry strides of the list reached through the coordinate dispatch. `resolveCoordListEntryToAbsolute` [code] resolves one list entry to an absolute coordinate: it reads the byte at the pointer offset by Y and adds the base value in `ENEMY_CLIMB_DELTA_LO_0`, returning the 8-bit sum — a pure compute helper with no memory write, so its role rests on the code.

`fetchCoordListEntryByCounter` [seen] is the coordinate helper the computed-jump coordinate generator consumes. Its own write is only the scratch at `loc_29`, where it stashes the incoming Y; it then combines an index value with the list entry two positions back — reading the byte at pointer+(Y-2), subtracting it from the index value and adding back the saved Y — re-indexes the pointer by that result, and loads the entry it lands on, returning both that entry and the new index. The `fetchCoordListEntryByCounter` entry derives its index value as `((loc_2b - 1) & 0x0f) + 1` (a counter-derived value wrapped into 1..0x10); the sibling `fetchCoordListEntryByIndex` entry uses the raw `loc_2b`, and `readCoordListEntry` is the bare form that just reads pointer+Y. `computeCoordListBackDelta` [code] is the front half of that same arithmetic exposed alone: it records Y at `loc_29` and returns `loc_2b` minus the pointed byte two slots back (pointer+(Y-2)); as a leaf whose result is only consumed downstream, its role rests on the code. `sumCoordListEntryRun` [code] uses `computeCoordListBackDelta` as a repeat count, loads the first entry it selects from the pointer at Y, then folds that many further consecutive entries into a single wrapped one-byte total.

### The display cursor and the vector emitters

`advanceDisplayCursor` [seen] is the display-cursor advance and the hinge every emitter turns on. It adds Y+1 to the low byte `DRAW_CURSOR_LO` (the carry is forced set, so the stride is `DRAW_CURSOR_LO + Y + 1`), stores it back, and on overflow bumps the high byte `DRAW_CURSOR_HI`; the returned accumulator is the new low byte. Under load the cursor sweeps continuously across `$2000`-`$2fff`, which is what makes it the display-list write head.

The primitive word emitter is `emitVectorWord` [seen]: it stores the pair {A, X} — A at the cursor origin `(DRAW_CURSOR_LO)`+0, X at +1 — then advances the cursor by two via `advanceDisplayCursor`. `emitVectorHeaderWord` [seen] rides that tail with the fixed pair preset, emitting the `{0x40, 0x80}` header word (0x40 then 0x80 into the vector RAM) before the same advance. `emitVectorWordAtOffset` [seen] is the indexed form of the core emitter: it stores {A, X} at cursor offset Y and Y+1 and advances the cursor past them (by (Y+1)+1); its stores lay real vector data (for example a `0x3c` low byte against a `0x72` high byte) across a wide value range, which grounds it as a role-defining emit.

`emitStrokeWordFromNibble` [seen] emits a table-selected word: from the accumulator's low nibble it forms a word-table index — 0 when the carry is set and the nibble is zero, otherwise nibble+1 — doubles it, copies the two bytes of `NIBBLE_GLYPH_TABLE`[index] into the display list at the cursor, and advances two. `emitStrokeWordFromNibblePlusOne` [seen] is the thin index wrapper: it forms the index as `(A & 0x0f) + 1` and shares the same `NIBBLE_GLYPH_TABLE` copy-and-advance emit tail; its own index arm is pure compute, [seen] by reaching that shared emit.

`emitHeaderedBodyRecord` [code] builds a two-byte-header record: it emits the `{0x40, 0x80}` header via `emitVectorHeaderWord`, then stores a fixed body byte 0x20 at the cursor origin through `emitRecordBodyByte` and runs the shared record tail; it is not reached in the capture. `emitRecordBodyByte` [code] is the shared body-byte entry — it stores its input byte at the cursor origin `(DRAW_CURSOR_LO)` and continues into the shared record tail; it is reached along a path that presets the body byte to a constant, so its emit is observed but never varies and its role rests on the code.

Two producers assemble complete on-screen objects through the cursor. `drawThreeCharGlyphString` [seen] renders text: it walks three character codes from the `SLOT_VALUE` buffer (tracking the source position at `TABLE_CURSOR` and a two-count at `loc_39`), clamps each code to at most 0x1a (any value 0x1e or above folds to 0x1a), doubles it to index the glyph word table `CHAR_GLYPH_TABLE`, and copies each 2-byte glyph word into the display list at the cursor; after the copies it advances the cursor past everything written. `emitObjectPositionVector` [seen] emits an object's position vector: starting the cursor offset at zero, it writes the fixed `{0x40, 0x80}` header, then an X word taken from the zero-page pair `GAME_MODE_PENDING`/`FRAME_COUNTER` indexed by X and a Y word from the pair `GAME_MODE`/`MODE_DISPATCH_SEL`, each word's high byte masked to five bits (`& 0x1f`). As it writes it caches the raw coordinate bytes as the "previous point" — the low/high X at `PREV_X_LO`/`PREV_X_HI` and the low/high Y at `PREV_Y_LO`/`PREV_Y_HI` — which later stroke-delta drawing subtracts from, then advances the cursor past the six emitted bytes.

## Draw-pointer setup and vector emission

Every frame is assembled into the AVG vector RAM at 0x2000-0x2fff, where each two-byte word carries drawing data in its low byte and a generator opcode in the high nibble. The routines here fall into four bands: the frame sequencer that walks the display layers, the pointer-setup helpers that aim the working cursor at each layer's slice of RAM, a family of tiny tail-emitters that lay one vector word at a time, and the object builders that turn tube-slot and enemy coordinates into vector records.

### The frame sequencer and its layer brackets

loc_b230 (b230, [seen]) drives one whole frame. It calls each drawing subsystem in a fixed order — the score/status draw (drawScoreStatusList), the twelve-slot shape draw (drawSlotShapeList), then drawStyledSlotList, drawEnemyShapeList, buildObjectDisplayList, the marker-row builder (buildTextOverlayList), paintRimLanes, the enemy-list builder (buildEnemyDisplayList), and drawTimedObjectList — and brackets every one with a setup call seatDrawCursor and a matching teardown closeLayerPointer keyed to that layer's id (0x07, 0x04, 0x03, 0x06, 0x05, 0x00, 0x01, 0x08). Inside the player-layer bracket, when the sign flag STATUS_FLAGS bit7 is clear, it sums a forty-byte block (0x28 bytes) reached through the pointer DRAW_RECORD_PTR_LO/DRAW_RECORD_PTR_HI — carry-chained from a seed of 0xf2, walking index 0x27 down to 0 — and leaves the running total in the status cell PLAYER_SHAPE_SUM. After the layers it zeroes the change counter REDRAW_COUNTER and latches the two ROM constants VECHEAD0_FRAME and VECHEAD1_FRAME into the first two vector words VEC_LIST_HEADER_LO and VEC_LIST_HEADER_HI, which head the display list every frame.

seatDrawCursor (b2be, [seen]) is the per-subsystem draw-pointer setup: from the layer index A it forms the two-byte stride 2*A and, choosing table DRAW_PTR_TABLE_A when the per-index flag POINTER_PARITY+A is non-zero (else DRAW_PTR_TABLE_B), copies that table's 16-bit pointer into the indirect draw cursor DRAW_CURSOR_LO/DRAW_CURSOR_HI, then clears the status cell DRAW_CURSOR_OFFSET so the cursor offset restarts at zero for the layer. seatAltDrawPointer (b2de, [seen]) is the same selector aimed at the alternate working pointer WORK_PTR_LO/WORK_PTR_HI, with the table sense reversed (DRAW_PTR_TABLE_B when the flag is set, else DRAW_PTR_TABLE_A), again clearing DRAW_CURSOR_OFFSET. seatInPagePointer (91b5, [seen]) is the in-page variant: it doubles the selector A into a word index, clears the paired flag byte loc_29, and copies the little-endian pointer at the ROM table POINTER_TABLE_LO/POINTER_TABLE_HI into the working pointer loc_2a/loc_2b.

emitFrameLink (b332, [seen]) emits a link record between draw lists but first guards against a mid-frame change: if the source byte VECHEAD0_PLAY differs from the checkpoint VEC_LIST_HEADER_LO it latches the new value into VEC_LIST_HEADER_LO and returns carry set, signalling the caller to redo the frame. Otherwise it copies a two-byte word from DRAW_PTR_EVEN_LO (at offset 8 when POINTER_PARITY is non-zero, else 2) out through the draw cursor DRAW_CURSOR_LO, clears SCORE_DISPLAY_TIMER, then reloads the cursor DRAW_CURSOR_LO/DRAW_CURSOR_HI from DRAW_PTR_TABLE_A at that same offset and returns carry clear.

loc_b84e (b84e, [code]) is a computed-jump dispatcher: the caller's Y is a byte offset (0,2,4,6) selecting one of four draw-pointer targets seedTripleArrays, rotateTripleArray, resetVectorTailCursor, emitVectorTailRecord. emitVectorTailRecord (b896, [code], reached only via that dispatcher) writes the 16-bit cursor VECRAM_TAIL_CURSOR_LO/VECRAM_TAIL_CURSOR_HI into the vector-RAM tail — VEC_LIST_JMP_LO gets the low byte, VEC_LIST_JMP_HI the high byte tagged 0x70, VEC_LIST_HALT the 0xc0 terminator — then steps the cursor down by 0x20 with a 16-bit borrow into VECRAM_TAIL_CURSOR_HI and masks the low byte to 0x7f; it is not reached in the capture. swapDrawPointers (b944, [code]) swaps the two 16-bit pointers DRAW_CURSOR_LO/DRAW_CURSOR_HI and DRAW_CURSOR_ALT_LO/DRAW_CURSOR_ALT_HI so the shared cursor addresses the other structure, and selectPointerPair (b967, [code]) picks one of two ROM pointer pairs by the flag POINTER_PARITY (zero selects ALT_DRAW_PTR_CLR_HI/ALT_DRAW_PTR_CLR_LO, non-zero ALT_DRAW_PTR_SET_HI/ALT_DRAW_PTR_SET_LO); neither is reached in the capture.

### The shared vector-word tail-emitters

A cluster of small routines each lay exactly one vector word through the draw cursor DRAW_CURSOR_LO and step past it, differing only in the header nibble and the payload source. loc_ab0d (ab0d, [code]) emits the fixed pair (0x20, 0x80). loc_df4c ([code]) stores Y as the first byte and A tagged with 0x60 as the second; loc_df6c ([code]) is the same with the 0x70 tag. emitVectorWordTag60FromKey (df4a, [code]) drives loc_df4c with the low table byte VG_RECORD_HEADER as its data, and loc_df6a (df6a, [code]) drives loc_df6c with a zero data byte. loc_df09 (df09, [code]) stores the fixed body byte 0xc0 at the cursor origin (emitRecordBodyByte) and continues the shared record tail. emitCoordinateVectorWord (df39, [code]) emits a coordinate word: the high byte is A's upper nibble tagged 0xa0, the low byte is X shifted right with A's carry bit rotated into bit7; it writes the high byte at cursor+1 and the low byte at cursor+0, then either advances (advanceDisplayCursor) or, if the offset wrapped to zero, falls through to loc_df4c with the tag byte VG_RECORD_HEADER.

emitCoordinateRecord (df92, [seen]) emits a four-byte coordinate record from four zeropage slots indexed off X: the raw byte GAME_MODE_PENDING+x, the packed FRAME_COUNTER+x masked to five bits, GAME_MODE+x, and a key-folded five-bit last byte built by XOR-folding MODE_DISPATCH_SEL+x with the key VG_RECORD_HEADER — the last byte handed to emitRecordTailByte, which stores it at the next cursor slot and either advances the cursor or, on wrap to zero, runs the terminating nibble run. emitScaledCoordinateRecord (df75, [seen]) widens two input values by four with sign extension — each value shifted left two with its high bit propagated into the adjacent byte — into the little-endian delta pairs VEC_DELTA_Y_LO/DRAW_DELTA_A_HI and DRAW_DELTA_B_LO/DRAW_DELTA_B_HI, then emits the record they anchor through emitCoordinateRecord. emitKeyedScaledCoordinateRecord (df73, [code]) merely stashes the index byte into VG_RECORD_HEADER before scaling the two coordinates through emitScaledCoordinateRecord.

emitNibbleDigitRun (dfb1, [seen], reached extensively) draws a run of Y zeropage bytes from the top index A+Y-1 downward: for each byte it emits the high nibble then the low nibble through emitStrokeWordFromNibble (which looks up a glyph word-pair from table NIBBLE_GLYPH_TABLE at 2*nibble and writes it through the cursor DRAW_CURSOR_LO), chaining carry so that only the final low nibble sees carry cleared — the run's terminator marker. emitSlotIndexDigit (aa9e, [code]) increments the slot index, publishes it into PROJ_Y_LO, and emits that single byte via emitNibbleDigitRun. loc_af77 (af77, [code]) packs the incoming byte to BCD (packBinaryToBcd, which writes the same packed digits into loc_29) then emits that one zeropage byte as nibbles; loc_b0c6 (b0c6, [code]) seats a table pointer by index through seatInPagePointer then emits the three-byte run at loc_29 as nibbles.

emitBlankValueRecord (b56a, [seen]) appends a blank-plus-value record: it stores 0, 0, 0, A at the draw cursor DRAW_CURSOR_LO and advances the cursor by four, carrying into DRAW_CURSOR_HI.

### Glyph strings and per-digit runs

writeNibbleGlyphToTextBuffer (a9fc, [seen]) maps A's low nibble to a stroke word for the text buffer: the beq/clc/bcs carry dance yields y = nibble+1, or 0 for a zero nibble with carry in, and it reads a **single byte** from ROM table NIBBLE_GLYPH_TABLE at offset 2*y (not a word), stores it at the buffer cursor VEC_GLYPH_BUFFER+x, and advances x by two. buildTextBufferDigitString (a9d7, [seen], reached heavily) walks three source bytes backward — pass counter in loc_2a, source pointer in WORK_PTR_LO/WORK_PTR_HI — emitting each byte's high then low nibble through writeNibbleGlyphToTextBuffer, threading the carry so only the last low nibble on the final pass sees it forced clear. buildMarkerRowVectorList (a97f, [seen]) builds a marker-row vector list: it lays a header byte (A OR 0x70, zeroed only when the row index Y equals the marker loc_3d and STATUS_FLAGS bit7 is set) at VEC_GLYPH_BUFFER, fills seven glyph entries from BAR_GLYPH_LOW/BAR_GLYPH_HIGH (the alternate glyph used once the row passes the count in SLOT_COUNTDOWN), then — unless it is state 4 away from the marker — seeds the glyph pointer WORK_PTR_LO/WORK_PTR_HI and hands off to buildTextBufferDigitString.

emitByteBitsAsDigits (dd2b, [code]) stashes Y into SAVED_INDEX, scales the two coordinates through emitScaledCoordinateRecord, then shifts SAVED_INDEX out **MSB-first**, emitting each of its eight bits as one vector digit via emitStrokeWordFromNibblePlusOne. loc_dd29 (dd29, [code]) is a fixed-operand front feeding X = 0xf8, and loc_dd27 (dd27, [code]) a further front feeding the value byte A = 0xd0 — so the pair delivers the coordinate deltas 0xd0/0xf8 into emitScaledCoordinateRecord before the eight-bit run. loc_d8a9 (d8a9, [code]) stashes A into loc_29, scales its two coordinates through emitScaledCoordinateRecord, then emits that one stashed byte as a single-entry nibble run.

buildLargeDecimalNumber (dd41, [code]) is the large packed-decimal digit builder: it doubles the first little-endian input pair (DIGIT_IN_LO/DIGIT_IN_HI, its high bit carried) and adds the second (COORD_ACC_LO/COORD_ACC_HI) into the math-box operands MATHBOX_LD_R7_LO/MATHBOX_LD_R7_HI, forcing a minimum of one, seeds a divide through runMathboxDivide into DIV_QUOTIENT/DIV_REMAINDER, then emits a header via emitCoordinateVectorWord. It then makes four passes over the three-byte source the pointer WORK_PTR_LO/WORK_PTR_HI walks (seeded 0x0406), each pass running twenty-three rounds of binary-to-BCD double-dabble across the four accumulator bytes at loc_31 and emitting the converted digits via emitNibbleDigitRun, followed by a scaled coordinate record via emitScaledCoordinateRecord.

loc_dd0d (dd0d, [code]) builds the spinner/pot readout vector list: a fixed header word (emitVectorHeaderWord), a zero-tagged word (loc_df6a), then two eight-digit runs keyed by the DIP-switch ports DSW1_COINAGE (DSW1) and DSW2_OPTIONS (DSW2) via loc_dd29/loc_dd27. The exit accumulator of the DSW2_OPTIONS run drives assemblePotStatusByte's POKEY pot-scan pulse, whose returned pot-status byte keys a final eight-digit run; it is not reached in the capture.

### Object and enemy coordinate builders

loadSlotCoordBlock (c43c, [seen]) gathers a tube slot's attributes: reading the slot index SLOT_LOOP_INDEX, it copies that column of the four parallel object tables OBJ_DY_LO/OBJ_DY_HI/OBJ_DX_LO/OBJ_DX_HI into the working coordinate block PROJ_Y_LO/PROJ_Y_HI/PROJ_X_LO/PROJ_X_HI. emitProjectedSlotRecord (c423, [seen]) does the same from the second attribute bank COL_SUB_A/COL_VAL_A/COL_SUB_B/COL_VAL_B (indexed by SLOT_LOOP_INDEX) before emitting. emitCoordDeltaRecord (c3ba, [seen]) forms two 16-bit differences of the working block minus the previous block (PROJ_Y_LO-PREV_Y_LO and PROJ_X_LO-PREV_X_LO, with borrow) into the delta slots VEC_DELTA_Y_LO-DRAW_DELTA_B_HI, emits the record via emitCoordinateRecord, then latches the current values into the previous slots PREV_Y_LO-PREV_X_HI and flags VG_RECORD_HEADER = 0xc0.

emitSlotMidpointVertex (c66d, [seen]) emits a tube-slot midpoint vertex: it round-up averages slot TABLE_CURSOR's two 16-bit coordinate pairs (OBJ_DY_LO/OBJ_DY_HI and OBJ_DX_LO/OBJ_DX_HI) with those of the wrap-around neighbour (TABLE_CURSOR+1 masked 0x0f), stashes the two midpoints in PROJ_Y_LO/PROJ_Y_HI and PROJ_X_LO/PROJ_X_HI, appends the four midpoint bytes through the draw pointer DRAW_CURSOR_LO at cursor DRAW_CURSOR_OFFSET with the high bytes masked to 0x1f (the opcode field), and mirrors all four into the scratch block PREV_Y_LO-PREV_X_HI. emitDeltaVectorPair (c73c, [seen]) then emits two 16-bit differences through DRAW_CURSOR_LO at cursor DRAW_CURSOR_OFFSET — (PROJ_X_LO:PROJ_X_HI)-(PREV_X_LO:PREV_X_HI) then (PROJ_Y_LO:PROJ_Y_HI)-(PREV_Y_LO:PREV_Y_HI) — each high byte masked to five bits and the second OR'd with the vector opcode 0xa0, advancing the cursor by four.

appendNormalizedMantissaExponent (bd3e, [seen]) appends a normalized (mantissa, exponent) pair. ## Enemy spawning and lane selection

This subsystem decides which tube slots hold live climbers, seeds each new climber's starting depth, lane, and heading, chooses the segment a climber walks toward, and runs the separate eight-entry table that spawns timed objects and retires them when they expire or are hit.

**Allocating a climber slot.** `spawnClimberInFreeSlot` [seen] is the core allocator for the parallel per-slot enemy arrays. It saves the caller's Y into `SAVED_INDEX2`, then walks the free-slot index down from `ENEMY_SLOT_TOP`, skipping any entry whose depth cell `ENEMY_DEPTH,y` is already non-zero; if the index passes below zero (its high bit sets) the routine reports `0x00` — no slot free. On a free entry it seeds the whole parallel row at that index: depth `ENEMY_DEPTH,y` from `loc_29`; the target segment `ENEMY_SEGMENT,y` from `loc_2a`, except that when `loc_2a` equals `0x0f` and `TUBE_GEOM_FLAG` has its high bit set the segment is replaced with a POKEY-random even value `POKEY1_RANDOM & 0x0e`; the successor segment `ENEMY_PHASE,y` as `(segment+1) & 0x0f`; the timer `ENEMY_TIMER,y` cleared to `0x00`; the flag byte `ENEMY_SLOT_DIR,y` from `COORD_LIST_PTR_LO`; the coordinate-high `ENEMY_SCRIPT_CURSOR,y` from `COORD_LIST_PTR_HI`; and the lane/flags byte `ENEMY_SLOT_FLAGS,y` from `loc_2b`. It then bumps the active count `ENEMY_TOTAL_COUNT`, increments the per-lane counter `LANE_ENEMY_COUNT_0` at the lane index `loc_2b & 0x07`, restores X into `SAVED_INDEX2`, and reports `0x10` (slot taken).

**Seeding the random tag table.** `seedSlotRandomTags` [seen] first zeroes the 64-byte tag table `OBJECT_RECORD_TABLE+0x00..0x3f`, then walks each active slot from `FIRE_GATE-1` down to zero, writing a fresh 4-bit POKEY-random value `POKEY1_RANDOM & 0x0f` into `OBJECT_INDEX_TABLE,x` and packing the slot index with that nibble into the tag `OBJECT_RECORD_TABLE,x = (x<<4) | nibble`, substituting `0x0f` whenever that packed byte would come out zero so no live slot carries a zero tag.

**Selecting a candidate lane.** `selectClimberSpawnLane` [seen] picks the lane a new climber will use. It seeds a wrapping index from a POKEY-random start `POKEY1_RANDOM & 0x03`, sets a four-step countdown in `loc_2b` to `0x04`, and stashes the caller's X in `loc_39`. Each pass decrements the countdown (underflow below zero reports `0x00` — no lane found), steps the index back one and wraps it to `0x03` at the low end, reads a candidate lane from the four-entry table `CANDIDATE_LANE_0,y` (mapping the raw value `0x03` up to `0x05`), and stops when that lane's occupancy cell `OBJECT_ANIM_TIMER` is non-empty. On a hit it builds the selection: `COORD_LIST_PTR_LO` receives the chosen lane value with bit6 forced on (`CANDIDATE_LANE_0,y | 0x40`), `loc_2b` is reset to `0x02`, `COORD_LIST_PTR_HI` takes the list-high byte `LIST_PTR_TABLE_HI[2]`, and the routine reports `loc_29`.

**Choosing the target segment by deepest column.** `aimClimberAtDeepestColumn` [code] picks the segment a slot heads for by scanning the 16-column depth table `LANE_LIMIT` for the column holding the greatest depth. It starts at a POKEY2-random column `POKEY2_RANDOM & 0x0f`, tracks the running maximum in `COORD_LIST_PTR_HI` and its column in `loc_29`, treats an empty column (depth `0x00`) as maximal `0xff`, and skips column `0x0f` while the gate `TUBE_GEOM_FLAG` is non-zero; the walk counts down 16 columns through `SPAWN_DEFICIT_C3`. The winning column becomes the slot's target segment `ENEMY_SEGMENT,x`, its successor `ENEMY_PHASE,x = (winner+1) & 0x0f`, and bit7 of the slot flag `ENEMY_SLOT_DIR,x` is cleared. This is reached only through `advanceClimberTrackingColumnMin`, so it is not entered on its own in the capture.

**Tracking the nearest column depth as a slot approaches.** `advanceClimberTrackingColumnMin` [seen] advances slot x toward the rim while keeping each column's shallowest occupant. It raises `SCRIPT_BRANCH_FLAG`, and for the slot's current column `ENEMY_SEGMENT,x` seeds an empty column cell `LANE_LIMIT,col` to `0xf1`; if the slot's own depth `ENEMY_DEPTH,x` is shallower than the stored column value it becomes the column's new minimum and tags `LANE_TARGET_FLAG,col = 0x80`. A depth below `0x20` is too shallow: it forces bit7 of `ENEMY_SLOT_DIR,x` and clamps the depth to `0x20`. A depth below `0xf2` needs nothing further. Past that far limit it calls `aimClimberAtDeepestColumn` to pick a fresh column, reparks the depth at `0xf0`, and — only when `FIRE_GATE` is zero — rewrites the slot's flag `ENEMY_SLOT_DIR,x` to `(…&0xfc)|0x01` and its lane byte `ENEMY_SLOT_FLAGS,x` to `(…&0xf8)|0x02`, and clears `SCRIPT_BRANCH_FLAG`.

**The depth-gated flip keeper and per-slot segment step.** `keepClimberFlipBitByDepth` [code] keeps bit6 of the slot's lane byte `ENEMY_SLOT_FLAGS,x`, but only while the gate `TUBE_GEOM_FLAG` is non-zero: when bit6 is set it clears it once the slot's segment depth `ENEMY_SEGMENT,x` reaches `0x0e`, and when bit6 is clear it sets it only while that depth is `0x00`; neither conditional write is exercised in the capture, so its role rests on the code. `loc_9e5c` [seen] is the full entry that runs this bit6 guard first and then falls into the shared body `stepClimberSegmentAndHeading` [seen], which forces bit7 on `ENEMY_SLOT_FLAGS,x` (marking the slot live) and branches on its low three bits. For the seam segment `0x04`: with bit6 set it steps the depth `ENEMY_SEGMENT,x` down one modulo 16 and stores `0x87` in the successor `ENEMY_PHASE,x`, and with bit6 clear it stores `0x81` and leaves the depth alone. For any other segment: with bit6 set it steps the depth up one modulo 16, then looks the depth up through `lookupRingHeading` (bit6 selecting the half-turn) and stores the returned heading in `ENEMY_PHASE,x`. `lookupRingHeading` [code] reads the ring-direction table `SEG_DIRECTION,y` and forces bit7 on the result; when the caller's bit6 is set it takes the half-turn first — index `y = (y-1) & 0x0f`, value `(SEG_DIRECTION,y + 8) & 0x0f` — before forcing bit7. Its write-free compute leaves it [code].

**The timed-object table.** A separate eight-slot table holds timed objects. `insertTimedObject` [seen] inserts one: it saves X/Y into `SAVED_INDEX`/`SAVED_INDEX2`, scans the eight slots from 7 down for a free entry (`SHAPE_ACTIVE,i == 0`), and if none is free evicts the slot with the largest counter `SHAPE_ANIM,i` (tracked in `loc_2a`/`loc_2b`) while dropping the live count `TIMED_OBJECT_COUNT` by one. Into the chosen slot it writes counter `SHAPE_ANIM = 0`, type `SHAPE_ID` from `COORD_LIST_PTR_LO`, presence `SHAPE_ACTIVE` from `loc_29`, and lane `SHAPE_COORD` from `COORD_LIST_PTR_HI`, then bumps `TIMED_OBJECT_COUNT`. `insertTimedObjectOfType` [code] is the thin front that stashes A into `COORD_LIST_PTR_LO` before that insert; its only own write is a constant `0x00` in the capture, so it rests on the code. `ageTimedObjects` [seen] ages the table: if the pending flag `TIMED_OBJECT_COUNT` is zero it does nothing, otherwise it clears the flag and for every live slot advances the counter `SHAPE_ANIM,i` by the per-type step `TIMED_OBJ_STEP_TABLE[type]`; a slot that reaches its per-type limit `TIMED_OBJ_LIMIT_TABLE[type]` is freed (`SHAPE_ACTIVE,i = 0`), while any slot still short re-raises `TIMED_OBJECT_COUNT` for the next pass.

**Object-insert callers.** The shared insert tail `insertObjectAndSignalReady` [seen] seats the type byte `COORD_LIST_PTR_LO`, copies `loc_29` from `PLAYER_SHOT_DEPTH` and `COORD_LIST_PTR_HI` from `PLAYER_SEGMENT`, fires the sound gate `loc_ccb0`, inserts through `insertTimedObject`, then raises the ready flags `PLAYER_FINE_ANGLE = 0x81` and `OBJECT_ANIM_TIMER = 0x01`. `insertType1WithHeadFlag` [seen] writes the caller's value into the head flag `OBJECT_ANIM_PHASE` and then runs the tail with type `0x01`. `primeTopPriorityObject` [code] is the top-priority prime — head flag `OBJECT_ANIM_PHASE = 0xff` and a type-`0x01` insert — but that specific head is not observed in the capture, so it rests on the code. `insertType5AndDrainPending` [seen] inserts an object typed `0x05` through the tail and then steps the pending counter `PLAYER_FINE_ANGLE` down one. `loc_a343` [code] and `loc_a347` [code] are two seed entries that stamp the head flag with `0x09` and `0x07` respectively before the shared type-1 insert. `retireSpawnedObject` [seen] retires the object in slot Y: it cues sound `loc_ccc1`, stages `loc_29` from `loc_2db,y` and `COORD_LIST_PTR_HI` from `loc_2b5,y`, re-inserts a zeroed object via `insertTimedObjectOfType(0x00)`, clears the slot `loc_2db,y`, drops the live count `ACTIVE_ENEMY_COUNT`, and flags lane X spent with `HIT_TALLY,x = 0xff`. `insertObjectFromSlotDepth` [seen] rings the same sound cue, copies the y-indexed depth byte `ENEMY_DEPTH,y` into `loc_29`, and inserts a fresh object through `insertTimedObjectOfType`.

**Spawn drivers and collision-triggered spawns.** `spawnClimbersFromSourceSlots` [seen] is the per-frame spawn loop across the seven source slots. It does nothing while `PLAYER_FINE_ANGLE` has its high bit set; otherwise for each slot x from 6 down it requires the depth `ENEMY_DEPTH,x` to be non-zero and at least `0x30` and the flag `ENEMY_SLOT_DIR,x` bit6 (armed) to be set, decrements the slot timer `ENEMY_TIMER,x`, and acts only when that timer underflows (its high bit sets), immediately restoring it (`+1`). Both guards are unexercised in the capture and so are [code], reached only through their dispatchers.

## Enemy motion and the pursuit AI

Enemies live in a bank of slots indexed by `x`. Each slot carries a whole-coordinate cell `ENEMY_SLOT_FLAGS,x` (nonzero while the slot is alive, also serving as a per-slot flag byte), a segment/lane number `ENEMY_SEGMENT,x`, a phase counter `ENEMY_PHASE,x`, a direction/state byte `ENEMY_SLOT_DIR,x`, and a depth pair `ENEMY_DEPTH,x` (high) / `ENEMY_DEPTH_LO,x` (low). Two distinct locomotion styles run over these slots: a free-flight three-axis integrator used at spawn time, and the lane-by-lane climb that carries the pursuit logic. Both are stepped once per frame by the slot walk.

### The per-frame slot walk and spawning

`stepEnemyFleetAndSpawn` [code] drives the frame. It first copies the spawn budget `SPAWN_BUDGET_TIMER` into the frame-active flag `SPAWN_FOUND_FLAG`, then walks the sixteen slots from `0x0f` down to `0`. A slot whose `ENEMY_SLOT_FLAGS,x` is nonzero is live: it is integrated by `advanceEnemyFreeFlight` and then decayed by `decayEnemyFreeFlightVelocity`, and it forces `SPAWN_FOUND_FLAG = 0xff` to mark the frame active. A free slot (`ENEMY_SLOT_FLAGS,x == 0`) is refilled by `spawnEnemyInSlot` as long as the budget `SPAWN_BUDGET_TIMER` remains nonzero. The decay step leaves its last axis's whole byte in a register, and `stepEnemyFleetAndSpawn` carries that register value forward so each subsequent spawn stamps it in; after the walk it settles the slot counter `SLOT_LOOP_INDEX = 0xff`. On even frames (`FRAME_COUNTER` bit0 clear) with budget remaining it ticks `SPAWN_BUDGET_TIMER` down by one, and if the walk found nothing live or spawned (`SPAWN_FOUND_FLAG` still zero) it raises the mode-request byte `GAME_MODE = 0x12`.

`spawnEnemyInSlot` [code] populates a free slot. It marks the slot active by writing `0x80` to `OBJECT_AXIS1_POS,x`, `ENEMY_SLOT_FLAGS,x`, and `ENEMY_POS2,x`, then seeds three velocity/coordinate pairs from the POKEY random draws `POKEY2_RANDOM`/`POKEY1_RANDOM`. For each axis the raw draw becomes the low byte (`ENEMY_VEL1_LO,x`, `ENEMY_VEL0_LO,x`, `ENEMY_VEL2_LO,x`) and a signed nudge from `drawSignedVelocityNudge` becomes the whole byte (`ENEMY_VEL1_HI,x`, `ENEMY_VEL0_HI,x`, `ENEMY_VEL2_HI,x`); the middle axis's nudge is forced non-positive (negated when it comes out positive). It closes by cueing a sound (`loc_ccc1`). `drawSignedVelocityNudge` [code] is the leaf that produces that nudge: it reads a 3-bit magnitude (`POKEY2_RANDOM & 0x07`, so 0..7) and negates it when the caller's incoming value has bit0 set, giving a signed step in [-7, +7]. It makes no own write and is not reached in the capture (its effect would land only through `spawnEnemyInSlot`, which also did not run in the capture).

### Free-flight integration and decay

`advanceEnemyFreeFlight` [code] integrates the live slot's three motion axes. Each axis adds its low velocity into a position fraction (axis 0: `OBJECT_AXIS0_FRAC,x += ENEMY_VEL0_LO,x`; axis 1: `OBJECT_INDEX_TABLE,x += ENEMY_VEL1_LO,x`; axis 2: `OBJECT_RECORD_TABLE,x += ENEMY_VEL2_LO,x`), then folds that fraction's carry together with the signed whole velocity (`ENEMY_VEL0_HI,x`, `ENEMY_VEL1_HI,x`, `ENEMY_VEL2_HI,x`) into a whole coordinate. The whole is tested against the tube ring [0x10, 0xf0): a rising axis (velocity sign bit clear) overflows when the whole reaches `0xf0` or more, a falling axis (sign bit set) overflows when it drops below `0x10`. Axis 1's whole commits to `OBJECT_AXIS1_POS,x`, axis 2's to `ENEMY_POS2,x`, and axis 0's whole commits to the shared cell `ENEMY_SLOT_FLAGS,x` — but any axis overflowing forces that committed value to `0`, which retires the slot. 

`decayEnemyFreeFlightVelocity` [code] is the companion decay. It seeds a saturation counter `loc_29 = 0xfd`, then steps each of the three velocity pairs (`ENEMY_VEL1_LO,x`/`ENEMY_VEL1_HI,x`, `ENEMY_VEL0_LO,x`/`ENEMY_VEL0_HI,x`, `ENEMY_VEL2_LO,x`/`ENEMY_VEL2_HI,x`) one increment toward zero through `stepVelocityTowardZero`, writing the stepped low/whole back. `stepVelocityTowardZero` bumps `loc_29` on each axis that reaches zero, so the counter climbs from `0xfd` to `0` only when all three axes saturate in the same frame; in that case `decayEnemyFreeFlightVelocity` clears the slot's whole coordinate `ENEMY_SLOT_FLAGS,x`. `stepVelocityTowardZero` [code] steps one signed 16-bit velocity toward zero by the fixed increment `VELOCITY_DECAY_STEP` (0x20): it stashes the whole into `loc_2b`, adds when the whole is negative and subtracts otherwise, and on crossing zero snaps the low byte `loc_2a = 0` and increments `loc_29`. It is not reached in the capture.

### The lane climb (the pursuit path)

The deeper coordinate is a 16-bit tube depth (`ENEMY_DEPTH,x` high / `ENEMY_DEPTH_LO,x` low) advanced per segment. `stepEnemyDepthInLaneDirection` [seen] is the direction selector: it reads the slot's segment `seg = ENEMY_SLOT_FLAGS,x & 0x07`, seats it in the index used to fetch the per-segment delta from the `ENEMY_CLIMB_DELTA_LO_0` (low) / `ENEMY_CLIMB_DELTA_HI_0` (high) table, and branches on the sign of `ENEMY_SLOT_DIR,x` — bit7 clear takes the add path `advanceEnemyLaneDepth`, bit7 set the subtract path `reverseEnemyLaneDepth`.

`advanceEnemyLaneDepth` [seen] adds the segment delta with carry (`ENEMY_DEPTH_LO,x += ENEMY_CLIMB_DELTA_LO_0,seg`; `ENEMY_DEPTH,x += ENEMY_CLIMB_DELTA_HI_0,seg + carry`). On the resulting high byte it decides the slot's fate: a high byte at or below the shared floor `PLAYER_SHOT_DEPTH` steps the slot through `settleEnemyAtTargetDepth` (the depth-target settle); a high byte of `0x20` or more finishes with the new high as the exit accumulator; otherwise a high byte still under `0x20` with an armed gate (`ENEMY_SLOT_DIR,x & 0x03` nonzero) retires and replaces the slot through `retireEnemyAndSpawnSplit` (invoked with the slot index as both arguments). `reverseEnemyLaneDepth` [code] is the mirror subtract path: it takes the delta out with borrow and, if the high byte underflows past `0xf0` (i.e. lands at `0xf0` or above after the subtract), floors it to `0xf2`, returning the new high. It is not reached in the capture; only the add path runs there.

`settleEnemyAtTargetDepth` [seen] settles a slot at the target depth. It stashes the shared floor `PLAYER_SHOT_DEPTH` into `ENEMY_DEPTH,x`, then acts by kind: a kind-1 slot (`ENEMY_SLOT_FLAGS,x & 0x07 == 1`) with `FIRE_GATE` nonzero flips bit7 of `ENEMY_SLOT_DIR,x` and stops; a slot flagged negative (`ENEMY_SLOT_FLAGS,x` bit7) simply bumps its stashed depth byte and stops. Otherwise it drops the total active count `ENEMY_TOTAL_COUNT`, and when the per-type count `ENEMY_TYPE_COUNT` is exactly 1 it scans slots 6..0 for a non-empty, non-self entry whose stashed depth matches the shared `PLAYER_SHOT_DEPTH` (recording the index in `TABLE_CURSOR`) and copies that neighbour's bit6, inverted, into its own flag `ENEMY_SLOT_FLAGS,x` — otherwise it re-aims through `faceEnemyTowardPlayerSegment`. It then marks `SCRIPT_CURSOR = 0x41` and bumps `ENEMY_TYPE_COUNT`.

`advanceEnemyPursuit` [code] is a self-contained per-slot mover with the same climb machinery. When `ENEMY_SLOT_DIR,x` bit7 is set it re-seeks the slot the subtract way (`reverseEnemyLaneDepth` with the delta index forced to `0x04`) and dispatches on the returned high byte: a high under `0x80` runs the fire gate `maybeFireEnemyStep`, otherwise `ENEMY_FIRE_SELECT` bit6 chooses between the two segment steps `flipEnemyLaneRandomSide` and `flipEnemyLaneTowardTarget`. When bit7 is clear it advances the 16-bit coordinate by the per-frame delta (`ENEMY_DEPTH_LO,x += ENEMY_CLIMB_DELTA_LO_4`; `ENEMY_DEPTH,x += ENEMY_CLIMB_DELTA_HI_4 + carry`, where `ENEMY_CLIMB_DELTA_LO_4`/`ENEMY_CLIMB_DELTA_HI_4` are the segment-4 entries of the same delta table). A new high below the floor `PLAYER_SHOT_DEPTH` is clamped to the floor (which leaves the fire selector clear); a carry into the fire selector is produced only when `FIRE_GATE` is nonzero and either `loc_9f >= 0x11` or the new high is `0x20` or more. A set carry runs the fire gate; otherwise `ENEMY_FIRE_SELECT`'s sign bit picks between `flipEnemyLaneTowardTarget` and `flipEnemyLaneRandomSide`. When `FIRE_GATE` is zero it returns early. It is not reached in the capture.

`retireEnemyAndSpawnSplit` [seen] retires an enemy in slot `y` and can respawn it. It clears the slot's depth entry `ENEMY_DEPTH,y` (saving the retired value into `loc_29`); it drops the per-type count `ENEMY_TYPE_COUNT` when the retired depth equalled `PLAYER_SHOT_DEPTH` and the slot's lane (`ENEMY_SLOT_FLAGS,y & 0x07`) is not 4, and otherwise drops the total `ENEMY_TOTAL_COUNT`; it then drops the per-lane counter `LANE_ENEMY_COUNT_0` at that lane (the caller's `x` is parked in `SAVED_INDEX` and reloaded, so it survives). A clear replacement gate (`ENEMY_SLOT_DIR,y & 0x03 == 0`) ends there. Otherwise it seats the draw cells: `loc_2b` from the gate (gate-1, but gate 3 wraps to 4), and `loc_2a` from `(ENEMY_SEGMENT,y - 1) & 0x0f` (snapping `0x0f` to `0` when `TUBE_GEOM_FLAG` bit7 is set). It builds the coordinate list through `setupEnemyCoordList`, seeds the lane counters (`SCRIPT_CURSOR = COORD_LIST_PTR_HI - 1`, `SCRIPT_WALK_CONTINUE = 0`), and spawns a replacement via `spawnClimberInFreeSlot`; if that spawn took, it advances `loc_2a` by 2 (snapping `0x0f` to `0x0e` under the same `TUBE_GEOM_FLAG` bit7 rule), sets bit6 of `loc_2b`, and spawns a mirrored second one.

`setupEnemyCoordList` [seen] builds that coordinate list for the packed index in `loc_2b`, saving and restoring the caller's index in the scratch cell `SAVED_INDEX2`. When the held count `loc_29` is `0x20` or more the index selects one of the list-setup entries through the selector `loc_9a88` (only the first of its five entries is reached in the capture); otherwise the pointer pair is seated directly at that index via `seatCoordListPointer`.

### Rim walking and the flipper turn

A flipping enemy hops between adjacent lanes; several routines maintain the lane flag and the turn animation. `faceEnemyTowardPlayerSegment` [code] records which rotational side the target lies on: it takes the signed segment delta of `ENEMY_SEGMENT,x` against the player segment `PLAYER_SEGMENT` (through `signedSegmentDelta`) and sets bit6 of `ENEMY_SLOT_FLAGS,x` when the delta is non-negative, clears it when negative. `toggleEnemyTurnSide` [seen] toggles that same bit6 of `ENEMY_SLOT_FLAGS,x` in place and returns the new value; its bit6 XOR of `ENEMY_SLOT_FLAGS,x` is observed changing in the capture. `signedSegmentDelta` [seen] is the shared signed-delta helper: it computes A minus Y, stashes the difference in `loc_2a`, and either keeps the full byte (when `TUBE_GEOM_FLAG` bit7 is set) or masks to the low nibble and sign-extends bit3 into a signed byte.

`flipEnemyLaneTowardTarget` [code] is the multi-entry segment-flip step. Entry `flipEnemyLaneTowardTarget` re-derives the lane flag from the target (`faceEnemyTowardPlayerSegment`), then toggles it (`toggleEnemyTurnSide`), then runs the shared tail; entry `flipEnemyLaneRandomSide` instead reseeds bit6 of `ENEMY_SLOT_FLAGS,x` from a random bit (`POKEY1_RANDOM & 0x40`) before the tail. The shared tail, on a live board (`TUBE_GEOM_FLAG` nonzero), flips bit6 once more according to how deep the slot sits on the ring — when bit6 is set it flips at `ENEMY_SEGMENT,x == 0`, when clear it flips at `ENEMY_SEGMENT,x >= 0x0f` — then marks `SCRIPT_CURSOR = 0x66` and continues into `stepClimberSegmentAndHeading`.

`maybeFireEnemyStep` [code] is the per-slot fire gate that guards those steps: it fires only when the slot's fire bit is set (`ENEMY_DEPTH,x & 0x20`) and a fresh POKEY draw clears the threshold (`POKEY2_RANDOM >= ENEMY_FIRE_THRESHOLD`); the target flag `ENEMY_FIRE_SELECT` bit6 (clear) or an even slot index routes to `flipEnemyLaneRandomSide`, an odd slot to `flipEnemyLaneTowardTarget`. It is not reached in the capture.

`animateFlipperTurn` [seen] runs the flipper's turn animation. It steps the phase counter `ENEMY_PHASE,x` one increment in the direction of `ENEMY_SLOT_FLAGS,x` bit6 (bit6 set decrements, else increments), keeping the low nibble and forcing bit7. When the state's low three bits are not `0x04` it re-derives the target direction (`lookupRingHeading` of `ENEMY_SLOT_FLAGS,x ^ 0x40` against `ENEMY_SEGMENT,x`) and, only when that matches the phase, drops bit7 of `ENEMY_SLOT_FLAGS,x` and either seats the phase from `ENEMY_SEGMENT,x + 1` (bit6 set) or reseeds the phase from the coordinate and decrements `ENEMY_SEGMENT,x`. When the state is `0x04` and the phase has reached a step boundary (low three bits zero) it rotates `ENEMY_SEGMENT,x` (incrementing when phase bit3 is set), clears bit7 of `ENEMY_SLOT_FLAGS,x`, reseeds the phase to `0x20`, and flips bit7 of `ENEMY_SLOT_DIR,x`; then, when `FIRE_GATE` is zero, a slot whose depth `ENEMY_DEPTH,x` equals the floor `PLAYER_SHOT_DEPTH` kicks the next segment step `flipEnemyLaneTowardTarget`, otherwise it isolates the sign bit of `ENEMY_SLOT_DIR,x`. Every exit copies bit7 of `ENEMY_SLOT_FLAGS,x` into the shared flag `SCRIPT_BRANCH_FLAG`.

`aimSpinnerAtNearestEnemy` [seen] turns the aim toward the nearest enemy. It scans the depth table `ENEMY_DEPTH` over the count in `ENEMY_SLOT_TOP` for the smallest nonzero entry, keeping the value in `loc_29` and its slot index in `loc_2a`; with no candidate it returns the last entry seen. With a candidate it takes the signed segment delta of that slot's segment `ENEMY_SEGMENT[idx]` against the player segment `PLAYER_SEGMENT` (through `signedSegmentDelta`) and returns a direction code — `0x00` when already aligned, `0x09` when the target lies to one side, `0xf7` to the other. This code is consumed by `rotateBlasterAroundRim` as an auto-aim spinner delta.

### The rim rotation state

`rotateBlasterAroundRim` (grounding tag not on record) advances the rim rotation. It skips while the fine-angle flag `PLAYER_FINE_ANGLE` bit7 is still set. When `STATUS_FLAGS` bit7 is set it takes the manual reading `SPINNER_ACCUM`, clamping it into the band [0xe1, 0x1f] and then consuming the reading; otherwise it takes the auto-aim delta from `aimSpinnerAtNearestEnemy`. It folds the delta into work cells (`loc_2b = delta`, `COORD_LIST_PTR_LO = RIM_ROT_OFFSET - delta`), and while the level gate `TUBE_GEOM_FLAG` is live it caps `COORD_LIST_PTR_LO` to `0xef` and, on a sign flip against both the delta and the stored offset, saturates it toward the stored sign (`0xef` or `0x00`). The high nibble of `COORD_LIST_PTR_LO` becomes the coarse angle staged in `loc_2a`, with `loc_2b = (nibble + 1) & 0x0f`; a changed coarse angle rings the sound cue `loc_ccb5`; finally the new coarse/fine/offset commit to `PLAYER_SEGMENT`, `PLAYER_FINE_ANGLE`, and `RIM_ROT_OFFSET`.

`autoAdvanceRimRotation` [seen] feeds that update from a fixed-stride position accumulator. It sets the floor `PLAYER_SHOT_DEPTH = 0x10`, sign-extends the delta source `LEVEL_GEOM_SCALE` across the work bytes `loc_29`/`loc_2a`/`loc_2b`, arithmetic-shifts the mid:low pair right twice, and folds the result into the 24-bit running total `ZOOM_ACCUM_HI`/`PROJ_OFS_X_LO`/`PROJ_OFS_X_HI`. It steps the 16-bit position `DEPTH_HI`:`DEPTH_LO` by the fixed stride `0x18`, arming the saturation flag `SPIKE_TABLE_GUARD = 0x01` once `DEPTH_LO` reaches `0xfc` or more. When the high difference against the target `DEPTH_TARGET` collapses to zero it rebuilds the position seeds (`DEPTH_HI = DEPTH_TARGET`, `DEPTH_LO = 0xff`), sets `GAME_MODE` to `0x04` or `0x08` by the sign of `STATUS_FLAGS`, and clears `loc_102[loc_3d]`. It marks the dirty flag `REDRAW_COUNTER = 0xff` and continues into `rotateBlasterAroundRim`.

`stepActiveShots` [seen] walks a separate active set from index `0x0b` down to `0`, acting on slots whose `SLOT_STATE,x` is nonzero. Slots at index 8 and above integrate a 16-bit velocity into their position pair (`loc_2e6,x += OBJECT_VELOCITY_LO`; high `SLOT_STATE,x += OBJECT_VELOCITY_HI + carry`) and, when the new high stays at or above the floor `PLAYER_SHOT_DEPTH`, keep it; otherwise they drop the count `ACTIVE_ENEMY_COUNT`, finalize through `primeTopObjectOnTargetMatch`, and clear `SLOT_STATE,x`. Slots below 8 step a counter by `0x09` (less `0x04` when `HIT_TALLY,x` is flagged), remap the working index through `advanceShotAndScoreLaneHit`, and at the far limit (`SLOT_STATE` at that index reaching `0xf0` or more) drop the count `ACTIVE_OBJECT_COUNT` and clear the entry.

### The moving spike

`advanceMovingSpike` (grounding tag not on record) steps the moving spike/pulsar object each frame, running only while `PLAYER_FINE_ANGLE` bit7 is clear and the arm flag `SPIKE_ACTIVE_FLAG` bit7 is set. At the trigger height (`PLAYER_SHOT_DEPTH == 0x10`) it seeds a start sound (`loc_ccee`). It advances a 16-bit height (`SPIKE_HEIGHT_LO`/`PLAYER_SHOT_DEPTH` by `SPIKE_STEP_LO`/`SPIKE_STEP_HI`); on overflow past the ceiling (high carry out, or `PLAYER_SHOT_DEPTH >= 0xf0`) it requests mode `GAME_MODE = 0x0e`, cues an end sound (`loc_ccf2`), and parks the height at `PLAYER_SHOT_DEPTH = 0xff`. Once the height passes `0x50` while `SPIKE_TABLE_GUARD` is still zero it rebuilds the spike table through `rebuildSpikeTable`. It steps a second accumulator (`DEPTH_ACCUM_LO`/`DEPTH_HI`, paging `DEPTH_LO` and bumping the change counter `REDRAW_COUNTER` when the high byte moves), then rederives the per-frame delta from `loc_9f << 2` clamped to `0x30`, plus `0x20`, folded back into `SPIKE_STEP_LO`/`SPIKE_STEP_HI`. Finally, below the ceiling (`PLAYER_SHOT_DEPTH < 0xf0`), it scans the slot row `LANE_LIMIT` from `0x0f` down for a nonzero entry that matches the player segment `PLAYER_SEGMENT` and sits shallower than `PLAYER_SHOT_DEPTH` (value below the height); such a match registers the collision (`loc_cd06`, `loc_a347`, clear `SPIKE_TABLE_GUARD`, `clearActiveShots`).

`stepSpikeTableCollapse` [seen] remaps the 8-entry spike table `loc_3fe` against the reference `SPIKE_TABLE_GUARD` (a no-op while `SPIKE_TABLE_GUARD` is zero). Scanning `x` from 7 down to 0: an entry of `0x17` or more shrinks by 7; a nonzero entry below `0x17` snaps to a rail (`0xf0` or `0`) chosen by the sign of `SPIKE_TABLE_GUARD`; a zero entry adopts a rail from its next neighbour (neighbour nonzero and below `0xd5` yields `0xf0` while `SPIKE_TABLE_GUARD` is negative). Each result is OR-folded into `loc_29`; it sets `SLOT_LOOP_INDEX = 0xff`, and if every entry ended up zero it clears the reference `SPIKE_TABLE_GUARD`.

### Fixed-point step helpers

`foldStepIntoFraction` [code] folds a signed sub-step into a fractional accumulator: `RIM_ROT_OFFSET = ((SPINNER_ACCUM << 3) & 0xff) + RIM_ROT_OFFSET`, then carries the fold-carry plus the sign extension of `SPINNER_ACCUM` up into the returned accumulator, and clears `SPINNER_ACCUM`. It is reached but its fold never carried a nonzero step in the capture (`SPINNER_ACCUM` and `RIM_ROT_OFFSET` observed only `0x00 -> 0x00`). `nudgeBlasterRimPosition` [code] consumes it to nudge a clamped position: it reads `PLAYER_SEGMENT`, folds through `foldStepIntoFraction`, clamps the result into [0, `DEPTH_CEILING`] (a negative result floors to `0`, an over-ceiling result pins to `DEPTH_CEILING`), and writes it back to `PLAYER_SEGMENT`; here too `PLAYER_SEGMENT` stayed `0x00 -> 0x00` in the capture, so the mechanism is clear from the code but the value never moved.

`scaleByPhaseFraction` [code] scales a value by a slot's phase fraction: it stashes the input in `loc_29`, takes the low three bits of `ENEMY_PHASE,x` as a fraction into `COORD_LIST_PTR_LO`, and runs three rounds of conditional add (LSB-first) with a sign-preserving right shift. It is not reached in the capture.

`buildSlotScreenPoint` [seen] builds a screen point for slot `x`. Using the segment `ENEMY_SEGMENT,x` as an index into the base coordinate tables `SEG_BASE_X`/`SEG_BASE_Y` (staged as `PROJ_PT_Y`/`PROJ_PT_X`), it offsets each base by a signed delta from `VERTEX_X_OFS_BY_PHASE`/`VERTEX_Y_OFS_BY_PHASE` indexed by `ENEMY_PHASE,x & 0x0f`, using a `0x80`-biased signed-saturating add, and writes the point to `loc_2e` (X) and `loc_30` (Y). It copies `OBJ_DEPTH` into `loc_2f` and loads a style pair from `STYLE_TABLE_59`/`STYLE_TABLE_5A` at `TUBE_SHAPE_INDEX` into `CLAMP_TALLY`/`RUN_SIZE`.

### Enemy pacing and timers

`tickEnemyPacingCountdown` [seen], reached through the dispatch, ticks the active slot's countdown. It clears `MODE_DELAY_TIMER`, decrements the countdown `SLOT_COUNTDOWN[loc_3d]`, and when the `SLOT_COUNTDOWN`/`SLOT_COUNTDOWN_HI` pair is fully spent it finalizes through `reloadPacingFromPeakSlot`. Otherwise, if the just-decremented countdown reached zero it flags `MODE_DISPATCH_SEL = 0x0c` and `MODE_DELAY_TIMER = 0x28`; it then toggles `LEVEL_ID` (gated by `ACTIVE_SLOT_COUNT`) to select the next non-empty slot and arms its timers, setting `GAME_MODE_PENDING` to `0x1c` when `PLAYER_LEVEL_TBL[x] + 1` wraps to zero and `0x02` otherwise, with `GAME_MODE = 0x0a`.

`reloadPacingFromPeakSlot` [seen] computes a peak-slot value and re-arms a timer: it scans the zero-page window `PLAYER_LEVEL_TBL` from `ACTIVE_SLOT_COUNT` down to 0 for the maximum, stores it into `WAVE_PEAK_SEED` decremented once when nonzero, and sets `GAME_MODE` to `0x14`, or `0x10` when the status byte `STATUS_FLAGS` is negative.

`advanceLevelCounter` [seen] derives pending steps and bumps a tally; its game-vocabulary meaning is unresolved. From the two-bit gate `INPUT_EDGE_FLAGS & 0x60` (which it then clears) and a `>= 2` test on the counter `PHASE_COUNTER`, it derives a step of 0..2 and drains `PHASE_COUNTER` by it. When the gate is clear it may seed four intro cells (`MODE_DISPATCH_SEL = 0x10`, `MODE_DELAY_TIMER = 0x20`, `GAME_MODE = 0x0a`, `GAME_MODE_PENDING = 0x14`) provided `SPINNER_ACCUM` is nonzero and `STATUS_FLAGS` bit7 is clear, then clearing `SPINNER_ACCUM`/`SPIKED_SEGMENT_COUNT`. It stores the step in `ACTIVE_SLOT_COUNT`; a nonzero step sets `STATUS_FLAGS |= 0xc0`, zeroes `HEARTBEAT_ACCUM_LO`/`HEARTBEAT_ACCUM_OVERFLOW`/`GAME_MODE`, bumps the 16-bit tally at `COORD_ACC_LO,x` (carrying into `COORD_ACC_HI,x`), and clamps `loc_100 + step` to `0x63`.

### An unreached leaf

`rotateTripleArray` [code] rotates a three-entry array (`COLOR_CYCLE_0`..`COLOR_CYCLE_2`) down by one with wrap, threading the displaced value, and mirrors each new entry into the paired array `COLOR_RAM_9`..`COLOR_RAM_B`. It is not reached in the capture, so its game role is unconfirmed from behaviour.

## The per-slot object-record draw loop

Every frame the machine turns a compact per-slot object record into a run of
vector-generator words appended to the display list at the write cursor
`DRAW_CURSOR_LO`/`DRAW_CURSOR_HI`. Three near-identical builders — `drawSlotShapeRecord` [seen],
`drawSlotShapeWithHeader` [seen], and the shared tail `expandShapeListToVectors` [seen] — do the expansion, and
a family of small drivers calls them once per fixed slot to compose the frame.

### The shared record builder

`drawSlotShapeRecord`, `drawSlotShapeWithHeader`, and `expandShapeListToVectors` share one body; they differ only in how
much of the record they seed before the common work begins. `drawSlotShapeRecord` is the
primary entry: given a slot index `x`, it latches the slot into `SAVED_INDEX`, takes
that slot's header/colour seed from the ROM byte at `HEADER_COLOR_SEED + x` into `loc_2b`,
and loads the slot's 16-bit shape-list pointer from the pointer table based at
`(loc_ac)` — the entry at `(loc_ac) + x` becomes `WORK_PTR_LO` and the next byte
`WORK_PTR_HI`. When the slot is the marker slot `0x2c` it snapshots the current cursor
into `DRAW_RECORD_PTR_LO`/`DRAW_RECORD_PTR_HI`, remembering where in the display list that record began.
It then reads the first byte of the shape list (`(WORK_PTR_LO)` indirect) into `loc_2a`
as a position seed and lays down the fixed positioning word `0x20`/`0x80` through
`loc_ab0d`. `drawSlotShapeWithHeader` is the same routine but takes its `loc_2b` header seed as a
direct argument `a` instead of reading `HEADER_COLOR_SEED`; `drawShapeListAtPosition` [code] is a thinner
front that seats `SAVED_INDEX = x`, `loc_2a = a`, and a zero header `loc_2b = 0x00`
before falling into `expandShapeListToVectors`.

`expandShapeListToVectors` is the common tail all three converge on, and it is where the record is
actually built. It clears `VG_RECORD_HEADER`, sets `VG_LAST_STAT = 0x01`, and emits an intensity
header word (`loc_df6a` with `0x01`). It positions the object by widening the two
seeds `loc_2a` and `loc_2b` by four with sign extension into little-endian
coordinate pairs and emitting that beam-position record (`emitScaledCoordinateRecord`, whose
`scale4` shifts each value left by two and sign-extends the high byte). It reloads
the shape-list pointer from `(loc_ac)` keyed by `SAVED_INDEX`, then reads the slot's
scale key from the ROM byte at `SCALE_KEY_TABLE + SAVED_INDEX` and splits it into two scale
settings: the high nibble drives `emitColorStatIfChanged` (which latches `loc_9e` and re-emits
only when it changes) and the low nibble drives `emitScaleWordIfChanged` (which latches `VG_LAST_STAT`
the same way). Finally it walks the shape list: with the output offset `loc_2a`
reset to zero and the read index `COORD_LIST_PTR_LO` starting at one, each list entry is
fetched from `(WORK_PTR_LO) + listIdx`, its low seven bits `entry & 0x7f` used as a
point offset `src`, and the byte pair at `NIBBLE_GLYPH_TABLE + src` and `NIBBLE_GLYPH_TABLE_HI + src`
(the two consecutive bytes of a packed vector word in the point table at
`NIBBLE_GLYPH_TABLE`) is copied into the display list at `(DRAW_CURSOR_LO) + outOff`, advancing the
output offset by two each time. The loop runs until an entry with its high bit set
(`entry & 0x80`) terminates the list, after which `advanceDisplayCursor` advances the cursor
past everything written (`loc_2a - 1` plus one). The effect is that a slot's shape
is stored as a short list of point indices and expanded here into a stream of
coordinate words, scaled and positioned per slot.

### The 16-slot moving-object cascade

`drawMovingObjectSlots` [code] is the eponymous loop over the object slots, and it is not
reached in the capture. It resets its running accumulators (`PREV_Y_LO` through
`PREV_X_HI`, plus `PLAYER_SHOT_DEPTH`, `PROJ_OFS_X_LO`, `PROJ_OFS_X_HI`, all cleared, with `DEPTH_HI` seeded to
`0xe0` and `DEPTH_LO` to `0xff`), lays down an opening coordinate through `emitCoordinateVectorWord`
(`0x3f`/`0xf2`), and caches a base draw-struct pointer (selected by `selectPointerPair`,
which picks one of two ROM pointer-table entries by the `loc_0415` flag) into
`DRAW_CURSOR_ALT_HI`/`DRAW_CURSOR_ALT_LO`. It then counts `SLOT_LOOP_INDEX` down from `0x0f`, and for each slot
whose active byte `ENEMY_SLOT_FLAGS + x` is nonzero it loads that slot's three parallel
attributes — the active value into `OBJ_DEPTH`, `OBJECT_AXIS1_POS + x` into `PROJ_PT_Y`, and
`ENEMY_POS2 + x` into `PROJ_PT_X` — and draws the record: `projectPointThroughMathbox` computes clamped
signed X/Y deltas through the math coprocessor into the accumulators, `emitCoordDeltaRecord`
emits the current-minus-previous 16-bit differences and latches current into
previous, `emitBlankValueRecord` and `emitObjectPositionVector` (a fixed header plus two clamped coordinate
words) lay down the body, and the pointer pair is swapped in and out with
`swapDrawPointers` so the shared cursors address the shadow structure between passes. The
slot's low three bits (`SLOT_LOOP_INDEX & 0x07`, with `0x07` folded to `0x00`) become the
phase in `loc_9e` and feed a scale word, and each slot closes with a fresh header
coordinate. When the counter goes negative the loop ends, swaps the pointers back,
emits a trailing intensity word, and finishes the base list through `loc_df09`.

### The per-frame draw drivers

A cluster of small routines invokes the builder for specific fixed slots to
assemble one frame's worth of overlay. `drawOverlayFrame` [seen] is the recurring driver:
it draws a slot chosen from the ROM table `DRAW_SLOT_TABLE` by `DSW1_SNAPSHOT & 0x03`, ticks the
timer `SCORE_DISPLAY_TIMER` down, then draws either the alternate slot `0x32` (when `DSW2_SNAPSHOT`
bit 0 is set and `FRAME_COUNTER` bit 5 is clear) or defers to `computeDisplayListChecksum`; it always redraws
the marker slot `0x2c` and slot `0x2e`, clamps `PHASE_COUNTER` to a ceiling of `0x28` and
emits it as a packed value through `loc_af77`, and when `HEARTBEAT_ACCUM_HI` is nonzero posts a
final coordinate word from `OVERLAY_VEC_WORD_A`/`OVERLAY_VEC_WORD_B`.

The count-draw drivers share the numeric-run tail. `loc_aa92` [code] draws the
fixed slot `0x02` and then runs `loc_aa97` [code], which publishes a zero scale
header (`emitScaleWordIfChanged` with `0x00`) and emits the one-byte digit run for the slot named
by `loc_3d` through `emitSlotIndexDigit` — that advances the index, stores it in `PROJ_Y_LO`,
and emits the run as nibble digits. `loc_aa5a` [code] draws slot `0x08` first and
then chains `loc_aa69` [code], which runs the `loc_aa92` prep followed by the
frame-setup routine `composeFrameDisplayList`. `loc_aa62` [code] primes slot `0x00` with header
`0x30` through `drawSlotShapeWithHeader`, runs the `loc_aa92` prep, and dispatches `composeFrameDisplayList`.
`loc_aa6f` [code] runs the alternate frame setup `buildTextOverlayList` and then primes slot
`0x06`, while `loc_aa79` [code] draws slot `0x32`, adds a second draw of slot
`0x22` (header `0xe0`) only while the status nibble `FRAME_COUNTER & 0x1f` is still below
`0x10`, and finishes with `buildTextOverlayList`.

`buildTextOverlayList` [seen] and `composeFrameDisplayList` [seen] are the two per-frame composition
routines the drivers hand off to, and they are near twins. Both draw the base
overlay through `drawOverlayFrame`, and emit the base list and — only
when the flag source is nonzero (`ACTIVE_SLOT_COUNT` while `STATUS_FLAGS` bit 7 is set, otherwise the
OR of `loc_43`, `loc_44`, `loc_45`) — a second list through `buildMarkerRowVectorList`. Both, unless
the state byte `GAME_MODE` equals `0x04`, rebuild a self-check byte in `DECIMAL_MODE_FLAG` by
XOR-folding `0xa7` over the eleven bytes at `SELFCHECK_XOR_BYTES`, and rebuild a strided mirror
in `VEC_GLYPH_BUFFER` by copying three doubled-index entries from `loc_61b` through the
point table `CHAR_GLYPH_TABLE`. Both emit the framing word `0x2f`/`0x60`, and both, when
`SPIKED_SEGMENT_COUNT` bit 7 is set, draw slot `0x36`; and when `GAME_MODE` equals `0x18` with
`STATUS_FLAGS` bit 7 set, they draw slot `0x30` and its numeric run (`loc_b0c6`) if
`loc_102 + loc_3d` is nonzero, then slots `0x3a` and `0x38`. Ahead of all that,
`buildTextOverlayList` alone refreshes the scale header (setting `VG_LAST_STAT`=0x01, emitting through `loc_df6a`, latching scale via `emitColorStatIfChanged`), selects a marker slot (`0x00`, `0x22`, or `0x06` depending on
`FRAME_COUNTER` bit 5, `PHASE_COUNTER` being zero, and `loc_a2` bit 7), draws it, and duplicates
the snapshot byte `NIBBLE_GLYPH_TABLE` into the mirror cells `VEC_SNAPSHOT_MIRROR_A` and `VEC_SNAPSHOT_MIRROR_B` before
drawing the base overlay.

## Object-record projection and emission helpers

This family turns live game state — the rim lanes of the tube, the enemies climbing it, the ship, the score and status glyphs, the depth of the well — into four-byte coordinate records written through the vector draw cursor at `DRAW_CURSOR_LO`/`DRAW_CURSOR_HI` (the low/high halves of the write pointer), with `DRAW_CURSOR_OFFSET` tracking the byte offset within the current run and the shared emitters (`loc_df4c`, `loc_df6a`, `loc_df6c`, `emitCoordinateVectorWord`, `emitScaledCoordinateRecord`, `emitVectorWord`, `loc_df09`) laying down the actual header and vector words and `advanceDisplayCursor` closing each run. The routines split into a rim-segment builder and its dispatch fan, a per-object display-list pass, a pair of paired-cursor gauges, the sixteen-lane colour pass, and a cluster of glyph/count/well draws.

### The rim-segment builder and its spread

`drawTubeRimSegmentFromCorner` [seen] is the workhorse that draws one tube-rim segment. Its full entry captures the segment's two rim endpoints from the corner tables — the source corner at `SEG_BASE_X+y`/`SEG_BASE_Y+y` into `PROJ_PT_Y`/`PROJ_PT_X` (with `loc_2f` taking the current `OBJ_DEPTH`), and the next corner at index `(y+1)&0x0f` into `loc_2e`/`loc_30`, so the sixteen rim corners wrap modulo sixteen — then seeds the run counters `CLAMP_TALLY`=0 and `RUN_SIZE`=4 before falling into the shared builder `emitTubeRimSegmentVectors`. `emitTubeRimSegmentVectors` (also entered directly, notably from the dispatch handlers below) first gates: unless `DEPTH_LO` bit7 is set it returns early when `OBJ_DEPTH < DEPTH_HI`. It reads the record count `DRAW_RECORD_COUNT` from `SEG_RECORD_COUNT+corner` and the packed-table cursor `TABLE_CURSOR` from `SEG_PACK_CURSOR+corner`, transforms both endpoints through the math box (`projectPointThroughMathbox`/`layHeaderAndBuildRecord`), then forms two signed deltas: delta one becomes the clamped magnitude `SEG_SPREAD_A_LO_1` with sign high byte `SEG_DELTA_A_SIGN` (`SEG_DELTA_A_SIGN`=`PROJ_Y_HI-PREV_Y_HI-borrow`; when the high byte is nonzero the magnitude saturates to 0xff, with the 0xff/−1 case negating instead), and delta two likewise becomes `SEG_SPREAD_B_LO_1` with sign `SEG_DELTA_B_SIGN`. From `SEG_SPREAD_A_LO_1` and `SEG_SPREAD_B_LO_1` it expands a fivefold spread into two multi-byte chains (`SEG_SPREAD_A_HI_2`–`SEG_SPREAD_A_HI_7` and `SEG_SPREAD_B_HI_2`–`SEG_SPREAD_B_HI_7`, with the low bytes `SEG_SPREAD_A_LO_2`–`SEG_SPREAD_A_LO_7` and `SEG_SPREAD_B_LO_2`–`SEG_SPREAD_B_LO_7`). It then emits `DRAW_RECORD_COUNT` four-byte records into `(DRAW_CURSOR_LO)+DRAW_CURSOR_OFFSET`: each record picks a header from `SEG_HEADER_BYTE+TABLE_CURSOR` (a header of 1 is remapped to 0xc0) and a packed corner byte from `SEG_PACKED_BYTE+TABLE_CURSOR`, advances `TABLE_CURSOR` by two, and decodes `yLo = packed & 0x07` and `xHi = ((packed<<1)>>4) & 0x07`. Point A (`PROJ_Y_LO`/`PROJ_Y_HI`) is fetched from the offset tables `SEG_SPREAD_A_LO`/`SEG_SPREAD_A_HI` at `yLo`, negated when the doubled-packed byte and `SEG_DELTA_A_SIGN` disagree in bit7, then combined with the `SEG_SPREAD_B_LO`/`SEG_SPREAD_B_HI` offset at `xHi` under `SEG_DELTA_B_SIGN`'s sign; point B (`PROJ_X_LO`/`PROJ_X_HI`) is fetched from `SEG_SPREAD_B_LO`/`SEG_SPREAD_B_HI` at `yLo` under `SEG_DELTA_B_SIGN` and combined with the `SEG_SPREAD_A_LO`/`SEG_SPREAD_A_HI` offset under `SEG_DELTA_A_SIGN`. The four bytes written per record are `PROJ_X_LO`, `PROJ_X_HI & 0x1f`, `PROJ_Y_LO`, and `(PROJ_Y_HI & 0x1f) | header`, after which `DRAW_CURSOR_OFFSET` advances and `DRAW_RECORD_COUNT` counts down; the run closes with `advanceDisplayCursor` at `(DRAW_CURSOR_OFFSET-1)&0xff`.

`drawScoreStatusList` [seen] is one front for that builder: it raises the rebuild flag `loc_9e`=0x01, reads the gate byte `PLAYER_SHOT_DEPTH`, and bails when it is zero or ≥0xf0; otherwise it latches the gate into both `OBJ_DEPTH` and `loc_2f`, and unless the marker `PLAYER_FINE_ANGLE` holds the skip value 0x81 it kicks `drawTubeRimSegmentFromCorner` with the corner index `PLAYER_SEGMENT` and a run size of `((RIM_ROT_OFFSET>>1)&0x07)+1`.

The main dispatch fan into that builder runs `drawStyledSlotList` → `loc_b5d7` → `drawSlotRimSegment`/`drawStyledSlotRimSegment`. `drawStyledSlotList` [seen] is the per-slot draw loop: it returns immediately when guard `SPIKE_ACTIVE_FLAG` bit7 is set, otherwise walks the loop counter `SLOT_LOOP_INDEX` from 6 down through wrap, and for each nonzero control byte `ENEMY_DEPTH,x` it caches the byte into `OBJ_DEPTH`, splits the paired slot byte `ENEMY_SLOT_FLAGS,x` into a style nibble `DRAW_STYLE = (paired & 0x18) >> 3` and a doubled selector `(paired & 0x07) << 1`, and dispatches through `loc_b5d7` carrying the slot index `x`. `loc_b5d7` [seen] is the computed-jump dispatcher `drawStyledSlotList` drives: it selects one of five draw handlers `[drawSlotRimSegment, drawStyledSlotRimSegment, emitJumpModeSlot, emitAnimatedPhaseSlot, emitInterpolatedSlotVector]` by `A>>1` and tail-returns its result. Of those, `drawSlotRimSegment` [seen] sets the run count `loc_9e`=0x03 and splits on the slot's sign byte `ENEMY_SLOT_FLAGS,x`: a negative slot preps a coordinate via `buildSlotScreenPoint` and builds a segment at corner zero (`emitTubeRimSegmentVectors(0x00)`), while a nonnegative slot builds at the slot's own corner `ENEMY_SEGMENT,x` with a run size chosen from `SEG_SHAPE_BY_STYLE` by the style index `DRAW_STYLE`. `drawStyledSlotRimSegment` [code] — not reached in the capture, though it is the selector-1 target — latches the run flag `loc_9e` from `ENEMY_ANIM_ACCUM`'s sign (0x04 when negative, else 0x00) and a style byte from `SEG_STYLE_TABLE` indexed by `((ENEMY_ANIM_ACCUM+0x40)&0xff)>>4` (clamped to 0 when ≥5), storing it in `loc_29`, then splits on `ENEMY_SLOT_FLAGS,x`'s sign the same way — `buildSlotScreenPoint` then `emitTubeRimSegmentVectors(loc_29)` for a negative slot, or `drawTubeRimSegmentFromCorner(loc_29, ENEMY_SEGMENT,x)` otherwise.

### Per-object and per-slot display-list passes

`buildObjectDisplayList` [seen] builds a vector display list for up to 0x12 active objects. It sets the run tag `loc_9e`=0x0c, emits an opening header (`loc_df4c(0x08,0x0c)`, `layHeaderAndBuildRecord(0x66)`), seeds the remaining-object count `PROJ_PT_Y`=0x12 and the table index `SLOT_LOOP_INDEX`=0x3f, and walks `SLOT_LOOP_INDEX` downward. For each nonzero kind byte `OBJECT_RECORD_TABLE,idx` it emits a header word derived by rotating the raw kind left three times and forming `((rot & 0x03)+1) | 0x70` (kinds ≥0x50 also step `SLOT_LOOP_INDEX` an extra time and carry a 1 into the rotate), then writes the object's screen-relative coordinates: `dxLo = OBJ_DX_LO,obj - PROJ_OFS_X_LO`, `dxHi = OBJ_DX_HI,obj - PROJ_OFS_X_HI - borrow` (masked to `&0x1f`), and `dyLo`/`dyHi` straight from `OBJ_DY_LO,obj`/`OBJ_DY_HI,obj`, where `obj = OBJECT_INDEX_TABLE,idx`. Four fixed bytes (0,0,0,0xa0) follow, then the negated shadow of each coordinate word (two's-complement mirror), so every object is drawn once and once mirrored. When the byte offset `y` saturates at ≥0xf0 it flushes with `advanceDisplayCursor` and restarts the run; the object count `PROJ_PT_Y` ending negative or the index `SLOT_LOOP_INDEX` ending negative breaks the loop. After a final flush it conditionally sets `IRQ_HEARTBEAT`=0x7a when `CHECKSUM_ACC`≠0 and `PLAYER_LEVEL_TBL`≥0x0a, and closes with `loc_df6a(0x01)`.

`drawEnemyShapeList` [seen] emits one shape record per active slot across the eight enemy slots, walking `SLOT_LOOP_INDEX` from 7 down. For each nonzero cell `SHAPE_ACTIVE,slot` it latches the cell into `OBJ_DEPTH` and the coordinate `SHAPE_COORD,slot` into `loc_29`, then reads the shape id `SHAPE_ID,slot`: shape 1 hands off to the animated emitter `animateShapeOneVector`, while any other shape computes a table base `((SHAPE_ANIM,slot>>1)&0xfe`, forced to 0 when shape≥2) added to `ENEMY_SHAPE_BASE+shape` and draws through `seatShapeParamsAndEmit`. Its tail, when `loc_720`≠0, copies the saved byte `loc_9f` into `HIGH_LEVEL_MARKER` only if `loc_9f`≥0x0d. The shape-1 handler `animateShapeOneVector` [code] — not reached in the capture — refreshes two axis parameters `PROJ_PT_Y`/`PROJ_PT_X` from `SEG_MID_X`/`SEG_MID_Y` at `loc_29`, runs the frame updaters (`projectPointThroughMathbox`, `layHeaderAndBuildRecord(0x61)`), counts down the sub-timer `OBJECT_ANIM_TIMER` and, on wrap, advances the phase index `OBJECT_ANIM_PHASE` and reloads `OBJECT_ANIM_TIMER` from `ANIM_PHASE_DURATION+OBJECT_ANIM_PHASE`; it runs the phase handler `loc_b84e` when the phase byte `ANIM_PHASE_CODE+OBJECT_ANIM_PHASE` is under 0x80, then emits the phase's vector-pair word from `OBJ_TEMPLATE_WORD_LO`/`OBJ_TEMPLATE_WORD_HI` at index `((OBJECT_ANIM_PHASE<<1)+0x28)&0xff` through the shared vector-word tail `emitVectorWord`.

`buildEnemyDisplayList` [seen] rebuilds the per-frame enemy display list of up to sixteen slots. It returns when `loc_110`≠0, or when `DEPTH_LO`==0 with `DEPTH_HI`≥0xf0; otherwise it opens with `loc_df6a(0x01)`, saves the cursor `DRAW_CURSOR_LO`/`DRAW_CURSOR_HI`, zeroes the table index `TABLE_CURSOR` and byte offset `DRAW_CURSOR_OFFSET`, and starts at slot 0x0f (0x0e when `TUBE_GEOM_FLAG`≠0). Each pass copies the fixed four-byte header from `ENEMY_LIST_HEADER` into the cursor, then either — when `REDRAW_COUNTER`≠0 — runs `emitSlotMidpointVertex` and the perspective enemy-entry producer `emitEnemySlotEntry`, or reads a kind byte `LANE_TARGET_FLAG,TABLE_CURSOR`: a negative kind copies four bytes from the source `(DRAW_SRC_PTR_LO)` into `PREV_X_LO`/`PREV_X_HI`/`PREV_Y_LO`/`PREV_Y_HI` (sign-extending the two high bytes with `|0xe0` when ≥0x10) and then calls `emitEnemySlotEntry`, while a nonnegative kind copies a straight 0x0c-byte block. After each slot it shifts `LANE_TARGET_FLAG,idx` left, advances `TABLE_CURSOR`, and steps `SLOT_LOOP_INDEX` until it wraps; it then restores the cursor into `DRAW_SRC_PTR_LO`/`DRAW_SRC_PTR_HI` and flushes with `advanceDisplayCursor`.

`drawTimedObjectList` [seen] draws eight slots while the guard `SPIKE_TABLE_GUARD` is set: it forces `DEPTH_HI`=0xe8, `DEPTH_LO`=0xff, and `loc_a0`=0x28, walks `SLOT_LOOP_INDEX` from 7 down, and for each nonzero entry `loc_3fe,slot` sets `OBJ_DEPTH` to the entry with `PROJ_PT_Y`=`PROJ_PT_X`=0x80, picks a colour mode (`slot & 0x07`, with 7 remapped to 4, when `loc_9f`≥0x05, else 0x06) into `loc_9e`, emits it (`loc_df4c(0x08,mode)`), sets the style `DRAW_STYLE = ((slot & 0x03)<<1)+0x0a`, and draws via `emitColoredShapeVector`; the three forced cells are restored afterward. Its tail, gated on `loc_11f`≠0 and `loc_42`≥0x15, increments the coordinate cell `PLAYER_SEGMENT+loc_40`.

### The sixteen-lane colour pass and its pointer setup

`paintRimLanes` [seen] rebuilds the sixteen-entry lane-flag block `LANE_FLAGS` and paints the rim lanes. When `REDRAW_COUNTER`≠0 it first runs the pointer/slot pre-pass (`seatDrawCursor(0x02)`, `initAndDrawRimDepthCounters`, `closeLayerPointer(0x02)`), then always refreshes the base pointer with `seatAltDrawPointer(0x02)`. It clears `LANE_FLAGS[0..0x0f]`, and unless guard `SPIKE_ACTIVE_FLAG` bit7 is set it merges enemy presence: for each slot from `ENEMY_SLOT_TOP` down, when the control byte `ENEMY_DEPTH,x`≠0 and `(ENEMY_SLOT_FLAGS,x & 0x07)`==0x01 it sets `loc_29`=1, and for a nonnegative `ENEMY_SLOT_FLAGS,x` it adds 2 to `loc_29` when `ENEMY_ANIM_ACCUM` is nonnegative and `ENEMY_DEPTH,x < NEAR_DEPTH_THRESHOLD`, then ORs `loc_29` into the near lane `LANE_FLAGS[ENEMY_PHASE,x]` and `loc_29 | 0x80` into the far lane `LANE_FLAGS[ENEMY_SEGMENT,x]`. A base colour `loc_29`=0x06 is chosen (dropped to 0x01 when `WAVE_PHASE_LATCH` is live and `(FRAME_COUNTER & 0x07)`==0x07); the two special columns `loc_2a`/`loc_2b` are cached from `PLAYER_SEGMENT`/`PLAYER_FINE_ANGLE` when `PLAYER_SHOT_DEPTH`≠0 and `PLAYER_FINE_ANGLE` is nonnegative; and an animation offset `COORD_LIST_PTR_LO = (RIM_COLOR_ANIM & 0x0e)>>1` is taken (decrementing `RIM_COLOR_ANIM`) while `RIM_COLOR_ANIM` is nonnegative. The first pass, over all sixteen lanes, chooses each value — a flagged lane yields `FRAME_COUNTER & 0x01` when flag bit1 is set else 0x06; a special column yields 0x01; a stalled animation yields the base `loc_29`; otherwise a cycling rainbow index `seg = (x + COORD_LIST_PTR_LO) & 0x07` (7 remapped to 3) — and stores it through `(WORK_PTR_LO)` at slot `RIM_LANE_SLOT_TABLE_A+x`. The second pass ORs the flag's colour bits (0x00 when `LANE_FLAGS,x` bit7 set, else 0xc0) into `(DRAW_PATCH_PTR_LO)` at slot `RIM_LANE_SLOT_TABLE_B+x`, starting at 0x0e when `TUBE_GEOM_FLAG` is negative else 0x0f.

`closeLayerPointer` [seen] emits a header (`loc_df09`), toggles this slot's parity flag `POINTER_PARITY+slot ^= 0x01`, and writes the pointer target `(WORK_PTR_LO)` with the word chosen by the freshly toggled parity — `DRAW_PTR_ODD_LO`/`DRAW_PTR_ODD_HI` when parity is set, `DRAW_PTR_EVEN_LO`/`DRAW_PTR_EVEN_HI` when clear — at stride `2*slot`, having first seated the base pointer from `DRAW_BASE_PTR_LO`/`DRAW_BASE_PTR_HI`. `initAndDrawRimDepthCounters` [seen] performs the first-time counter setup: when `loc_110`==0 it seeds `loc_110`/`loc_10f` through the integrator `projectAllLanesThroughMathbox` (nudging the low counter when it lags), always emits a header (`loc_df6a`, `loc_9e`=0x06), and returns unless both counters are live and `loc_113`≠0; then it clears the record slots by looping `loc_c3ee` two indices at a time and draws each counter's record set with `drawGatedRecordLoop`. `loc_c3ee` [seen] draws a framed element in two passes: it emits the current slot `SLOT_LOOP_INDEX` with the colour `VG_RECORD_HEADER` live, steps back one slot and re-emits it uncoloured, then restores the colour and closes the frame, returning the stepped-back index.

### Glyph, count, and well draws

`loc_ae4e` [seen] emits a descending run of glyph rows, seeding each row's coordinate triple from `GLYPH_PARAM_X`/`GLYPH_PARAM_Y`/`GLYPH_PARAM_Z`. It stashes the caller's argument in `PROJ_X_LO`, primes the pen with `emitScaleWordIfChanged(0x01)`, sets the running column `COORD_LIST_PTR_LO`=0x28 and the row index `SLOT_LOOP_INDEX`=0x15, and each pass steps `COORD_LIST_PTR_LO` back by 0x0a, positions with `emitScaledCoordinateRecord(0xd0, prev)`, selects a tag through `emitColorStatIfChanged` (0x00 when the current row `SLOT_LOOP_INDEX` equals the argument `PROJ_X_LO`, else 0x07), draws the glyph body (`emitNibbleDigitRun`, `emitBlankValueRecord`, `drawThreeCharGlyphString`), and re-seats `PROJ_PT_Y`/`OBJ_DEPTH`/`PROJ_PT_X` from the coordinate tables before drawing them and dropping `SLOT_LOOP_INDEX` by 3. `seedRngAndDrawCounterPanel` [seen] feeds it: it folds two POKEY random samples `POKEY1_RANDOM` and `POKEY2_RANDOM` into a scratch `loc_29` and a stored nibble `loc_11f`, draws the counters via `loc_af26`, then calls `loc_ae4e(0xff)`. `loc_adea` [code] — not reached in the capture — draws a fixed frame, ticks the countdown `SCORE_DISPLAY_TIMER`, and hands a score delta `ACTIVE_SLOT - REARM_COUNTER` to `loc_ae4e`.

The two low-level pen latches keep the emitter from re-declaring an unchanged attribute. `emitColorStatIfChanged` [seen] skips when the current tag `loc_9e` already equals its argument, otherwise latches it and emits a fixed-tag record (`loc_df4c(0x08, y)`); `emitScaleWordIfChanged` [seen] skips when `VG_LAST_STAT` already matches its argument, otherwise latches it and emits its vector word (`loc_df6a`).

## The mathbox: projection and level tables

Tempest draws its tube in perspective through a hardware math coprocessor — the "Math Box" — mapped into the register block at MATHBOX_LD_R0_LO through MATHBOX_LD_R7_HI, with its busy signal in the high bit of MATHBOX_STATUS and its two-byte result read back from MATHBOX_RESULT_LO (low) and MATHBOX_RESULT_HI (high). Several routines here feed that coprocessor points from the current level's geometry tables and read back projected screen coordinates; others build and unpack those level tables in the first place.

### Projecting one point (projectPointThroughMathbox [seen])

projectPointThroughMathbox is the projection driver: it turns one tube-space point into a pair of accumulated screen coordinates. It first forms a signed 16-bit delta from the coordinate operands, writing the low byte OBJ_DEPTH minus DEPTH_HI into the coprocessor delta register MATHBOX_LD_R7_LO and the negated high part (`0 - DEPTH_LO - (1 - carry)`) into MATHBOX_LD_R7_HI; a negative result is clamped up to the smallest positive value, forcing MATHBOX_LD_R7_HI to 0x00 and MATHBOX_LD_R7_LO to 0x01. It then computes the absolute horizontal magnitude `|PROJ_PT_X - PROJ_X_REF|`, recording its sign (0xff when PROJ_PT_X is the smaller) in MATHBOX_SIGN_X and pushing the magnitude to the coprocessor inputs MATHBOX_LD_RA_HI and MATHBOX_DIVIDE, and the absolute vertical magnitude `|PROJ_PT_Y - PROJ_Y_REF|` into loc_32 with its sign in MATHBOX_SIGN_Y. After spinning until MATHBOX_STATUS bit 7 clears, it reads the coprocessor result into PROJ_X_LO/PROJ_X_HI, re-issues loc_32 to MATHBOX_LD_RA_HI/MATHBOX_DIVIDE, and folds the offset pair PROJ_OFS_X_LO/PROJ_OFS_X_HI into PROJ_X_LO/PROJ_X_HI as a 16-bit signed add or subtract chosen by the sign flag MATHBOX_SIGN_X — a signed overflow saturates the pair to 0x0080 (most-negative) or 0x7fff (most-positive). It waits on the coprocessor a second time, reads the next result into PROJ_Y_LO/PROJ_Y_HI, and similarly folds PROJ_OFS_Y_LO/PROJ_OFS_Y_HI into that second accumulator under the control of sign flag MATHBOX_SIGN_Y, with the same saturation. The two 16-bit accumulators PROJ_Y_LO/PROJ_Y_HI and PROJ_X_LO/PROJ_X_HI are the projected coordinate pair handed back to the caller.

### Resetting the coprocessor (resetMathboxInputs [seen])

resetMathboxInputs clears the working state before a projection run. It zeroes the zero-page scratch cells SEG_SPREAD_A_LO, SEG_SPREAD_A_HI, SEG_SPREAD_A_HI_1, SEG_SPREAD_B_LO, SEG_SPREAD_B_HI and SEG_SPREAD_B_HI_1, then blanks the coprocessor input block MATHBOX_LD_R0_LO, MATHBOX_LD_R0_HI, MATHBOX_LD_R1_HI, MATHBOX_LD_R2_LO, MATHBOX_LD_R2_HI, MATHBOX_LD_R3_LO, MATHBOX_LD_R3_HI, MATHBOX_LD_R4_HI, MATHBOX_LD_RA_LO, MATHBOX_LD_RA_HI, MATHBOX_LD_RB_LO and MATHBOX_LD_RB_HI — every input except the control latch — and finally writes the control value 0x0f into MATHBOX_LD_R6_COUNT to arm the coprocessor for the next operation.

### Sweeping the tube rim through the coprocessor (projectAllLanesThroughMathbox [seen])

projectAllLanesThroughMathbox [seen] projects a whole ring of lane points in one pass. It seeds OBJ_DEPTH from the caller's value and the output index TABLE_CURSOR from the caller's index, clears the clamp tally CLAMP_TALLY, and runs sixteen passes with the column counter SLOT_LOOP_INDEX walking 0x0f down to 0. Each pass loads that column's base coordinates from the per-lane tables SEG_BASE_X and SEG_BASE_Y into PROJ_PT_Y and PROJ_PT_X, drives projectPointThroughMathbox to project them, then clamps each returned 16-bit accumulator's high byte to the window [-4..+3] (0xfc..0x03). The clamp reports a value and a sign: a value with bit 7 set below 0xfc floors to 0xfc with sign 0x01, a value 0x04 or above ceilings to 0x03 with sign 0xff, and anything in range passes through with its stored sign. The first pair (high byte PROJ_Y_HI, sign byte PROJ_Y_LO) is written to COL_VAL_A and COL_SUB_A indexed by TABLE_CURSOR, the second pair (PROJ_X_HI, PROJ_X_LO) to COL_VAL_B and COL_SUB_B; each actual clamp bumps CLAMP_TALLY, which is returned as the clamp count once TABLE_CURSOR and SLOT_LOOP_INDEX have counted down past zero. The four output arrays COL_VAL_A/COL_SUB_A/COL_VAL_B/COL_SUB_B thus hold the projected, range-limited screen deltas for all sixteen tube lanes.

### Packing a level/shape byte (resolveShapeTableIndex [seen])

resolveShapeTableIndex [seen] reduces an input byte into a packed table reference. A value of 0x62 or higher is discarded and replaced by a masked hardware byte, POKEY1_RANDOM AND 0x5f, before the split; the value is then divided into a quotient (`value >> 4`) and remainder (`value & 0x0f`). The remainder indexes the ROM table SHAPE_INDEX_TABLE, and that entry is stored to TUBE_SHAPE_INDEX — the shape/level index other routines read back — while the routine hands back a packed byte whose high nibble is the table entry and whose low nibble is forced to 0x0f, along with the quotient and remainder.

### Unpacking the per-level nibble tables (unpackLevelNibbleTables [seen], resetVectorTailCursor [code], buildLevelLayout [seen])

unpackLevelNibbleTables [seen] expands the packed ROM table LEVEL_LAYOUT_PACKED into the working nibble tables. It masks the selector loc_9f with 0x70, clamps it to at most 0x5f, and forms the read index `(selector >> 1) | 0x07`. Walking y from 7 down to 0, it reads each packed byte, sends its low nibble to both the zero-page table LEVEL_GEOM_LO+y and the display-list mirror COLOR_RAM+y, and its high nibble to LEVEL_GEOM_HI+y and the mirror COLOR_RAM_8+y, stepping the read index down each pass. The result is two eight-entry tables and their on-screen mirrors describing the current level.

resetVectorTailCursor [code] rebuilds those tables — it runs the same unpack through unpackLevelNibbleTables and then seats the vector-list tail cursor, writing 0x7f to VECRAM_TAIL_CURSOR_LO and 0x04 to VECRAM_TAIL_CURSOR_HI. It is not reached in the capture.

buildLevelLayout [seen] is the fuller level-layout builder. It primes the working flags (setting PROJ_Y_REF to 0x80 and REDRAW_COUNTER to 0xff), builds the tube geometry through buildTubeLaneCoords, and manages the mode trigger LEVEL_LAYOUT_TRIGGER — clearing AVG_RESET_STROBE only when LEVEL_LAYOUT_TRIGGER was already zero, then forcing LEVEL_LAYOUT_TRIGGER to zero. It mirrors the two header bytes VECHEAD0_LEVEL and VECHEAD1_LEVEL into the display registers VEC_LIST_HEADER_LO and VEC_LIST_HEADER_HI, then inlines the same LEVEL_LAYOUT_PACKED nibble unpack as unpackLevelNibbleTables — clamping loc_9f AND 0x70 to 0x5f, halving and OR-ing with 0x07, and filling LEVEL_GEOM_LO/COLOR_RAM and LEVEL_GEOM_HI/COLOR_RAM_8 across eight entries. Its own writes — PROJ_Y_REF, REDRAW_COUNTER, LEVEL_LAYOUT_TRIGGER and the header mirror into VEC_LIST_HEADER_LO/VEC_LIST_HEADER_HI — are observed in the capture.

### Building the tube's lane coordinates (buildTubeLaneCoords [seen])

buildTubeLaneCoords [seen] lays out the current level's tube. It first reduces a selected table byte (indexed by PLAYER_LEVEL_TBL+loc_3d) through resolveShapeTableIndex, taking the shape index TUBE_SHAPE_INDEX as its row `y` into the ROM level-parameter tables. From those it derives the span cells: the negated value of LEVEL_TUBE_DEPTH+y seeds both DEPTH_HI and DEPTH_TARGET, its complement `0x10 - value` seeds loc_a0, the guard DEPTH_LO is set to 0xff, PROJ_X_REF takes LEVEL_PARAM_LOC60+y, and TUBE_GEOM_FLAG takes LEVEL_GATE_FLAG+y. When the mode byte GAME_MODE_PENDING holds 0x1e the offset pair PROJ_OFS_X_LO/PROJ_OFS_X_HI is copied straight from LEVEL_OFFSET_LO+y and LEVEL_OFFSET_HI+y; otherwise the routine forms the signed 16-bit difference between {LEVEL_OFFSET_HI:LEVEL_OFFSET_LO} and {PROJ_OFS_X_HI:PROJ_OFS_X_LO}, shifts it right four bits, and keeps the low byte as the level geometry scale LEVEL_GEOM_SCALE. It then clears PROJ_OFS_Y_LO, PROJ_OFS_Y_HI, loc_10f and loc_110 and sets loc_113 to 0x2c.

With those scalars in place it seeds six per-column arrays top-down over x from 0x0f to 0, walking a neighbour index down from the reduced seed: each column's base coordinates come from the ROM vertex tables LANE_VERTEX_X into SEG_BASE_X+x and LANE_VERTEX_Y into SEG_BASE_Y+x, a third vertex table LANE_RING_DIR into SEG_DIRECTION+x, while the projected-output arrays COL_VAL_A+x, COL_VAL_B+x and LANE_TARGET_FLAG+x are cleared to zero. Finally it fills two midpoint arrays by rounding-averaging each column with its wrapping next neighbour — SEG_MID_X+x from SEG_BASE_X and SEG_MID_Y+x from SEG_BASE_Y — where the average adds the two bytes plus one and rotates the sum right, carrying the ninth bit back into bit 7. SEG_BASE_X/SEG_BASE_Y hold the tube's per-lane vertex coordinates and SEG_MID_X/SEG_MID_Y the averaged midpoints between adjacent lanes.

### Snapping a coordinate up to reference (snapCoordUpToReference [seen])

snapCoordUpToReference [seen] nudges one coordinate up toward a reference. If the guard DEPTH_LO is non-zero it does nothing; if OBJ_DEPTH already sits 0x0c or more above the reference DEPTH_HI it also leaves it alone; otherwise it raises OBJ_DEPTH to `DEPTH_HI + 0x0f`, capped at the ceiling 0xf0. These are the same OBJ_DEPTH/DEPTH_LO/DEPTH_HI operands the projection driver consumes.

### Selecting the projection scale (selectProjectionScale [seen])

selectProjectionScale [seen] chooses a scale and a mode bit from two gate cells. The default selection is value 0x00 with scale 0x10; only when both gates loc_117 and loc_3d are non-zero does it switch to value 0x04 with scale 0x08 — in the capture only the default branch is exercised. It copies bit 2 of the chosen value into the mode flag VG_MODE_FLAG while preserving every other bit, and stores the chosen scale into VG_SCALE.

### Emitting a shape from the vertex tables (drawTubeShapeOutline [seen])

drawTubeShapeOutline [seen] draws an outline by walking the same ROM vertex tables the geometry builder uses. It reduces its input byte through resolveShapeTableIndex, keeping the reduced value in SAVED_INDEX2 and the quotient in SAVED_INDEX, clears VG_RECORD_HEADER and emits a framing record. The low three bits of SAVED_INDEX index the ROM header table OUTLINE_HEADER, whose entry is stored to loc_9e and emitted as an eight-wide record. It then reads the shape index TUBE_SHAPE_INDEX, chooses a starting seed of SAVED_INDEX2 (rolled back by 0x0f when LEVEL_GATE_FLAG+shape is zero), and seats the first vertex — LANE_VERTEX_Y+seed into OBJ_DEPTH and LANE_VERTEX_X+seed into PROJ_PT_Y — emitting it with both coordinates biased by 0x80. Raising VG_RECORD_HEADER to 0xc0 and loading the step counter TABLE_CURSOR with 0x0f, it then walks sixteen steps: each pass reads the next vertex from LANE_VERTEX_X and LANE_VERTEX_Y at index SAVED_INDEX2, emits the signed delta from the previous vertex, updates PROJ_PT_Y/OBJ_DEPTH, and steps SAVED_INDEX2 down until the counter passes below zero, closing with a final framing record. The effect is a sixteen-segment vector outline traced through the level's own vertex coordinate tables.

## Sound, POKEY and the interrupt heartbeat

Tempest carries two POKEY chips, mapped side by side: the first occupies the eight audio registers `POKEY1_AUDF1`..`loc_60c7` with its control register `POKEY1_AUDCTL`, its random-number register `POKEY1_RANDOM`, and its serial-control register `POKEY1_SKCTL`; the second mirrors that layout at `POKEY2_AUDF1`..`loc_60d7`, `POKEY2_AUDCTL`, `POKEY2_RANDOM`, and `POKEY2_SKCTL`. A software voice engine sits above them, translating abstract sound requests into per-frame register writes, and a short chain of counters riding on the CPU interrupt keeps the game's timebase and running tallies moving.

### The interrupt heartbeat

`tickHeartbeatCounters` [seen] runs on every interrupt, immediately ahead of the voice stepper, and it is the busiest routine in this group. It walks three parallel lanes indexed 2, 1, 0, each lane gated by its own bit of the control byte `INPUT_PORT_LATCH`: lane 2 by bit 0, lane 1 by bit 1, lane 0 by bit 2 (the code shifts `INPUT_PORT_LATCH` right once for lane 2, twice for lane 1, three times for lane 0, landing the chosen bit in carry — the first shift tests bit 0, so lane order runs opposite to bit order). For each enabled lane it advances a wrapped position held in the `LANE_WRAP_POS`/`loc_e`/`loc_f` triple, keeping it masked to five bits (0x1f) and folding it around the 0x20 boundary — a value climbing past 0x1f wraps back low, and the descending branch adds 0x20 then re-clamps to 0x1f. Alongside the position it runs the per-lane down-timer `LANE_DOWNTIMER`,x: when that timer hits zero it reloads it to 0x78 and raises the carry that drives the accumulator step. That step folds a small per-lane increment into the running pair `HEARTBEAT_ACCUM_LO`/`HEARTBEAT_ACCUM_HI` (a low/high accumulator advanced with a carry link) and bumps the per-lane counter `LANE_COUNTER`,x. The increment itself is tiny and lane-specific: lane 0 contributes 0, lane 1 contributes 0x01 only when bit 4 of `DSW1_SNAPSHOT` is set, and lane 2 derives its value from `(DSW1_SNAPSHOT & 0x0c) >> 2` with a `+2+carry` adjustment — in every case the masked bits act as a gate on whether the contribution lands, not as its magnitude.

After the three-lane sweep, `tickHeartbeatCounters` reduces the high accumulator `HEARTBEAT_ACCUM_LO` by a table amount indexed from the top bits of `DSW1_SNAPSHOT` (the lookup `ACCUM_REDUCE_TABLE`), advancing the overflow tally `HEARTBEAT_ACCUM_OVERFLOW` when the subtraction stays non-negative, and it may nudge `PHASE_COUNTER` from the low two bits of `DSW1_SNAPSHOT` before finally storing `HEARTBEAT_ACCUM_HI`. It closes with two clamp passes over the `LANE_COUNTER` lane triple whose constants differ and must not be conflated: the first pass fires only on a lane counter that has reached 0x10 or more, subtracting 0x10 from it (encoded as `+0xef` with the incoming carry set); the second pass, taken only when the first found nothing to trim, subtracts 0x11 from any non-zero lane counter (`+0xef` with carry clear) and stops at the first that would go negative. The masks throughout gate which lanes and which steps apply; they are not themselves the stepped values.

`commitPendingModeAfterDelay` [seen] is the guarded delay that promotes a pending mode. While the guard formed by `FRAME_COUNTER & MODE_DELAY_GUARD` is set it does nothing but hand off. Otherwise it runs the delay counter `MODE_DELAY_TIMER` down, and on the frame that counter reaches zero it arms the live mode `GAME_MODE` from the pending mode `GAME_MODE_PENDING` and clears the guard `MODE_DELAY_GUARD` back to zero. Every path tail-delegates the spinner update to `rotateBlasterAroundRim`.

### The voice engine and the request path

`stepSoundVoices` [seen] is the per-frame sound engine. It scans all sixteen voice slots from 0x0f down to 0, skipping any slot whose value byte `SOUND_VOICE_VALUE`,x is zero (idle) and the one slot currently reserved by the sentinel in `SOUND_SLOT_SENTINEL`. For a live slot it decrements the fast timer `SOUND_FAST_TIMER`,x; only when that reaches zero does it decrement the slow timer `SOUND_SLOW_TIMER`,x. If the fast timer expired but the slow one is still running, it takes a single animation step: the slot's frame byte selects a table pair (the `VOICE_ENV_FASTTIMER`/`VOICE_ENV_LEVEL` pair, or the `VOICE_ENV_FASTTIMER_HI`/`VOICE_ENV_LEVEL_HI` pair when the frame's high bit is set), reloads the fast timer from one entry, and folds the other into the slot's level byte `SOUND_VOICE_LEVEL`,x — with odd-numbered slots preserving the prior high nibble of that level. When both timers have expired it instead walks the frame forward (in steps of two) through the `VOICE_ENV_FRAME_A`/`VOICE_ENV_FRAME_B` (or `VOICE_ENV_FRAME_A_HI`/`VOICE_ENV_FRAME_B_HI`) tables until it lands on a non-zero frame, reloading both timers and the level as it goes. Whatever the path, the slot's final level byte `SOUND_VOICE_LEVEL`,x is published to a POKEY audio register: slots below 8 write into `POKEY1_AUDF1`,x on the first chip, the upper slots into `POKEY1_AUDCTL`,x. MAME confirms the POKEY audio-register writes; this routine is heavily exercised.

Requests reach that engine through `loadSoundVoiceSlots` [seen], the sound loader. Given a sound id in A, it first stashes the caller's X and Y into `loc_31`/`loc_32`, then reads the sound's row of table bytes from `SOUND_VOICE_TABLE` indexed by a descending id, one entry per slot from 0x0f down to 0. Every non-zero table byte claims a slot: it marks the slot number in `SOUND_SLOT_SENTINEL`, writes the table byte into that slot's value `SOUND_VOICE_VALUE`,x, sets both the fast flag `SOUND_FAST_TIMER`,x and slow flag `SOUND_SLOW_TIMER`,x to 1, then drops the 0xff sentinel back into `SOUND_SLOT_SENTINEL`. MAME shows it stamping the channel-value table `SOUND_VOICE_VALUE`..`loc_cf` and the paired flag arrays `SOUND_FAST_TIMER`..`loc_ef`/`SOUND_SLOW_TIMER`..`loc_ff` heavily, which is where the voice engine picks the work up.

In front of `loadSoundVoiceSlots` sits the enable gate `requestSoundIfEnabled` [code]: it tests the high bit of the enable flag `STATUS_FLAGS` and, only when that bit is set, falls through to register the id in A; with sound disabled it simply returns. Its own vectoring was not witnessed in the capture, though its handler is [seen].

A family of one-line trampolines each carry a fixed sound id into that gate, all threading the caller's X/Y through to the loader, and each is [code] because it makes no cell write of its own — the audible effect is entirely the loader's: `loc_ccb5` id 0x0f, `loc_ccc1` id 0x1f, `loc_ccea` id 0x2f, `loc_cd02` id 0x3f, `loc_ccb9` id 0x4f, `loc_ccb0` id 0x5f, `loc_ccee` id 0x6f, `loc_ccf2` id 0x7f, `loc_ccbd` id 0x8f, `loc_ccf6` id 0x9f, `loc_ccfe` id 0xbf, and `loc_cd06` id 0xcf. `loc_ccfa` [code] is the one exception in shape: it loads id 0xaf but jumps straight into the loader `loadSoundVoiceSlots`, bypassing the enable gate; which in-game event 0xaf denotes is not settled from the code alone.

### Reset, pot scan and switch decode

`resetBothPokeyChips` [seen] is the dual-POKEY reset. It first zeroes both serial-control registers `POKEY1_SKCTL`/`POKEY2_SKCTL` and a scratch flag `loc_720`. It then samples the two random-number registers `POKEY1_RANDOM` and `POKEY2_RANDOM` across a five-iteration poll and, the moment either reading changes, latches the first sample into `loc_720` — a random-generator liveness check. It sets both serial-control registers to 7 (the canonical POKEY init) and clears the eight audio registers of each chip, `POKEY1_AUDF1`..`loc_60c7` and `POKEY2_AUDF1`..`loc_60d7`, together with the paired software arrays `SOUND_VOICE_VALUE`,x and `SOUND_VOICE_LEVEL`,x, finishing by zeroing both control registers `POKEY1_AUDCTL`/`POKEY2_AUDCTL`.

`assemblePotStatusByte` [code] assembles a status nibble around the second POKEY. It writes its incoming value to `POKEY2_POTGO` — a pot-scan pulse the board discards — then mirrors the low three bits of the control register `POKEY2_AUDCTL` into both the scratch byte `SLOT_LOOP_INDEX` and the register `POKEY1_POTGO`, and returns those three bits merged with one relocated bit lifted from `(POKEY1_AUDCTL & 0x20) >> 2`. The return therefore carries an assembled pot-status byte drawn from `POKEY2_AUDCTL` and `POKEY1_AUDCTL`; every value observed in the capture was constant, so the packing role rests on the code rather than on witnessed variety.

`decodeOptionSwitches` [seen] decodes the option (DIP) switch input ports into game configuration. It reads port `DSW2_OPTIONS` into `DSW2_SNAPSHOT` and slices it three ways: bits 5-3 index the table `DIP_BONUS_INTERVAL` into `BONUS_LIFE_INTERVAL`, bits 7-6 index `DIP_PARAM_158` into `DSW_BONUS_CONFIG`, and the two-bit field at `a0 & 0x06` indexes the paired tables `DIP_CONFIG_A`/`DIP_CONFIG_B` into `loc_ac` and `loc_ad`. It stores the other port `DSW1_COINAGE` (with bit 1 toggled) into `DSW1_SNAPSHOT`, and folds `loc_ad` through `assemblePotStatusByte`, recording the merged result in `DSW_DIFFICULTY`.

`runMathboxDivide` [code] primes a memory-mapped arithmetic unit and reads its result. It clears `VG_RECORD_HEADER`, `loc_414`, and `MATHBOX_LD_RB_HI`, seeds the operand registers `MATHBOX_LD_RA_HI`/`MATHBOX_LD_RB_LO` from A and X, and sets the count registers `MATHBOX_LD_R6_COUNT`/`MATHBOX_DIVIDE` to 0x10 to launch the operation. It then scans a sixteen-slot window at `MATHBOX_STATUS` for the first slot whose high bit is clear (ready) and hands back that slot's low/high result pair from `MATHBOX_RESULT_LO`/`MATHBOX_RESULT_HI`, or exits with the counter run past the end when none is ready. It was not exercised in the capture, so the reading is code-level.

### Channel record sort and active-slot tick

`buildSortedSoundRequest` [seen] builds a sound draw request by sorting each channel's record table. It clears bit 6 of `STATUS_FLAGS`, optionally pre-clears the staging block through `clearChannelStagingBlock` when `DSW1_SNAPSHOT & 0x43` equals 0x40, and zeroes the running total `loc_601`. For each of the two channels (0 or 3, chosen from `ACTIVE_SLOT_COUNT`) it seats the key triple `COORD_LIST_PTR_LO`/`COORD_LIST_PTR_HI`/`loc_2e` from the channel's `loc_42`/`loc_41`/`loc_40` entries, sets the channel bit `SAVED_INDEX2`, seeds the working values `loc_2a`/`loc_29` to 0x1a with `loc_2b` cleared, and bubble-sorts the row triples `SORT_KEY_HI`/`SORT_KEY_MID`/`SORT_KEY_LO` (with the parallel payload `SORT_PAYLOAD_LO`/`SORT_PAYLOAD_MID`/`SORT_PAYLOAD_HI`) into lexicographic order, counting settle passes in `PASS_COUNTER`. Each channel's pass count is stored to `SLOT_METRIC`,channel. It then nudges the total `loc_601` when it has caught up to `SLOT_METRIC` and stayed under 0x63, derives the packed request byte `REQUEST_BITS` from the flag `loc_3d`, and hands off to the request walker `armRequestedSoundSlot`.

`tickActiveSoundSlot` [code] is the per-frame tick of the active slot; it was not exercised in the capture, so this reading is code-level. It sets `MODE_DISPATCH_SEL` to 0x06, and while the low five bits of `FRAME_COUNTER` are clear it expires the countdown `PASS_COUNTER` — on reaching zero it loads `GAME_MODE` with 0x14 and returns. Otherwise it clamps the active slot's value `SLOT_VALUE`,slot through `foldStepIntoFraction`, mapping the result to 0x1a on a negative reading, to 0x00 when 0x1b or above, and passing smaller values through. It gates on bits 3-4 of `INPUT_EDGE_FLAGS` (clearing them along with bit 7), and when that gate is set it steps the slot cursor `ACTIVE_SLOT` and the counter `REARM_COUNTER`: when the counter goes negative it re-arms — refilling through `loc_ddf7` if the channel's `SLOT_METRIC` entry is under 4 and delegating to `armRequestedSoundSlot` — otherwise it clears the retired slot at `SLOT_VALUE`,slot-1.

## The EAROM high-score store

Persistent settings and high scores live in a small serial NVRAM (an ER-2055-class EAROM) reached through the $6000 hardware block: a data window at `EAROM_DATA` (indexed by a cursor), a control/strobe port at `MATHBOX_STATUS`, and a read-back port at `EAROM_READ`. Nothing touches that hardware directly on demand; instead callers post a request into three zero-page flag cells and let a single step-driver drain it one entry at a time.

### Posting a request

The request is held in three cells. `EAROM_REGION_PENDING` carries the region-pending bits (up to three independent regions, one per low bit); `EAROM_REGION_DIR` carries the matching direction bits (a set bit means write that region out, a clear bit means read it back in); and `EAROM_BLANK_FLAG` is the blank flag — when nonzero, the write path zeros each source cell as it goes, erasing a region rather than saving it. A family of small front doors seats these cells:

`queueEaromRegionSave` ([seen]) is the general entry: it forces the direction/value pair (mask `0x04`, index `0x00`) and folds them through its shared tail, which stores the index byte into `EAROM_BLANK_FLAG` and ORs the mask into both `EAROM_REGION_PENDING` and `EAROM_REGION_DIR` — a plain, non-blanked write of the region carried by bit `0x04`. `queueEaromEraseAllRegions` ([code]) is the all-regions erase entry: it stamps `EAROM_BLANK_FLAG` to `0xff` and ORs `0x07` into both `EAROM_REGION_PENDING` and `EAROM_REGION_DIR`, requesting a blanked write of all three regions; its specific operands were not observed in the capture (the shared tail those stores live in ran with another entry's values). `loc_ddf3` ([code]) forces the index byte to `0xff` (blank mode) and then merges whatever mask it is handed, so it requests a blanked write of the caller's regions. `loc_ddf7` ([code]) supplies the fixed mask `0x03` to the zeroed-index (non-blank) merge, requesting a write of the two low regions; that particular mask is not reached in the capture. `loc_dde9` ([code]) is a trampoline that feeds mask `0x04` into `loc_ddf3`, i.e. a blanked write of the single region on bit `0x04`.

`armEaromReadback` ([seen]) stands apart from the OR-in family: it *sets* `EAROM_REGION_PENDING` to `0x07` and clears `EAROM_REGION_DIR` to `0x00`, then immediately drives the step-machine. With every direction bit clear this arms a read-back of all three regions — the path that reloads saved state at power-up. Its two direct writes to `EAROM_REGION_PENDING`/`EAROM_REGION_DIR` are observed, which is what grounds it.

### Draining the queue

`stepEaromTransfer` ([seen]) is the step-driver, reached often. When the mode byte `EAROM_MODE` is idle and `EAROM_REGION_PENDING` shows a pending region, it opens a fresh region: it clears the pass counter `EAROM_PASS_COUNTER`, the running accumulator `EAROM_CHECKSUM_ACC`, and the mask cell `EAROM_REGION_MASK`, then isolates a single requested region into `EAROM_REGION_MASK` by rotating `EAROM_REGION_PENDING` rightward through carry across eight positions until one set bit falls out, counting `x` down from `0x08`. The surviving pass count, doubled, indexes four packed ROM rows: `EAROM_REGION_START` gives the starting cursor stored into `EAROM_CURSOR`, `EAROM_REGION_LIMIT` the limit into `EAROM_LIMIT`, and `EAROM_REGION_PTR_LO`/`EAROM_REGION_PTR_HI` the low/high halves of a zero-page row pointer in `NVRAM_SCAN_PTR_LO`/`NVRAM_SCAN_PTR_HI` that walks the region's RAM copy. The direction is decided here: `EAROM_MODE` is armed to `0x80` when this region's bit is also set in `EAROM_REGION_DIR` (a write), otherwise `0x20` (a read), and the serviced bit is cleared from `EAROM_REGION_PENDING` by XOR with `EAROM_REGION_MASK`.

Each subsequent pass handles one entry and returns, resetting `MATHBOX_STATUS` to `0` on the way in and bailing once `EAROM_MODE` reaches `0`. On a write, the next RAM byte is fetched through the `NVRAM_SCAN_PTR_LO`/`NVRAM_SCAN_PTR_HI` pointer — or forced to zero first when the blank flag `EAROM_BLANK_FLAG` is set — folded into the running sum `EAROM_CHECKSUM_ACC`, and pushed to `EAROM_DATA+cursor`; when the cursor reaches the limit `EAROM_LIMIT`, the accumulated sum in `EAROM_CHECKSUM_ACC` is written out as a trailing checksum and the mode retires. On a read, the entry strobes the control port through its `0x08`/`0x09`/`0x08` handshake, takes the byte from `EAROM_READ`, and stores it through the row pointer while folding it into `EAROM_CHECKSUM_ACC`; at the limit the freshly read checksum byte is XOR-compared against `EAROM_CHECKSUM_ACC`, and a mismatch walks the row pointer back down zeroing every cell and records this region's bit into the result-status cell `PENDING_WORK_FLAGS`. The pass counter `EAROM_PASS_COUNTER` and cursor `EAROM_CURSOR` advance together, and the final control write to `MATHBOX_STATUS` (values `0x0e`, `0x0c`, or `0`) both clocks the hardware and signals whether to re-enter or stop. The result flags left in `PENDING_WORK_FLAGS` are what a caller reads back to learn which regions were serviced or failed their checksum.

### Routines assigned here that the code places elsewhere

Six routines grouped with this section are, by their own bodies and their [code] grounding, not part of the NVRAM store; they belong to the vector-display register/word emission path and are recorded here for completeness rather than folded into a high-score role the code does not support.

`initVectorDisplayRegisters` ([code]) performs a broad reset of the $60xx register block — zeroing `LED_FLIP_LATCH`, `MATHBOX_LD_R0_LO`, `POKEY1_AUDF1`, `POKEY2_AUDF1`, `EAROM_DATA`, and `MATHBOX_STATUS`, taking four throwaway settling reads, then raising `LED_FLIP_LATCH` to `0x08` — and marches a single set bit (rotating left with carry) across the thirty-two slots at `MATHBOX_LD_R0_LO` before emitting one framing word through `emitCoordinateVectorWord` with the pair `(0x34, 0xa6)`. `emitCoordinateVectorWord` and its siblings `loc_df4c`/`loc_df6c` (all [code]) write two-byte words into the display cursor at `DRAW_CURSOR_LO`, tagging the header nibble differently in each case. `emitFixedHeaderAndClearVectorSlots` ([code]) emits a framing word `(0x33, 0x0a)` then clears the four even slots of `POKEY1_AUDC1` and `POKEY2_AUDC1`; `emitVectorHeaderAndClearSlots` ([code]) does the same clear behind a caller-supplied header word. `emitPrimedHeaderAndClearVectorSlots` ([code]) is a fixed front onto `emitVectorHeaderAndClearSlots` with `(0x32, 0xb6)`, its value always nonzero so the self-seeding alternate is never taken. `loc_db6f` ([code]) emits a header from the halved slot count in `SPINNER_ACCUM` via `loc_df4c(0x68, SPINNER_ACCUM>>1)` and then runs `emitVectorHeaderAndClearSlots(0x33, 0x4e)`. `stepVectorPhaseAnimation` ([code]) advances the phase counter `loc_39` only while the frame gate `FRAME_COUNTER & 0x3f` is clear, indexes three parallel ROM rows (`ATTRACT_SND_SLOTA`, `ATTRACT_SND_SLOTB`, `ATTRACT_SND_VALUE`) by `loc_39 & 0x07` to seed two output cells — clearing `POKEY1_AUDC1+slotA`, then writing the ROM value into `POKEY1_AUDF1+slotB` and `0xa8` into `POKEY1_AUDC1+slotB` — and emits three words (`emitCoordinateVectorWord(0x34,0x56)`, `loc_df6c(0x01, FRAME_COUNTER & 0x7f)`, `emitCoordinateVectorWord(0x34,0xaa)`). None of these read, write, or strobe the EAROM ports or the request cells `EAROM_BLANK_FLAG`/`EAROM_REGION_PENDING`/`EAROM_REGION_DIR`/`PENDING_WORK_FLAGS`.

## State-reset, init and per-frame update chains

This subsystem is the machinery that wipes and re-seeds the game's working RAM at every state transition, and the small handful of per-frame housekeeping passes that age timers, drain a request queue, and fold score. The routines fall into four families: the reset orchestrator and its leaves, the fixed-constant seeders, the control-block rebuild chain, and the per-frame agers.

**The reset orchestrator.** loc_902b [code] is the master state-entry sweep: it runs six clears/seeds back to back — the twelve-byte clear clearActiveShots, the seven-byte clear clearShotTableAndStateFlags, the random-tag seeder seedSlotRandomTags, the eight-byte clear clearEightByteTableAndFlag, the single-byte clear clearByte50, and buildLevelLayout — then closes by arming RIM_COLOR_ANIM and ENEMY_ANIM_ACCUM to 0xff and clearing SPIKED_SEGMENT_COUNT. It is reached through the boot/init chain (its callers fall into it), though in the capture its own three tail writes held constant, so its role rests on the code.

## Utilities and shared tails

This subsystem gathers the small format-and-scratch helpers that other routines lean on, the fixed-array seeders, and the bare return leaves that terminate several branch chains.

**Binary-to-BCD conversion.** packBinaryToBcd [seen] turns the byte handed to it into packed binary-coded decimal by the classic double-dabble method: it walks eight passes, each pass shifting the top bit out of the source and doubling a BCD accumulator with that bit folded back in as a decimal-mode add-with-carry. The digit-bearing writes are observed inside the body — the packed BCD result lands in loc_29 (up to 0x99) and the SAME byte is written a second time to COORD_LIST_PTR_LO (also up to 0x99); both cells receive the identical result, they are not two different digits. (loc_29 is also written earlier in the body with the raw input byte before the conversion, so its stash value ranges lower.) This is the shared numeric-formatting primitive: whenever a raw count needs to be shown as decimal digits, it passes through here first.

**Clamped two-digit readout.** loc_af71 [code] is the front of that display path. It clamps the incoming byte to a maximum of 0x63 (99 decimal), then routes it into the pack-and-emit helper: the clamped value is converted to BCD via packBinaryToBcd, which seats it in loc_29, and that single zero-page byte is then spilled out as its two decimal digits. The clamp fixes the field at two digits, so the effect is a bounded two-digit on-screen readout. No role-defining own-cell write lives in loc_af71 itself; its work is the clamp and the hand-off.

**Byte-splitter for a fine value plus a coarse index.** partitionByteToFineCoarseSeed [seen] partitions one input byte three ways. It folds the input's top three bits, MSB first, into the low bits of a 0xff seed, producing a seed of the form 0xf8-with-those-three-bits, which it both stashes in loc_29 and carries out as the seed live-out. The input itself is left shifted up by three positions, giving a fine value carrying the low five bits in the high part of the byte. From the seed's complement it derives a small coarse index as ((seed ^ 0xff) + 0x0d) >> 1. It is reached, exclusively through reseedStateTables's three entry points, and its only memory write is the loc_29 scratch, marking it a pure compute helper: one byte in, a fine value / coarse index / seed triple out.

**Rebuild-request flag.** raiseRebuildRequestBits [seen] sets the two low request bits of the working flags cell PENDING_WORK_FLAGS, ORing 0x03 into it and returning the merged value; the resulting byte with bits 0 and 1 present is observed written at the body's store. This is the "both blocks need rebuilding" request — callers that detect a geometry-state change (including the mismatch path into requestRebuildIfSwitchesChanged) mark the pending work here, and the two bits are later consumed where the actual block copies are performed. It flows straight into the shared no-op return at switchesUnchangedReturn.

**Fixed-array seeders.** Two routines lay down constant seed values into paired tables. swapParallelTables [code] swaps two parallel eighteen-entry tables slot for slot: for each index from 0x11 down to 0, the entry in SWEEP_STAGE and the entry in loc_3bc trade places, so each table ends holding what its sibling held. seedTripleArrays [code] seeds two paired three-entry arrays with the fixed values 0, 4, and 0x0c — writing 0 to COLOR_CYCLE_0 and COLOR_RAM_9, 4 to COLOR_CYCLE_1 and COLOR_RAM_A, and 0x0c to COLOR_CYCLE_2 and COLOR_RAM_B. Neither routine's role-defining writes are exercised in the capture, so both are grounded [code] / not reached in the capture; their bodies are readable and unambiguous, they simply are not entered along the paths the capture covered.

**A constant-returning leaf that reads like a computation.** returnConstantTwo [code] appears to count bits: it reads OBJ_DEPTH, shifts it right four, and runs an iny/lsr/bne loop over the remaining bits. But the loop's result is discarded — a clc followed by adc #2 leaves the accumulator at 0+2, and a ldy #0 resets the second register to 0 — so the routine ALWAYS returns the constant pair (2, 0) regardless of what OBJ_DEPTH holds. It is a fixed-constant leaf, not a population-count of OBJ_DEPTH; the read of OBJ_DEPTH has no effect on the output.

**Bare return leaves.** The remaining routines are do-nothing terminators, each grounded [code] with no write to ground. noopDispatchStub is a no-op dispatch stub: a single bare return occupying a slot in a computed-dispatch set, so selecting it simply falls straight back to the caller. noRebuildRequestReturn is the nothing-to-rebuild leaf, tail-branched to when the rebuild-request bits in PENDING_WORK_FLAGS are clear. switchesUnchangedReturn is the shared return tail reached when the live geometry snapshot ((DSW2_SNAPSHOT & 0xf8) against the latch INPUT_SNAPSHOT_HI, and (DSW_DIFFICULTY & 3) against INPUT_SNAPSHOT_LO) already matches and no rebuild is needed. sharedReturnTail is the exposed return tail of the loc_af3f draw routine, branched to when both draw slots (SLOT_METRIC and loc_601) are empty and there is nothing to draw. Each is a genuine control-flow terminator whose only job is to unwind.

## The RESET / IRQ / main-loop spine

Every reachable routine now runs as idiomatic JavaScript — the frozen translated oracle serves none of the
live game. The last set decompiled was the strongly-connected spine that drives the whole machine: the
power-on RESET, the periodic interrupt handler, the main loop, and the computed-jump trampoline they turn
on. Because Tempest has no vblank NMI — a fixed ~246Hz timer interrupt is the only heartbeat — this spine is
where the clock-free model lives: the main loop is a generator whose wait for the interrupt counter is the
frame boundary, and the interrupt handler is fired directly per slot.

`bootMachineFromReset` [seen] is the power-on RESET entry (the reset vector target), written as a generator. It clears
the two mapped RAM windows (`GAME_MODE`-page work RAM and the `VEC_LIST_HEADER_LO` vector/display pages), seeds the
`POKEY1_AUDF1` control block, then splits on the self-test switch (`IN0_PORT` bit4): held, it spins the operator
diagnostic; released (normal boot), it seeds `VG_SCALE`, runs the device-init chain (EAROM + POKEY setup) and
delegates into the main loop, which never returns. The CPU stack seat, interrupt-enable and decimal-clear
the ROM performs here are vestigial in the clock-free engine (the stack pointer is retired and the engine
gates interrupts itself), so they carry no memory effect and are dropped. Reached at boot: its RAM-clear
and init writes are observed (e.g. pc 0xd98d, 0xd94d; ~6141 own writes).

`runMainFrameLoop` [seen] is the main loop, a generator. After a one-time board-init pass (`resetBothPokeyChips`) it free-runs
forever: each pass waits until the interrupt counter `IRQ_HEARTBEAT` reaches nine, clears it, and runs the three
per-update passes `loc_c7bd`, `seedFramePhaseAndTick` and `buildFrameVectors`. The wait is the frame boundary — the engine fires
nine interrupts per resume, so `IRQ_HEARTBEAT` climbs to nine and the loop advances once per game update (~26.5Hz,
below the 60Hz display; the game logic updates slower than the beam refreshes). Reached: the IRQ_HEARTBEAT clear
(pc 0xc7af, n=2431) and the one-time GAME_MODE seed (pc 0xc7a5) are observed.

`serviceHeartbeatInterrupt` [seen] is the ~246Hz interrupt handler — the heartbeat. Guarded against a corrupt stack or
counter (a path unreachable in the clock-free layer, where the stack pointer is retired), it kicks the
watchdog, advances the frame counter `SPINNER_ACCUM`/`SPINNER_POT_PREV` from the spinner, folds the coin/switch inputs
through `INPUT_CUR`-`INPUT_PREV`, drives the coin/LED latch `COIN_FLIP_LATCH`, picks a state code from the `IRQ_STATE_CODE`
table into `VG_MODE_FLAG`/`LED_FLIP_LATCH`, runs the per-tick updaters `tickHeartbeatCounters`/`stepSoundVoices`, ticks the software timer
cascades (`IRQ_HEARTBEAT`, `IRQ_SUBTIMER`, and the `TIMER1_LO`/`TIMER2_LO` chains), pulses the vector generator when the
AVG-done input is asserted, and latches the raw input port into `INPUT_PORT_LATCH`. It is dispatched raw (self-managing
its own entry/exit) rather than through the routine seam. Heavily reached — the heartbeat advance IRQ_HEARTBEAT
(pc 0xd7a5, n=43996) and its other own writes are observed.

`loc_b20d` [seen] is the computed-jump trampoline the main loop's housekeeping turns on: the pre-doubled
selector in `MODE_DISPATCH_SEL` picks one of twelve targets from the word table at 0xb218 and runs it. `buildFrameVectors` [seen]
is that housekeeping — per-frame vector bookkeeping that early-returns when the guard cells report the frame
settled, otherwise publishes the active pointer, runs the trampoline, and folds a block into a checksum via
a carry-chained subtract (decimal-aware when the CPU decimal flag is live — a mode gated on `DECIMAL_MODE_FLAG`, not
reached in normal play). `buildVectorItemList` [code] is one of the trampoline's targets: it builds a set of vector
items into display RAM via a dec-counted draw loop over the `DIAG_MASK_TABLE` table. loc_b20d is reached (its
dispatch observed, n=971) and buildFrameVectors producing (vector-RAM VEC_LIST_HEADER_LO/VEC_LIST_HEADER_HI at pc 0xb1fd/0xb203, checksum
loc_455 at pc 0xb1f2); buildVectorItemList is not reached in the capture (a display-path target), so it stands [code].

Deep-tail roles tagged `[code]` lift to `[seen]` once a capture drives the states that exercise them.

`seedFramePhaseAndTick` [seen] is a per-frame dispatcher. From the coin input `IN0_PORT`, the mode flag `STATUS_FLAGS`, and the
phase counters `DSW2_SNAPSHOT`/`PHASE_COUNTER`, it seeds the speed/mode cells `GAME_MODE`/`MODE_DISPATCH_SEL`/`loc_a2`, running the setup
step `advanceLevelCounter` on the appropriate phase; a common tail then advances the frame counter `FRAME_COUNTER` and fires
the periodic sub-steps — the EAROM step `stepEaromTransfer` on odd frames and the sound-register call `loc_ccfa` when
`SOUND_STEP_GATE` is live — carrying the slot index (X/Y) from one sub-step into the next. When `DECIMAL_MODE_FLAG` is set and
`loc_9f` exceeds 0x13 it leaves the CPU in decimal mode for the arithmetic that follows the dispatcher, and
finally it trims bit7 of `INPUT_EDGE_FLAGS`. Reached and producing: the frame-counter write FRAME_COUNTER (pc 0xc8e3, n=4862)
and the INPUT_EDGE_FLAGS trim (pc 0xc909) are observed.

`loc_db0f` [code] is the draw-handler dispatcher on the display-finalize path: it selects one of seven per-frame draw handlers — `beginEaromSequenceIfIdle`, `emitReadoutVectorList`, `emitFixedHeaderAndClearVectorSlots`, `stepVectorPhaseAnimation`, `emitPrimedHeaderAndClearVectorSlots`, `loc_db6f`, `initVectorDisplayRegisters` — by a byte offset held in `GAME_MODE` (handler index offset>>1); an out-of-range offset (>= 0x0e) is clamped to the second handler and the clamp persisted to `GAME_MODE`. It is called from `bootMachineFromReset`'s display-finalize block, which seats the display cursor at vector RAM 0x2000, derives `INPUT_CUR`/`INPUT_EDGE_FLAGS`/`SPINNER_ACCUM`/`SPINNER_POT_PREV` from an input port and a POKEY read, and pre-doubles the offset in `GAME_MODE` before entering. Not reached in the gameplay+attract write-tap capture: that finalize block did not execute in the captured window (its sibling `emitHeaderedBodyRecord` on the same path is likewise [code] not-reached), so it stands [code]; once a capture drives the display state that enters the block, it grounds derivatively on its dispatch cell `GAME_MODE` plus its handlers.

`emitReadoutVectorList` [code] is the per-frame vector-list emit, handler index 1 of `loc_db0f`: it advances the `loc_2e`/`loc_2f` frame counter, seeds the POKEY control cells, fires the digit and coordinate readout draws, walks the `SEG_SPREAD_A_LO_5` and `SEG_SPREAD_A_LO` emit tables, and hands the `SPINNER_ACCUM`-indexed colour pair to the shared colour-pair emitter.
