# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them; the frozen-oracle
remainder is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG
vector RAM (`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt
as the per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode
handler (attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Tempest drives each on-tube object through a tiny byte-coded program — a *motion script* — held in the ROM table at `loc_a0f7` (`$a0f7`). A driver (`loc_9b1e`) walks that table: it raises a continuation flag at `loc_10a` (`$010a`) to 1, then repeatedly fetches the script byte selected by the current cursor and hands it to a jump-table dispatch (`loc_9b98`), looping for as long as `loc_10a` stays nonzero. The dispatched byte is the opcode; the handlers in this section are the instruction set it decodes into. They all share three pieces of state: the rolling script cursor / instruction pointer `loc_10b` (`$010b`), the branch-condition flag `loc_10c` (`$010c`), and the walk flag `loc_10a`. Note that `loc_a0f8` (`$a0f8`) is simply `loc_a0f7 + 1`, so an opcode that indexes `loc_a0f8` by the cursor is reading the operand byte that sits immediately after the byte the cursor points at.

**Store opcodes — load a value into the object's slot.** The two workhorse opcodes both first advance the cursor and then deposit a value into the per-object cell `loc_298 + x` (`$0298,x`), where `x` is the object slot. `loc_9bd0` [seen] is the immediate form: it bumps `loc_10b` by one (wrapping to a byte) and copies the freshly-selected script byte `loc_a0f7[loc_10b]` straight into `$0298,x` — a constant baked into the script becomes the slot's new value. `loc_9bdd` [seen] is the indirect form: it likewise advances `loc_10b`, but treats the selected script byte as a zero-page address, reads the *live* variable at `loc_00 + ptr` (`$00 + ptr`), and stores that into `$0298,x` — so the slot tracks a running variable rather than a fixed literal. The write-tap confirms both: `loc_9bd0` was seen writing slots `$029b`–`$029e` (object slots x=3..6) and advancing its cursor 0x42→0x43; `loc_9bdd` was seen doing the same across `$029b`–`$029e` with a cursor step 0x4a→0x4b.

**Control-flow opcodes — conditional skip and jump.** The branch flag `loc_10c` gates the script's control flow, and two opcodes read it. `loc_9bee` [seen] is a conditional skip: if `loc_10c` is nonzero it does nothing, otherwise it advances the cursor `loc_10b` by two (wrapping to a byte), stepping past a two-byte operand — i.e. when the condition is clear it jumps *over* the following operand. `loc_9bfa` [seen] is a conditional goto: it always bumps `loc_10b` by one, then, only while `loc_10c` is zero, reloads the cursor from the table entry now under it (`loc_10b = loc_a0f7[loc_10b]`), i.e. it jumps to the operand-named target when the flag is clear and otherwise falls through past the operand. `loc_9c17` [seen] is the unconditional goto: it reloads the cursor from `loc_a0f8[loc_10b]` — the operand byte following the current position — making it the plain jump/loop-back. It is reached heavily (the reload write at the cursor pulsed across 0x06–0x4b), consistent with scripts that loop.

**The dwell/timer opcode.** `loc_9c0c` [seen] reuses the same slot family `loc_298 + x` as a countdown: it decrements `$0298,x` in place, and while that timer is still nonzero it runs the table-driven state step `loc_9c17` (advancing the cursor to the operand-named target) so the object stays in its current scripted state; once the timer reaches zero it instead bumps the shared cursor `loc_10b` by one, letting the script fall through to whatever opcode comes next. This is the "hold this pose for N ticks, then move on" primitive: on most ticks the timer is still running, so the hold branch is taken and the object stays put, and only occasionally does it reach zero and let the script advance. Note that `$0298,x` therefore serves double duty across the opcode set: the store opcodes treat it as the object's value cell, while this opcode treats it as a per-slot dwell counter, the interpretation set by which opcode the script invokes.

**Test opcodes — produce the branch flag.** Two opcodes *set* `loc_10c` for the conditional opcodes above to consume; both are tagged [code] because the captured window never exercised their stores (the flag was being produced elsewhere, at pc `0x9e2b`, during that capture), so their game role rests on the code rather than an observed write. `loc_9c21` [code] is a position test: it reads the slot's segment/lane from `loc_2b9 + x` (`$02b9,x`), looks up that segment's boundary in the per-lane array `loc_3ac + segment` (`$03ac`, where a zero entry is read as the maximum, `0xff`), and sets `loc_10c = 1` when the boundary is at or beyond the slot's depth along the tube `loc_2df + x` (`$02df,x`), else 0 — a test of whether the object has reached its lane's boundary given how far up the tube it has travelled. `loc_9c3b` [code] is a phase test over the accumulator pair `loc_147`/`loc_148` (`$0147`/`$0148`, the second being the phase value the driver advances by the first): it forms `((loc_147 << 2) + loc_148) & loc_148 & 0x80`, all byte-wrapped, then inverts bit 7, yielding `loc_10c = 0x00` when that high bit is set and `0x80` when it is clear — effectively gating on the sign/phase of the accumulator so the script can branch on an oscillation.

**Terminator.** `loc_9bca` [seen] is the halt opcode: it writes `loc_10a = 0`, clearing the driver's continuation flag so `loc_9b1e`'s walk stops after this object's script. It is a leaf reached very often — its single write to `$010a` fires on essentially every per-object script pass, the expected frequency for the byte that ends each one.

**A record-skip helper (adjacent, different dispatch).** `loc_96c7` [code] is register-only and reached through a *different* computed dispatch — the `$969d` table selected by `loc_9683` on `$015e`, not the script dispatch above. Its two entry points step the list cursor `y` past a packed record without reading it: entering at `loc_96c7` advances `y` by three (it bumps once and delegates to `loc_96c8`, which adds two), while entering at `loc_96c8` advances by two. With no own writes there is nothing for the write-tap to observe, hence [code]; it belongs here as the "skip this record" mover for the packed object/script list rather than as a motion-script opcode proper.

## Vector coordinate lists and the display cursor

Two pointers in zero page anchor everything the display machinery does: the pair at `loc_2c`/`loc_2d` chases a packed *coordinate list* held in ROM, and the pair at `loc_74`/`loc_75` is the moving *write cursor* into the vector display RAM (the sweep `loc_df5f` drives runs across `$22xx`–`$2fxx`, the region the AVG scans out). The first is a source of shape data; the second is where finished vector words are laid down for the beam. This section covers how a coordinate list is selected and walked, and how the cursor is advanced and fed.

### Selecting and walking a coordinate list

`loc_9aee` [seen] sets up the source pointer. Indexed by Y, it loads the low byte of a list address from the ROM table at `loc_9b02` into `loc_2c` and the high byte from the parallel table at `loc_9afd` into `loc_2d`, so the two tables together hold a set of little-endian list pointers selected by a single index. It stashes that selecting index Y into `loc_2b`, then reloads A from the `loc_29` scratch cell before returning. Grounding shows all three writes live — `loc_2c`←`0x41`, `loc_2d`←`0x07`, `loc_2b` moving `0x02`→`0x00` — i.e. a chosen list resolving to an address like `$0741`. With the pointer standing, the walkers read entries through `(loc_2c),y`.

`loc_96cb` [seen] steps the cursor forward by an inter-entry stride derived from the data itself. It reads the entry at the current offset (`ptr + y`) and its immediate predecessor (`ptr + y-1`), takes their difference, and records that difference as the step delta in `loc_29`. It then advances the running offset: the returned Y is `(y-1) + delta + 3` (that is, `y + delta + 2`), so the cursor jumps ahead by `delta + 2` entries from the original `y`, and the returned A carries the intermediate `(y-1)+delta+1`. Grounding caught the delta cell holding real values in the `0x1`–`0xf` range, confirming these are genuine variable-length steps between packed points, and confirming the routine is reached through the coordinate machinery rather than dead.

`loc_96ab` [seen] is a small family of readers over the same `(loc_2c)` list, sharing one `body`. `loc_96ab` enters with a counter-derived seed `((loc_2b - 1) & 0x0f) + 1` (a 1..16 wrap off the stashed list index), `loc_96b7` enters with the raw `loc_2b` value, and `loc_96c4` is the plain path that just reads the entry at `ptr + y` and returns it in A. The shared body stashes the incoming Y into `loc_29`, subtracts the entry sitting two positions back (`ptr + (y-2)`) from its seed, adds the stashed Y back in, and uses that computed value both as the new Y and as the offset for the final read (`ptr + a`), returning the entry it lands on. In effect the routine re-indexes the list by a value that folds in a two-entries-back delta — a relative hop within the coordinate stream. Its one memory write is the `loc_29` stash; grounding marks it reached with its A output consumed by the `$968f`/`$969d` computed-jump coordinate generator (`loc_9677`/`loc_9683`).

`loc_96db` [code] resolves a single list entry to an absolute coordinate: it reads the byte at `ptr + y` and adds the base value in `loc_160`, returning the 8-bit sum in A. It is a pure compute helper with no memory write of its own, and it is a computed-dispatch target reached through the `$968f` table via `loc_9677`; because a write-tap cannot observe a routine that only produces a register value, its reach and the identity of its consumer are unconfirmed — hence the honest [code] tag rather than [seen]. What the code *does* support is the arithmetic role: a list entry plus the `loc_160` base yields a display coordinate.

### The display cursor and its advancer

Every emitter below ends by moving the write cursor forward through one shared routine, `loc_df5f` [seen]. It treats `loc_74`/`loc_75` as a little-endian 16-bit pointer and advances it by the stride argument plus one: it computes `loc_74 + Y + 1`, stores the low result back into `loc_74`, and carries into `loc_75` on overflow past `0xff`. Callers therefore pass the offset of the last byte they wrote, and the "+1" lands the cursor on the first free byte. Grounding shows this as the busiest cell in the subsystem — the low byte `loc_74` pulses continuously and the high byte `loc_75` steps with it, the pointer sweeping the `$22xx`–`$2fxx` display-RAM band — so it is unambiguously the vector display cursor's advance step.

### Emitting words onto the cursor

`loc_df59` [seen] is the core two-byte emitter. Given a value pair `{A, X}` and an offset Y, it stores A at `(loc_74)+Y` and X at `(loc_74)+Y+1`, then advances the cursor by `Y+1` through `loc_df5f` (net stride `Y+2`). Grounding recorded 2585 write-rows of real vector data into `$2000`–`$2fff` (for example `$2202`←`0x3c`, `$2203`←`0x72`), the role-defining evidence that this pair-store is what actually populates the display list.

`loc_df53` [seen] writes the fixed header word `{0x40, 0x80}` at the cursor and steps past it: it stores `0x40` at `(loc_74)` and `0x80` at `(loc_74)+1`, then advances by 2. Grounding observed the `0x40`/`0x80` pair landing in the `$2xxx` stream. This header prefix is the same one the object emitter below writes inline.

`loc_df19` and `loc_df1f` [seen] emit a word chosen from the ROM word-table at `loc_31e4` by a 4-bit index. `loc_df19` builds its index from the low nibble of A with a special case: when carry is set and the nibble is zero the index is `0`, otherwise it is `nibble+1`. `loc_df1f` is the thinner wrapper — it forms the index as `(A & 0x0f) + 1` unconditionally and then shares `loc_df24`, the common tail that copies both bytes of `loc_31e4[index*2]` into `(loc_74)` and advances the cursor by 2. Grounding confirms the `loc_31e4` reads and the resulting stores into vector RAM (e.g. `$2172`←`0xb4`); `loc_df1f`'s own index arithmetic leaves no write, so it is tagged [seen] via its callers reaching the shared emit tail.

`loc_c772` [seen] emits a complete object-position vector — a header followed by an absolute X word and Y word. Its entry starts the write offset at 0 and hands off to `loc_c774`, which writes the `0x40`/`0x80` header first, then reads the object's low/high X bytes from the zero-page pair `loc_2`/`loc_3` (indexed by X) and its low/high Y bytes from `loc_00`/`loc_1`, emitting each coordinate as a two-byte word whose high byte is masked to five bits (`& 0x1f`). As it goes it caches the four raw bytes into `loc_6c`/`loc_6d` (X) and `loc_6a`/`loc_6b` (Y), preserving this point as the "previous point" that later stroke-relative drawing can measure from. Six bytes emitted in all, after which it advances the cursor by 6 via `loc_df5f`. Grounding marks it a heavily reached producer with exactly these X-from-`$02/$03`, Y-from-`$00/$01` sources.

`loc_aef8` [seen] is the text emitter: it copies three glyph words from a font table into the display list so a short string appears on screen. It seeds `loc_38` with `A+2` (the read index into the character buffer at `loc_606`) and `loc_39` with `0x02` (a down-counter for three passes), snapshots the cursor into a local base, and loops. Each pass fetches a character code `loc_606[loc_38]`, clamps any code `>= 0x1e` down to `0x1a`, doubles it to index the glyph word-table at `loc_31fa`, and copies that entry's two bytes into consecutive cursor slots; it then decrements both `loc_38` (walking the buffer backward) and `loc_39`, continuing while `loc_39` stays non-negative and breaking when it wraps below zero — three glyphs, six bytes. Finally it advances the cursor by the six bytes written through `loc_df5f`. Grounding observed roughly 549 writes per cell across `$2343`–`$2b71` with high byte `0xa8` (the vector draw opcode), the signature of real glyph geometry being laid into the display list.

## Draw-pointer setup and vector emission

Tempest paints its tube, its enemies, and its text onto an Atari color vector display whose analog vector generator reads a display list built in RAM from `loc_2000` up through `loc_2fff`. The routines in this subsystem fall into two cooperating groups: a set of *pointer-setup* producers that seat a working pointer over the region to be written, and a set of *emitters* that push vector-generator words through that pointer to grow the display list. Two distinct addressing disciplines run side by side — some emitters advance the two-byte pointer `loc_74`/`loc_75` itself, while others hold that pointer fixed and walk a separate one-byte cursor `loc_a9` that is added to it — and the setup routines are what establish either form before an emitter runs.

### Seating the working pointer

`loc_b2be` [seen] is the per-subsystem draw-pointer setup. Given a selector in A it forms a two-byte table stride `(A<<1)&0xff` and reads a 16-bit little-endian pointer out of one of two ROM tables: `loc_ce68` when the per-index flag byte at `loc_415 + A` is nonzero, or `loc_ce7a` when that flag is zero. The low byte lands in `loc_74` and the high byte in `loc_75`, and the routine then clears the cursor `loc_a9` so a following emitter starts writing at offset zero. Under MAME both writes were seen changing with real pointer values — `loc_74` pulsing across `0x00..0xf0` and `loc_75` across `0x20..0x2e` — confirming this seats a live vector-RAM address rather than a constant.

`loc_b2de` [seen] is the mirror-image of that routine for a *different* consumer pointer: same `(A<<1)&0xff` stride and same pair of ROM tables, but the table selection is inverted (nonzero flag at `loc_415 + A` picks `loc_ce7a`, zero picks `loc_ce68`) and the resulting pointer is published into `loc_3b`/`loc_3c` instead of `loc_74`/`loc_75`. It likewise clears `loc_a9`. Observed writes (`loc_3b` moving 0x4e→0x0c, `loc_3c` 0x25→0x24) confirm live pointer selection.

`loc_91b5` [seen] is a smaller, self-contained pointer loader used outside the `loc_74` family: it doubles the selector to `(A<<1)&0xff`, clears the paired flag byte `loc_29`, and copies a little-endian pointer from the in-page table `loc_91c6`(low)/`loc_91c7`(high) into the general-purpose indirect slot `loc_2a`/`loc_2b`. In the capture the loaded pointer resolved to `0x0540`.

`loc_b944` [code] swaps the two 16-bit pointers `loc_74`/`loc_75` and `loc_76`/`loc_77`, so whichever structure the shared cursors had been addressing is exchanged for the other. Its sole driver is the object-draw loop, which did not execute in the capture, so the swap itself was never exercised; the role reads from code and the translated header agrees.

`loc_b967` [code] chooses a pointer-table entry pair by the RAM flag `loc_415`: a zero flag returns `(A=loc_ce87, X=loc_ce86)` and a nonzero flag returns `(A=loc_ce6f, X=loc_ce6e)`, handing back the two bytes of a draw-struct pointer for the caller to store. The flag `loc_415` is itself exercised (toggling 0↔1), but this routine's body did not run in the capture.

### Advancing-pointer emitters

`loc_b56a` [seen] appends one four-byte vector-list record — three zero bytes followed by the caller's A — at the address in `loc_74`/`loc_75`, then advances that pointer by four, carrying from `loc_74` into `loc_75` on overflow. It is heavily exercised: the four-byte pattern was seen written across the whole `0x22f4..0x2b67` span of the vector buffer with the trailing byte supplied by the caller, and the low-byte advance wrapped often enough to carry into the high byte.

`loc_b332` [seen] emits a link record but first gates on a frame checkpoint: it compares the source byte `loc_cec4` against the checkpoint byte at `loc_2000`, and if they differ it latches the new value into `loc_2000` and returns carry set to signal "frame changed, restart the list." Otherwise it selects a record slot `x = 8` when `loc_415` is nonzero else `x = 2`, clears `loc_16e`, copies the two-byte word `loc_ce9e[x]`/`loc_ce9e[x+1]` through the pointer in `loc_74`/`loc_75`, and then reloads that pointer from `loc_ce68[x]`/`loc_ce68[x+1]` — relinking the cursor to the next record — and returns carry clear. Both the copy path (`loc_74` 0x0→0x2, `loc_75` 0x29→0x22) and the checkpoint-latch path were reached.

`loc_b896` [code] writes the display-list tail: it stores the 16-bit cursor `loc_139`(low, raw)/`loc_13a`(high, OR'd with `0x70`) into `loc_2ffc`/`loc_2ffd` at the very top of vector RAM and drops a `0xc0` terminator at `loc_2fff`, then steps the cursor down by 0x20 — subtracting from `loc_139`, borrowing into `loc_13a` on underflow, and masking the low byte to `0x7f`. This tail record and the descending 32-byte stride are readable from the code but were not exercised in the capture (no write appeared inside the body), so the tag stays [code].

### Cursor-walking geometry emitters

The remaining vector emitters keep `loc_74`/`loc_75` fixed as a base and walk the one-byte cursor `loc_a9`, so that a whole run of vertices lands contiguously without the base pointer moving.

`loc_c43c` [seen] is the producer that feeds them: it reads the current slot index `loc_37` and copies that object's column out of four parallel attribute tables into the working block — `loc_61 = loc_36a[x]`, `loc_62 = loc_35a[x]`, `loc_63 = loc_38a[x]`, `loc_64 = loc_37a[x]`. Those four tables (`loc_35a`/`loc_36a`/`loc_37a`/`loc_38a`) are the object coordinate arrays, seen filled with real RAM values, and `loc_61`..`loc_64` are the (x-pair, y-pair) working coordinates every geometry emitter below consumes.

`loc_c66d` [seen] produces a midpoint vertex between one tube slot and its wrap-around neighbour. It takes slot `loc_38` and its neighbour `(loc_38 + 1) & 0x0f` — the `& 0x0f` giving the sixteen-way wrap around the tube rim — and forms two round-up signed averages: the first coordinate pair from `loc_36a`/`loc_35a` of both slots into `loc_61`/`loc_62`, the second from `loc_38a`/`loc_37a` into `loc_63`/`loc_64` (each average halves while preserving the sign bit). It then appends four bytes through the base pointer `loc_74` at cursor `loc_a9` — low of the second pair, its high masked to `0x1f`, low of the first pair, its high masked to `0x1f` — advancing `loc_a9` by four and mirroring the same two midpoints into the scratch block `loc_6a`/`loc_6b` and `loc_6c`/`loc_6d`. The `0x1f` mask keeps only the coordinate magnitude, leaving the top three bits of each high byte as the vector-generator's opcode field. The mask value being 0x1f, not 0x7f, is confirmed against the code.

`loc_c73c` [seen] emits a pair of relative moves — the deltas that draw one segment of a shape. It computes `d1 = (loc_63:loc_64) - (loc_6c:loc_6d)` and `d2 = (loc_61:loc_62) - (loc_6a:loc_6b)` as 16-bit differences (current working coordinate minus mirrored previous), and stores each through the base pointer at cursor `loc_a9`: `d1`'s low byte raw then its high masked to five bits, then `d2`'s low raw and its high masked to five bits *and OR'd with `0xa0`* — the `0xa0` forcing a vector-generator draw opcode into the second high byte. The cursor advances four. Under MAME `loc_a9` was seen stepping 0x0c→0xfc and the `0xa0`-tagged high bytes landed in vector RAM as `0xa0`/`0xbf` across `0x220f..0x2403`, confirming these are drawn vectors.

`loc_bd3e` [seen] appends a normalized (exponent, mantissa) pair, used where a coordinate must be range-reduced through the hardware math box. For a small input (`loc_57 < 0x10`) it emits the trivial pair `(0x00, 0x71)`. Otherwise it forms the 16-bit difference `loc_57 - loc_5f` (with borrow into a negated `loc_5b`) into the coprocessor operand registers `loc_6095`/`loc_6096`, issues the computation by writing `0x18`→`loc_608c`, `loc_a0`→`loc_608e` and `loc_a0`→`loc_6094`, then spins while `loc_6040` bit 7 is set. It reads the results `loc_6060`→`loc_79` and `loc_6070`→`loc_7a`, sets mode `0x0f`→`loc_608c`, and normalizes: it shifts `loc_79` and the working value left in lockstep, counting shifts in x until a 1 rolls out of the working value's top bit; the shift count becomes the mantissa scale stored at `loc_78`, and `y = (((a>>1) ^ 0x7f) + 1) & 0xff` becomes the exponent. It then writes the exponent and the mantissa-scale (OR'd with `0x70`) through `loc_74`/`loc_75` at offset `loc_a9`. Note that this routine reads `loc_a9` but does not advance it; the caller owns the cursor step, and its most durable output for the caller is the scale byte left in `loc_78`.

`loc_c6c7` [seen] is the enemy-slot emitter, driving the geometry routines above to build one display-list entry per enemy slot. It indexes the active slot `loc_38` and reads the slot's kind byte from `loc_3ac[x]`. For an inactive slot (kind byte zero) it lays down four blank marker pairs — `0x00`,`0x71` repeated — advancing `loc_a9` by eight, so the slot contributes nothing visible but keeps the list layout fixed. For an active slot it seats the scratch inputs (`loc_57 = loc_3ac[x]`, then `loc_56 = loc_435[x]`, `loc_58 = loc_445[x]`), runs the depth clamp `loc_c453`, the math-box transform `loc_c098`, and the delta emitter `loc_c73c` to draw the shape, then dispatches on a kind bit: when `loc_39a[loc_38] & 0x40` is set it invokes `loc_bd3e` (computing `loc_78` and a provisional pair at the cursor) and then overwrites those two cursor bytes with a table word chosen by a randomized even offset `idx = (loc_60ca & 0x02) + 0x1c` — reading `loc_cec8[idx]`/`loc_cec9[idx]` — advancing `loc_a9` by two; otherwise it writes a fixed marker word `0x00`,`0x68` followed by `loc_3db2` and `loc_3db3`, advancing `loc_a9` by four. This is the routine that turns each live enemy in a lane into its perspective-scaled vector figure.

### Text emission into the glyph buffer

Two routines paint stroked text into the separate glyph region beginning at `loc_2f60`. `loc_a9fc` [seen] maps A's low nibble to a stroke word and appends it: with the carry dance it forms `y = 0` for a zero nibble with carry set, else `y = nibble + 1`, reads the word at `loc_31e4 + ((y<<1)&0xff)`, stores it at `loc_2f60 + x`, and steps the cursor x by two. Its writes into the `loc_2f60` buffer were seen taking real, varying table values. `loc_a9d7` [seen] drives that writer to emit a three-byte packed glyph string: it seeds a pass counter `loc_2a = 2` and walks the source pointer `loc_3b`/`loc_3c` backward one byte per pass, emitting each source byte as its high nibble then its low nibble through `loc_a9fc`, threading the carry between nibbles (carry is preserved across a zero nibble and forced clear before the low nibble of the final pass) so the zero-vs-nonzero nibble distinction survives into the stroke selection. The loop ends when the pass counter underflows past zero. This is the display path for on-screen text such as the score and messages.

## Enemy spawning and lane selection

This subsystem decides **where** a new enemy enters the tube and **which slot** holds it, then drives a parallel "timed object" table used for the shorter-lived things that also appear in lanes. Enemies live in a bank of parallel per-slot arrays indexed by a slot number `y`/`x`: `loc_2df` (depth down the tube), `loc_2b9` (target segment/column, 0..0xf), `loc_2cc` (the successor segment, always the target+1 wrapped), `loc_2a6`, `loc_28a` and `loc_291` (a coordinate/flag pair), and `loc_283` (a lane/flag byte). Two aggregate counters ride alongside: `loc_108` (active-enemy count) and the per-lane tally table `loc_142`.

**Allocating and seeding a slot — `loc_994d` [seen].** This is the allocator that turns a set of pre-staged scratch values into a live enemy. It first saves the caller's `y` into scratch `loc_36`, then scans the occupancy field `loc_2df` downward from the index in `loc_11c`, treating any non-zero `loc_2df+y` as taken; if the index walks below zero (the decremented `y` shows bit7) it gives up and returns `0x00` in A, meaning "no free slot." On a free slot it seeds the whole parallel row: the depth `loc_2df+y` is set from scratch `loc_29`; the target segment `loc_2b9+y` is set from scratch `loc_2a`, except that when that staged segment is `0x0f` **and** the global gate `loc_111` has bit7 set the segment is instead randomized to `loc_60ca & 0x0e` (an even POKEY-random column); the successor `loc_2cc+y` is written as `(segment+1) & 0x0f`; `loc_2a6+y` is zeroed; the coordinate pair `loc_28a+y`/`loc_291+y` is copied from scratch `loc_2c`/`loc_2d`; and the lane/flag byte `loc_283+y` is copied from scratch `loc_2b`. It then bumps the active count `loc_108` by one, extracts the lane as `loc_2b & 0x07`, restores `x` into `loc_36`, increments that lane's tally `loc_142+lane`, and returns `0x10` as the success flag. So the caller stages the enemy's segment, depth, coordinate and flags in the `loc_29`..`loc_2d` scratch bytes, and this routine commits them into the first free row while keeping the population counters honest.

**Choosing the entry lane — `loc_9abb` [seen].** This routine picks the lane a new enemy will use and builds the `loc_2c`/`loc_2d` pair that `loc_994d` later consumes. It starts from a POKEY-random lane index `y = loc_60ca & 0x03`, primes a four-try countdown in `loc_2b` (`0x04`), and stashes the caller's `x` in `loc_39`. Each pass decrements the countdown first: an underflow (bit7 set) returns `0x00`, meaning no candidate lane qualified. Otherwise it steps `y` back by one, wrapping to `0x03` on underflow, so it walks the four candidate entries of the `loc_149` table in a rotating order. The looked-up candidate `idx = loc_149+y` is remapped from `0x03` to `0x05`, and the lane qualifies only if the per-lane field `loc_13c+idx` is non-empty; an empty lane is skipped and the loop continues. On a qualifying lane it forms `a = (loc_149+y) | 0x40` and stores it into `loc_2c` (the low half of the seed coordinate, with bit6 marking it), then reads the list-hi table `loc_9afd` at index `2` into `loc_2d`, records `2` in `loc_2b`, and returns the value already sitting in `loc_29`. The effect is a bounded (four-attempt) random search for a usable entry lane that leaves the spawn coordinate half-staged for the allocator.

**Seeding per-slot random tags — `loc_9246` [seen].** For each active slot this stamps a random nibble and a packed identity tag, the raw material for per-enemy randomized behavior. It first clears the 64-byte tag table `loc_243` (indices `0x3f`..`0`), then walks slots from `loc_3ab - 1` down through zero. For each slot `x` it draws `rand = loc_60ca & 0x0f`, stores that nibble in `loc_203+x`, and forms `tag = (x << 4) | rand`, writing it to `loc_243+x` — but substituting `0x0f` when the packed tag would be zero, so slot 0 with a zero nibble still carries a non-zero tag. Both tables were observed filling with live values, confirming this runs over the real active-slot set.

**Picking a target column and steering toward it.** Once an enemy exists it needs a segment to aim for as it climbs, and `loc_a028` [code] makes that choice by "deepest column." It clears the running-best `loc_2d`, primes a 16-step counter in `loc_140` (`0x0f`), and scans the 16-entry column depth table `loc_3ac` starting from a POKEY2-random column `loc_60da & 0x0f`. Each column's depth is read, an **empty** column (depth 0) is treated as maximal (`0xff`), and the routine keeps the column with the greatest depth in `loc_2d` while recording its index in `loc_29`; the last column (`0x0f`) is skipped while the gate `loc_111` is non-zero. After all 16 columns it writes the winner as slot `x`'s target `loc_2b9+x`, sets the successor `loc_2cc+x = (winner+1) & 0x0f`, and clears bit7 of the coordinate/flag byte `loc_28a+x`. The tag is `[code]` because in the capture the write paths were reached but not exercised into varied state.

**The per-slot approach step — `loc_9fc4` [seen].** This advances one slot toward its target column and maintains the shared depth map that `loc_a028` reads. It raises the busy flag `loc_10c = 1`, reads the slot's current column `col = loc_2b9+x`, and if that column's map entry `loc_3ac+col` is empty seeds it to `0xf1`. It then keeps `loc_3ac+col` as the running **minimum** of the slot's own depth `loc_2df+x`: when the slot is shallower than the recorded column depth it overwrites `loc_3ac+col` with the slot depth and tags `loc_39a+col = 0x80` to mark a fresh minimum. Depth then gates three outcomes. A very shallow slot (`depth < 0x20`, i.e. near the rim) forces bit7 of `loc_28a+x`, clamps the depth to `0x20`, and returns. A mid-range slot (`0x20 <= depth < 0xf2`) returns with nothing further. A slot past the far limit (`depth >= 0xf2`) calls `loc_a028` to pick a new target column, reparks its depth at `0xf0`, and — only when `loc_3ab` is zero — rewrites its flags, setting the low two bits of `loc_28a+x` to `%01` and the low three bits of `loc_283+x` to `%010`, then drops the busy flag `loc_10c = 0`. So an enemy that overshoots the near end is recycled onto a freshly-chosen deep column with a reset behavior state.

**Turn/flip bookkeeping.** Two small helpers support lane-to-lane movement. `loc_9eab` [code] is a per-slot bit6 keeper gated by `loc_111`: it returns immediately if the gate is zero, otherwise, using the slot's flag `loc_283+x` and rim segment `loc_2b9+x`, it **clears** bit6 once the segment reaches `0x0e` (lane 14) when bit6 is set, and **sets** bit6 only while the segment is `0` (lane 0) when bit6 is clear. Neither write fired in the capture, so the tag is honest `[code]`. `loc_9ed7` [code] is a pure direction lookup with no writes of its own: it reads a direction byte from the ring table `loc_3ee` at index `y`, forcing bit7 on; when the caller's A has bit6 set it instead takes a half-turn, stepping the index back one within the 16-slot ring (`y = (y-1) & 0x0f`) and adding 8 to the looked-up value within that ring before the `| 0x80`. Its reachability was not established in the capture.

**The timed-object table.** A separate 8-slot bank holds shorter-lived lane objects, with parallel fields `loc_2fa` (lane), `loc_302` (type), `loc_30a` (position/liveness) and `loc_312` (a per-object counter), plus the pending/count byte `loc_116`. `loc_a3d4` [code] is a thin front door that stores A into the type scratch `loc_2c` and falls straight into the inserter; its only own write was a constant in the capture, hence `[code]`. `loc_a3d6` [seen] performs the insertion: it saves `x`/`y` into `loc_35`/`loc_36`, zeroes the "oldest" trackers `loc_2a`/`loc_2b`, then scans slots `7`..`0` looking for a free entry (`loc_30a+i == 0`, taken immediately), while simultaneously remembering the slot holding the largest counter `loc_312+i` in `loc_2a`/`loc_2b`. If no slot is free it evicts that highest-counter (oldest) slot and decrements the live count `loc_116` by one. It then fills the chosen slot — counter `loc_312 := 0`, type `loc_302 := loc_2c`, position `loc_30a := loc_29`, lane `loc_2fa := loc_2d` — and bumps `loc_116` back up. `loc_a416` [seen] ages the table: if the pending flag `loc_116` is zero it does nothing, otherwise it clears the flag and, for each live slot (`loc_30a+i != 0`), advances the counter `loc_312+i` by the per-type step `loc_a44e[type]`; a slot whose counter reaches its per-type limit `loc_a448[type]` is freed (`loc_30a+i := 0`), while any slot still short of its limit re-raises `loc_116` so the next pass keeps advancing it.

## Enemy motion and the pursuit AI

An enemy walking the tube has to answer two questions every frame: *which way around the rim is the player, and how do I move to get there*. This subsystem holds both halves — a small pack of rotational-geometry primitives that turn a pair of segment numbers into a signed "which side" answer, and a set of integrators that push a slot's coordinates along under velocity.

### The rotational-distance primitive

Everything that reasons about the rim rests on `loc_a7a6` [seen]. It computes the signed difference `A - Y` between two segment numbers and stashes it at `$2a`. When flag `$0111` has its high bit set it hands back the full signed byte; otherwise it masks to the low four bits and sign-extends bit 3 (`a &= 0x0f; if (a & 0x08) a |= 0xf8`), so on a 16-lane closed tube the result is the *shortest* signed arc from one segment to the other rather than the raw numeric gap. The write-tap confirms two stores at `$2a` — first the Y operand (a transient the subtract consumes), then the raw signed difference `A − Y`; the masked/sign-extended shortest-arc value lives only in the returned A and is never written to `$2a`, so a consumer reading `$2a` back sees the raw gap, not the masked arc. This is a live helper, not dead geometry.

Two consumers turn that arc into a decision. `loc_9d67` [code] reads slot x's target segment `$02b9,x` and the shared reference segment `$0200`, takes their signed distance through `loc_a7a6`, and then records the answer as a single bit: if the distance is negative it clears bit 6 of the slot's flag byte `$0283,x` (`&= 0xbf`), otherwise it sets it (`|= 0x40`). Bit 6 of `$0283,x` is thus the enemy's "the thing I'm chasing is on *this* side" flag — the code supports that mechanism cleanly, though its store never fired in this capture so the tag stays [code]. Its sibling `loc_9c4f` [code] is the blunt counterpart: it simply toggles that same bit 6 of `$0283,x` in place (`^= 0x40`) and returns the new value, i.e. it reverses the enemy's chosen travel direction without consulting geometry.

### Auto-aim / demo pursuit

`loc_97c5` [seen] is the closest thing here to an actual pursuit brain, and it is grounded. It walks the per-slot depth table `$02df` from index `$011c` down to zero looking for the smallest *nonzero* entry — the nearest live object down a lane — keeping that minimum in `$29` and its slot index in `$2a`. If nothing qualified (index still has its high bit set) it returns the last value it saw. Otherwise it feeds that slot's segment `$02b9[idx]` and the reference segment `$0200` to `loc_a7a6` and converts the sign of the arc into a discrete turn code: `0x00` when already aligned, `0x09` when the target is negative-side, `0xf7` (i.e. `-9`) otherwise. Its caller `loc_9749` reads that code back as a spinner delta, so this is the routine that swings the Blaster (or the demo player) one notch toward whichever lane holds the nearest enemy.

### Velocity integration — moving the slot

Enemy position is a fixed-point integration over three parallel axes. `loc_a6a9` [code] does the per-frame advance for slot x: for each axis it adds the velocity-low byte into a position fraction and keeps the carry (`$0223+$02e3`, `$0203+$02c3`, `$0243+$0303`), then folds that carry plus the signed velocity-whole (`$0343`/`$0323`/`$0363`) into a whole coordinate. Each whole is clamped to the tube ring: a rising axis (velocity sign ≥ 0) that reaches `>= 0xf0` resets, a falling axis (`sign & 0x80`) that drops below `0x10` resets. Axis 1's whole lands in `$0263,x`, axis 2's in `$02a3,x`, and axis 0's is written last into `$0283,x` — the very cell the direction bit lives in — but is forced to `0` if *any* of the three axes overflowed its ring bound. The routine's stores never fired in this capture, hence [code], but the arithmetic is unambiguous.

Velocities themselves are bled toward rest by `loc_a721` [code] driving `loc_a75d` [code]. `loc_a75d` steps one signed 16-bit velocity (whole in the Y argument, low in A) by the fixed increment at `$a788` (= `0x20`): it *adds* the step when the whole is negative and *subtracts* it otherwise, always walking the value toward zero, and on a zero-crossing it snaps both halves to zero and increments the saturation counter `$29`. `loc_a721` seeds that counter to `0xfd`, then runs all three axes — `(low $02c3, whole $0323)`, `(low $02e3, whole $0343)`, `(low $0303, whole $0363)` — storing each stepped pair back. Because each saturation bumps `$29` by one, the counter only reaches `0` when all three axes have bottomed out, and in that case the slot's whole coordinate `$0283,x` is zeroed. This is the machinery that lets a shoved enemy coast to a stop. `loc_a721` runs inside `loc_a618`'s walk over live enemy slots.

The velocities are seeded with jitter by `loc_a69b` [code], a signed random step: it reads three random bits from POKEY 2's RANDOM register `$60da & 0x07` (magnitude 0..7) and negates them when the caller's incoming byte has bit 0 set, yielding a nudge in `[-7, +7]`. Its consumer `loc_a65b` uses that to fill the velocity/coordinate deltas `$0323`/`$0343`/`$0363` of a freshly spawned enemy — so an enemy enters the tube with a random push.

### The fractional position accumulator

A second, finer integrator drives the shared position cell `$0200`. `loc_adce` [code] folds a signed sub-step into a fractional accumulator: it computes `($50 << 3) + $51`, writes the sum back to `$51`, carries out both the fold-carry and the sign of `$50` (a negative step sign-extends to `0xff` as the high byte) into A, then clears the step cell `$50`. `loc_b0ab` [code] wraps that: it reads `$0200`, runs it through `loc_adce`, then clamps the result — anything `>= 0x80` (negative) floors to `0`, anything above the ceiling `$0127` is pinned to `$0127` — and writes the clamped value back to `$0200` as well as out through A and Y. The mechanism (a signed step integrated into a bounded position) is clear from the code, though `$0200` held steady across this capture so both stay [code].

### Projecting a slot to the screen

To draw a moving enemy the game turns its abstract lane/phase into an actual vector point. `loc_b634` [seen] builds that point for slot x: the slot's segment `$02b9,x` indexes the lane base-coordinate tables `$03ce`/`$03de` into `$56`/`$58`, then the low nibble of the slot's phase counter `$02cc,x` indexes the signed offset tables `$b68b`/`$b687`, which are added to the base with a `0x80`-biased signed-saturating add (overflow clamps toward the sign that overflowed) to give screen X in `$2e` and Y in `$30`; `$57` is copied through to `$2f`, and a style-byte pair `$bcdc`/`$bcec` selected by `$0112` lands in `$59`/`$5a`. The phase counter offset is what slides an enemy *between* two adjacent lanes as it flips.

`loc_b6fa` [code] is the interpolation weight behind that motion: it scales an input delta by the low three bits of the same phase counter `$02cc,x`, treated as a fraction. It stashes the input at `$29` and the fraction at `$2c`, then runs three rounds of shift-add — consuming the fraction LSB-first, conditionally adding the input, and applying a sign-preserving `>>1` each round (`(acc >> 1) | (acc & 0x80)`). The result is the input scaled by fraction/8, letting a flipping enemy be drawn part-way through its hop; its caller `loc_b69b` uses it only on the interpolation path, and it never ran in this capture, so [code].

`loc_b875` [code] rotates a three-entry array `$22..$24` down by one with wrap-around, mirroring each new entry into the paired array `$0809..$080b`. The code is a clean triad rotate against what appear to be high-nibble geometry tables, but no caller was found and it never executed in the capture, so its role in enemy motion is **unconfirmed** — named by shape only.

### Slot countdown / pacing

Two grounded routines pace when slots act. `loc_c9af` [seen] clears `$04`, then decrements the active slot's countdown `$48,x` (with `x = $3d`). When the pair `$48 | $49` reaches zero it hands off to `loc_c9f1` and returns. Otherwise, if the current slot's countdown has hit zero it stamps `$0001 = 0x0c` and `$0004 = 0x28`, then spins the selector `$3f` — toggling its low bit (gated on `$3e` being nonzero) until it lands on a slot whose countdown `$48,x` is still nonzero — and arms that slot from `$46,x`: it loads `$46,x + 1` and sets `$0002` to `0x1c` when that wrapped to zero else `0x02`, with `$0000 = 0x0a`. `loc_c9f1` [seen] is the pacer it defers to: it scans the zero-page window `$46,x` for `x = $3e` down to `0`, keeps the maximum into `$0126`, decrements that when nonzero, and finally sets the timer cell `$0000` to `0x14`, or to `0x10` when status byte `$05` is negative. These meter the cadence of active tube slots rather than their geometry.

`loc_c81b` [seen] is grounded at the write level but its game vocabulary is **unresolved** — I flag it rather than assert a pursuit role. From the two-bit gate `$4e & 0x60` and a `>= 2` test on counter `$06` it derives a step of 0..2, drains `$06` by that many, records the step in `$3e`, and clears `$4e`. When the gate is clear it may instead seed four intro cells (`$0001=0x10`, `$0004=0x20`, `$0000=0x0a`, `$0002=0x14`) and clear `$50`/`$0123`. When the step is nonzero it sets both top bits of status `$05` (`|= 0xc0`), zeros `$16`/`$18`/`$0000`, bumps a 16-bit tally at `$040c,x`/`$040d,x` (index 0 or 3 by the decremented step), and clamps `$0100 + step` to `0x63`. The mechanism is exact; what the tally and the step count *mean* in the game's terms is not settled from the code alone.

## The mathbox: projection and level tables

Tempest draws its tube in perspective, and the arithmetic that turns a lane's flat base coordinates into on-screen slot positions is handed to a hardware math coprocessor mapped into the $6040/$6080–$6096 register window. This section covers the routines that drive that coprocessor, the routines that prepare its coordinate operands, and the routines that unpack a level's shape tables from packed ROM and lay out the current tube's per-lane geometry.

### Driving the coprocessor — `loc_c098` `[seen]`

`loc_c098` is the projection primitive: it feeds one point through the coprocessor and folds the two results into a pair of 16-bit accumulators. It first forms a 16-bit depth/scale delta from the `loc_5b`/`loc_57`/`loc_5f` operand triple — the low byte is `loc_57 − loc_5f`, written to input register `$6095`, and the high byte is `(0 − loc_5b − borrow) & 0xff`, written to `$6096`; when that high byte comes out negative (bit 7 set) the whole delta is clamped up to a floor of `$6096=0x00`, `$6095=0x01`. It then takes the absolute value of the two point components: `|loc_58 − loc_60|` (call it dx) with its sign recorded in `loc_33` (`0xff` when `loc_58 < loc_60`, else `0x00`), and `|loc_56 − loc_5e|` (dy) with its sign in `loc_34`, stashing dy itself in `loc_32`. The dx magnitude is issued to the coprocessor through `$608e` and `$6094`. The routine then spins on the coprocessor's status port `$6040` while bit 7 (busy) is set, and once the result is ready reads the two output bytes `$6060` and `$6070` into `loc_63`/`loc_64`, re-issues dy (`loc_32`) to `$608e`/`$6094`, and folds the paired offset `loc_68`/`loc_69` into the `{loc_64:loc_63}` accumulator — subtracting when the dx sign `loc_33` is negative, adding otherwise, in both cases with signed-overflow saturation (an overflowing subtract pins to `0x8000`, the signed minimum; an overflowing add to `0x7fff`). It spins on `$6040` a second time, reads the next result into `loc_61`/`loc_62`, and folds `loc_66`/`loc_67` into the `{loc_62:loc_61}` accumulator under the dy sign `loc_34` with the same saturation. The net effect, in the tube's terms, is one projected point: `{loc_62:loc_61}` holds the projected X pair and `{loc_64:loc_63}` the projected Y pair. Its confirmed writes to the input/output registers and the spin on `$6040` bit 7 tag it `[seen]`.

### Resetting the coprocessor and accumulators — `loc_c1c3` `[seen]`

Before a projection run the work area is cleared by `loc_c1c3`. It zeroes the zero-page accumulator and work cells `loc_81`, `loc_91`, `loc_80`, `loc_78`, `loc_90`, `loc_88`, then zeroes the coprocessor input block `$6080`, `$6081`, `$6083`, `$6084`, `$6085`, `$6086`, `$6087`, `$6089`, `$608d`, `$608e`, `$608f`, `$6090` — every input register except `$608c`, which it instead loads with the control value `0x0f`. This is the coprocessor's per-frame arming: all operands cleared, one mode/control byte set. It is heavily exercised and `[seen]`, though because the target cells were already zero in the capture every observed transition is a constant (`0→0`, and `$608c 0xf→0xf`) — the clear is confirmed present, not confirmed to change a nonzero cell.

### Sixteen-lane projection sweep — `loc_c473` `[seen]`

`loc_c473` runs the projection primitive once per lane to build the on-screen slot-coordinate tables. It seeds the depth operand `loc_57` from the incoming A, the output cursor `loc_38` from X, clears the clamp tally `loc_59`, and sets the loop counter `loc_37` to `0x0f`. On each of the sixteen passes it reads that lane's base coordinates from `loc_3ce + loc_37` into `loc_56` and `loc_3de + loc_37` into `loc_58`, calls `loc_c098` to project them, then clamps each projected pair into the `[−4..+3]` window (a byte `< 0xfc` saturates to `0xfc` with sign `0x01`; a byte `>= 0x04` saturates to `0x03` with sign `0xff`; anything inside passes through unchanged). The projected-X pair `{loc_62:loc_61}` is clamped and written as value to `loc_31a + loc_38` and sign to `loc_32a + loc_38`; the projected-Y pair `{loc_64:loc_63}` is clamped into `loc_33a + loc_38` and `loc_34a + loc_38`. Every clamp that actually fired increments `loc_59`. The output cursor `loc_38` and the loop counter `loc_37` both count down, the loop ending when `loc_37` goes negative, and the routine returns the total clamp count in `loc_59`. With 622 fills observed across the tables it is `[seen]`.

### Preparing the projection operands — `loc_c453` `[seen]`

`loc_c453` conditions the same depth operand triple the coprocessor consumes. It does nothing if the guard `loc_5b` is nonzero; otherwise, if `loc_57 − loc_5f` is already `0x0c` or more it leaves `loc_57` alone, and only when that gap is small does it snap `loc_57` up to `loc_5f + 0x0f`, capped at a ceiling of `0xf0`. In effect it pulls a lagging coordinate up toward its reference without overshooting a limit. The write to `loc_57` (observed jumping e.g. `0x14→0xe7`) and `loc_57`'s independent pulsing across the capture tag it `[seen]`.

### Nibble table pack/unpack — `loc_c196` `[seen]` and `loc_c2e8` `[seen]`

`loc_c196` unpacks the current level's shape/colour nibble tables from packed ROM. It takes the level selector `loc_9f & 0x70`, clamps it to at most `0x5f`, and forms an index `x = (selector >> 1) | 0x07`. Walking `y` from 7 down to 0 it reads the packed ROM byte at `loc_c1fd + x` and splits it: the low nibble goes to both `loc_19 + y` and its display mirror `loc_800 + y`, the high nibble to both `loc_21 + y` and its mirror `loc_808 + y`, decrementing `x` each step. One pass fills all four tables with the level's per-segment values (the `loc_800`/`loc_808` copies being the colour-RAM mirrors). It is `[seen]`.

`loc_c2e8` is the inverse packing helper. Given an input byte it substitutes a masked hardware value `loc_60ca & 0x5f` whenever the input is `0x62` or larger (a random/timer fallback for out-of-range values), then splits the byte into a quotient `x = value >> 4` and remainder `y = value & 0x0f`, looks the remainder up in the ROM table at `loc_bc7c + remainder`, stores that table entry to `loc_112`, and returns the value repacked as `(entry << 4) | 0x0f` in A with the quotient in X and remainder in Y. The observed write to `loc_112` tags it `[seen]`.

### Building the tube's lane geometry — `loc_c235` `[seen]`

`loc_c235` lays out the whole current tube once per level setup. It first packs a seed: it reads the byte at `loc_46 + loc_3d` (a per-slot selector), runs it through `loc_c2e8`, keeps the returned packed value as the neighbour-walk seed, and takes the stored entry `loc_112` as a table index `y`. From `y` it derives the span cells — `loc_5f` and `loc_5d` both get the negation `(−ROM[loc_bc8c + y]) & 0xff`, `loc_a0` gets `0x10 −` that negation, the guard `loc_5b` is set to `0xff`, `loc_60` is loaded from `ROM[loc_bc9c + y]`, and `loc_111` from `ROM[loc_bccc + y]`. The offset pair is then folded one of two ways: when the mode cell `loc_2` equals `0x1e` it copies `loc_68`/`loc_69` straight from `ROM[loc_bcac + y]`/`ROM[loc_bcbc + y]`; otherwise it forms the signed 16-bit difference `{bcbc:bcac} − {loc_69:loc_68}`, shifts it right four times keeping the low byte, and stores that in the level-scale cell `loc_121`. It clears the running accumulators `loc_66`, `loc_67`, `loc_10f`, `loc_110` and sets `loc_113` to `0x2c`.

It then seeds six per-column arrays top-down, walking the neighbour index down from the seed: for `x` from `0x0f` to `0`, `loc_3ce + x` gets `ROM[loc_b97c + ny]`, `loc_3de + x` gets `ROM[loc_ba7c + ny]`, the projected-slot value/sign arrays `loc_31a + x` and `loc_33a + x` and the array at `loc_39a + x` are all cleared, `loc_3ee + x` gets `ROM[loc_bb7c + ny]`, and `ny` decrements. Finally it fills two neighbour-midpoint arrays: for each `x`, `loc_435 + x` is the rounding average of `loc_3ce`'s next-neighbour (`(x+1) & 0x0f`, wrapping) and `loc_3ce + x`, and `loc_445 + x` the same average over the `loc_3de` table — where the average is `(a + b + 1)` rotated right one bit with the ninth (carry) bit rotated back into bit 7. These `loc_3ce`/`loc_3de` base coordinates are exactly what `loc_c473` later reads back and projects. Reached once per level setup and filling those tables with real varying values, it is `[seen]`.

### Arming a level's tables — `loc_b888` `[code]`

Its role is the level-table arm followed by pointing the vector tail at `0x047f`. It carries the `[code]` tag: it was not reached in the capture, its own two writes at `loc_139`/`loc_13a` never fired, and no direct caller was seen — it is most likely a computed-dispatch target, so its game role here is read from the code, not confirmed under MAME.

### Projection mode flag and scale — `loc_ca48` `[seen]`

`loc_ca48` sets a mode flag bit and its paired scale. It defaults to `a = 0x00`, `y = 0x10`, and only when both gates `loc_117` and `loc_3d` are nonzero does it select the alternate pair `a = 0x04`, `y = 0x08`. ## Sound, POKEY and the interrupt heartbeat

Sound in this machine is not driven by the game frame. It is driven by the free-running periodic interrupt, and the two POKEY chips (POKEY1 mapped at `loc_60c0`, POKEY2 at `loc_60d0`) are the machine's only voices. Everything in this subsystem is either the per-interrupt engine that repaints those chips, the code that queues a sound for it to play, or the housekeeping that resets and side-loads the same POKEY register file. A few routines bucketed here by their `loc_60xx`/`loc_60xx`-adjacent addresses turn out on reading to serve the pot/DIP and vector-math hardware rather than sound proper; those are called out honestly below.

### The heartbeat and the per-interrupt engine

Every interrupt, the handler runs two things back to back before it does anything else with the audio state: first `loc_cf24`, then `loc_cd0a`. That ordering is the whole rhythm section — a control-lane integrator followed by the voice stepper — and because the interrupt is periodic and untied to the display, both advance at a fixed rate regardless of how the game frame is doing.

`loc_cf24` **[seen]** is the control-lane integrator. It walks three parallel lanes indexed `x = 2,1,0`, each gated by a distinct low bit of the control byte `loc_8` (which the interrupt handler reloads from the `loc_c00` input latch each interrupt): lane 2 is gated by bit 0, lane 1 by bit 1, lane 0 by bit 2, extracted by shifting `loc_8` right one, two, or three times respectively and testing the carry. For an active lane it advances a per-lane position `loc_d + x` and keeps it inside `0..0x1f` — a decrement/increment path clamps to `0x1f` and wraps at the `0x20` boundary (the clamp at ROM 0xcf4a is the heavily-exercised one). A per-lane one-shot timer `loc_10 + x` (reloaded to `0x78`) gates when the lane is allowed to step, and a per-lane counter `loc_13 + x` is bumped on each accepted step. When a lane steps it folds a signed contribution into the running accumulator triple `loc_16` / `loc_17` / `loc_18`, and a tail section subtracts a threshold read from the table at `loc_cfd9` (indexed by the top bits of `loc_9`) to carry `loc_16` into `loc_18`, optionally nudging `loc_6`. Two final passes sweep the `loc_13` lane triple, and they differ: the first, over lanes at or above `0x10`, subtracts `0x10` (the guard compare leaves carry set, so its `adc #0xef` is `a + 0xf0`); the second, over any nonzero lane, subtracts `0x11` (`clc` then `adc #0xef`) — clamping the counts back down. What these three lanes *are* in game terms — a control/knob debounce, an attract-mode animator, a tone/period accumulator feeding sound — is not settled by the code alone; what is certain is that they are gated by the `loc_c00` input latch via `loc_8` and are integrated once per interrupt in lockstep with the voice stepper. (The routine defensively throws if state ever wraps far enough to fall through into the embedded data table past ROM 0xd004 — an unreachable-in-valid-state guard, not a game path.)

`loc_cd0a` **[seen]** is the voice stepper: one pass per interrupt over sixteen slots `x = 0x0f..0`, one slot per POKEY audio register. A slot is skipped when its channel-value byte `loc_c0 + x` is zero (idle) or when `x` equals the reservation marker `loc_bf` (the slot currently being loaded — see below). For a live slot it counts down the fast timer `loc_e0 + x`; while that is still non-zero the slot is left alone. When the fast timer hits zero it counts down the slow timer `loc_f0 + x`, and two things can happen:

- **Slow timer still running** — a single envelope step. Using the current frame byte `a = loc_c0 + x` it forms `y = (a << 1) & 0xff` and, choosing the high bank when `a`'s bit 7 is set and the low bank otherwise, reloads the fast timer `loc_e0 + x` from `loc_cccc + y` / `loc_cbcc + y` and reads a step delta from `loc_cccd + y` / `loc_cbcd + y`. That delta is added to the slot's level byte `loc_d0 + x`. For odd-numbered slots the update preserves the byte's high nibble — `loc_d0 + x = ((prev ^ new) & 0xf0) ^ new` keeps the old high nibble and takes only the new low nibble — which is exactly the shape you want for a POKEY AUDC register, where bits 7–5 are the distortion/control field to hold steady and the low nibble is the volume being animated (even slots, holding AUDF frequency, take the whole byte).
- **Both timers expired** — walk to the next frame. It advances the frame byte `loc_c0 + x` by two, forms `y` the same way, and from the same two four-byte-strided banks (`loc_cbcb`/`loc_cbcc`/`loc_cbce` low, `loc_cccb`/`loc_cccc`/`loc_ccce` high) loads a fresh level into `loc_d0 + x`, a fresh slow-timer reload into `loc_f0 + x`, and a fresh fast-timer value into `loc_e0 + x`. A zero fast-timer entry means "keep walking" — the loop steps the frame again until it lands on a non-zero frame or the level runs out, which is how a voice reaches the end of its envelope table.

After stepping, the slot's level byte `loc_d0 + x` is published to its POKEY register: slots `0..7` write POKEY1's audio file `loc_60c0 + x` (`loc_60c0..loc_60c7`), and slots `8..15` write POKEY2's audio file at `loc_60c8 + x`, which lands on `loc_60d0..loc_60d7`. So the sixteen slots map one-to-one onto the sixteen audio registers of the two chips — eight channels total, each an AUDF/AUDC pair — and the envelope tables at `loc_cbcb`/`loc_cccb` are the per-frame sound program the stepper replays.

### Queuing a sound

Sounds are requested by loading the channel tables that `loc_cd0a` consumes. The producer is `loc_ccc7` **[seen]**. It takes a sound id in `A`, saves the caller's `X`/`Y` into `loc_31`/`loc_32`, then walks the sixteen slots `x = 0x0f..0` while decrementing the id, reading one byte per slot from the sound's row in the table based at `loc_cb01`. Each non-zero table byte claims that slot: it stamps `loc_bf = x` (marking the slot reserved so an interrupting `loc_cd0a` skips it mid-load), writes the byte to the channel-value table `loc_c0 + x`, arms both timers `loc_e0 + x = 1` and `loc_f0 + x = 1` so the stepper picks the voice up on the very next interrupt, then releases the reservation with `loc_bf = 0xff`. That `loc_bf` set-then-clear is the re-entrancy guard between the main thread (which queues sounds) and the interrupt thread (which steps them). In the capture the marker is seen taking slot `0x9`/`0xa` and settling back to `0xff`, and the channel values stamp into `loc_c0`-block registers, consistent with a sound being loaded.

Two thin front doors feed `loc_ccc7`. `loc_ccc3` **[code]** is the enable gate: it tests bit 7 of the status byte `loc_5` and only registers the sound in `A` when that bit is set, otherwise it drops the request; the gate itself was not exercised in the capture, though its handler `loc_ccc7` is heavily seen. `loc_ccfa` **[code]** is a fixed-id trampoline: it always queues sound id `0xaf` (which in-game event that id denotes is not settled from the code) and was likewise not reached in the capture.

### POKEY reset, init and self-test

`loc_cd95` **[seen]** is the textbook dual-POKEY bring-up. It first silences the serial/keyboard control registers, writing `0` to SKCTL on both chips (`loc_60cf`, `loc_60df`, offset `0x0F`) and clearing the flag `loc_720`. It then runs a RANDOM-generator proof-of-life: it samples each chip's RANDOM register once (`loc_60ca` and `loc_60da`, offset `0x0A`) and polls up to five times (`x = 4..0`) for either reading to change; the first time one does, it latches the initial sample into `loc_720` and stops — confirming the POKEY LFSRs are actually running. Finally it performs the real init: SKCTL on both chips is set to `7` (the canonical POKEY init value), the eight audio registers of each chip are zeroed (`loc_60c0 + x` and `loc_60d0 + x` for `x = 7..0`) along with the zero-page shadows `loc_c0 + x`/`loc_d0 + x` for the first eight slots, and AUDCTL on both chips (`loc_60c8`, `loc_60d8`, offset `0x08` on write) is cleared to `0`. This is the routine that leaves both chips silent and correctly configured before the voice stepper starts painting them.

### The pot/selector side of the POKEY register file

The same offset `0x08` that is AUDCTL on write is ALLPOT on read, and offset `0x0B` is POTGO (a write there kicks a pot scan) — and two routines here work that read side rather than the audio side. `loc_dbe0` **[code]** stores its incoming argument to `loc_60db` (POKEY2 POTGO, offset `0x0B`), reads the low three bits of `loc_60d8` and bit 5 of `loc_60c8` (offset `0x08` read on each chip), writes only the three-bit value `(loc_60d8 & 0x07)` to the scratch byte `loc_37` and to `loc_60cb` (POKEY1 POTGO), and returns a full nibble `(loc_60d8 & 0x07) | ((loc_60c8 & 0x20) >> 2)` — so the returned nibble folds in the relocated bit 5 of `loc_60c8` that `loc_37`/`loc_60cb` do not carry. The shape — write POTGO, read ALLPOT, fold selected pot-status bits into a nibble — is a pot/line selector read, but the packing was never exercised with varying inputs in the capture (every observed write was a constant: `loc_60cb = 0`, `loc_37 = 0`, `loc_60db = 0xd0`), so the pot-selector role stays a code-supported reading only, hence **[code]**.

`loc_d6bb` **[seen]** is the option/DIP decoder, and it drives `loc_dbe0` as one of its final steps. It reads the two option-switch input ports `loc_e00` and `loc_d00`, and slices `loc_e00` into three ROM-table lookups: bits 5–3 index `loc_d6f7` into the config cell `loc_156`, bits 7–6 index `loc_d6ff` into `loc_158`, and bits 2–1 (`loc_e00 & 0x06`) index `loc_d6b3`/`loc_d6b4` into the pair `loc_ac`/`loc_ad`. It records `loc_9 = loc_d00 ^ 0x02`, then hands `loc_ad` to `loc_dbe0` and stores the returned nibble into `loc_16a` — so this routine folds a DIP-derived byte through the pot-selector packer and lands the current selector nibble in `loc_16a`. Its caller re-runs it and compares the decoded configuration against stored copies, confirming the DIP-decode role; it is exercised in the capture.

### A non-sound neighbor

`loc_dce6` **[code]** sits in this address neighborhood but is not part of the sound path — it works the custom hardware block at `loc_6040`–`loc_609x` (the vector/math region), not the POKEYs. It zeroes `loc_73`/`loc_414`/`loc_6090`, seeds two operands (`A` into `loc_608e`, `X` into `loc_608f`), sets the two count registers `loc_608c`/`loc_6094` to `0x10`, then runs a sixteen-step `dex` scan over the result block: it reads `loc_6040` each pass and, on the first slot whose byte is non-negative (bit 7 clear), returns that slot's low/high result pair from `loc_6060`/`loc_6070` in `A`/`Y`; if the counter runs past the end it exits with the run count. The role — seed operands, kick the hardware, poll the result file for the first ready slot — is consistent with driving the machine's math/vector coprocessor, but the routine was never reached in the capture, so the reading is code-only, hence **[code]**.

## The EAROM high-score store

Tempest keeps its persistent machine state — the high-score table and initials that survive a power-off, per the operator's non-volatile store — in an ER-2055 EAROM, and reaches it only through a serial IO block at `loc_6000`/`loc_6040`/`loc_6050`. Nothing in the game touches that chip directly; instead a small family of request setters posts *what* it wants moved into a three-byte queue at `loc_1c6`/`loc_1c7`/`loc_1c8`, and a single bit-serial state machine, `loc_de1b`, drains that queue one region at a time across many frames. The core state machine and its grounded entries are [seen] (`loc_de1b`, `loc_de11`, `loc_ddfb`), with three of the request entries left [code] (`loc_ddf1`, `loc_ddf7`, `loc_ddf3`) because only the mask-`0x04` path was ever driven in the capture.

### Queueing a transfer request

The request byte trio is the interface. `loc_1c7` carries the request-pending bits: each set bit names one of up to three RAM regions that still needs servicing. `loc_1c8` is the direction mask, read bit-for-bit against `loc_1c7` when a region is picked up — a set bit there makes that region a *write-out* (RAM→EAROM), a clear bit a *read-back* (EAROM→RAM). `loc_1c6` is the blank/erase-mode byte: when it is nonzero the transfer engine zeroes the source RAM cell as it writes each entry out, turning a write pass into an erase pass.

Four entry points feed this trio, all converging on the same shared tail. `loc_ddfb` [seen] begins the alt-entry chain: it supplies mask `0x04`, drops into the middle link that zeroes the index byte, and lands in the tail that stores `loc_1c6 = 0x00` and ORs `0x04` into both `loc_1c7` and `loc_1c8` — i.e. "queue region 4 for a write-out, no erase." That same chain is reached with other masks: `loc_ddf7` [code] hands it `0x03` (queue regions 1 and 2 for write-out, index zeroed), and `loc_ddf3` [code] jumps straight to the tail with the caller's live mask but forces the index byte to `0xff`, requesting the named regions be written in blank/erase mode. `loc_ddf1` [code] is the fixed maximal entry: it stamps `loc_1c6 = 0xff` and ORs the full `0x07` into both `loc_1c7` and `loc_1c8`, arming all three regions for an erasing write. Because each entry ORs rather than assigns, several requests can accumulate in the queue before the engine gets a turn. The [code] tags on `loc_ddf1` and `loc_ddf7` reflect that their erase-all (`0xff`/`0x07`) and mask-`0x03` paths are never actually exercised in the capture — at the shared merge points only `loc_ddfb`'s `0x00`/`0x04` values were ever observed, so only that path is grounded.

`loc_de11` [seen] is the odd one out: rather than ORing, it *assigns* `loc_1c7 = 0x07` and `loc_1c8 = 0x00`, then falls straight into `loc_de1b` to run the walk immediately. Setting the direction mask to all-zero while requesting all three regions makes this a full read-back initiator — the "load everything from EAROM" path, distinct from the ORing write-request family.

### The bit-serial transfer engine

`loc_de1b` [seen] is the state machine that actually clocks the EAROM, and it is by far the most heavily reached routine here (151 own-role writes). It is written to be re-entered from the top every service tick, doing a bounded slice of work and then either yielding or looping internally to the next region.

When it finds no transfer in progress and a request waiting (`loc_1ca == 0 && loc_1c7 != 0`), it opens a fresh region. It clears the per-region cursors `loc_1cb` (entry index) and `loc_1cf` (running byte-sum), then isolates a single walking bit from the pending mask: with an 8-count in `x`, it shifts a copy of `loc_1c7` LEFT one bit per pass, building the walking bit in `loc_1ce` and decrementing `x` until a set request bit falls out of the high end. `loc_1ce` then holds exactly one bit — the highest-numbered pending region — and `x` records its position. That bit chooses the direction: `y = (loc_1ce & loc_1c8) ? 0x80 : 0x20`, and `loc_1ca` is seeded with that value, so `0x80` starts a write pass and `0x20` a read pass. The region is retired from the queue with `loc_1c7 ^= loc_1ce`. Finally the position is doubled (`x = x << 1`) into a table index and the region's descriptor is fetched from four packed ROM tables: `loc_1cc` gets the starting port cursor from `loc_dddd[x]`, `loc_1cd` the end/length bound from `loc_ddde[x]`, and the row's RAM pointer is loaded low/high into `loc_bd`/`loc_be` from `loc_dde3[x]`/`loc_dde4[x]`. That pointer, plus `y`, is how the engine reads and writes the actual RAM cells being backed up or restored (`ind(y)` addresses `loc_be:loc_bd + y`).

The common block then resets the control port with `loc_6040 = 0`, reloads `loc_1ca`, and returns outright if it is clear (nothing active). Otherwise it rotates `loc_1ca` left one bit, and the carry it shifts out selects the phase for this entry — the routine threads a nested block ladder that implements the ER-2055's handshake. In the write phase it drives the data byte to `loc_6000 + x` and re-arms `loc_1ca = 0x40` for the follow-up. In the address/latch phase (`loc_1ca` high bit still set) it optionally zeroes the source cell first when `loc_1c6` is nonzero (the blank/erase case), reads the byte through the row pointer, and — once the port cursor `x` reaches the length bound `loc_1cd` — closes the region by clearing `loc_1ca` and emitting the accumulated sum `loc_1cf` as the final byte. The read phase is the EAROM read handshake proper: it pulses the control port `loc_6040` through `0x08 → 0x09 → 0x08` around a `0x08` strobe on `loc_6000 + x`, then latches the returned byte from the data-in port `loc_6050`. On the last entry of a read-back it XORs that byte against the running sum `loc_1cf`; a nonzero result is a checksum failure, and the engine responds by walking the row pointer back down (`ind(y)` from `loc_1cb` toward the low end) zeroing every cell and recording the fault by ORing `loc_1ce` into `loc_1c9` — so `loc_1c9` accumulates a per-region "this stored copy was corrupt, its RAM has been cleared" flag.

Every successfully handled entry is folded into the checksum and both cursors advance: `loc_1cf += a`, `loc_1cb++`, `loc_1cc++`. The tail writes the phase code `y` (`0x0e`, `0x0c`, or `0`) to the control port `loc_6040`; a nonzero `y` means the transfer is mid-flight and the routine yields, to be resumed on the next tick, while `y == 0` loops back to the outer top to pick up the next pending region bit. In this way one call can either take a single serial step of an in-progress region or, when a region completes, roll straight on to the next queued one until the whole `loc_1c7` mask is drained.

### What the code does and does not pin down

The code firmly establishes an EAROM/NVRAM transfer engine: a queue of region requests with per-region direction and erase flags, a table-driven descriptor fetch, a bit-serial read/write handshake over the `0x6000` port block, and a checksum with corruption recovery. That the transferred regions are specifically the high-score table and entered initials is the outside-in reading (the persisted store that survives power-off) rather than something the routines themselves name — the engine moves opaque RAM regions described only by the `loc_dddd`-family tables. The grounding is honest to that: the mechanism (serial EAROM transfer, request queueing, checksum) is [seen], while the exact game-facing payload of each region is not proven inside this subsystem's code.

## State-reset, init and per-frame update chains

This subsystem is the machine's plumbing for bringing RAM to a known baseline — at cold start, and again whenever a wave or mode is (re)entered — plus the once-per-frame housekeeping tick that ages in-flight objects and drives the level's countdown clock. Most of the routines here are small, single-purpose leaves that a higher-level init sequence (the chain rooted at `loc_902b`, and the reset paths `loc_9009`/`loc_90c4`) fires in order; a handful are the working heads that decide *which* baseline to lay down.

### Constant seeders (cold-start value tables)

Several leaves do nothing but stamp fixed constants into scattered work cells, each serving a different entry point. **`loc_921b`** `[seen]` seeds a five-cell cluster: `loc_200` ← `0x0e`, the zero-page cell `loc_51` ← `0xf0`, `loc_106` ← `0x00`, `loc_201` ← `0x0f`, and `loc_202` ← `0x10`. Because `loc_201` is the sign-flag control byte the per-frame tick later branches on and `loc_202` is the counter that same tick advances, this seed establishes the starting phase for the update chain; both `loc_200` and `loc_51` are cells that vary during play, so this is a genuine state seed rather than a no-op.

**`loc_b0e7`** `[seen]` is a straight-line startup seeder writing six work cells to constants — `loc_0` ← `0x0a`, `loc_2` ← `0x00`, `loc_4` ← `0xdf`, `loc_1` ← `0x12`, `loc_14e` ← `0x19`, `loc_14d` ← `0x18` — the last pair a stable `0x18/0x19` value stashed together. **`loc_c97b`** `[seen]` and **`loc_ca18`** `[seen]` are two more state-entry seeders that overlap on the same low zero-page scratch block `loc_0`..`loc_4` but with different constants, so which one runs selects a different starting configuration: `loc_c97b` lays down `loc_2`=`0x04`, `loc_1`=`0x00`, `loc_0`=`0x0a`, `loc_4`=`0x14`; `loc_ca18` first masks `loc_5` down to its low six bits (`loc_5 &= 0x3f`, clearing the top two flag bits) and then writes `loc_3e`=`0x00`, `loc_2`=`0x1a`, `loc_0`=`0x0a`, `loc_4`=`0xa0`, `loc_16b`=`0x01`, `loc_1`=`0x0a`. The shared `loc_0`=`0x0a` across all three is the one constant every entry agrees on.

**`loc_9234`** `[seen]`, reached from the reset path `loc_9009` and from `loc_90c4`, is the per-lane parameter loader: it copies one source byte into the header cell `loc_3ab` (`loc_3ab` ← `loc_15b`), then fills all sixteen entries of the per-lane array `loc_3ac`..`loc_3ac+0x0f` with a second source byte read once from `loc_15a`. `loc_3ab` is a real, draining state cell (it counts down elsewhere), so seeding it here is role-defining; the sixteen-wide array it fills is exactly the segment table the wave builder and the frame tick later read.

### Reset leaves (zero a table + clear its flags)

A family of leaves each blanks one array and clears the flag cells that ride with it, and the init chain at `loc_902b` calls them in sequence. **`loc_926f`** `[seen]` zeros the 7-byte block `loc_2df`..`loc_2df+6` top-down, then clears seven scattered flags `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146`. The block it clears, `loc_2df`, is the same object/shot depth table the per-frame tick ages, and the pair `loc_108`/`loc_109` reappear as the running total the tick accumulates — so this leaf zeroes both the table and its bookkeeping. **`loc_928f`** `[seen]` zeros the 12-byte block `loc_2d3`..`loc_2d3+0x0b` and clears the two flags `loc_135` and the zero-page cell `loc_a6`; it is reused well beyond init, being called from the frame tick `loc_a504` and from the per-frame stepper `loc_97f8`. **`loc_929f`** `[seen]` zeros the 8-byte table `loc_30a`..`loc_30a+7` and clears the trailing flag `loc_116` (a flag several update paths test before doing work). **`loc_92ad`** `[seen]` is the smallest: a single clear of the zero-page cell `loc_50` to `0`, run both from the init chain and from `loc_90c4`.

**`loc_a831`** `[seen]`, run inside the `loc_9009`/`loc_90c4` reset sequences, clears a pair of cells together — the header `loc_3aa` ← `0` and `loc_125` ← `0`; since `loc_125` is a latch that other code arms to `0xff`, clearing it here is a deliberate disarm. **`loc_ca62`** `[seen]` zeros a six-byte zero-page working block `loc_40`..`loc_45` (with 8-bit address wrap); its callers (`loc_ac3f`, `loc_c90c`) use it as an optional pre-clear before staging three-byte entries out of `loc_40`/`loc_41`/`loc_42`, so it is scratch-buffer hygiene rather than persistent state.

**`loc_a789`** `[code]` — not reached in the capture, so its role is legible from the code only, not confirmed by a write-tap — is the per-slot table reset: it zeros the 16-byte table `loc_283`..`loc_283+0x0f`, then re-seeds scalars `loc_10e`=`0x20`, `loc_10d`=`0x20`, `loc_1`=`0x04`, and `loc_68`=`loc_69`=`0`. It runs as the tail of a slot (re)init driven by `loc_ad22` (below), after that caller has already seeded the slot's paired cells.

**`loc_a7bd`** `[seen]` prepares an eight-entry table with a sentinel: it zeros `loc_3fe`..`loc_3fe+7`, then overwrites the last of those slots, `loc_405`, with `0xf0`, and arms the flag `loc_115` ← `0xff`. Its caller `loc_97f8` (the per-frame step of the descending spike/pulsar object) invokes it once the object crosses a depth threshold (`loc_202 >= loc_50` while `loc_115 == 0`), i.e. it re-primes the table and latches the flag exactly when the moving object passes its mark.

### Wave-state builder — `loc_a5cb`

**`loc_a5cb`** `[seen]` is the head that stands up wave state and decides whether the intro parameter block is needed. It writes `loc_0` ← `0x20`, sets bit 7 of `loc_106` (`loc_106 |= 0x80`), clears `loc_104`, `loc_107`, the zero-page cell `loc_5c` and `loc_123`, and sets `loc_105` ← `0x02`. It then walks all sixteen entries of the segment array `loc_3ac`..`loc_3ac+0x0f`, incrementing `loc_123` once for each nonzero entry — a tally of occupied/spiked segments (grounded: the write-tap shows `loc_123` climbing `0x0`→`0x6`, six live segments in that capture, pulsing across the 0..0xe range). If that tally is nonzero **and** the level cell `loc_9f` is below `0x07`, it loads an intro/param set — `loc_4`=`0x1e`, `loc_0`=`0x0a`, `loc_2`=`0x20`, and `loc_123`=`0x80` (repurposing the tally cell as a mode marker). Regardless of that branch it finishes by arming `loc_125` ← `0xff`. So the routine is: reset the wave's control cells, count how many lanes carry something, and conditionally arm an early-level intro.

### Slot-request drain — `loc_ad22`

**`loc_ad22`** `[seen]` consumes a packed request word two bits at a time to spawn the next requested slot. Each pass: if the word `loc_603` is exhausted (`== 0`) it writes the idle exit status `loc_0` ← `0x14` and stops. Otherwise it takes the low two bits as a slot index minus one (`loc_3d` ← `(loc_603 & 0x03) - 1`) and shifts the word right twice to consume that field. It reads that slot's byte from the table `loc_600 + loc_3d`; a value of `0` or `>= 0x09` is out of range and the walk continues to the next field. A valid byte `n` (1..8) is scaled into the paired value `loc_602`: triple it (`n<<1` then `+ n`), invert the byte (`^ 0xff`), and subtract `0xe5` — all with 8-bit wrap — yielding for `n`=1..8 a small byte `0x17`..`0x02` in `loc_602`. This valid-slot branch was not reached in the capture (only the exhausted-exit and out-of-range paths ran), so `loc_602`'s value here is code-derived. It then drives the mode/scale selector `loc_ca48`, seeds `loc_605`=`0x60`, `loc_4e`=`0x00`, the zero-page cell `loc_50`=`0x00`, and `loc_604`=`0x02`, runs the per-slot table reset `loc_a789`, writes the armed exit status `loc_0` ← `0x24`, and returns. So `loc_ad22` is the queue that turns one entry of the request word into a fully seeded, armed slot.

### Per-frame update tick — `loc_a504`

**`loc_a504`** `[seen]` is the once-per-frame housekeeping tick, run at the tail of the dispatcher `loc_970b` every frame and again from `loc_9729` when the control byte is negative. It splits on the sign of `loc_201` (the very cell `loc_921b` seeded).

The **positive arm** (`loc_201 < 0x80`) first, when a gate is live (`(loc_455 | loc_11b) != 0`) and a limit is not yet reached (`loc_42 > 0x17`), bumps one timer cell of the zero-page block indexed by `loc_40` (`loc_00 + loc_40` incremented, with 8-bit address wrap). If `loc_106` is nonzero it stops there. Otherwise, when both `loc_3ab` and `loc_116` are clear, it scans the depth table `loc_2df` downward from index `loc_11c`, looking for any live entry that has already grown past the threshold (`v != 0 && v >= 0x11`); only if none has does it rebuild wave state via `loc_a5cb` and then blank the 12-byte block via `loc_928f`. Finally, a triple gate — `(loc_4d & 0x60) != 0`, `(loc_5 & 0x80) != 0`, and `(loc_9 & 0x43) == 0x40` — must all hold for it to rebuild wave state once more with `loc_a5cb` before returning.

The **negative arm** (`loc_201 >= 0x80`, the arm the capture exercised) first bails if any of `loc_135`, `loc_a6` or `loc_116` is set. It then ages every live object in the depth table `loc_2df`, walking downward from `loc_11c`: each nonzero entry is advanced by `+0x0f`, snapping to `0x00` once it reaches or passes `0xf0` — objects that reach the far ceiling expire. Next it consults the flag `loc_48 + loc_3d`: if that flag is not `0x01`, it advances the counter `loc_202` by `0x0f` and proceeds once the sum crosses `0xf0`; if the flag *is* `0x01`, it instead clears `loc_10f` and sets `loc_114` ← `0x01`, then steps the 16-bit countdown clock `loc_5b`/`loc_5f` down by `0x20` (subtract from the low byte `loc_5f`, borrow into the high byte `loc_5b`) and proceeds when the high byte reaches the marker `0xfa`. Unless the proceed condition holds it returns. When it does proceed, it writes `loc_00` ← `0x06`, blanks the 12-byte block again via `loc_928f`, and folds a running total into `loc_3ab`: `loc_3ab` ← `min(loc_108 + loc_109 + loc_3ab, 0x3f)` (an 8-bit sum clamped at a ceiling of `0x3f`). That total draws on the same `loc_108`/`loc_109` cells that `loc_926f` zeroed at init and on the `loc_3ab` header that `loc_9234` and `loc_a831` seed and clear — closing the loop between the reset leaves above and the per-frame accumulation here.

## Utilities and shared tails

This group collects the small, reusable arithmetic helpers, the table/seed
maintenance leaves, one geometry-rebuild request-and-latch chain, and the several
bare return points that other routines branch to. Because they are leaves and
shared tails, most carry a `[code]` tag — a bare `rts` writes nothing for the
write-tap to catch — while the two helpers that actually compute and store are
reached and grounded `[seen]`.

### Binary-to-BCD conversion

`loc_aaf5` `[seen]` is the machine's decimal-digit converter. It takes the byte
in A and runs the classic double-dabble: eight passes, each shifting the top bit
out of the source and doubling a BCD accumulator in decimal arithmetic so the
carried-out bit folds into the low digit (the helper `bcdDouble` doubles each
nibble with the incoming carry, adding the 6-correction whenever a nibble or the
whole byte overflows past 9). The packed-BCD result is stored to **both** `loc_29`
(0x0029) and `loc_2c` (0x002c) and returned in A. The write-tap confirms this is
heavily exercised: the store PCs inside the body fire against `$29` (range
0..0x63 in the capture) and `$2c` (0..0x99), exactly the two-digit BCD you would
expect. Its caller `loc_af77` runs the conversion and then, with A=0x29 and Y=1,
performs a one-byte block operation reading from `$29` — i.e. it converts a value
and immediately hands the freshly written low cell to a copy/format tail.

### Byte-splitting helper

`loc_93e0` `[seen]` decomposes a byte for the callers that need both a fine value
and a coarse index out of one input. Starting from a seed of 0xff, it folds the
input's top three bits (MSB first) into the seed's low bits across three shifts,
so the seed lands as `0xf8 | (top three bits of the input)`. That seed is stored
to `loc_29` (0x0029) and also ridden back in Y. Meanwhile A is left holding the
input shifted left three times (the low five bits promoted into the high end — the
"fine" value), and X is derived from the seed's complement as
`((seed ^ 0xff) + 0x0d) >> 1`, giving a small coarse index. It is reached 81
times in the capture, always from `loc_92c5`'s three call sites, and its output is
consumed by a `[seen]` caller, so it grounds as a genuinely-used compute helper
rather than dead code. (The one own-cell write is the `$29` scratch seed; the
three live-out registers are the real product.)

### Constant, seed, and table-maintenance leaves

`loc_b955` `[code]` is a deliberate proposer trap. It reads `loc_57` (0x0057),
shifts it right by four, and runs an iny/lsr/bne loop that looks like a bit-count
of `$57` — but the loop's result is thrown away: the trailing `clc/adc #2` starts
from zero so A always resolves to the constant 2, and `ldy #0` forces Y to 0. It
therefore **always** returns the pair (A=2, Y=0) irrespective of `$57`, touching
no memory. A blind reader would mis-name it "log2/popcount of `$57`"; the code
returns a constant. Its `[code]` tag is honest — there is no role-defining write
to ground.

`loc_b85f` `[code]` seeds a pair of parallel three-entry arrays to fixed values:
`loc_22`/`loc_809` ← 0x00, `loc_23`/`loc_80a` ← 0x04, and `loc_24`/`loc_80b` ←
0x0c (the second array living up at 0x0809-0x080b), then returns with A=0. No
role write is observed in the capture — neither the low-page nor the 0x08xx stores
fire across attract, coin, start, and play — so it is tagged `[code]`, accounted
"not exercised in this capture"; the body is plainly readable, so it is named by
its effect (a fixed 0/4/12 seed of the paired triples) rather than by a role the
trace can confirm.

`loc_92b2` `[code]` swaps two parallel eighteen-entry tables slot-for-slot: for
x from 0x11 down to 0, it exchanges `loc_3aa`[x] (0x03aa base) with `loc_3bc`[x]
(0x03bc base), so each slot ends up holding what its sibling held. It exists to
flip an "active" versus "shadow" copy of an 18-entry structure in one pass. The
tap shows zero own-cell writes — the two swap stores never fire in the capture and
the base cells appear only as constant 0 read at unrelated PCs — so the routine
was not reached; `[code]`, named by effect.

### Geometry-rebuild request and latch chain

Three of these leaves are the tail points of a small state-mismatch → request →
rebuild → re-latch mechanism that keeps a couple of built blocks in sync with the
current tube/geometry state.

`loc_ac36` `[seen]` is the request setter: it ORs 0x03 into `loc_1c9` (0x01c9),
raising the two pending-rebuild request bits (bits 0 and 1), stores the merged
value back, and returns it in A, then falls into the shared `rts` at
`loc_ac3e`. The tap catches its own write at the store PC — `$01c9` taking the
value 0x07 (both request bits present alongside whatever was already set). Its
callers are the mismatch detector `loc_ac20` and the rebuilder's front `loc_abac`.

`loc_ac20` is the detector that decides whether a rebuild is needed: it compares
the live geometry state — `$0a & 0xf8` against the latch `$071e`, and `$016a & 3`
against the latch `$071f` — and if **both** match it branches to the shared return
`loc_ac3e` `[code]` (nothing to do); on **any** mismatch it falls straight into
`loc_ac36` to raise the request bits. So `loc_ac3e` is precisely the "state
already matches the latch, no rebuild" exit — a lone `rts` with nothing to ground,
hence `[code]`.

`loc_ac07` `[code]` is the sibling "nothing pending" exit one level up: the
dispatcher `loc_aba2` runs the detector, then tests `$01c9 & 3`; when it is zero
it tail-branches to `loc_ac07` (no request outstanding → do nothing), and only
when a request bit is set does it proceed into `loc_abac`, which consumes the
bits — bit 0 copies the `$ac08,x` source block into `$0606,x`, bit 1 fills
`$0706,x` with 1 — re-latches the current `$0a & 0xf8 → $071e` and
`$016a & 3 → $071f`, and clears the two request bits. `loc_ac07` is a bare `rts`,
so `[code]`, no write to ground.

### Draw tail and no-op dispatch slot

`loc_af6e` `[code]` is the exposed `rts` tail of the counter-draw routine
`loc_af3f`. `loc_af3f` draws one slot's count value, but returns immediately at
`loc_af6e` when that slot's cell `$0600,x` is 0 (nothing to draw). One level up,
`loc_af26` tail-branches to the same `loc_af6e` when `loc_600` (0x0600) OR'd with
0x0601 is 0 — i.e. both draw slots empty — otherwise it draws slot 0 and falls
through to draw slot 1. Either way `loc_af6e` is the shared "nothing to render"
return; a lone `rts`, `[code]`.

`loc_9bcf` `[code]` is a do-nothing handler slot in a computed-dispatch table: a
single bare `rts` that returns immediately, letting the caller's own return unwind
as if the dispatched entry did nothing. Its role is readable — an intentionally
empty table entry — but it is unexercisable through the write-tap (no memory
write, and reach cannot be confirmed from writes alone), so it stays `[code]`.
