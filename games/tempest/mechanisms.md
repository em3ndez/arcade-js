# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (deeper callers and the rest of the dispatcher spine)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each active object carries a tiny byte-coded motion program, and this cluster of routines is the interpreter that runs it. The programs themselves live in a table addressed from `loc_a0f7` (0xa0f7), an instruction pointer selects the current byte, and a handful of shared cells carry interpreter state across the walk: `loc_10b` (0x010b) is the rolling script instruction pointer, `loc_10a` (0x010a) is the walk-continuation flag that keeps the interpreter looping, `loc_10c` (0x010c) is the branch flag that the conditional opcodes read, and `loc_298` (0x0298) is the per-object cell the script writes into and counts down. The driver `loc_9b1e` is what turns the crank: for every object slot `x` whose depth cell `loc_2df` (0x02df,x) is nonzero it arms `loc_10a`=1, restores that slot's saved instruction pointer from 0x0291,x into `loc_10b`, then repeatedly reads the script byte at `loc_a0f7`+`loc_10b` as an opcode, hands it to the RTS-trick jump table in `loc_9b98`, advances `loc_10b` by one, and keeps going while `loc_10a` stays nonzero — saving `loc_10b` back to 0x0291,x when the walk ends. The routines below are the opcodes that dispatch lands on; several of them consume additional operand bytes from the same `loc_a0f7` script region, and the interpreter reads them essentially every pass over the live object list.

### Terminating the per-object walk

`loc_9bca` [seen] is the opcode that stops the current object's walk: it writes `loc_10a`=0, which the driver's inner loop tests immediately after each dispatch, so once this fires the interpreter falls out of the loop and saves the instruction pointer for next pass. It is a leaf handler with that single write to `loc_10a`, and it is reached on a busy cadence — it is the normal way each object's per-pass script run comes to rest.

### Store opcodes — writing the per-object cell

Two opcodes copy a script value into the object's motion cell `loc_298` (0x0298,x). `loc_9bd0` [seen] is the immediate form: it advances the instruction pointer by one (`loc_10b` = (`loc_10b`+1)&0xff), then reads the script byte now under the pointer at `loc_a0f7`+`loc_10b` and stores it straight into `loc_298`+x. The observed slot writes land at 0x029b–0x029e (the +3..+6 object slots), an immediate literal being loaded into the object's parameter cell. `loc_9bdd` [seen] is the indirect form: it advances `loc_10b`, reads the script byte at `loc_a0f7`+`loc_10b`, but treats that byte as a zero-page address, and copies the live value it finds at `loc_00`+ptr into `loc_298`+x. So where `loc_9bd0` bakes a constant into the object cell, `loc_9bdd` snapshots a running variable into it — the same 0x029b–0x029e destinations, sourced from a pointer rather than a literal.

### Control-flow opcodes — goto, conditional goto, conditional skip

`loc_9c17` [seen] is the unconditional goto. It reads the operand byte through the odd-aligned view `loc_a0f8` (0xa0f8, i.e. `loc_a0f7`+1) indexed by the current `loc_10b`, and writes that byte back into `loc_10b` — reloading the instruction pointer to the operand target so the next fetch resumes there. It is reached heavily, the pointer pulsing across a range of low targets as scripts loop back on themselves.

`loc_9bfa` [seen] is the conditional goto. It first bumps `loc_10b` by one to sit on the operand, then checks the branch flag: if `loc_10c` is nonzero it simply returns and the operand is left to be consumed as the next opcode; only when `loc_10c` is zero does it reload `loc_10b` from `loc_a0f7`+`loc_10b`, taking the jump. `loc_9bee` [seen] is the matching conditional skip: if `loc_10c` is nonzero it does nothing, and only when `loc_10c` is zero does it advance `loc_10b` by two, stepping the interpreter past a two-byte operand. Both opcodes act only when the branch flag is *clear* (zero); a set flag makes the goto fall through and the skip a no-op.

`loc_9c0c` [seen] is the dwell/timer opcode, and it drives `loc_9c17` directly. It decrements the object's cell `loc_298` (0x0298,x); while that timer is still nonzero it runs `loc_9c17` to reload `loc_10b` from the `loc_a0f8` operand — holding the object on its current scripted state and looping — and only when the timer reaches zero does it instead bump `loc_10b` by one so the interpreter falls through to the following opcode. It is reached very heavily; through its delegation to `loc_9c17` the instruction pointer is reloaded on essentially every timed pass, which is how an object lingers in one motion phase for a set number of ticks before advancing.

### Test opcodes — setting the branch flag

Two opcodes produce the branch flag `loc_10c` that the conditional opcodes above consume. `loc_9c21` [code] tests the object against a per-segment boundary: it reads the object's segment/lane from `loc_2b9` (0x02b9,x), looks up that segment's boundary in `loc_3ac` (0x03ac+segment) — treating a zero table entry as the maximum 0xff — and sets `loc_10c` to 1 when the boundary is at or beyond the object's coordinate `loc_2df` (0x02df,x), else 0. In game terms this reads as a lane-limit check: the flag is true while the object is still within its segment's allowed reach. `loc_9c3b` [code] instead derives the flag from the phase accumulator pair `loc_147`/`loc_148` (0x0147/0x0148): it computes ((`loc_147`<<2)+`loc_148`) & `loc_148` & 0x80, keeps bit 7, and inverts it, storing 0x00 into `loc_10c` when that high bit is set and 0x80 when it is clear — a sign/phase probe of the accumulator that `loc_9b1e`'s tail advances by `loc_147` each pass. Both are tagged [code]: neither routine's store to `loc_10c` was observed in the captured window (the branch flag was produced from another site during that trace), so their exact game trigger is inferred from the arithmetic rather than confirmed by a live write.

### List-cursor skip helper

`loc_96c7` [code] sits apart from the opcode set: it is a register-only cursor advance reached through a separate computed-dispatch table (the 0x969d table off `loc_9683`), used to step over a packed list record without reading it. Its first entry advances the cursor `Y` by three — it does so by delegating to its second entry `loc_96c8` with `Y` already bumped by one, and `loc_96c8` adds two more — while entering at `loc_96c8` directly advances `Y` by two. It writes no memory of its own (nothing to observe, hence [code]); its whole effect is the new cursor position it hands back so the surrounding list walk lands on the next record.

## Vector coordinate lists and the display cursor

Everything Tempest draws on its vector monitor is assembled into a display list in RAM, and the write end of that list is a single little-endian 16-bit cursor held in the zero-page pair `loc_74`/`loc_75`. The whole family of emitters in this subsystem shares one advance primitive, `loc_df5f` [seen], to step that cursor: it computes `loc_74 + Y + 1`, stores the low byte back into `loc_74`, and on carry (`sum > 0xff`) increments the high byte `loc_75`. Because the argument is `Y + 1`, a caller that has just written `Y+1` bytes at offsets `0`..`Y` passes its final `Y` and the cursor lands exactly on the next free slot. This routine is exercised on essentially every emit; its stores are grounded as a live cursor sweeping through the vector display RAM in the `0x2000`–`0x2fff` region, the high byte cycling roughly across `0x22`..`0x2a` as the list fills.

The lowest-level producers all fetch the current cursor from `loc_74`/`loc_75`, plant one or two bytes, and hand `loc_df5f` the stride. `loc_df59` [seen] is the core two-byte emitter: it writes the pair `{A, X}` at cursor offsets `Y` and `Y+1` and advances by `Y+2` (it passes `next = Y+1` to `loc_df5f`, which adds one more). Its stores are grounded landing real vector data across `0x2000`–`0x2fff` with wide value ranges. `loc_df53` [seen] is a fixed-header shorthand over that same tail — it plants the constant word `{0x40, 0x80}` at the cursor and advances by two; the `0x40`/`0x80` bytes are observed adjacently in the emit stream. The nibble-indexed pair emitters draw their word from the ROM word table at `loc_31e4`: `loc_df19` [seen] takes the low nibble of `A`, chooses table index `0` only when carry is set and that nibble is zero and otherwise `nibble + 1`, doubles it to a byte offset, copies `loc_31e4[idx]` and `loc_31e4[idx+1]` into the list, and advances by two. `loc_df1f` [seen] is the thin index variant of the same body: it forms the index as `(A & 0x0f) + 1` unconditionally and shares the identical copy-and-advance tail (`loc_df24`), so it leaves no distinct write of its own — its `[seen]` standing rests on being reached into that shared emit, whose `loc_31e4` word stores into vector RAM are grounded.

Two higher-level producers build multi-word records through the same cursor. `loc_c772` [seen] emits an absolute-position vector for an object: entering with cursor offset zero (its alternate entry `loc_c774` resumes at a nonzero offset), it lays a `{0x40, 0x80}` header word, then an X coordinate word taken from the zero-page pair at `loc_2`/`loc_3` indexed by X, then a Y coordinate word from the pair at `loc_00`/`loc_1` indexed by X. Each coordinate's high byte is masked to five bits (`& 0x1f`) before it is written, while the low bytes go through unmasked; along the way it caches the raw four coordinate bytes into `loc_6a`–`loc_6d` (Y-low, Y-high, X-low, X-high) as a remembered "previous point," then advances the cursor past the six emitted bytes. It is heavily reached and grounded as a real position producer. `loc_aef8` [seen] renders a short run of text into the list: it points a source index at `loc_606 + (A + 2)` and copies three consecutive glyph words backward through that character buffer. For each of the three character codes it clamps any value `>= 0x1e` down to `0x1a`, doubles the (clamped) code to index the glyph word table at `loc_31fa`, and copies that table entry's two bytes into the list; after three words (six bytes) it advances the cursor by `loc_df5f`. Its writes are grounded flowing into the vector display RAM with the AVG draw opcode `0xa8` appearing as the words' high byte, confirming these are genuine on-screen glyph strokes.

The read side of the subsystem walks packed coordinate lists in ROM through a second zero-page indirect pointer, the pair `loc_2c`/`loc_2d`, with the selected list index parked in `loc_2b` and a scratch/holding cell in `loc_29`. `loc_9aee` [seen] chooses which list to walk: indexed by Y it loads the list's low pointer byte from the table at `loc_9b02` into `loc_2c` and the high byte from `loc_9afd` into `loc_2d`, records the chosen index Y in `loc_2b`, and reloads `A` from the holding cell `loc_29`; its three stores (`loc_2c`, `loc_2d`, `loc_2b`) are all grounded. `loc_9a9d` [code] is the fixed-list variant used to seed a specific list — it takes the low byte from the first table slot `loc_9b02[0]` and the high byte from the source cell `loc_15d`, forces the index `loc_2b` to zero, and likewise reloads `A` from `loc_29`; its lone captured write is constant, so its role rests on the code rather than an observed behavior.

With that pointer set up, the walkers step and resolve entries. `loc_96cb` [seen] reads the entry at the cursor offset Y and its predecessor at `Y-1` through `(loc_2c)`, stores their difference as a step delta in `loc_29`, and returns an advanced cursor: `A = Y + delta` and `Y = A + 2`, i.e. it skips ahead by the inter-entry step plus two. Its write of `loc_29` is grounded holding real inter-entry steps in the `1`..`0xf` range drawn from the list. `loc_96db` [code] resolves a single list entry to an absolute coordinate — it reads `(loc_2c)[Y]` and adds the base value in `loc_160`, returning the 8-bit sum in `A`; it is a pure compute helper with no memory write to observe, and because it is entered through a computed dispatch its reach cannot be pinned from the write trace, so it holds the code tag honestly. `loc_96ab` [seen] is a coordinate helper reached through the same computed vector-coordinate generator: it stashes the incoming cursor Y into the scratch `loc_29`, forms a starting value from the selected-index cell (`((loc_2b - 1) & 0x0f) + 1`), subtracts the list entry two positions back (`(loc_2c)[Y-2]`), adds the stashed Y, and finally re-indexes to return the entry `(loc_2c)[A]` in `A` along with that new index in `Y`. Its only own store is the `loc_29` scratch, so it is grounded as a reached compute helper whose coordinate output is consumed by the computed-jump generator that assembles the vector coordinates. (Its sibling entries in the same body — a raw-index variant and a plain `(loc_2c)[Y]` fetch — share this pointer without altering the walk described here.)

## Draw-pointer setup and vector emission

Tempest paints its screen by filling the AVG (Analog Vector Generator) display RAM at `loc_2000`–`loc_2fff` with a list of opcode words, and almost every routine in this subsystem writes through a shared 16-bit indirect cursor held in the zero-page pair `loc_74`/`loc_75` (low byte then high byte), advancing an offset in `loc_a9` as it goes. Setting that cursor up correctly is the first half of the job; emitting well-formed vector words through it is the second.

**Publishing a draw pointer.** `loc_b2be` [seen] takes a subsystem selector in the accumulator, doubles it into a two-byte stride (`(a<<1)&0xff`), and reads a 16-bit pointer out of one of two ROM pointer tables — `loc_ce68` when the per-index flag `loc_415`+idx is nonzero, otherwise `loc_ce7a` — depositing the low byte in `loc_74`, the high byte in `loc_75`, and clearing the status cell `loc_a9` so the next emitter starts its offset at zero. Both target cells were seen pulsing across the full pointer range as the machine cycled through subsystems, which grounds it as the live cursor loader. `loc_b2de` [seen] is the same selection against the same `loc_415` flag but publishes into the *other* cursor pair `loc_3b`/`loc_3c`, and it inverts the table choice (nonzero flag picks `loc_ce7a`, zero picks `loc_ce68`); it too clears `loc_a9`. `loc_91b5` [seen] serves the alternate working pointer `loc_2a`/`loc_2b`: it doubles its selector, clears the companion flag byte `loc_29`, and copies a little-endian pointer from the in-page ROM table at `loc_91c6`/`loc_91c7`. `loc_b967` [code] is a smaller variant that, keyed only on the global flag `loc_415`, returns a two-byte parameter pair — `(loc_ce87, loc_ce86)` when the flag is zero, `(loc_ce6f, loc_ce6e)` when set — for its caller to install as a draw-struct pointer; its own body was never reached in the capture, so the role rests on the code. `loc_b944` [code] swaps the whole `loc_74`/`loc_75` cursor with a second pointer `loc_76`/`loc_77`, letting the same emitters address a second structure without reloading; it likewise stayed unexercised. `loc_b84e` [code] is a computed dispatcher: the caller hands it a byte offset in the Y register, and it indexes a four-entry function table (`loc_b85f`, `loc_b875`, `loc_b888`, `loc_b896`) by `y>>1` and tail-returns the selected routine — the vector-list rebuild path among them.

**Draw-list linkage and frame-change detection.** `loc_b332` [seen] guards the list build against a mid-frame change: it compares a source byte `loc_cec4` against the checkpoint stored in the first vector-RAM cell `loc_2000`, and if they differ it latches the new value into `loc_2000` and returns carry set to tell its caller "frame moved, rebuild." When they match it instead does the linkage work — it selects a record slot (offset 8 when `loc_415` is nonzero, else 2), clears `loc_16e`, copies a two-byte word from `loc_ce9e`+slot through the current `loc_74` cursor, then reloads `loc_74`/`loc_75` from the paired entry in `loc_ce68`+slot so the cursor now points at the next list segment, returning carry clear. Both the copy and the pointer-reload writes were seen with changing values.

**Raw list appends.** `loc_b56a` [seen] is the smallest emitter: it writes the four bytes `0, 0, 0, A` at the `loc_74` cursor and then advances that pointer by four, carrying into `loc_75` on overflow. It is strongly exercised, sweeping the whole vector buffer with the fourth byte carrying the caller's opcode value. `loc_b896` [code] emits the vector-list *tail*: it stores the 16-bit cursor held in `loc_139`/`loc_13a` into fixed RAM slots — `loc_2ffc` gets the low byte raw, `loc_2ffd` gets the high byte OR'd with `0x70`, and `loc_2fff` gets the `0xc0` terminator — then steps the cursor down by `0x20` (masking the low byte to `0x7f` and borrowing `loc_13a` down by one when the subtraction underflows). It was not reached in this capture, so its role is read from the code.

**Text and packed-digit runs.** A family of routines turns zero-page bytes into glyph words. `loc_a9fc` [seen] maps the low nibble of A to a word index — a zero nibble with carry set indexes entry 0, otherwise `nibble+1` — reads the single byte at ROM font table `loc_31e4`+`2*index`, stores that one byte into the text vector buffer `loc_2f60` at the X cursor, and steps X by two (leaving the odd slot `loc_2f60`+x+1 for another writer); the real, varying font bytes it lands into `loc_2f60` ground it. `loc_a9d7` [seen] drives three source bytes through that writer: it seeds a pass counter `loc_2a`=2, and for each pass emits the current byte's high nibble then its low nibble via `loc_a9fc`, walking the glyph source pointer `loc_3b` backward one byte per pass, with a carry-chaining dance so only the final low nibble is fed a cleared carry (the string terminator). `loc_a97f` [seen] builds a seven-entry row of the vector list keyed by the Y selector: it stashes Y in `loc_2b`, forms a head byte (OR'd with `0x70`, and zeroed only when Y equals the marker index `loc_3d` while the top bit of `loc_5` is set), places it into `loc_2f60` via the base-index tables `loc_cdde`/`loc_cde0`, fills the remaining rows from a count in `loc_48`+Y (one short at the marker) choosing between glyphs `loc_3284` and `loc_3286`, and — unless it is in state `loc_00`==4 away from the marker, where it returns without emitting — seeds the glyph pointer `loc_3b` from `loc_a97d`+Y (with `loc_3c`=0) and hands off to `loc_a9d7`.

The nibble-run engine underneath the numeric displays is `loc_dfb1` [seen], reached extensively: given a source base A and a length Y, it walks `Y` zero-page bytes downward from index `A+Y-1` (tracking the running length in `loc_ae` and the source index in `loc_af`), emitting each byte's high nibble then its low nibble through `loc_df19`, and chains the carry so only the very last low nibble sees it cleared — the terminator marker for the run. Several thin callers feed it: `loc_af77` [code] first packs its argument to BCD via `loc_aaf5` and then emits that single byte `loc_29` as a nibble run; `loc_aa9e` [code] bumps the slot index, publishes it into `loc_61`, and emits that one byte; and `loc_b0c6` [code] first loads a table pointer into `loc_2a`/`loc_2b` (clearing `loc_29`) via `loc_91b5` and then emits the three-byte run `loc_29`/`loc_2a`/`loc_2b` as nibbles. These three do their work entirely through the helpers, so their own bodies show only constant writes in the capture and their roles rest on the code.

**Coordinate and object vertices.** `loc_c43c` [seen] is the attribute gatherer that feeds the vertex emitters: reading the slot index in `loc_37`, it copies that column of four parallel object tables — `loc_36a`/`loc_35a` and `loc_38a`/`loc_37a` — into the working block `loc_61`/`loc_62`/`loc_63`/`loc_64`. `loc_c66d` [seen] produces a tube-lane midpoint vertex: for slot `loc_38` it round-up-averages that slot's two coordinate pairs with those of its wrap-around neighbour `(slot+1)&0x0f` (a `(a+b+1)>>1` halving that preserves the sign bit), leaving the two midpoints in `loc_61`/`loc_62` and `loc_63`/`loc_64`, then appends the four midpoint bytes through the `loc_74` pointer at the `loc_a9` cursor (each high byte masked to `0x1f`, the vector-opcode field) while mirroring all four into the "previous point" scratch `loc_6a`–`loc_6d`. `loc_c73c` [seen] then emits the *stroke deltas* from that anchor: it computes two 16-bit differences — `(loc_63:loc_64)-(loc_6c:loc_6d)` and `(loc_61:loc_62)-(loc_6a:loc_6b)` — writing each through the `loc_74` cursor at `loc_a9` with the low byte raw and the high byte masked to five bits, and OR-ing `0xa0` (a vector-generator opcode) into the second high byte before advancing the cursor by four.

`loc_c765` [seen] is an alternate entry for the object-position vector: it lays a fixed `{0x00, 0x71}` header word at cursor slots 0 and 1, then resumes the shared build (`loc_c772`'s tail `loc_c774`) from slot two, so the standard `{0x40, 0x80}` header and the two absolute coordinate words follow its own leading header rather than starting the record. `loc_c6c7` [seen] emits the per-enemy vector entry for slot `loc_38`: when the slot's kind byte `loc_3ac`+x is zero it writes four blank `{0x00, 0x71}` pairs (an empty placeholder); otherwise it seats the depth into `loc_57`, clamps it toward the reference depth `loc_5f` via `loc_c453`, seats the lane coordinates `loc_56`/`loc_58` from `loc_435`/`loc_445`, runs the math-box projection `loc_c098` and the delta emit `loc_c73c`, and then — reading the shape flag `loc_39a`+`loc_38` & `0x40` — either appends a randomly chosen table word (running `loc_bd3e`, then picking one of two adjacent words at `loc_cec8`/`loc_cec9` with index `(loc_60ca & 0x02) + 0x1c`) or a fixed marker word `{0x00, 0x68, loc_3db2, loc_3db3}`, advancing `loc_a9` in each case.

`loc_bd3e` [seen] appends a normalized (mantissa, exponent) pair and is where the vertex pipeline reaches into the math coprocessor. For a small input (`loc_57` < `0x10`) it emits the trivial pair `(1, 0)`; otherwise it forms the 16-bit difference `loc_57-loc_5f` (with borrow into `-loc_5b`) into the math-box operand registers `loc_6095`/`loc_6096`, sets control `loc_608c`=`0x18`, issues the operation through `loc_608e`/`loc_6094` (both from `loc_a0`), spins while the busy bit `loc_6040 & 0x80` is set, then reads the result `loc_6060`→`loc_79` and `loc_6070`→`loc_7a`, restores control to `0x0f`, and normalizes `loc_79` by rolling it left until a set bit falls out — the roll count becomes the mantissa shift stored in `loc_78` and the accumulator becomes the exponent — finally writing the pair through the `loc_74` cursor at `loc_a9` with the second byte OR'd `0x70`.

`loc_df92` [seen] emits a complete four-byte coordinate record through the `loc_74` cursor from four zero-page slots offset by X: `zp[loc_2+x]` at slot 0, `zp[loc_3+x] & 0x1f` at slot 1, `zp[loc_0+x]` at slot 2, and a key-folded last byte `((zp[loc_1+x] ^ loc_73) & 0x1f) ^ loc_73` at slot 3, then hands to its tail `loc_dfac`, which stores that last byte at the next cursor slot and either advances the cursor (via the shared step that moves `loc_74`/`loc_75` past the emitted bytes) or, when the slot index wraps to zero, closes out with a terminating nibble run through `loc_dfb1`.

**Two routines here are not vector emitters.** Read straight from the code, `loc_db5a` [code] and `loc_dded` [code] drive the EAROM (ER-2055 NVRAM) high-score machinery, not the draw pointer. `loc_db5a` checks the guard bytes `loc_1ca`/`loc_1c7` and, only when both are clear, runs the EAROM state-machine seeder `loc_de11` and stamps `loc_7c`=`loc_1c9` and `loc_0`=`0x02`; in this capture the guards were never both clear, so its own write path was not taken. `loc_dded` is a trampoline that forwards mask `0x03` into the shared EAROM request-merge `loc_ddf3`, requesting a set of blocks be transferred; it performs no write of its own and its mask-`0x03` merge was not observed in the capture (the captured merges into `loc_1c7` carry masks `0x04`/`0x07`, not `0x03`), so its role rests on the code.

## Enemy spawning and lane selection

Two distinct object tables live behind this subsystem, and the spawn machinery routes new arrivals into whichever one fits: a wide per-slot enemy table keyed on the tube depth cell `loc_2df` and the segment cell `loc_2b9`, and a narrow eight-entry timed-object table keyed on `loc_30a`/`loc_302`/`loc_2fa`/`loc_312`. The lane-selection code decides *where around the rim* an enemy is placed and *which lane* it should climb, while the allocators commit the choice into a slot's parallel arrays.

**Per-wave tag seeding.** `loc_9246` ([seen]) prepares the wave's lane-tag scratch before enemies begin flowing. It first blanks the 64-byte tag table `loc_243`..`loc_243+0x3f`, then walks the active-slot count down from `loc_3ab`-1 to 0. For each slot index `x` it draws a POKEY-1 random nibble (`loc_60ca & 0x0f`), stores that raw nibble at `loc_203+x`, and packs a tag `(x<<4)|nibble` into `loc_243+x`, substituting `0x0f` whenever the packed byte would be zero so that a zero-index/zero-random slot still carries a nonzero tag. The result is a per-slot table pairing each slot with a fresh random nibble, keyed off the same `loc_3ab` slot count that later gates the approach step.

**Candidate lane selection.** `loc_9abb` ([seen]) chooses a lane to feed from among four candidates. It seeds a starting index from a POKEY-1 random value (`loc_60ca & 0x03`), primes a four-count countdown in `loc_2b`, and stashes the caller's X in `loc_39`. Each pass decrements the `loc_2b` countdown — an underflow (bit7 set) abandons the search and reports 0 — then steps the wrapping index `y` down through the four-entry candidate list `loc_149`, wrapping back to 3 at underflow. The list entry is read as a lane id, with id `0x03` remapped to `0x05`, and the lane qualifies only when its occupancy cell `loc_13c+idx` is nonzero. On a qualifying hit it builds the placement scratch the allocator will consume: `loc_2c` takes the chosen lane id with bit6 forced on (`loc_149[y] | 0x40`), `loc_2d` takes the list's high byte from ROM table `loc_9afd` at index 2, `loc_2b` is left holding that index (2), and the routine reports `loc_29`. These are the same zero-page cells `loc_994d` reads, so the selector stages the coordinate/flag seeds and the allocator commits them.

**Enemy-slot allocation.** `loc_994d` ([seen]) is the enemy/entity slot allocator, heavily exercised. It saves the caller's Y in `loc_36`, then scans the depth table `loc_2df` from index `loc_11c` downward looking for a free entry (value 0); if the scan runs past index 0 (bit7 set) it reports 0 with nothing allocated. On a free slot at index `y` it seeds the parallel per-slot arrays: depth `loc_2df+y` from `loc_29`; the segment `loc_2b9+y` from `loc_2a`, except that when `loc_2a` is `0x0f` *and* gate flag `loc_111` has bit7 set the segment is instead a random even value `loc_60ca & 0x0e`; the successor segment `loc_2cc+y` = `(segment+1) & 0x0f`; a cleared `loc_2a6+y`; the slot flag byte `loc_28a+y` from `loc_2c` and the saved motion-script instruction pointer `loc_291+y` from `loc_2d`; and the slot flags `loc_283+y` from `loc_2b`. It bumps the active-enemy count `loc_108` and increments the per-lane counter `loc_142` at index `loc_2b & 0x07`, restores X into `loc_36`, and reports `0x10` to signal a successful allocation. The `0x0f`/bit7 branch means that a "wildcard" segment request under an active gate is scattered to a random even rim segment rather than a fixed one.

**Deepest-column targeting.** `loc_a028` ([code], its write path unexercised in the capture) picks a target segment for slot x by finding the deepest tube column. It clears the running maximum `loc_2d`, primes the loop counter `loc_140` to `0x0f`, and starts scanning the 16-column depth table `loc_3ac` from a random column (`loc_60da & 0x0f`, the POKEY-2 random). Each pass reads a column depth, treats an empty column (0) as maximal `0xff`, and keeps the column with the greatest depth in `loc_2d` with its index in `loc_29`; column `0x0f` is skipped while the gate `loc_111` is nonzero. After sixteen columns it records the winner as the slot's segment `loc_2b9+x`, its successor `loc_2cc+x` = `(winner+1) & 0x0f`, and clears bit7 of the slot flag `loc_28a+x`. In game terms this aims a slot at the lane that has descended furthest.

**Per-slot approach and lane-depth tracking.** `loc_9fc4` ([seen]) advances one slot toward its column and maintains the per-column nearest-depth record. It raises the continuation flag `loc_10c`=1, reads the slot's column from `loc_2b9+x`, and seeds an empty column entry `loc_3ac+col` to `0xf1`. If the slot's own depth `loc_2df+x` is shallower than the stored column value it becomes the column's new running minimum and tags `loc_39a+col` = `0x80` to mark a fresh minimum. It then branches on the slot depth: below `0x20` it forces bit7 of the flag `loc_28a+x`, clamps the depth up to `0x20`, and returns; between `0x20` and `0xf1` it simply returns; at `0xf2` or deeper it calls `loc_a028` to choose a new column, reparks the depth to `0xf0`, and — only when the wave slot count `loc_3ab` has drained to 0 — rewrites the slot's low flag bits (`loc_28a+x` cleared of its low two bits then OR'd with `0x01`, `loc_283+x` cleared of its low three bits then OR'd with `0x02`) and clears the continuation flag `loc_10c`. So a slot that reaches the far end recycles onto a fresh deepest column, and it only re-flags itself into a new mode once the wave has finished spawning.

**Direction and side-bit helpers.** Two small helpers, both [code] and not exercised in the capture, support flipping enemies as they walk the rim. `loc_9eab` (gated by `loc_111` — an immediate return when it is zero) keeps bit6 of the slot flag `loc_283+x` in step with the slot's rim segment `loc_2b9+x`: when bit6 is already set it clears it once the segment reaches `0x0e`, and when bit6 is clear it sets it only while the segment is exactly 0. `loc_9ed7` looks up a direction byte from the 16-entry ring table `loc_3ee+y` and forces bit7 on; when the caller's accumulator has bit6 set it takes the half-turn variant, stepping the index back one within the ring (`(y-1) & 0x0f`) and adding 8 to the looked-up value modulo the ring before setting bit7.

**Timed-object insertion.** The eight-slot table is filled by `loc_a3d6` ([seen]). It saves X/Y into `loc_35`/`loc_36`, clears the eviction trackers `loc_2a`/`loc_2b`, and scans slots 7..0: the first empty slot (`loc_30a+i` == 0) is taken immediately, otherwise it tracks the slot holding the largest counter `loc_312+i` in `loc_2a`/`loc_2b`. If no slot was free it evicts that largest-counter slot and decrements the live count `loc_116`. Into the chosen slot it writes counter `loc_312`=0, type `loc_302` from `loc_2c`, position `loc_30a` from `loc_29`, and lane `loc_2fa` from `loc_2d`, then bumps `loc_116`. `loc_a3d4` ([code]; its own write to `loc_2c` stayed constant in the capture) is a thin front door that stashes the accumulator into the type-seed cell `loc_2c` and falls straight into `loc_a3d6`.

**Timed-object aging.** `loc_a416` ([seen]) advances the same table each pass, gated by the pending flag `loc_116`: when it is zero the routine returns, otherwise it clears the flag and, for each occupied slot (`loc_30a+i` != 0), advances the slot's counter `loc_312+i` by the per-type step read from ROM table `loc_a44e` indexed by the slot's type `loc_302+i`. A slot whose counter reaches the per-type limit in ROM table `loc_a448` is freed (`loc_30a+i` set to 0); any slot still short of its limit re-raises `loc_116` so the next pass revisits the table. Each type therefore carries its own lifespan and step rate through the two ROM tables.

**Insertion callers.** Three routines drive the timed-object insert with their own setup and a sound cue. `loc_a34b` ([code]) primes a fresh top-priority object: it sets `loc_13b`=`0xff`, seeds the type field `loc_2c`=`0x01`, copies `loc_202` into the position seed `loc_29` and `loc_200` into the lane seed `loc_2d`, fires its sound cue through `loc_ccb0`, inserts the object via `loc_a3d6`, and finally raises the ready flags `loc_201`=`0x81` and `loc_13c`=`0x01`. Its distinctive head (the `loc_13b`=`0xff` sentinel and type `0x01`) was not observed in the capture — only the shared insert tail ran, reached from another caller — so its priming role rests on the code. `loc_a36f` ([seen]) retires the object in slot Y: it rings its cue through `loc_ccc1`, stages the source and target seeds from `loc_2db+y` (into `loc_29`) and `loc_2b5+y` (into `loc_2d`), re-inserts a zeroed-type object via `loc_a3d4` with A=0, clears `loc_2db+y`, drops the live count `loc_a6`, and marks lane X spent with `loc_2f2+x`=`0xff`. `loc_a3ca` ([seen]) rings the same `loc_ccc1` cue, copies the Y-indexed depth byte `loc_2df+y` into the position seed `loc_29`, and inserts through `loc_a3d4` carrying the caller's accumulator as the object type. The three callers thus share one insertion path while differing in what they seed and whether they arm the ready flags, retire a slot, or simply queue a new object.

## Enemy motion and the pursuit AI

Enemies live in a bank of parallel per-slot arrays indexed by the slot number in X. The cells this subsystem reads and writes are the slot's segment around the rim (`loc_2b9`, $02b9), its depth down the tube (`loc_2df`, $02df), a phase counter (`loc_2cc`, $02cc), and a flag/state byte (`loc_283`, $0283) whose low three bits carry the enemy's kind, whose bit 7 marks it as "negative", and whose bit 6 records a travel direction. The player's own position on the near rim is the shared segment cell `loc_200` ($0200), and the shared far-end depth the tube feeds toward is `loc_202` ($0202). Two distinct motion models write into these same slot arrays, and the code supports both readings without reconciling them: a free-flying three-axis integrator (built around `loc_a65b`/`loc_a6a9`/`loc_a721`, all `[code]` — not exercised in this capture) and a rim-walking flag machine (`loc_9d06`/`loc_9d67`/`loc_9c4f`, of which only `loc_9d06` is `[seen]`). The rim-walking reading is the one the capture actually witnessed.

**Spawning an enemy with a random velocity.** `loc_a65b` (`[code]`) seeds a new enemy into slot x. It stamps 0x80 into the three whole-coordinate/state cells `loc_263`, `loc_283`, and `loc_2a3`, then fills three velocity pairs from the two POKEY random registers: the low bytes `loc_2c3`/`loc_2e3`/`loc_303` take raw random values (`loc_60da` for the first, `loc_60ca` for the other two), and the matching whole bytes `loc_323`/`loc_343`/`loc_363` take a signed random step. That step comes from `loc_a69b` (`[code]`, `signedRandomStep`), which reads a three-bit magnitude 0..7 out of the POKEY-2 random cell `loc_60da` and negates it when the caller's incoming value has bit 0 set, yielding a nudge in [-7, +7]; the argument only decides the sign, never the magnitude. `loc_a65b` additionally forces the middle axis' step non-positive (it negates any already-positive value) before finally raising the enemy's sound cue through `loc_ccc1`. Because none of these write PCs fired, the whole spawn path is accounted not-exercised here.

**Integrating three motion axes.** `loc_a6a9` (`[code]`, `integrateEnemyMotionAxes`) advances a slot along three axes. Each axis folds a low velocity byte into a fraction accumulator (axis 0: `loc_2e3` into `loc_223`; axis 1: `loc_2c3` into `loc_203`; axis 2: `loc_303` into `loc_243`), then adds the carry out of that fraction plus the signed whole-velocity byte (`loc_343`/`loc_323`/`loc_363`) into the whole coordinate (`loc_283`/`loc_263`/`loc_2a3`). Each axis checks its whole against the tube-ring bounds (0xf0 on a rising axis, 0x10 on a falling one), but only axis 0's committed coordinate `loc_283` is reset on overflow — axes 1 and 2 write their wrapped whole (`loc_263`, `loc_2a3`) unconditionally, regardless of their own overflow. Axis 0's result is held back and committed to `loc_283` only at the end, and is forced to zero if axis 0, 1, or 2 overflowed — so an object that runs off the ring on any axis collapses its primary coordinate while the other two axes keep their wrapped values. Its companion `loc_a721` (`[code]`, `stepSlotThreeAxisVelocity`) bleeds those velocities toward rest: it seeds a saturation counter `loc_29` to 0xfd and steps each of the three (low, whole) velocity pairs through `loc_a75d` (`[code]`, `stepVelocityTowardZero`), storing the stepped bytes back. `loc_a75d` moves a signed 16-bit velocity one fixed increment of 0x20 (from `loc_a788`) toward zero — adding when the whole is negative, subtracting otherwise — and on crossing zero it snaps the value to zero and increments `loc_29`. When all three axes have saturated, the counter wraps from 0xfd through 0x00, and `loc_a721` responds by zeroing the slot's whole coordinate `loc_283`.

**Folding a fractional step into the rim reference.** `loc_adce` (`[code]`, `integrateFractionalStep`) is a small fixed-point integrator: it folds a signed sub-step times eight (`loc_50` << 3) into the fractional accumulator `loc_51`, propagates the carry plus the sign of the sub-step up into A, and clears `loc_50`. It was reached but folded only zeros in this capture, so the step never actually moved. `loc_b0ab` (`[code]`, `integrateStepIntoClampedPosition0200`) drives that integrator over the shared rim-position cell `loc_200`: it reads `loc_200`, runs it through `loc_adce`, floors a negative result to zero and clamps a large one to the lane-count ceiling in `loc_127`, writes the clamped value back, and hands it out through both A and Y. In the capture `loc_200` never moved (the sub-step was always zero), so the clamp is read from code; the mechanism is a signed step into the ring position bounded by the number of lanes.

**Which way to walk: the direction bit.** Several routines treat bit 6 of the slot flag byte `loc_283` as the enemy's travel direction around the rim, and they lean on the signed-distance helper `loc_a7a6` (`[seen]`, `computeSignedSegmentDelta`) to decide it. `loc_a7a6` computes A minus Y, stashes it in `loc_2a`, and then — depending on the geometry flag `loc_111` — either keeps the full signed byte (when bit 7 of `loc_111` is set) or masks to the low nibble and sign-extends bit 3, giving a wrapped short-distance measure suited to a closed loop of lanes; the two modes plausibly correspond to open versus closed tube shapes, though the code only shows the switch, not the geometry meaning. `loc_9d67` (`[code]`, `flagSlotTargetSideBit6`) uses it to record which rotational side a slot's target lies on: it takes the difference of the player/reference segment `loc_200` and the slot's segment `loc_2b9`, and then clears bit 6 of `loc_283` when that difference is negative or sets it otherwise. `loc_9c4f` (`[code]`, `toggleSlotFlipDirectionBit`) simply flips that same bit 6 in place and returns the new byte, reversing the walk direction of a rim-crawling enemy.

**Settling at the target depth and inheriting a neighbour's direction.** `loc_9d06` (`[seen]`, `settleTubeObjectAtTargetDepth`) is the rim-machine step that ran in this capture. It first copies the shared far-end depth `loc_202` into the slot's depth cell `loc_2df`. If the slot's kind (low three bits of `loc_283`) is 1 and the gate byte `loc_3ab` is set, it just flips bit 7 of a second flag cell `loc_28a` and stops; if the slot is already "negative" (bit 7 of `loc_283`), it merely increments its stashed depth and stops. Otherwise it decrements a shared counter `loc_108`, and — when the mode byte `loc_109` equals 1 — scans slots 6..0 for another occupied slot whose stashed depth matches the shared value, then copies that matched slot's bit 6, inverted, into slot x's flag byte (so a flipping enemy adopts the opposite travel direction of a chosen neighbour). When the mode byte is not 1 it instead calls `loc_9d67` to set the direction bit purely from the target's rotational side. Either way it finishes by writing 0x41 into `loc_10b` and bumping the mode byte `loc_109`.

**Aiming at the nearest enemy.** `loc_97c5` (`[seen]`, `turnDirTowardNearestObject`) is the pursuit/auto-aim reader. It walks the slot depth table `loc_2df` down from the count in `loc_11c`, keeping the smallest nonzero depth in `loc_29` and its slot index in `loc_2a` — that is, it finds the enemy nearest the rim. If none is found it returns the last value seen; otherwise it takes that slot's segment `loc_2b9`, differences it against the player segment `loc_200` through `loc_a7a6`, and turns the sign of the result into a rotation code: 0 when the target is already lined up, 0x09 (a positive spinner nudge) when the difference is negative, and 0xf7 (a negative nudge) otherwise. Its caller consumes that code as the spinner delta that steers the blaster toward the nearest climbing enemy, the mechanism behind the attract-mode demo's aiming.

**Spikes remapping toward a rail.** `loc_a7d2` (`[seen]`, `remapObjectTableTowardRail`) reshapes the eight-entry object table `loc_3fe` (the moving spike/pulsar column set that `resetSpikeTableAndArmFlag` arms) against the reference flag `loc_115`. When `loc_115` is zero it is a no-op. Otherwise it sweeps the eight entries from 7 down to 0: an entry of 0x17 or more shrinks by seven, a nonzero mid-range entry snaps to one of the two rails (0xf0 or 0) chosen by the sign of `loc_115`, and a zero entry adopts a rail only when `loc_115` is negative and its next wrap-around neighbour is a nonzero value below 0xd5. Every result is OR-folded into `loc_29`, a marker 0xff is stored to `loc_37`, and if the whole table has collapsed to zero the reference `loc_115` is itself cleared — the column has finished retracting to the rim.

**Pacing the active slot.** `loc_c9af` (`[seen]`, `tickActiveSlotCountdownAndAdvance`) services one active slot per pass. It clears `loc_4`, decrements the active slot's countdown byte `loc_48`,x (indexed by `loc_3d`), and when the `loc_48`/`loc_49` pair is fully spent it finalizes through `loc_c9f1` and returns. Otherwise, if the active countdown has just hit zero it seeds `loc_1`=0x0c and `loc_4`=0x28, then advances a toggle `loc_3f` (gated by `loc_3e`) until it lands on a non-empty slot, and arms that slot's timer from its window byte `loc_46`,x — writing 0x1c or 0x02 into `loc_2` and 0x0a into `loc_0`. The finalizer `loc_c9f1` (`[seen]`, `computePeakSlotValueAndSetTimer`) scans the zero-page window `loc_46` from the cursor in `loc_3e` down to zero, takes the maximum into `loc_126`, decrements it once when nonzero, and sets the timer cell `loc_0` to 0x14, or to 0x10 when the status byte `loc_5` is negative. Together they read as a per-slot countdown scheduler and peak/timer pacer; the exact game-vocabulary meaning of the scheduled quantity is not settled from the code alone.

`loc_c81b` (`[seen]`, `applyPendingStepsAndBumpTally`) sits alongside them but its game role stays unresolved (flagged). From the two-bit gate in bits 5/6 of `loc_4e` and a "counter ≥ 2" test on `loc_6` it derives a step of 0..2, drains `loc_6` by that step, and stores it in `loc_3e`. With the gate clear it may seed four intro cells (`loc_1`=0x10, `loc_4`=0x20, `loc_0`=0x0a, `loc_2`=0x14) when `loc_50` is nonzero and `loc_5` is non-negative. With a nonzero step it ORs 0xc0 into `loc_5`, zeros `loc_16`/`loc_18`/`loc_0`, bumps a 16-bit tally at `loc_40c`/`loc_40d`, and clamps `loc_100` + step to a ceiling of 0x63. The arithmetic is confirmed against MAME; what the tally counts in the game's terms is not.

**Placing a slot on the screen.** Three routines here are geometry rather than pursuit logic. `loc_b634` (`[seen]`, `computeSlotScreenPoint`) builds a screen point for slot x: it takes the slot's segment `loc_2b9` as an index into the per-lane base-coordinate tables `loc_3ce`/`loc_3de` (into scratch `loc_56`/`loc_58`), offsets each by a signed delta drawn from `loc_b68b`/`loc_b687` (indexed by the low nibble of the phase counter `loc_2cc`) using a 0x80-biased signed-saturating add, and writes the resulting X to `loc_2e` and Y to `loc_30`; it also copies `loc_57` to `loc_2f` and loads a style-byte pair from `loc_bcdc`/`loc_bcec` (indexed by `loc_112`) into `loc_59`/`loc_5a`. `loc_b6fa` (`[code]`, `scaleDeltaByPhaseFraction`) scales an input delta by the low three bits of the same phase counter `loc_2cc`,x: it stashes the input in `loc_29` and the three-bit fraction in `loc_2c`, then runs three rounds of shift-add with a sign-preserving right shift, returning the scaled value — its only caller invokes it from the object-draw path, and it was not reached here. `loc_b875` (`[code]`, `rotateTriadDownAndMirror`) rotates the three-entry array `loc_22`..`loc_24` down by one with wrap-around, threading the displaced value, and mirrors each new entry into the paired array `loc_809`..`loc_80b`; it is reached only through the computed dispatch `loc_b84e` (table index 1) and never ran in the capture, so its game role is unconfirmed.

## The mathbox: projection and level tables

Tempest draws its tube in perspective, and the arithmetic that turns a lane's stored geometry into on-screen vector coordinates runs through a hardware math coprocessor mapped into the `loc_6040`–`loc_6096` register window (the "mathbox"). Two threads meet in this subsystem: the routines that drive that coprocessor point by point, and the routines that load a level's shape and colour tables out of packed ROM and lay down the per-lane vertex coordinates the projector consumes.

**Priming the coprocessor.** `loc_c1c3` [seen] is the reset that opens a projection sequence. It zeroes a cluster of zero-page working cells (`loc_78`, `loc_80`, `loc_81`, `loc_88`, `loc_90`, `loc_91`) and a set of the coprocessor's input registers across `loc_6080`–`loc_6090` (leaving `loc_6082`, `loc_6088`, `loc_608a` and `loc_608b` untouched), then finally sets the control byte `loc_608c` to `0x0f`. It is exercised on essentially every pass through the projection path. A caveat carried from grounding: in the capture every observed transition was constant (cells already zero, `loc_608c` `0xf`→`0xf`), so the clears are confirmed as writes but their draining effect was not seen in motion.

**Projecting one point.** `loc_c098` [seen] is the per-point driver. It first forms a signed 16-bit depth delta from `loc_57` − `loc_5f`, with `loc_5b` supplying the high byte's borrow source, writing the low byte to `loc_6095` and the high byte to `loc_6096`; if that high byte comes out negative it forces the delta to +1 (`loc_6096` = `0x00`, `loc_6095` = `0x01`), clamping the depth to the near side. It then computes two magnitudes, |`loc_58` − `loc_60`| and |`loc_56` − `loc_5e`|, recording each sign as `0xff`/`0x00` in `loc_33` and `loc_34`. The first magnitude is issued into the coprocessor through the paired write `loc_608e`/`loc_6094`, and the routine spins on bit 7 of `loc_6040` until the result is ready. It reads the 16-bit product back from `loc_6060`/`loc_6070` into `loc_63`/`loc_64`, issues the second magnitude (held in `loc_32`) through `loc_608e`/`loc_6094`, and — keyed on the `loc_33` sign — folds the offset pair `loc_68`/`loc_69` into the `loc_63`/`loc_64` accumulator, adding when the sign bit is clear and subtracting when set, saturating to `0x7fff` on positive overflow and to `0x8000` on negative overflow. After a second spin on `loc_6040` bit 7 it reads the next product into `loc_61`/`loc_62` and, keyed on the `loc_34` sign, folds the `loc_66`/`loc_67` offset pair into that accumulator under the same saturating rules. The two saturated 16-bit accumulators `loc_61`/`loc_62` and `loc_63`/`loc_64` are the routine's projected output.

**Snapping the depth operand.** `loc_c453` [seen] conditions that same `loc_57` operand before it reaches the projector. It returns immediately when the guard `loc_5b` is non-zero, and again when `loc_57` already sits `0x0c` or more above the reference `loc_5f`; otherwise it snaps `loc_57` up to `loc_5f` + `0x0f`, capped at a ceiling of `0xf0`. Because `loc_57`, `loc_5b` and `loc_5f` are the very operands `loc_c098` consumes, this is a pre-projection clamp that pulls a lagging coordinate up toward its reference (in the capture, a large `0x14`→`0xe7` jump). Its callers sit in the projection setup path.

**Projecting a whole tube.** `loc_c473` [seen] drives `loc_c098` across all sixteen lanes. It takes the depth operand in A (stored to `loc_57`) and an output base index in X (stored to `loc_38`), clears the clamp tally `loc_59`, and walks a lane counter `loc_37` from `0x0f` down through 0. Each pass copies that lane's stored base coordinates `loc_3ce` + col and `loc_3de` + col into `loc_56` and `loc_58` and calls `loc_c098`. It then clamps each of the two projected 16-bit results to a small screen window: the `loc_62`/`loc_61` pair and the `loc_64`/`loc_63` pair are each squeezed to the range −4..+3 (byte value `0xfc`..`0x03`), writing the clamped value and a sign byte into the paired slot arrays `loc_31a`/`loc_32a` and `loc_33a`/`loc_34a` at the output index `loc_38`. A value below the window yields `0xfc` with sign `0x01`; a value at or above the window yields `0x03` with sign `0xff`; anything inside passes through with its own sign byte. Every clamp bumps `loc_59`, and the routine hands that clamp count back in A. The output index and the lane counter both decrement each pass until `loc_37` underflows past 0.

**Unpacking the level's nibble tables.** `loc_c196` [seen] loads the current level's packed shape/colour tables. It takes the level selector `loc_9f` masked to `0x70`, clamps it to at most `0x5f`, forms an index x = (selector >> 1) | `0x07`, and walks y from 7 down to 0, reading one packed byte from the ROM table at `loc_c1fd` + x each step. Each byte carries two nibbles: the low nibble goes to `loc_19` + y and is mirrored to `loc_800` + y, while the high nibble goes to `loc_21` + y and is mirrored to `loc_808` + y. The `loc_800`/`loc_808` writes are the display mirrors of the working tables. One call fills all four eight-entry tables in a single pass; the trace shows them filled with real, varying per-level values.

**Arming the level tables.** `loc_b888` [code] wraps that unpack: it calls `loc_c196` and then seats a two-byte vector-list tail cursor, `loc_139` = `0x7f` and `loc_13a` = `0x04`. This routine was not reached in the capture — its own writes at `loc_139`/`loc_13a` never fired — and no direct caller was found, so it is reached only through the computed dispatch into the level-setup ROM; its tag stays [code], and its role is read from the code rather than confirmed in motion.

**Building the tube's lane coordinates.** `loc_c235` [seen] is the level-geometry builder, run once per level setup. It first picks a geometry-table entry: it passes the byte at `loc_46` + `loc_3d` through `loc_c2e8`, taking the packed return as a seed and reading the resulting table index from `loc_112` into y. From that index it derives the level's span operands: a negated base at `loc_bc8c` + y goes into both `loc_5f` and `loc_5d`, its complement `0x10` − that value into `loc_a0`, `loc_5b` is set to `0xff`, `loc_60` takes `loc_bc9c` + y, and `loc_111` takes `loc_bccc` + y. The offset pair depends on a mode byte `loc_2`: when `loc_2` equals `0x1e` it copies `loc_bcac` + y and `loc_bcbc` + y straight into `loc_68` and `loc_69`; otherwise it forms the signed 16-bit difference {`loc_bcbc`:`loc_bcac` + y} − {`loc_69`:`loc_68`}, shifts it right four bits keeping the low byte, and stores that as the level geometry scale `loc_121`. It then clears `loc_66`, `loc_67`, `loc_10f`, `loc_110` and seeds `loc_113` = `0x2c`.

With the scalars set, `loc_c235` lays down the tube's per-lane vertex arrays top-down. A neighbour index walks down from the seed as x runs `0x0f`..0, copying `loc_b97c` + ny into `loc_3ce` + x, `loc_ba7c` + ny into `loc_3de` + x, and `loc_bb7c` + ny into `loc_3ee` + x, while clearing the projected-slot arrays `loc_31a` + x, `loc_33a` + x and `loc_39a` + x for that lane. Finally it fills two midpoint arrays by rounding-averaging each lane's coordinate with its next neighbour (the index wrapping at 16): `loc_435` + x from the `loc_3ce` pair and `loc_445` + x from the `loc_3de` pair, where the average adds the two bytes plus one and rotates the nine-bit sum right, carrying bit 8 into bit 7. Because these `loc_3ce`/`loc_3de` base tables are exactly what `loc_c473` later reads lane by lane, `loc_c235` lays the tube's vertices down and `loc_c473` projects them.

**Selecting the geometry entry.** `loc_c2e8` [seen] is the small helper `loc_c235` leans on. Given a value in A, it substitutes a masked hardware byte `loc_60ca` & `0x5f` whenever the input is `0x62` or larger (a random/timer fallback), then splits the value into a quotient v >> 4 (returned in X) and a remainder v & `0x0f` (returned in Y). It looks the remainder up in the ROM table at `loc_bc7c`, stores that entry byte to `loc_112`, and returns in A a packed byte carrying the table entry in the high nibble with the low nibble forced to `0x0f`. The stored `loc_112` is the y index `loc_c235` reads straight back.

**A mode/scale gate.** `loc_ca48` [seen] sets a flag bit and a paired scale byte from two gates. It defaults to (a, y) = (`0x00`, `0x10`) and switches to (`0x04`, `0x08`) only when both `loc_117` and `loc_3d` are non-zero. It then copies bit 2 of the chosen a into flag `loc_a1` while preserving the other bits, and stores y to the scale byte `loc_b4`. In the capture only the default branch was taken (both gates giving a = 0, y = `0x10`), so bit 2 of `loc_a1` stayed clear and the alternate `0x08` scale was not observed; the tag is [seen] from those two default-path writes, with the alternate branch's game effect unconfirmed.

## Sound, POKEY and the interrupt heartbeat

Tempest speaks to two POKEY chips mapped side by side in the $60xx block — POKEY1 at $60c0-$60cf and POKEY2 at $60d0-$60df — and the sound machinery here is the chain that gets them initialised, fed effect requests, and driven one voice-step per frame, with a separate counter engine ticking on every interrupt underneath it.

### Bringing the chips up

`loc_cd95` [seen] is the cold reset of both POKEYs. It first parks SKCTL on each chip ($60cf and $60df) at zero and clears the random-latch cell `loc_720`, then reads the two RANDOM registers `loc_60ca` (POKEY1) and `loc_60da` (POKEY2) and polls each five times (x from 4 down to 0); the moment either RANDOM value differs from its first sample it stamps that first sample into `loc_720` and stops — a live-chip self-test that proves the noise generators are actually clocking. It then writes 7 into both SKCTL registers `loc_60cf`/`loc_60df` (the canonical POKEY keyboard/serial init), sweeps x from 7 down to 0 clearing all eight audio registers of POKEY1 (`loc_60c0`+x) and POKEY2 (`loc_60d0`+x) together with the paired software voice arrays `loc_c0`+x and `loc_d0`+x, and finally zeroes both AUDCTL registers `loc_60c8`/`loc_60d8`. After it runs, every hardware channel and every software voice slot is silent.

### Triggering an effect

A sound effect is asked for by id. A cluster of one-line trampolines each loads a fixed id and drops into the shared gate: `loc_ccb0` [code] carries id 0x5f, `loc_ccc1` [code] 0x1f, `loc_ccbd` [code] 0x8f, `loc_ccea` [code] 0x2f, `loc_ccee` [code] 0x6f, `loc_ccf2` [code] 0x7f, `loc_ccf6` [code] 0x9f, `loc_cd02` [code] 0x3f, and `loc_cd06` [code] 0xcf. Most of them route through `loc_ccc3` [code], the enable gate, which tests bit 7 of the mute/enable flag `loc_5` and simply returns when it is clear, otherwise falling through to register the id — so a single flag can suppress every gated effect at once. `loc_ccfa` [code] is the exception: carrying id 0xaf, it bypasses `loc_ccc3` and jumps straight to the registrar, so its sound plays regardless of that flag. Which in-game events the individual ids stand for is not settled by these routines; they only fix the id and the gating.

The registrar itself is `loc_ccc7` [seen]. It saves the caller's X and Y into `loc_31`/`loc_32`, then walks the 16 voice slots (slot 0x0f down to 0) while stepping an id cursor downward in lockstep, reading one byte per slot from the effect table at `loc_cb01`+cursor. A zero byte leaves that slot untouched; a nonzero byte claims the slot — it writes the slot index into the reservation cell `loc_bf`, stores the table byte as the voice's frame in `loc_c0`+slot, arms both the fast timer `loc_e0`+slot and the slow timer `loc_f0`+slot to 1 so the voice fires on the very next engine pass, then restores `loc_bf` to its 0xff idle sentinel. The effect's row of table bytes is thus fanned across as many slots as it needs.

### Stepping the voices onto the chips

`loc_cd0a` [seen] is the per-frame voice engine and the point where software voices actually reach the hardware. For each slot x from 0x0f down to 0 it skips any slot whose frame `loc_c0`+x is zero (idle) and the one slot currently reserved in `loc_bf`. It decrements the fast timer `loc_e0`+x and does nothing further while it is still counting; when it reaches zero it decrements the slow timer `loc_f0`+x. If the slow timer is still running, the voice takes a single table step: with y = frame<<1 and the table half chosen by the frame's bit 7, it reloads the fast timer from `loc_cbcc`/`loc_cccc`+y, reads the next level from `loc_cbcd`/`loc_cccd`+y, adds the slot's prior level, and stores the result in `loc_d0`+x — and for odd-numbered slots it preserves the previous high nibble of that level byte, keeping the distortion/control bits stable while only the low bits move. If instead the slow timer has also expired, it enters a walk loop that advances the frame `loc_c0`+x by two and keeps stepping through the `loc_cbcb`/`loc_cbce`/`loc_cbcc` (or `loc_cccb`/`loc_ccce`/`loc_cccc`) tables — writing level `loc_d0`+x, reloading slow timer `loc_f0`+x, and reloading fast timer `loc_e0`+x — until the reloaded fast timer `loc_e0`+x is nonzero. Finally it publishes the slot's level byte `loc_d0`+x to a POKEY register chosen by the slot's half: slots 0-7 write `loc_60c0`+x (POKEY1's eight audio registers), and slots 8-15 write `loc_60c8`+x, which for x of 8 and up resolves into POKEY2's `loc_60d0`-`loc_60d7`. The 16 software voices therefore map cleanly onto the two chips' eight audio registers each, with the odd/even split and the nibble-preserve behaviour matching the AUDF-frequency / AUDC-control register pairing of a POKEY channel.

### The interrupt heartbeat

`loc_cf24` [seen] runs on every interrupt, immediately ahead of the voice engine, and steps three parallel counter lanes indexed x = 2..0. Each pass pulls the control byte `loc_8` and shifts out one gating bit per lane (bits 0/1/2), so a lane only advances when its bit is set. For an enabled lane it adjusts the position cell `loc_d`+x (the `loc_d`/`loc_e`/`loc_f` triple), keeping it clamped and wrapped within a modulo-0x20 range, decrements the per-lane timer `loc_10`+x and reloads it to 0x78 on expiry, and bumps the per-lane counter `loc_13`+x. As lanes expire it folds a small increment (driven by config bits from `loc_9`) into the running accumulators `loc_16`/`loc_17`/`loc_18` and nudges `loc_6`, using the table at `loc_cfd9` to bound `loc_16`. It closes with two clamp passes over the `loc_13`+x lane triple: the first subtracts 0x10 from any lane at 0x10 or more, the second subtracts 0x11 from any nonzero lane. The routine is the steady counter/accumulator tick that keeps these three lanes advancing under the interrupt; its exact game-facing product (a pitch or sweep value handed to the audio path) is consistent with the code but not pinned down by this routine alone. One state-wrap branch is guarded by a thrown error rather than being allowed to run off into the following data.

### The channel-record scheduler

`loc_ac3f` [seen] settles the per-channel event records that feed the request path. It clears bit 6 of `loc_5`, optionally pre-clears the scratch block via `loc_ca62` when the low bits of `loc_9` match a pattern, queues an EAROM request through `loc_ddfb`, and zeroes the running total `loc_601`. Then, for one or two channels (starting at 0 or 3 depending on `loc_3e`), it stages a key triple into `loc_2c`/`loc_2d`/`loc_2e` and bubble-sorts the stored record rows at `loc_620`/`loc_61f`/`loc_61e` — with the parallel payload at `loc_520`/`loc_51f`/`loc_51e` moved alongside — comparing lexicographically and swapping out-of-order rows while counting the settling passes in `loc_605`. Each channel's pass count is recorded into `loc_600`+channel, the total `loc_601` is nudged when it is at or above the last channel's count (capped at 0x63), and a packed request byte is derived from the flag `loc_3d` into `loc_603` before handing off to the request walker `loc_ad22`. Whether this request ultimately drives a sound or a draw action is not decided within this routine.

`loc_ad6e` [code] is the per-frame tick of the currently active record slot in that same family (it shares `loc_600`, `loc_605` and `loc_ad22`). It sets `loc_1` to 6, and while the low five bits of `loc_3` are zero it expires the `loc_605` countdown, resetting `loc_00` to 0x14 when it hits zero. Otherwise it clamps the active slot value `loc_606`+slot (via `loc_adce`) to the 0x00-0x1a rails, gates on bits 3-4 of `loc_4e` (which it then masks down with 0x67), and steps the cursors `loc_602` and `loc_604`; when the step underflows it re-arms — calling `loc_ddf7` when the channel's `loc_600` entry is below 4 and then `loc_ad22` — and otherwise clears the retired neighbouring slot. It was not exercised in the capture, so its role rests on the code.

### POKEY-mapped configuration and the coprocessor slots

Two routines here read and pack values through the $60xx-mapped side channels. `loc_d6bb` [seen] decodes the option switches into game configuration: it reads the switch ports `loc_e00` and `loc_d00`, mirrors `loc_e00` into `loc_a`, slices its bits 5-3 through table `loc_d6f7` into `loc_156` and its bits 7-6 through `loc_d6ff` into `loc_158`, sets `loc_9` to `loc_d00` XOR 0x02, looks its bits 2-1 up in the paired `loc_d6b3`/`loc_d6b4` tables into `loc_ac`/`loc_ad`, and folds `loc_ad` through the merge below into `loc_16a`. That merge, `loc_dbe0` [code], stores the incoming value into POKEY2's `loc_60db`, mirrors the low three bits of `loc_60d8` into scratch `loc_37` and into `loc_60cb`, then returns those three bits OR'd with a relocated bit 5 of `loc_60c8` (the returned nibble carries that extra bit, which `loc_37`/`loc_60cb` do not); in the capture every write it made was a constant, so the bit-packing role is supported only by the code, not witnessed doing real work. Finally `loc_dce6` [code] primes what reads as a $60xx math coprocessor: it zeroes `loc_73`/`loc_414`/`loc_6090`, loads the operands A and X into `loc_608e`/`loc_608f`, sets the count `loc_608c`/`loc_6094` to 0x10, then scans the 16-slot status window at `loc_6040` for the first slot whose high bit is clear and hands back that slot's low/high result pair from `loc_6060`/`loc_6070` (or exits with the counter run past the end). It was not reached in the capture, so this reading too rests on the code.

## The EAROM high-score store

Tempest keeps its high-score table and bookkeeping in a small non-volatile store on the boardset — an EAROM reached only through the memory-mapped port block at `loc_6000` (the byte data port, addressed as `loc_6000 + x` where `x` is a walking cursor), `loc_6040` (the access-control/strobe port) and `loc_6050` (the read-back port). Because that store can only be touched a few bytes at a time under a multi-step access protocol, the game never talks to it inline. Instead it posts a *request* into a small block of flag cells and lets a single state machine, `loc_de1b`, drain the request over many frames. This section covers the request-posting family (`loc_ddf1`, `loc_ddf3`, `loc_ddf7`, `loc_ddfb`, `loc_dde9`), the mode-7 initiator `loc_de11`, and the transfer engine `loc_de1b` itself.

### The request block

Three consecutive cells hold a pending EAROM request. `loc_1c7` is the *region request-pending* bitmask: each set bit asks for one of (at most) three regions to be serviced. `loc_1c8` carries a *direction* bit per region — as `loc_de1b` reads it (below), a set bit means "write this region out to the store" and a clear bit means "read this region in". `loc_1c6` is an *index/blank-mode* byte: when it is left nonzero the transfer engine zeros each source RAM cell as it passes over it, which turns a write into a blanking pass (clearing a region rather than saving it).

The posting routines are a family of trampolines that funnel into one shared tail. The tail (`loc_ddff` inside `loc_ddfb.js`) does exactly three stores: `loc_1c6 = Y`, `loc_1c7 |= A`, and `loc_1c8 |= A`. The masks are ORed in, so several callers can accumulate requests before the engine next runs. The entry points differ only in the constants they feed that tail:

- `loc_ddf1` **[code]** is the fixed all-regions blanking entry: it stamps `loc_1c6 = 0xff` and ORs `0x07` into both `loc_1c7` and `loc_1c8` — every region requested, every direction set to write, blank-mode armed. This is the "clear the entire high-score store" request. Its own body only loads registers and branches to the shared tail, and the `0xff`/`0x07` values were never observed in the capture (only the `loc_ddfb` mask-`0x04` path ran the tail), so its role rests on the code.
- `loc_ddf3` **[code]** forces the index byte to `0xff` (blank-mode) and then merges a caller-supplied mask `A` through the shared tail — a blank/write-out of just the regions named in `A`.
- `loc_dde9` **[code]** is `loc_ddf3` with the mask fixed to `0x04`: blank/write-out of the third region only (`loc_1c6 = 0xff`, `loc_1c7 |= 0x04`, `loc_1c8 |= 0x04`).
- `loc_ddfb` **[seen]** posts a plain write-out of the third region with the index byte zeroed: `loc_1c6 = 0x00`, `loc_1c7 |= 0x04`, `loc_1c8 |= 0x04`. Its inner entries `loc_ddfd` (zero the index, take mask from `A`) and `loc_ddff` (both mask and index from the caller) are the shared spine the whole family lands on.
- `loc_ddf7` **[code]** supplies mask `0x03` down the zeroed-index path: `loc_1c6 = 0x00`, `loc_1c7 |= 0x03`, `loc_1c8 |= 0x03` — a write-out of the first two regions.

A fourth cell, `loc_1c9`, is not part of a request; it is the engine's *result* accumulator, an OR of the masks of any regions whose read-back failed verification (see below). Callers read it after the fact to learn whether the stored data was intact.

The game-level triggers for these posts sit in the surrounding code and set the sense of each region. `loc_ac3f`, which bubble-sorts the per-channel high-score record tables in place and folds a running total into `loc_601`, posts a plain write-out through `loc_ddfb` — persisting the freshly sorted table. `loc_ad6e` posts `loc_ddf7` (regions 0–1) when a channel's `loc_600`-block byte has dropped below `0x04`. So the request family is how a completed high-score edit or a table reset reaches the non-volatile store.

### Mode-7: reading the whole store back in

`loc_de11` **[seen]** is the read-all initiator. Rather than OR into the request cells, it *sets* them outright: `loc_1c7 = 0x07` (all three regions requested) and `loc_1c8 = 0x00` (all directions clear → read). It then falls straight into `loc_de1b` to begin draining that request the same call. With every direction bit clear this is a pure load — pulling all three regions of the high-score store back into RAM. Its caller `loc_db5a` **[code]** only fires it when the store is idle: it returns immediately unless both the phase byte `loc_1ca` and the request mask `loc_1c7` are clear, and after seeding the read it copies the result flag `loc_1c9` into scratch `loc_7c` and sets `loc_00 = 0x02`. That guard-then-seed is how the machine kicks off a high-score load once nothing else is mid-transfer.

### The transfer engine

`loc_de1b` **[seen]** is the state machine that actually moves bytes across the port block, and it is heavily exercised — it is re-entered from the top (`continue outer`) after each region until the request drains. `loc_1ca` is its phase byte and doubles as the "busy" flag: while it is zero and no request bit is pending the engine has nothing to do.

**Picking a region.** On a fresh step (`loc_1ca == 0` and `loc_1c7 != 0`) the engine isolates a single request bit. It clears its counters (`loc_1cb`, `loc_1cf`, `loc_1ce`) and rebuilds a walking single-bit mask in `loc_1ce`: an eight-iteration rotate loop shifts `loc_1c7` left while rotating a bit down into `loc_1ce`, stopping at the first set bit and leaving `x` at that bit's position (0–7). It then decides this region's direction — `Y` becomes `0x80` when `(loc_1ce & loc_1c8)` is nonzero (a write) and `0x20` otherwise (a read) — and stores it as the phase `loc_1ca`. The isolated bit is cleared from the pending mask with `loc_1c7 ^= loc_1ce`, so the next region is taken on a later pass. Finally `x` is doubled and used to index four packed ROM tables: `loc_dddd + x → loc_1cc` (the starting port cursor `x` for `loc_6000 + x`), `loc_ddde + x → loc_1cd` (the region's length / terminal cursor), and `loc_dde3 + x` / `loc_dde4 + x → loc_bd` / `loc_be` (the low/high bytes of the RAM pointer for that region). `loc_bd`/`loc_be` thereafter form the base of an indexed pointer `(loc_bd),y` into the region's RAM image.

**Servicing one entry.** Each pass through the common block first writes `loc_6040 = 0` to quiesce the control port and returns as soon as the phase byte is clear. Otherwise it loads `y = loc_1cb` (the entry cursor), `x = loc_1cc` (the port cursor), and shifts the phase byte left to fall into one of the protocol steps:

- If the shift carries out, this is a data-emit step: it writes the accumulated value to `loc_6000 + x`, advances the phase to `0x40`, and leaves with a control-port value of `0x0e`.
- If the phase's high bit is set, this is the address/data placement step for a *write*: it advances the phase to `0x80`, and — honoring blank-mode — if `loc_1c6` is nonzero it first zeros the source through `(loc_bd),y`. It reads that source byte, and if the port cursor `x` has reached the region length `loc_1cd` it ends the region (`loc_1ca = 0`) and substitutes the running total `loc_1cf` as the byte to emit — writing the accumulated checksum as the region's last cell. Either way it stores the byte to `loc_6000 + x` and leaves with control value `0x0c`.
- Otherwise it performs the EAROM access handshake for a *read* entry: it toggles the control port through `0x08`, then writes `0x08` to `loc_6000 + x`, pulses the control port `0x09` then `0x08`, and reads the byte back from `loc_6050`. If the cursor has not yet reached the region end the byte is stored through `(loc_bd),y` into the RAM image (the load path). If it *has* reached the end, the read-back byte is the stored checksum: the engine EORs it against its own running total `loc_1cf`, and a nonzero result means the region failed verification. On a mismatch it walks the whole region back down through `(loc_bd),y` writing zeros — discarding the corrupt image — and ORs this region's bit (`loc_1ce`) into the result flag `loc_1c9` so the caller learns the store was bad. A clean checksum leaves the loaded data in place.

**Running total and advance.** For the non-terminal entries the engine folds the current byte into `loc_1cf` with an add (`loc_1cf += A`), so `loc_1cf` builds a simple additive checksum across the region — the same total that is emitted (on write) or compared (on read) at the region's last cell. It then bumps both the entry cursor `loc_1cb` and the port cursor `loc_1cc`, writes the step's control value to `loc_6040`, and — if that value was zero — loops back to service the next entry of this region; a nonzero control value returns, yielding the CPU until the next call resumes the same region. When a region's phase byte finally reaches zero the outer loop re-enters from the top and either picks up the next pending request bit or, finding none, returns.

The net effect in the game's terms: the request family stamps *which* high-score regions to save, load, or clear and in *which* direction, `loc_de11` posts the boot-time read of the entire table, and `loc_de1b` drains those requests one region and one byte at a time through the EAROM port — accumulating an additive checksum on the way, writing it as each region's trailer on a save, and on a load verifying that trailer, wiping and flagging (in `loc_1c9`) any region whose stored copy did not check out.

## State-reset, init and per-frame update chains

This subsystem is the machine's scaffolding: the short leaf routines that blank tables and stamp starting constants when a mode or wave is (re)entered, one heavily-exercised per-frame updater that ages in-flight objects and drives a phase clock, and a small pair of chains that re-derive the tube geometry from the operator switches and refresh a per-request work slot.

### Leaf seeders — stamping starting constants

Several routines do nothing but write fixed bytes into work RAM, and they cluster on the same handful of zero-page scratch cells `loc_0`, `loc_1`, `loc_2`, `loc_4`, `loc_5`. `loc_b0e7` [seen] is a straight-line seeder that stamps `loc_0=0x0a`, `loc_2=0x00`, `loc_4=0xdf`, `loc_1=0x12` and then two higher cells `loc_14e=0x19`, `loc_14d=0x18`; all six writes land at their own PCs in capture, so the routine genuinely does its seeding even though the values themselves are constant. `loc_c97b` [seen] is a reached leaf that seeds a smaller overlapping set — `loc_2=0x04`, `loc_1=0x00`, `loc_0=0x0a`, `loc_4=0x14`. `loc_ca18` [seen] first masks `loc_5 &= 0x3f` (dropping the top two flag bits of that cell) and then writes its own init block: `loc_3e=0x00`, `loc_2=0x1a`, `loc_0=0x0a`, `loc_4=0xa0`, `loc_16b=0x01`, `loc_1=0x0a`. That three routines all write different constants into the same `loc_0..loc_4` cells tells us these are per-state entry seeders — each names the starting `loc_0..loc_4` configuration for a distinct mode/phase the machine is entering — but the code alone does not resolve which visible game state each one belongs to, so the specific role stays open behind the constants.

`loc_921b` [seen] seeds a different fixed set that reaches out of zero page: `loc_200=0x0e`, `loc_51=0xf0`, `loc_106=0x00`, `loc_201=0x0f`, `loc_202=0x10`. Two of these targets — `loc_200` and `loc_51` — are real state cells that vary elsewhere, and `loc_201`/`loc_202` are the sign-control byte and a counter that the per-frame updater below reads and steps, so this leaf is priming the object/phase machinery to its round-start values.

### Table-clearing resets

A second family blanks arrays and their associated flag cells. `loc_926f` [seen] zeroes the 7-byte block `loc_2df..` (indices 6 down to 0) and then clears seven scattered flags `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146`; because several of these hold non-zero values elsewhere this is a meaningful reset of that block plus its bookkeeping. `loc_928f` [seen] zeroes the 12-byte block `loc_2d3..` (0x0b down to 0) and clears the two flags `loc_135` and `loc_a6`. `loc_929f` [seen] blanks the 8-byte table `loc_30a..` and its trailing flag `loc_116`. `loc_ca62` [seen] zeroes a six-byte working block `loc_40..loc_45`; its callers use it as an optional pre-clear before staging three-byte entries back through that block. `loc_a831` [seen] clears just the pair `loc_3aa=0` and `loc_125=0` — notable because `loc_125` is elsewhere latched to `0xff`, so zeroing it here is the role-defining act. `loc_92ad` [seen] is the smallest reset of all: a single write of `loc_50=0`, resetting one state cell that ranges 0x00..0xde during play.

`loc_9234` [seen] seeds a 17-byte parameter block by role rather than by fixed constant: the header `loc_3ab` takes the current source byte `loc_15b`, and the 16-entry per-lane array `loc_3ac..loc_3bb` (index 0x0f down to 0) is filled with a second source byte `loc_15a`. Both sources vary at runtime — `loc_3ab` is a header cell that drains 0xf→0x0 elsewhere and `loc_3ac` is the head of the sixteen-lane array — so this routine (re)initialises the per-lane table from live parameters, not from constants.

Two more clearers carry an arming step. `loc_a7bd` [seen] zeroes the eight-byte table `loc_3fe..loc_405`, then overwrites the last slot `loc_405=0xf0` and arms the flag `loc_115=0xff`. `loc_a789` [code] (not reached in this capture — its role rests on the code) zeroes the 16-byte per-slot table `loc_283..loc_292` and re-seeds scalars `loc_10e=0x20`, `loc_10d=0x20`, `loc_1=0x04`, `loc_68=0` and `loc_69=0`; it is invoked as part of a per-slot (re)init and is one of the callees driven by `loc_ad22` below.

### Wave-entry setup: `loc_a5cb`

`loc_a5cb` [seen] is the composite wave/level-entry initializer. It resets a batch of bytes — `loc_0=0x20`, sets bit 7 of `loc_106` (`loc_106 |= 0x80`), clears `loc_104`, `loc_107`, `loc_5c` and `loc_123`, and sets `loc_105=0x02` — then walks the 16-entry lane array `loc_3ac+x` (x from 0x0f to 0) counting how many entries are non-zero into `loc_123`. This is the grounded tally: in capture `loc_123` climbs 0x0→0x6 as six occupied/spiked lane segments are counted. When at least one segment is live and the level cell `loc_9f < 0x07`, it loads an early-level intro/parameter block (`loc_4=0x1e`, `loc_0=0x0a`, `loc_2=0x20`, and forces `loc_123=0x80`). It always finishes by latching `loc_125=0xff`, marking the block ready. So `loc_a5cb` reads the shape of the lane table left over from setup, records how many segments are occupied, and, only on the early levels, layers in the intro parameters.

### Per-frame update: `loc_a504`

`loc_a504` [seen] is the machine's per-frame object/clock updater, run from the tail of the frame dispatcher and again when the control byte `loc_201` is negative; it is exercised on essentially every pass. The sign of `loc_201` splits it into two arms.

The positive arm (`loc_201 < 0x80`) first, when a gate is live (`(loc_455 | loc_11b) != 0`) and a limit has been passed (`loc_42 > 0x17`), bumps one per-slot timer cell `loc_00+loc_40` by one. It bails immediately if `loc_106 != 0`. Otherwise, when both `loc_3ab` and `loc_116` are clear, it scans the shot-depth table `loc_2df` downward from index `loc_11c` looking for any live entry that has already grown to `0x11` or beyond; only if none has does it run the wave-entry initializer `loc_a5cb` followed by the 12-byte reset `loc_928f`. A further guarded path runs `loc_a5cb` again when `loc_4d & 0x60`, `loc_5 & 0x80` and `(loc_9 & 0x43) == 0x40` all hold.

The negative arm — the one exercised in capture — first bails if any of `loc_135`, `loc_a6` or `loc_116` is set. It then ages every live shot in the depth table `loc_2df` (from index `loc_11c` down through the wrap): each non-zero entry is advanced by `+0x0f`, snapping to `0x00` once it reaches `0xf0` or above — objects that run out the far end of their travel expire. Next it branches on a per-index flag `loc_48+loc_3d`: if that flag is not `0x01` it advances the counter `loc_202 += 0x0f` and proceeds once the sum reaches `0xf0`; if it is `0x01` it instead clears `loc_10f=0x00`, sets `loc_114=0x01`, and steps the 16-bit countdown clock `loc_5b:loc_5f` down by `0x20` (low byte `loc_5f -= 0x20` with borrow into `loc_5b`), proceeding when the high byte equals `0xfa`. On proceeding, it writes `loc_00=0x06`, runs the reset `loc_928f`, and folds a running total into the header: `loc_3ab = min(0x3f, loc_108 + loc_109 + loc_3ab)`, clamping at `0x3f`. So each frame this routine ages the in-flight shot/object depths, ticks a phase clock or per-index counter toward its threshold, and at threshold rolls a bounded accumulator forward.

### Request-slot init: `loc_ad22`

`loc_ad22` [seen] drains a packed request word and initialises the first requested slot. It loops over the two-bit fields of `loc_603`: an empty word (`loc_603 == 0`) writes the exit status `loc_0 = 0x14` and returns idle. Otherwise it takes the low two bits as a slot index (`loc_3d = (loc_603 & 3) - 1`) and consumes them (two right shifts of `loc_603`); the grounded trace shows the word draining 0x4→0x0 and 0x9→0x1 as slots are pulled and the index `loc_3d` stepping 0x1→0x2. It reads that slot's byte `n = loc_600+loc_3d` and skips slots that are empty or out of range (`n == 0` or `n >= 0x09`). For an in-range slot it derives the paired value `loc_602` by scaling and inverting the byte — `a = (n<<1)+n`, then `a ^= 0xff`, then `a -= 0xe5` — seeds `loc_605=0x60`, `loc_4e=0x00`, `loc_50=0x00`, `loc_604=0x02`, arms two subsystems by calling `loc_ca48` (which sets bit 2 of flag `loc_a1` and its paired count `loc_b4` from the gates `loc_117`/`loc_3d`) and the per-slot reset `loc_a789`, then writes the armed status `loc_0 = 0x24` and returns. So one call finds the first valid pending slot, builds its scaled parameter, and hands the freshly-zeroed slot table to the rest of the machine.

### Geometry-rebuild chain: `loc_ac20` and `loc_abac`

The final pair keeps the drawn tube in sync with the operator option switches. `loc_ac20` [code] refreshes the live control snapshot by running `loc_d6bb` — the option-switch decoder that reads the switch ports `loc_e00`/`loc_d00` and folds them into config cells including `loc_a` and `loc_16a` — then compares the fresh state against the cached targets: `(loc_a & 0xf8) == loc_71e` and `(loc_16a & 0x03) == loc_71f`. On a match it takes the no-op return; on a mismatch it calls `loc_ac36`, which ORs `0x03` into `loc_1c9`, raising the two pending-rebuild request bits. In this capture only the match (no-rebuild) path fired, since the switch state was fixed, so the mismatch branch rests on the code.

`loc_abac` [code] is the rebuild driver that consumes those bits. It first runs `loc_ac20` to refresh the edge state, writes `loc_100 = 0x08`, and — when all three sources `loc_71b | loc_71c | loc_71d` are idle — forces both request bits via `loc_ac36`. It then reads `loc_1c9`: bit 0 selects a copy length of 0x17 (else 0x0e) and copies that many bytes from the template `loc_ac08+x` into the block at `loc_606+x`; bit 1 selects a fill length of 0x17 (else 0x0e) and fills `loc_706+x` with `0x01`. If either request bit was set (`loc_1c9 & 0x03`), it latches the current snapshot into the caches `loc_71e = loc_a & 0xf8` and `loc_71f = loc_16a & 0x03`, so the next `loc_ac20` comparison sees the new geometry as current. Finally it clears the two request bits (`loc_1c9 &= 0xfc`). Its own writes are present but constant here because the switch state did not change, so the branching role again rests on the code. Together the pair form a request-then-service loop: `loc_ac20` notices when the switch-derived tube geometry has drifted from the cached target and raises a flag, and `loc_abac` rebuilds the two control-block regions from the template and re-latches the cache.

## Utilities and shared tails

This section gathers the small, self-contained helpers that other routines lean on for arithmetic conversions, byte-field unpacking, table maintenance, and the bare return points where callers land when there is nothing to do. Several of them are leaves with no game state of their own; their role is defined entirely by what the machine asks of them.

**loc_aaf5 — binary-to-BCD conversion.** This is a classic double-dabble converter [seen], heavily exercised. It takes the byte in the accumulator and runs eight passes: each pass shifts the source byte left by one, capturing the bit that falls out of the top, and doubles a decimal-mode accumulator while folding that carried bit in (the low-nibble and high-nibble halves each add to themselves plus the incoming carry, with the +6 / +0x60 decimal corrections applied when a nibble overruns 9). The finished packed-BCD result is written to both `loc_29` and `loc_2c` and returned. The write-tap confirms the role: both `loc_29` and `loc_2c` fill with BCD digits ranging 0x00..0x99, matching the two-digit output of the loop. Its caller `loc_af77` runs it and then performs a single-byte store of the converted value, so the routine's job is to turn a raw binary count (a score fragment or similar tally) into displayable decimal digits.

**loc_93e0 — split a byte into a fine value and a coarse index.** Reached [seen] exclusively through the three call sites inside `loc_92c5` (0x9387 / 0x9396 / 0x93a4). It partitions its input byte into several register outputs at once. First it folds the input's top three bits, most-significant first, into the low bits of a seed that begins as 0xff, so the seed ends as `0xf8 | top3` — this is stashed at scratch `loc_29` and also handed back as Y. Meanwhile the accumulator is left holding the input shifted left three times, i.e. `(input & 0x1f) << 3`, the "fine" fractional value. The X output is derived from the seed's complement: `X = ((seed ^ 0xff) + 0x0d) >> 1`, which simplifies to `(0x14 - top3) >> 1` — a coarse index that shrinks as the top three bits grow. Its only memory write is the `loc_29` scratch, so it is grounded as a compute helper whose three live-out registers are consumed by `loc_92c5`'s vector/coordinate work. (Note: the grounded-roles file's coarse-index range does not match the arithmetic in the code above; the formula quoted here is what the routine computes.)

**loc_92b2 — swap a parallel table pair.** A leaf [code] that walks an index from 0x11 down to 0 (eighteen entries) and, for each slot, exchanges the byte in `loc_3aa` with the byte in `loc_3bc`, so the two 18-entry tables trade contents slot-for-slot. The two swap stores never fired in the capture, so it is not reached; the effect is readable from the code but its place in the game — presumably rotating between a live copy and a shadow copy of some per-slot geometry array — cannot be confirmed here, and the tag stays honest at [code].

**loc_b85f — seed the paired triple-entry arrays.** Straight-line [code] initializer that writes the fixed triple 0x00, 0x04, 0x0c into `loc_22 / loc_23 / loc_24` and mirrors the same three values into `loc_809 / loc_80a / loc_80b`. Two three-entry arrays are seeded identically, one in zero page and one in its 0x0800 mirror. No writes were observed in the capture, so the routine went unexercised across attract, coin, start, and play, and its game role is left unconfirmed at [code].

**loc_b955 — return the constant pair.** A register-only leaf [code] flagged as a proposer trap. The underlying routine reads `loc_57`, right-shifts it, and runs an iny/lsr/bne bit-counting loop — but the loop's result is thrown away: the final `clc / adc #2` starts from zero, so the accumulator always comes out as 2, and Y is reset to 0. It therefore *always* returns the pair (A = 2, Y = 0) regardless of `loc_57`. The idiomatic form collapses this to the constant return it actually is; a blind reading might mis-name it as a log2 or bit-count of `loc_57`, but the code discards that computation entirely.

**loc_ac36 — request both block rebuilds.** This helper [seen] ORs 0x03 into `loc_1c9`, setting the two low pending-rebuild request bits, and returns the merged value. The write is observed at its own body (`loc_1c9` taking a value with bits 0–1 present). Its callers raise the request through this routine — `loc_ac20` when a live-state comparison detects a mismatch, and `loc_abac` — after which the downstream rebuild logic reads and drains those two bits (one governs one display block, the other its sibling). The routine's whole job is to stamp the "both blocks need rebuilding" request into the shared `loc_1c9` flag word.

**The shared no-op return tails.** Four routines are bare return leaves [code] — they touch no memory and simply hand control back — but each occupies a distinct exit point in the machine, so they are named by where callers land rather than by any effect. `loc_9bcf` is a do-nothing handler slot in a computed-dispatch table: when the dispatch resolves to it, it returns at once and lets the caller's own return unwind, a deliberate empty entry. `loc_ac07` is the exit `loc_aba2` branches to when `loc_1c9 & 3 == 0` — the nothing-to-rebuild path, the counterpart to the request `loc_ac36` sets. `loc_ac3e` is a shared return tail that `loc_ac20` falls to when the live geometry snapshot (`loc_0a & 0xf8` versus the cached `loc_71e`, and `loc_16a & 3` versus `loc_71f`) already matches the latch, meaning no rebuild is needed. `loc_af6e` is the exposed return tail of the `loc_af3f` draw routine, reached when `loc_af26` finds both draw slots empty (`loc_600 | loc_601 == 0`) and there is nothing to draw. None of the four has a role-defining write to ground, so all four keep the [code] tag; together they mark the "nothing to do" fall-throughs of the rebuild-request and draw machinery that `loc_ac36` feeds.
