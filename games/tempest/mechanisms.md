# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
object-record draw loop, the mathbox projection, sound, and the EAROM — down to the caller routines that
drive them and the first computed-jump dispatcher; the frozen-oracle remainder (the dispatcher spine and
two register-thread callers) is noted at the end. The machine is a colour vector game: the 6502 builds a
display list in AVG vector RAM (`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with
the vblank interrupt as the per-frame heartbeat and a game-state index driving a computed-jump dispatch
that selects the mode handler (attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each active object on the web runs a little bytecode program that steers it frame to frame, and this cluster of handlers is that bytecode's instruction set. The programs live in the table based at `loc_a0f7`, and the driver that runs them walks every populated slot: for each slot whose depth cell `loc_2df,x` is nonzero it loads that slot's saved program cursor from `$0291,x` into the shared instruction pointer `loc_10b`, raises the continuation flag `loc_10a` to 1, then repeatedly fetches the script byte `loc_a0f7[loc_10b]`, treats it as an opcode, dispatches to the matching handler here, advances `loc_10b`, and keeps looping so long as `loc_10a` stays nonzero — writing the final `loc_10b` back to `$0291,x` when the object's turn ends. So `loc_10b` is the program cursor, `loc_10c` is the single-bit test/branch flag the compare opcodes set and the conditional opcodes read, and `loc_10a` is the run/halt latch. The handlers below are those opcodes; the driver's `loc_a0f8` reload table sits one byte past `loc_a0f7`, so an index into it reads the operand byte trailing the indexed opcode.

The two store opcodes plant a value into the object's own working cell `loc_298,x`. `loc_9bd0` [seen] is the immediate store: it bumps the cursor once (`loc_10b = (loc_10b + 1) & 0xff`) and copies the byte now under the cursor, `loc_a0f7[loc_10b]`, straight into `loc_298,x` — the write lands on `$029b`..`$029e` for the slots exercised, with the cursor's own pre-copy increment observed advancing. `loc_9bdd` [seen] is its indirect twin: it advances `loc_10b`, but the script byte it fetches is used as a zero-page address rather than a literal — it reads `loc_00 + ptr` (the live variable that address names) and stores *that* into `loc_298,x`. Immediate loads a constant into the object; indirect wires the object's cell to a running variable.

The conditional opcodes both consult the test flag `loc_10c` and skip or divert only when it is clear. `loc_9bee` [seen] is the conditional two-byte skip: if `loc_10c != 0` it does nothing (falling through to the following opcode), otherwise it steps `loc_10b` forward by two (`u8`-wrapped), hopping past a two-byte operand — both increments were seen changing. `loc_9bfa` [seen] is the conditional jump: it first advances `loc_10b` by one, then if `loc_10c != 0` simply continues, but if the flag is clear it reloads `loc_10b` from `loc_a0f7[loc_10b]`, taking the branch to the operand's target address — both the pre-branch advance and the table reload were observed. `loc_9c17` [seen] is the unconditional goto and is exercised heavily: it sets `loc_10b = loc_a0f8[loc_10b]`, i.e. jumps the cursor to the operand byte that trails the current opcode; it doubles as the loop-back tail of the timer opcode below.

`loc_9c0c` [seen] is the dwell/timer opcode and runs on essentially every pass. It counts the object's cell `loc_298,x` down by one; while that counter is still nonzero it delegates to `loc_9c17` to take the state-step reload through `loc_a0f8` and returns, holding the object on the current step; only when the counter reaches zero does it bump `loc_10b` to release the program onto the next opcode. So an object parks on a script step for as many frames as its `loc_298,x` cell holds, then moves on.

The two compare opcodes produce the test flag but were not reached in the capture. `loc_9c21` [code] is the boundary test: it reads the slot's lane/segment from `loc_2b9,x`, looks up that segment's boundary in `loc_3ac[segment]` — where a stored zero is read as the maximum `0xff` — and sets `loc_10c = 1` when the boundary is at or beyond the object's depth `loc_2df,x`, else `0`; its store to `loc_10c` is absent from the trace (the flag was produced by another site, `pc 0x9e2b`, during the captured window), so it stands [code] rather than [seen] — not reached in the capture. `loc_9c3b` [code] is the phase test over the accumulator pair `loc_147`/`loc_148`: it forms `((loc_147 << 2) + loc_148) & loc_148 & 0x80`, then XORs that high bit with `0x80`, yielding `loc_10c = 0x00` when the resulting bit-7 is set and `0x80` when it is clear (all arithmetic byte-wrapped); `loc_148` is the signed phase accumulator the driver's tail advances by `loc_147`. Its store to `loc_10c` at `pc 0x9c4e` never appears in the trace — not reached in the capture.

`loc_9bca` [seen] is the halt opcode: a leaf that writes zero to `loc_10a`. Because the driver runs the inner script loop only while `loc_10a != 0`, clearing it here ends the object's script turn for this frame and lets the driver store the cursor back and move to the next slot.

Finally, `loc_96c7` [code] is a list-cursor skip that lives on a *different* dispatch path — the `$969d` computed table reached through `loc_9683`'s RTS-dispatch on `$015e`, not the `loc_a0f7` opcode stream. It advances the packed-record cursor held in register Y without reading the record: entry `loc_96c7` steps Y forward by three (it hands off to the second entry with Y already bumped by one), and entry `loc_96c8` steps Y forward by two. It is register-only with no memory write of its own, so there is nothing to observe — not reached in the capture, and reachable only through that computed jump.

## Vector coordinate lists and the display cursor

Tempest paints its tube, enemies and text on a color vector monitor whose Analog Vector Generator reads a display list out of vector RAM. This subsystem is the machinery on both sides of that list: a moving write cursor that the emitters push words into, and a family of coordinate-list walkers that chase packed point tables in ROM to compute the numbers those words carry.

### The write cursor

Every producer appends to the display list through a single little-endian write pointer held in the `loc_74`/`loc_75` pair. `loc_df5f` [seen] is the one routine that moves it: it takes a stride in the caller's index register, forms `loc_74 + stride + 1` (the ROM sets carry before the add, so the constant `+1` is always folded in), writes the low byte back to `loc_74`, and on overflow bumps the high byte `loc_75`. So a call advertising a stride of *n* walks the cursor forward by *n+1* bytes, past whatever was just written. This is the most heavily exercised routine in the group — essentially every vector word emitted anywhere in the game ends by advancing here — and the cursor is observed sweeping across the vector-RAM page (`loc_74` pulsing over its full 0x00–0xfe range, `loc_75` climbing through the mid-$20s), which is the AVG display list being rebuilt frame after frame.

### The low-level word emitters

The atomic store is the two-byte tail shared by `loc_df57` and `loc_df59`. `loc_df59` [seen] is the general form: given a pair `{A, X}` and an offset `y`, it stores `A` at cursor+`y` and `X` at cursor+`y+1`, then hands `y+1` to `loc_df5f`, so the cursor lands `y+2` bytes on. `loc_df57` is the fixed-origin form of that same store — it writes `A` at the cursor origin (offset 0) and `X` at offset 1, then advances by two; it is reached [seen] under the header path below, since that path is `loc_df57` with its arguments preset. `loc_df53` [seen] is exactly that preset: it loads the fixed header word `{0x40, 0x80}` and drops into the shared store, emitting the two header bytes and stepping the cursor past them. The observed emit stream carries that 0x40/0x80 pair into vector RAM as expected.

Two more emitters translate a nibble into a word pulled from the ROM word-table at `loc_31e4`. `loc_df19` [seen] takes an accumulator value and picks a table index from its low nibble — index 0 when carry is set and the nibble is zero, otherwise nibble+1 — doubles it to a word offset, copies both bytes of `loc_31e4[index]` to the cursor, and advances two. `loc_df1f` [seen] is the plainer sibling: it forms the index directly as `(A & 0x0f) + 1` and shares the identical copy-and-advance tail, so it never takes the special index-0 case. The bytes these copy are real AVG opcode words landing in the $2000-page vector RAM.

A second body-byte path exists but the game does not drive it here. `loc_df12` [code] stores a single input byte at the cursor origin and then continues into the shared record tail at `loc_dfac`; it is reached in the capture only through the `loc_df09` entry, which presets the byte to a constant 0xc0, so its emit is real but single-valued and its role rests on the code rather than on varied output. `loc_df0d` [code] would drive the same body path with a fixed 0x20 after first laying down a `loc_df53` header, but it is not reached in the capture at all.

### The compound producers

Above the atomic emitters sit two routines that lay whole records into the list. `loc_c772`/`loc_c774` [seen] is the object-position producer, `loc_c772` being the entry that starts the offset at zero. It writes the `{0x40, 0x80}` header, then an X coordinate word taken from the `loc_2`/`loc_3` zero-page pair indexed by the object slot in X, then a Y coordinate word from the `loc_00`/`loc_1` pair. The two high bytes are each masked to five bits (`& 0x1f`) before being stored, while the raw unmasked bytes are cached into `loc_6c`/`loc_6d` (X lo/hi) and `loc_6a`/`loc_6b` (Y lo/hi) as the previous point that later stroke-delta work reads back. Six bytes go down and the cursor advances past all of them. This producer is heavily reached — object positions are re-emitted constantly.

`loc_aef8` [seen] is the text-glyph producer. It seeds a descending source index at `loc_38 = A + 2` with a three-entry counter in `loc_39`, then for each of three passes reads a character code from the `loc_606` buffer, clamps any code of 0x1e or higher down to 0x1a, doubles the code to index the glyph word-table at `loc_31fa`, and copies that two-byte glyph word to the cursor. After three glyph words (six bytes) it steps the cursor past them. The observed stores carry glyph words with the vector-draw high byte into the display RAM, so this is the path that turns the on-screen score and message buffer into vectors.

### The coordinate-list walkers

The other half of the subsystem does not touch the cursor at all; it computes coordinate values by chasing packed point lists in ROM through the `loc_2c`/`loc_2d` indirect pointer, leaving results in A for a caller to emit. Two routines arm that pointer. `loc_9aee` [seen] selects a list: indexed by Y it loads the low pointer byte from the ROM table at `loc_9b02` into `loc_2c` and the high byte from `loc_9afd` into `loc_2d`, stashes the selecting index into `loc_2b`, and reloads A from the holding cell `loc_29`. `loc_9a9d` [code] is the fixed-index seed used for the demo/attract list: it takes the low byte from `loc_9b02` at index zero, marks the index `loc_2b` as zero, takes the high byte from the held cell `loc_15d` rather than the ROM hi-table, and likewise reloads A from `loc_29`.

With the pointer armed, `loc_96cb` [seen] walks it one step: it reads the list entry at the cursor and its immediate predecessor, stores their difference into `loc_29` as the inter-entry step delta, and advances the cursor index by that delta plus two. The delta cell is observed taking the small step values (0x01 through 0x0f) that real neighbouring coordinate entries produce. `loc_96db` [code] is the value resolver: it reads the entry at the pointer offset and adds the base held in `loc_160`, returning the absolute coordinate in A; it is a pure compute leaf reached only through a computed dispatch, so its role rests on the code.

`loc_96ab` [seen] and its siblings are the re-indexing coordinate helper. `loc_96ab` enters with an accumulator of `((loc_2b - 1) & 0x0f) + 1` and `loc_96b7` with the raw index cell `loc_2b`; the shared body first stashes the incoming Y into `loc_29`, subtracts the list entry two slots back (at offset `y-2`) from that accumulator, adds `loc_29` back in, and then re-indexes the list by the result — returning the entry it lands on in A and that same result in Y. `loc_96c4` is the trivial form that simply fetches the entry at the current offset. The only own write is the `loc_29` scratch, and the routine is reached with its output consumed by the coordinate generator downstream.

Finally, two routines fold a run of entries into a single byte. `loc_96f4` [code] is the count/head computation shared with the helper above: it records Y into `loc_29` and returns `loc_2b` minus the list entry two slots back — the value that serves as a repeat count. `loc_96e2` [code] uses it: it takes that count, loads the entry the cursor points at as the running sum, and then folds in `count` further copies of the next entry (the entry at offset `y+1`, re-read each pass), accumulating into a single wrapped byte. Both are compute-only, leaving no role-defining write, so they carry the code-level tag.

## Draw-pointer setup and vector emission

Everything the game puts on the tube is built by writing byte pairs into the analog vector generator's display RAM at `loc_2000`..`0x2fff`. The write address is never a fixed location: it is held in a little-endian indirect cursor in zero page — chiefly `loc_74`/`loc_75`, with a companion pair `loc_76`/`loc_77`, plus the alternate pointers `loc_3b`/`loc_3c` and `loc_2a`/`loc_2b` used for the glyph-list buffer at `loc_2f60`. A separate byte, `loc_a9`, is the running offset (in bytes) into the record currently being laid down through `(loc_74)`. This subsystem is the collection of routines that (a) point those cursors at the right place and (b) push formatted vector words out through them.

### Pointing the cursor

`loc_b2be` is the per-subsystem draw-pointer setup [seen]. Given a selector in A it reads the per-index flag at `loc_415`+A: when that flag is non-zero it takes the pointer table `loc_ce68`, and when it is zero it takes `loc_ce7a`; it fetches the 16-bit little-endian entry at stride 2×A, publishes the low byte to `loc_74` and the high byte to `loc_75`, and clears `loc_a9` so the next emit starts at offset zero. The write-tap sees `loc_74`/`loc_75` pulsed across their whole range with real pointer values, confirming this as the live cursor producer. `loc_b2de` is the twin that aims the *other* pointer pair `loc_3b`/`loc_3c`, and note the table selection is the mirror image of `loc_b2be`: here a non-zero `loc_415`+idx flag selects `loc_ce7a` and a zero flag selects `loc_ce68` [seen], again clearing `loc_a9`. `loc_91b5` builds the `loc_2a`/`loc_2b` working pointer instead [seen]: it doubles its selector into a word index, zeroes the paired flag `loc_29`, and copies the little-endian pointer from the in-page table at `loc_91c6`/`loc_91c7` into `loc_2a`/`loc_2b`.

Two helpers reshuffle the cursor pair rather than reload it. `loc_b944` swaps the whole 16-bit `loc_74`/`loc_75` pointer with `loc_76`/`loc_77`, so the shared emitters address the other structure [code]; `loc_b967` chooses an (A,X) pair from ROM — `loc_ce87`/`loc_ce86` when `loc_415` is zero, otherwise `loc_ce6f`/`loc_ce6e` [code]. Both are consumed only by the object-draw loop `loc_b8ba`, which did not run in this capture; the flag `loc_415` itself is exercised, but neither routine's own body executed, so their roles rest on the code.

`loc_b332` sits between setup and emit [seen]. It compares a source byte at `loc_cec4` against the checkpoint held in the first vector-RAM byte `loc_2000`: if they differ it latches the new value into `loc_2000` and returns carry set, the signal to its caller that the frame changed and the list must be rebuilt. Otherwise it emits a two-byte record through `(loc_74)` — the record slot index is 0x08 when `loc_415` is non-zero and 0x02 when zero, sourced from `loc_ce9e`+slot — clears `loc_16e`, then reloads the cursor `loc_74`/`loc_75` from `loc_ce68`+slot and returns carry clear.

### The low-level vector-word emitters

The primitive that every list-builder funnels through is `loc_df59` [seen]: it stores the pair {A, X} at `(loc_74)`+Y and +Y+1, then steps the cursor past them via `loc_df5f`. `loc_df5f` advances the little-endian cursor by its argument plus one, carrying into `loc_75` on overflow — this "+1" is why callers pass the last-written offset rather than a length. `loc_df57` is the same store aimed at the cursor origin (offset 0), and its sibling entry `loc_df53` calls it with the fixed header pair {0x40, 0x80}. `loc_ab0d` is another fixed-pair front onto that shared tail, emitting the constant word {0x20, 0x80} [code].

A family of one-line fronts tag a payload with the vector generator's opcode bits before handing to `loc_df57`. `loc_df4c` emits {Y, A | 0x60}; `loc_df6c` emits {Y, A | 0x70} [both code]. `loc_df4a` calls `loc_df4c` using the key byte `loc_73` as the payload's Y [code], and `loc_df6a` calls `loc_df6c` with a zero data byte [code]. `loc_df39` builds a coordinate word directly [code]: the high byte is A shifted right one with its low nibble kept and OR'd with 0xa0 (bits 4..1 of A, not the upper nibble), and the low byte is A's bit0 rotated up into bit7 above X shifted right — it writes the high byte at cursor+1 and the low byte at cursor+0, then advances (falling back to a `loc_df4c` emit only if the offset wraps to zero, which it does not on the normal path).

`loc_df12` stores a single body byte at the cursor origin `mem16[loc_74]` and continues the shared record tail through `loc_dfac` [code]; `loc_df09` is the front that presets that body byte to 0xc0 and enters `loc_df12` [code]. `loc_df12` is reached only through the `loc_df09` path and emits that constant 0xc0, so its role stands on the code rather than on a varying observed write; the companion `loc_df0d`, which lays the {0x40,0x80} header then a 0x20 body byte, did not run. `loc_dfac` is the shared record tail: it stores one more byte at cursor+(Y+1), and if that offset is non-zero it advances the cursor by Y+2, otherwise it drops into the digit-run emitter `loc_dfb1` as a terminator.

`loc_c772` lays a complete six-byte draw-record header through `(loc_74)`: the fixed word {0x40, 0x80}, then two coordinate words taken from the zero-page pairs at `loc_2`/`loc_3`+X and `loc_00`/`loc_1`+X (each high byte clamped to five bits), caching the raw bytes into `loc_6a`..`loc_6d`, and advancing past all six. `loc_c765` is the alternate entry [seen]: it first writes the fixed {0x00, 0x71} header word at cursor offsets 0 and 1, then resumes the same build from offset 2. `loc_b56a` appends a minimal four-byte list entry — 0, 0, 0, A — at `(loc_74)` and advances the cursor by four [seen]; the observed fourth byte comes from its caller and the cursor is seen walking the whole `0x22f4`..`0x2b67` span.

`loc_b896` writes the vector-list *tail* record [code]: it stores the 16-bit cursor `loc_139`/`loc_13a` into vector RAM as `loc_2ffc` (low, raw), `loc_2ffd` (high, OR 0x70), and `loc_2fff` = 0xc0 (the terminator), then steps that cursor down by 0x20 with a 16-bit borrow into `loc_13a` and masks `loc_139` to 0x7f. It was not reached in the capture; it is reachable only through the computed dispatcher `loc_b84e`, which selects one of four draw-pointer targets — `loc_b85f`, `loc_b875`, `loc_b888`, `loc_b896` — by the caller-supplied offset (Y>>1) into a two-byte-per-entry table [code].

### Coordinate and delta records

Above the primitives sit the routines that assemble a coordinate record and push it. `loc_df92` emits a four-byte record from four zero-page slots based off index X — the byte at `loc_2`+X raw, `loc_3`+X clamped to five bits, `loc_0`+X raw, and `loc_1`+X folded through the key byte `loc_73` down to five bits — then finishes through `loc_dfac` [seen]. `loc_df75` is the scaler that feeds it [seen]: it widens its two inputs by four with sign extension into the little-endian pairs `loc_6e`/`loc_6f` and `loc_70`/`loc_71` (bit7 of the input fills the high byte, so a negative input scales to a 0xFFxx pair), then emits via `loc_df92`. `loc_df73` merely stashes its index byte into the key `loc_73` before scaling through `loc_df75` [code].

`loc_c3ba` computes two 16-bit differences, current minus previous — `loc_61`/`loc_62` minus `loc_6a`/`loc_6b` into `loc_6e`/`loc_6f`, and `loc_63`/`loc_64` minus `loc_6c`/`loc_6d` into `loc_70`/`loc_71`, each with borrow — emits them through `loc_df92`, then latches the current values into the previous slots and sets `loc_73` to 0xc0 [seen]. `loc_c423` is its front [seen]: from slot index `loc_37` it snapshots four indexed table cells (`loc_32a`, `loc_31a`, `loc_34a`, `loc_33a`)+X into `loc_61`..`loc_64` and then runs `loc_c3ba`. `loc_c43c` fills the same working block from a different set of parallel object tables (`loc_36a`, `loc_35a`, `loc_38a`, `loc_37a`)+`loc_37` [seen], the attribute-gather that precedes a delta emit.

`loc_c73c` emits two 16-bit differences straight through `(loc_74)` at the running offset `loc_a9`: first `loc_63`/`loc_64` minus `loc_6c`/`loc_6d`, then `loc_61`/`loc_62` minus `loc_6a`/`loc_6b`; each difference's high byte is kept to five bits, and the second high byte is additionally OR'd with 0xa0 (the vector-generator opcode), with the cursor advancing four [seen]. `loc_c66d` produces a midpoint vertex [seen]: it round-up-averages slot `loc_38`'s two 16-bit coordinate pairs (`loc_36a`/`loc_35a` and `loc_38a`/`loc_37a`) with those of its wrap-around neighbour (`loc_38`+1 & 0x0f), stashes the two midpoints into `loc_61`..`loc_64`, appends the four midpoint bytes through `(loc_74)` at `loc_a9` with high bytes masked to 0x1f, and mirrors all four into the scratch pairs `loc_6a`..`loc_6d`.

### The math-box normalized appender

`loc_bd3e` appends a (mantissa, exponent) pair and is the point where the hardware math unit is used [seen]. For a small input (`loc_57` < 0x10) it emits the trivial pair (A=1, Y=0). Otherwise it forms a 16-bit difference into the coprocessor operands `loc_6095`/`loc_6096` — the minuend is `loc_57` as a low byte with a zero high byte, and the subtrahend is the 16-bit pair `loc_5b`:`loc_5f` (`loc_6095 = loc_57 - loc_5f`, `loc_6096 = 0 - loc_5b - borrow`) — issues the operation via `loc_608c`=0x18 and `loc_608e`/`loc_6094`=`loc_a0`, spins until `loc_6040` bit7 clears, reads the result `loc_6060`/`loc_6070` into `loc_79`/`loc_7a`, then normalizes: it rotates `loc_79` left while shifting A until a one rolls out of the top, giving a mantissa shift count and an exponent, stores the shift count in `loc_78`, and writes the pair {exponent, mantissa | 0x70} at `(loc_74)`+`loc_a9`. Its exit convergence leaves the cursor offset at `loc_a9`+2, which its callers persist and reuse.

`loc_bd09` drives that appender for a colored vertex [seen]: it folds live deltas (`loc_c098`), lays the {0x00,0x71} header (`loc_c765` at X=0x61), zeroes `loc_a9`, appends the pair via `loc_bd3e`, then clamps the color/intensity nibble (`loc_78` XOR 0x07, shifted up, floored at 0x0a, moved to the high nibble), emits that plus a 0x60 byte at the threaded cursor, and tails into `loc_df59` with an entry-template word read from `loc_cec8`/`loc_cec9`[`loc_55`]. `loc_bcfd` is its seat-and-emit front [seen]: it stashes A into `loc_55`, loads two indexed table entries (`loc_435`+Y, `loc_445`+Y) into `loc_56`/`loc_58`, then runs `loc_bd09`. Three thin marshallers feed `loc_bcfd`: `loc_b60f` picks a jump-mode byte from `loc_b61e` indexed by the low two bits of the slot flag `loc_28a`+X (that flag byte carries the arm/sign bits — it is not a coordinate) and pairs it with the slot target `loc_2b9`+X [code]; `loc_b622` pairs the slot target with a four-phase animation offset ((`loc_3`&3)<<1)+0x12 [code]; and `loc_b75b` walks the twelve slots high-to-low, emitting each non-empty entry from `loc_2d3`+X — near slots (X≥8) taking a phase-derived value, far slots a fixed 0x08 — and finally latches a level byte into `loc_808` chosen from the stage value `loc_135` [seen].

`loc_b69b` builds a slot's screen position and tails into the emitter [code]: it seats the slot coordinate `loc_2df`+X and the segment-indexed base pair (`loc_3ce`/`loc_3de`+segment), and when the phase byte `loc_2cc`+X is negative it interpolates toward the next segment by scaling the delta through `loc_b6fa`; it folds deltas, lays the header, appends the pair via `loc_bd3e` threading the returned cursor, and emits the frame-indexed template word through `loc_df59`. It was not reached in the capture. `loc_c6c7` is the enemy-slot vector entry [seen]: for an inactive slot (`loc_3ac`+`loc_38` == 0) it appends four blank+0x71 pairs; for an active slot it seats `loc_57` from `loc_3ac`+X, runs the depth clamp `loc_c453`, seats `loc_56`/`loc_58` from `loc_435`/`loc_445`+X, runs the math-box delta pass `loc_c098` and the delta emit `loc_c73c`, then — depending on bit6 of `loc_39a`[`loc_38`] — either drives `loc_bd3e` and appends a randomly selected word (`loc_60ca`&0x02 offsets into `loc_cec8`/`loc_cec9`) or lays the fixed marker word {0x00, 0x68, `loc_3db2`, `loc_3db3`}. `loc_c36e` is a gated record-draw loop [seen]: unless its gate byte is set it seats four fields from `loc_31a`/`loc_32a`/`loc_33a`/`loc_34a`[Y], emits the header via `loc_c772`, caches the cursor into `loc_b0`/`loc_b1`, sets `loc_73`=0xc0, and draws one record per pass through `loc_c423`, decrementing the slot index `loc_37` and bumping it by 0x10 whenever its low nibble saturates, seeding that index at 0x0e or 0x0f depending on `loc_111` and running one pass per step until it underflows.

### Glyph and digit runs

## Enemy spawning and lane selection

Enemies live in a bank of parallel per-slot arrays indexed by a slot number. The core columns are the tube depth `loc_2df` (a full byte; low values sit near the player's rim, high values are far down the well), the segment/column index `loc_2b9` (masked to `0..0x0f`, the position around the tube's sixteen segments), the successor/heading field `loc_2cc`, a spawn/refire timer `loc_2a6`, the flag/arm byte `loc_28a` (bit6 = armed, bit7 = sign) and a second flag byte `loc_283` (low three bits select segment behaviour, bit6 gates a step, bit7 forced on when stepped). Around these sit per-lane and per-column bookkeeping (`loc_142` lane occupancy, `loc_3ac` per-column nearest depth, `loc_39a` a per-column tag) and a separate eight-slot object table (`loc_2fa`/`loc_302`/`loc_30a`/`loc_312`). Spawning proceeds by choosing a lane, allocating and seeding a slot, then repeatedly picking a target segment and stepping toward the rim.

**Wave tag seeding.** `loc_9246` [seen] runs at wave setup off the init chain. It first clears the 64-byte tag table `loc_243`..`loc_282` to zero (the loop counts `x` from `0x3f` down through 0), then walks the active slots from `loc_3ab - 1` down to 0. For each slot it draws a four-bit POKEY random `loc_60ca & 0x0f` into `loc_203+x`, and packs the slot index with that nibble as `(x << 4) | nibble` into `loc_243+x`, substituting `0x0f` whenever the packed value would be zero so no slot carries a null tag. Both the raw-nibble table `loc_203` and the packed-tag table `loc_243` are observed filling with these random values, which is why the routine is grounded.

**Candidate lane selection.** `loc_9abb` [seen] chooses which lane a new enemy will occupy. It seeds a wrapping index `y` from a POKEY random `loc_60ca & 0x03`, primes a four-count countdown in `loc_2b` (the value `0x04`), and stashes the caller's X into `loc_39`. Each iteration decrements the `loc_2b` countdown and returns 0 if it underflows (bit7 set — no lane qualified); otherwise it steps `y` back one, wrapping to `0x03` when it underflows, reads a candidate lane from the four-entry table `loc_149+y`, remaps the value `0x03` to `0x05`, and accepts the first candidate whose lane-occupancy entry `loc_13c+idx` is non-zero. On a hit it builds the armed flag `a = loc_149[y] | 0x40` (bit6 set) into `loc_2c`, then loads a list-hi byte `loc_9afd[2]` into `loc_2d`, leaves the countdown holding `0x02`, and returns `loc_29`. The own-body writes observed are the `loc_2b` countdown stepping (e.g. `0x04`→`0x03`) and the X stash into `loc_39`. The two products it leaves behind — the armed flag in `loc_2c` and the list-hi in `loc_2d` — are exactly the scratch cells the slot allocator consumes next.

**Slot allocation and seeding.** `loc_994d` [seen] takes a free slot and populates it. It saves Y into `loc_36`, then scans the depth table `loc_2df` starting at the index in `loc_11c` and walking down; an entry of 0 is free, and if the scan runs past index 0 (Y goes negative, bit7 set) it reports 0 for "no slot free." **Target-segment choice by deepest column.** `loc_a028` [code] selects a fresh target segment for a slot by hunting the deepest column. **Per-slot approach step.** `loc_9fc4` [seen] advances one slot toward the rim and maintains the per-column nearest-depth table. ## Enemy motion and the pursuit AI

This subsystem drives the things that climb the tube: it carries each enemy slot's position and velocity forward every frame, steers a flipper's lane-to-lane hops toward the player, and offers an auto-aim that turns the Blaster onto whatever is nearest. Two independent per-slot arrays live here. One is the free three-axis motion set keyed off `loc_283` (sixteen slots, `x = 0x0f..0`); the other is the twelve-slot object array keyed off `loc_2d3`. Across both, an enemy's place in the tube is described by three cooperating per-slot cells: `loc_2df` holds its depth along the well (large = far end, small = near the rim), `loc_2b9` holds its segment/lane index around the rim (0..15 on a closed ring), and `loc_2cc` holds a phase/animation counter that paces the turn between lanes. `loc_283` is the slot's state-and-flags byte — its low three bits are a kind/state code, bit 6 is the travel-direction flag, bit 7 marks the slot live, and a zero byte means the slot is free.

### Free three-axis integration and deceleration

The population manager `loc_a618` [code] walks the sixteen slots once per frame from high index to low. It first mirrors the spawn countdown `loc_10e` into the frame-active latch `loc_10d`. For a live slot (`loc_283,x != 0`) it integrates that slot's motion with `loc_a6a9` and then decays its velocities with `loc_a721`, and stamps `loc_10d = 0xff` to record that something moved; for a free slot, and only while the countdown `loc_10e` is still nonzero, it spawns a fresh enemy with `loc_a65b`. It settles the slot counter `loc_37` to `0xff`, and on even frames (`loc_3` bit 0 clear) with budget remaining it ticks `loc_10e` down by one. If the whole pass found nothing live and spawned nothing (`loc_10d` still 0) it raises the mode-request byte `loc_0 = 0x12`, handing the wave back to the higher-level state machine.

`loc_a6a9` [code] does the actual position integration for one slot across three motion axes. Each axis folds a low/whole velocity pair into a fraction+whole coordinate: the fraction cell (`loc_223` / `loc_203` / `loc_243`) accumulates the velocity-low byte (`loc_2e3` / `loc_2c3` / `loc_303`) keeping the carry, and the whole coordinate (`loc_283` / `loc_263` / `loc_2a3`) then takes velocity-whole (`loc_343` / `loc_323` / `loc_363`, whose sign steers the direction) plus that carry. Each axis clamps to the tube ring: a rising axis (velocity-whole positive) overflows and resets when the whole reaches `0xf0` or beyond, a falling axis (velocity-whole bit 7 set) overflows and resets when the whole drops below `0x10`. The first axis's whole is written to the shared cell `loc_283,x` only at the end and is forced to zero if any of the three axes overflowed its ring — so an enemy that rides an axis past the tube edge frees its own slot.

`loc_a721` [code] is the companion deceleration step: it seeds the saturation counter `loc_29 = 0xfd` and calls `loc_a75d` on all three velocity pairs (`loc_2c3`/`loc_323`, then `loc_2e3`/`loc_343`, then `loc_303`/`loc_363`), storing each stepped low/whole back. If all three saturated — which drives `loc_29` up through zero — it zeroes the slot's whole coordinate `loc_283,x`, again freeing the slot once its motion has fully died. `loc_a75d` [code] itself steps one signed 16-bit velocity a single fixed increment toward zero: the increment is the constant `loc_a788` (0x20), added when the whole is negative and subtracted otherwise, and on crossing zero it saturates — bumping `loc_29`, forcing the low byte `loc_2a` to zero, and returning a zeroed pair. Both `loc_a721` and `loc_a75d` are held [code]: their per-slot write paths were not reached in the capture.

New enemies enter through `loc_a65b` [code], reached by `loc_a618` when a free slot has spawn budget. It marks the slot's three whole-coordinate cells (`loc_263`, `loc_283`, `loc_2a3`) at `0x80` — the ring centre — and fills the three velocity pairs from the two POKEY random registers: `loc_2c3` and `loc_323` from a `loc_60da` draw (the whole passed through the signed random step `loc_a69b`), `loc_2e3` and `loc_343` from a `loc_60ca` draw with its whole forced non-positive (already-negative kept, otherwise negated) so that axis always drives one way, and `loc_303` and `loc_363` from a second `loc_60ca` draw. It then rings the spawn sound cue `loc_ccc1`. `loc_a69b` [code] is the signed random magnitude it leans on: it reads the low three bits of `loc_60da` (0..7) and negates the result when the caller's incoming value has bit 0 set, yielding a nudge in [-7, +7]; it is a pure helper with no cell of its own, held [code] because `loc_a65b`'s write sites did not run in the capture.

### Segment pursuit — steering flippers toward the player

The rotational math all funnels through `loc_a7a6` [seen], which computes the signed distance from one segment to another (A minus Y) and stashes it at `loc_2a`. When the topology flag `loc_111` has its high bit set it keeps the full signed byte; otherwise it masks to the low nibble and sign-extends bit 3, giving the shorter signed distance around a closed sixteen-segment ring. That "which way is shorter" answer is what the pursuit routines use to decide which way an enemy should turn.

`loc_9d67` [code] applies it per slot: it takes the slot's segment `loc_2b9,x` and the player's rim segment `loc_200`, runs them through `loc_a7a6`, and then records the side the player lies on in bit 6 of the slot flag `loc_283,x` — clearing bit 6 when the difference is negative (top bit set) and setting it otherwise. `loc_9c4f` [seen] is the plain toggle of that same direction flag: it XORs bit 6 of `loc_283,x` in place and returns the new byte; its bit-6 flip of `loc_283` is observed changing in the capture.

`loc_9f81` [code] is the per-slot segment-flip driver. It first re-derives the slot's side bit with `loc_9d67`, toggles it with `loc_9c4f`, and then runs a shared tail: on a live board (`loc_111 != 0`) it may flip bit 6 again according to the slot's segment position `loc_2b9,x` — flipping when bit 6 is set and the position is 0, or when bit 6 is clear and the position has reached `0x0f` — so a flipper reverses at the ends of an open lane run. It writes the motion-script cursor `loc_10b = 0x66` and continues into the shared segment-step body `loc_9e5f`. Its sibling entry `loc_9f8a` reseeds bit 6 from a random bit (`loc_60ca` bit 6) instead of from the player's side before running the same tail. This routine is held [code], not reached in the capture.

`loc_9f5f` [code] is the fire/flip gate that decides when a slot is allowed to take one of those steps. It fires only when the slot's fire bit — bit 5 of `loc_2df,x` — is set and a fresh POKEY random draw `loc_60da` is at least the threshold `loc_15f`; failing either test it does nothing. When it does fire, the target flag `loc_159` bit 6 together with the slot's parity chooses the path: with `loc_159` bit 6 clear, or on an even slot, it takes the random-reseed step `loc_9f8a`; on an odd slot with the flag set it takes the player-seeking step `loc_9f81`. It is held [code], not reached in the capture.

The actual lane-hop animation lives in `loc_9d82` [seen]. It advances the slot's phase counter `loc_2cc,x` by one — counting down when the direction flag `loc_283` bit 6 is set, up otherwise — keeps the low nibble and forces bit 7. ## The per-slot object-record draw loop

This subsystem lays the frame's object records into the AVG vector display list (vector RAM 0x2000-0x2fff) through the loc_74/loc_75 cursor — not into the loc_2f60 glyph buffer, which is a separate path. Every record is written through that single 16-bit little-endian output cursor, and the shared record builders that follow all walk an object's point list through a list pointer read from a table based at (loc_ac), emitting the resulting vector words at the cursor. Working from the game's cast, these records are the on-screen objects — the enemies and the fixed rim/panel glyphs — each rendered from a compact index list into scaled coordinate pairs.

### The slot loop (loc_b8ba)

loc_b8ba [code] is the per-slot object-record draw loop, but it is not reached in the capture — no write anywhere in its body was observed, and the seeds to its own accumulator cells arrive only from other routines. ## Object-record projection and emission helpers

These routines are the machine's producers: each one reads game state, projects it into screen-space coordinate records, and lays those records into the vector-RAM write cursor held little-endian in `loc_74`/`loc_75`. They all draw against the same low-level emit family — `loc_df57` (store two bytes at the cursor origin and step it forward two), `loc_df4c`/`loc_df6c`/`loc_df6a` (store a payload byte plus a header-tagged byte, the header being `0x60`, `0x70`, or `0x70`-with-zero-data respectively), `loc_df39` (a rotated coordinate word), `loc_df75` (widen two values four-fold with sign extension into `loc_6e`..`loc_71` and emit), and `loc_df5f` (advance the cursor by a stride plus one). The projection helpers `loc_c098` (the math-box signed-delta engine), `loc_c765`/`loc_c772` (fixed header plus a coordinate pair from zeropage), and the object-render walkers `loc_ab14`/`loc_ab17` (copy indexed point pairs from the shape table at `loc_31e4` through a draw-list pointer) do the geometry these routines lean on.

`loc_b0d1` and `loc_b0dd` are the two "emit only on change" guards that keep the colour/mode word from being re-sent every record. `loc_b0d1` compares its argument against the mode latch `loc_9e`: if they already match it returns without emitting, otherwise it stores the new value into `loc_9e` and emits it as a `loc_df4c` word whose first (payload) byte is the mode argument just latched and whose second byte is the constant `0x68` (0x08 tagged with `0x60`). `loc_b0dd` does the same against `loc_72`, emitting through `loc_df6a` when the byte changes. ## The mathbox: projection and level tables

Tempest draws its tube in perspective by feeding coordinates through a hardware math coprocessor — the "mathbox" — mapped into the `0x6080`-region I/O block, and by unpacking a bank of per-level shape and colour tables out of ROM at setup. This section covers the projection driver, the coprocessor reset, the shape/coordinate table builders, and the small arithmetic helpers that dress the level bytes for those tables.

### The projection driver — loc_c098 [seen]

`loc_c098` is the per-point projection primitive: it hands the coprocessor one point's depth delta and axis magnitudes, waits for the hardware, and folds the scaled result into two running 16-bit accumulators. It first forms a signed 16-bit depth delta whose low byte is `loc_57 - loc_5f` written to `loc_6095` and whose high byte is `(0 - loc_5b - borrow)` written to `loc_6096`; when that high byte comes out negative (bit 7 set) the delta is clamped up to a floor of `+1` by forcing `loc_6096 = 0x00` and `loc_6095 = 0x01`. It then computes the unsigned magnitude `|loc_58 - loc_60|` and stashes it into the coprocessor multiplicand registers `loc_608e` and `loc_6094` while recording the comparison's sign in `loc_33` (`0xff` when `loc_58 < loc_60`, else `0x00`); the other axis magnitude `|loc_56 - loc_5e|` is held in `loc_32` with its sign in `loc_34`. The routine spins on `loc_6040 & 0x80` — the coprocessor busy bit — until the hardware finishes, then reads the paired result `loc_6060`/`loc_6070` into `loc_63`/`loc_64` and immediately re-issues the second magnitude (`loc_32`) into `loc_608e`/`loc_6094` to start the next operation. The first result becomes a 16-bit accumulator `{loc_64:loc_63}` into which the offset pair `{loc_69:loc_68}` is added or subtracted according to sign flag `loc_33`, with saturating overflow detection: a signed underflow pins the pair to `0x0080` (`loc_63=0x00, loc_64=0x80`) and a signed overflow pins it to `0x7fff` (`loc_63=0xff, loc_64=0x7f`). After a second busy-bit spin it reads the next result into the accumulator `{loc_62:loc_61}` and likewise folds the offset pair `{loc_67:loc_66}` in or out under sign flag `loc_34`, with the same two saturation limits. The two accumulators are the projected X and Y of the point; `loc_57`/`loc_5b`/`loc_5f` are the depth operands and `loc_56`/`loc_58`/`loc_5e`/`loc_60` the axis operands, all fed from the level's tube tables by the callers below.

## Sound, POKEY and the interrupt heartbeat

The audio machine hangs off the interrupt. On every IRQ the handler at loc_d704 latches the raw control-port byte at `loc_0c00` into `loc_8`, advances its frame counter (`loc_50`/`loc_52`, folded from POKEY register `loc_60c8`), and then runs the two audio steppers back to back: first the counter/accumulator engine `loc_cf24`, immediately followed by the voice engine `loc_cd0a`. That fixed ordering — `loc_8` freshly refilled, then `loc_cf24`, then `loc_cd0a` — is the heartbeat every voice rides on.

`loc_cf24` is `[seen]`, exercised on essentially every pass. It carries three parallel lanes indexed by `x` = 2,1,0, each lane gated by a distinct bit of the control byte `loc_8`: the body opens by right-shifting `loc_8` a lane-specific number of times so lane 0 tests bit 2, lane 1 bit 1, lane 2 bit 0, with the shifted-out bit becoming the running `carry`. For each lane it works a position cell — `loc_d+x`, i.e. `loc_d`/`loc_e`/`loc_f` — masking it to `& 0x1f` and, along the `carry` path, wrapping it modulo 0x20 (a `+0x20` fold with the `0x1f` upper rail, clamped to `0x1f`); the non-carry path either leaves it or subtracts through the `loc_cf48` borrow step. A per-lane free-run timer lives in `loc_10+x` and a shared 0xf0-reload dwell lives in `loc_c`: when `loc_8 & 0x08` is clear the dwell is forced to 0xf0, and while it counts down it zeroes both `loc_d+x` and `loc_10+x`. When a lane fires it contributes a small increment into the running accumulators `loc_16` and `loc_17` (each `sv + cell + 1`) and bumps that lane's `loc_13+x` counter. ## The EAROM high-score store

Tempest keeps its persistent state -- the high-score table and its bookkeeping -- in an ER-2055 EAROM on the $6000 IO page, and reaches it not by touching the part directly but by posting a request into a three-cell mailbox that a bit-serial transfer engine drains one region at a time. The mailbox is `loc_1c6`, `loc_1c7`, and `loc_1c8`: `loc_1c7` carries the request-pending bits (which of the persistent regions want service), `loc_1c8` carries the matching direction bits (a set bit means write that region out, a clear bit means read it back in), and `loc_1c6` is an index/blank byte -- when it is left nonzero the write path zeroes the RAM source before shipping it, erasing rather than copying.

A small family of front routines fills that mailbox, all funnelling through the shared merge in `loc_ddfb`'s tail: `loc_ddff` stores its Y argument into `loc_1c6` and ORs its A argument into both `loc_1c7` and `loc_1c8`, `loc_ddfd` reaches it with the index preset to 0, and `loc_ddfb` reaches `loc_ddfd` with the mask fixed at 0x04. `loc_ddfb` is the one member of this family whose fingerprint is actually seen in the capture -- the 0x04 mask does appear OR'd into the request pair -- so it is **[seen]**; it queues a single region (the 0x04 bit) for service with a zero index. `loc_ddf1` **[code]** would post the strongest request of all: it drops 0xff into `loc_1c6` and ORs 0x07 into both `loc_1c7` and `loc_1c8`, i.e. all three regions flagged for a blanked write-out (the high-score *save*). Although those three cell writes are spelled out in its body, the distinctive all-region signature it would leave -- index 0xff together with a 0x07 merged into the request cells -- is never observed; the 0x07 that does show up at `loc_1c7` is put there by `loc_de11`'s outright *set*, not by this routine's OR, so it stays **[code]**. `loc_ddf3` **[code]** forces the index to 0xff (blank mode) and merges whatever mask it is handed, `loc_ddf7` **[code]** supplies the constant mask 0x03 through the zeroed-index entry (that 0x03 pattern is never seen reaching the merge point), and `loc_dde9` **[code]** is a trampoline that requests region 0x04 in blank mode by calling `loc_ddf3` with 0x04. None of these blank-write request paths are exercised in the capture, matching a session that only ever reads the store back.

The read-side initiator, `loc_de11` **[seen]**, does not go through the merge at all: it *sets* `loc_1c7` to 0x07 and `loc_1c8` to 0x00 -- all three regions requested, every one in read direction -- and then drops straight into the transfer engine to run the load. Both of those own writes are observed, which is what makes this the grounded entry point for pulling the saved high-score table out of the EAROM at start-up.

The engine itself is `loc_de1b` **[seen]**, and it is heavily exercised -- it advances one step per invocation and re-enters itself from the top until a step completes. When the mode byte `loc_1ca` is idle (0) but `loc_1c7` still holds a pending bit, it opens a fresh region: it clears the pass counter `loc_1cb`, the checksum accumulator `loc_1cf`, and the mask cell `loc_1ce`, then walks a single bit down through `loc_1c7` from the high end, shifting a marker rightward into `loc_1ce` and counting down an index in step, stopping as soon as it meets a set request bit. `loc_1ce` is left holding exactly that one bit, and the index is doubled to address four packed tables at $dddd/$ddde/$dde3/$dde4: `loc_1cc` takes the region's starting port cursor from `loc_dddd`, `loc_1cd` its byte limit from `loc_ddde`, and the pointer pair `loc_bd`/`loc_be` the 16-bit address of that region's RAM shadow from `loc_dde3`/`loc_dde4`. The direction is decided on the spot -- `loc_1ca` becomes 0x80 (write) if the selected bit is also set in `loc_1c8`, otherwise 0x20 (read) -- and the serviced bit is cleared out of `loc_1c7` by XORing `loc_1ce` back into it, so each region is retired once.

From there the common block clears the control port `loc_6040` and, guided by `loc_1ca`, does one byte of work against the port block. In write mode it ships a byte through `loc_6000` offset by the cursor in `loc_1cc`, honouring the blank flag in `loc_1c6` by first zeroing the RAM cell reached through `loc_bd`/`loc_be`, and substitutes the running checksum `loc_1cf` once the cursor passes the limit `loc_1cd`. In read mode it drives the EAROM handshake -- pulsing `loc_6040` through 0x08/0x09/0x08 and a strobe to `loc_6000` -- then latches the returned byte from `loc_6050`, storing it through the region pointer while below the limit, and at the limit XORs it against the accumulated checksum `loc_1cf`: a zero result means the region verified, and a nonzero result walks the pointer back down clearing the just-read cells and ORs `loc_1ce` into `loc_1c9`, flagging that region as corrupt. Every serviced byte is folded into `loc_1cf` and both the pass counter `loc_1cb` and the port cursor `loc_1cc` advance. Each step ends by writing a control code to `loc_6040`; a zero code means keep going and the routine loops to service the next byte or region, a nonzero code ends the step. `loc_1c9` is thus the store's health word, `loc_1ca` its live mode/state, and `loc_1cb`/`loc_1cc`/`loc_1cd`/`loc_1ce`/`loc_1cf` the per-region working set.

The remaining routines grouped here -- `loc_db22`, `loc_db84`, `loc_db88`, `loc_db9a`, `loc_db7e`, `loc_db6f`, all **[code]** -- are not part of the high-score store: none of them read or write the EAROM mailbox cells `loc_1c6`..`loc_1cf`. They belong to the vector/object display path, emitting two-byte display words through the cursor `loc_74` by way of `loc_df39`, `loc_df4c`, and `loc_df6c`. `loc_db22` overlaps the store only in hardware: it resets a spread of $6000-page registers (`loc_60e0`, `loc_6080`, `loc_60c0`, `loc_60d0`, `loc_6000`, `loc_6040`), takes four settling reads across `loc_6040`/`loc_6060`/`loc_6070`/`loc_6050` -- the same control and readback ports the EAROM engine uses, here touched as part of a broad IO reset -- then raises `loc_60e0` to 0x08 and marches a single set bit, rotated left through carry, across the 32-cell bank at `loc_6080`, finishing with one framing word `loc_df39(0x34,0xa6)`. `loc_db84` emits a framing word `loc_df39(0x33,0x0a)` and then blanks the four even slots (offsets 6,4,2,0) of the `loc_60c1` and `loc_60d1` banks; `loc_db88` does the same clear behind a caller-supplied framing word, and `loc_db7e` drives it with the fixed pair (0x32,0xb6) -- that value being nonzero, the self-seeding alternate is never taken. `loc_db6f` emits one word from half the count in `loc_50` (`loc_df4c(0x68, loc_50 >> 1)`) before the same clear via `loc_db88(0x33,0x4e)`. `loc_db9a` is the animated one: gated by the low six bits of the frame counter `loc_3`, it bumps the phase counter `loc_39`, takes `loc_39 & 0x07` as an index into the parallel tables `loc_dbd5`/`loc_dbd6`/`loc_dfdc`, uses those to clear one `loc_60c1` slot and to seed a `loc_60c0` slot with the table datum plus a 0xa8 marker in the matching `loc_60c1` slot, and emits three display words (`loc_df39(0x34,0x56)`, then `loc_df6c(0x01, loc_3 & 0x7f)`, then `loc_df39(0x34,0xaa)`). The code supports these only as frame-driven vector emitters over the $6000-page display registers; it gives no basis for treating them as EAROM machinery, and none of the six is reached along an EAROM path in the capture.

## State-reset, init and per-frame update chains

This subsystem covers the machine's cold-start wipe, the scattered constant-seeding leaves that arm a fresh wave, the queue that spawns a slot into play, the per-frame ageing/clock step, the control-block rebuild cascade that keeps the tube geometry in step with the option switches, and the scoring adders that ride on top of a hit.

### The cold-start reset orchestrator

`loc_902b` is the top of the reset fan: it runs six subsystem-clear leaves back to back — `loc_928f`, `loc_926f`, `loc_9246`, `loc_929f`, `loc_92ad`, and `loc_c16e` — and then latches two arm bytes high and clears one, writing `0xff` to `loc_124`, `0xff` to `loc_148`, and `0x00` to `loc_123`. It is entered by falling through from the init chain, so the clear leaves it drives were exercised, but its own three tail writes are constant seeds that never vary in the capture, so its role rests on the code `[code]`.

The four of those clear leaves that live in this subsystem each wipe one block plus a few associated flags. `loc_928f` `[seen]` blanks the twelve-byte block `loc_2d3..loc_2de` (index `0x0b` down to `0`) and then zeroes the two flags `loc_135` and `loc_a6`. `loc_926f` `[seen]` blanks the seven-byte block `loc_2df..loc_2e5` (index `6` down to `0`) and zeroes seven scattered flag cells — `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146`. `loc_929f` `[seen]` blanks the eight-byte table `loc_30a..loc_311` (index `7` down to `0`) and clears the trailing flag `loc_116`. `loc_92ad` `[seen]` does the smallest job of all, clearing the single state byte `loc_50` to zero (a cell that ranges widely elsewhere, so the reset is real). ### The wave-init routine

`loc_a5cb` `[seen]` sets up a wave. It writes `loc_0=0x20`, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c`, and `loc_123`, and sets `loc_105=0x02`. It then walks the sixteen-entry lane table `loc_3ac..loc_3bb` and counts how many entries are non-zero, accumulating the total into `loc_123` — grounded by the observed `loc_123` climb from `0x0` to `0x6`, i.e. six occupied/spiked lanes tallied. If that count is non-zero and the level counter `loc_9f` is below `0x07`, it loads an intro/parameter block — `loc_4=0x1e`, `loc_0=0x0a`, `loc_2=0x20`, and `loc_123=0x80` (the tally cell repurposed as a flag). Finally it always latches `loc_125=0xff` to mark the block ready. The `loc_9f < 0x07` test is the code's own gate keyed on the level number, so the extra intro load only happens on the earliest levels.

### The slot-spawn queue drain

`loc_ad22` `[seen]` pulls the next requested slot into play by draining the packed request word `loc_603` two bits at a time. On each pass, if `loc_603` is zero it writes the idle exit status `loc_0=0x14` and returns; otherwise it takes the low two bits minus one as the slot index into `loc_3d` (observed `0x1`→`0x2`), shifts `loc_603` right twice to consume that field (observed `0x4`→`0x0`, `0x9`→`0x1`), and reads the per-slot request byte `mem8[loc_600 + index]`. A byte of zero or `>= 0x09` is skipped and the drain continues to the next field. For a live byte `n` in `1..8` it builds a scaled/inverted spawn value — `a = ((n<<1) + n) ^ 0xff`, then `a = a - 0xe5`, i.e. `-(3n) - 0xe6` (the `^ 0xff` negates and subtracts one) — and stores it in `loc_602`. It then invokes `loc_ca48`, seeds the paired spawn cells `loc_605=0x60`, `loc_4e=0x00`, `loc_50=0x00`, and `loc_604=0x02`, wipes the per-slot table through `loc_a789`, and writes the armed exit status `loc_0=0x24` before returning. So the word `loc_603` is a queue of pending slot indices and `loc_600` the per-index request magnitudes; one drain arms at most one slot per call.

### The per-frame ageing / clock step

`loc_a504` `[seen]` runs at the tail of the frame dispatcher and splits on the sign of the control byte `loc_201`. In the capture the negative arm (`loc_201 >= 0x80`) is the one exercised: it bails if any of `loc_135`, `loc_a6`, or `loc_116` is set, then ages each live entry of the depth table `loc_2df` (from index `loc_11c` downward) by adding `0x0f` and snapping to `0x00` at the ceiling (`v >= 0xf0` → `0`), which is how objects that reach the far end of the tube expire. It then branches on the per-slot flag `mem8[loc_48 + loc_3d]`: if that flag is not `0x01`, it advances the counter `loc_202` by `0x0f` and proceeds once it crosses `0xf0`; if it is `0x01`, it clears `loc_10f`, sets `loc_114=0x01`, and steps the sixteen-bit countdown clock `loc_5f`(low)/`loc_5b`(high) down by `0x20`, proceeding when the high byte lands on the marker `0xfa`. When it proceeds it writes `loc_00=0x06`, calls `loc_928f`, and finally folds `loc_108 + loc_109 + loc_3ab` into `loc_3ab`, clamped to a ceiling of `0x3f`.

The positive arm (`loc_201 < 0x80`), which the negative-arm capture did not drive through its reset paths, bumps a per-slot timer: when `(loc_455 | loc_11b)` is set and `loc_42 > 0x17`, it increments `mem8[loc_00 + loc_40]`. It returns early if `loc_106` is non-zero; otherwise, when `(loc_3ab | loc_116)` is zero, it scans `loc_2df` from index `loc_11c` down for any live entry that has already grown to `>= 0x11`, and only if none has does it re-init via `loc_a5cb` followed by `loc_928f`. It then falls through a chain of gates — `(loc_4d & 0x60)`, `(loc_5 & 0x80)`, and `(loc_9 & 0x43) == 0x40` — and runs `loc_a5cb` again if all pass.

### The control-block rebuild cascade

Four callers keep the two control-block regions consistent with the live option/switch snapshot. `loc_ac20` `[code]` refreshes the snapshot by running `loc_d6bb` (the option-switch decoder) and then compares the live geometry state `(loc_a & 0xf8)` against the cached target `loc_71e` and `(loc_16a & 0x03)` against `loc_71f`; on a match it tail-calls the shared no-op return, and on a mismatch it requests a rebuild through `loc_ac36`. It is reached only through its callers, and only the match path (the no-op return) fired in the capture, so its role rests on the code.

`loc_aba2` `[code]` refreshes the snapshot via `loc_ac20` and then branches on the low two request bits of `loc_1c9`: an idle value takes the no-op return leaf `loc_ac07`, otherwise it runs the full rebuild path `loc_abac`. It has no role-defining own write — it refreshes through `loc_ac20` and branches — so its role rests on the code.

`loc_abac` `[seen]` is the rebuild worker. It first refreshes through `loc_ac20`, writes `loc_100=0x08`, and — when all three edge sources `loc_71b`, `loc_71c`, `loc_71d` are idle — requests both rebuilds via `loc_ac36`. It then reads the request bits `loc_1c9`: for bit 0 it copies a template block, running index `0x17` down to `0` when bit 0 is set (else `0x0e`), from `loc_ac08` into `loc_606`; for bit 1 it fills the second region `loc_706` with `0x01` over index `0x17` down to `0` when bit 1 is set (else `0x0e`). When either request bit is present it latches the fresh snapshot into the cache (`loc_71e = loc_a & 0xf8`, `loc_71f = loc_16a & 0x03`), and finally clears the two request bits with `loc_1c9 &= 0xfc`. Its rebuild path did fire in the capture, so it is `[seen]`.

`loc_d7e1` `[code]` is the gated front to the rebuild: it arms two mode bytes, `loc_5=0x00` and `loc_1=0x02`, then bails if `loc_1ca` is non-zero (busy) or if `(loc_c00 & 0x10)` is clear (not enabled); once past those it writes `loc_0=0x00` and, only if a rebuild request is pending (`loc_1c9 & 0x03`), delegates to `loc_abac`. It is not reached in the capture — even its unconditional entry writes to `loc_5`/`loc_1` never appear in the trace — so its role rests on the code.

### The scoring adders

`loc_ca6c` `[seen]` adds a multi-byte BCD amount into the score cell trio and drives a threshold state machine. It is gated off unless `loc_5` bit 7 is set. The destination offset `y` is `0` when `loc_3d` is zero, otherwise `3`, so the trio is either `loc_40/loc_41/loc_42` or the second copy at `+3`. When the caller passes an index below `0x08`, the amount comes from the fixed ROM tables `loc_caf1 + x` and `loc_caf9 + x`; otherwise it comes from the live operand triplet `loc_29`/`loc_2a`/`loc_2b`. Two low bytes add with carry chained through, then a third byte adds `loc_42 + y`. The result is range-checked against the threshold cell `loc_156`, and on qualification the award helper bumps the per-slot counter `mem8[loc_48 + loc_3d]` — but only while it is still under six — then fires the sound cue `loc_ccc3` (code `0x4f`, threaded with the slot index and `y`) and raises the flag `loc_124=0x20`. The score-add itself is grounded `[seen]`; the bonus-life award path is code-only in the capture. When the threshold `loc_156` is three or higher the routine repeatedly subtracts it from the accumulator and awards only on landing exactly on zero (an exact multiple).

`loc_a1fa` `[seen]` advances a slot's counter toward a per-target limit and, on reaching it, scores and can cost a life. It reads the slot's target index `y = mem8[loc_2ad + x]` and the limit `mem8[loc_3ac + y]` from the sixteen-entry lane table; a zero limit returns immediately. When the counter `mem8[loc_2d3 + x]` has reached the limit, it writes the reached counter value back to the limit cell `loc_3ac + y`, clearing it to zero only when that value is already saturated at `>= 0xf0`, bumps the hit tally `mem8[loc_2f2 + x]`, flags the target `mem8[loc_39a + y] = 0xc0`, chimes through `loc_ccf6`, then stages a one-point BCD amount (`loc_2a=0`, `loc_2b=0`, `loc_29=0x01`) and awards it via `loc_ca6c` with index `0xff`, picking up the refreshed slot index from `loc_37` afterward. Finally, once a target's hit tally reaches `0x02` (the second hit), it resets that slot's counter `mem8[loc_2d3 + xEff] = 0x00` and decrements the life/credit counter `loc_135`. It returns the slot index live at exit.

## Utilities and shared tails

This section gathers the small, reusable service routines the rest of the machine leans on: a binary-to-BCD packer, a byte-splitting helper, two table-maintenance routines, a rebuild-request flag setter, a constant-returning leaf, and a cluster of bare-return tails that serve as the "nothing to do" exits of larger routines.

### Numeric packing and display emission

**loc_aaf5** (`[seen]`) is the machine's binary-to-BCD converter, and it is heavily exercised. Given a binary byte in `A`, it runs a classic decimal-mode double-dabble: the accumulator `loc_2c` starts at zero and the source byte is walked through eight passes, each pass shifting the top bit out of the source and folding that bit into a decimal-mode double of the accumulator (`loc_2c = loc_2c + loc_2c + carry`, with the nibble/high-nibble decimal corrections that `sed` arithmetic applies). When the eight passes finish, the packed BCD result is stored to **both** `loc_29` and `loc_2c`, so both cells end holding the same packed value and both therefore range across `0x00..0x99`. The write taps confirm the accumulator reaching up into the high-BCD range during the fold and the final digit store landing in `loc_29`.

**loc_af71** (`[code]`) is the front door to the "pack this count and draw it" path. It clamps its incoming byte to a ceiling of `0x63` — if the value already sits at or below `0x63` it passes through unchanged, otherwise it is forced to exactly `0x63` (never `+step`, a flat clamp to the constant) — and then hands the clamped value down the pack-and-emit chain: `loc_aaf5` packs it to BCD in `loc_29`, and the shared nibble emitter walks that single zeropage byte out as its high-then-low nibble digits. This is how the on-screen counters (whose live values arrive through `loc_af3f`/`loc_af26`) get rendered without ever exceeding the two-digit `99` display width. Its role rests on the code rather than an own-cell write, so it stays `[code]`.

### Byte splitting

**loc_93e0** (`[seen]`) is a compute helper that partitions one input byte into three live-out register results, reached through the three call sites in its dispatcher chain. It seeds an accumulator at `0xff` and runs three passes that fold the input's top three bits (MSB first) into the accumulator's low bits (`acc = (acc << 1) | bit`), so the accumulator ends as `0xf8 | top3bits`. That accumulator is written to the scratch cell `loc_29` and also returned as the "seed" in `Y`. `A` ends holding the input shifted left three places (its low five bits become a fine value in the upper bits), and `X` is derived from the accumulator's complement as `((acc ^ 0xff) + 0x0d) >> 1`; since `acc = 0xf8 | top3bits`, `acc ^ 0xff = 7 - top3bits`, so `X = ((7 - top3bits) + 0x0d) >> 1`, which lands in the coarse-index range `{6..10}`. Its only own write is the `loc_29` scratch, which the tap observes, so it grounds as a reached compute helper: one byte in, a fine value plus a coarse index plus a seed out.

### Table maintenance

**loc_92b2** (`[code]`) swaps two parallel eighteen-entry byte tables slot-for-slot. Walking the index from `0x11` down to `0`, it exchanges the byte at `loc_3aa + x` with the byte at `loc_3bc + x` (a single byte per slot at each address, using `Y` as the temporary), so after the pass each slot holds what its sibling table held. Neither swap store fires anywhere in the capture, so the routine is not reached across attract, coin, start, or play; the body is readable but stays `[code]`.

**loc_b85f** (`[code]`) is a straight-line seed of two paired three-entry arrays with the fixed values `0`, `4`, `12`: it writes `loc_22`/`loc_809 = 0x00`, `loc_23`/`loc_80a = 0x04`, and `loc_24`/`loc_80b = 0x0c`, then returns with `A = 0`. None of these seed writes appear in the capture, so the routine is not reached in this capture and stays `[code]`; the body is nonetheless a clean paired-array initialization.

### Rebuild-request flag

**loc_ac36** (`[seen]`) posts a rebuild request by OR-ing `0x03` into the working flags cell `loc_1c9` — setting the two low pending-rebuild request bits — and returns the merged value, then falls through to the shared return tail. The tap observes the own-body write to `loc_1c9` landing with both request bits present (value `0x7`). It is driven both from `loc_ac20`, which routes here when its geometry-state comparison finds a mismatch, and from `loc_abac`; the request bits it sets are the ones those callers' rebuild consumers later act on.

### Constant leaf

**loc_b955** (`[code]`) reads like a bit-population count but is not one, and a blind reader will mis-name it. It loads `loc_57`, shifts it right four places, and runs an `iny`/`lsr`/`bne` loop that would count set bits — but the loop's result is thrown away: the trailing `clc`/`adc #2` leaves `A = 0 + 2 = 2` and the `ldy #0` resets `Y = 0`. It therefore **always** returns the constant pair `A = 2, Y = 0`, regardless of `loc_57`, and touches no memory. It is register-only with no groundable write, so it stays `[code]`; the correct name is "returns the constant pair," not "log2/bit-count of `loc_57`."

### Shared return tails (bare-RTS exits)

Four one-byte routines are pure return leaves — a single `rts` with no memory write — that serve as the "nothing to do" exit for a larger routine's fast path. None can be grounded from a write tap, so all four stay `[code]`.

**loc_ac07** is the nothing-to-rebuild exit: `loc_aba2` branches here when `loc_1c9 & 3 == 0`, i.e. no rebuild request is pending.

**loc_ac3e** is the shared return tail of the rebuild-check path: `loc_ac20` lands here when the live geometry state already matches its cached latch (`loc_a & 0xf8` against `loc_71e`, and `loc_16a & 3` against `loc_71f`), so no rebuild is needed.

**loc_af6e** is the exposed return tail of the counter-draw routine `loc_af3f`: `loc_af26` branches here when `loc_600 | loc_601 == 0`, i.e. both counter slots are empty and there is nothing to draw.

**loc_9bcf** is a do-nothing handler slot occupying an entry in a computed-dispatch table: it returns immediately, letting control unwind, so a table index that selects it produces no effect. Its readable role is exactly "no-op dispatch slot"; reach cannot be confirmed from the write tap.

## Still on the frozen oracle

The subsystems above are the idiomatic layer's decompiled set — the leaves, the caller routines that drive
them, and the first computed-jump dispatcher (`loc_b84e`, described above). The rest of the reachable call
graph still runs as the frozen translated oracle: the deeper callers whose callees are not yet decompiled,
and the remaining computed-jump dispatchers that form the game's spine (each is decompiled only once all of
its jump-table targets are idiomatic). Two register-thread callers remain deferred, each needing a register
an intervening frozen leaf leaves that cannot yet be faithfully modelled: `loc_c891` (whose call to
`loc_ccfa` needs the X/Y left by a leaf with too many exit paths) and `loc_9749` (whose call to `loc_ccb5`
needs the Y left by `loc_97c5`, not yet extended to return it). Deep-tail roles tagged `[code]` lift to
`[seen]` once a capture drives the states that exercise them.
