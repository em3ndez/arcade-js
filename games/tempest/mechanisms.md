# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (the dispatcher spine and two register-thread callers)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Tempest animates the objects that ride the tube — enemies climbing the lanes, and the moving fixtures the wave sequencer spawns — by running a tiny byte-coded program per object rather than hand-coding each motion. The programs live in the ROM table `loc_a0f7` (with `loc_a0f8` naming the same table one byte higher, so a read from `loc_a0f8[i]` fetches the operand that sits just past the opcode at `loc_a0f7[i]`). A per-object walk fetches an opcode byte, dispatches it through an RTS-trick jump table, and lets the handler consume its own operands, so the routines below are the *opcodes* of that little machine. Three engine-wide zero-page cells carry the walk's state: `loc_10b` is the instruction pointer / cursor into the script tables, `loc_10a` is the walk-continuation flag (the walk keeps stepping while it is nonzero), and `loc_10c` is the branch flag that the conditional opcodes read. The written motion parameters and per-object countdowns land in the object's slot cell `loc_298,x`.

**Ending the walk.** `loc_9bca` [seen] is the terminator opcode: it writes zero into `loc_10a`. Because the driving walk continues only while `loc_10a` stays nonzero, this is the single act that stops the current object's program for this tick and lets the machine move on to the next object. It is exercised on essentially every pass of the engine, which is consistent with each object's script running to a stop each frame.

**Store opcodes.** Two opcodes deposit a value into the object's slot `loc_298,x`, differing only in how they source the value. `loc_9bd0` [seen] first advances the cursor — it computes `(loc_10b + 1) & 0xff`, writes that back to `loc_10b`, and then copies the script byte at `loc_a0f7[loc_10b]` straight into `loc_298 + x`. This is the immediate-load form: the value to store is the very next byte of the program. `loc_9bdd` [seen] is the indirect form: it bumps `loc_10b` by one, reads the script byte at `loc_a0f7[loc_10b]`, but treats that byte as a zero-page address, and copies the live variable found at `loc_00 + ptr` into `loc_298 + x`. So one opcode stamps a constant motion parameter into the slot and the other pulls whatever a named zero-page variable currently holds — both are heavily exercised as objects load their per-tick movement values.

**Timer / state-step opcode.** `loc_9c0c` [seen] treats the object's slot `loc_298,x` as a countdown. It decrements that cell, and while it remains nonzero it hands off to `loc_9c17` to take one table-driven state step; only when the cell reaches zero does it instead bump the shared cursor `loc_10b` by one, letting the walk fall through to the following opcode. This is how an object dwells in a motion state for a fixed number of ticks before the script proceeds. It runs on essentially every pass.

**Goto opcodes.** `loc_9c17` [seen] is the unconditional goto (and the "still counting" branch of the timer opcode above): it takes the current cursor `loc_10b` as an index, fetches `loc_a0f8[loc_10b]`, and writes that byte back as the new `loc_10b`. Because `loc_a0f8` is `loc_a0f7 + 1`, the fetched byte is the target operand that follows the current position, so the effect is to reseat the instruction pointer at a scripted destination. Its cursor-reload write is exercised heavily, pulsing across a range of low cursor values as objects loop within their scripts. `loc_9bfa` [seen] is the *conditional* goto: it first advances `loc_10b` by one (byte-wrapped), then, only while the branch flag `loc_10c` is zero, replaces `loc_10b` with the inline target byte read from `loc_a0f7[loc_10b]`. When the flag is nonzero it leaves the cursor sitting just past the operand, so the jump is skipped. Its cursor-advance write is common and its target-reload write fires when the branch is actually taken.

**Conditional-skip opcode.** `loc_9bee` [seen] is the paired skip: if the branch flag `loc_10c` is nonzero it does nothing, and otherwise it advances `loc_10b` by two, byte-wrapped — stepping the cursor over a two-byte operand. Both of the two-in-one increments are observed advancing together, which is the signature of skipping an operand pair.

**Test opcodes (produce the branch flag).** Two opcodes compute `loc_10c` for the conditional opcodes to read. `loc_9c21` [code] is the geometry test: it reads the object's segment from `loc_2b9,x`, looks up that segment's boundary in `loc_3ac[segment]` (treating a stored zero as the maximum, `0xff`), and sets `loc_10c` to `1` when the boundary is at or beyond the object's coordinate in `loc_2df,x`, else `0` — a "has this object reached the edge of its lane" test. `loc_9c3b` [code] is the phase test, driven by the driver's signed accumulator pair `loc_147`/`loc_148`: it forms `((loc_147 << 2) + loc_148) & loc_148 & 0x80`, keeps that high bit, and inverts it, so `loc_10c` becomes `0x00` when the selected high bit is set and `0x80` when it is clear (note this flag is `0x80`/`0x00`, whereas `loc_9c21` produces `1`/`0`; the conditional opcodes only test for nonzero). Neither test opcode's store to `loc_10c` appears in the capture — during the captured window the branch flag was produced by another site (around `0x9e2b`) — so both are tagged [code]: not reached in the capture, their intended flag-setting role read from the code rather than observed.

**List-cursor skip primitive.** `loc_96c7` [code] belongs to a separate, register-only cursor mechanism: it advances the list index in `Y` by a fixed run to skip a packed record without reading it. The first entry (`loc_96c7`) steps forward by three, delegating to its second entry (`loc_96c8`) with `Y` already bumped by one, and that second entry adds two more; there are no memory writes of its own. It is reached only through the `loc_9683` computed dispatcher (an RTS-dispatch keyed on `loc_15e`), and it was not reached in the capture, so its skip-by-three / skip-by-two behavior is read from the code rather than observed.

## Vector coordinate lists and the display cursor

Two pointers organize the whole business of turning stored geometry into strokes on the color-vector tube. One is the *coordinate-list* pointer at `loc_2c`/`loc_2d`, a little-endian address that walks packed lists of point offsets; the other is the *display cursor* at `loc_74`/`loc_75`, the write head that lays finished opcode/coordinate words into the AVG vector display RAM in the `$2000`–`$2fff` range. The routines here either aim the coordinate-list pointer and read entries through it, or they append words at the display cursor and step it forward.

**Aiming and seeding the coordinate-list pointer.** `loc_9aee` [seen] selects which stored list to walk: indexed by Y, it loads the low byte of the list address from the ROM table at `loc_9b02` into `loc_2c` and the high byte from the table at `loc_9afd` into `loc_2d`, records the chosen index Y in `loc_2b`, and reloads A from the `loc_29` scratch cell before returning. The write-tap confirms all three stores firing (`loc_2c` taking a low byte, `loc_2d` a high byte such as `0x07`, and `loc_2b` the index), so the list-selection role is grounded. Its sibling `loc_9a9d` [code] seeds the same pointer pair for the fixed first list rather than an arbitrary indexed one: it copies the head of the `loc_9b02` table straight into `loc_2c`, clears the index at `loc_2b`, takes the high byte from the held source cell `loc_15d` into `loc_2d`, and likewise reloads A from `loc_29`. Its lone captured store is a constant, so this seeding path's distinctive role rests on the code rather than on observed variation.

**Walking a list through the pointer.** With the pointer aimed, `loc_96cb` [seen] steps the cursor by inter-entry deltas: forming the 16-bit address from `loc_2c`/`loc_2d`, it reads the entry at offset Y and its predecessor at Y−1, stores their difference at `loc_29`, and reports a new cursor of (Y−1)+delta+1 in A and that value plus two in Y — i.e. it advances the walk past the entry it just measured by delta+2. The write-tap shows `loc_29` taking real step values across the `0x01`–`0x0f` range, and those deltas are genuine spacings between entries in the list reached through the coordinate-generator dispatch, so the delta-walk role is grounded. `loc_96db` [code] converts one list entry into an absolute display coordinate: it reads the byte at the pointer offset by Y and adds the base held in `loc_160`, returning the 8-bit sum in A. It performs no store of its own, so as a pure compute helper reached through a computed jump it carries the honest [code] tag — the write-tap has no store to witness and no downstream consumer of its A output can be named from it.

`loc_96ab` [seen] is the coordinate helper that the computed-jump generator leans on. Its two heads pick the starting value differently — the `loc_96ab` entry uses ((`loc_2b`−1) AND `0x0f`)+1, while the `loc_96b7` entry uses `loc_2b` raw — but both fall into a shared body that first stashes the incoming cursor Y into the `loc_29` scratch cell, then subtracts the list entry two positions back (at pointer offset Y−2) from that value, adds the stashed cursor back in, and finally re-indexes the list by the result to return both the entry there (in A) and the new index (in Y). A third small head, `loc_96c4`, simply fetches the entry at the current Y. The scratch write at `loc_29` is the only store, and the tap confirms the body is reached and that scratch stashing happening; its A/Y output feeds the coordinate-vector generator downstream, which grounds it.

**The display cursor and its advance.** Every emitter finishes by pushing the write head forward through `loc_df5f` [seen], the shared cursor-advance. It adds the caller's stride Y plus one to `loc_74` (the carry is forced in, so the effective step is Y+1), writes the sum back to `loc_74`, and on overflow increments the high byte `loc_75`. The write-tap shows `loc_74` pulsing across nearly its full 8-bit range and `loc_75` climbing through the high bytes of the display RAM (around `0x25`–`0x2a`) as the cursor sweeps the list region, which grounds it as the live cursor that all the producers hand off to.

**Appending words at the cursor.** The core emitter `loc_df59` [seen] stores a pair {A, X} at the cursor offsets Y and Y+1, then advances the cursor by Y+2 via `loc_df5f`. The tap captures it writing real vector data into the `$2000`–`$2fff` region (for example a `0x3c`/`0x72` pair into adjacent cells), grounding the pair-emit role; other draw routines jump directly into it with A/X preset. `loc_df53` [seen] is the fixed-header form of that emit: it lays the constant word {`0x40`, `0x80`} at the cursor and advances one word, and the tap shows both header bytes landing in the display RAM (an adjacent `0x40`/`0x80` pair appears in the stream). `loc_df19` [seen] appends a table-selected word: from the low nibble of A it chooses a word-table index — index 0 when carry is set and the nibble is zero, otherwise nibble+1 — doubles it, and copies the two bytes of the `loc_31e4` ROM word-table entry at that index into the list before stepping the cursor one word; it is reached through the packed-digit driver that iterates a run of nibbles into the list, and the tap shows both its `loc_31e4` reads and its display-RAM stores. `loc_df1f` [seen] is the thin index variant that turns A's low nibble into (nibble AND `0x0f`)+1 and shares the same copy-and-advance emit tail as `loc_df19`; its own index arm computes only and leaves no store, so it is grounded as a pure index helper reached through that shared, tapped emit rather than by a write of its own.

**Composite producers.** `loc_c772` [seen] emits a whole object-position vector in one pass. Starting the cursor offset at zero, it writes the fixed header word {`0x40`, `0x80`}, then an X coordinate word — low byte from (`loc_2`+X), high byte from (`loc_3`+X) masked to its low five bits — and a Y coordinate word — low byte from (`loc_00`+X), high byte from (`loc_1`+X) likewise masked to five bits — caching the four raw coordinate bytes at `loc_6c`, `loc_6d`, `loc_6a`, `loc_6b` as the previous-point anchor, and finally advances the cursor six bytes past the header-plus-two-coordinate group. It is a heavily exercised producer, grounded by its stores landing in the display RAM. `loc_aef8` [seen] is the text-glyph emitter: it sets up the source index at `loc_38` (the incoming A plus two) and a three-iteration counter at `loc_39`, reads three character codes from the `loc_606` buffer at descending offsets, replaces any code at or above `0x1e` with `0x1a` before use, doubles the code to index the glyph word-table at `loc_31fa`, and copies each entry's two bytes into the display list through the cursor; after the three words it advances the cursor past what it wrote via `loc_df5f`. The tap shows it writing glyph words across the display RAM with the vector-draw opcode in the high byte, grounding the text-to-vector role.

## Draw-pointer setup and vector emission

This subsystem builds the frame's vector display list. Everything the game draws is a stream of words written into the AVG vector RAM at 0x2000-0x2fff; a 16-bit little-endian write cursor lives in `loc_74`/`loc_75` (with a running byte offset in `loc_a9`, or a local `y`), and the high byte of each emitted word carries the vector-generator opcode field, which is why so many stores mask a coordinate high byte down to five bits (`& 0x1f`) or force an opcode pattern (`0x70`, `0xa0`, `0x60`, `0x68`, `0x71`, `0xc0`) into it. The routines here fall into three layers: they first aim the cursor at the right structure, then gather coordinates and fold them into vector words, and finally stamp glyph/digit runs and math-box-normalized coordinate pairs into the list.

### Aiming the draw cursor at a structure

Before anything is drawn, the code chooses which ROM record the cursor will address. `loc_b2be` [seen] takes a subsystem index in A, forms the two-byte stride `(A<<1)&0xff`, and selects between two ROM pointer tables by the per-index flag `loc_415`: a nonzero flag picks table `loc_ce68`, a zero flag picks `loc_ce7a`. It publishes the selected 16-bit pointer into the draw cursor `loc_74`/`loc_75` and clears the status cell `loc_a9` (both write bytes were observed changing across the capture). `loc_b2de` [seen] is the mirror-image producer for the secondary pointer slot `loc_3b`/`loc_3c`: same stride and same two tables, but the table sense is reversed — a nonzero `loc_415` picks `loc_ce7a`, a zero picks `loc_ce68` — and it likewise clears `loc_a9`. `loc_91b5` [seen] serves a different pointer, `loc_2a`/`loc_2b`: it doubles the selector in A into a word index, clears the paired flag byte `loc_29`, and copies a little-endian pointer out of the split ROM tables `loc_91c6` (low bytes) and `loc_91c7` (high bytes) at that index.

`loc_b332` [seen] both checkpoints the frame and re-seats the cursor. It compares the source byte `loc_cec4` against the checkpoint `loc_2000`; if they differ it latches the new value into `loc_2000` and returns carry set, signalling the caller that the frame changed and the list must be rebuilt. On the matching path it emits a two-byte record — selected by `loc_415` (offset 8 when nonzero, else 2) out of table `loc_ce9e` — through the current `loc_74`/`loc_75` cursor, clears `loc_16e`, then reloads the cursor from `loc_ce68` at the same offset and returns carry clear; both copy stores were observed with real pointer values.

`loc_b944` [code] swaps the whole pointer pair `loc_74`/`loc_75` with `loc_76`/`loc_77`, so the shared cursor addresses the other structure; and `loc_b967` [code] selects an (A, X) pointer pair by `loc_415` (the `loc_ce87`/`loc_ce86` pair when the flag is zero, else `loc_ce6f`/`loc_ce6e`). Neither ran in this capture — their only caller, the object-draw loop, did not execute — so both are read from the code, not seen; the selector flag `loc_415` itself is exercised elsewhere.

`loc_b84e` [code] is a computed dispatcher: the caller hands it Y as a byte offset (0, 2, 4, 6) into a four-entry table of draw-pointer targets, and it tail-returns the selected routine (`loc_b85f`, `loc_b875`, `loc_b888`, or `loc_b896`). One of those targets, `loc_b896` [code], writes the vector-RAM tail terminator: it stores the 16-bit cursor `loc_139`/`loc_13a` into the list tail (`loc_2ffc` = low byte, `loc_2ffd` = high byte OR'd with `0x70`, `loc_2fff` = `0xc0` terminator), then steps the cursor down by 0x20 with a 16-bit borrow into `loc_13a` and masks the low byte to `0x7f`. `loc_b896` was not reached in the capture, so its five target cells are read from the code. `loc_b84e` reaches `loc_b875` and its siblings only through this dispatcher rather than through a direct caller; it has no own write and its role rests on the code.

### Gathering coordinates and emitting delta records

The workhorse of coordinate drawing gathers a slot's attributes into a small work block, differences them against the previous position, and emits the difference as a vector word. `loc_c43c` [seen] reads the current slot index `loc_37` and copies that column of four parallel object-attribute tables — `loc_36a`, `loc_35a`, `loc_38a`, `loc_37a` — into the work block `loc_61`/`loc_62`/`loc_63`/`loc_64` (all four writes observed changing). `loc_c423` [seen] does the analogous snapshot from a different table family (`loc_32a`, `loc_31a`, `loc_34a`, `loc_33a`, again indexed by `loc_37`) into the same `loc_61`-`loc_64` block, then falls straight into the emitter `loc_c3ba`.

`loc_c3ba` [seen] forms two 16-bit differences of the work block against the mirror/previous block `loc_6a`-`loc_6d`: `loc_61`-`loc_6a` (with borrow into `loc_62`-`loc_6b`) into the delta slots `loc_6e`/`loc_6f`, and `loc_63`-`loc_6c` into `loc_70`/`loc_71`. It emits the record through `loc_df92`, then latches the current block into the mirror block and stamps the ready/key byte `loc_73` = `0xc0`. `loc_df92` [seen] is where those deltas reach the list: through the cursor it stores `loc_70`, then `loc_71` masked to five bits, then `loc_6e`, and finally a key-folded five-bit last byte `((loc_6f ^ key) & 0x1f) ^ key` where `key` is `loc_73` — so the folded byte carries both the coordinate low bits and the opcode/key from `loc_73`; its stores land in vector RAM with a wide value range. `loc_c3ba`'s sibling `loc_df75` [seen] reaches the same emitter from raw inputs: it sign-extends and widens two bytes by four (`v<<2` into the low byte, the sign and top bit into the high byte) into the `loc_6e`/`loc_6f` and `loc_70`/`loc_71` pairs, then emits via `loc_df92`. `loc_df73` [code] is a thin front for `loc_df75` that first stashes its index byte into the key cell `loc_73` so the fold above picks it up; it drives `loc_df75` and has no own role write.

`loc_c73c` [seen] is a second delta emitter that works directly against the running cursor offset `loc_a9`: it stores the 16-bit difference `(loc_63:loc_64)-(loc_6c:loc_6d)` (high byte masked to five bits) then `(loc_61:loc_62)-(loc_6a:loc_6b)` (high byte masked to five bits and OR'd with the `0xa0` opcode), advancing the offset by four. `loc_c66d` [seen] builds a segment midpoint instead of a raw delta: for the current tube slot `loc_38` and its wrap-around neighbour `(slot+1) & 0x0f` (the 16-segment perimeter wrap), it computes the round-up signed average of each of the two coordinate pairs (`loc_36a`/`loc_35a` with the neighbour, and `loc_38a`/`loc_37a` with the neighbour), stashes the two midpoints into `loc_61`/`loc_62` and `loc_63`/`loc_64`, then appends four bytes through the cursor — `lo2`, `hi2 & 0x1f`, `lo1`, `hi1 & 0x1f` — while mirroring the full (unmasked) midpoints into `loc_6a`-`loc_6d`.

`loc_c6c7` [seen] emits one enemy-slot entry, reached through its per-frame builder. For an inactive slot (`loc_3ac[loc_38] == 0`) it appends four blank/`0x71` pairs from the current cursor offset. For an active slot it seats the depth scratch `loc_57` from `loc_3ac`, runs the depth clamp and math-box passes, seats `loc_56` and `loc_58` from `loc_435`/`loc_445`, folds the deltas through `loc_c73c`, then — depending on bit 6 of the slot's kind byte `loc_39a[loc_38]` — either appends a randomly chosen word (an even offset from the random source `loc_60ca` selects one of two adjacent words in `loc_cec8`/`loc_cec9`, offset `0x1c`) after driving the math-box appender, or lays a fixed marker word `{0x00, 0x68, loc_3db2, loc_3db3}`, advancing `loc_a9` in each case.

`loc_c36e` [seen] draws a whole run of these coordinate records. It skips entirely when its gate byte (A) is nonzero; otherwise it seats `loc_37` = Y and the four record fields from `loc_32a`/`loc_31a`/`loc_34a`/`loc_33a`, lays the shared header (through `loc_c772` at `loc_61`), caches the resulting cursor into `loc_b0`/`loc_b1`, sets the key `loc_73` = `0xc0`, and loops `count`+1 times (`count` = `0x0e` when `loc_111` is nonzero, else `0x0f`; the post-decrement do-while runs the body once more as `loc_38` wraps past zero), decrementing `loc_37` each pass, bumping it by 0x10 whenever its low nibble saturates to `0x0f`, and drawing one record per pass through `loc_c423`. Its role writes were observed changing.

`loc_b56a` [seen] is the simplest emitter: it writes the four-byte record `{0, 0, 0, A}` at the cursor and advances `loc_74`/`loc_75` by four, laying a blank+opcode marker (the fourth byte carries the caller's opcode, e.g. `0xa0`) into the vector buffer; the cursor advance and the low-to-high carry were both observed.

### Header framing and the math-box coordinate pair

`loc_c765` [seen] is an alternate entry into the shared vector builder: it lays the fixed `{0x00, 0x71}` header word at the cursor start, then resumes the shared six-byte coordinate-record build from slot two, so a caller can prepend a header before the standard record. Its two header stores were observed at thousands of distinct cursor addresses in the 0x2xxx display RAM.

`loc_bd3e` [seen] appends a normalized (mantissa, exponent) coordinate pair and is the point where the math coprocessor feeds the vector list. For a small input (`loc_57 < 0x10`) it uses the trivial pair (a = 1, y = 0). Otherwise it forms the 16-bit difference `loc_57 - loc_5f` (with `-loc_5b - borrow` for the high byte) into the math-box operands `loc_6095`/`loc_6096`, issues the compute (`loc_608c` = 0x18, `loc_608e` and `loc_6094` = `loc_a0`), spins on `loc_6040` bit 7 until done, reads the results `loc_6060` into `loc_79` and `loc_6070` into `loc_7a`, sets `loc_608c` = 0x0f, then normalizes `loc_79` into a mantissa-shift count by rotating bits until a 1 rolls out of the accumulator — the shift count becomes the mantissa and `((a>>1) ^ 0x7f) + 1` the exponent. It stores the mantissa-shift count into `loc_78`, then writes the pair through the `loc_74`/`loc_75` cursor at offset `loc_a9`: the exponent, then `(shift | 0x70)`. It returns its exit cursor (`loc_a9 + 2`), which its callers thread into their next stores.

`loc_b69b` [code] builds a slot's screen position and tails into the vector emitter. It loads the slot coordinate `loc_2df[x]`, reads the segment index `loc_2b9[x]`, and seats `loc_56`/`loc_58` from the segment base pair `loc_3ce`/`loc_3de`; when the phase byte `loc_2cc[x]` is negative it interpolates each coordinate toward the next segment `(seg+1) & 0x0f` by scaling the delta through the phase-fraction helper `loc_b6fa` and adding it back. It then runs the math-box pass, lays the `loc_c765` header, resets `loc_a9` to zero, calls `loc_bd3e` to append the pair and takes back its exit cursor, and finally reads a template word from `loc_cec8`/`loc_cec9` (indexed by the frame's low bits `loc_3`) and emits it through `loc_df59` at the threaded cursor. `loc_b69b` has no role-defining own write of its own — all its output goes through the helpers — and its phase-interpolation branch, which is the only caller of `loc_b6fa`, did not run in the capture, so that scaling path is read from the code.

`loc_bd09` [seen] follows the same shape: it runs the math-box pass, lays the `loc_c765` header, resets `loc_a9`, and appends the pair via `loc_bd3e`, taking its exit cursor. It then clamps the colour/intensity nibble from `loc_78` (XOR `0x07`, shift left, floor at `0x0a`, shift into the high nibble), stores that byte and a `0x60` opcode byte at the threaded cursor, records the advanced length back into `loc_a9`, and reloads the entry template from `loc_cec8`/`loc_cec9` (indexed by `loc_55`) before tailing into `loc_df59`; its role writes were observed. `loc_bcfd` [seen] is its front end: it stashes the value byte into `loc_55`, loads two indexed table entries `loc_435[y]`/`loc_445[y]` into the work cells `loc_56`/`loc_58`, then emits through `loc_bd09`.

### Glyph, digit, and bit-pattern runs

A parallel emitter path writes text and numeric glyphs by looking each nibble up in the ROM stroke-word table `loc_31e4` (two bytes per entry). `loc_a9fc` [seen] is the innermost step: it maps A's low nibble to an index — a zero nibble with carry set indexes entry 0, otherwise `nibble + 1` — and stores a **single** byte from `loc_31e4` at index `2*y` into the `loc_2f60` glyph buffer at cursor X, then advances X by two (so it fills the even cursor slot and leaves the odd slot). `loc_a9d7` [seen] drives it over three source bytes: it seeds the pass counter `loc_2a` = 2, and for each byte emits the high nibble then the low nibble through `loc_a9fc`, chaining the carry so it stays set only across zero nibbles and is forced clear on the final pass, while walking the source pointer `loc_3b` backward one byte per iteration. `loc_a97f` [seen] is the producer that feeds it: keyed by Y, it writes a `0x71`-tagged header (A OR `0x70`, zeroed only when Y hits the marker `loc_3d` and bit 7 of `loc_5` is set) at the buffer index from `loc_cdde[y]`, fills six more glyph cells from `loc_cde0[y]` with either `loc_3284` (rows within the count `loc_48[y]`, held in `loc_38`) or `loc_3286` (rows past it), then — unless the state cell `loc_00` is 4 and Y is away from the marker — seeds the glyph source pointer `loc_3b` = `loc_a97d[y]`, `loc_3c` = 0, and hands off to `loc_a9d7`.

The other glyph path emits full word pairs into the `loc_74` cursor rather than single bytes into `loc_2f60`. `loc_dfb1` [seen] drives it heavily: it emits a run of `loc_ae + 1` zeropage bytes, top index `A + Y - 1` and stepping downward (source index tracked in `loc_af`, remaining count in `loc_ae`), sending each byte's high nibble then low nibble through `loc_df19`, and chaining the carry so only the final low nibble sees it cleared as the terminator marker. Several thin callers preset `loc_dfb1`'s run: `loc_aa9e` [code] increments the slot index, publishes it through `loc_61`, and emits a one-byte run at `loc_61`; `loc_af77` [code] packs the incoming binary value to BCD (into `loc_29`, via the double-dabble converter) and emits that single byte's two nibbles; and `loc_b0c6` [code] selects a pointer from the table via `loc_91b5` and then emits a three-byte zeropage run starting at `loc_29`. Each of these is a caller whose role rests on the code, with no own role-defining write beyond the constant index bookkeeping.

`loc_d8a9` [code] combines both worlds: it stashes A into `loc_29`, scales the two coordinates (Y, X) into the delta pair through `loc_df75` (which emits a scaled coordinate record), then emits the stashed byte as a single-entry run through `loc_dfb1`. `loc_dd2b` [code] draws a coordinate then a bit pattern: it stashes Y into `loc_35`, emits the scaled coordinate through `loc_df75`, sets `loc_37` = 7, and shifts `loc_35` left MSB-first eight times, emitting each shifted-out bit as one vector digit via `loc_df1f`. `loc_dd29` [code] is a front for it that presets the coordinate register to the fixed slot `0xf8`. All three drive their emitters and have no role-defining own write in the capture.

### The two EAROM routines carried in this list

Two routines here belong to the high-score EAROM (NVRAM) sequence rather than to vector emission, and are described honestly as such. `loc_db5a` [code] checks the two guard bytes `loc_1ca` and `loc_1c7`; only when both are clear does it run the EAROM walk seeder `loc_de11` and then stamp `loc_7c` = `loc_1c9` and `loc_0` = 2. In this capture that seeding path was never taken — the guard was nonzero (or the routine unreached) whenever it was hit — so it is read from the code. `loc_dded` [code] is a branch-only trampoline that hands the mask value `0x03` to `loc_ddf3` (which routes to the EAROM op-request writer `loc_ddff`, where `loc_1c7` and `loc_1c8` are OR'd with the mask); `loc_dded` performs no write of its own and its `0x03` mask value was not observed in the capture, so it stays [code] even though the downstream request flags are seen changing elsewhere.

## Enemy spawning and lane selection

This subsystem decides *when* a new adversary appears on the tube, *which* segment (lane) it enters on, and how the pool of live climbers is kept in step with the per-slot arrays the rest of the machine reads. It runs across several parallel tables keyed by a slot index: the per-slot depth/liveness table `loc_2df`, the segment (lane) index `loc_2b9` with its successor `loc_2cc`, the per-slot flag bytes `loc_28a` and `loc_283`, the spawn timer `loc_2a6`, and the auxiliary bytes `loc_291`. Alongside the enemy slots sits a smaller eight-entry table of timed transient objects (`loc_302`/`loc_30a`/`loc_2fa`/`loc_312`) that the same spawn/retire events feed.

### Seeding a wave's random tag table

At the head of a wave `loc_9246` [seen] wipes a 64-byte tag region by walking `loc_243+x` from index `0x3f` down to `0`, storing zero into every cell. It then counts down from `loc_3ab - 1` and, for each slot, draws the low nibble of the POKEY random source (`loc_60ca & 0x0f`), writing that nibble into the per-slot byte `loc_203+x` and packing a tag `(x << 4) | nibble` into `loc_243+x` — substituting `0x0f` whenever that packed value would come out zero, so the tag is always non-zero. The write-tap shows both tables filling: `loc_203` with random nibbles pulsing across the `0x0`–`0xe` range and `loc_243` with the packed slot-tag values, so the routine is grounded.

### Allocating and seeding a fresh enemy slot

`loc_994d` [seen] is the slot allocator. It parks the incoming Y in `loc_36`, loads the scan cursor from `loc_11c`, and walks the liveness/depth table `loc_2df` downward looking for a free entry; if the scan runs past index 0 (the index goes negative, `y & 0x80`) it reports `0x00` — no slot free. On a hit it commits the new adversary into the parallel arrays at that index: the depth cell `loc_2df+y` takes the staged value from `loc_29`; the segment index `loc_2b9+y` takes the value in `loc_2a`, except that when `loc_2a` reads `0x0f` *and* the global gate byte `loc_111` has bit7 set, the segment is instead randomized to `loc_60ca & 0x0e` (an even POKEY-random column); the successor segment `loc_2cc+y` is set to `(segment + 1) & 0x0f`; the spawn timer `loc_2a6+y` is cleared to zero; the flag byte `loc_28a+y` takes `loc_2c` and `loc_291+y` takes `loc_2d`; and the primary flag/lane byte `loc_283+y` takes `loc_2b`. It then bumps the active-slot count `loc_108` by one, extracts the lane as `loc_2b & 0x07`, and increments the per-lane occupancy counter `loc_142+lane`. It reports `0x10` on success. All of these field writes are observed changing on the write-tap.

### Choosing a candidate lane

`loc_9abb` [seen] selects a lane from a short candidate list. It seeds a starting index from `loc_60ca & 0x03` (POKEY random), sets a countdown of `0x04` in `loc_2b`, and stashes the caller's X in `loc_39`. It then loops: each pass decrements the `loc_2b` countdown and bails with `0x00` if it underflows (bit7 set); otherwise it steps the wrapping index down by one, wrapping back to `0x03` at the top, reads the candidate lane `loc_149+y`, promotes the value `0x03` to `0x05`, and accepts the lane only when its occupancy byte `loc_13c+idx` is non-zero (an occupiable lane qualifies). On a hit it forms `loc_149[y] | 0x40` into the scratch pointer-low `loc_2c`, reads the list-high byte from `loc_9afd+2` into `loc_2d`, records the tag `0x02` in `loc_2b`, and reports `loc_29`. The `loc_2b` countdown steps and the X stash into `loc_39` are observed, grounding the routine.

### Choosing a target segment by the deepest column

`loc_a028` [code] picks a new segment for slot x by finding the most open column of the tube. It clears the running-best depth `loc_2d`, primes a 16-count loop counter `loc_140` to `0x0f`, and starts the scan at a random column `loc_60da & 0x0f` (the second POKEY random). Each pass reads a column depth from `loc_3ac+y`, treats an empty column (depth 0) as maximal (`0xff`), and keeps the column whose depth is greatest-or-equal in `loc_2d` with its column index recorded in `loc_29`; the final column `0x0f` is skipped while the gate `loc_111` is non-zero. When the counter `loc_140` underflows, the winning column becomes the slot's segment `loc_2b9+x` and successor `loc_2cc+x` (`winner+1` mod 16), and bit7 of the flag `loc_28a+x` is cleared. This routine is not reached in the capture — it is reached only through the far-limit branch of `loc_9fc4` below, which did not fire — so its role rests on the code.

### Advancing a slot toward its column and re-parking it

`loc_9fc4` [seen] runs the per-slot approach step. It raises `loc_10c` to 1, reads the slot's column from `loc_2b9+x`, and seeds an empty column cell `loc_3ac+col` to `0xf1`. It then keeps that column cell as the running *minimum* of the slot's own depth `loc_2df+x`: when the slot depth is below the column cell it copies the depth in and tags a fresh minimum by writing `0x80` into `loc_39a+col`. From there it branches on the slot depth: a depth below `0x20` is treated as too shallow — it forces bit7 of `loc_28a+x` and clamps the depth up to `0x20` before returning; a depth in the mid-range (below `0xf2`) returns with nothing further; and a depth at or past `0xf2` means the slot has reached the far limit, at which point it picks a fresh column via `loc_a028`, re-parks the depth at `0xf0`, and — only when `loc_3ab` is zero — rewrites the slot's flag low bits `loc_28a+x` to `…01` and the primary flag `loc_283+x` low bits to `…02`, dropping `loc_10c` back to 0. The `loc_10c` write, the column-cell seeding and the fresh-minimum tag are all observed.

### Stepping a slot around the rim (segment / direction)

The per-slot segment step has a guarded full entry and a shared body. `loc_9e5c` [seen] is the full entry: it first runs the gated bit6-keeper `loc_9eab`, then continues into the shared body `loc_9e5f`; the guard-less mid-entry `loc_9e5f` [seen] is the body alone. `loc_9e5f` first forces bit7 on the flag `loc_283+x` (a persistent write back to that cell) and reads the low three bits as the segment. For an ordinary segment (not 4): if bit6 of the flag is set it steps the segment index `loc_2b9+x` up by one (mod 16); it then looks the resulting index up through `loc_9ed7` (which selects a half-turn when bit6 is set) and stores that bit7-forced direction byte into the successor `loc_2cc+x`. For the seam segment 4: with bit6 set it steps `loc_2b9+x` *down* one (mod 16) and stores `0x87`, and with bit6 clear it leaves the index alone and stores `0x81`, again into `loc_2cc+x`. The bit7 flag write and the `loc_2cc` stores are observed.

`loc_9eab` [code] is the bit6 keeper, active only while the gate `loc_111` is non-zero. Reading the flag `loc_283+x` and the segment `loc_2b9+x`, it clears bit6 (`& 0xbf`) once the segment reaches `0x0e` while bit6 is set, and sets bit6 (`| 0x40`) only while the segment is 0 when bit6 is clear. Neither conditional write fired in the capture — the gate/segment conditions went unmet — so the routine is not exercised here and its role is read from the code.

`loc_9ed7` [code] is the direction lookup used by `loc_9e5f`. It is a pure compute helper with no cell of its own: it returns `loc_3ee[y] | 0x80`, or, when bit6 of the caller's value is set, the half-turn `((loc_3ee[(y-1)&0x0f]) + 8) & 0x0f | 0x80`. Having no own write, it can only be grounded from the code.

### Promoting armed slots into live climbers

`loc_a2a6` [seen] is the spawn loop that turns armed source slots into live enemies. It bails immediately if `loc_201` has bit7 set. Otherwise it walks the seven source slots x = 6…0, skipping any whose depth `loc_2df+x` is zero or below the `0x30` threshold, or whose flag `loc_28a+x` lacks bit6. For a qualifying slot it decrements the spawn timer `loc_2a6+x` and acts only when that timer underflows (bit7 set), immediately restoring the timer by one; it then skips the slot if the primary flag `loc_283+x` has bit7 set, and applies the per-wave difficulty gate — the roll `loc_60ca` must be at least the table value `loc_a304[loc_a6]`, where `loc_a6` is the running count of live climbers, so the gate stiffens as more enemies are already on the tube. Passing that, it scans the destination slots from `loc_11a` for the first free entry (`loc_2db+y == 0`) and copies the spawn fields across: depth `loc_2df+x` → `loc_2db+y`, segment `loc_2b9+x` → `loc_2b5+y`, successor `loc_2cc+x` → `loc_2c8+y`; it reseeds the source timer `loc_2a6+x` from `loc_119`, cues the fixed sound through `loc_ccbd`, and bumps the live-climber count `loc_a6`. These field writes and the count bump are observed.

### The eight-slot timed-object table and its drivers

Underneath the enemy slots is an eight-entry table of timed transient objects with parallel type `loc_302`, position `loc_30a`, lane `loc_2fa`, and counter `loc_312` fields, plus a live-count/pending byte `loc_116`. What these objects represent in play is not settled by the code (their insertions ride alongside sound cues at enemy spawn and retire events); the mechanism itself is precise.

`loc_a3d6` [seen] inserts one object: it saves X/Y in `loc_35`/`loc_36`, zeroes the tracking pair `loc_2a`/`loc_2b`, and scans slots 7…0 for a free entry (`loc_30a+i == 0`), reusing the first found; failing that it evicts the slot holding the largest counter `loc_312+i` (tracked in `loc_2a`/`loc_2b`) and drops `loc_116` by one. Into the chosen slot it writes counter `loc_312 := 0`, type `loc_302 := loc_2c`, position `loc_30a := loc_29`, lane `loc_2fa := loc_2d`, and bumps `loc_116`. The real field writes are observed. `loc_a3d4` [code] is the thin front door: it stores A into the scratch type field `loc_2c` and falls into `loc_a3d6`; it is reached, but its own `loc_2c` write held a constant (`0`→`0`) across the capture, so it grounds only from the code.

`loc_a416` [seen] ages the table each pass. If the pending byte `loc_116` is zero it does nothing; otherwise it clears `loc_116` and, for every live slot (`loc_30a+i != 0`), advances the counter `loc_312+i` by the per-type step `loc_a44e[type]`; a slot whose counter reaches its per-type limit `loc_a448[type]` is freed (`loc_30a+i := 0`), while any slot still short re-raises `loc_116` for the next pass. The counter advance and the `loc_116` re-raise are observed.

Several event handlers drive that table by staging the scratch fields and then inserting. `loc_a34b` [seen] primes a fresh top-priority object: it seeds the flag `loc_13b` to `0xff`, sets the type scratch `loc_2c` to `0x01`, copies the current descriptor `loc_202`→`loc_29` (source) and `loc_200`→`loc_2d` (target), rings the sound gate through `loc_ccb0`, inserts through `loc_a3d6`, and raises the ready flags `loc_201 := 0x81` and `loc_13c := 0x01`. Its role write into `loc_2d` (and the `loc_2c`/`loc_29`/`loc_201`/`loc_13c` writes) are observed on the tap, grounding the routine; the distinctive head values — `loc_13b = 0xff` and the type-`0x01` seed — are code-supported but were not among the write-tapped changes. `loc_a1e4` [code] guards that priming: it primes the top object through `loc_a34b` only when the live descriptor `loc_200` equals the slot's target `loc_2ad+x` and the ready flag `loc_201` does not already have bit7 set, then latches `loc_201 := 0x81`; it left no role-defining write in the capture, so its role rests on the code.

`loc_a36f` [seen] retires the object in slot Y: it fires the sound gate `loc_ccc1`, stages source `loc_2db+y`→`loc_29` and target `loc_2b5+y`→`loc_2d`, re-inserts a zeroed (type `0x00`) object through `loc_a3d4`, clears the retired slot `loc_2db+y := 0x00`, drops the live-climber count `loc_a6`, and flags lane X spent with `loc_2f2+x := 0xff`. Its own writes — the cleared `loc_2db+y`, the decremented `loc_a6`, and the `loc_2f2+x` flag — are observed. `loc_a3ca` [seen] is the sibling insert-with-cue: it rings the same `loc_ccc1` sound gate, copies the y-indexed depth byte `loc_2df+y` into the scratch source `loc_29`, and inserts through `loc_a3d4`; the observed source-byte copy grounds it.

## Enemy motion and the pursuit AI

The enemy field lives in a bank of sixteen slots indexed high-to-low, and `loc_a618` is the per-frame engine that walks them. It opens by copying the spawn-budget countdown `loc_10e` into the frame-active flag `loc_10d`, then loops `x` from 0x0f down to 0. A slot counts as occupied when its primary flag byte `loc_283`,x is nonzero; for such a live slot it integrates the object's motion (`loc_a6a9`) and then relaxes its velocities (`loc_a721`, whose returned whole byte it keeps in a register), and it forces `loc_10d`=0xff to record that the frame had life in it. A slot whose `loc_283`,x is zero is free, and if the countdown `loc_10e` is still nonzero the routine spawns a fresh enemy into it (`loc_a65b`), handing across that carried register. After the sweep it settles the slot counter `loc_37`=0xff, and on even frames only (`loc_3` bit0 clear) with budget remaining it decrements `loc_10e` by one, throttling how fast the tube keeps feeding objects. If nothing was live and nothing spawned (`loc_10d` still zero) it raises the mode-request byte `loc_0`=0x12 to hand control on. This whole driver's writes are constant across the capture (code).

`loc_a6a9` integrates one slot across three motion axes, and its structure is uniform per axis: a fraction cell accumulates the velocity-low byte (axis 0: `loc_223` += `loc_2e3`; axis 1: `loc_203` += `loc_2c3`; axis 2: `loc_243` += `loc_303`), and the whole coordinate is then formed as the signed velocity-whole byte plus the current coordinate plus the fraction's carry (axis 0 uses velocity `loc_343` over coordinate `loc_283`; axis 1 velocity `loc_323` over `loc_263`; axis 2 velocity `loc_363` over `loc_2a3`). Each axis tests the tube-ring boundary against the velocity's sign — a non-negative axis overflows when its new whole reaches >= 0xf0, a negative axis when it drops below 0x10. Axes 1 and 2 always store their computed whole into `loc_263`,x and `loc_2a3`,x, but axis 0's whole is special: it is forced to 0 both on its own overflow and whenever axis 1 or axis 2 overflows, and only then written to `loc_283`,x. Because `loc_283`,x nonzero is exactly what marks the slot live in `loc_a618`, an object that rings past any axis boundary has its axis-0 coordinate zeroed and is thereby retired from the field — the "reaches the end of its run" event. This routine's role writes are code-only in this capture (code).

`loc_a721` supplies the velocity decay that eventually settles a moving object. It seeds a saturation counter `loc_29`=0xfd, then steps each of the three velocity pairs toward zero through `loc_a75d` — axis 1 (`loc_2c3`/`loc_323`), axis 0 (`loc_2e3`/`loc_343`), axis 2 (`loc_303`/`loc_363`) — writing each stepped low/whole pair back. Each axis that crosses zero bumps `loc_29`; since three saturations carry 0xfd up through 0x00, the counter lands on zero exactly when all three axes have stalled, at which point the routine clears the slot's coordinate/flag byte `loc_283`,x, freeing the slot. `loc_a75d` itself is the single-axis primitive: it stashes the whole byte in `loc_2b`, reads the fixed increment `loc_a788` (=0x20), and pushes a signed 16-bit velocity toward zero — adding the step when the whole is negative, subtracting it otherwise — and on the carry/borrow that signals a zero crossing it saturates, bumping `loc_29`, forcing the low byte `loc_2a`=0 and returning both bytes zeroed. Neither of these two makes an own-cell write in the capture (code for both).

Spawning is `loc_a65b`. It seeds the three coordinate cells to the ring midpoint (`loc_263`,x, `loc_283`,x, `loc_2a3`,x all = 0x80) and then fills the three velocity pairs from the RNG cells `loc_60da`/`loc_60ca`: axis 1 low `loc_2c3`,x = `loc_60da` with a signed random whole `loc_323`,x; axis 0 low `loc_2e3`,x = `loc_60ca` with a whole `loc_343`,x that is forced non-positive (a positive draw is negated, an already-negative one kept); axis 2 low `loc_303`,x = `loc_60ca` with a signed random whole `loc_363`,x. The forced-negative axis-0 velocity is what makes every new object march the depth axis downward toward the near rim (into `loc_a6a9`'s "< 0x10 resets" boundary), i.e. climb the tube toward the player, while the other two axes drift randomly. It closes by firing the spawn sound cue `loc_ccc1`. The signed random magnitudes come from `loc_a69b`, a pure leaf that reads a 3-bit magnitude (`loc_60da` & 0x07, so 0..7) and negates it when its incoming value has bit 0 set, yielding a nudge in [-7, +7]. Both spawn and its random helper are code-only here — `loc_a65b` did not run in this capture, so its role rests on the code (code); `loc_a69b` never writes memory at all (code).

A second, distinct use of the same slot byte drives the rim-walking pursuit — the flipper-style enemies that hop between adjacent lane segments toward the player. Here `loc_283`,x is read as a packed field (low three bits a kind code, bit 6 a travel-direction/side flag, bit 7 a sign), rather than as the raw coordinate the free-object path treats it as. The shared distance primitive is `loc_a7a6`: it computes A minus Y, stashes it in `loc_2a` (observed changing, seen), and then either keeps the full signed byte when geometry flag `loc_111` has bit 7 set or masks to the low nibble and sign-extends bit 3 otherwise — the nibble path giving modular rotational distance around a 16-segment ring, the full-byte path an open span. `loc_9d67` uses it to record which side a target lies on: it takes slot x's target segment `loc_2b9`,x, diffs the shared player segment `loc_200` against it, and then clears bit 6 of `loc_283`,x when the difference is negative or sets it otherwise (code). `loc_9c4f` simply toggles that same bit 6 in place and returns the new byte; its bit-6 XOR of `loc_283` is observed changing in the capture (seen).

Those two combine in `loc_9f81` and its siblings, the per-slot segment-flip step. `loc_9f81` re-derives the direction bit from the current target side (`loc_9d67`) and then toggles it (`loc_9c4f`) before running the shared tail; the alternate entry `loc_9f8a` instead reseeds bit 6 from a random bit (`loc_60ca` & 0x40). The shared tail `step9f99` only acts on a live board (`loc_111` nonzero): it reverses direction at the ends of travel — flipping bit 6 of `loc_283`,x when the slot's rim segment `loc_2b9`,x has reached 0 while travelling one way (bit 6 set) or reached >= 0x0f the other way — then marks a pending step by writing `loc_10b`=0x66 and advances through `loc_9e5f`. The whole `loc_9f81` family's own writes are constant or land via its callees in the capture (code). When one of these tube objects reaches its target depth, `loc_9c58` calls `loc_9d06` (settle at target). It stashes the shared target depth `loc_202` into `loc_2df`,x, then branches on kind: a kind-1 slot with gate byte `loc_3ab` set just flips bit 7 of `loc_28a`,x and stops; a negative slot (`loc_283`,x bit 7) merely bumps its stashed depth `loc_2df`,x and stops; otherwise it decrements `loc_108`, and — when the pass flag `loc_109` equals 1 — scans slots 6..0 for a non-empty, non-self entry whose stashed byte matches the shared `loc_202`, copying that matched slot's bit 6 inverted into `loc_283`,x (coordinating its flip direction against a neighbour), or else falls back to `loc_9d67`; finally it writes `loc_10b`=0x41 and increments `loc_109`. The target-clamp stash into `loc_2df`,x and the cross-slot bit-6 copy are both observed (seen).

`loc_97c5` is the aim/steer heuristic that turns the shooter toward the nearest object — the auto-aim used by the demo. It scans the slot depth table `loc_2df`[0..count `loc_11c`] for the smallest nonzero entry, holding the running minimum in `loc_29` and its slot index in `loc_2a` (0xff meaning none seen). If none was found it returns the last entry examined; otherwise it feeds that slot's segment `loc_2b9`[idx] and the player segment `loc_200` through `loc_a7a6` and returns a spinner delta by the sign of the rotational difference — 0x00 when already aligned, 0x09 when the target is on one side, 0xf7 on the other. Its consumer `loc_9749` reads that as the spinner nudge. Both this scanner and its distance helper are exercised (seen).

Beneath the walk sits a slot-pacing timer chain that governs when objects are released and advanced. `loc_c9af` ticks the active slot: it clears `loc_4`, decrements the active slot's countdown `loc_48`,x (x = `loc_3d`), and when the `loc_48`|`loc_49` pair is fully spent it finalizes through `loc_c9f1` and returns. Otherwise, if the current slot's countdown just hit zero it flags `loc_1`=0x0c and `loc_4`=0x28, then walks the selector `loc_3f` — toggling its low bit (gated by `loc_3e`) until it lands on a non-empty slot — and arms that slot's timers, deriving `loc_2` from the slot's `loc_46`,x entry (0x1c when the incremented value wraps to zero, else 0x02) and setting `loc_0`=0x0a. It is reached through a computed-jump dispatch rather than a textual caller (seen). `loc_c9f1` is the peak/timer pacer it finalizes into: it scans the zero-page window `loc_46`,x for x = `loc_3e`..0, takes the maximum into `loc_126`, decrements that when nonzero, and then sets the timer cell `loc_0` to 0x10 when status `loc_5` is negative or 0x14 otherwise — the peak taking a real 0->1 and decrementing 1->0 across the capture (seen).

`loc_c81b` derives and applies a pending advance step, though its precise game meaning is not fully resolved from the code (flag). From bits 5/6 of gate `loc_4e` (which it then clears) and a >= 2 test on counter `loc_6` it computes a step of 0..2, draining `loc_6` by that amount, and stores the step in `loc_3e`. When the gate is clear it may instead seed four intro cells (`loc_1`=0x10, `loc_4`=0x20, `loc_0`=0x0a, `loc_2`=0x14) and clear `loc_50`/`loc_123`. ## The mathbox: projection and level tables

Tempest draws its tube in perspective, and the arithmetic that turns a lane's flat geometry into a viewed point is handed to a hardware coprocessor — the "math box" — mapped into the $6040–$6096 register window: $6040 carries a busy flag in bit 7, the operand registers around $6080–$6096 are loaded to start a computation, and the two result bytes come back at $6060 (low) and $6070 (high). This subsystem does two related jobs: it unpacks each level's shape tables out of packed ROM into working RAM, and it drives the math box to project every lane of that shape into the small per-lane coordinate deltas the display builder consumes.

### Unpacking the per-level shape tables

`loc_c196` (`unpackLevelNibbleTables`, [seen]) turns a level selector into a pair of nibble tables. It reads the selector cell loc_9f, keeps its bits 4–6 (`& 0x70`), and clamps that to at most 0x5f, then forms a ROM index `x = (sel >> 1) | 0x07`. Walking `y` from 7 down to 0 it reads one packed byte from ROM table loc_c1fd (decrementing `x` each pass) and splits it: the low nibble is written both to zero-page loc_19+y and to its display mirror loc_800+y, while the high nibble goes to loc_21+y and its mirror loc_808+y. A single pass fills all four eight-entry tables with real, level-dependent values, so the routine is grounded as the producer of the current shape's packed-nibble descriptor.

`loc_c2e8` (`packTableByteFromValue`, [seen]) is the small selector helper that both chooses a geometry entry and re-packs a byte. Given an input value it first guards against out-of-range indices — anything `>= 0x62` is discarded in favour of a masked hardware value, loc_60ca (a POKEY register) `& 0x5f`, a random/timer fallback. It then splits the value into a quotient `X = value >> 4` and remainder `value & 0x0f`, uses the remainder to look up ROM table loc_bc7c, stores that looked-up byte to loc_112, and returns the byte repacked into the high nibble with the low nibble forced to 0x0f (`(entry << 4) | 0x0f`), with the quotient in X and the remainder in Y. The write to loc_112 is observed changing, so the store is role-defining; loc_112 is the surviving table-entry index the geometry builder reads back.

`loc_b888` (`loadLevelTablesAndArmVectorTail`, [code]) chains the unpack to a display step: it calls `loc_c196` to rebuild the packed nibble tables, then seats the vector-list tail cursor, writing loc_139 = 0x7f and loc_13a = 0x04. That cursor is the one the tail emitter `loc_b896` reads (it stamps a tail record into the AVG vector RAM and steps the cursor down by 0x20). This routine is not reached in the capture — neither the loc_139 nor the loc_13a seed (0x7f, 0x04) was ever observed — so the cursor-arming role is read from the code only; it is a computed-dispatch/jump-table target rather than a routine with a located call site.

### Building the tube's per-lane coordinates

`loc_c235` (`buildLevelTubeLaneCoordinates`, [seen]) runs once when a level's geometry is laid down and produces the full per-lane vertex geometry for the current tube. It first reduces the selected slot — the byte at loc_46 offset by loc_3d — through `loc_c2e8`, keeping that routine's returned seed and reading back the chosen table index `y` from loc_112. Indexed by `y` it pulls a span from ROM: loc_bc8c[y] is negated into both loc_5f and loc_5d, its complement `0x10 - that` into loc_a0, loc_5b is armed to 0xff, loc_60 takes loc_bc9c[y], and loc_111 takes loc_bccc[y]. The offset pair loc_68/loc_69 is handled two ways: when mode cell loc_2 equals 0x1e the routine copies loc_bcac[y]/loc_bcbc[y] straight in; otherwise it forms the signed 16-bit difference `{bcbc[y]:bcac[y]} - {loc_69:loc_68}`, shifts it right four bits (rotating the high byte's low bits down into the low byte), and stores the low byte as the level's geometry scale in loc_121 (observed climbing to a real nonzero value). It then clears loc_66/loc_67/loc_10f/loc_110 and sets loc_113 = 0x2c.

The heart of the routine is a sixteen-pass loop (`x` from 0x0f down to 0) that lays down the tube's base coordinates: for each lane it copies loc_b97c[ny] into base-coordinate table loc_3ce+x and loc_ba7c[ny] into loc_3de+x, zeroes the projection output cells loc_31a+x / loc_33a+x / loc_39a+x, and copies loc_bb7c[ny] into loc_3ee+x — with the ROM read index `ny` walking downward from the seed returned by `loc_c2e8`. A final sixteen-pass then produces the midpoint tables: each column is rounding-averaged with its wrap-around neighbour (`(x+1) & 0x0f`) — sum the two bytes plus one and rotate the ninth bit back into bit 7 — writing loc_435+x from the loc_3ce pair and loc_445+x from the loc_3de pair. Grounding confirms the base tables loc_3ce/loc_3de, the neighbour-averaged tables loc_435/loc_445, the scale loc_121, and the span cells loc_5f/loc_5d all fill with real values.

### Resetting and driving the math box

`loc_c1c3` (`resetMathboxAndAccumulators`, [seen]) is the pre-projection clear, run on essentially every projection pass. It zeroes the zero-page work cells loc_81, loc_91, loc_80, loc_78, loc_90, loc_88, and then zeroes the math-box input block across loc_6080, loc_6081, loc_6083, loc_6084, loc_6085, loc_6086, loc_6087, loc_6089, loc_608d, loc_608e, loc_608f, loc_6090 — leaving loc_6082, loc_6088, loc_608a and loc_608b untouched — before writing the one control register loc_608c = 0x0f. `loc_c453` (`snapValueUpToReference`, [seen]) conditions one coordinate operand just before it is fed to the math box. It returns immediately if guard byte loc_5b is nonzero, and again if loc_57 already sits 0x0c or more above the reference loc_5f; otherwise it snaps loc_57 up to `loc_5f + 0x0f`, capped at a ceiling of 0xf0. Its callers are the enemy-slot and per-lane vector emitters loc_c6c7 and loc_c30d.

`loc_c098` (`projectScaledPointViaMathbox`, [seen]) is the projection driver for one point and is heavily exercised. It first forms the 16-bit delta `loc_57 - {loc_5b:loc_5f}` into the operand registers loc_6095 (low) and loc_6096 (high), and when that delta goes negative it substitutes a `+1` clamp (loc_6096 = 0x00, loc_6095 = 0x01). It then computes two absolute offsets with their signs: `|loc_58 - loc_60|` with sign flag loc_33, issued into loc_608e and loc_6094 to start the coprocessor, and `|loc_56 - loc_5e|` cached in loc_32 with sign flag loc_34. After spinning while loc_6040 bit 7 stays set, it reads the first result (loc_6060 → loc_63, loc_6070 → loc_64), re-issues loc_32 through loc_608e/loc_6094 for the next computation, and folds an offset pair into that accumulator: gated by the sign flag loc_33 it either subtracts loc_63/loc_64 from loc_68/loc_69 or adds loc_68/loc_69 into it, with signed 16-bit saturation to 0x8000 on underflow and 0x7fff on overflow. It waits again, reads the second result into loc_61/loc_62, and folds loc_66/loc_67 into it under sign flag loc_34 with the same saturating add/subtract. The two 16-bit results (loc_63/loc_64 and loc_61/loc_62) are the projected, offset-folded coordinate components. Grounding observes the operand write to loc_6095 and the sign flag loc_34 both changing.

`loc_c473` (`projectLanePointsToSlotCoordTables`, [seen]) is the loop that projects the whole tube. It saves its arguments (the point value into loc_57, the output cursor into loc_38), clears the clamp tally loc_59, and seeds the lane counter loc_37 = 0x0f. For each of the sixteen lanes it loads that lane's base coordinates from loc_3ce[col] into loc_56 and loc_3de[col] into loc_58, calls `loc_c098` to project the point, and then clamps each of the two accumulator results down to the small signed window −4..+3 (bytes 0xfc..0x03). A value already in range keeps its paired byte; a value at or above 0x04 is pinned to 0x03 with sign byte 0xff, and a negative value below 0xfc is pinned to 0xfc with sign byte 0x01, each such saturation bumping loc_59. The clamped value/sign pairs are written into the parallel per-lane tables indexed by the descending cursor loc_38: the first pair into loc_31a and loc_32a, the second into loc_33a and loc_34a. It returns the clamp count in loc_59. These four tables are the compact per-lane perspective deltas the display list is built from; its caller is loc_c30d.

`loc_ca48` (`setModeFlagBitAndScale`, [seen]) sets a rendering mode bit and a companion scale byte. It defaults to `(a = 0x00, y = 0x10)` and switches to `(a = 0x04, y = 0x08)` only when both gates loc_117 and loc_3d are nonzero. It then folds bit 2 of the chosen `a` into flag loc_a1, preserving that flag's other bits, and stores `y` into the scale cell loc_b4. Both writes are observed, but only the default arm ran in the capture — loc_a1's bit 2 stayed clear and loc_b4 took 0x10 — so the alternate (a = 0x04) selection is read from the code rather than seen.

## Sound, POKEY and the interrupt heartbeat

Tempest's audio lives on the two POKEY chips mapped into the $6000 hardware page (POKEY 1 at $60c0-$60cf, POKEY 2 at $60d0-$60df), and it is driven by two engines that fire on every interrupt plus a request path that any game routine can poke. This section follows the heartbeat first, then the sound engine it feeds, then the request path that seeds it, and finally the neighbouring $6000-page devices (the config switches, the packer, the math box) and the per-channel record machinery that shares the same slot cells.

### The interrupt step: loc_cf24

`loc_cf24` [seen] runs on essentially every interrupt, reached from the interrupt handler at loc_d704 immediately before the sound stepper `loc_cd0a`. It advances three parallel lanes indexed `X = 2, 1, 0`, each lane individually enabled by a distinct bit of the control byte `loc_8`: lane 2 is gated by bit 0, lane 1 by bit 1, lane 0 by bit 2 (the code selects the bit by shifting `loc_8` right once, twice, or three times respectively and testing the carry out). When a lane is enabled its position cell — `loc_d`, `loc_e`, `loc_f` at `loc_d + x` — is nudged one step and kept inside a five-bit range: the value is masked with `0x1f`, stepped up (adding `0x20` and wrapping on the enable path) or clamped/decremented, so it circulates modulo `0x20`. Each lane also carries a countdown timer at `loc_10 + x` that is reloaded to `0x78` when it expires, and a counter at `loc_13 + x` that is bumped as the lane accumulates. Along the way the routine folds a per-lane contribution into a running trio of accumulators `loc_16`/`loc_17`/`loc_18` (and, on one branch, nudges `loc_6`) through a subtraction against the ROM table `loc_cfd9` indexed by the high bits of `loc_9`. The routine closes with two clamp passes over the `loc_13` lane triple, and these two passes subtract **different** constants: the first pass is gated on the lane value being `>= 0x10` and subtracts `0x10` (adding `0xef` with carry set), while the second pass is gated on the lane value being nonzero and subtracts `0x11` (adding `0xef` with carry clear). The dense branch web is walked block by block with an explicit `carry` variable standing in for the 6502 carry flag; the embedded fall-through into the ROM data table past `loc_18` wrapping is guarded as unreachable in a valid state.

### The sound engine: loc_cd0a → POKEY

`loc_cd0a` [seen] is the per-frame sound voice stepper, run right after `loc_cf24` on the interrupt. It walks all sixteen voice slots from `X = 0x0f` down to `0`. A slot with a zero frame byte at `loc_c0 + x` is idle and skipped, and the one slot whose index equals the reservation cell `loc_bf` is also skipped. For a live slot it counts down the fast timer `loc_e0 + x`; while that is still nonzero the slot is left alone for this pass. When the fast timer reaches zero it counts down the slow timer `loc_f0 + x`. If the slow timer is still running, the slot takes a single animation step: the frame byte's top bit selects between two ROM table pairs — `loc_cbcc`/`loc_cbcd` when clear or `loc_cccc`/`loc_cccd` when set — from which it reloads the fast timer and reads a new level increment, adds that to the prior level in `loc_d0 + x`, and stores the result back; on **odd** slots the prior high nibble of the level byte is preserved (the new value's low nibble is kept while the high nibble is restored from the previous byte). If both timers have expired, the slot instead walks its animation frame forward — stepping `loc_c0 + x` by two each iteration and reading the `loc_cbcb`/`loc_cbce`/`loc_cbcc` (or `loc_cccb`/`loc_ccce`/`loc_cccc`) tables — until a nonzero frame lands, reloading both timers and the level from the table as it goes. Whatever path was taken, the slot's level byte `loc_d0 + x` is then published to a POKEY register: slots `0..7` write to `loc_60c0 + x` (POKEY 1's eight audio registers $60c0-$60c7) and slots `8..15` write to `loc_60c8 + x`, which lands in POKEY 2's audio registers $60d0-$60d7. So the sixteen software voices are split eight-and-eight across the two chips.

### POKEY reset and self-test: loc_cd95

`loc_cd95` [seen] is the dual-POKEY initialiser. It first drops both SKCTL cells `loc_60cf` and `loc_60df` to zero and clears the flag `loc_720`. It then samples the two RANDOM registers at the chips' offset `0x0a` — `loc_60ca` (POKEY 1) and `loc_60da` (POKEY 2) — and polls them across five iterations; if either register has changed from its first sample, the first `loc_60ca` value is latched into `loc_720`, which is a RANDOM-generator self-test confirming the noise source is running. It then writes the canonical SKCTL init value `7` into both `loc_60cf` and `loc_60df`, zeroes both banks of eight audio registers (`loc_60c0 + x` and `loc_60d0 + x` for `x = 7..0`) along with their software mirrors `loc_c0 + x` and `loc_d0 + x`, and finally clears the two AUDCTL registers `loc_60c8` and `loc_60d8`. The effect is a silent, freshly-initialised pair of POKEYs with cleared voice state.

### The sound request path: trampolines → gate → registrar

Game code raises a sound by calling one of a family of fixed-id trampolines, each of which carries a single hard-coded sound number. They fan out by id in steps of `0x10`: `loc_ccb5` → `0x0f`, `loc_ccc1` → `0x1f`, `loc_ccea` → `0x2f`, `loc_cd02` → `0x3f`, `loc_ccb9` → `0x4f`, `loc_ccb0` → `0x5f`, `loc_ccee` → `0x6f`, `loc_ccf2` → `0x7f`, `loc_ccbd` → `0x8f`, `loc_ccf6` → `0x9f`, `loc_ccfe` → `0xbf`, and `loc_cd06` → `0xcf`. All of these route through the enable gate `loc_ccc3`, and the ones invoked from movement/state handlers additionally carry the caller's `X`/`Y` through to the stamp routine. The one exception is `loc_ccfa`, which loads id `0xaf` and goes **straight** to the registrar `loc_ccc7`, bypassing the gate. Every one of these trampolines is [code]: their own bodies perform no memory write, so the write-tap cannot witness their execution regardless of whether they ran, and their audible effect is entirely delegated to the registrar. (Which in-game event each id denotes is not settled from the code alone; the ids are named by their numeric value, e.g. `loc_ccfa` queues sound `0xaf`.)

`loc_ccc3` [code] is the enable gate: it tests bit 7 of the enable flag `loc_5` and returns immediately (dropping the request) when that bit is clear, otherwise falling through into the registrar with the requested id. It was not reached in the capture, so the gate's own vectoring is unwitnessed and the tag rests on the code.

`loc_ccc7` [seen] is the registrar where a request becomes live voice state — heavily exercised. It first stashes the caller's `X` and `Y` into `loc_31` and `loc_32`. Taking the sound id as an index, it walks the sixteen slots from `0x0f` down to `0`, decrementing the id on each step, and reads that id's row byte from the ROM table at `loc_cb01`. A zero byte leaves the slot alone; a nonzero byte claims the slot — it parks the slot index in the reservation cell `loc_bf`, stores the row byte as the slot's initial frame at `loc_c0 + slot`, arms both the fast timer `loc_e0 + slot` and the slow timer `loc_f0 + slot` to `1` (so the very next pass of `loc_cd0a` immediately steps the voice), and restores `loc_bf` to the `0xff` sentinel. A single request can therefore seed several voice slots at once, one per nonzero byte in the sound's table row.

### The POKEY-page selector nibble: loc_dbe0

`loc_dbe0` [code] is a small bit-packer sitting in the POKEY register page. It stores its incoming value into `loc_60db`, then builds a nibble from the low three bits of `loc_60d8` (`& 0x07`); those three bits are mirrored into the scratch cell `loc_37` and into `loc_60cb`. The value it **returns** additionally carries one relocated bit — bit 5 of `loc_60c8` shifted down to bit 3 (`(loc_60c8 & 0x20) >> 2`) — OR'd onto the three low bits; the mirrored copies in `loc_37`/`loc_60cb` do **not** carry that relocated bit, only the return does. Its consumers are `loc_d6bb`, which records the return into `loc_16a`, and a draw routine that uses it as an index. The packing role is [code]: while the routine was reached, every observed write was a constant (`loc_60cb = 0`, `loc_37 = 0`, `loc_60db = 0xd0`), so the genuine nibble-packing behaviour was not exercised in the capture.

### Option-switch decode: loc_d6bb

`loc_d6bb` [seen] reads the two option-switch input ports on the $0d00/$0e00 page and turns them into config cells. It reads `loc_e00`, stores it verbatim into `loc_a`, then slices it three ways: bits 5-3 (`(a0 >> 3) & 0x07`) index the ROM table `loc_d6f7` into `loc_156`; bits 7-6 (`(a0 >> 6) & 0x03`) index `loc_d6ff` into `loc_158`; and bits 2-1 (`a0 & 0x06`, used as a table offset) index `loc_d6b3` into `loc_ac` and `loc_d6b4` into `loc_ad`. ### The math box: loc_dce6

`loc_dce6` [code] drives the hardware math coprocessor, another device on the $6000 page distinct from the POKEYs. It seeds the operand registers `loc_608e` (from A) and `loc_608f` (from X), zeroes `loc_73`, `loc_414`, and `loc_6090`, and primes the count registers `loc_608c` and `loc_6094` to `0x10` to kick off the operation. ### The per-channel record machinery: loc_ac3f and loc_ad6e

Two routines manage a per-channel record table built on the `loc_600`-block slot cells and share their timing with the frame loop; their exact game-facing role is not settled from the code, so it is left tentative.

`loc_ac3f` [seen] is heavily exercised and is entered as a fall-through/dispatch target (no direct caller). `loc_ad6e` [code] is the per-frame tick of the active slot, and it was **not reached in the capture** — its clamp and step logic is read from the code only. ## The EAROM high-score store

Tempest keeps its high-score table (and the initials the player types after a qualifying game) in the machine's ER-2055 EAROM — a small serial NVRAM that survives power-off. All traffic to that chip is funnelled through one bit-serial transfer engine, `loc_de1b`, which is fed by a little family of request-setter routines that stamp three control cells at `$01c6`/`$01c7`/`$01c8`. Nothing writes the EAROM directly; a caller instead marks *which* regions it wants moved and in *which* direction, and the engine services the request one region, one bit at a time.

**The request cells and their setters.** The queue is three bytes. `loc_1c7` (`$01c7`) is the pending-request bitmask — each set bit asks the engine to service one region of the store. `loc_1c8` (`$01c8`) is the matching direction mask: for a given region, if its bit is set in `loc_1c8` the engine drives that region *out* to the EAROM (a save), and if it is clear the engine reads that region *back* (a load). `loc_1c6` (`$01c6`) is the index/blank byte: when it is left nonzero (0xff) the write path first zeros each source RAM cell before shipping it, i.e. it erases the region rather than persisting live data.

The setters all converge on a shared tail (`loc_ddff`) that performs exactly three stores — `loc_1c6 = Y`, `loc_1c7 |= A`, `loc_1c8 |= A` — so requests accumulate (OR) into the pending and direction masks rather than overwriting them. `loc_ddfb` is the observed entry: it supplies mask `A = 0x04` through `loc_ddfd` (which forces the index byte `Y = 0x00`) into that tail, so it ORs bit 2 into both `loc_1c7` and `loc_1c8` and clears `loc_1c6` — a plain single-region save with no blanking. This 0x04/0x00 path is the one seen running, so `loc_ddfb` is **[seen]**. `loc_ddfd` and `loc_ddff` are the shared merge points it flows through; they carry whatever mask/index the caller presents.

The remaining setters are alternate presets over the same tail and are code-level only in the capture. `loc_ddf1` **[code]** is the "all blocks, blank-write" preset: it forces `loc_1c6 = 0xff` and ORs `0x07` (all three region bits) into both `loc_1c7` and `loc_1c8`, queueing every region for a blanking write-out — but neither the 0x07 mask nor the 0xff index byte was observed at the merge stores, so its own write path did not run. `loc_ddf3` **[code]** forces the index byte to `Y = 0xff` (blank mode) and runs the merge with the caller's live-in mask; `loc_ddf7` **[code]** supplies the fixed mask `A = 0x03` with a zeroed index (bits 0 and 1, read-back of two regions); and `loc_dde9` **[code]** is a trampoline that runs `loc_ddf3` with `A = 0x04`, i.e. a blank-mode (index 0xff) request for the bit-2 region. None of these three preset paths fired in the capture — only the `loc_ddfb` 0x04/0x00 value reached the merge stores — so each stays **[code]**; their masks and blank byte are read from the code, not observed.

**Priming and running the engine.** `loc_de11` **[seen]** is the direct initiator: rather than OR-ing bits, it *sets* `loc_1c7 = 0x07` and clears `loc_1c8 = 0x00` (all three regions requested, all in read-back direction) and then falls straight into `loc_de1b`. Both of those stores are observed, and the SET (not OR) distinguishes it from the setter family. This is the boot-time load that pulls the saved high-score table back out of the EAROM into RAM; the idle-start guard `loc_db5a` reaches it, though that guarded path itself was not taken in the capture.

**The transfer engine.** `loc_de1b` **[seen]** is the heart of the store and is heavily exercised. It is a re-entrant state machine keyed on the mode byte `loc_1ca` (`$01ca`) and driven against three memory-mapped ports: `loc_6000` (`$6000`, the data byte, indexed by a cursor), `loc_6040` (`$6040`, the control/clock strobes) and `loc_6050` (`$6050`, the read-back data). On a fresh request — `loc_1ca == 0` with `loc_1c7 != 0` — it clears the counters `loc_1cb`/`loc_1cf` and the working mask `loc_1ce`, then rebuilds `loc_1ce` as a single walking bit that isolates the **highest** (most-significant) set bit of the request mask `loc_1c7`: it rotates left across up to eight passes and breaks on the bit-7 carry-out, so it always picks the top pending region, never the lowest. It then decides that region's direction, `loc_1ca = ((loc_1ce & loc_1c8) != 0) ? 0x80 : 0x20` (write vs. read), clears the serviced bit with `loc_1c7 = loc_1ce ^ loc_1c7`, and uses the doubled bit index to fetch that region's parameters from the packed ROM tables: the port cursor `loc_1cc` from `loc_dddd`, the limit `loc_1cd` from `loc_ddde`, and the 16-bit RAM base pointer `loc_bd`/`loc_be` from `loc_dde3`/`loc_dde4`. That pointer, offset by the entry counter `loc_1cb`, addresses the RAM cell for each byte the region carries.

Each subsequent entry into the engine advances one step. It resets `loc_6040 = 0`, returns immediately if `loc_1ca` has gone to zero, and otherwise shifts `loc_1ca` left to read its two phase bits. The first pass (the address/command latch) writes the shifted mode to `loc_6000 + cursor`, sets `loc_1ca = 0x40`, and clocks `loc_6040 = 0x0e` before returning. On the write branch it sets `loc_1ca = 0x80`, and — if the blank byte `loc_1c6` is nonzero — zeros the source RAM cell before reading it, so a blanked request ships zeros; when the cursor reaches the limit `loc_1cd` it instead ships the accumulated checksum `loc_1cf` and retires the region (`loc_1ca = 0`). The read branch performs the EAROM read handshake — `loc_6040 = 0x08`, `loc_6000+cursor = 0x08`, then `loc_6040 = 0x09`/`0x08` — and takes the byte from `loc_6050`; below the limit it stores that byte through the region pointer, and at the limit it XORs the read-back against the running checksum `loc_1cf`. A zero result means the region verified and it retires cleanly; a nonzero result means the stored copy is corrupt, so it walks the entry counter `loc_1cb` back down zeroing every RAM cell of that region (invalidating the bad load) and records the failure by OR-ing the region bit into `loc_1c9` (`$01c9`). Good data bytes are folded into the checksum (`loc_1cf += byte`) as both the entry counter `loc_1cb` and the port cursor `loc_1cc` advance. When a step ends with a nonzero clock value written to `loc_6040` the engine returns to be re-entered next tick; when it ends at zero it loops internally to begin the next region. In this way one call chews through the whole pending mask, region by region and byte by byte, until `loc_1c7` is empty and `loc_1ca` falls back to zero.

## State-reset, init and per-frame update chains

This subsystem is the machine's plumbing for bringing RAM to a known baseline — at power-up, between waves, and once every frame — and for keeping the derived control-block geometry in step with the live cabinet/state inputs. Most of the leaves here are straight-line seeders and blankers that the boot/init chain fans through in order; a smaller set runs on the per-frame path or on the wave-start path, and a rebuild chain reacts to change.

### Fixed-constant init seeders

Several leaves do nothing but stamp a handful of RAM cells with fixed startup constants, and the init chain calls them one after another. `loc_921b` [seen] seeds five cells: `loc_200`=0x0e, `loc_51`=0xf0, `loc_106`=0x00, `loc_201`=0x0f, `loc_202`=0x10. In the capture the writes land at their own PCs with exactly these constants; because `loc_200` and `loc_51` vary elsewhere, this is a genuine reset of live state rather than a no-op. `loc_b0e7` [seen] is the same shape, writing `loc_0`=0x0a, `loc_2`=0x00, `loc_4`=0xdf, `loc_1`=0x12, `loc_14e`=0x19, and `loc_14d`=0x18 in that order before returning, all six writes observed. `loc_c97b` [seen] and `loc_ca18` [seen] are two more state-entry seeders that overlap on the `loc_0`..`loc_4` zero-page block: `loc_c97b` writes `loc_2`=0x04, `loc_1`=0x00, `loc_0`=0x0a, `loc_4`=0x14; `loc_ca18` first masks `loc_5 &= 0x3f` (clearing its top two flag bits) and then seeds `loc_3e`=0x00, `loc_2`=0x1a, `loc_0`=0x0a, `loc_4`=0xa0, `loc_16b`=0x01, and `loc_1`=0x0a. That these several routines all write the same `loc_0`/`loc_1`/`loc_2`/`loc_4` cells with different constants is the signature of distinct game states each priming the same shared working scalars to their own starting values.

### Array-and-flag blankers

A cluster of reset leaves zero a contiguous run and then clear a few associated scalar flags, all top-down. `loc_926f` [seen] zeros the seven bytes `loc_2df`..`loc_2df+6`, then clears `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, and `loc_146`; several of these (for instance `loc_108` and `loc_142`) carry real non-zero values elsewhere, so the clear is meaningful. `loc_928f` [seen] zeros the twelve bytes `loc_2d3`..`loc_2d3+0x0b` and clears `loc_135` and `loc_a6`. `loc_929f` [seen] blanks the eight-byte table `loc_30a`..`loc_30a+7` and clears the trailing flag `loc_116`. `loc_92ad` [seen] is the smallest of these, clearing only `loc_50` to zero — a cell that swings across a wide range elsewhere, so the reset is real. `loc_a831` [seen] clears the pair `loc_3aa` and `loc_125` at once; the `loc_125` clear is role-defining because that cell is a latch driven to 0xff elsewhere. `loc_ca62` [seen] zeros the six-byte scratch block `loc_40`..`loc_45`, which downstream code then reads back as three-byte staging entries. The 16-byte per-slot state table at `loc_283` is handled by `loc_a789`, which zeros `loc_283`..`loc_283+0x0f` and then re-seeds scalars `loc_10e`=0x20, `loc_10d`=0x20, `loc_1`=0x04, `loc_68`=0, and `loc_69`=0; this routine is [code] — it is not reached in the capture (no writes to its own cells were observed, `loc_283` being touched only from elsewhere), so its table-clear and scalar seeds rest on the code.

`loc_9234` [seen] builds a 17-byte parameter block rather than clearing one: it copies the header from `loc_15b` into `loc_3ab`, then fills the sixteen per-lane body cells `loc_3ac`..`loc_3ac+0x0f` with the single source byte at `loc_15a`. In the capture `loc_15a`=0 so the body stays zeroed, while the header source was seen varying (0x0f→0x0c) — and `loc_3ab` is itself a real cell that drains 0x0f→0x00 elsewhere, so this is the routine that primes the per-lane limit table the enemy/hit logic later consumes.

`loc_a7bd` [seen] is a spike-table (re)arm: it zeros the eight bytes `loc_3fe`..`loc_3fe+7`, then overwrites the last slot `loc_405`=0xf0 and arms the flag `loc_115`=0xff. It is invoked on the per-frame step of the descending object once that object passes a threshold while the flag was still clear, resetting the eight-entry table and re-arming for the next pass.

### Wave-start state build

`loc_a5cb` [seen] is the wave/entry reset that also tallies the occupied lanes. It sets `loc_0`=0x20, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c`, and `loc_123`, and sets `loc_105`=0x02. It then walks the sixteen per-lane cells `loc_3ac`..`loc_3ac+0x0f` and increments `loc_123` once for each nonzero entry — the count of occupied/spiked lane segments, observed climbing to six in the capture. If that count is nonzero and the level cell `loc_9f` is below 0x07, it loads an intro/parameter block (`loc_4`=0x1e, `loc_0`=0x0a, `loc_2`=0x20, and overwrites `loc_123`=0x80). Regardless of that branch it finishes by driving the ready latch `loc_125`=0xff.

`loc_ad22` [seen] drains a packed request word to spawn the next requested slot. On each pass it checks `loc_603`; when it is zero the queue is exhausted and it writes the idle status `loc_0`=0x14 and returns. Otherwise it takes the low two bits as a slot index, `loc_3d = (loc_603 & 0x03) - 1`, then consumes those two bits with two right shifts of `loc_603`. It reads the candidate slot byte `n` = `loc_600 + loc_3d`; a value of 0 or one of 0x09-and-up is skipped and the drain continues. For an in-range slot it scales the byte into the paired value `a = ((n<<1) + n) ^ 0xff`, then `a = a - 0xe5`, stored to `loc_602`; it then drives `loc_ca48` to spawn, seeds `loc_605`=0x60, `loc_4e`=0x00, `loc_50`=0x00, `loc_604`=0x02, runs the slot-table (re)init `loc_a789`, marks the armed status `loc_0`=0x24, and returns. The queue-drain half (the `loc_603` shifts and the `loc_3d` slot-index write) is what was exercised; the full per-slot spawn tail is code-supported.

### Per-frame update

`loc_a504` [seen] runs on the per-frame path (the tail of the frame dispatcher, and again when the control byte is negative), and the sign of `loc_201` splits it into two arms. The positive arm (`loc_201` < 0x80) bumps a per-slot timer cell `loc_00 + loc_40` when a gate `(loc_455 | loc_11b)` is live and `loc_42` has passed 0x17; it then returns early if `loc_106` is set, and when `(loc_3ab | loc_116)` is clear it scans the depth table `loc_2df` downward from index `loc_11c` for any live entry that has already grown to 0x11 or more, and only if none has does it re-run the wave reset `loc_a5cb` followed by the blanker `loc_928f`. A further chain of gates on `loc_4d & 0x60`, `loc_5 & 0x80`, and `loc_9 & 0x43 == 0x40` can re-run `loc_a5cb` a second time. The negative arm is the one exercised in the capture: it ages each live shot in the depth table `loc_2df` (from index `loc_11c` downward) by +0x0f, snapping the cell to 0x00 once the sum reaches 0xf0 so objects that reach the far end expire; then, keyed on `loc_48 + loc_3d`, it either advances `loc_202` by +0x0f (proceeding once that crosses 0xf0) or, on the 0x01 case, clears `loc_10f`, sets `loc_114`=0x01, and steps the 16-bit clock `loc_5b`/`loc_5f` down by 0x20 (proceeding when the high byte reaches 0xfa). When either path proceeds it writes `loc_00`=0x06, runs `loc_928f`, and folds `loc_108 + loc_109 + loc_3ab` into `loc_3ab`, clamping the running total up at 0x3f.

### Control-block rebuild chain

A small chain keeps two rebuildable control-block regions in step with the live cabinet/geometry inputs. At its head, `loc_ac20` [code] refreshes the live snapshot through `loc_d6bb` (which decodes the option switches into the game config), then compares `(loc_a & 0xf8)` against the cached `loc_71e` and `(loc_16a & 0x03)` against the cached `loc_71f`; on a match it falls to a bare no-op return, and on a mismatch it drives `loc_ac36` to OR 0x03 into `loc_1c9`, setting the two pending-rebuild request bits. In the capture only the match/no-op path fired — the mismatch request path is not reached — so its role rests on the code.

`loc_abac` [seen] is the rebuild body, and its template-copy and flag writes were observed running. It first refreshes the snapshot via `loc_ac20`, arms `loc_100`=0x08, and when all three edge sources `(loc_71b | loc_71c | loc_71d)` are idle it requests both rebuild bits via `loc_ac36`. It then reads the request flags from `loc_1c9`: for bit 0 it copies a template block, `loc_606 + x` = `loc_ac08 + x` for x from 0x17 (when bit 0 is set) or 0x0e (when clear) down to 0; for bit 1 it fills `loc_706 + x` = 0x01 over the same 0x17-or-0x0e range. If either request bit was set it latches the snapshot, `loc_71e` = `loc_a & 0xf8` and `loc_71f` = `loc_16a & 0x03`, and finally clears the two request bits with `loc_1c9 &= 0xfc`, leaving the higher bits untouched.

Two guarded entry points drive that body. `loc_aba2` [code] refreshes the snapshot via `loc_ac20` and then branches on the low two request bits of `loc_1c9`: idle takes a no-op return tail, otherwise it runs `loc_abac`; its own writes were constant in the capture so the branch rests on the code. `loc_d7e1` [code] arms two mode bytes, `loc_5`=0x00 and `loc_1`=0x02, then gates the rebuild on being idle (`loc_1ca` zero), enabled (`loc_c00 & 0x10` set) and with a request pending (`loc_1c9 & 0x03` nonzero); when enabled it also writes `loc_0`=0x00 before delegating to `loc_abac`. Its writes were likewise constant in this capture, so its role is code-supported.

### Scoring folded into the hit handlers

Two routines in this set fold a score/threshold update into the moment a target is hit. `loc_ca6c` [seen] adds a three-byte BCD amount into the score cell trio and range-checks it against a threshold. It is gated on `loc_5 & 0x80`, and picks the destination triplet offset `y` = 0 when `loc_3d` is zero, else 3. When its index argument is below 0x08 it adds the fixed table entries `loc_caf1 + x` and `loc_caf9 + x` into `loc_40 + y` and `loc_41 + y`; otherwise it adds the live operand pair `loc_29`/`loc_2a` into those same cells and carries `loc_2b` forward. The third BCD byte then updates `loc_42 + y`. The score cells were observed changing, which grounds the score-add half as [seen]. The award tail — `doAward`, which bumps the per-slot counter `loc_48 + loc_3d` while it is still under 0x06, rings the sound cue `loc_ccc3` with code 0x4f, and raises `loc_124`=0x20 — did not fire in the capture, so that half is code-supported only; the threshold logic that reaches it (comparing and repeatedly subtracting `loc_156` from the high byte, awarding on an exact multiple) is code-level for the same reason.

`loc_a1fa` [seen] advances a slot's counter toward its per-lane limit and, on reaching it, scores the hit. It reads the lane index `y` = `loc_2ad + x` and the per-lane limit `loc_3ac + y` (the same table `loc_9234`/`loc_a5cb` maintain); a zero limit returns immediately. When the slot counter `loc_2d3 + x` has reached the limit it clamps the limit cell (writing back the counter unless it has already saturated at 0xf0-or-more, in which case it clears to 0x00), bumps the hit tally `loc_2f2 + x`, flags the target with `loc_39a + y`=0xc0, chimes through `loc_ccf6`, seeds the operand triplet `loc_2a`=0, `loc_2b`=0, `loc_29`=1, and drives the score-add `loc_ca6c` with the live-operand index 0xff, then re-reads the working index from `loc_37`. Finally, once the hit tally `loc_2f2` at the effective index has reached 0x02 (a second hit), it resets that slot's counter `loc_2d3` to 0x00 and drops a life by decrementing `loc_135`. Its role writes were observed changing, grounding it [seen].

## Utilities and shared tails

This subsystem collects the small, reusable service routines the rest of the machine leans on — decimal formatting for on-screen counters, a bit-field splitter, a geometry-rebuild request flag, two table shufflers, and the several bare return leaves that other routines branch to as their "nothing to do" exits.

### Binary-to-decimal formatting and its clamp

The workhorse here is loc_aaf5 [seen], a classic double-dabble binary-to-BCD converter that is exercised heavily. It sets decimal mode, stashes the incoming source byte in `loc_29`, and zeroes an accumulator in `loc_2c`. It then runs eight passes counted by Y from 7 down to 0: each pass shifts the source in `loc_29` left one bit (`asl`, moving the source's current top bit out into carry) and doubles the decimal accumulator by adding `loc_2c` to itself with that carry folded in, so successive source bits are absorbed into a running packed-BCD figure. After the eighth pass it clears decimal mode and writes the finished value back into `loc_29`. The net effect is that **both** `loc_29` and `loc_2c` come to rest holding the *same* packed-BCD result, each spanning the full `0x00..0x99` range; the narrower `0x00..0x63` figure is the raw *binary input* that callers hand in, not the BCD output. Both role writes are observed in the capture — `loc_29` receiving the source and then the result, and `loc_2c` accumulating the doubled digits.

loc_af71 [code] is the front door callers use when they want a value shown as a capped two-digit decimal. It first clamps the incoming byte to a maximum of `0x63` (99) and then routes it into the pack-and-emit path: that path packs the clamped byte to BCD through loc_aaf5 and emits the resulting zeropage byte as display nibbles. loc_af71 itself performs no role-defining store of its own — its entire contribution is the ceiling and the hand-off — so its role rests on the code rather than on any observed write, hence the [code] tag.

### Splitting a byte into a fine value, a seed, and a coarse index

loc_93e0 [seen] is a compute helper reached exclusively through its caller's three invocation sites, and it is genuinely exercised — its `loc_29` scratch write is observed (seeded to `0xff`, then rotated). It takes the input byte and, over three passes, peels off the top three bits most-significant-first while shifting the input left; each peeled bit is rotated into the low end of a seed that starts life as `0xff`. The seed therefore settles at `0xf8 | top3bits` and is stashed in `loc_29`. Three register results ride back to the caller: A holds the input shifted left three times (the low bits promoted into a "fine" position, since the preserve/restore around the store keeps the *shifted* A rather than the original), Y holds the seed itself, and X is a small coarse index derived from the seed's complement — computed as `((seed ^ 0xff) + 0x0d) >> 1`. Because `seed ^ 0xff` equals `0x07` minus the three-bit field, X works out to `(0x14 - top3bits) >> 1`, landing in the range 6..10 as the three-bit field runs 0 through 7. The routine's grounded standing is as a reached splitter with an observed scratch write; the downstream game meaning of the three live-outs is not settled by its own writes.

### Requesting a geometry rebuild

loc_ac36 [seen] is the tiny primitive that flags both geometry blocks as needing to be rebuilt: it ORs `0x03` into the working request cell `loc_1c9` and returns the merged value, then falls straight through into the shared return leaf at loc_ac3e. Its own store into `loc_1c9` is observed (the cell carrying bits 0 and 1 set alongside an already-present higher bit). Two callers drive it — the state-comparison path that notices the live geometry snapshot has diverged from its cached latch, and the rebuild coordinator — and the two request bits it raises are later consumed by that coordinator, which uses bit 0 and bit 1 to trigger the two respective template-block copies.

### Table shufflers (present but idle in the capture)

Two routines rearrange parallel tables and neither was reached in the capture; both are readable from the code but carry [code] tags because their role-defining stores never fired.

loc_92b2 [code] exchanges two parallel 18-entry tables slot-for-slot: for each index from `0x11` down to `0`, it reads `loc_3aa + x` and `loc_3bc + x` and writes each into the other's slot, so every entry ends up holding what its sibling held. The two swap stores never execute in this capture, so the routine is not reached in the capture.

loc_b85f [code] is a straight-line seeder for a pair of three-entry arrays, planting the fixed values `0x00`, `0x04`, and `0x0c`: it writes `0x0c` into `loc_80b` and `loc_24`, `0x04` into `loc_80a` and `loc_23`, and `0x00` into `loc_22` and `loc_809`. None of these writes are observed, so it too is not reached in the capture.

### Constant and no-op leaves

loc_b955 [code] is a register-only leaf and a known proposer trap. Although the underlying routine reads `loc_57`, shifts it, and runs a bit-counting loop, that loop's result is thrown away: the final `clc`/`adc #2` leaves A at exactly 2 and `ldy #0` resets Y to 0, so the routine *always* returns the constant pair A=2, Y=0 regardless of `loc_57`. It is not a log2 or population-count of `loc_57` — the code discards the count. It touches no memory, so its reach cannot be confirmed from the write-tap, hence [code].

The remaining four are bare `rts` leaves that other routines branch to as their empty-handed exits; none writes memory, so each is grounded only as far as the code shows and carries a [code] tag:

- loc_9bcf [code] is a do-nothing slot in a computed-dispatch table — it returns immediately, letting the caller's own return unwind. It is reachable only through that dispatch table, and being writeless it is unexercisable via the write-tap.
- loc_ac07 [code] is the "nothing-to-rebuild" tail that the rebuild coordinator branches to when the request cell shows no pending bits (`loc_1c9 & 3 == 0`).
- loc_ac3e [code] is the shared return tail into which loc_ac36 falls; the state-comparison path also branches here directly when the live geometry state (`$0a & 0xf8` versus its latch, `$016a & 3` versus its latch) already matches, i.e. no rebuild is needed.
- loc_af6e [code] is the exposed return tail of the draw routine at loc_af3f; its caller tail-branches here when both draw-slot cells (`$0600 | $0601`) are empty, meaning there is nothing to draw.
