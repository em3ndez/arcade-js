# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
mathbox projection, sound, and the EAROM — down to the caller routines that drive them and the first
computed-jump dispatcher; the frozen-oracle remainder (the dispatcher spine and two register-thread callers)
is noted at the end. The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM
(`0x2000-0x2FFF`) each frame and the Analog Vector Generator draws it, with the vblank interrupt as the
per-frame heartbeat and a game-state index driving a computed-jump dispatch that selects the mode handler
(attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Tempest steers its on-field objects with a tiny byte-coded interpreter. A driver (loc_9b1e) walks the active object list — counting `loc_37` down from the `loc_11c` object count while the sign gate `loc_201` permits it — and for each object `x` whose depth cell `loc_2df,x` is nonzero it opens a script pass: it raises the walk-continuation flag `loc_10a` to 1, seeds the shared instruction pointer `loc_10b` from that object's saved cursor `loc_291,x`, and then loops. Each turn of the loop reads `loc_10b` as an index into the script byte stream based at `loc_a0f7`, hands that byte to the RTS-trick opcode table (loc_9b98, which turns the byte into one of the handlers below), bumps `loc_10b` by one, and repeats as long as `loc_10a` stays nonzero; when the walk finally stops it writes `loc_10b` back to `loc_291,x` so the object resumes where it left off next frame. The handlers in this section are the opcode vocabulary that pass executes. Three cells are the interpreter's registers: `loc_10b` is the instruction pointer/cursor, `loc_10c` is a one-byte branch flag that conditionals read, and `loc_10a` is the "keep walking this object" flag.

**Terminating the pass.** loc_9bca is the halt opcode: it stores 0 into `loc_10a` (a single write, observed on essentially every object that runs a script), which drops the driver out of its inner walk and ends this object's script pass for the frame. It is a leaf reached through the computed-dispatch table [seen].

**Writing an object's motion cell.** Two opcodes deposit a value into the per-object output cell `loc_298,x`. loc_9bd0 is the store-immediate form: it pre-increments the cursor (`loc_10b = (loc_10b+1)&0xff`) so it points at the operand byte, then copies that operand — `loc_a0f7[loc_10b]` — straight into `loc_298,x` (IP-advance and the slot writes to `loc_29b`–`loc_29e` were both observed) [seen]. loc_9bdd is the store-indirect form: it increments the cursor, reads the operand `loc_a0f7[loc_10b]` and treats that byte as a zero-page address, then copies the live variable it points at — `mem[loc_00 + ptr]` — into `loc_298,x`, so the stored value tracks a running variable rather than a literal [seen].

**Conditional control flow.** The branch flag `loc_10c` gates two opcodes. loc_9bee is the conditional skip: if `loc_10c` is nonzero it does nothing (falls through to the next opcode), otherwise it advances the cursor by two (`loc_10b = (loc_10b+2)&0xff`), stepping over a two-byte operand; both increments were seen firing [seen]. loc_9bfa is the conditional jump: it first bumps the cursor by one, and then — only while `loc_10c` is zero — reloads the cursor from the operand it now points at (`loc_10b = loc_a0f7[loc_10b]`), i.e. a scripted goto taken when the flag is clear; both the plain advance and the table-reload write were observed [seen].

**Unconditional goto.** loc_9c17 reloads the cursor from the table shifted by one, `loc_10b = loc_a0f8[loc_10b]` (with `loc_a0f8` being `loc_a0f7 + 1`, so the index selects the byte following the current position — the jump operand). It is heavily exercised, serving both as its own opcode and as the loop-back tail of the timer opcode below [seen].

**Dwelling on a step.** loc_9c0c is the timer/dwell opcode and reuses the same per-object cell `loc_298,x` as a countdown: it decrements `loc_298,x`, and while the result is still nonzero it delegates to loc_9c17 to re-run the goto (holding the object on the current script step), but once the count reaches zero it instead bumps the shared cursor `loc_10b` to fall through to the next opcode. It is heavily exercised. Because loc_9bd0/loc_9bdd write `loc_298,x` and loc_9c0c counts it down, the same object cell can be loaded with a dwell value and then ticked off, though the code alone does not pin the exact producer/consumer pairing [seen].

**Test opcodes (not reached in the capture).** Two handlers set the branch flag `loc_10c` for the conditionals above; neither executed during the capture, so both are code-only. loc_9c21 is the segment-boundary test: for object `x` it reads the object's segment `loc_2b9,x`, looks up that segment's boundary `loc_3ac[segment]` (a zero entry is treated as the maximum, 0xff), compares the boundary against the object's coordinate `loc_2df,x`, and stores `loc_10c = (boundary >= position) ? 1 : 0`; the flag store at 0x9c3a never appears in the trace [code]. loc_9c3b is the accumulator-phase test: it computes `a = ((loc_147 << 2) + loc_148) & loc_148 & 0x80`, all byte-wrapped, then stores `loc_10c = a ^ 0x80` — 0x00 when that high bit is set, 0x80 when it is clear — reading the signed phase accumulator pair `loc_147`/`loc_148` that the driver's tail advances; its store at 0x9c4e is likewise absent [code].

**Packed-list cursor skip.** loc_96c7 stands slightly apart from the opcode set: it is a register-only cursor advance reached through a different computed jump (the `loc_9683` RTS-dispatch keyed on `loc_15e`). Its two entry points step the list cursor `Y` past a packed record without reading it — the first entry advances by three (it enters at `Y+1` and hands off to the second, which adds two more), the second by two. It has no own memory writes, so there is nothing to observe, and it was not reached in the capture [code].

## Vector coordinate lists and the display cursor

Tempest draws its tube, ship, enemies and text onto a color vector monitor, so the frame the machine hands to the AVG is not a bitmap but a list of vector-draw words assembled in RAM. Two zero-page pointers organize that work: `loc_74`/`loc_75` is the *write cursor* into the display list being built (it sweeps through vector RAM roughly 0x2000-0x2fff), while `loc_2c`/`loc_2d` is a *read pointer* into a packed coordinate list held in ROM. This section covers the cursor itself, the routines that pick which coordinate list to read, the walkers that step through that list, and the producers that stamp finished vector words at the cursor.

### The display cursor

Everything that appends to the frame ends by moving the cursor, and that is `loc_df5f` [seen]. Its body computes `sum = loc_74 + Y + 1` (the carry is forced set before the add, so it is always Y **plus one**, never Y), stores the low result back to `loc_74`, and on overflow past 0xff increments the high byte `loc_75`. In effect it advances the little-endian 16-bit pointer past the Y+1 bytes just written. Both stores are grounded — the low byte at `loc_74` is written on essentially every append and the high byte `loc_75` ticks up as the cursor rolls across page boundaries, sweeping the display-list region. Every producer below leaves the number of bytes it emitted (less one) in Y and lets `loc_df5f` reconcile the pointer, which is why the emitters and the cursor advance are inseparable.

### Choosing a coordinate list

Before a list can be walked, the read pointer `loc_2c`/`loc_2d` must be aimed at one. `loc_9aee` [seen] does this from ROM tables indexed by Y: it loads `loc_9b02[Y]` into the low byte `loc_2c` and `loc_9afd[Y]` into the high byte `loc_2d`, stashes the selecting index Y into `loc_2b`, and reloads A from the holding cell `loc_29`. All three of its writes are grounded (for example `loc_2c` taking 0x41 and `loc_2d` taking 0x07), so the machine is observed pointing itself at a chosen ROM coordinate list keyed by index.

`loc_9a9d` is the fixed-seed variant used to point at a single, un-indexed list — it copies the base byte `loc_9b02` straight into `loc_2c`, zeroes the index `loc_2b`, takes the high byte from the source cell `loc_15d` into `loc_2d`, and likewise reloads A from `loc_29`. It is tagged [code]: the only write captured from it was a constant value, so its list-seeding role rests on the code rather than on an observed changing store; it is not reached with varying state in the capture.

### Walking the packed list

Once `loc_2c`/`loc_2d` is aimed, three helpers chase it. They are reached through the computed-jump coordinate generator (the `$968f`/`$969d` dispatch tables), so they run as the machine's list-walking machinery rather than as standalone calls.

`loc_96cb` [seen] reads the entry at the cursor `(loc_2c),Y` and its immediate predecessor `(loc_2c),Y-1`, takes their difference as an inter-entry step `delta = cur - prev`, and stores that step at the scratch cell `loc_29`; it then advances the walk, computing `A = (Y-1) + delta + 1` and returning `Y = A + 2`. The `loc_29` store is grounded taking real step values across roughly 0x01..0x0f — genuine spacings between successive points in the coordinate list.

`loc_96ab` [seen] is a coordinate helper with two heads over the same body: the `loc_96ab` entry forms its working value as `((loc_2b - 1) & 0x0f) + 1` (a counter-derived, wrapped index off the stashed selector `loc_2b`), while the `loc_96b7` entry uses the raw `loc_2b`. The shared body first stashes the incoming Y into `loc_29`, then combines that value with the list entry two positions back — `A = A - (loc_2c),Y-2`, then `A = A + loc_29` — re-indexes by the result, and returns the entry it lands on in A with `Y = A`. Its only own write is the `loc_29` scratch; it is grounded as reached, its A output consumed downstream. `loc_96c4` in the same file is the trivial read — `A = (loc_2c),Y`.

`loc_96db` [code] resolves a list entry to an absolute coordinate: it reads the byte at `(loc_2c),Y` and adds the base value in `loc_160`, returning the sum in A (`& 0xff`). It performs no memory write of its own, so a write-tap cannot confirm its computed-dispatch reach or name a downstream consumer of its A output; its coordinate-resolution role is stated from the code, hence [code], not [seen].

### Producing vector words at the cursor

The remaining routines stamp finished words into the display list through the write cursor `loc_74`/`loc_75`.

`loc_df59` [seen] is the core two-byte emitter: it stores the pair {A, X} at `(loc_74)+Y` and `(loc_74)+(Y+1)`, then advances the cursor by Y+2 via `loc_df5f`. Its two stores are heavily grounded, writing wide-ranging real vector data into the 0x2000-0x2fff display region.

`loc_df53` [seen] is the fixed-header producer built on that emitter's tail: it writes the header pair {0x40, 0x80} — A=0x40 at the cursor, X=0x80 at cursor+1 — and then advances by 2. Both the 0x40 and the 0x80 stores are observed in the emit stream.

`loc_df19` [seen] and `loc_df1f` [seen] append a table-indexed word. `loc_df19` derives its index from the low nibble of A: with carry set and the nibble equal to zero the index is 0, otherwise it is `nibble + 1`. That index times two reaches into the ROM word table `loc_31e4`, and the two bytes found there are copied into the list at the cursor, which is then advanced by 2. `loc_df1f` is the thin index wrapper — it forms `(A & 0x0f) + 1` (no carry-zero special case) and drops into the same `loc_df24` emit tail, copying `loc_31e4[idx]`'s two bytes and advancing. The vector-RAM stores of the shared tail are grounded with real AVG opcode bytes; `loc_df1f`'s own index arm is pure computation and leaves no write, so it is [seen] as a reached index helper by virtue of that shared emit.

`loc_c772` [seen] is the object-position producer: it emits a fixed header word {0x40, 0x80} followed by two absolute coordinate words through the cursor. The X word comes from the zero-page pair at `loc_2+X` (low) and `loc_3+X` (high, masked to five bits with `& 0x1f`); the Y word from `loc_00+X` (low) and `loc_1+X` (high, likewise `& 0x1f`). As it emits, it caches the raw bytes into `loc_6a`/`loc_6b` (Y low/high) and `loc_6c`/`loc_6d` (X low/high) as the "previous point" anchor, then advances the cursor past the six bytes written. The `loc_c772` entry starts the offset at 0; the `loc_c774` entry takes an incoming offset. It is a heavily exercised producer, its coordinate stores grounded across the display region. (It is reached from the vector-draw sites and from the `loc_c765` alt-entry that first lays its own {0x00, 0x71} header.)

`loc_aef8` [seen] is the text-glyph emitter. It seeds a descending source index in `loc_38` (`= A + 2`) and a count in `loc_39` (`= 0x02`), then loops three times, each pass reading a character code from the buffer at `loc_606 + loc_38`. Any code 0x1e or above is folded to 0x1a; the (possibly clamped) code is doubled to index the glyph word table at `loc_31fa`, and both bytes of that glyph word are copied into the display list through the cursor `(loc_74)`. The high byte of each emitted glyph word is the vector-draw opcode 0xa8. After each pass `loc_38` and `loc_39` decrement; the loop continues while `loc_39` stays non-negative, so exactly three glyph words (six bytes) are written before it exits and hands Y=5 to `loc_df5f`, advancing the cursor by six. Its glyph stores are grounded, writing genuine glyph words across the display region.

## Draw-pointer setup and vector emission

Everything Tempest puts on screen is a list of records written into the AVG (analog vector generator) vector RAM at `loc_2000`-`0x2fff`. The routines in this subsystem fall into two halves that meet at a shared cursor: a small set that *seats a draw pointer* — deciding which structure the emitter will write through and where — and a larger set that *emits* the actual vector words, glyphs and coordinate deltas into that RAM. The pointer that ties the two together is the little-endian pair `loc_74`/`loc_75` (the display write pointer), with `loc_a9` acting as the running byte cursor into the structure it addresses; a second pointer pair `loc_3b`/`loc_3c` serves the text/glyph path, and `loc_29`/`loc_2a` are used as loop and scratch state.

### Seating the draw pointer

Two nearly-mirror routines publish a 16-bit pointer chosen from one of two ROM tables. `loc_b2be` [seen] takes a subsystem index in A, forms the two-byte stride `(A<<1)&0xff`, and — when the per-index flag `loc_415`+A is non-zero — reads its pointer from table `loc_ce68`, otherwise from `loc_ce7a`; it lands the low and high bytes into `loc_74`/`loc_75` and clears the status cell `loc_a9` to reset the cursor. Both stores were observed changing (the pointer pulsed across its range), grounding it as the live per-subsystem render setup. `loc_b2de` [seen] is the same mechanism aimed at the *text* pointer pair `loc_3b`/`loc_3c` instead of `loc_74`/`loc_75`, and with the table sense inverted — non-zero flag selects `loc_ce7a`, zero selects `loc_ce68` — again clearing `loc_a9`. `loc_91b5` [seen] is a third, simpler pointer loader: it doubles its selector A into a word index, clears the paired flag `loc_29`, and copies the little-endian pointer from the in-page ROM table `loc_91c6`/`loc_91c7` into the working pointer `loc_2a`/`loc_2b` (the observed pointer resolved to `0x0540`).

Two routines re-aim an already-seated pointer rather than loading one fresh. `loc_b944` [code] swaps the `loc_74`/`loc_75` pair with `loc_76`/`loc_77` through byte temporaries, so a subsequent emit writes through the other structure; its only driver is the object-draw loop at `loc_b8ba`, which was not reached in the capture, so `loc_b944`'s own body did not run. `loc_b967` [code] selects an (A, X) pointer-pair from ROM by the RAM flag `loc_415` — zero yields (`loc_ce87`, `loc_ce86`), non-zero yields (`loc_ce6f`, `loc_ce6e`) — for that same `loc_b8ba` consumer; although `loc_415` itself is exercised elsewhere, `loc_b967`'s body was not reached in the capture.

`loc_b332` [seen] guards the top of a draw pass against a mid-frame change: it compares the source byte `loc_cec4` against the checkpoint at `loc_2000`, and when they differ it latches the new value into `loc_2000` and returns carry set to signal the caller to redo. When they match it copies a two-byte record from `loc_ce9e` (offset 0x08 when `loc_415` is non-zero, else 0x02) out through the `loc_74`/`loc_75` cursor, clears `loc_16e`, reloads the cursor from `loc_ce68` at the same offset, and returns carry clear; both the copy and the reload stores were observed with real changing pointer values.

`loc_b84e` [code] is a computed dispatcher over a four-entry function table (`loc_b85f`, `loc_b875`, `loc_b888`, `loc_b896`) indexed by `Y>>1` (Y arriving as a 0/2/4/6 byte offset); it tail-returns the selected target's result and has no write of its own. `loc_b896` [code] is one of those targets — reached only through `loc_b84e`, and not reached in the capture. When it does run it emits a vector-RAM tail record from the 16-bit cursor `loc_139`/`loc_13a`: `loc_2ffc` gets the raw low byte, `loc_2ffd` gets the high byte OR'd with `0x70`, and `loc_2fff` gets the `0xc0` terminator; it then steps the cursor down by `0x20`, borrowing `loc_13a` down by one on underflow and masking `loc_139` to `0x7f`. Those four targets showed no writes in the capture, so the record values rest on the code.

### The coordinate work block and its feeders

Several routines fill the four-byte working coordinate block `loc_61`/`loc_62`/`loc_63`/`loc_64` (two little-endian pairs) that the delta emitters consume. `loc_c43c` [seen] reads the current slot index `loc_37` and copies that column of four parallel object-attribute tables — `loc_36a`, `loc_35a`, `loc_38a`, `loc_37a` — into `loc_61`..`loc_64` respectively; all four stores were observed with real varying attribute values. `loc_c423` [seen] does the same shape from a different table family (`loc_32a`, `loc_31a`, `loc_34a`, `loc_33a`, indexed by `loc_37`) and then drives the delta emit at `loc_c3ba`.

### Emitting coordinate and delta records

`loc_b56a` [seen] is the trivial record appender: it writes the four bytes `0, 0, 0, A` at the `loc_74`/`loc_75` cursor and advances that pointer by four (carrying `loc_74` into `loc_75`); it was observed filling the vector buffer across a wide span with the caller-supplied fourth byte.

`loc_c73c` [seen] emits two 16-bit differences through the `loc_74`/`loc_75` pointer at the running cursor `loc_a9`: first `(loc_63:loc_64) - (loc_6c:loc_6d)` then `(loc_61:loc_62) - (loc_6a:loc_6b)`. Each difference's low byte goes out raw; the high byte of the first is masked to five bits, and the high byte of the second is masked to five bits then OR'd with `0xa0` (a vector-generator opcode field). The cursor `loc_a9` advances by four across the pass. `loc_c3ba` [seen] computes the same two 16-bit deltas as *current minus previous* — `loc_61`/`loc_62` minus the latched `loc_6a`/`loc_6b`, and `loc_63`/`loc_64` minus `loc_6c`/`loc_6d`, with proper borrow — depositing them into `loc_6e`..`loc_71`, emits the record through the record writer at `loc_df92`, then latches the current values into the previous slots `loc_6a`..`loc_6d` and sets the ready flag `loc_73` to `0xc0`.

`loc_df92` [seen] is the general four-byte record writer: through the `loc_74` cursor it lays byte 0 from `loc_2`+X, byte 1 from `loc_3`+X masked to five bits, byte 2 from `loc_0`+X, and a fourth byte that folds a key: `((loc_1+X ^ loc_73) & 0x1f) ^ loc_73`. Its tail (`loc_dfac`) stores one further byte at the next cursor slot and advances the cursor unless the slot index wrapped to zero, in which case it runs the terminating nibble run at `loc_dfb1`; the vector-RAM stores here were observed across a wide value range. `loc_df75` [seen] prepares that record's coordinate pairs by widening two input bytes by four with sign extension — `low = (v<<2)&0xff`, `high` carries the replicated sign bit and bit 6 of v — into `loc_6e`/`loc_6f` and `loc_70`/`loc_71`, then falls into `loc_df92`. `loc_df73` [code] simply stashes an index byte into `loc_73` (the fold key) before entering `loc_df75`; it was not reached in the capture, so its role rests on the code.

`loc_c66d` [seen] produces a mid-tube vertex between a slot and its wrap-around neighbour. For slot `loc_38` and neighbour `(loc_38+1)&0x0f`, it forms the round-up signed average (sum plus one, then halved preserving the sign bit) of each slot's two coordinate pairs — `loc_36a`/`loc_35a` and `loc_38a`/`loc_37a` — storing the two midpoints into `loc_61`/`loc_62` and `loc_63`/`loc_64`. It then appends the four midpoint bytes through the `loc_74` pointer at cursor `loc_a9` (each high byte masked to `0x1f`), mirrors all four into the scratch block `loc_6a`..`loc_6d`, and writes the advanced cursor back to `loc_a9`.

### Headers, glyph strokes and the text path

`loc_c765` [seen] is an alternate entry that lays a fixed two-byte header `{0x00, 0x71}` at the start of the structure addressed by `loc_74`/`loc_75`, then resumes the shared vector build from cursor slot two; the two header stores were seen landing at thousands of distinct cursor addresses in the `0x2xxx` display RAM.

`loc_a9fc` [seen] is the glyph-stroke appender. It maps A's low nibble to a table entry — a zero nibble with carry set indexes entry 0, otherwise the index is `nibble+1` — reads a **single byte** from the stroke table `loc_31e4` at offset `2*index` (leaving the odd slot of that word untouched), stores it into the `loc_2f60` vector-list buffer at the X cursor, and advances X by two; the stored values were observed changing with real table data. `loc_a9d7` [seen] drives three source bytes through that appender: it seeds the pass counter `loc_2a` to two, and for each of three passes reads a glyph byte through `loc_3b`/`loc_3c`, emits its high nibble then its low nibble via `loc_a9fc`, chains the carry so it stays set only across zero nibbles (and is forced clear before the final byte's low nibble), then decrements the source pointer `loc_3b` and the counter until it underflows past zero. Its own writes are only that loop state; the glyph output is `loc_a9fc`'s.

`loc_a97f` [seen] builds a marker/status row into the `loc_2f60` buffer. It records the row selector into `loc_2b`, forms a head value that is OR'd with `0x70` (and zeroed only when the selector equals the marker `loc_3d` and bit 7 of `loc_5` is set), writes it at the base index `loc_cdde`[y], then fills six further glyph cells from `loc_3286` (the alternate glyph) once past the row count taken from `loc_48`[y] into `loc_38`, else `loc_3284`, stepping the cursor by two each time. Unless `loc_00` equals 4 while the row selector is not the marker row (an early out with no emit), it seeds the glyph pointer `loc_3b` from `loc_a97d`[y] with `loc_3c` cleared and hands off to `loc_a9d7`; the `0x71` header and glyph-cell writes were observed.

`loc_dfb1` [seen] emits a run of zeropage bytes as vector digits: given a start index and a length in Y, it walks from the top index (`A + Y - 1`) downward through `loc_ae` (count) and `loc_af` (source index), and for each byte emits its high nibble then its low nibble via `loc_df19` — the stroke-table writer for the `loc_74` path, of which `loc_dfb1` is the sole caller — chaining carry so only the very last low nibble sees it cleared (the terminator marker). This driver is heavily exercised.

Three thin callers preload that run. `loc_af77` [code] packs its input byte to BCD via `loc_aaf5` and then emits the single zeropage byte at `loc_29` as nibbles through `loc_dfb1`; its role rests on the code. `loc_aa9e` [code] increments the slot index in X, publishes it to `loc_61`, and emits that one byte as a one-entry run. `loc_b0c6` [code] selects a pointer by index through `loc_91b5` and then emits a three-byte zeropage run starting at `loc_29`. `loc_d8a9` [code] stashes A into `loc_29`, scales two coordinates into the vector work pair via `loc_df75`, then emits that one stashed byte as a single-entry run; it was not reached in the capture.

A small family emits a byte one bit at a time. `loc_dd2b` [code] stashes Y into `loc_35`, scales two coordinates through `loc_df75`, sets the bit counter `loc_37` to `0x07`, and then shifts `loc_35` left through eight passes, emitting each shifted-out MSB as a single vector digit via `loc_df1f`. `loc_dd29` [code] preloads that with a fixed slot index of `0xf8`, and `loc_dd27` [code] preloads a fixed value byte of `0xd0`; both are pure trampolines not reached in the capture, so their roles rest on the code.

### Math-box normalized coordinate pairs

The perspective-projected entries route through the math coprocessor and land as a (mantissa, exponent) pair. `loc_bd3e` [seen] is the appender. For a small input (`loc_57 < 0x10`) it emits the trivial pair (mantissa `0x01`, exponent `0x00`); otherwise it forms the 16-bit difference `loc_57`-`loc_5f` into operand `loc_6095` and the borrowed negation of `loc_5b` into `loc_6096`, sets mode `loc_608c`=`0x18`, issues the compute by writing `loc_a0` to `loc_608e` and `loc_6094`, spins while bit 7 of `loc_6040` is set, then reads results into `loc_79` (from `loc_6060`) and `loc_7a` (from `loc_6070`) and drops the mode to `0x0f`. It normalizes by rolling `loc_79` left into a decremented copy of the high result until a one rolls out of the top, yielding the exponent `((a>>1)^0x7f)+1` and the shift count as the mantissa; it stores the shift count into `loc_78` and appends the exponent then the mantissa-OR-`0x70` through the `loc_74` cursor at `loc_a9`, returning the exit cursor `loc_a9 + 2`.

`loc_bd09` [seen] folds the live deltas via `loc_c098`, lays the `loc_c765` header at offset `0x61`, resets `loc_a9`, and appends the math-box pair through `loc_bd3e`, threading its returned exit cursor. ## Enemy motion and the pursuit AI

Enemies occupy a bank of sixteen slots, and their per-frame life runs out of `loc_a618` [code]. It opens by seeding the frame-active marker `loc_10d` from the spawn budget `loc_10e`, then walks the slots from index `0x0f` down to `0`. A slot counts as live when its whole-coordinate cell `loc_283`,x is nonzero: for such a slot it integrates the motion axes (`loc_a6a9`), steps the velocities toward rest (`loc_a721`), and forces `loc_10d` to `0xff` to record that something moved. A slot whose `loc_283`,x is zero is free, and while the budget `loc_10e` is still nonzero the walk spawns a fresh enemy into it (`loc_a65b`). The step routine leaves its last axis's whole byte in a register, and the walk threads that value into each later spawn, where it reaches only the spawn's sound cue — the spawn coordinates themselves are always the fixed mid-ring `0x80` seed. After the walk it parks the slot counter `loc_37` at `0xff`; on even frames (`loc_3` bit 0 clear) with budget remaining it drains `loc_10e` by one; and if the whole pass found nothing live or spawned (`loc_10d` still zero) it raises the mode-request byte `loc_0` to `0x12`, the machine's way of asking for the next state when the tube empties.

### Spawning a new enemy

`loc_a65b` [code] fills a free slot. It marks the slot's three whole-coordinate cells `loc_263`,x, `loc_283`,x and `loc_2a3`,x with `0x80` (a mid-of-ring, sign-set seed), then loads three velocity pairs from the hardware random cells. From `loc_60da` it takes axis-1's velocity-low `loc_2c3`,x and, through `loc_a69b`, its velocity-whole `loc_323`,x. From `loc_60ca` it takes axis-0's velocity-low `loc_2e3`,x and a random whole step which it forces non-positive — the step is negated only when its top bit is clear — storing it as `loc_343`,x, so the primary axis always launches the enemy in the one direction (up the tube toward the rim). A second draw from `loc_60ca` gives axis-2's `loc_303`,x / `loc_363`,x. It closes by handing off to the sound cue `loc_ccc1`. Its helper `loc_a69b` [code] is a pure leaf: it reads a three-bit magnitude (`loc_60da & 0x07`, so 0..7) and negates it when the incoming value's bit 0 is set, yielding a signed random nudge in [-7,+7]. Neither routine's writes appear in the capture — spawning did not fire here — so both rest on the code.

### Integrating motion up the tube

`loc_a6a9` [code] advances a live slot's three axes with a shared fixed-point fold. For each axis it adds the velocity-low byte into a position fraction (axis 0: `loc_2e3`,x into `loc_223`,x; axis 1: `loc_2c3`,x into `loc_203`,x; axis 2: `loc_303`,x into `loc_243`,x), keeps the low byte of that sum as the new fraction, and folds the resulting carry plus the velocity-whole byte (`loc_343`/`loc_323`/`loc_363`,x) into the whole coordinate. The velocity-whole byte doubles as the direction sign: when its bit 7 is set the axis is falling and overflows when the whole drops below `0x10`, otherwise it is rising and overflows at `>= 0xf0` — the two ends of the tube ring. Axis 0's whole is provisionally the return value; if any of the three axes overflows the ring, that return is forced to zero. Axis 1's whole lands in `loc_263`,x and axis 2's in `loc_2a3`,x, and the (possibly zeroed) axis-0 whole is written last into `loc_283`,x — the same cell `loc_a618` reads to judge liveness, so a ring overflow that zeroes it retires the slot. The whole write-out is returned as a register live-out.

Velocities do not persist; `loc_a721` [code] bleeds them toward zero each frame. It seeds the saturation counter `loc_29` to `0xfd`, then steps each of the three velocity pairs through `loc_a75d` and stores the stepped low/whole back (`loc_2c3`/`loc_323`, then `loc_2e3`/`loc_343`, then `loc_303`/`loc_363`,x). Each axis that reaches rest bumps the counter by one, so only when all three saturate does `0xfd` roll through `0x00`; in that case the slot's whole coordinate `loc_283`,x is cleared, again retiring the slot. `loc_a75d` [code] does the single-axis work: it steps a signed 16-bit velocity (whole in the Y argument stashed to `loc_2b`, low in A) one fixed increment `loc_a788` (= `0x20`) toward zero — adding when the whole is negative, subtracting otherwise — and on crossing zero snaps both bytes to zero, writes `loc_2a` = 0, and increments the saturation counter `loc_29`. It returns the stepped low and whole. Neither `loc_a721` nor `loc_a75d` is reached in the capture, so their tags stay [code].

### Aiming at the player's segment

The pursuit math turns on a signed rotational distance around the tube rim, computed by `loc_a7a6` [seen]. It forms A − Y and stashes that raw difference into `loc_2a` (observed changing), then either returns the full byte when the flag `loc_111`'s high bit is set or masks to the low four bits and sign-extends bit 3 — the choice between a full-circle segment count and a wrapped short-way-around delta.

`loc_97c5` [seen] is the auto-aim toward the nearest threat. It scans the slot depth table `loc_2df`[0..`loc_11c`] for the smallest nonzero entry, holding that minimum in `loc_29` and its slot index in `loc_2a` (both observed), then feeds that slot's segment `loc_2b9`,idx and the player's segment `loc_200` through `loc_a7a6`. The same delta drives which way a rim-walking enemy chases. `loc_9d67` [code] reads slot x's target segment `loc_2b9`,x, differences it against `loc_200` through `loc_a7a6`, and records the side the target lies on in bit 6 of the slot flag `loc_283`,x: it clears bit 6 when the delta's top bit is set and sets it otherwise. `loc_9c4f` [seen] simply toggles that same bit 6 of `loc_283`,x in place and returns the new value — its XOR of `loc_283` is observed changing, so it carries [seen].

### Flipping between segments

`loc_9d82` [seen] animates a flipper's move from one segment to the next. `loc_9d06` [seen] settles an enemy the moment it climbs to its target depth — it is entered when a slot's tube-depth high byte `loc_2df`,x reaches the shared target `loc_202`. ## The mathbox: projection and level tables

Tempest draws its tube in perspective by handing point coordinates to a memory-mapped hardware math coprocessor and reading back the projected result. The coprocessor presents an input register block at `loc_6080`..`loc_6090` (plus the delta pair `loc_6095`/`loc_6096`), a busy/status register `loc_6040` whose bit 7 stays set while it computes, and result registers `loc_6060` (low) / `loc_6070` (high). The routines in this section prepare that hardware, drive a point through it, integrate the results, and — around all of that — build the per-level geometry tables the projection consumes.

### Preparing the coprocessor (loc_c1c3 [seen])

`loc_c1c3` is the between-passes reset. It clears a handful of zero-page work cells — `loc_81`, `loc_91`, `loc_80`, `loc_78`, `loc_90`, `loc_88` — and then wipes the coprocessor input block: `loc_6080`, `loc_6081`, `loc_6083`, `loc_6084`, `loc_6085`, `loc_6086`, `loc_6087`, `loc_6089`, `loc_608d`, `loc_608e`, `loc_608f`, `loc_6090` are all set to zero, while `loc_608c` is loaded last with the control value `0x0f`. Note precisely which input cells it does *not* touch: `loc_6082`, `loc_6088`, `loc_608a` and `loc_608b` are left as they were — this is not a blanket clear of the whole `loc_6080`..`loc_6090` range. The routine is heavily exercised, but in the capture every one of its writes landed on a cell that was already zero (and `loc_608c` was already `0x0f`), so although the reset genuinely ran, no transition to a non-zero value was ever observed at these targets; the role is confirmed [seen] but the effect of the clear on live data is not visible in this trace.

### The projection driver (loc_c098 [seen])

`loc_c098` feeds one point's signed X and Y deltas to the coprocessor, waits for each answer, and folds the scaled results into two running 16-bit accumulators. It first forms a 16-bit delta from the difference `loc_57 - loc_5f` in the low byte and `0 - loc_5b` (minus the borrow) in the high byte, writing the pair to `loc_6095`/`loc_6096`; a negative result is clamped up to +1 (`loc_6096` = 0, `loc_6095` = 1). It then computes the absolute horizontal magnitude `|loc_58 - loc_60|` with its sign captured in `loc_33` (`0xff` when `loc_58 < loc_60`, else `0x00`), and the absolute vertical magnitude `|loc_56 - loc_5e|` with its sign in `loc_34`. The horizontal magnitude is issued to the coprocessor through `loc_608e`/`loc_6094`, and the routine spins on `loc_6040` bit 7 until the result is ready.

The first accumulate reads the coprocessor result `loc_6060`/`loc_6070` into `loc_63`/`loc_64`, and — before waiting again — issues the *vertical* magnitude `loc_32` to `loc_608e`/`loc_6094` so the next multiply is already in flight. Guided by the horizontal sign in `loc_33`, it either subtracts or adds the offset pair `{loc_69:loc_68}` into the 16-bit accumulator `{loc_64:loc_63}`. On a subtract that signed-overflows, the accumulator saturates to the minimum `0x8000` (`loc_63` = `0x00`, `loc_64` = `0x80`); on an add that overflows it saturates to the maximum `0x7fff` (`loc_63` = `0xff`, `loc_64` = `0x7f`). After a second spin on `loc_6040` bit 7, the routine reads the vertical result into `loc_61`/`loc_62` and, guided by the vertical sign in `loc_34`, folds the second offset pair `{loc_67:loc_66}` into the accumulator `{loc_62:loc_61}` with the same saturating min/max limits. The net effect is a scaled, sign-directed integration of a point's two coordinate components into two clamped 16-bit results.

### Projecting a whole tube (loc_c473 [seen])

`loc_c473` runs every lane of the current tube through the projection driver in one sweep. It seats the caller's coordinate into `loc_57`, takes the output base index into `loc_38`, clears the clamp tally `loc_59`, and counts sixteen passes with `loc_37` running `0x0f` down through `0` (the loop ends when the decrement of `loc_37` goes negative). Each pass loads that lane's base coordinates from the geometry tables — `loc_3ce + col` into `loc_56` and `loc_3de + col` into `loc_58` — and invokes `loc_c098` to project them. It then squeezes each of the two signed accumulator results into a small on-screen window of `-4..+3`: a value with bit 7 set below `0xfc` is clamped to `0xfc` (with sign byte `0x01`), a non-negative value at or above `0x04` is clamped to `0x03` (with sign byte `0xff`), and anything in range passes through unchanged. The first pair is written to `loc_31a + out` (value) and `loc_32a + out` (sign); the second pair to `loc_33a + out` (value) and `loc_34a + out` (sign), indexed by `loc_38`, which walks down alongside `loc_37`. Every clamp bumps `loc_59`, and the routine hands back that clamp count. This is the step that turns each lane's stored tube-vertex geometry into the slot coordinate arrays the renderer reads.

### Building the level geometry (loc_c235 [seen])

`loc_c235` lays down the current level's per-lane tube geometry, once per level setup. It first derives a table seed by packing the byte at `loc_46 + loc_3d` through `loc_c2e8`, which also leaves an index in `loc_112`; call that index `y`. Using ROM tables addressed by `y`, it seeds the span scalars: the negated value `-loc_bc8c[y]` goes to both `loc_5f` and `loc_5d`, its complement `0x10 - that` to `loc_a0`, the guard `loc_5b` to `0xff`, `loc_bc9c[y]` to `loc_60`, and `loc_bccc[y]` to `loc_111`. A mode branch keyed on `loc_2` follows: when `loc_2` equals `0x1e` the offset pair is copied straight from ROM (`loc_bcac[y]` into `loc_68`, `loc_bcbc[y]` into `loc_69`); otherwise it forms the signed 16-bit difference `{loc_bcbc:loc_bcac} - {loc_69:loc_68}`, shifts it right four times keeping the low byte, and stores that as the level geometry scale in `loc_121`. It then clears `loc_66`, `loc_67`, `loc_10f`, `loc_110` and sets `loc_113` to `0x2c`.

The heart of the routine is a sixteen-column fill running `x` from `0x0f` down to `0`, with the ROM index `ny` starting at the seed and decrementing each column: it copies the tube-vertex base coordinates `loc_b97c[ny]` into `loc_3ce + x` and `loc_ba7c[ny]` into `loc_3de + x`, zeroes the projected-slot arrays `loc_31a + x`, `loc_33a + x` and `loc_39a + x` (the very cells `loc_c473` later fills), and copies `loc_bb7c[ny]` into `loc_3ee + x`. A second sixteen-column pass builds neighbour-midpoint tables by rounding-averaging each column with the next one, wrapping at the ends: `loc_435 + x` gets the average of `loc_3ce[(x+1)&0x0f]` and `loc_3ce[x]`, and `loc_445 + x` the average of the two `loc_3de` neighbours. The averaging adds the two bytes plus one and rotates right, carrying the ninth bit into bit 7 — a midpoint with round-to-nearest and a wrap through the top bit. So `loc_c235` produces the base coordinate tables (`loc_3ce`, `loc_3de`), the height/shape table (`loc_3ee`), the neighbour-midpoint tables (`loc_435`, `loc_445`), and the geometry scalars, all of which downstream projection consumes.

### The seed and the packed nibble tables (loc_c2e8 [seen], loc_c196 [seen], loc_b888 [code])

`loc_c2e8` reduces an input value into a packed table byte. If the value is `0x62` or greater it is replaced by a masked hardware read `loc_60ca & 0x5f` (a fallback drawn from a hardware/timer source). It splits the value into a quotient (`value >> 4`) and a remainder (`value & 0x0f`), looks the remainder up in ROM at `loc_bc7c + remainder`, stores that entry to `loc_112`, and returns the entry repacked into the high nibble with the low nibble forced to `0xf`, alongside the quotient in X and the remainder in Y. `loc_c235` uses exactly this: the returned packed byte becomes its column seed and the stored `loc_112` becomes its `y` index into the geometry ROM tables.

`loc_c196` unpacks the per-level shape/colour nibble tables. It takes the selector `loc_9f & 0x70`, clamps it to at most `0x5f`, and forms the packed-ROM index `X = (selector >> 1) | 0x07`. For `y` from 7 down to 0 it reads the packed byte at `loc_c1fd + X` and splits it: the low nibble is written to the zero-page table `loc_19 + y` and mirrored into display/colour RAM at `loc_800 + y`, while the high nibble goes to `loc_21 + y` and its mirror `loc_808 + y`, decrementing X each step. One pass thus fills four eight-entry tables from eight packed ROM bytes; in the trace all four came out holding real, varying values.

`loc_b888` is a small level-load wrapper: it runs `loc_c196` to rebuild those nibble tables and then seats a two-byte value into the vector-list tail cursor, writing `0x7f` to `loc_139` and `0x04` to `loc_13a`. This routine was **not reached in the capture** — no caller into it appears in the trace, and it is reached only through a computed dispatch / jump-table entry rather than a direct call — so neither the `loc_139` nor the `loc_13a` write was observed, and the specific tail-cursor values (`0x7f`, `0x04`) are read from the code, not confirmed by the write-tap; the routine is tagged [code].

### Coordinate clamp and mode scalars (loc_c453 [seen], loc_ca48 [seen])

`loc_c453` is a pre-projection nudge on the same coordinate operands `loc_c098` consumes. Guarded by `loc_5b` (it returns immediately when the guard is non-zero), it checks whether `loc_57` already sits `0x0c` or more above the reference `loc_5f`; if so it leaves it alone, otherwise it snaps `loc_57` up to `loc_5f + 0x0f`, capped at a ceiling of `0xf0`. The observed writes show `loc_57` making exactly this large jump up toward its reference, and the cell independently pulses across a wide range through the capture.

`loc_ca48` sets a mode flag bit and a paired scale byte from two gates. It defaults to `(a, y) = (0x00, 0x10)`, but when both `loc_117` and `loc_3d` are non-zero it selects the alternate pair `(0x04, 0x08)`. It then copies bit 2 of the chosen `a` into the flag `loc_a1` while preserving that byte's other bits, and stores `y` to the scale cell `loc_b4`. Both writes were observed, but only the default branch ran in the capture — `loc_a1`'s bit 2 stayed clear and the alternate `a = 0x04` path was never taken — so the bit-set behaviour of the alternate branch is supported by the code but not exercised in this trace.

## Sound, POKEY and the interrupt heartbeat

Tempest's audio hardware is two POKEY chips mapped into the $60xx space: POKEY 1 begins at loc_60c0 (its four AUDF/AUDC voice pairs run loc_60c0..$60c7, its AUDCTL is loc_60c8, its RANDOM/SKRES port is loc_60ca, its SKCTL is loc_60cf) and POKEY 2 begins sixteen bytes later at $60d0 (voices $60d0..$60d7, AUDCTL loc_60d8, RANDOM loc_60da, SKCTL loc_60df). Above the hardware sits a software mixer of sixteen slots kept in zero-page tables, and the whole thing is pumped once per interrupt. The routines here split into three layers: the request front end that asks for a sound, the per-slot engine that renders active sounds into POKEY registers, the cold reset that scrubs both chips, and — sharing the same interrupt tick — a trio of gated counters plus the display-channel bookkeeping that rides alongside them.

### Requesting a sound: trampolines, the enable gate, and the registrar

Most of the routines in this group are one-line request stubs. Each loads a fixed sound identifier and hands it down the same chain. loc_ccb5 raises id 0x0f, loc_ccc1 raises 0x1f, loc_ccea raises 0x2f, loc_cd02 raises 0x3f, loc_ccb9 raises 0x4f, loc_ccb0 raises 0x5f, loc_ccee raises 0x6f, loc_ccf2 raises 0x7f, loc_ccbd raises 0x8f, loc_ccf6 raises 0x9f, loc_ccfe raises 0xbf, and loc_cd06 raises 0xcf. Every one of these routes its id through the enable gate loc_ccc3, and those that receive them from a live caller (loc_ccb5, loc_ccc1, loc_ccb0, loc_ccee, loc_ccf2, loc_ccf6, loc_ccbd) carry the caller's X and Y through unchanged so the registrar can save and restore them. All of these stubs are [code]: they make no write of their own, so a write-only capture cannot witness them executing, even though the registrar they feed is heavily exercised and observed. loc_ccfa is the one outlier in shape — it raises id 0xaf but jumps straight to the registrar loc_ccc7, skipping the enable gate entirely; it is [code], not reached in the capture (the branch into it never fired).

The enable gate loc_ccc3 [code] is the choke point: it tests bit 7 of the sound-enable flag loc_5, and if that bit is clear it simply returns and the request is dropped; only with the flag set does it fall through into the registrar with the id still in A. It too writes nothing of its own, so the gate's own vectoring is unwitnessed in this capture, though the registrar it guards is [seen].

The registrar loc_ccc7 [seen] is where a request actually lands in the mixer. It first stashes the caller's X into loc_31 and Y into loc_32 so it can restore them on the way out. Then it walks the sixteen mixer slots from 0x0f down to 0, and for each slot reads one byte from the sound-definition table at loc_cb01 indexed by an id that decrements in step with the slot counter. A zero table byte means "nothing for this slot" and is skipped; a nonzero byte claims the slot — the routine writes the slot number into the reservation cell loc_bf, stores the table byte into that slot's frame cell (loc_c0 + slot), lights both of the slot's live flags by writing 0x01 into (loc_e0 + slot) and (loc_f0 + slot), and then immediately restamps loc_bf back to the 0xff sentinel. MAME confirms these table writes into the loc_c0/loc_e0/loc_f0 slot arrays together with the loc_bf claim-then-0xff dance. The effect is that a single request can seed several slots at once — one per nonzero row of its definition — each armed with its starting frame and its two timers primed to one tick.

### Rendering active sounds into POKEY: loc_cd0a

loc_cd0a [seen] is the per-slot voice engine, stepped once every interrupt immediately after the counter stepper below. It sweeps the sixteen slots from 0x0f down to 0. A slot whose frame cell (loc_c0 + slot) is zero is idle and skipped, and the slot currently named in the reservation cell loc_bf is skipped as well. For a live slot it decrements the fast timer (loc_e0 + slot); while that timer is still nonzero the slot waits and the sweep moves on. When the fast timer reaches zero it decrements the slow timer (loc_f0 + slot), and the outcome forks on whether the slow timer is still running.

If the slow timer has not yet expired, the engine takes a single animation step. It uses the slot's current frame byte, chooses one of two envelope banks by that byte's high bit — the high bank rooted at loc_cccb (via loc_cccc/loc_cccd) when bit 7 is set, otherwise the low bank rooted at loc_cbcb (via loc_cbcc/loc_cbcd) — indexes it by the frame byte doubled, reloads the fast timer from the bank, and reads a level delta which it adds to the running level cell (loc_d0 + slot). For odd-numbered slots it then restores the previous high nibble of that level byte, so those slots only ever update their low nibble.

If both timers have expired, the engine instead walks the frame forward: it advances the frame cell (loc_c0 + slot) by two, re-reads it, again selects the high bank at loc_cccb or the low bank at loc_cbcb by the frame's high bit, and from the chosen bank loads a fresh level into (loc_d0 + slot), a fresh slow-timer reload into (loc_f0 + slot), and a fresh fast-timer value into (loc_e0 + slot). It keeps walking until it lands on a nonzero fast-timer entry; a zero entry that also leaves a zero level ends the slot, otherwise it loops.

Whichever branch ran, the engine finishes the slot by publishing its level byte to hardware: slots 0 through 7 write their level into POKEY 1 at (loc_60c0 + slot), and slots 8 through 15 write into (loc_60c8 + slot), which for those indices lands in POKEY 2's voice registers at $60d0..$60d7. MAME confirms these POKEY register writes, so this routine is the observed bridge from the software mixer to the two sound chips.

### Cold reset of both chips: loc_cd95

loc_cd95 [seen] is the dual-POKEY initialiser. It first parks both SKCTL registers, loc_60cf and loc_60df, at 0 and clears the flag cell loc_720. It then performs a RANDOM-generator self-test: it samples POKEY 1's RANDOM port loc_60ca and POKEY 2's RANDOM port loc_60da once, then polls up to five times, and the moment either port reads a different value than its first sample it latches that original loc_60ca sample into loc_720 and stops — proving the noise generators are actually free-running. With the test done it writes the canonical SKCTL value 7 into both loc_60cf and loc_60df, then loops the eight-entry voice arrays: it zeroes POKEY 1's registers (loc_60c0 + x) and POKEY 2's registers (loc_60d0 + x) for x from 7 down to 0, and in the same pass clears the matching software slot cells (loc_c0 + x) and (loc_d0 + x). Finally it zeroes both AUDCTL registers, loc_60c8 and loc_60d8. The result is both chips reset to silence with their control registers in a known state and the mixer's low eight slots cleared.

### The interrupt heartbeat: loc_cf24

loc_cf24 [seen] runs on essentially every interrupt, reached from the interrupt handler at loc_d704 immediately before the sound engine loc_cd0a, and it is the busiest arithmetic in this group. It steps three parallel lanes indexed x = 2, 1, 0, each lane enabled by a distinct bit of the control byte loc_8 (bit 0, bit 1, bit 2, extracted by the per-lane shift pattern that consumes the carry). For an enabled lane it advances that lane's position cell (loc_d + x): the value is masked to five bits and clamped/wrapped modulo 0x20 (the observed write caps 0x20 down to 0x1f), with a separate branch that adds 0x20 and rewraps when the carry path is taken. It manages a per-lane down-counter (loc_10 + x) that reloads to 0x78 when it expires, drives a blanking countdown through loc_c (set to 0xf0 when the loc_8 & 0x08 gate is clear), and on each qualifying step bumps the per-lane counter (loc_13 + x). It also folds a per-pass contribution — derived from bits of loc_9 (the 0x0c and 0x10 fields) — into the running accumulators loc_16 and loc_17, and separately advances loc_18 and nudges loc_6, using the small table at loc_cfd9 (indexed by the high bits of loc_9) as the threshold it subtracts loc_16 against.

After the three lanes, loc_cf24 runs two tail clamp passes over the loc_13 lane triple, and the two passes are deliberately different. The first pass (entered when bit 0 of loc_7 is clear) processes each lane only when its counter is at least 0x10, and subtracts 0x10 from it (adding 0xef with carry set), tallying how many lanes it touched. Only if that first pass touched nothing does the second pass run, and the second pass processes any nonzero lane, subtracting 0x11 (adding 0xef with carry clear) and stopping the moment a subtraction goes negative. The two constants — 0x10 gated on "at least 0x10", then 0x11 gated on "nonzero" — are not interchangeable. The precise game meaning of the three lanes and their accumulators is not fully settled from the code alone, but the routine's role as the per-interrupt counter/accumulator step that immediately precedes the sound render is clear and observed.

### POKEY control-register packing and the option switches

loc_dbe0 [code] is a small bit-packer that reaches into the POKEY control registers. It first stores its incoming argument into POKEY 2's register loc_60db, then reads the low three bits of POKEY 2's AUDCTL loc_60d8 and mirrors exactly those three bits into both the scratch cell loc_37 and POKEY 1's register loc_60cb. The value it returns is those same three low bits merged with one further bit — bit 5 of POKEY 1's AUDCTL loc_60c8, relocated down (shifted right by two) into the returned nibble; that relocated bit rides only in the return value and is not part of what was mirrored to loc_37/loc_60cb. It is tagged [code] because although the routine is entered, every write observed in the capture was a constant (loc_60cb and loc_37 seen at 0, loc_60db seen at 0xd0), so the bit-packing behaviour itself was never witnessed varying.

loc_d6bb [seen] decodes the cabinet option switches into game configuration and is the live caller of that packer. It reads the option-switch input port loc_e00, keeps a copy in loc_a, and slices it three ways: bits 5-3 index the ROM table at loc_d6f7 to set loc_156, bits 7-6 index loc_d6ff to set loc_158, and bits 2-1 (the value masked with 0x06) index the paired tables loc_d6b3 and loc_d6b4 to set loc_ac and loc_ad. It also reads the second option port loc_d00, toggles it with 0x02, and stores the result in loc_9. Finally it passes loc_ad through loc_dbe0's merge and records the returned nibble in loc_16a. The write-tap confirms the port reads and the loc_156/loc_158/loc_ac/loc_ad/loc_9 stores, so the config-decode role is observed.

### The math-block handshake: loc_dce6

loc_dce6 [code] reads like the operand-load and result-collection half of a hardware compute-block exchange, and it is not reached in the capture. By code it zeroes the scratch cells loc_73, loc_414 and loc_6090, deposits its two operands — A into loc_608e and X into loc_608f — sets a step count of 0x10 into both loc_608c and loc_6094, and then scans a sixteen-slot window: counting X down from 0x10, it reads loc_6040 and, on the first slot whose high bit is clear (a "ready" slot), reads that slot's low result from loc_6060 and high result from loc_6070 and returns the pair; if the counter runs off the end first it exits with no result. Because it is [code] and not exercised, only this static reading stands — its precise hardware identity and the meaning of the $6040/$6060/$6070 window are suggested by the operand/result shape but not confirmed by the capture.

### Draw-channel record sorting and slot ticking

Two further routines share this group's "channel" and "slot" bookkeeping. loc_ac3f [seen] is a per-channel record sorter that is heavily reached. It clears bit 6 of loc_5, conditionally pre-clears a scratch block through loc_ca62 when (loc_9 & 0x43) equals 0x40, seeds a request entry through loc_ddfb, and zeroes loc_601. It then processes two channels (0 and 3, chosen by whether loc_3e is zero): for each it loads the channel's key triple into loc_2c/loc_2d/loc_2e, sets the parity flag loc_36 from the channel's low bit, primes the working bounds (loc_2b = 0, loc_2a = 0x1a, loc_29 = 0x1a) and the pass counter loc_605 = 0, then bubble-sorts the stored row triples at loc_620/loc_61f/loc_61e (with the parallel payload rows at loc_520/loc_51f/loc_51e swapped alongside once the cursor is high enough) into lexicographic order, incrementing loc_605 for each pass it takes to settle. It records that pass count per channel into (loc_600 + channel), and MAME confirms loc_605 climbing and the per-channel loc_600 store. After both channels it nudges the running total loc_601 (bumping it when it has caught up to loc_600 and is still below 0x63), then derives the packed request byte loc_603 from the flag loc_3d — building ((flag XOR 1) << 2) OR flag, then adding 0x05 plus flag's bit 6 — and hands off to the request walker loc_ad22.

loc_ad6e [code] is the per-frame tick of the active slot, and it is not reached in the capture. By code it sets loc_1 to 0x06, and while the low five bits of loc_3 are zero it expires the countdown loc_605 into a reset (writing 0x14 into loc_00 when the countdown hits zero, then returning). Otherwise it clamps the active slot's value at (loc_606 + slot) through loc_adce and pins it to the 0x00..0x1a rail (values with bit 7 set collapse to 0x1a, values at or above 0x1b collapse to 0x00), writing the clamped value back. It then gates on bits 3-4 of loc_4e (clearing that byte down with a 0x67 mask), and when the gate is open it steps loc_602 and the counter loc_604 down by one; if that step goes negative it re-arms — routing through loc_ddf7 when (loc_600 + loc_3d) is below 0x04 and then loc_ad22 — otherwise it clears the retired neighbouring slot (loc_606 + (slot - 1)) to zero. Being [code], only this static reading stands; none of its write paths ran in the capture.

## The EAROM high-score store

The high-score table, entered initials, and operator settings survive power-off because Tempest keeps them in an ER-2055 EAROM — a small serial NVRAM wired behind three ports: `loc_6000` (the data/address byte the machine drives into the chip), `loc_6040` (the control line that clocks and strobes it), and `loc_6050` (the byte the chip reads back). Software never touches those ports directly except through one state machine, `loc_de1b`, which is fed by a short family of request-setters that raise flags in a fixed cluster of zero-page-adjacent cells, `loc_1c6` through `loc_1cf`.

**The request cluster.** `loc_1c7` holds one pending-request bit per EAROM region; `loc_1c8` holds the matching direction bit for each region (set means write the region out to the chip, clear means read it back in); `loc_1c6` is a blank-mode flag (when nonzero the write path zeros the RAM source as it goes, i.e. erases rather than saves); `loc_1c9` is where the machine leaves a per-region read-verify status for its caller; and `loc_1ca` through `loc_1cf` are the machine's private working state (`loc_1ca` current-op mode byte, `loc_1cb` the RAM cursor within a region, `loc_1cc` the port cursor, `loc_1cd` the region's end offset, `loc_1ce` the isolated single-region walking bit, `loc_1cf` the running checksum accumulator).

**Queuing a transfer.** All of the setter entries converge on one tail that stamps `loc_1c6` from Y and ORs a mask into *both* `loc_1c7` and `loc_1c8`, so a queued region defaults to a write. `loc_ddfb` [seen] is that observed path: it drives mask `0x04` with a zeroed index, requesting the single region whose bit is `0x04` as a plain (non-blank) write-back — the save that follows a game that made the table. `loc_ddf7` [code] would instead OR `0x03` (the two lower regions) through the same zeroed-index tail, and `loc_ddf3` [code] forces the index byte to `0xff` (blank mode) while passing the caller's live mask, so it requests an *erasing* write of whatever regions are in A; neither of those exact masks/indexes appears in the capture — only `loc_ddfb`'s `0x04`-with-zero-index write is reached. `loc_dde9` [code] is a thin trampoline that hands `loc_ddf3` the fixed mask `0x04`, i.e. a blank (erase) write of that one region; it is not reached in the capture. `loc_ddf1` [code] is the all-regions erase: it stamps `loc_1c6 = 0xff` and ORs `0x07` into both `loc_1c7` and `loc_1c8`, queuing all three regions as blank write-backs — but its own values (index `0xff`, mask `0x07`) are never seen at the merge, so its role rests on the code, not the tap.

**Loading versus saving.** The read side has its own initiator. `loc_de11` [seen] sets `loc_1c7 = 0x07` (all three regions pending) and clears `loc_1c8` to `0x00` (all directions clear = read), then runs `loc_de1b` in place — this is the power-on load that pulls the whole saved table back out of the chip. Because it *sets* rather than ORs, and its writes of `loc_1c7 = 0x07` / `loc_1c8 = 0x00` are both observed, it is grounded as the load initiator, distinct from the OR-in-a-mask save family above.

**Servicing a transfer, one byte per pass — `loc_de1b` [seen].** This is the engine, reached on essentially every pass and doing the great bulk of the real work in this subsystem. Each entry it looks at `loc_1ca`: if the mode byte is idle and `loc_1c7` still has a pending region, it opens a fresh region. To do that it clears `loc_1cb`, `loc_1cf`, and `loc_1ce`, then runs a rotate loop that scans `loc_1c7` from the top down and isolates the **highest** (most-significant) set request bit into `loc_1ce` — it rotates left and breaks on the carry-out of bit 7, so it takes the most-significant pending region first, never the lowest. It sets the op mode in `loc_1ca` to `0x80` when that region's direction bit is also set in `loc_1c8` (a write) or `0x20` otherwise (a read), clears the serviced bit out of `loc_1c7` by XORing `loc_1ce` back in, and then, indexing four packed ROM tables at `loc_dddd`/`loc_ddde`/`loc_dde3`/`loc_dde4` by twice the bit position, loads the region's starting port cursor into `loc_1cc`, its end offset into `loc_1cd`, and its RAM-side row pointer into `loc_bd`/`loc_be`.

With a region open, every re-entry services exactly one byte. The machine resets `loc_6040` to 0, shifts `loc_1ca` to decide the sub-step, and either drives a byte out to `loc_6000 + loc_1cc` (on a write, zeroing the RAM source first through the `(loc_bd),Y` pointer when `loc_1c6` marks blank mode) or performs the EAROM read handshake — pulsing `loc_6040` through its strobe codes, reading the byte back from `loc_6050`, and storing it into RAM through that same row pointer. Either way it folds the byte into the running checksum in `loc_1cf`, bumps both the RAM cursor `loc_1cb` and the port cursor `loc_1cc`, and re-enters. When the port cursor reaches the region's `loc_1cd` limit the final byte is the checksum itself: on a write it is emitted, and on a read it is XORed against the accumulated `loc_1cf`. A clean match retires the region; a mismatch walks back down from `loc_1cb` zeroing the whole region through `(loc_bd),Y` (discarding a corrupt block) and records the failure by ORing `loc_1ce` into `loc_1c9`, the status the caller later reads to know which saved blocks came back bad. Each pass ends by writing an output code to `loc_6040`; a nonzero code yields back to the caller between hardware strobes, while a zero code loops straight back to the top to open the next pending region.

## State-reset, init and per-frame update chains

This subsystem is the machine's skeleton: the leaves that blank RAM and stamp fixed
constants at a cold start or a fresh round, and the per-frame spine that ages the
in-flight objects, steps the master clock, keeps the drawn control-block in sync with
the operator inputs, and folds scoring into place. Many of the same reset leaves are
reused by the per-frame path, so the boundary between "init" and "update" is a matter
of who calls them, not of what they do.

### The cold-init reset leaves

A small family of straight-line leaves is walked in sequence by the boot/reset driver
(the init entry that falls through loc_902b) to wipe the previous game out of RAM and
plant the starting values. **loc_921b** ([seen]) seeds five scalars — `loc_200`=0x0e,
`loc_51`=0xf0, `loc_106`=0x00, `loc_201`=0x0f, `loc_202`=0x10 — all fixed constants;
`loc_201` and `loc_202` are the phase-control byte and a counter the per-frame spine
later reads and advances, and `loc_51`/`loc_200` vary elsewhere, so this is a genuine
state stamp rather than a no-op. **loc_9234** ([seen]) builds a seventeen-byte
parameter block: the header cell `loc_3ab` takes the current value of `loc_15b`
(a live source, observed draining 0xf→0xc), then the sixteen-entry per-lane array
`loc_3ac`..`loc_3ac+0x0f` (one byte per tube lane) is filled top-down with `loc_15a`;
in the capture `loc_15a` read 0, so the lane array clears, but the loop writes whatever
that source holds. It is reached both from the reset chain and from loc_9009/loc_90c4.

Three near-identical block-clearers follow. **loc_926f** ([seen]) zeroes the seven
bytes `loc_2df`..`loc_2df+6` then clears seven scattered flag cells
(`loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146`);
`loc_108` and `loc_142` hold live values elsewhere, so the reset is meaningful even
though its precise game role is unresolved and it keeps a `loc_`-form name.
**loc_928f** ([seen]) zeroes the twelve bytes `loc_2d3`..`loc_2d3+0x0b` and clears
`loc_135` and `loc_a6`. **loc_929f** ([seen]) zeroes the eight bytes
`loc_30a`..`loc_30a+7` and clears the trailing flag `loc_116`. **loc_92ad** ([seen])
is the smallest of the group: a single clear of `loc_50` to 0 — a cell the frame code
churns hard elsewhere, so zeroing it at init matters. Alongside these, **loc_a831**
([seen]) clears the pair `loc_3aa` and `loc_125` together; `loc_125` is a readiness
latch that other code raises to 0xff, so dropping it to 0 here re-arms that handshake.
This leaf is invoked from the reset sequence in loc_9009 (which then seeds its own
scalars) and from loc_90c4.

Two of these leaves outlive the boot chain: `loc_928f`'s twelve-byte wipe is called
again every frame by the update spine (see loc_a504 below), and `loc_a5cb` (below) is
likewise shared between init and the frame loop — the reset code is not boot-only, it
is the machine's general "return this region to baseline" primitive.

### Constant-seeding leaves reused at state entry

A second cluster stamps fixed working values when the machine enters a particular
state, several of them overlapping on the zero-page scratch cells `loc_0`..`loc_5`.
**loc_b0e7** ([seen]) is a startup seeder: `loc_0`=0x0a, `loc_2`=0x00, `loc_4`=0xdf,
`loc_1`=0x12, `loc_14e`=0x19, `loc_14d`=0x18 — every write observed at its own site,
values constant. **loc_c97b** ([seen]) and **loc_ca18** ([seen]) are entered by
computed dispatch and seed the same scratch block for their respective states:
loc_c97b writes `loc_2`=0x04, `loc_1`=0x00, `loc_0`=0x0a, `loc_4`=0x14; loc_ca18 first
masks `loc_5` down to its low six bits (`loc_5 &= 0x3f`, clearing the top two flag
bits) and then lays down `loc_3e`=0x00, `loc_2`=0x1a, `loc_0`=0x0a, `loc_4`=0xa0,
`loc_16b`=0x01, `loc_1`=0x0a. The three differ only in the constants they choose for
the shared cells, which is how each state hands the common machinery a different
tempo/geometry setup.

**loc_ca62** ([seen]), `clearBlock40`, zeroes the six-byte staging block
`loc_40`..`loc_45` — all six writes observed. It is an optional pre-clear invoked by
loc_ac3f and loc_c90c, which then read `loc_40`/`loc_41`/`loc_42`-relative bytes back
as three-byte staging entries. **loc_a7bd** ([seen]), `resetSpikeTableAndArmFlag`,
zeroes the eight-byte table `loc_3fe`..`loc_405`, overwrites the last slot `loc_405`
with 0xf0, and arms `loc_115`=0xff. Its caller loc_97f8 — the per-frame step of the
descending spike/pulsar object — invokes it once the object's depth `loc_202` reaches
its threshold `loc_50` while the flag `loc_115` is still clear, i.e. it re-lays the
spike table when the moving object crosses that mark.

**loc_a789** ([code]), `resetSlotStateTable`, would zero the sixteen-byte per-slot
state/flag table `loc_283`..`loc_283+0x0f` and re-seed scalars (`loc_10e`=0x20,
`loc_10d`=0x20, `loc_1`=0x04, `loc_68`=0, `loc_69`=0), but it is **not reached in the
capture** — it made no own-cell writes there (that table's cells were touched only by
loc_d953). It runs only through loc_ad22's spawn arm, which itself did not fire in the
capture; its role therefore rests on the code.

### Wave / round (re)init

**loc_a5cb** ([seen]) prepares a wave. It sets `loc_0`=0x20, ORs bit7 into `loc_106`,
clears `loc_104`, `loc_107`, `loc_5c`, `loc_123`, sets `loc_105`=0x02, then walks the
sixteen lane entries `loc_3ac`..`loc_3ac+0x0f` and counts how many are nonzero into the
tally `loc_123` (observed climbing 0x0→0x6 as it counted six occupied/spiked lanes).
If any lane is live *and* the level `loc_9f` is below 0x07, it loads an intro/parameter
set — `loc_4`=0x1e, `loc_0`=0x0a, `loc_2`=0x20 — and overwrites the tally with the
marker `loc_123`=0x80. It always finishes by raising the readiness latch `loc_125`=0xff.
It is reached both from the reset path and from the per-frame spine.

**loc_ad22** ([seen]), `initNextRequestedSlotFromField`, drains a packed request word
to spawn the next queued slot. Each pass tests `loc_603`: when it reaches 0 the routine
writes the exhausted status `loc_0`=0x14 and returns (this is the observed path). While
bits remain, it takes the low two bits as a slot index — `loc_3d = (loc_603 & 3) - 1`
— and consumes them with two right shifts of `loc_603`; if that slot's byte
`loc_600+index` is 0 or ≥0x09 it loops on to the next field. For a valid slot (1..8)
the spawn arm — which is **code-only in this capture** — triples the slot byte
(`n<<1` then `+n`), complements it (`^0xff`), subtracts 0xe5, and stores the result in
`loc_602`; runs loc_ca48; seeds `loc_605`=0x60, `loc_4e`=0, `loc_50`=0, `loc_604`=0x02;
runs loc_a789 to blank the per-slot table; and writes the armed status `loc_0`=0x24
before returning. Only the drain/exhaust half (the `loc_603` shifts, the `loc_3d`
index, the 0x14 exit) was exercised.

### The per-frame update spine

**loc_a504** ([seen]), `ageShotsAndStepPhaseClock`, runs at the tail of the frame
dispatcher loc_970b every frame, and again from loc_9729 when the phase-control byte
`loc_201` is negative; that byte's sign selects one of two arms.

The **positive arm** (`loc_201 < 0x80`) bumps a per-slot timer: when either gate
`loc_455` or `loc_11b` is live and `loc_42` has climbed past 0x17, it increments the
cell at `loc_00 + loc_40`. It then bails if `loc_106` is nonzero; otherwise, when both
`loc_3ab` and `loc_116` are clear, it scans the shot/depth table `loc_2df` downward
from index `loc_11c` and, only if no live entry has already grown to ≥0x11, runs the
resets loc_a5cb then loc_928f. Finally, a chain of input/mode gates
(`loc_4d & 0x60`, `loc_5` bit7, `loc_9 & 0x43 == 0x40`) each of which must pass leads
to a bare loc_a5cb.

The **negative arm** (`loc_201 ≥ 0x80`), the one exercised in the capture, first bails
if any of `loc_135`, `loc_a6`, `loc_116` is set. It then **ages every live shot**:
scanning `loc_2df` downward from `loc_11c`, each nonzero entry is advanced by +0x0f and
snapped to 0 when it would reach the 0xf0 ceiling — objects that run out the far end of
the tube expire. Next, keyed on `loc_48 + loc_3d`: if that byte is not 0x01 it advances
a single counter, `loc_202` += 0x0f (kept to a byte), and proceeds once the sum reaches
0xf0; if it *is* 0x01 it clears `loc_10f`, sets `loc_114`=0x01, and steps the 16-bit
countdown clock `loc_5b`(high)/`loc_5f`(low) **down by 0x20** — `loc_5f -= 0x20` with a
borrow into `loc_5b` — proceeding when the high byte lands on the marker 0xfa. On a
"proceed", it writes `loc_00`=0x06, runs loc_928f, and folds a running total into
`loc_3ab`: `loc_3ab = min(0x3f, loc_108 + loc_109 + loc_3ab)`, clamped at 0x3f.

### The control-block snapshot / rebuild chain

This chain keeps the drawn control-block regions in step with the operator's live
switch/spinner state, rebuilding them only when that state changes.

**loc_ac20** ([code]) refreshes the live snapshot via loc_d6bb, then compares the top
five bits of `loc_a` (`loc_a & 0xf8`) against the cached `loc_71e` and the low two bits
of `loc_16a` (`loc_16a & 3`) against the cached `loc_71f`. On a match it takes the
shared no-op tail loc_ac3e; on a mismatch it falls to loc_ac36, which sets the low two
request bits of `loc_1c9`. It is entered in the capture, but only the match→no-op path
fired — the mismatch→rebuild-request path is **code-only here**.

**loc_abac** ([seen]) is the rebuilder, and its rebuild body did fire (the template
copy and the latch writes were observed). It first refreshes edge state through
loc_ac20, arms `loc_100`=0x08, and — when all three sources `loc_71b`, `loc_71c`,
`loc_71d` are idle — asks loc_ac36 to raise both request bits. It then reads the
request byte `loc_1c9`: bit0 chooses the copy length (0x17 entries if set, else 0x0e)
and copies the template `loc_ac08`..`loc_ac08+top` into `loc_606`..`loc_606+top`; bit1
chooses the fill length and writes 0x01 across `loc_706`..`loc_706+top`. If either bit
is set it latches the current snapshot into the caches (`loc_71e = loc_a & 0xf8`,
`loc_71f = loc_16a & 3`), and finally clears the two request bits (`loc_1c9 &= 0xfc`).

**loc_aba2** ([code]) is the gated front door: it refreshes through loc_ac20 and, if the
low two request bits of `loc_1c9` are clear, takes the no-op tail loc_ac07; otherwise it
runs loc_abac. **loc_d7e1** ([code]) is another entry that arms two mode bytes
(`loc_5`=0x00, `loc_1`=0x02) and then only rebuilds while conditions are quiet: it bails
if `loc_1ca` is nonzero (busy), bails if bit4 of the hardware byte `loc_c00` is clear
(disabled), sets `loc_0`=0x00, and — only if a request is pending in `loc_1c9 & 3` —
runs loc_abac. Both aba2 and d7e1 had constant inputs in the capture, so their branch
selection rests on the code.

### Scoring folds reached from the update path

**loc_ca6c** ([seen] for the score add; the award half is code-only) adds a three-byte
BCD amount into the score trio and, on crossing a threshold, may award. Gated off unless
bit7 of `loc_5` is set, it picks the destination offset `y` = 0 when `loc_3d`==0 else 3,
addressing the score bytes `loc_40+y`/`loc_41+y`/`loc_42+y`. When the passed index
`x < 0x08` it adds the two fixed table bytes `loc_caf1+x` and `loc_caf9+x` into the low
two score bytes (the observed score-cell changes) and treats the top byte as 0; for
`x ≥ 0x08` it adds the live operand triplet `loc_29`/`loc_2a`/`loc_2b`. It then adds the
carried third byte into `loc_42+y`. The threshold logic range-checks the high byte
against `loc_156` — including a subtract loop (bcdSubByte) that lands an award only on an
exact multiple — and the award itself, `doAward`, bumps a per-slot counter at
`loc_48 + loc_3d` while it is still under six, fires sound cue 0x4f via loc_ccc3, and
raises `loc_124`=0x20. The score arithmetic was observed; the bonus-life award path did
not fire, so that half is code-only.

**loc_a1fa** ([seen]) advances a slot's counter toward its per-target limit and, on a
hit, awards and can cost a life — role writes observed changing. It reads the target
index `y` = `loc_2ad + x` and the limit `loc_3ac + y`; a zero limit returns immediately.
When the counter `loc_2d3 + x` reaches the limit it clamps the limit cell
(`loc_3ac+y` = counter, or 0 if the counter has saturated at ≥0xf0), bumps the hit tally
`loc_2f2 + x`, flags the target with `loc_39a + y`=0xc0, chimes through loc_ccf6, primes
the award operand (`loc_2a`=0, `loc_2b`=0, `loc_29`=0x01) and folds it in via
loc_ca6c(0xff), then picks up the live index from `loc_37`. Finally, once a target's hit
tally `loc_2f2` reaches 0x02, it resets that slot's counter `loc_2d3` to 0 and decrements
the life counter `loc_135`. It returns the slot index live at exit.

## Utilities and shared tails

This section collects the small, general-purpose leaves the rest of the machine leans on: a binary-to-decimal converter and the digit-emit chain that formats on-screen counters, a byte-splitter that seeds the tube geometry math, two array seed/swap helpers, a flag-setter that requests block rebuilds, and a family of bare-return stubs that terminate branch chains.

**Numeric display formatting.** `loc_aaf5` [seen] is the game's binary-to-BCD converter, heavily exercised. It runs the classic double-dabble: eight passes, each shifting the top bit out of the source byte and doubling a BCD accumulator in decimal arithmetic so the shifted-out bit folds into the units digit. The finished packed-BCD result is written to **both** `loc_29` and `loc_2c` — the two cells receive the identical value, so both span `0x00..0x99`. (The narrower `0x00..0x63` seen on the input side is the raw binary handed in by clamping callers, not the BCD output.) Its immediate caller `loc_af77` packs a value this way and then hands `loc_29` to the nibble-emit helper `loc_dfb1(0x29, 0x01)`, which walks a run of zeropage bytes high-nibble-then-low into the vector draw stream — turning a binary count into drawn decimal digits. `loc_af71` [code] sits one step above: it clamps its incoming byte to a maximum of `0x63` (`Math.min(a, 0x63)`) and then routes into that same `loc_af77` pack-and-emit path, so a value that would overflow two BCD digits is pinned at 99 before it is drawn. `loc_af71` performs no own-cell write of its own; its role rests on the code — clamp, then emit through the BCD chain.

**Byte partitioning for tube geometry.** `loc_93e0` [seen] splits an input byte into a fine value and a coarse index, reached exclusively through the three call sites in `loc_92c5`. It runs three MSB-first passes: each pass shifts the input left one bit while folding that same bit into the low end of a `0xff` seed accumulator. After three passes the input has been shifted left three places (`A = input << 3`, its low five bits promoted, its top three shifted away), the seed holds `0xf8 | top-three-bits`, and that seed is its one own-cell write, stored to the `loc_29` scratch (observed changing, e.g. from `0xff` to `0xfe`). A coarse index is then derived from the seed's complement as `((seed ^ 0xff) + 0x0d) >> 1`, observed landing in the range 3..6. The three live-outs — the shifted value in A, the coarse index in X, the seed in Y — all ride the return so the caller receives the full partition.

**Array seed and swap helpers.** `loc_92b2` [code] swaps two parallel 18-entry tables slot for slot: for each index from `0x11` down to `0`, the entry at `loc_3aa + x` and the sibling at `loc_3bc + x` trade places, so each slot ends up holding what its partner held. Neither store fired in the capture, so the routine was not reached; the swap logic reads cleanly from the code but is ungrounded here. `loc_b85f` [code] is a straight-line seed of two paired three-entry arrays, writing the fixed values `0x00`, `0x04`, `0x0c` into `loc_22`/`loc_809`, `loc_23`/`loc_80a`, and `loc_24`/`loc_80b` respectively before returning. It, too, was not reached in the capture — no dispatch or tail target exercised it — so it is accounted for as readable but not exercised.

**Rebuild-request flag.** `loc_ac36` [seen] ORs `0x03` into the working flags cell `loc_1c9`, setting its two low request bits, and returns the merged value; the write was observed producing a value with both bits present (`0x7`). This is how the geometry-tracking code asks for both pending blocks to be rebuilt — callers such as the control-snapshot check fall into it on a mismatch, and the request bits it sets are later consumed when the rebuild actually copies the affected blocks. It falls straight through into the shared return at `loc_ac3e`.

**Bare-return stubs and shared tails.** Several of this subsystem's entries are single-`rts` leaves that exist to terminate a branch or fill a dispatch slot; none has a role-defining write, so all carry [code]. `loc_ac07` [code] is the "nothing to rebuild" return: the rebuild-driver tail-branches here when the relevant request bits are clear. `loc_ac3e` [code] is the shared return tail reached when the live geometry snapshot already matches its latch (no rebuild needed) — and, as noted, the fall-through terminator for `loc_ac36`. `loc_af6e` [code] is the exposed return of the `loc_af3f` draw routine, taken when both draw slots (`loc_600` and `loc_601`) are empty and there is nothing to draw. `loc_9bcf` [code] is a do-nothing handler slot in a computed-dispatch table: it returns immediately, letting the caller unwind, and is reachable only through that dispatch rather than a direct call. Because these are pure returns with no memory effect, a write-tap cannot confirm they were reached; they are grounded from the code as no-op leaves, not reached in the capture.

**A constant-returning leaf (proposer trap).** `loc_b955` [code] looks like it computes a bit-count of `loc_57` — it reads that cell, shifts it right four places, and runs an increment/shift/branch loop — but the loop's result is discarded: the tail clears carry and adds 2 to a zeroed accumulator and resets Y to 0, so the routine **always** returns the constant pair `A = 2, Y = 0` regardless of `loc_57`. A blind reading might mis-name it a `log2`/bit-count helper; the code and the logic trace both confirm it is a register-only constant leaf that touches no memory.
